`node:v8` module က Node.js binary ထဲမှာ တည်ဆောက်ထားတဲ့ [V8][] version အတွက် သီးသန့် ဖြစ်တဲ့ APIs တွေကို ထုတ်ဖော် ပံ့ပိုးပေးပါတယ်။ အောက်ပါအတိုင်း ဝင်ရောက်သုံးနိုင်ပါတယ်:
```mjs
import v8 from 'node:v8';
```

```
const v8 = require('node:v8');
```
## `v8.cachedDataVersionTag()`

* Returns: {integer}

V8 version၊ command-line flags နဲ့ detected CPU features တွေကနေ ဆင်းသက်လာတဲ့ (derived) version tag တစ်ခုကို ကိုယ်စားပြုတဲ့ integer တစ်ခုကို ပြန်ပေးပါတယ်။ [`vm.Script`][] ရဲ့ `cachedData` buffer တစ်ခုက ဒီ V8 instance နဲ့ ကိုက်ညီမှု ရှိ/မရှိ ဆုံးဖြတ်ရာမှာ ဒါက အသုံးဝင်ပါတယ်။
```js
console.log(v8.cachedDataVersionTag()); // 3947234607
// The value returned by v8.cachedDataVersionTag() is derived from the V8
// version, command-line flags, and detected CPU features. Test that the value
// does indeed update when flags are toggled.
v8.setFlagsFromString('--allow_natives_syntax');
console.log(v8.cachedDataVersionTag()); // 183726201
```
## `v8.getHeapCodeStatistics()`

* Returns: {Object}

Heap ထဲမှာ ရှိတဲ့ code နဲ့ ၎င်းရဲ့ metadata အကြောင်း statistics တွေကို ရယူပါတယ် — V8 ရဲ့ [`GetHeapCodeAndMetadataStatistics`][] API ကို ကြည့်ပါ။ အောက်ပါ properties တွေ ပါဝင်တဲ့ object တစ်ခုကို ပြန်ပေးပါတယ်:

* `code_and_metadata_size` {number}
* `bytecode_and_metadata_size` {number}
* `external_script_source_size` {number}
* `cpu_profiler_metadata_size` {number}
```json
{
  "code_and_metadata_size": 212208,
  "bytecode_and_metadata_size": 161368,
  "external_script_source_size": 1410794,
  "cpu_profiler_metadata_size": 0
}
```
## `v8.getHeapSnapshot([options])`

* `options` {Object}
  * `exposeInternals` {boolean} `true` ဆိုရင် heap snapshot ထဲမှာ internals တွေကို ထည့်သွင်း ဖော်ပြပါတယ်။ **Default:** `false`။
  * `exposeNumericValues` {boolean} `true` ဆိုရင် artificial fields တွေထဲမှာ numeric values တွေကို ထည့်သွင်း ဖော်ပြပါတယ်။ **Default:** `false`။

* Returns: {stream.Readable} V8 heap snapshot ပါဝင်တဲ့ Readable တစ်ခု။

လက်ရှိ V8 heap ရဲ့ snapshot တစ်ခုကို ထုတ်လုပ်ပြီး — JSON အဖြစ် serialize လုပ်ထားတဲ့ ကိုယ်စားပြုမှုကို ဖတ်ရှုဖို့ သုံးနိုင်တဲ့ Readable Stream တစ်ခုကို ပြန်ပေးပါတယ်။ ဒီ JSON stream format ကို Chrome DevTools လိုမျိုး tools တွေနဲ့ တွဲသုံးဖို့ ရည်ရွယ်ထားပါတယ်။ JSON schema ကတော့ မှတ်တမ်းမပြုစုထားဘဲ V8 engine အတွက် သီးသန့် ဖြစ်ပါတယ်။ ဒါကြောင့် — schema က V8 version တစ်ခုကနေ နောက်တစ်ခုကို ပြောင်းသွားတဲ့အခါ ပြောင်းလဲနိုင်ပါတယ်။

Heap snapshot တစ်ခု ဖန်တီးဖို့က snapshot ဖန်တီးချိန်မှာ heap ရဲ့ အရွယ်အစား နှစ်ဆလောက် ရှိတဲ့ memory လိုအပ်ပါတယ်။ ဒါကြောင့် OOM killers တွေက process ကို terminate လုပ်ပစ်နိုင်တဲ့ အန္တရာယ် ရှိပါတယ်။

Snapshot တစ်ခု ထုတ်လုပ်တာက synchronous operation တစ်ခု ဖြစ်ပြီး — heap ရဲ့ အရွယ်အစားပေါ် မူတည်ပြီး event loop ကို အချိန်အတိုင်းအတာ တစ်ခုအထိ block လုပ်ထားပါတယ်။
```mjs
// Print heap snapshot to the console
import { getHeapSnapshot } from 'node:v8';
import process from 'node:process';
const stream = getHeapSnapshot();
stream.pipe(process.stdout);
```

```
// Print heap snapshot to the console
const v8 = require('node:v8');
const stream = v8.getHeapSnapshot();
stream.pipe(process.stdout);
```

## `v8.getHeapStatistics()`

* Returns: {Object}

အောက်ပါ properties တွေ ပါဝင်တဲ့ object တစ်ခုကို ပြန်ပေးပါတယ်:

* `total_heap_size` {number}
* `total_heap_size_executable` {number}
* `total_physical_size` {number}
* `total_available_size` {number}
* `used_heap_size` {number}
* `heap_size_limit` {number}
* `malloced_memory` {number}
* `peak_malloced_memory` {number}
* `does_zap_garbage` {number}
* `number_of_native_contexts` {number}
* `number_of_detached_contexts` {number}
* `total_global_handles_size` {number}
* `used_global_handles_size` {number}
* `external_memory` {number}
* `total_allocated_bytes` {number}

`total_heap_size` — total\_heap\_size ရဲ့ တန်ဖိုးဆိုတာ heap အတွက် V8 က ခွဲဝေပေးထားတဲ့ (allocate) byte အရေအတွက်ပါ။ used\_heap က memory ပိုလိုအပ်လာရင် ဒီတန်ဖိုး ကြီးထွားနိုင်ပါတယ်။

`total_heap_size_executable` — total\_heap\_size\_executable ရဲ့ တန်ဖိုးဆိုတာ executable code တွေ ပါဝင်နိုင်တဲ့ heap ရဲ့ အစိတ်အပိုင်း ဖြစ်ပြီး — byte နဲ့ ဖော်ပြပါတယ်။ ဒီထဲမှာ JIT-compiled code တွေ သုံးတဲ့ memory ရော၊ executable အဖြစ် ထိန်းသိမ်းထားရမယ့် memory တွေပါ ပါဝင်ပါတယ်။

`total_physical_size` — total\_physical\_size ရဲ့ တန်ဖိုးဆိုတာ V8 heap က သုံးနေတဲ့ အမှန်တကယ် physical memory ပမာဏ ဖြစ်ပြီး — byte နဲ့ ဖော်ပြပါတယ်။ ဒါက reserve လုပ်ထားရုံသာမက — commit လုပ်ထား (သို့) အသုံးပြုနေတဲ့ memory ပမာဏ ဖြစ်ပါတယ်။

`total_available_size` — total\_available\_size ရဲ့ တန်ဖိုးဆိုတာ V8 heap အတွက် ရရှိနိုင်တဲ့ memory ရဲ့ byte အရေအတွက်ပါ။ ဒီတန်ဖိုးက — V8 က heap limit ကို မကျော်ခင် နောက်ထပ် memory ဘယ်လောက် သုံးနိုင်သေးလဲ ဆိုတာကို ဖော်ပြပါတယ်။

`used_heap_size` — used\_heap\_size ရဲ့ တန်ဖိုးဆိုတာ V8 ရဲ့ JavaScript objects တွေက လက်ရှိ သုံးနေတဲ့ byte အရေအတွက်ပါ။ ဒါက အမှန်တကယ် အသုံးပြုနေတဲ့ memory ဖြစ်ပြီး — allocate လုပ်ထားပေမယ့် မသုံးရသေးတဲ့ memory တွေ မပါဝင်ပါဘူး။

`heap_size_limit` — heap\_size\_limit ရဲ့ တန်ဖိုးဆိုတာ V8 heap ရဲ့ အများဆုံး အရွယ်အစား ဖြစ်ပြီး — byte နဲ့ ဖော်ပြပါတယ် (system resources တွေကို ကြည့်ပြီး သတ်မှတ်တဲ့ default limit ဖြစ်စေ၊ `--max_old_space_size` option ဆီ ပေးလိုက်တဲ့ တန်ဖိုး ဖြစ်စေ)။

`malloced_memory` — malloced\_memory ရဲ့ တန်ဖိုးဆိုတာ V8 က `malloc` ကနေတစ်ဆင့် ခွဲဝေပေးထားတဲ့ byte အရေအတွက်ပါ။

`peak_malloced_memory` — peak\_malloced\_memory ရဲ့ တန်ဖိုးဆိုတာ process ရဲ့ သက်တမ်းအတွင်း V8 က `malloc` ကနေတစ်ဆင့် ခွဲဝေပေးခဲ့တဲ့ byte တွေရဲ့ အမြင့်ဆုံး (peak) အရေအတွက်ပါ။

`does_zap_garbage` — 0/1 boolean တစ်ခု ဖြစ်ပြီး — `--zap_code_space` option ကို enable လုပ်ထား/မထား ဆိုတာကို ဖော်ပြပါတယ်။ ဒါက V8 ကို heap ထဲက garbage တွေကို bit pattern တစ်ခုနဲ့ ပြန်ရေး (overwrite) လုပ်စေပါတယ်။ RSS footprint (resident set size) က ပိုကြီးလာပါတယ် — ဘာလို့လဲဆိုတော့ heap pages အားလုံးကို အဆက်မပြတ် ထိမိနေလို့ operating system က အဲဒါတွေကို swap ထုတ်ပစ်ဖို့ အလားအလာ နည်းသွားလို့ပါ။

`number_of_native_contexts` — native\_context ရဲ့ တန်ဖိုးဆိုတာ လက်ရှိ လှုပ်ရှားနေတဲ့ (active) top-level contexts အရေအတွက်ပါ။ ဒီဂဏန်း အချိန်ကြာလာတာနဲ့အမျှ တက်လာတာက memory leak ရှိတယ်ဆိုတဲ့ အရိပ်အယောင် ဖြစ်ပါတယ်။

`number_of_detached_contexts` — detached\_context ရဲ့ တန်ဖိုးဆိုတာ detach လုပ်ထားပြီး garbage collected မဖြစ်ရသေးတဲ့ contexts အရေအတွက်ပါ။ ဒီဂဏန်း သုည မဟုတ်ဘူးဆိုရင် — memory leak ဖြစ်နိုင်ခြေ ရှိတယ်လို့ ညွှန်ပြနေတာပါ။

`total_global_handles_size` — total\_global\_handles\_size ရဲ့ တန်ဖိုးဆိုတာ V8 global handles တွေရဲ့ စုစုပေါင်း memory အရွယ်အစားပါ။

`used_global_handles_size` — used\_global\_handles\_size ရဲ့ တန်ဖိုးဆိုတာ V8 global handles တွေရဲ့ အသုံးပြုနေတဲ့ memory အရွယ်အစားပါ။

`external_memory` — external\_memory ရဲ့ တန်ဖိုးဆိုတာ array buffers နဲ့ external strings တွေရဲ့ memory အရွယ်အစားပါ။

`total_allocated_bytes` — Isolate ကို ဖန်တီးပြီးကတည်းက စုစုပေါင်း allocated bytes ရဲ့ တန်ဖိုးပါ။
```json
{
  "total_heap_size": 7326976,

  "total_physical_size": 7326976,
  "total_available_size": 1152656,
```

## `v8.getCppHeapStatistics([detailLevel])`

[CppHeap][] ရဲ့ — memory သုံးစွဲမှုနဲ့ အသုံးချမှု (utilization) ဆိုင်ရာ statistics တွေကို V8 ရဲ့ [`CollectStatistics()`][] function ကို သုံးပြီး ရယူပါတယ် — ဒီ function က V8 version တစ်ခုကနေ နောက်တစ်ခုကို ပြောင်းတဲ့အခါ ပြောင်းလဲနိုင်ပါတယ်။

* `detailLevel` {string|undefined}: **Default:** `'detailed'`။
  ပြန်ပေးတဲ့ statistics တွေထဲက အသေးစိတ် အဆင့်ကို သတ်မှတ်ပါတယ်။ လက်ခံနိုင်တဲ့ တန်ဖိုးတွေကတော့:
  * `'brief'`: Brief statistics တွေမှာ heap တစ်ခုလုံးအတွက် အဆင့်မြင့် (top-level) allocated နဲ့ used
    memory statistics တွေပဲ ပါဝင်ပါတယ်။
  * `'detailed'`: Detailed statistics တွေမှာ space နဲ့ page အလိုက် ခွဲခြမ်းစိတ်ဖြာမှု အပြင် —
    freelist statistics တွေနဲ့ object type histograms တွေပါ ပါဝင်ပါတယ်။

## `v8.queryObjects(ctor[, options])`

* `ctor` {Function} Heap ထဲက target objects တွေကို စစ်ထုတ်ဖို့ prototype chain ပေါ်မှာ ရှာဖွေဖို့ သုံးနိုင်တဲ့ constructor ပါ။
* `options` {undefined|Object}
  * `format` {string} `'count'` ဆိုရင် — ကိုက်ညီတဲ့ (matched) objects တွေရဲ့ အရေအတွက်ကို ပြန်ပေးပါတယ်။ `'summary'` ဆိုရင် — ကိုက်ညီတဲ့ objects တွေရဲ့ summary strings တွေ ပါဝင်တဲ့ array တစ်ခုကို ပြန်ပေးပါတယ်။
* Returns: {number|string\[]}

ဒါက Chromium DevTools console က ပံ့ပိုးပေးတဲ့ [`queryObjects()` console API][] နဲ့ ဆင်တူပါတယ်။ Full garbage collection တစ်ခု ပြီးပြီးနောက် — prototype chain ပေါ်မှာ ကိုက်ညီတဲ့ constructor ပါတဲ့ objects တွေကို heap ထဲမှာ ရှာဖွေဖို့ သုံးနိုင်ပြီး — memory leak regression tests တွေအတွက် အသုံးဝင်နိုင်ပါတယ်။ အံ့အားသင့်စရာ ရလဒ်တွေ မဖြစ်စေဖို့ — user တွေက ကိုယ်တိုင် ထိန်းချုပ်မထားတဲ့ implementation ရှိတဲ့ constructors တွေပေါ်မှာ (သို့) application ထဲက တခြား ပါတီများက ခေါ်ယူနိုင်တဲ့ constructors တွေပေါ်မှာ ဒီ API ကို သုံးတာ ရှောင်သင့်ပါတယ်။

မရည်ရွယ်ဘဲ ယိုစိမ့်မှုတွေ (accidental leaks) မဖြစ်စေဖို့ — ဒီ API က တွေ့ရှိရတဲ့ objects တွေရဲ့ raw references တွေကို ပြန်မပေးပါဘူး။ မူလအားဖြင့် တွေ့ရှိရတဲ့ objects တွေရဲ့ အရေအတွက်ကို ပြန်ပေးပါတယ်။ `options.format` က `'summary'` ဆိုရင် — object တစ်ခုချင်းစီအတွက် အတိုချုပ် string representations တွေ ပါဝင်တဲ့ array တစ်ခုကို ပြန်ပေးပါတယ်။ ဒီ API မှာ ရရှိနိုင်တဲ့ မြင်နိုင်မှု (visibility) က heap snapshot က ပေးတဲ့အတိုင်း ဆင်တူပြီး — user တွေက serialization နဲ့ parsing ရဲ့ ကုန်ကျစရိတ်ကို သက်သာစေပြီး — ရှာဖွေနေစဉ်အတွင်း target objects တွေကို တိုက်ရိုက် စစ်ထုတ်နိုင်ပါတယ်။

ရလဒ်တွေထဲမှာ လက်ရှိ execution context ထဲမှာ ဖန်တီးထားတဲ့ objects တွေပဲ ပါဝင်ပါတယ်။
```cjs

console.log(queryObjects(A)); // 0
```

## `v8.setFlagsFromString(flags)`

* `flags` {string}

`v8.setFlagsFromString()` method ကို V8 command-line flags တွေကို programmatically သတ်မှတ်ဖို့ သုံးနိုင်ပါတယ်။ ဒီ method ကို သတိထားပြီး သုံးသင့်ပါတယ်။ VM စတင်ပြီးမှ settings တွေ ပြောင်းလိုက်ရင် — crashes နဲ့ data loss အပါအဝင် ခန့်မှန်းရခက်တဲ့ အပြုအမူတွေ ဖြစ်စေနိုင်သလို — ဘာမှ မလုပ်ဘဲလည်း နေနိုင်ပါတယ်။

Node.js version တစ်ခုအတွက် ရနိုင်တဲ့ V8 options တွေကို `node --v8-options` run လုပ်ပြီး သိနိုင်ပါတယ်။

အသုံးပြုပုံ:
```mjs
import { setFlagsFromString } from 'node:v8';
import { setInterval } from 'node:timers';

// setFlagsFromString to trace garbage collection events
setFlagsFromString('--trace-gc');

// Trigger GC events by using some memory
let arrays = [];
const interval = setInterval(() => {
  for (let i = 0; i < 500; i++) {
    arrays.push(new Array(10000).fill(Math.random()));
  }

  if (arrays.length > 5000) {
    arrays = arrays.slice(-1000);
  }

  console.log(`\n* Created ${arrays.length} arrays\n`);
}, 100);

// setFlagsFromString to stop tracing GC events after 1.5 seconds
setTimeout(() => {
  setFlagsFromString('--notrace-gc');
  console.log('\nStopped tracing!\n');
}, 1500);

// Stop triggering GC events altogether after 2.5 seconds
setTimeout(() => {
  clearInterval(interval);
}, 2500);
```

## `v8.stopCoverage()`

`v8.stopCoverage()` method က [`NODE_V8_COVERAGE`][] နဲ့ စတင်ထားတဲ့ coverage collection ကို ရပ်တန့်ဖို့ user ကို ခွင့်ပြုပါတယ် — ဒါမှ V8 က execution count records တွေကို လွှတ်ပေးပြီး code တွေကို optimize လုပ်နိုင်မှာ ဖြစ်ပါတယ်။ Coverage ကို လိုအပ်သလို (on demand) စုဆောင်းချင်ရင် [`v8.takeCoverage()`][] နဲ့ တွဲသုံးနိုင်ပါတယ်။

## `v8.takeCoverage()`

`v8.takeCoverage()` method က [`NODE_V8_COVERAGE`][] နဲ့ စတင်ထားတဲ့ coverage ကို လိုအပ်သလို disk ပေါ်ကို ရေးထုတ်ဖို့ user ကို ခွင့်ပြုပါတယ်။ ဒီ method ကို process ရဲ့ သက်တမ်းအတွင်း အကြိမ်များစွာ ခေါ်နိုင်ပါတယ်။ အကြိမ်တိုင်းမှာ execution counter ကို ပြန်လည် သတ်မှတ်ပြီး — [`NODE_V8_COVERAGE`][] မှာ သတ်မှတ်ထားတဲ့ directory ထဲကို coverage report အသစ်တစ်ခု ရေးသားမှာ ဖြစ်ပါတယ်။

Process က ထွက်တော့မယ့် အချိန်မှာ — process မထွက်ခင် [`v8.stopCoverage()`][] ကို ခေါ်မထားဘူးဆိုရင် — နောက်ဆုံး coverage တစ်ခုကို disk ပေါ် ထပ်ရေးသွားပါဦးမယ်။

## `v8.writeHeapSnapshot([filename[,options]])`

* `filename` {string} V8 heap snapshot ကို သိမ်းမယ့် file path ပါ။ သတ်မှတ်မပေးထားဘူးဆိုရင် — `'Heap-${yyyymmdd}-${hhmmss}-${pid}-${thread_id}.heapsnapshot'` ဆိုတဲ့ ပုံစံနဲ့ file name တစ်ခုကို ထုတ်ပေးပါလိမ့်မယ် — အဲဒီမှာ `{pid}` က Node.js process ရဲ့ PID ဖြစ်ပြီး၊ `{thread_id}` ကတော့ `writeHeapSnapshot()` ကို main Node.js thread ကနေ ခေါ်ရင် `0` ဖြစ်ပြီး — worker thread တစ်ခုကနေ ခေါ်ရင်တော့ အဲဒီ worker thread ရဲ့ id ဖြစ်ပါတယ်။
* `options` {Object}
  * `exposeInternals` {boolean} `true` ဆိုရင် heap snapshot ထဲမှာ internals တွေကို ထည့်သွင်း ဖော်ပြပါတယ်။ **Default:** `false`။
  * `exposeNumericValues` {boolean} `true` ဆိုရင် artificial fields တွေထဲမှာ numeric values တွေကို ထည့်သွင်း ဖော်ပြပါတယ်။ **Default:** `false`။
* Returns: {string} Snapshot ကို သိမ်းလိုက်တဲ့ filename ပါ။

လက်ရှိ V8 heap ရဲ့ snapshot တစ်ခုကို ထုတ်လုပ်ပြီး JSON file တစ်ခုအနေနဲ့ ရေးသားပါတယ်။ ဒီ file ကို Chrome DevTools လိုမျိုး tools တွေနဲ့ တွဲသုံးဖို့ ရည်ရွယ်ထားပါတယ်။ JSON schema ကတော့ မှတ်တမ်းမပြုစုထားဘဲ V8 engine အတွက် သီးသန့် ဖြစ်ပြီး — V8 version တစ်ခုကနေ နောက်တစ်ခုကို ပြောင်းတဲ့အခါ ပြောင်းလဲနိုင်ပါတယ်။

Heap snapshot တစ်ခုက V8 isolate တစ်ခုတည်းအတွက် သီးသန့် ဖြစ်ပါတယ်။ [worker threads][] တွေ သုံးနေတဲ့အခါ — main thread ကနေ ထုတ်ထားတဲ့ heap snapshot ထဲမှာ workers တွေအကြောင်း ဘာအချက်အလက်မှ ပါမှာ မဟုတ်သလို — အပြန်အလှန်အားဖြင့်လည်း ထိုနည်းတူပါ။

Heap snapshot တစ်ခု ဖန်တီးဖို့က snapshot ဖန်တီးချိန်မှာ heap ရဲ့ အရွယ်အစား နှစ်ဆလောက် ရှိတဲ့ memory လိုအပ်ပါတယ်။ ဒါကြောင့် OOM killers တွေက process ကို terminate လုပ်ပစ်နိုင်တဲ့ အန္တရာယ် ရှိပါတယ်။

Snapshot တစ်ခု ထုတ်လုပ်တာက synchronous operation တစ်ခု ဖြစ်ပြီး — heap ရဲ့ အရွယ်အစားပေါ် မူတည်ပြီး event loop ကို အချိန်အတိုင်းအတာ တစ်ခုအထိ block လုပ်ထားပါတယ်။
```mjs
import { writeHeapSnapshot } from 'node:v8';
import { Worker, isMainThread, parentPort } from 'node:worker_threads';
import { fileURLToPath } from 'node:url';

if (isMainThread) {
  const __filename = fileURLToPath(import.meta.url);
  const worker = new Worker(__filename);

  worker.once('message', (filename) => {
    console.log(`worker heapdump: ${filename}`);
    // Now get a heapdump for the main thread.
    console.log(`main thread heapdump: ${writeHeapSnapshot()}`);
  });

  // Tell the worker to create a heapdump.
  worker.postMessage('heapdump');
} else {
  parentPort.once('message', (message) => {
    if (message === 'heapdump') {
      // Generate a heapdump for the worker
      // and return the filename to the parent.
      parentPort.postMessage(writeHeapSnapshot());
    }
  });
}
```

## Serialization API (JavaScript values များကို serialize/deserialize ပြုလုပ်ရန် API)

Serialization API က JavaScript values တွေကို — [HTML structured clone algorithm][] နဲ့ လိုက်ဖက်ညီတဲ့ နည်းလမ်းနဲ့ — serialize လုပ်ဖို့ နည်းလမ်းတွေကို ပံ့ပိုးပေးပါတယ်။

ဒီ format က backward-compatible (နောက်ပြန် လိုက်ဖက်ညီ) ဖြစ်ပါတယ် (ဆိုလိုတာက disk ပေါ်မှာ သိမ်းဆည်းဖို့ လုံခြုံပါတယ်)။ တူညီတဲ့ JavaScript values တွေက မတူညီတဲ့ serialized output တွေ ဖြစ်သွားနိုင်ပါတယ်။

### `v8.serialize(value)`

* `value` {any}
* Returns: {Buffer}

[`DefaultSerializer`][] ကို သုံးပြီး `value` ကို buffer တစ်ခုအဖြစ် serialize လုပ်ပါတယ်။

[`buffer.constants.MAX_LENGTH`][] ထက် ကြီးတဲ့ buffer လိုအပ်တဲ့ ကြီးမားတဲ့ object တစ်ခုကို serialize လုပ်ဖို့ ကြိုးစားတဲ့အခါ [`ERR_BUFFER_TOO_LARGE`][] ကို throw လုပ်ပါလိမ့်မယ်။

### `v8.deserialize(buffer)`

* `buffer` {Buffer|TypedArray|DataView} [`serialize()`][] က ပြန်ပေးထားတဲ့ buffer တစ်ခု။

Default options တွေနဲ့ [`DefaultDeserializer`][] ကို သုံးပြီး buffer တစ်ခုကနေ JS value တစ်ခုကို ဖတ်ယူပါတယ်။

### Class: `v8.Serializer`

#### `new Serializer()`

`Serializer` object အသစ်တစ်ခုကို ဖန်တီးပါတယ်။

#### `serializer.writeHeader()`

Serialization format version အပါအဝင် header တစ်ခုကို ရေးထုတ်ပါတယ်။

#### `serializer.writeValue(value)`

* `value` {any}

JavaScript value တစ်ခုကို serialize လုပ်ပြီး — internal buffer ထဲကို serialized ကိုယ်စားပြုမှုကို ထည့်သွင်းပေးပါတယ်။

`value` ကို serialize လုပ်လို့ မရဘူးဆိုရင် error တစ်ခုကို throw လုပ်ပါတယ်။

#### `serializer.releaseBuffer()`

* Returns: {Buffer}

သိမ်းထားတဲ့ internal buffer ကို ပြန်ပေးပါတယ်။ Buffer ကို လွှတ်လိုက်ပြီဆိုရင် ဒီ serializer ကို နောက်ထပ် မသုံးသင့်ပါဘူး။ အရင် write တစ်ခု မအောင်မြင်ခဲ့ဘူးဆိုရင် ဒီ method ကို ခေါ်မိခြင်းက undefined behavior ဖြစ်ပါတယ်။

#### `serializer.transferArrayBuffer(id, arrayBuffer)`

* `id` {integer} 32-bit unsigned integer တစ်ခု။
* `arrayBuffer` {ArrayBuffer} `ArrayBuffer` instance တစ်ခု။

`ArrayBuffer` တစ်ခုကို — ၎င်းရဲ့ contents တွေ out of band (သီးခြား လမ်းကြောင်းနဲ့) transfer လုပ်တာ ဖြစ်ကြောင်း — အမှတ်အသား လုပ်ပါတယ်။ Deserializing လုပ်နေတဲ့ context ထဲမှာ သက်ဆိုင်ရာ `ArrayBuffer` ကို [`deserializer.transferArrayBuffer()`][] ဆီ ပေးပို့ပါ။

#### `serializer.writeUint32(value)`

* `value` {integer}

Raw 32-bit unsigned integer တစ်ခုကို ရေးပါတယ်။ Custom [`serializer._writeHostObject()`][] တစ်ခုရဲ့ အတွင်းမှာ သုံးဖို့ ဖြစ်ပါတယ်။

#### `serializer.writeUint64(hi, lo)`

* `hi` {integer}
* `lo` {integer}

Raw 64-bit unsigned integer တစ်ခုကို — high နဲ့ low 32-bit parts နှစ်ပိုင်း ခွဲပြီး — ရေးပါတယ်။ Custom [`serializer._writeHostObject()`][] တစ်ခုရဲ့ အတွင်းမှာ သုံးဖို့ ဖြစ်ပါတယ်။

#### `serializer.writeDouble(value)`

* `value` {number}

JS `number` value တစ်ခုကို ရေးပါတယ်။ Custom [`serializer._writeHostObject()`][] တစ်ခုရဲ့ အတွင်းမှာ သုံးဖို့ ဖြစ်ပါတယ်။

#### `serializer.writeRawBytes(buffer)`

* `buffer` {Buffer|TypedArray|DataView}

Raw bytes တွေကို serializer ရဲ့ internal buffer ထဲကို ရေးပါတယ်။ Deserializer ဘက်က buffer ရဲ့ အလျားကို တွက်ချက်ဖို့ နည်းလမ်းတစ်ခု လိုအပ်ပါလိမ့်မယ်။ Custom [`serializer._writeHostObject()`][] တစ်ခုရဲ့ အတွင်းမှာ သုံးဖို့ ဖြစ်ပါတယ်။

#### `serializer._writeHostObject(object)`

* `object` {Object}

ဒီ method ကို host object တစ်မျိုးမျိုး — ဆိုလိုတာက native C++ bindings တွေက ဖန်တီးတဲ့ object — ရေးဖို့ ခေါ်ပါတယ်။ `object` ကို serialize လုပ်ဖို့ မဖြစ်နိုင်ဘူးဆိုရင် သင့်တော်တဲ့ exception တစ်ခုကို throw သင့်ပါတယ်။

ဒီ method က `Serializer` class ပေါ်မှာ ကိုယ်တိုင် မရှိပါဘူး — subclasses တွေက ပံ့ပိုးပေးနိုင်ပါတယ်။

ဒီ method က default အားဖြင့် [`Error`][] constructor ကို သုံးပြီး — subclasses တွေပေါ်မှာ override လုပ်နိုင်ပါတယ်။

#### `serializer._getSharedArrayBufferId(sharedArrayBuffer)`

* `sharedArrayBuffer` {SharedArrayBuffer}

Serializer က `SharedArrayBuffer` object တစ်ခုကို serialize လုပ်တော့မယ့်အခါ ဒီ method ကို ခေါ်ပါတယ်။ ဒီ object အတွက် unsigned 32-bit integer ID တစ်ခုကို ပြန်ပေးရပါမယ် — ဒီ `SharedArrayBuffer` ကို အရင်က serialize လုပ်ပြီးသား ဖြစ်နေရင် တူညီတဲ့ ID ကိုပဲ သုံးရပါမယ်။ Deserializing လုပ်တဲ့အခါ ဒီ ID ကို [`deserializer.transferArrayBuffer()`][] ဆီ ပေးပို့ပါလိမ့်မယ်။

Object ကို serialize လုပ်လို့ မရဘူးဆိုရင် exception တစ်ခုကို throw သင့်ပါတယ်။

ဒီ method က `Serializer` class ပေါ်မှာ ကိုယ်တိုင် မရှိပါဘူး — subclasses တွေက ပံ့ပိုးပေးနိုင်ပါတယ်။

#### `serializer._setTreatArrayBufferViewsAsHostObjects(flag)`

* `flag` {boolean} **Default:** `false`

`TypedArray` နဲ့ `DataView` objects တွေကို host objects တွေအဖြစ် — ဆိုလိုတာက [`serializer._writeHostObject()`][] ဆီ ပေးပို့ပြီး — သဘောထား/မထား ဆိုတာကို ညွှန်ပြပါတယ်။

## Promise hooks (promise များ၏ lifecycle events များကို ခြေရာခံရန်)

`promiseHooks` interface ကို promise lifecycle events တွေကို ခြေရာခံဖို့ သုံးနိုင်ပါတယ်။ async activity အားလုံးကို ခြေရာခံချင်ရင်တော့ [`async_hooks`][] ကို ကြည့်ပါ — သူက ဒီ module ကို အတွင်းပိုင်းမှာ သုံးပြီး — တခြား async resources တွေရဲ့ events တွေအပြင် promise lifecycle events တွေကိုပါ ထုတ်ပေးတာပါ။ Request context management အတွက်ကတော့ [`AsyncLocalStorage`][] ကို ကြည့်ပါ။
```mjs
import { promiseHooks } from 'node:v8';

// There are four lifecycle events produced by promises:

// The `init` event represents the creation of a promise. This could be a
// direct creation such as with `new Promise(...)` or a continuation such
// as `then()` or `catch()`. It also happens whenever an async function is
// called or does an `await`. If a continuation promise is created, the
// `parent` will be the promise it is a continuation from.
function init(promise, parent) {
  console.log('a promise was created', { promise, parent });
}

// The `settled` event happens when a promise receives a resolution or
// rejection value. This may happen synchronously such as when using
// `Promise.resolve()` on non-promise input.
function settled(promise) {
  console.log('a promise resolved or rejected', { promise });
}

// The `before` event runs immediately before a `then()` or `catch()` handler
// runs or an `await` resumes execution.
function before(promise) {
  console.log('a promise is about to call a then handler', { promise });
}

// The `after` event runs immediately after a `then()` handler runs or when
// an `await` begins after resuming from another.
function after(promise) {
  console.log('a promise is done calling a then handler', { promise });
}

// Lifecycle hooks may be started and stopped individually
const stopWatchingInits = promiseHooks.onInit(init);
const stopWatchingSettleds = promiseHooks.onSettled(settled);
const stopWatchingBefores = promiseHooks.onBefore(before);
const stopWatchingAfters = promiseHooks.onAfter(after);

// Or they may be started and stopped in groups
const stopHookSet = promiseHooks.createHook({
  init,
  settled,
  before,
  after,
});

// Trigger the hooks by using promises
const promiseLog = (word) => Promise.resolve(word).then(console.log);
promiseLog('Hello');
promiseLog('World');

// To stop a hook, call the function returned at its creation.
stopWatchingInits();
stopWatchingSettleds();
stopWatchingBefores();
stopWatchingAfters();
stopHookSet();
```

**Hook callbacks တွေက plain functions တွေ ဖြစ်ရပါမယ်။ Async functions တွေ ပေးလိုက်ရင် — infinite microtask loop (အဆုံးမဲ့ microtask သံသရာ) ဖြစ်ပေါ်စေတာမို့ — throw လုပ်ပါလိမ့်မယ်။**

Promise တစ်ခုချင်းစီရဲ့ မတူညီတဲ့ lifetime events တွေမှာ ခေါ်ယူမယ့် functions တွေကို register (မှတ်ပုံတင်) လုပ်ပေးပါတယ်။

`init()`/`before()`/`after()`/`settled()` callbacks တွေကို promise တစ်ခုရဲ့ သက်တမ်းအတွင်း သက်ဆိုင်ရာ events တွေ ဖြစ်ပေါ်တဲ့အခါ ခေါ်ပါတယ်။

Callbacks တွေအားလုံးက optional ပါ။ ဥပမာ — promise ဖန်တီးမှုကိုပဲ ခြေရာခံချင်တယ်ဆိုရင် `init` callback တစ်ခုတည်းကိုပဲ ပေးလိုက်ရင် ရပါတယ်။ `callbacks` ထဲ ပေးလို့ရတဲ့ functions အားလုံးရဲ့ အသေးစိတ်ကို [Hook Callbacks][] section မှာ ဖော်ပြထားပါတယ်။
```mjs

const stopAll = promiseHooks.createHook({
  init(promise, parent) {},
});
```

### Hook callbacks (hook ၏ callbacks များ)

Promise တစ်ခုရဲ့ သက်တမ်းထဲက အဓိက ဖြစ်ရပ်တွေကို ကဏ္ဍ လေးခု ခွဲထားပါတယ်: promise ဖန်တီးခြင်း၊ continuation handler တစ်ခုကို ခေါ်တဲ့အခါ (သို့) await တစ်ခု ဝန်းကျင်မှာ before/after ဖြစ်ရပ်တွေ၊ နဲ့ promise resolve (သို့) reject ဖြစ်ချိန် တို့ပါ။

ဒီ hooks တွေက [`async_hooks`][] ရဲ့ hooks တွေနဲ့ ဆင်တူပေမယ့် — `destroy` hook တော့ မပါပါဘူး။ တခြား async resources အမျိုးအစားတွေက ပုံမှန်အားဖြင့် sockets (သို့) file descriptors တွေကို ကိုယ်စားပြုပြီး — `destroy` lifecycle event ကို ဖော်ပြဖို့ သီးခြား "closed" state တစ်ခု ရှိပါတယ်။ Promises တွေကတော့ code က သူတို့ဆီ ရောက်ရှိနိုင်သရွေ့ အသုံးပြုနိုင်ဆဲ ဖြစ်နေပါတယ်။ Promises တွေကို `async_hooks` event model ထဲကို လိုက်ဖက်အောင် ထည့်သွင်းနိုင်ဖို့ garbage collection tracking ကို သုံးပါတယ် — ဒါပေမယ့် ဒီ tracking က အလွန် စျေးကြီးပြီး — သူတို့က တကယ်တမ်း garbage collected ဖြစ်ချင်မှလည်း ဖြစ်နိုင်ပါတယ်။

Promises တွေက သူတို့ရဲ့ lifecycle ကို promise hooks mechanism ကနေ ခြေရာခံခံရတဲ့ asynchronous resources တွေ ဖြစ်တာမို့ — `init()`, `before()`, `after()`, နဲ့ `settled()` callbacks တွေက async functions တွေ _မဖြစ်ရပါဘူး_ — ဘာလို့လဲဆိုတော့ သူတို့က promise တွေ ထပ်ဖန်တီးပြီး infinite loop ဖြစ်စေလို့ပါ။

ဒီ API က promise events တွေကို [`async_hooks`][] ထဲကို ပို့ပေးဖို့ သုံးပေမယ့် — နှစ်ခုကြားက အစီအစဉ် (ordering) ကတော့ သတ်မှတ်မထားပါဘူး။ APIs နှစ်ခုလုံးက multi-tenant ဖြစ်တာမို့ — တစ်ခုနဲ့တစ်ခု နှိုင်းယှဉ်ရင် events တွေက ဘယ်လို အစီအစဉ်နဲ့မဆို ထွက်နိုင်ပါတယ်။

#### `init(promise, parent)`

* `promise` {Promise} ဖန်တီးနေတဲ့ promise။
* `parent` {Promise} ရှိခဲ့ရင် — ဆက်လုပ်တဲ့ (continued from) promise။

Promise တစ်ခုကို တည်ဆောက်တဲ့အခါ ခေါ်ပါတယ်။ ဒါက သက်ဆိုင်ရာ `before`/`after` events တွေ ဖြစ်ပေါ်လာမယ်လို့ ဆိုလိုတာ _မဟုတ်ပါဘူး_ — ဖြစ်နိုင်ခြေ ရှိတယ်ဆိုတာကိုပဲ ဆိုလိုပါတယ်။ Promise တစ်ခုကို continuation တစ်ခုမှ မရဘဲ ဖန်တီးလိုက်ရင် ဒီလို ဖြစ်တတ်ပါတယ်။

#### `before(promise)`

* `promise` {Promise}

Promise continuation တစ်ခု execute မလုပ်ခင် ခေါ်ပါတယ်။ ဒါက `then()`, `catch()`, (သို့) `finally()` handlers တွေ (သို့) `await` တစ်ခု ပြန်လည် စတင်ခြင်းတွေရဲ့ ပုံစံနဲ့ ဖြစ်နိုင်ပါတယ်။

`before` callback ကို 0 ကနေ N ကြိမ်အထိ ခေါ်နိုင်ပါတယ်။ Promise အတွက် continuation တစ်ခုမှ မလုပ်ခဲ့ဘူးဆိုရင် `before` callback ကို ပုံမှန်အားဖြင့် 0 ကြိမ်ပဲ ခေါ်ပါလိမ့်မယ်။ တူညီတဲ့ promise တစ်ခုကနေ continuations အများကြီး လုပ်ထားတဲ့ အခြေအနေမှာတော့ `before` callback ကို အကြိမ်များစွာ ခေါ်နိုင်ပါတယ်။

#### `after(promise)`

* `promise` {Promise}

Promise continuation တစ်ခု execute လုပ်ပြီးချင်း ချက်ချင်း ခေါ်ပါတယ်။ ဒါက `then()`, `catch()`, (သို့) `finally()` handler တစ်ခု ပြီးဆုံးပြီးနောက်မှာ (သို့) နောက် `await` တစ်ခုရဲ့ ရှေ့မှာ ဖြစ်နိုင်ပါတယ်။

#### `settled(promise)`

* `promise` {Promise}

Promise က resolution (သို့) rejection value တစ်ခု ရတဲ့အခါ ခေါ်ပါတယ်။ `Promise.resolve()` (သို့) `Promise.reject()` တို့လိုမျိုး နေရာတွေမှာ synchronous အနေနဲ့လည်း ဖြစ်ပေါ်နိုင်ပါတယ်။

## Startup Snapshot API (startup snapshot ဆိုင်ရာ API)

`v8.startupSnapshot` interface ကို — custom startup snapshots တွေအတွက် serialization နဲ့ deserialization hooks တွေ ထည့်သွင်းဖို့ — သုံးနိုင်ပါတယ်။
```console
$ node --snapshot-blob snapshot.blob --build-snapshot entry.js
# This launches a process with the snapshot
$ node --snapshot-blob snapshot.blob
```
အပေါ်က ဥပမာမှာ — `entry.js` က serialization လုပ်နေစဉ်အတွင်း custom objects တွေရဲ့ အချက်အလက်တွေကို snapshot ထဲမှာ ဘယ်လို သိမ်းဆည်းမလဲ၊ ပြီးတော့ snapshot ကို deserialization လုပ်တဲ့အခါ အဲဒီ objects တွေကို ထပ်တူကျအောင် (synchronize) လုပ်ဖို့ အဲဒီ အချက်အလက်တွေကို ဘယ်လို သုံးမလဲ ဆိုတာ သတ်မှတ်ဖို့ `v8.startupSnapshot` interface ထဲက methods တွေကို သုံးနိုင်ပါတယ်။ ဥပမာ — `entry.js` မှာ အောက်ပါ script ပါရှိတယ်ဆိုရင်:
```cjs
const fs = require('node:fs');
const zlib = require('node:zlib');
const path = require('node:path');
const assert = require('node:assert');

const v8 = require('node:v8');

class BookShelf {
  storage = new Map();

  // Reading a series of files from directory and store them into storage.
  constructor(directory, books) {
    for (const book of books) {
      this.storage.set(book, fs.readFileSync(path.join(directory, book)));
    }
  }

  static compressAll(shelf) {
    for (const [ book, content ] of shelf.storage) {
      shelf.storage.set(book, zlib.gzipSync(content));
    }
  }

  static decompressAll(shelf) {
    for (const [ book, content ] of shelf.storage) {
      shelf.storage.set(book, zlib.gunzipSync(content));
    }
  }
}

// __dirname here is where the snapshot script is placed
// during snapshot building time.
const shelf = new BookShelf(__dirname, [
  'book1.en_US.txt',
  'book1.es_ES.txt',
  'book2.zh_CN.txt',
]);

assert(v8.startupSnapshot.isBuildingSnapshot());
// On snapshot serialization, compress the books to reduce size.
v8.startupSnapshot.addSerializeCallback(BookShelf.compressAll, shelf);
// On snapshot deserialization, decompress the books.
v8.startupSnapshot.addDeserializeCallback(BookShelf.decompressAll, shelf);
v8.startupSnapshot.setDeserializeMainFunction((shelf) => {
  // process.env and process.argv are refreshed during snapshot
  // deserialization.
  const lang = process.env.BOOK_LANG || 'en_US';
  const book = process.argv[1];
  const name = `${book}.${lang}.txt`;
  console.log(shelf.storage.get(name));
}, shelf);
```
ရလာတဲ့ binary က စတင်ချိန်မှာ — စတင်လိုက်တဲ့ process ရဲ့ အသစ်ပြန်လည် သတ်မှတ်ပေးထားတဲ့ (refreshed) `process.env` နဲ့ `process.argv` တွေကို သုံးပြီး — snapshot ကနေ deserialize လုပ်လိုက်တဲ့ data ကို ပုံနှိပ်ထုတ်ပေးမှာ ဖြစ်ပါတယ်:
```console
$ BOOK_LANG=es_ES node --snapshot-blob snapshot.blob book1
# Prints content of book1.es_ES.txt deserialized from the snapshot.
```
လောလောဆယ် user-land snapshot တစ်ခုကနေ deserialize လုပ်ထားတဲ့ application ကို နောက်တစ်ကြိမ် snapshotted လုပ်လို့ မရပါဘူး။ ဒါကြောင့် ဒီ APIs တွေက user-land snapshot တစ်ခုကနေ deserialize လုပ်ထားတာ မဟုတ်တဲ့ applications တွေအတွက်ပဲ ရရှိနိုင်ပါတယ်။

### `v8.startupSnapshot.addSerializeCallback(callback[, data])`

* `callback` {Function} Serialization မလုပ်ခင် ခေါ်ယူမယ့် callback။
* `data` {any} ခေါ်ယူတဲ့အခါ `callback` ဆီ ပေးပို့မယ့် optional data။

Node.js instance ကို snapshot တစ်ခုအဖြစ် serialize လုပ်ပြီး ထွက်တော့မယ့် အချိန်မှာ ခေါ်မယ့် callback တစ်ခုကို ထည့်သွင်းပါတယ်။ Serialize မလုပ်သင့် (သို့) မလုပ်နိုင်တဲ့ resources တွေကို လွှတ်ပေးဖို့ (သို့) user data တွေကို serialization အတွက် ပိုသင့်တော်တဲ့ ပုံစံအဖြစ် ပြောင်းလဲဖို့ ဒါကို သုံးနိုင်ပါတယ်။

Callbacks တွေကို ထည့်သွင်းခဲ့တဲ့ အစီအစဉ်အတိုင်း run ပါတယ်။

### `v8.startupSnapshot.addDeserializeCallback(callback[, data])`

* `callback` {Function} Snapshot ကို deserialize လုပ်ပြီးနောက် ခေါ်ယူမယ့် callback။
* `data` {any} ခေါ်ယူတဲ့အခါ `callback` ဆီ ပေးပို့မယ့် optional data။

Node.js instance ကို snapshot တစ်ခုကနေ deserialize လုပ်တဲ့အခါ ခေါ်မယ့် callback တစ်ခုကို ထည့်သွင်းပါတယ်။ `callback` နဲ့ `data` (ပေးထားရင်) တို့ကို snapshot ထဲကို serialize လုပ်ထားမှာ ဖြစ်ပြီး — application ကို snapshot ကနေ ပြန်လည် စတင်တဲ့အခါ application ရဲ့ state ကို ပြန်လည် စတင်သတ်မှတ်ဖို့ (သို့) application လိုအပ်တဲ့ resources တွေကို ပြန်လည် ရယူဖို့ သူတို့ကို သုံးနိုင်ပါတယ်။

Callbacks တွေကို ထည့်သွင်းခဲ့တဲ့ အစီအစဉ်အတိုင်း run ပါတယ်။

### `v8.startupSnapshot.setDeserializeMainFunction(callback[, data])`

* `callback` {Function} Snapshot ကို deserialize လုပ်ပြီးနောက် entry point အဖြစ် ခေါ်ယူမယ့် callback။
* `data` {any} ခေါ်ယူတဲ့အခါ `callback` ဆီ ပေးပို့မယ့် optional data။

ဒါက — application ကို snapshot တစ်ခုကနေ deserialize လုပ်တဲ့အခါ — Node.js application ရဲ့ entry point ကို သတ်မှတ်ပေးပါတယ်။ ဒါကို snapshot တည်ဆောက်တဲ့ script ထဲမှာ တစ်ကြိမ်ပဲ ခေါ်လို့ ရပါတယ်။ ခေါ်ထားရင် — deserialize လုပ်ထားတဲ့ application က စတင်ဖို့ နောက်ထပ် entry point script တစ်ခု မလိုတော့ဘဲ — callback ကို deserialize လုပ်ထားတဲ့ data (ပေးထားရင်) နဲ့အတူ ရိုးရိုး ခေါ်ယူလိုက်ရုံပါပဲ။ မခေါ်ထားဘူးဆိုရင်တော့ deserialize လုပ်ထားတဲ့ application ကို စတင်ဖို့ entry point script တစ်ခု ထပ်ပေးဖို့ လိုအပ်ပါသေးတယ်။

### `v8.startupSnapshot.isBuildingSnapshot()`

* Returns: {boolean}

Node.js instance ကို snapshot တစ်ခု တည်ဆောက်ဖို့ run လုပ်နေတာဆိုရင် `true` ပြန်ပေးပါတယ်။

## `v8.isStringOneByteRepresentation(content)`

* `content` {string}
* Returns: {boolean}

V8 က string တစ်ခုရဲ့ အောက်ခံ ကိုယ်စားပြုမှု (underlying representation) အနေနဲ့ `Latin-1/ISO-8859-1` နဲ့ `UTF16` တို့ကိုပဲ support လုပ်ပါတယ်။ `content` က အောက်ခံ ကိုယ်စားပြုမှုအနေနဲ့ `Latin-1/ISO-8859-1` ကို သုံးထားရင် ဒီ function က `true` ပြန်ပေးပြီး — မဟုတ်ရင် `false` ပြန်ပေးပါတယ်။

ဒီ method က `false` ပြန်ပေးတာက string ထဲမှာ `Latin-1/ISO-8859-1` ထဲ မပါဝင်တဲ့ characters တွေ ရှိနေတယ်လို့ ဆိုလိုတာ မဟုတ်ပါဘူး။ တစ်ခါတစ်ရံ `Latin-1` string တစ်ခုကို `UTF16` အနေနဲ့လည်း ကိုယ်စားပြုနိုင်ပါတယ်။
```mjs
import { isStringOneByteRepresentation } from 'node:v8';
import { Buffer } from 'node:buffer';

const Encoding = {
  latin1: 1,
  utf16le: 2,
};
const buffer = Buffer.alloc(100);
function writeString(input) {
  if (isStringOneByteRepresentation(input)) {
    console.log(`input: '${input}'`);
    buffer.writeUint8(Encoding.latin1);
    buffer.writeUint32LE(input.length, 1);
    buffer.write(input, 5, 'latin1');
    console.log(`decoded: '${buffer.toString('latin1', 5, 5 + input.length)}'\n`);
  } else {
    console.log(`input: '${input}'`);
    buffer.writeUint8(Encoding.utf16le);
    buffer.writeUint32LE(input.length * 2, 1);
    buffer.write(input, 5, 'utf16le');
    console.log(`decoded: '${buffer.toString('utf16le', 5, 5 + input.length * 2)}'`);
  }
}
writeString('hello');
writeString('你好');
```

* `options` {Object}

  * `maxBufferSize` {integer} ပိုအဟောင်း entries တွေကို မဖျက်ခင် သိမ်းထားမယ့် samples အများဆုံး အရေအတွက်ပါ။ **Default:** `4294967295`။

## `v8.startHeapProfile([options])`

* `options` {Object}
  * `sampleInterval` {number} ပျမ်းမျှ sampling interval (byte နဲ့) ပါ။ **Default:** `524288` (512 KiB)။
  * `stackDepth` {integer} Samples တွေအတွက် အများဆုံး stack depth ပါ။ **Default:** `16`။
  * `forceGC` {boolean} Profile မယူခင် garbage collection ကို အတင်း လုပ်ဆောင်ရန်။ **Default:** `false`။
  * `includeObjectsCollectedByMajorGC` {boolean} Major GC က စုဆောင်းလိုက်တဲ့ objects တွေကို ထည့်သွင်းရန်။ **Default:** `false`။
  * `includeObjectsCollectedByMinorGC` {boolean} Minor GC က စုဆောင်းလိုက်တဲ့ objects တွေကို ထည့်သွင်းရန်။ **Default:** `false`။
* Returns: {SyncHeapProfileHandle}

Heap profile တစ်ခုကို စတင်ပြီး — `SyncHeapProfileHandle` object တစ်ခုကို ပြန်ပေးပါတယ်။ ဒီ API က `using` syntax ကို support လုပ်ပါတယ်။
