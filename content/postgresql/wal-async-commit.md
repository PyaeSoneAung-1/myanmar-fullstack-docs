## 28.4. Asynchronous Commit (မစောင့်ဆိုင်းဘဲ commit လုပ်ခြင်း)

*Asynchronous commit* ဆိုတာ transaction များကို ပိုမြန်မြန် ပြီးစီးစေတဲ့ option တစ်ခု ဖြစ်ပြီး — database ပျက်ကျခဲ့ရင် နောက်ဆုံး transaction များ ဆုံးရှုံးနိုင်တဲ့ ဆိုးကျိုးကို လဲလှယ် ခံယူရပါတယ်။ Application အများအပြားမှာ ဒါက လက်ခံနိုင်တဲ့ အပေးအယူ (trade-off) တစ်ခု ဖြစ်ပါတယ်။

အရင် section မှာ ဖော်ပြထားသလို — transaction commit က ပုံမှန်အားဖြင့် *synchronous* (တစ်ပြိုင်နက် စောင့်ဆိုင်းသော) ဖြစ်ပါတယ် — ဆိုလိုတာက server က transaction ရဲ့ WAL record များကို permanent storage ဆီ flush လုပ်ပြီးမှသာ client ဆီ success အချက်ပြ ပြန်ပေးပါတယ်။ ဒါကြောင့် client အနေနဲ့ — commit ဖြစ်ပြီလို့ အစီရင်ခံခံရတဲ့ transaction တစ်ခုဟာ — ချက်ချင်း ပြီးတာနဲ့ server ပျက်ကျသွားခဲ့ရင်တောင် — ထိန်းသိမ်းထားမယ်ဆိုတာ အာမခံရပါတယ်။ ဒါပေမယ့် — transaction တိုတောင်းတဲ့အခါ — ဒီ နှောင့်နှေးမှုက transaction အချိန် စုစုပေါင်းရဲ့ အဓိက အစိတ်အပိုင်း တစ်ခု ဖြစ်နေပါတယ်။ Asynchronous commit mode ကို ရွေးချယ်တာက — transaction က logical အားဖြင့် ပြီးစီးတာနဲ့ — သူ ထုတ်လိုက်တဲ့ WAL record များ တကယ် disk ဆီ မရောက်သေးခင်မှာပဲ — server က success ပြန်ပေးတယ်လို့ ဆိုလိုပါတယ်။ ဒါက transaction သေးသေးလေးများအတွက် throughput ကို သိသိသာသာ မြှင့်တင်ပေးနိုင်ပါတယ်။

Asynchronous commit က data ဆုံးရှုံးနိုင်တဲ့ အန္တရာယ်ကို ယူဆောင်လာပါတယ်။ Client ဆီ transaction ပြီးစီးကြောင်း အစီရင်ခံတဲ့ အချိန်နဲ့ — transaction တကယ် commit ဖြစ်တဲ့ အချိန် (ဆိုလိုတာက server ပျက်ကျခဲ့ရင် ဆုံးရှုံးမှာ မဟုတ်ဘူးလို့ အာမခံနိုင်တဲ့ အချိန်) အကြားမှာ အချိန်ကာလ တိုတောင်းတစ်ခု ရှိပါတယ်။ ဒါကြောင့် — transaction ကို မှတ်သားထားမယ်လို့ ယူဆပြီး client က ပြင်ပ လုပ်ဆောင်ချက်များ လုပ်မယ်ဆိုရင် — asynchronous commit ကို မသုံးသင့်ပါဘူး။ ဥပမာ — ATM က ငွေထုတ်ပေးမှုကို မှတ်တမ်းတင်တဲ့ transaction တစ်ခုအတွက် ဘဏ်တစ်ခုက asynchronous commit ကို သုံးမှာ သေချာပေါက် မဟုတ်ပါဘူး။ ဒါပေမယ့် event logging လို အခြေအနေ အများအပြားမှာတော့ ဒီလို ပြင်းထန်တဲ့ အာမခံချက် မလိုအပ်ပါဘူး။

Asynchronous commit သုံးခြင်းဖြင့် ယူတဲ့ အန္တရာယ်က data ဆုံးရှုံးမှုပါ — data ပျက်စီးမှု မဟုတ်ပါဘူး။ Database ပျက်ကျခဲ့ရင် — flush လုပ်ပြီးသား နောက်ဆုံး record အထိ WAL ကို replay လုပ်ပြီး ပြန်လည် ကုစားပါလိမ့်မယ်။ ဒါကြောင့် database က ကိုယ်တိုင် ညီညွတ်တဲ့ အခြေအနေ (self-consistent state) ဆီ ပြန်ရောက်ပါလိမ့်မယ် — ဒါပေမယ့် disk ဆီ မရောက်သေးတဲ့ transaction များကတော့ အဲဒီ အခြေအနေမှာ ထင်ဟပ်မှာ မဟုတ်ပါဘူး။ ဒါကြောင့် အဆုံးသတ် အကျိုးသက်ရောက်မှုက နောက်ဆုံး transaction အနည်းငယ် ဆုံးရှုံးခြင်းပါ။ Transaction များကို commit အစီအစဉ်အတိုင်း replay လုပ်တာမို့ ကွဲလွဲမှု (inconsistency) ဖြစ်လာနိုင်တာ မရှိပါဘူး — ဥပမာ — transaction B က အရင် transaction A ရဲ့ သက်ရောက်မှုအပေါ် မှီပြီး ပြောင်းလဲမှုများ လုပ်ခဲ့ရင် — B ရဲ့ သက်ရောက်မှုများ ကျန်ရှိနေချိန်မှာ A ရဲ့ သက်ရောက်မှုများ ဆုံးရှုံးသွားတယ်ဆိုတာ ဖြစ်နိုင်မှာ မဟုတ်ပါဘူး။

User က transaction တစ်ခုချင်းစီရဲ့ commit mode ကို ရွေးချယ်နိုင်တာမို့ — synchronous နဲ့ asynchronous commit transaction များကို တစ်ပြိုင်နက် လည်ပတ်နိုင်ပါတယ်။ ဒါက performance နဲ့ transaction durability (တည်ရှိနေမှု) ရဲ့ သေချာမှု အကြားမှာ လိုက်လျောညီထွေ အပေးအယူ လုပ်နိုင်စေပါတယ်။ Commit mode ကို user က သတ်မှတ်နိုင်တဲ့ parameter ဖြစ်တဲ့ [synchronous_commit](https://www.postgresql.org/docs/current/runtime-config-wal.html#GUC-SYNCHRONOUS-COMMIT) က ထိန်းချုပ်ပြီး — configuration parameter တစ်ခုကို သတ်မှတ်နိုင်တဲ့ နည်းလမ်း မှန်သမျှနဲ့ ပြောင်းလဲနိုင်ပါတယ်။ Transaction တစ်ခုအတွက် သုံးတဲ့ mode က transaction commit စတင်တဲ့အခါ `synchronous_commit` ရဲ့ တန်ဖိုးပေါ်မှာ မူတည်ပါတယ်။

Utility command အချို့ — ဥပမာ `DROP TABLE` — က `synchronous_commit` ရဲ့ သတ်မှတ်ချက် ဘယ်လိုပဲ ဖြစ်ဖြစ် synchronous အနေနဲ့ commit လုပ်ဖို့ အတင်းအကျပ် သတ်မှတ်ထားပါတယ်။ ဒါက server ရဲ့ file system နဲ့ database ရဲ့ logical အခြေအနေ အကြား ညီညွတ်မှုကို သေချာစေဖို့ပါ။ Two-phase commit ကို ထောက်ပံ့တဲ့ command များ — ဥပမာ `PREPARE TRANSACTION` — ကလည်း အမြဲတမ်း synchronous ဖြစ်ပါတယ်။

Asynchronous commit တစ်ခုနဲ့ transaction ရဲ့ WAL record များ ရေးသားခြင်း အကြားက အန္တရာယ် ကာလ (risk window) အတွင်း database ပျက်ကျခဲ့ရင် — အဲဒီ transaction အတွင်း ပြုလုပ်ခဲ့တဲ့ ပြောင်းလဲမှုများ ဆုံးရှုံးပါလိမ့်မယ်။ အန္တရာယ် ကာလရဲ့ ကြာချိန်က ကန့်သတ်ထားပါတယ် — အကြောင်းကတော့ background process တစ်ခု (“WAL writer”) က မရေးရသေးတဲ့ WAL record များကို [wal_writer_delay](https://www.postgresql.org/docs/current/runtime-config-wal.html#GUC-WAL-WRITER-DELAY) milliseconds တိုင်း disk ဆီ flush လုပ်ပေးလို့ပါ။ အန္တရာယ် ကာလရဲ့ အမှန်တကယ် အများဆုံး ကြာချိန်က `wal_writer_delay` ရဲ့ သုံးဆ ဖြစ်ပါတယ် — အကြောင်းကတော့ WAL writer က အလုပ်များတဲ့ အချိန်များမှာ page တစ်ခုလုံးကို တစ်ကြိမ်တည်း ရေးသားတာကို ဦးစားပေးအောင် ဒီဇိုင်းဆွဲထားလို့ပါ။

> **သတိထားရန်:** Immediate-mode shutdown (ချက်ချင်း ပိတ်ခြင်း မုဒ်) က server ပျက်ကျခြင်းနဲ့ အတူတူပါပဲ — ဒါကြောင့် မရောက်သေးတဲ့ (unflushed) asynchronous commit များ ဆုံးရှုံးစေပါလိမ့်မယ်။

Asynchronous commit ရဲ့ အပြုအမူက [fsync](https://www.postgresql.org/docs/current/runtime-config-wal.html#GUC-FSYNC) = off သတ်မှတ်ခြင်းနဲ့ မတူပါဘူး။ `fsync` က server တစ်ခုလုံးအတွက် သတ်မှတ်တဲ့ setting ဖြစ်ပြီး transaction အားလုံးရဲ့ အပြုအမူကို ပြောင်းလဲစေပါတယ်။ ဒါက database ရဲ့ အစိတ်အပိုင်း အမျိုးမျိုးဆီ ရေးသားမှုများကို ထပ်တူပြုဖို့ PostgreSQL အတွင်းမှာ ကြိုးစားတဲ့ logic အားလုံးကို ပိတ်ပစ်တာမို့ — system crash (ဆိုလိုတာက hardware သို့မဟုတ် operating system ပျက်ကျခြင်း၊ PostgreSQL ကိုယ်တိုင် ကျရှုံးခြင်း မဟုတ်) ဖြစ်ခဲ့ရင် database အခြေအနေကို ဆိုးရွားစွာ ပျက်စီးစေနိုင်ပါတယ်။ အခြေအနေ အများအပြားမှာ asynchronous commit က `fsync` ကို ပိတ်ခြင်းဖြင့် ရနိုင်တဲ့ performance တိုးတက်မှု အများစုကို — data ပျက်စီးနိုင်တဲ့ အန္တရာယ် မပါဘဲ — ပေးစွမ်းနိုင်ပါတယ်။

[commit_delay](https://www.postgresql.org/docs/current/runtime-config-wal.html#GUC-COMMIT-DELAY) ကလည်း asynchronous commit နဲ့ အလွန် ဆင်တူသလို ထင်ရပေမယ့် — တကယ်တော့ synchronous commit နည်းလမ်းတစ်ခု ဖြစ်ပါတယ် (တကယ်တော့ `commit_delay` ကို asynchronous commit လုပ်နေစဉ်အတွင်း လျစ်လျူရှုပါတယ်)။ `commit_delay` က transaction တစ်ခု WAL ကို disk ဆီ flush လုပ်ခါနီးမှာ နှောင့်နှေးမှု တစ်ခု ဖြစ်စေပြီး — အဲဒီလို transaction တစ်ခုက လုပ်ဆောင်တဲ့ flush တစ်ကြိမ်တည်းက — အချိန်တူနီးပါး commit လုပ်နေတဲ့ အခြား transaction များကိုလည်း အကျိုးပြုနိုင်မယ်လို့ မျှော်လင့်ပါတယ်။ ဒီ setting ကို — flush တစ်ကြိမ်တည်းမှာ ပူးပေါင်း ပါဝင်တော့မယ့် အုပ်စုထဲ transaction များ ပါဝင်နိုင်တဲ့ အချိန် ပြတင်းပေါက် (time window) ကို ချဲ့ထွင်ပြီး — flush ရဲ့ ကုန်ကျစရိတ်ကို transaction များစွာ အကြား ဖြန့်ခွဲပေးတဲ့ နည်းလမ်းတစ်ခုလို့ မှတ်ယူနိုင်ပါတယ်။
