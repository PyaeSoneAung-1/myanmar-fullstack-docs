## 28.6. WAL Internals (WAL ၏ အတွင်းပိုင်း လုပ်ဆောင်ပုံ)

WAL ကို အလိုအလျောက် enable လုပ်ထားပြီးသား ဖြစ်ပါတယ်။ Administrator အနေနဲ့ — WAL file များအတွက် disk space လိုအပ်ချက် ပြည့်မီကြောင်းနဲ့ — လိုအပ်တဲ့ tuning များ လုပ်ဆောင်ထားကြောင်း သေချာစေတာကလွဲလို့ — ဘာအလုပ်မှ လုပ်ဖို့ မလိုပါဘူး ([အပိုင်း 28.5](/docs/postgresql/wal-configuration) ကို ကြည့်ပါ)။

WAL record အသစ် တစ်ခု ရေးသားတိုင်း WAL file များဆီ နောက်ဆက်တွဲ ထည့်သွင်း (append) ပါတယ်။ ထည့်သွင်းတဲ့ နေရာ (insert position) ကို Log Sequence Number (LSN) နဲ့ ဖော်ပြပြီး — ဒါက WAL အတွင်းက byte offset တစ်ခု ဖြစ်ကာ — record အသစ် တစ်ခု တိုင်း တစ်လမ်းတည်း တိုးလာပါတယ်။ LSN တန်ဖိုးများကို [`pg_lsn`](https://www.postgresql.org/docs/current/datatype-pg-lsn.html) datatype အနေနဲ့ ပြန်ပေးပါတယ်။ တန်ဖိုးများကို နှိုင်းယှဉ်ပြီး သူတို့ကို ခြားထားတဲ့ WAL data ပမာဏကို တွက်ချက်နိုင်တာမို့ — replication နဲ့ recovery တိုးတက်မှုကို တိုင်းတာဖို့ သုံးပါတယ်။

WAL file များကို data directory အောက်က `pg_wal` directory ထဲမှာ segment file အစုတစ်ခုအနေနဲ့ သိမ်းဆည်းထားပြီး — ပုံမှန်အားဖြင့် တစ်ခုချင်းစီက 16 MB အရွယ် ရှိပါတယ် (ဒါပေမယ့် `--wal-segsize` ဆိုတဲ့ initdb option ကို ပြောင်းခြင်းဖြင့် အရွယ်ကို ပြောင်းနိုင်ပါတယ်)။ Segment တစ်ခုချင်းစီကို page များအဖြစ် ခွဲထားပြီး — ပုံမှန်အားဖြင့် တစ်ခုချင်းစီက 8 kB ရှိပါတယ် (ဒီအရွယ်ကို `--with-wal-blocksize` configure option နဲ့ ပြောင်းနိုင်ပါတယ်)။ WAL record header များကို `access/xlogrecord.h` မှာ ဖော်ပြထားပါတယ်; record ရဲ့ အကြောင်းအရာက log မှတ်တမ်းတင်နေတဲ့ event အမျိုးအစားပေါ် မူတည်ပါတယ်။ Segment file များကို `000000010000000000000001` ကနေ စပြီး — အမြဲ တိုးလာတဲ့ နံပါတ်များကို နာမည်အဖြစ် ပေးပါတယ်။ နံပါတ်များက ပြန်လည် လှည့်ပတ်ခြင်း (wrap) မရှိပါဘူး — ဒါပေမယ့် ရရှိနိုင်တဲ့ နံပါတ် လက်ကျန် ကုန်ဆုံးဖို့ အလွန် အလွန် ကြာမြင့်ပါလိမ့်မယ်။

WAL ကို အဓိက database file များနဲ့ မတူတဲ့ disk တစ်ခုပေါ်မှာ ထားရှိခြင်းက အကျိုးရှိပါတယ်။ ဒါကို — `pg_wal` directory ကို အခြား နေရာတစ်ခုဆီ ရွှေ့ပြီး (တကယ်တော့ server ပိတ်ထားချိန်မှာ လုပ်ရပါတယ်) — အဓိက data directory ထဲက မူရင်း နေရာကနေ နေရာအသစ်ဆီ symbolic link တစ်ခု ဖန်တီးခြင်းဖြင့် လုပ်ဆောင်နိုင်ပါတယ်။

WAL ရဲ့ ရည်ရွယ်ချက်က database record များ မပြောင်းလဲခင် log ကို အရင် ရေးသားထားကြောင်း သေချာစေဖို့ ဖြစ်ပါတယ် — ဒါပေမယ့် ဒါကို — kernel ဆီ write အောင်မြင်ကြောင်း မှားယွင်း အစီရင်ခံတဲ့ disk drive များက — တကယ်တော့ data ကို cache လုပ်ထားရုံသာ ဖြစ်ပြီး disk ပေါ် မသိမ်းရသေးချိန်မှာ — လမ်းလွဲစေနိုင်ပါတယ်။ ဒီလို အခြေအနေမှာ လျှပ်စစ် ပြတ်တောက်မှု (power failure) ဖြစ်ခဲ့ရင် ပြန်လည် ကုစားလို့ မရနိုင်တဲ့ data ပျက်စီးမှုဆီ ဦးတည်သွားနိုင်ပါတယ်။ Administrator များအနေနဲ့ — PostgreSQL ရဲ့ WAL file များ သိမ်းထားတဲ့ disk များက ဒီလို မှားယွင်း အစီရင်ခံမှုများ မလုပ်ကြောင်း သေချာစေဖို့ ကြိုးစားသင့်ပါတယ်။ ([အပိုင်း 28.1](/docs/postgresql/wal-reliability) ကို ကြည့်ပါ။)

Checkpoint တစ်ခု ပြုလုပ်ပြီး WAL ကို flush လုပ်ပြီးနောက် — checkpoint ရဲ့ တည်နေရာကို `pg_control` file ထဲမှာ သိမ်းဆည်းထားပါတယ်။ ဒါကြောင့် recovery စတင်ချိန်မှာ server က `pg_control` ကို အရင် ဖတ်ပြီး နောက် checkpoint record ကို ဖတ်ပါတယ်; ပြီးရင် checkpoint record မှာ ညွှန်ပြထားတဲ့ WAL တည်နေရာကနေ အရှေ့ဆီ scan လုပ်ပြီး REDO လုပ်ဆောင်ချက်ကို လုပ်ဆောင်ပါတယ်။ Checkpoint ပြီးနောက် ပထမဆုံး page ပြုပြင်မှုမှာ data page များ၏ အကြောင်းအရာ တစ်ခုလုံးကို WAL ထဲမှာ သိမ်းဆည်းထားတာမို့ ([full_page_writes](https://www.postgresql.org/docs/current/runtime-config-wal.html#GUC-FULL-PAGE-WRITES) ကို ပိတ်မထားဘူးလို့ ယူဆရင်) — checkpoint ကတည်းက ပြောင်းလဲထားတဲ့ page အားလုံးကို ညီညွတ်တဲ့ အခြေအနေဆီ ပြန်လည် ရောက်ရှိစေပါလိမ့်မယ်။

`pg_control` ပျက်စီးနေတဲ့ အခြေအနေကို ကိုင်တွယ်ဖို့ — နောက်ဆုံး checkpoint ကို ရှာဖွေနိုင်ဖို့ — ရှိပြီးသား WAL segment များကို ပြောင်းပြန် အစီအစဉ်နဲ့ (အသစ်ဆုံးကနေ အဟောင်းဆုံးဆီ) scan လုပ်နိုင်တဲ့ ဖြစ်နိုင်ခြေကို ထောက်ပံ့သင့်ပါတယ်။ ဒါကို အကောင်အထည် မဖော်ရသေးပါဘူး။ `pg_control` က သေးငယ်လုံလောက်တာမို့ (disk page တစ်ခုထက် နည်း) — partial-write (တစ်ပိုင်းတစ်စ ရေးသားခြင်း) ပြဿနာများ မခံစားရပါဘူး — ဒီစာကို ရေးသားနေချိန်အထိ `pg_control` ကိုယ်တိုင် ဖတ်လို့မရခြင်းကြောင့်သာ database ကျရှုံးတယ်လို့ အစီရင်ခံမှုများ မရှိသေးပါဘူး။ ဒါကြောင့် သီအိုရီအရတော့ အားနည်းချက် တစ်ခု ဖြစ်ပေမယ့် — လက်တွေ့မှာတော့ `pg_control` က ပြဿနာ မဖြစ်ပုံရပါဘူး။
