### 9.28.1. Configuration Settings Functions (configuration settings လုပ်ဆောင်ချက်များ)

Run-time (လည်ပတ်နေစဉ်) configuration parameters (ဆက်တင် ကန့်သတ်ချက်များ) တွေကို query လုပ်ဖို့နဲ့ ပြောင်းလဲဖို့ ရနိုင်တဲ့ functions တွေကို ဇယား 9.95 မှာ ပြထားပါတယ်။

**ဇယား 9.95. Configuration Settings Functions (configuration settings လုပ်ဆောင်ချက်များ)**

| လုပ်ဆောင်ချက် ဖော်ပြချက်နှင့် ဥပမာ(များ) |
| --- |
| current_setting ( setting_name text [, missing_ok boolean ] ) → text setting `setting_name` ရဲ့ လက်ရှိ တန်ဖိုးကို ပြန်ပေးပါတယ်။ အဲဒီလို setting မရှိဘူးဆိုရင် — `missing_ok` ကို ပေးအပ်ပြီး true ဖြစ်နေတဲ့ ကိစ္စကလွဲရင် (အဲဒီအခါ NULL ပြန်ပေးပါတယ်) — `current_setting` က error တစ်ခု ထုတ်ပါတယ်။ ဒီ function က SQL command `SHOW` နဲ့ သက်ဆိုင်ပါတယ်။ ဥပမာ — current_setting('datestyle') → ISO, MDY |
| set_config ( setting_name text, new_value text, is_local boolean ) → text parameter `setting_name` ကို `new_value` အဖြစ် သတ်မှတ်ပြီး — အဲဒီတန်ဖိုးကို ပြန်ပေးပါတယ်။ `is_local` က true ဆိုရင် — တန်ဖိုးအသစ်က လက်ရှိ transaction အတွင်းမှာသာ သက်ရောက်မှု ရှိပါမယ်။ တန်ဖိုးအသစ်ကို လက်ရှိ session ရဲ့ ကျန်တဲ့ အချိန်တွေအတွက် သက်ရောက်စေချင်ရင်တော့ false ကို သုံးပါ။ ဒီ function က SQL command `SET` နဲ့ သက်ဆိုင်ပါတယ်။ `set_config` က `new_value` အတွက် NULL တန်ဖိုးကို လက်ခံပါတယ် — ဒါပေမယ့် settings တွေက null မဖြစ်နိုင်တာမို့ — setting ကို ၎င်းရဲ့ default တန်ဖိုးဆီ reset လုပ်ဖို့ တောင်းဆိုချက်အဖြစ် အနက်ဖွင့်ပါတယ်။ ဥပမာ — set_config('log_statement_stats', 'off', false) → off |

### 9.28.2. Server Signaling Functions (server signaling လုပ်ဆောင်ချက်များ)

ဇယား 9.96 မှာ ပြထားတဲ့ functions တွေက — အခြား server processes တွေဆီ control signals (ထိန်းချုပ်ရေး အချက်ပြများ) ပို့ပေးပါတယ်။ ဒီ functions တွေကို ပုံမှန်အားဖြင့် superuser များသာ အသုံးပြုနိုင်ပြီး — အောက်မှာ ဖော်ပြထားတဲ့ ခြွင်းချက်တွေ မှလွဲ၍ — `GRANT` သုံးပြီး အခြားသူများကိုလည်း ဝင်ရောက်ခွင့် ပေးအပ်နိုင်ပါတယ်။

ဒီ functions တစ်ခုစီက — signal ကို အောင်မြင်စွာ ပို့လိုက်နိုင်ရင် `true` ကို ပြန်ပေးပြီး — signal ပို့တာ မအောင်မြင်ရင် `false` ကို ပြန်ပေးပါတယ်။

**ဇယား 9.96. Server Signaling Functions (server signaling လုပ်ဆောင်ချက်များ)**

| လုပ်ဆောင်ချက် ဖော်ပြချက် |
| --- |
| pg_cancel_backend ( pid integer ) → boolean သတ်မှတ်ထားတဲ့ process ID ရှိတဲ့ backend process ပိုင်ဆိုင်တဲ့ session ရဲ့ လက်ရှိ query ကို cancel လုပ်ပါတယ်။ ခေါ်ဆိုတဲ့ role က — backend ကို cancel လုပ်ခံနေရတဲ့ role ရဲ့ member ဖြစ်နေရင် သို့မဟုတ် `pg_signal_backend` ရဲ့ privileges တွေ ရှိနေရင်လည်း ခွင့်ပြုပါတယ် — ဒါပေမယ့် superuser backends တွေကိုတော့ superuser များသာ cancel လုပ်နိုင်ပါတယ်။ ခြွင်းချက်အနေနဲ့ — `pg_signal_autovacuum_worker` ရဲ့ privileges ရှိတဲ့ roles တွေက — တခြားနည်းနဲ့ဆို superuser backends အဖြစ် သတ်မှတ်ခံရတဲ့ — autovacuum worker processes တွေကို cancel လုပ်ခွင့် ရှိပါတယ်။ |
| pg_log_backend_memory_contexts ( pid integer ) → boolean သတ်မှတ်ထားတဲ့ process ID ရှိတဲ့ backend ရဲ့ memory contexts တွေကို log လုပ်ဖို့ တောင်းဆိုပါတယ်။ ဒီ function က logger ကလွဲလို့ — backends တွေနဲ့ auxiliary processes တွေဆီကို အဲဒီတောင်းဆိုချက်ကို ပို့နိုင်ပါတယ်။ ဒီ memory contexts တွေကို LOG message level မှာ log လုပ်ပါလိမ့်မယ်။ သတ်မှတ်ထားတဲ့ log configuration အရ (အသေးစိတ်အတွက် အပိုင်း 19.8 ကို ကြည့်ပါ) server log ထဲမှာ ပေါ်လာမှာ ဖြစ်ပြီး — `client_min_messages` ဘာပဲဖြစ်ဖြစ် client ဆီကိုတော့ ပို့မှာ မဟုတ်ပါဘူး။ |
| pg_reload_conf () → boolean PostgreSQL server ရဲ့ processes အားလုံးကို — သူတို့ရဲ့ configuration files တွေကို ပြန်ဖတ် (reload) လုပ်စေပါတယ်။ (ဒါကို postmaster process ဆီ SIGHUP signal ပို့ခြင်းဖြင့် စတင်ပြီး — postmaster က ၎င်းရဲ့ child process တစ်ခုစီဆီကိုလည်း SIGHUP ပြန်ပို့ပါတယ်။) Reload မလုပ်ခင် — `pg_file_settings`, `pg_hba_file_rules` နဲ့ `pg_ident_file_mappings` views တွေကို သုံးပြီး configuration files တွေမှာ error တွေ ရှိမရှိ စစ်ဆေးနိုင်ပါတယ်။ |
| pg_rotate_logfile () → boolean Log-file manager ကို — output file အသစ်တစ်ခုဆီ ချက်ချင်း ပြောင်းဖို့ signal ပေးပါတယ်။ ဒါက built-in log collector လည်ပတ်နေမှသာ အလုပ်လုပ်ပါတယ် — မဟုတ်ရင် log-file manager subprocess ဆိုတာ မရှိလို့ပါ။ |
| pg_terminate_backend ( pid integer, timeout bigint DEFAULT 0 ) → boolean သတ်မှတ်ထားတဲ့ process ID ရှိတဲ့ backend process ပိုင်ဆိုင်တဲ့ session ကို terminate (ရပ်စဲ) လုပ်ပါတယ်။ ခေါ်ဆိုတဲ့ role က — terminate လုပ်ခံနေရတဲ့ role ရဲ့ member ဖြစ်နေရင် သို့မဟုတ် `pg_signal_backend` ရဲ့ privileges တွေ ရှိနေရင်လည်း ခွင့်ပြုပါတယ် — ဒါပေမယ့် superuser backends တွေကိုတော့ superuser များသာ terminate လုပ်နိုင်ပါတယ်။ ခြွင်းချက်အနေနဲ့ — `pg_signal_autovacuum_worker` ရဲ့ privileges ရှိတဲ့ roles တွေက — တခြားနည်းနဲ့ဆို superuser backends အဖြစ် သတ်မှတ်ခံရတဲ့ — autovacuum worker processes တွေကို terminate လုပ်ခွင့် ရှိပါတယ်။ `timeout` ကို သတ်မှတ်မထားရင် သို့မဟုတ် zero ဆိုရင် — ဒီ function က process တကယ် terminate ဖြစ်မဖြစ် မသက်ဆိုင်ဘဲ true ပြန်ပေးပြီး — signal ပို့တာ အောင်မြင်တာကိုပဲ ညွှန်ပြပါတယ်။ `timeout` (milliseconds နဲ့) ကို သတ်မှတ်ပြီး zero ထက် ကြီးနေရင် — function က process တကယ် terminate ဖြစ်တဲ့အထိ သို့မဟုတ် သတ်မှတ်ထားတဲ့ အချိန် ကုန်ဆုံးတဲ့အထိ စောင့်ပါတယ်။ Process terminate ဖြစ်ရင် true ပြန်ပေးပြီး — timeout ဖြစ်ရင်တော့ warning တစ်ခု ထုတ်ပြီး false ပြန်ပေးပါတယ်။ |

`pg_cancel_backend` နဲ့ `pg_terminate_backend` တို့က — process ID နဲ့ ခွဲခြားသတ်မှတ်ထားတဲ့ backend processes တွေဆီ signals (အသီးသီး SIGINT သို့မဟုတ် SIGTERM) ပို့ပေးပါတယ်။ Active backend တစ်ခုရဲ့ process ID ကို — `pg_stat_activity` view ရဲ့ `pid` column ကနေ ဒါမှမဟုတ် server ပေါ်မှာ `postgres` processes တွေကို စာရင်းကြည့်ခြင်းအားဖြင့် (Unix မှာ ps သုံးပြီး သို့မဟုတ် Windows မှာ Task Manager သုံးပြီး) ရှာတွေ့နိုင်ပါတယ်။ Active backend တစ်ခုရဲ့ role ကို `pg_stat_activity` view ရဲ့ `usename` column ကနေ ရှာတွေ့နိုင်ပါတယ်။

`pg_log_backend_memory_contexts` ကို backend process တစ်ခုရဲ့ memory contexts တွေကို log လုပ်ဖို့ သုံးနိုင်ပါတယ်။ ဥပမာ:

```
postgres=# SELECT pg_log_backend_memory_contexts(pg_backend_pid());
 pg_log_backend_memory_contexts
--------------------------------
 t
(1 row)
```

တူညီတဲ့ parent တစ်ခုအောက်မှာ child contexts 100 ခုထက် ပိုများနေရင် — ပထမ child contexts 100 ခုကို — ကျန်တဲ့ contexts တွေရဲ့ အကျဉ်းချုပ်နဲ့အတူ — log လုပ်ပါတယ်။ ဒီ function ကို မကြာခဏ ခေါ်တာက — log messages အများအပြား ထုတ်ပေးနိုင်တာကြောင့် — သိသာတဲ့ overhead (အပိုတာဝန်) သင့်နိုင်တာကို သတိပြုပါ။

### 9.28.3. Backup Control Functions (backup ထိန်းချုပ်ရေး လုပ်ဆောင်ချက်များ)

ဇယား 9.97 မှာ ပြထားတဲ့ functions တွေက on-line backups (ဆာဗာ လည်ပတ်နေစဉ် backup များ) ပြုလုပ်ရာမှာ အထောက်အကူ ပေးပါတယ်။ ဒီ functions တွေကို recovery (ပြန်လည်ရယူခြင်း) အတွင်း run လို့ မရပါဘူး — (`pg_backup_start`, `pg_backup_stop` နဲ့ `pg_wal_lsn_diff` ကလွဲရင်)။

ဒီ functions တွေကို မှန်ကန်စွာ အသုံးပြုပုံ အသေးစိတ်အတွက် [အပိုင်း 25.3](https://www.postgresql.org/docs/current/continuous-archiving.html) ကို ကြည့်ပါ။

tablespace map file တို့ရဲ့ လိုအပ်တဲ့ ပါဝင်စရာတွေကို — function ရဲ့ result ရဲ့ တစ်စိတ်တစ်ပိုင်းအနေနဲ့ ပြန်ပေးပြီး — backup area ထဲက files တွေဆီ ရေးသားရပါမယ်။ ဒီ files တွေကို live data directory (တကယ် မဟုတ်ရင် — backup ကို consistent (တစ်သမတ်တည်း) ဖြစ်စေဖို့ လိုအပ်တဲ့ WAL ပျောက်ဆုံးနေပြီး backup အလဟသ ဖြစ်သွားနိုင်ပါတယ်။ ပုံမှန်အားဖြင့် သို့မဟုတ် ဒီ parameter က true ဆိုရင် — archiving log file ကို ချက်ချင်း archive လုပ်ပြီး backup ပြီးမြောက်အောင် လုပ်ပါတယ်။ Function ရဲ့ result က record တစ်ခုတည်း ဖြစ်ပါတယ်။ `lsn` column မှာ backup ရဲ့ အဆုံးသတ် write-ahead log location ကို | pg_switch_wal () → pg_lsn Server ကို write-ahead log file အသစ်တစ်ခုဆီ ပြောင်းစေပြီး — လက်ရှိ file ကို archive လုပ်နိုင်အောင် ပြုလုပ်ပေးပါတယ် (continuous archiving သုံးနေတယ်ဆိုရင်)။ Result က — ပြီးစီးသွားတဲ့ write-ahead log file ထဲက အဆုံးသတ် write-ahead log location ပေါင်း 1 ဖြစ်ပါတယ်။ နောက်ဆုံး write-ahead log switch ကစလို့ write-ahead log activity လုံးဝ မရှိခဲ့ဘူးဆိုရင် — `pg_switch_wal` က ဘာမှ မလုပ်ဘဲ — လက်ရှိ အသုံးပြုနေတဲ့ write-ahead log file ရဲ့ start location ကို ပြန်ပေးပါတယ်။ ဒီ function ကို ပုံမှန်အားဖြင့် superuser များသာ အသုံးပြုနိုင်ပြီး — အခြား user များကိုမူ ဒီ function ကို run လုပ်နိုင်ရန် EXECUTE privilege ပေးအပ်နိုင်ပါတယ်။ |

`pg_current_wal_lsn` က လက်ရှိ write-ahead log write location ကို — အပေါ်က functions တွေ သုံးတဲ့ format နဲ့ပဲ ပြသပါတယ်။ အလားတူပဲ — `pg_current_wal_insert_lsn` က လက်ရှိ write-ahead log insertion location ကို ပြသပြီး — `pg_current_wal_flush_lsn` က လက်ရှိ write-ahead log flush location ကို ပြသပါတယ်။ Insertion location က — ဘယ်အချိန်မဆို write-ahead log ရဲ့ “logical” (ယုတ္တိအရ) အဆုံးသတ် ဖြစ်ပြီး — write location ကတော့ server ရဲ့ internal buffers တွေကနေ တကယ် ရေးထုတ်ပြီးသား အကြောင်းအရာရဲ့ အဆုံးသတ် ဖြစ်ပါတယ်။ Flush location ကတော့ — durable storage (အမြဲတမ်း သိုလှောင်မှု) ဆီကို ရေးပြီးတယ်လို့ သိရတဲ့ နောက်ဆုံး location ဖြစ်ပါတယ်။ Write location က server အပြင်ဘက်ကနေ စစ်ဆေးကြည့်လို့ ရတဲ့ အဆုံးသတ် ဖြစ်ပြီး — မပြည့်စုံသေးတဲ့ (partially-complete) write-ahead log files တွေကို archive လုပ်ဖို့ စိတ်ဝင်စားနေရင် — ပုံမှန်အားဖြင့် သင်လိုချင်တာ ဒါပဲ ဖြစ်ပါတယ်။ Insertion နဲ့ flush locations တွေကိုတော့ — အဓိကအားဖြင့် server debugging ရည်ရွယ်ချက်တွေအတွက် ရနိုင်အောင် လုပ်ထားတာ ဖြစ်ပါတယ်။ ဒါတွေက read-only operations တွေ အားလုံး ဖြစ်ပြီး — superuser permissions မလိုအပ်ပါဘူး။

`pg_walfile_name_offset` ကို သုံးပြီး — `pg_lsn` တန်ဖိုးတစ်ခုကနေ သက်ဆိုင်တဲ့ write-ahead log file name နဲ့ byte offset ကို ထုတ်ယူနိုင်ပါတယ်။ ဥပမာ:

```
postgres=# SELECT * FROM pg_walfile_name_offset((pg_backup_stop()).lsn);
        file_name         | file_offset
--------------------------+-------------
 00000001000000000000000D |     4039624
(1 row)
```
အလားတူ — `pg_walfile_name` က write-ahead log file name ကိုပဲ ထုတ်ယူပေးပါတယ်။

`pg_split_walfile_name` က file offset နဲ့ WAL file name ကနေ LSN တစ်ခု တွက်ဖို့ အသုံးဝင်ပါတယ် — ဥပမာ:

```
postgres=# \set file_name '000000010000000100C000AB'
postgres=# \set offset 256
postgres=# SELECT '0/0'::pg_lsn + pd.segment_number * ps.setting::int + :offset AS lsn
  FROM pg_split_walfile_name(:'file_name') pd,
       pg_show_all_settings() ps
  WHERE ps.name = 'wal_segment_size';
      lsn
---------------
 C001/AB000100
(1 row)
```

| pg_last_wal_receive_lsn () → pg_lsn Streaming replication (စီးကြောင်းလိုက် ပုံတူပွားခြင်း) အားဖြင့် — လက်ခံရရှိပြီး disk ပေါ်ကို sync (တစ်ပြေးညီ မှတ်တမ်းတင်) လုပ်ပြီးသား — နောက်ဆုံး write-ahead log location ကို ပြန်ပေးပါတယ်။ Streaming replication လုပ်ဆောင်နေစဉ်မှာ ဒါက monotonically (တစ်သမတ်တည်း) တိုးလာပါတယ်။ Recovery ပြီးစီးသွားရင်တော့ — recovery အတွင်း လက်ခံရပြီး disk ပေါ်ကို sync လုပ်ပြီးသား နောက်ဆုံး WAL record ရဲ့ location မှာ တည်ငြိမ်စွာ ရှိနေပါလိမ့်မယ်။ Streaming replication ကို disable လုပ်ထားရင် သို့မဟုတ် မစတင်ရသေးဘူးဆိုရင် — function က NULL ပြန်ပေးပါတယ်။ |
| pg_last_wal_replay_lsn () → pg_lsn Recovery အတွင်း replay (ပြန်လည်ဖွင့်သုံး) လုပ်ပြီးသား နောက်ဆုံး write-ahead log location ကို ပြန်ပေးပါတယ်။ Recovery ဆက်လက် လုပ်ဆောင်နေသေးရင် — ဒါက monotonically တိုးလာပါတယ်။ Recovery ပြီးစီးသွားရင်တော့ — recovery အတွင်း apply (အသုံးချ) လုပ်ပြီးသား နောက်ဆုံး WAL record ရဲ့ location မှာ တည်ငြိမ်စွာ ရှိနေပါလိမ့်မယ်။ Server ကို recovery မပါဘဲ ပုံမှန် စတင်ထားတာဆိုရင် — function က NULL ပြန်ပေးပါတယ်။ |
| pg_last_xact_replay_timestamp () → timestamp with time zone Recovery အတွင်း replay လုပ်ပြီးသား နောက်ဆုံး transaction ရဲ့ time stamp (အချိန်တံဆိပ်) ကို ပြန်ပေးပါတယ်။ ဒါက အဲဒီ transaction အတွက် commit သို့မဟုတ် abort WAL record ကို primary ပေါ်မှာ ထုတ်လုပ်ခဲ့တဲ့ အချိန် ဖြစ်ပါတယ်။ Recovery အတွင်း transaction တစ်ခုမှ replay မလုပ်ရသေးဘူးဆိုရင် — function က NULL ပြန်ပေးပါတယ်။ မဟုတ်ရင် — recovery ဆက်လက် လုပ်ဆောင်နေသေးရင် ဒါက monotonically တိုးလာပြီး — recovery ပြီးစီးသွားရင်တော့ recovery အတွင်း apply လုပ်ပြီးသား နောက်ဆုံး transaction ရဲ့ အချိန်မှာ တည်ငြိမ်စွာ ရှိနေပါလိမ့်မယ်။ Server ကို recovery မပါဘဲ ပုံမှန် စတင်ထားတာဆိုရင် — function က NULL ပြန်ပေးပါတယ်။ |
| pg_get_wal_resource_managers () → setof record ( rm_id integer, rm_name text, rm_builtin boolean ) System ထဲမှာ လက်ရှိ load လုပ်ထားတဲ့ WAL resource managers တွေကို ပြန်ပေးပါတယ်။ `rm_builtin` column က — ၎င်းက built-in resource manager လား၊ extension တစ်ခုက load လုပ်တဲ့ custom resource manager လားဆိုတာကို ညွှန်ပြပါတယ်။ |

ဇယား 9.99 မှာ ပြထားတဲ့ functions တွေက recovery ရဲ့ တိုးတက်မှုကို ထိန်းချုပ်ပါတယ်။ ဒီ functions တွေကို recovery အတွင်းမှာသာ run လို့ ရပါတယ်။

**ဇယား 9.99. Recovery Control Functions (recovery ထိန်းချုပ်ရေး လုပ်ဆောင်ချက်များ)**

| လုပ်ဆောင်ချက် ဖော်ပြချက် |
| --- |
| pg_is_wal_replay_paused () → boolean Recovery pause (ရပ်နားခြင်း) ကို တောင်းဆိုထားရင် true ပြန်ပေးပါတယ်။ |
| pg_get_wal_replay_pause_state () → text Recovery pause state (ရပ်နားမှု အခြေအနေ) ကို ပြန်ပေးပါတယ်။ ပြန်ပေးတဲ့ တန်ဖိုးတွေကတော့ — pause တောင်းဆိုထားခြင်း မရှိရင် `not paused`၊ pause တောင်းဆိုထားပေမယ့် recovery က တကယ် မရပ်သေးရင် `pause requested`၊ ပြီးတော့ recovery တကယ် ရပ်နေရင်တော့ `paused` ဖြစ်ပါတယ်။ |
| pg_promote ( wait boolean DEFAULT true, wait_seconds integer DEFAULT 60 ) → boolean Standby server တစ်ခုကို primary အဆင့်အတန်းဆီ promote (ရာထူးတိုး) လုပ်ပေးပါတယ်။ `wait` ကို true (ပုံမှန်) ထားရင် — function က promotion ပြီးစီးတဲ့အထိ သို့မဟုတ် `wait_seconds` စက္ကန့် ကုန်ဆုံးတဲ့အထိ စောင့်ပြီး — promotion အောင်မြင်ရင် true၊ မအောင်မြင်ရင် false ပြန်ပေးပါတယ်။ `wait` ကို false ထားရင် — promotion ကို စတင်ဖို့ postmaster ဆီ SIGUSR1 signal ပို့ပြီးနောက် function က ချက်ချင်း true ပြန်ပေးပါတယ်။ ဒီ function ကို ပုံမှန်အားဖြင့် superuser များသာ အသုံးပြုနိုင်ပြီး — အခြား user များကိုမူ ဒီ function ကို run လုပ်နိုင်ရန် EXECUTE privilege ပေးအပ်နိုင်ပါတယ်။ |
| pg_wal_replay_pause () → void Recovery ကို ရပ်နားဖို့ တောင်းဆိုပါတယ်။ တောင်းဆိုချက် ရှိရုံနဲ့ recovery က ချက်ချင်း ရပ်သွားတယ်လို့ မဆိုလိုပါဘူး။ Recovery တကယ် ရပ်နေတယ်ဆိုတာကို သေချာစေချင်ရင် — `pg_get_wal_replay_pause_state()` က ပြန်ပေးတဲ့ recovery pause state ကို စစ်ဆေးဖို့ လိုပါတယ်။ `pg_is_wal_replay_paused()` က တောင်းဆိုချက် ရှိမရှိကိုပဲ ပြန်ပေးတာကို သတိပြုပါ။ Recovery ရပ်နေချိန်မှာ — နောက်ထပ် database ပြောင်းလဲမှုတွေကို apply လုပ်မှာ မဟုတ်ပါဘူး။ Hot standby သက်ဝင်နေရင် — query အသစ်တွေ အားလုံးက database ရဲ့ တူညီတဲ့ consistent snapshot (တစ်သမတ်တည်း အခြေအနေ မှတ်တမ်း) ကို မြင်ရမှာ ဖြစ်ပြီး — recovery ပြန်စတင်တဲ့အထိ — နောက်ထပ် query conflicts (ကွဲလွဲမှုများ) တွေ ထွက်ပေါ်မှာ မဟုတ်ပါဘူး။ ဒီ function ကို ပုံမှန်အားဖြင့် superuser များသာ အသုံးပြုနိုင်ပြီး — အခြား user များကိုမူ ဒီ function ကို run လုပ်နိုင်ရန် EXECUTE privilege ပေးအပ်နိုင်ပါတယ်။ |
| pg_wal_replay_resume () → void Recovery ရပ်နားထားခဲ့ရင် ပြန်စပါတယ်။ ဒီ function ကို ပုံမှန်အားဖြင့် superuser များသာ အသုံးပြုနိုင်ပြီး — အခြား user များကိုမူ ဒီ function ကို run လုပ်နိုင်ရန် EXECUTE privilege ပေးအပ်နိုင်ပါတယ်။ |

`pg_wal_replay_pause` နဲ့ `pg_wal_replay_resume` တို့ကို promotion လုပ်ဆောင်နေချိန်မှာ run လို့ မရပါဘူး။ Recovery ရပ်နားထားချိန်မှာ promotion ကို စတင်လိုက်ရင် — paused state က ဆုံးသွားပြီး promotion ဆက်လုပ်ပါတယ်။

Streaming replication ကို disable လုပ်ထားရင် — paused state က ပြဿနာ မရှိဘဲ အကန့်အသတ် မရှိ ဆက်ရှိနေနိုင်ပါတယ်။ Streaming replication လုပ်ဆောင်နေရင်တော့ — WAL records တွေ ဆက်လက် လက်ခံရနေမှာ ဖြစ်ပြီး — pause ရဲ့ ကြာချိန်၊ WAL ထုတ်လုပ်မှုနှုန်း နဲ့ ရနိုင်တဲ့ disk space ပေါ် မူတည်ပြီး — နောက်ဆုံးမှာ disk space ကို ပြည့်စေနိုင်ပါတယ်။

### 9.28.5. Snapshot Synchronization Functions (snapshot ထပ်တူပြုခြင်း လုပ်ဆောင်ချက်များ)

PostgreSQL က database sessions တွေကို — သူတို့ရဲ့ snapshots တွေ ထပ်တူပြုလို့ (synchronize) ရအောင် ခွင့်ပြုပါတယ်။ *Snapshot* ဆိုတာက — snapshot ကို သုံးနေတဲ့ transaction အတွက် ဘယ် data တွေ မြင်ရမယ်ဆိုတာကို သတ်မှတ်ပေးပါတယ်။ Session နှစ်ခု ဒါမှမဟုတ် နှစ်ခုထက်ပိုတာတွေက — database ထဲမှာ တူညီတဲ့ content တွေကို မြင်ရဖို့ လိုအပ်တဲ့အခါ — synchronized snapshots တွေ လိုအပ်ပါတယ်။ Session နှစ်ခုက သူတို့ရဲ့ transactions တွေကို တစ်ခုနဲ့တစ်ခု သီးခြား စတင်လိုက်ရင် — `START TRANSACTION` command နှစ်ခုရဲ့ လုပ်ဆောင်ချက်တွေကြားမှာ — တတိယ transaction တစ်ခုခု commit ဖြစ်သွားနိုင်တဲ့ ဖြစ်နိုင်ခြေ အမြဲ ရှိပါတယ် — အဲဒါကြောင့် session တစ်ခုက အဲဒီ transaction ရဲ့ အကျိုးသက်ရောက်မှုတွေကို မြင်ရပြီး နောက်တစ်ခုက မမြင်ရတဲ့ အခြေအနေ ဖြစ်နိုင်ပါတယ်။

ဒီပြဿနာကို ဖြေရှင်းဖို့ — PostgreSQL က transaction တစ်ခုကို — သူ သုံးနေတဲ့ snapshot ကို *export* (ထုတ်ယူမျှဝေ) လုပ်ခွင့် ပြုပါတယ်။ Export လုပ်ထားတဲ့ transaction က open (ဖွင့်) ထားသရွေ့ — အခြား transactions တွေက ၎င်းရဲ့ snapshot ကို *import* (သွင်းယူ) လုပ်နိုင်ပြီး — ပထမ transaction မြင်ရတဲ့ database ရဲ့ မြင်ကွင်းနဲ့ အတိအကျ တူညီတာကို မြင်ရမယ်လို့ အာမခံချက် ရပါတယ်။ ဒါပေမယ့် — ဒီ transactions တွေထဲက တစ်ခုခုက ပြုလုပ်တဲ့ database ပြောင်းလဲမှုတွေက — uncommitted transactions တွေရဲ့ ပြောင်းလဲမှုတွေအတွက် ပုံမှန်အတိုင်းပဲ — အခြား transactions တွေကို မမြင်ရဘူးဆိုတာ သတိပြုပါ။ ဒါကြောင့် — transactions တွေက ကြိုရှိပြီးသား (pre-existing) data တွေနဲ့ ပတ်သက်လို့ ထပ်တူပြုထားပြီး — သူတို့ ကိုယ်တိုင် ပြုလုပ်တဲ့ ပြောင်းလဲမှုတွေအတွက်တော့ ပုံမှန်အတိုင်း အလုပ်လုပ်ပါတယ်။

Snapshots တွေကို — ဇယား 9.100 မှာ ပြထားတဲ့ `pg_export_snapshot` function နဲ့ export လုပ်ပြီး — [SET TRANSACTION](https://www.postgresql.org/docs/current/sql-set-transaction.html) command နဲ့ import လုပ်ပါတယ်။

**ဇယား 9.100. Snapshot Synchronization Functions (snapshot ထပ်တူပြုခြင်း လုပ်ဆောင်ချက်များ)**

| လုပ်ဆောင်ချက် ဖော်ပြချက် |
| --- |
| pg_export_snapshot () → text Transaction ရဲ့ လက်ရှိ snapshot ကို သိမ်းဆည်းပြီး — snapshot ကို ခွဲခြားသတ်မှတ်ပေးတဲ့ text string တစ်ခုကို ပြန်ပေးပါတယ်။ ဒီ string ကို — snapshot ကို import လုပ်ချင်တဲ့ clients တွေဆီ (database အပြင်ဘက်ကနေ) ပေးပို့ရပါမယ်။ Snapshot ကို — ၎င်းကို export လုပ်ခဲ့တဲ့ transaction ရဲ့ အဆုံးအထိပဲ import လုပ်ဖို့ ရနိုင်ပါတယ်။ Transaction တစ်ခုက လိုအပ်ရင် snapshot တစ်ခုထက်ပိုပြီးလည်း export လုပ်နိုင်ပါတယ်။ ဒီလိုလုပ်တာက READ COMMITTED transactions တွေမှာသာ အသုံးဝင်တာကို သတိပြုပါ — REPEATABLE READ နဲ့ ၎င်းထက် မြင့်တဲ့ isolation levels တွေမှာ — transactions တွေက သူတို့ရဲ့ သက်တမ်းတစ်လျှောက် snapshot တစ်ခုတည်းကိုပဲ သုံးလို့ပါ။ Transaction တစ်ခုက snapshot တစ်ခုခု export လုပ်ပြီးသွားရင် — ၎င်းကို PREPARE TRANSACTION နဲ့ prepare လုပ်လို့ မရတော့ပါဘူး။ |
| pg_log_standby_snapshot () → pg_lsn Run နေတဲ့ transactions တွေရဲ့ snapshot တစ်ခုကို ယူပြီး — bgwriter ဒါမှမဟုတ် checkpointer က တစ်ခု log လုပ်ဖို့ မစောင့်ဘဲ — WAL ထဲကို ရေးသားပါတယ်။ ဒါက standby ပေါ်မှာ logical decoding (ယုတ္တိ ကုဒ်ဖော်ခြင်း) အတွက် အသုံးဝင်ပါတယ် — logical slot တစ်ခု ဖန်တီးတာက — အဲဒီလို record တစ်ခုကို standby ပေါ်မှာ replay လုပ်ပြီးတဲ့အထိ စောင့်ရလို့ပါ။ |

### 9.28.6. Replication Management Functions (replication စီမံခန့်ခွဲမှု လုပ်ဆောင်ချက်များ)

ဇယား 9.101 မှာ ပြထားတဲ့ functions တွေက — replication features တွေကို ထိန်းချုပ်ဖို့နဲ့ အပြန်အလှန် ဆက်သွယ်ဖို့ အတွက် ဖြစ်ပါတယ်။ နောက်ခံ features တွေအကြောင်း အချက်အလက်အတွက် [အပိုင်း 26.2.5](https://www.postgresql.org/docs/current/warm-standby.html#STREAMING-REPLICATION)၊ [အပိုင်း 26.2.6](https://www.postgresql.org/docs/current/warm-standby.html#STREAMING-REPLICATION-SLOTS) နဲ့ [အခန်း 48](https://www.postgresql.org/docs/current/replication-origins.html) ကို ကြည့်ပါ။ Replication origin အတွက် functions တွေကို ပုံမှန်အားဖြင့် superuser သာ အသုံးပြုခွင့် ရှိပြီး — `GRANT` command သုံးပြီးတော့ အခြား users တွေကိုလည်း ခွင့်ပြုနိုင်ပါတယ်။ Replication slots အတွက် functions တွေကိုတော့ superusers တွေနဲ့ `REPLICATION` privilege ရှိတဲ့ users တွေသာ အသုံးပြုနိုင်ပါတယ်။

ဒီ functions တွေ အများစုမှာ replication protocol ထဲမှာ ညီမျှတဲ့ commands တွေ ရှိပါတယ်; [အပိုင်း 54.4](https://www.postgresql.org/docs/current/protocol-replication.html) ကို ကြည့်ပါ။

အပိုင်း 9.28.3၊ အပိုင်း 9.28.4 နဲ့ အပိုင်း 9.28.5 တွေမှာ ဖော်ပြထားတဲ့ functions တွေကလည်း replication အတွက် သက်ဆိုင်ပါတယ်။

| pg_replication_origin_xact_setup ( origin_lsn pg_lsn, origin_timestamp timestamp with time zone ) → void လက်ရှိ transaction ကို — ပေးထားတဲ့ LSN နဲ့ timestamp မှာ commit လုပ်ပြီးသား transaction တစ်ခုကို replay လုပ်နေတယ်လို့ မှတ်သားပါတယ်။ `pg_replication_origin_session_setup` သုံးပြီး replication origin တစ်ခု ရွေးချယ်ထားမှသာ ခေါ်လို့ ရပါတယ်။ |
| pg_replication_origin_xact_reset () → void `pg_replication_origin_xact_setup()` ရဲ့ အကျိုးသက်ရောက်မှုတွေကို ပယ်ဖျက်ပါတယ်။ |
| pg_replication_origin_advance ( node_name text, lsn pg_lsn ) → void ပေးထားတဲ့ node အတွက် replication progress ကို ပေးထားတဲ့ location မှာ သတ်မှတ်ပေးပါတယ်။ ဒါက အဓိကအားဖြင့် — ကနဦး location တစ်ခု သတ်မှတ်ဖို့ ဒါမှမဟုတ် — configuration ပြောင်းလဲမှုတွေနဲ့ အလားတူ အခြေအနေတွေပြီးနောက် location အသစ်တစ်ခု သတ်မှတ်ဖို့ အသုံးဝင်ပါတယ်။ ဒီ function ကို ဂရုမစိုက်ဘဲ သုံးမိရင် — ညီညွတ်မှု မရှိတဲ့ (inconsistently) replicated data တွေ ဖြစ်လာနိုင်တာကို သတိထားပါ။ |
| pg_replication_origin_progress ( node_name text, flush boolean ) → pg_lsn ပေးထားတဲ့ replication origin အတွက် replay location ကို ပြန်ပေးပါတယ်။ `flush` parameter က — သက်ဆိုင်ရာ local transaction ကို disk ပေါ်ကို flush လုပ်ပြီးသား ဖြစ်မယ်လို့ အာမခံမလား ဆိုတာကို သတ်မှတ်ပါတယ်။ |
| pg_logical_emit_message ( transactional boolean, prefix text, content text [, flush boolean DEFAULT false] ) → pg_lsn pg_logical_emit_message ( transactional boolean, prefix text, content bytea [, flush boolean DEFAULT false] ) → pg_lsn Logical decoding message တစ်ခုကို ထုတ်လွှတ်ပါတယ်။ ဒါကို WAL ကနေတစ်ဆင့် logical decoding plugins တွေဆီ generic messages တွေ ပေးပို့ဖို့ သုံးနိုင်ပါတယ်။ `transactional` parameter က — message က လက်ရှိ transaction ရဲ့ အစိတ်အပိုင်း ဖြစ်သင့်လား၊ ဒါမှမဟုတ် — ချက်ချင်း ရေးသားပြီး logical decoder က record ကို ဖတ်တာနဲ့ ချက်ချင်း decode လုပ်သင့်လားဆိုတာကို သတ်မှတ်ပါတယ်။ `prefix` parameter က — logical decoding plugins တွေက သူတို့အတွက် စိတ်ဝင်စားစရာ messages တွေကို လွယ်လွယ်ကူကူ မှတ်မိနိုင်အောင် သုံးနိုင်တဲ့ textual prefix တစ်ခု ဖြစ်ပါတယ်။ `content` parameter က message ရဲ့ ပါဝင်စရာ ဖြစ်ပြီး — text ဒါမှမဟုတ် binary ပုံစံ နှစ်မျိုးလုံးနဲ့ ပေးနိုင်ပါတယ်။ `flush` parameter (ပုံမှန် false) က — message ကို WAL ဆီ ချက်ချင်း flush လုပ်မလား ဆိုတာကို ထိန်းချုပ်ပါတယ်။ `transactional` နဲ့တွဲရင် flush က အကျိုးသက်ရောက်မှု မရှိပါဘူး — message ရဲ့ WAL record က ၎င်းရဲ့ transaction နဲ့အတူ flush လုပ်ခံရလို့ပါ။ |
| pg_sync_replication_slots () → void Logical failover replication slots တွေကို primary server ကနေ standby server ဆီ ထပ်တူပြု (synchronize) လုပ်ပါတယ်။ ဒီ function ကို standby server ပေါ်မှာသာ run လို့ ရပါတယ်။ Temporary synced slots တွေ (ရှိရင်) ကို logical decoding အတွက် သုံးလို့ မရဘဲ — promotion ပြီးနောက်မှာ ဖျက်ပစ်ရပါမယ်။ အသေးစိတ်အတွက် အပိုင်း 47.2.3 ကို ကြည့်ပါ။ ဒီ function ကို အဓိကအားဖြင့် testing နဲ့ debugging ရည်ရွယ်ချက်တွေအတွက် ရည်ရွယ်ထားပြီး — သတိထားပြီးမှ သုံးသင့်တာကို သတိပြုပါ။ ထို့အပြင် — `sync_replication_slots` ကို enable လုပ်ထားပြီး slots တွေရဲ့ ထပ်တူပြုခြင်းကို လုပ်ဆောင်ဖို့ slotsync worker က လည်ပတ်နေပြီးသားဆိုရင် — ဒီ function ကို run လို့ မရပါဘူး။ **သတိပြုရန်:** function ကို run လုပ်ပြီးနောက်မှာ — standby ပေါ်က `hot_standby_feedback` ကို disable လုပ်လိုက်ရင် သို့မဟုတ် `primary_slot_name` ထဲမှာ သတ်မှတ်ထားတဲ့ physical slot ကို ဖယ်ရှားလိုက်ရင် — synchronized slot ရဲ့ လိုအပ်တဲ့ rows တွေကို primary server ပေါ်က VACUUM process က ဖယ်ရှားပစ်နိုင်ပြီး — synchronized slot က invalidated (အသုံးမဝင်တော့သော) ဖြစ်သွားနိုင်ပါတယ်။ |

### 9.28.7. Database Object Management Functions (database object စီမံခန့်ခွဲမှု လုပ်ဆောင်ချက်များ)

ဇယား 9.102 မှာ ပြထားတဲ့ functions တွေက — database objects တွေရဲ့ disk space အသုံးပြုမှုကို တွက်ချက်ပေးတာ ဒါမှမဟုတ် — အသုံးပြုမှု ရလဒ်တွေကို ပြသခြင်း/နားလည်ခြင်းမှာ အထောက်အကူ ပြုပါတယ်။ `bigint` ရလဒ်တွေကို bytes နဲ့ တိုင်းတာပါတယ်။ ရှိပြီးသား object တစ်ခုကို ကိုယ်စားမပြုတဲ့ OID တစ်ခုကို ဒီ functions တွေထဲက တစ်ခုဆီ ပေးလိုက်ရင် — NULL ပြန်ပေးပါတယ်။

**ဇယား 9.102. Database Object Size Functions (database object အရွယ်အစား လုပ်ဆောင်ချက်များ)**

| လုပ်ဆောင်ချက် ဖော်ပြချက် |
| --- |
| pg_column_size ( "any" ) → integer ဘယ် individual data value တစ်ခုကိုမဆို သိမ်းဆည်းဖို့ သုံးတဲ့ bytes အရေအတွက်ကို ပြသပါတယ်။ Table column တစ်ခုရဲ့ တန်ဖိုးပေါ်ကို တိုက်ရိုက် apply လုပ်ရင် — လုပ်ထားခဲ့တဲ့ compression (ချုံ့မှု) တွေကိုပါ ထင်ဟပ်ပြပါတယ်။ |
| pg_column_compression ( "any" ) → text Individual variable-length တန်ဖိုးတစ်ခုကို ချုံ့ဖို့ သုံးခဲ့တဲ့ compression algorithm ကို ပြသပါတယ်။ တန်ဖိုးကို ချုံ့မထားရင် NULL ပြန်ပေးပါတယ်။ |
| pg_column_toast_chunk_id ( "any" ) → oid Disk ပေါ်မှာ ရှိတဲ့ TOASTed တန်ဖိုးတစ်ခုရဲ့ chunk_id ကို ပြသပါတယ်။ တန်ဖိုးက un-TOASTed ဖြစ်နေရင် ဒါမှမဟုတ် disk ပေါ်မှာ မရှိရင် NULL ပြန်ပေးပါတယ်။ TOAST အကြောင်း ပိုမိုသိရှိရန် အပိုင်း 66.2 ကို ကြည့်ပါ။ |
| pg_database_size ( name ) → bigint pg_database_size ( oid ) → bigint သတ်မှတ်ထားတဲ့ name ဒါမှမဟုတ် OID ရှိတဲ့ database က အသုံးပြုထားတဲ့ စုစုပေါင်း disk space ကို တွက်ချက်ပါတယ်။ ဒီ function ကို သုံးဖို့ — သတ်မှတ်ထားတဲ့ database ပေါ်မှာ CONNECT privilege (ပုံမှန်အားဖြင့် ပေးထားတယ်) ရှိရမယ် ဒါမှမဟုတ် `pg_read_all_stats` role ရဲ့ privileges တွေ ရှိရပါမယ်။ |
| pg_indexes_size ( regclass ) → bigint သတ်မှတ်ထားတဲ့ table နဲ့ ချိတ်ထားတဲ့ indexes တွေ အသုံးပြုတဲ့ စုစုပေါင်း disk space ကို တွက်ချက်ပါတယ်။ |
| pg_relation_size ( relation regclass [, fork text ] ) → bigint သတ်မှတ်ထားတဲ့ relation ရဲ့ “fork” တစ်ခု အသုံးပြုတဲ့ disk space ကို တွက်ချက်ပါတယ်။ (အများစုအတွက်တော့ — forks အားလုံးရဲ့ အရွယ်အစားတွေကို ပေါင်းပေးတဲ့ — အဆင့်မြင့် functions ဖြစ်တဲ့ pg_total_relation_size ဒါမှမဟုတ် pg_table_size တွေကို သုံးတာ ပိုအဆင်ပြေတာကို သတိပြုပါ။) Argument တစ်ခုတည်းနဲ့ ဆိုရင် — relation ရဲ့ main data fork ရဲ့ အရွယ်အစားကို ပြန်ပေးပါတယ်။ ဒုတိယ argument ကို ပေးပြီး ဘယ် fork ကို စစ်ဆေးမယ်ဆိုတာ သတ်မှတ်နိုင်ပါတယ်: `main` — relation ရဲ့ main data fork ရဲ့ အရွယ်အစား။ `fsm` — relation နဲ့ ဆက်စပ်နေတဲ့ Free Space Map ရဲ့ အရွယ်အစား (အပိုင်း 66.3 ကို ကြည့်ပါ)။ `vm` — relation နဲ့ ဆက်စပ်နေတဲ့ Visibility Map ရဲ့ အရွယ်အစား (အပိုင်း 66.4 ကို ကြည့်ပါ)။ `init` — relation နဲ့ ဆက်စပ်နေတဲ့ initialization fork (ရှိရင်) ရဲ့ အရွယ်အစား။ |
| pg_size_bytes ( text ) → bigint pg_size_pretty က ပြန်ပေးတဲ့ လူဖတ်လို့ ရတဲ့ (human-readable) format ရှိတဲ့ အရွယ်အစားတစ်ခုကို bytes အဖြစ် ပြောင်းပေးပါတယ်။ တရားဝင် units တွေက bytes, B, kB, MB, GB, TB နဲ့ PB ဖြစ်ပါတယ်။ |
| pg_size_pretty ( bigint ) → text pg_size_pretty ( numeric ) → text bytes ရှိတဲ့ အရွယ်အစားတစ်ခုကို — size units (သင့်လျော်သလို bytes, kB, MB, GB, TB ဒါမှမဟုတ် PB) တွေနဲ့ — လူဖတ်ရ ပိုလွယ်တဲ့ format အဖြစ် ပြောင်းပေးပါတယ်။ Units တွေက 10 ၏ ထပ်ကိန်းများ မဟုတ်ဘဲ — 2 ၏ ထပ်ကိန်းများ ဖြစ်တာကို သတိပြုပါ — ဒါကြောင့် 1kB က 1024 bytes၊ 1MB က 1024^2 = 1048576 bytes စသဖြင့် ဖြစ်ပါတယ်။ |
| pg_table_size ( regclass ) → bigint သတ်မှတ်ထားတဲ့ table အသုံးပြုတဲ့ disk space ကို တွက်ချက်ပါတယ် — indexes တွေ မပါဝင်ဘဲ (ဒါပေမယ့် TOAST table (ရှိရင်)၊ free space map နဲ့ visibility map တွေတော့ ပါဝင်ပါတယ်)။ |
| pg_tablespace_size ( name ) → bigint pg_tablespace_size ( oid ) → bigint သတ်မှတ်ထားတဲ့ name ဒါမှမဟုတ် OID ရှိတဲ့ tablespace ထဲမှာ အသုံးပြုထားတဲ့ စုစုပေါင်း disk space ကို တွက်ချက်ပါတယ်။ ဒီ function ကို သုံးဖို့ — သတ်မှတ်ထားတဲ့ tablespace ပေါ်မှာ CREATE privilege ရှိရမယ် ဒါမှမဟုတ် `pg_read_all_stats` role ရဲ့ privileges တွေ ရှိရပါမယ် — လက်ရှိ database ရဲ့ default tablespace မဟုတ်ဘူးဆိုရင်။ |
| pg_total_relation_size ( regclass ) → bigint သတ်မှတ်ထားတဲ့ table အသုံးပြုတဲ့ စုစုပေါင်း disk space ကို တွက်ချက်ပါတယ် — indexes နဲ့ TOAST data တွေ အားလုံး အပါအဝင်။ ရလဒ်က pg_table_size + pg_indexes_size နဲ့ ညီမျှပါတယ်။ |

အပေါ်က functions တွေထဲက — tables ဒါမှမဟုတ် indexes တွေပေါ်မှာ လုပ်ဆောင်တဲ့ ဟာတွေက `regclass` argument တစ်ခုကို လက်ခံပါတယ် — ဒါက `pg_class` system catalog ထဲက table ဒါမှမဟုတ် index ရဲ့ OID သက်သက်ပဲ ဖြစ်ပါတယ်။ ဒါပေမယ့် — `regclass` data type ရဲ့ input converter က သင့်အတွက် အလုပ် လုပ်ပေးတာမို့ — OID ကို ကိုယ်တိုင် ရှာဖို့ မလိုပါဘူး။ အသေးစိတ်အတွက် [အပိုင်း 8.19](/docs/postgresql/datatype-oid) ကို ကြည့်ပါ။

Collations (စာလုံးစဉ် စည်းမျဉ်းများ) တွေကို စီမံခန့်ခွဲဖို့ သုံးတဲ့ functions တွေကို ဇယား 9.104 မှာ စာရင်းပြထားပါတယ်။

**ဇယား 9.104. Collation Management Functions (collation စီမံခန့်ခွဲမှု လုပ်ဆောင်ချက်များ)**

Statistics (ကိန်းဂဏန်း အချက်အလက်များ) တွေကို ပြုပြင်ဖို့ သုံးတဲ့ functions တွေကို ဇယား 9.105 မှာ စာရင်းပြထားပါတယ်။ ဒီ functions တွေကို recovery အတွင်း run လို့ မရပါဘူး။

> **သတိပေးချက်:** ဒီ statistics manipulation functions တွေကြောင့် ပြုလုပ်တဲ့ ပြောင်းလဲမှုတွေက — [autovacuum](https://www.postgresql.org/docs/current/routine-vacuuming.html#AUTOVACUUM) (သို့မဟုတ် manual `VACUUM` ဒါမှမဟုတ် `ANALYZE`) က ပြန်ရေးသားဖျက်သိမ်း (overwrite) ပစ်နိုင်ခြေ ရှိပြီး — ယာယီသာ ဖြစ်တယ်လို့ မှတ်ယူသင့်ပါတယ်။

**ဇယား 9.105. Database Object Statistics Manipulation Functions (database object statistics ပြုပြင်ရေး လုပ်ဆောင်ချက်များ)**

| pg_restore_relation_stats ( VARIADIC kwargs "any" ) → boolean Table-level statistics (table အဆင့် ကိန်းဂဏန်း အချက်အလက်များ) တွေကို update လုပ်ပါတယ်။ ပုံမှန်အားဖြင့် ဒီ statistics တွေကို VACUUM ဒါမှမဟုတ် ANALYZE ရဲ့ တစ်စိတ်တစ်ပိုင်းအနေနဲ့ အလိုအလျောက် စုဆောင်း/update လုပ်တာမို့ — ဒီ function ကို ခေါ်ဖို့ မလိုပါဘူး။ ဒါပေမယ့် — restore လုပ်ပြီးနောက်မှာ ANALYZE ကို မလုပ်ရသေးဘဲ — optimizer က ပိုကောင်းတဲ့ plans တွေ ရွေးချယ်နိုင်ဖို့ — ဒီ function က အသုံးဝင်ပါတယ်။ ခြေရာခံထားတဲ့ statistics တွေက version တစ်ခုနဲ့တစ်ခု ပြောင်းလဲနိုင်တာမို့ — arguments တွေကို argname နဲ့ argvalue တွဲတွေအနေနဲ့ ဒီပုံစံ ပေးပို့ပါတယ်: SELECT pg_restore_relation_stats(     'arg1name', 'arg1value'::arg1type,     'arg2name', 'arg2value'::arg2type,     'arg3name', 'arg3value'::arg3type); ဥပမာ — `mytable` table အတွက် relpages နဲ့ reltuples တန်ဖိုးတွေ သတ်မှတ်ဖို့: SELECT pg_restore_relation_stats(     'schemaname', 'myschema',     'relname',    'mytable',     'relpages',   173::integer,     'reltuples',  10000::real); `schemaname` နဲ့ `relname` arguments တွေက မဖြစ်မနေ လိုအပ်ပြီး — table ကို သတ်မှတ်ပါတယ်။ ကျန်တဲ့ arguments တွေက pg_class ထဲက column တချို့နဲ့ သက်ဆိုင်တဲ့ statistics တွေရဲ့ နာမည်တွေနဲ့ တန်ဖိုးတွေ ဖြစ်ပါတယ်။ လက်ရှိ ထောက်ပံ့ထားတဲ့ relation statistics တွေကတော့ — integer type တန်ဖိုးရှိတဲ့ relpages၊ real type တန်ဖိုးရှိတဲ့ reltuples၊ integer type တန်ဖိုးရှိတဲ့ relallvisible နဲ့ integer type တန်ဖိုးရှိတဲ့ relallfrozen တို့ ဖြစ်ပါတယ်။ ထို့အပြင် — ဒီ function က integer type ရှိတဲ့ version ဆိုတဲ့ argument name ကိုလည်း လက်ခံပြီး — အဲဒါက statistics တွေ စတင်ခဲ့တဲ့ server version ကို သတ်မှတ်ပါတယ်။ ဒါက PostgreSQL ရဲ့ ဗားရှင်းအဟောင်းတွေကနေ statistics တွေကို ရွှေ့ပြောင်း (porting) လုပ်ရာမှာ အသုံးဝင်ဖို့ မျှော်လင့်ထားပါတယ်။ အသေးစား error တွေကို WARNING အဖြစ် အစီရင်ခံပြီး လျစ်လျူရှုကာ — ကျန်တဲ့ statistics တွေကို ဆက်ပြီး restore လုပ်ပါလိမ့်မယ်။ သတ်မှတ်ထားတဲ့ statistics တွေ အားလုံး အောင်မြင်စွာ restore ဖြစ်ရင် true၊ မဟုတ်ရင် false ပြန်ပေးပါတယ်။ ခေါ်ဆိုသူက table ပေါ်မှာ MAINTAIN privilege ရှိရမယ် ဒါမှမဟုတ် database ရဲ့ owner ဖြစ်ရပါမယ်။ |

မဖြစ်မနေ လိုအပ်တဲ့ arguments တွေကတော့ — text type တန်ဖိုးရှိတဲ့ `schemaname` နဲ့ `relname` (table ကို သတ်မှတ်ပေးတယ်)၊ text type တန်ဖိုးရှိတဲ့ `attname` ဒါမှမဟုတ် smallint type တန်ဖိုးရှိတဲ့ `attnum` (column ကို သတ်မှတ်ပေးတယ်)၊ ပြီးတော့ statistics တွေမှာ child tables ကနေ တန်ဖိုးတွေ ပါဝင်မလား ဆိုတာကို သတ်မှတ်ပေးတဲ့ `inherited` တို့ ဖြစ်ပါတယ်။ ကျန်တဲ့ arguments တွေက pg_stats ထဲက columns တွေနဲ့ သက်ဆိုင်တဲ့ statistics တွေရဲ့ နာမည်တွေနဲ့ တန်ဖိုးတွေ ဖြစ်ပါတယ်။ ထို့အပြင် — ဒီ function က integer type ရှိတဲ့ version ဆိုတဲ့ argument name ကိုလည်း လက်ခံပြီး — အဲဒါက statistics တွေ စတင်ခဲ့တဲ့ server version ကို သတ်မှတ်ပါတယ်။ ဒါက PostgreSQL ရဲ့ ဗားရှင်းအဟောင်းတွေကနေ statistics တွေကို ရွှေ့ပြောင်း (porting) လုပ်ရာမှာ အသုံးဝင်ဖို့ မျှော်လင့်ထားပါတယ်။ အသေးစား error တွေကို WARNING အဖြစ် အစီရင်ခံပြီး လျစ်လျူရှုကာ — ကျန်တဲ့ statistics တွေကို ဆက်ပြီး restore လုပ်ပါလိမ့်မယ်။ သတ်မှတ်ထားတဲ့ statistics တွေ အားလုံး အောင်မြင်စွာ restore ဖြစ်ရင် true၊ မဟုတ်ရင် false ပြန်ပေးပါတယ်။ ခေါ်ဆိုသူက table ပေါ်မှာ MAINTAIN privilege ရှိရမယ် ဒါမှမဟုတ် database ရဲ့ owner ဖြစ်ရပါမယ်။ |
| pg_clear_attribute_stats ( schemaname text, relname text, attname text, inherited boolean ) → void ပေးထားတဲ့ relation နဲ့ attribute အတွက် column-level statistics တွေကို — table အသစ် ဖန်တီးထားသလိုမျိုး — ရှင်းလင်းပါတယ်။ ခေါ်ဆိုသူက table ပေါ်မှာ MAINTAIN privilege ရှိရမယ် ဒါမှမဟုတ် database ရဲ့ owner ဖြစ်ရပါမယ်။ |

Partitioned tables တွေရဲ့ ဖွဲ့စည်းပုံအကြောင်း အချက်အလက်တွေ ပေးတဲ့ functions တွေကို ဇယား 9.106 မှာ စာရင်းပြထားပါတယ်။

**ဇယား 9.106. Partitioning Information Functions (partitioning အချက်အလက် လုပ်ဆောင်ချက်များ)**

| လုပ်ဆောင်ချက် ဖော်ပြချက် |
| --- |
| pg_partition_tree ( regclass ) → setof record ( relid regclass, parentrelid regclass, isleaf boolean, level integer ) ပေးထားတဲ့ partitioned table ဒါမှမဟုတ် partitioned index ရဲ့ partition tree ထဲမှာ ရှိတဲ့ tables ဒါမှမဟုတ် indexes တွေကို — partition တစ်ခုစီအတွက် row တစ်ခုစီနဲ့ — စာရင်းပြုစုပါတယ်။ ပေးအပ်တဲ့ အချက်အလက်တွေထဲမှာ — partition ရဲ့ OID၊ ၎င်းရဲ့ တိုက်ရိုက် parent ရဲ့ OID၊ partition က leaf (အရွက်) ဟုတ်မဟုတ် ပြောတဲ့ boolean တန်ဖိုး နဲ့ — hierarchy (အဆင့်ဆင့်) ထဲမှာ ၎င်းရဲ့ level ကို ပြောတဲ့ integer တန်ဖိုး ပါဝင်ပါတယ်။ Level တန်ဖိုးက input table ဒါမှမဟုတ် index အတွက် 0၊ ၎င်းရဲ့ တိုက်ရိုက် child partitions တွေအတွက် 1၊ သူတို့ရဲ့ partitions တွေအတွက် 2 စသဖြင့် ဖြစ်ပါတယ်။ Relation က မရှိဘူးဆိုရင် ဒါမှမဟုတ် partition ဒါမှမဟုတ် partitioned table မဟုတ်ဘူးဆိုရင် rows ဘာမှ မပြန်ပါဘူး။ |
| pg_partition_ancestors ( regclass ) → setof regclass ပေးထားတဲ့ partition ရဲ့ ancestor relations (ဘိုးဘေး relation များ) တွေကို — relation ကိုယ်တိုင် အပါအဝင် — စာရင်းပြုစုပါတယ်။ Relation က မရှိဘူးဆိုရင် ဒါမှမဟုတ် partition ဒါမှမဟုတ် partitioned table မဟုတ်ဘူးဆိုရင် rows ဘာမှ မပြန်ပါဘူး။ |
| pg_partition_root ( regclass ) → regclass ပေးထားတဲ့ relation ပါဝင်တဲ့ partition tree ရဲ့ အထက်ဆုံး parent ကို ပြန်ပေးပါတယ်။ Relation က မရှိဘူးဆိုရင် ဒါမှမဟုတ် partition ဒါမှမဟုတ် partitioned table မဟုတ်ဘူးဆိုရင် NULL ပြန်ပေးပါတယ်။ |

ဥပမာ — `measurement` ဆိုတဲ့ partitioned table တစ်ခုထဲမှာ ပါဝင်တဲ့ data ရဲ့ စုစုပေါင်း အရွယ်အစားကို စစ်ဆေးချင်ရင် — အောက်ပါ query ကို သုံးနိုင်ပါတယ်:

```sql
SELECT pg_size_pretty(sum(pg_relation_size(relid))) AS total_size
  FROM pg_partition_tree('measurement');
```

### 9.28.8. Index Maintenance Functions (index ထိန်းသိမ်းမှု လုပ်ဆောင်ချက်များ)

Index maintenance (index ထိန်းသိမ်းမှု) လုပ်ငန်းတွေအတွက် ရနိုင်တဲ့ functions တွေကို ဇယား 9.107 မှာ ပြထားပါတယ်။ (ဒီ maintenance လုပ်ငန်းတွေကို ပုံမှန်အားဖြင့် autovacuum က အလိုအလျောက် လုပ်ပေးတာမို့ — ဒီ functions တွေကို အထူး ကိစ္စတွေမှာသာ သုံးဖို့ လိုပါတယ်ဆိုတာ သတိပြုပါ။) ဒီ functions တွေကို recovery အတွင်း run လို့ မရပါဘူး။ ဒီ functions တွေကို superusers တွေနဲ့ သတ်မှတ်ထားတဲ့ index ရဲ့ owner သာ အသုံးပြုနိုင်ပါတယ်။

**ဇယား 9.107. Index Maintenance Functions (index ထိန်းသိမ်းမှု လုပ်ဆောင်ချက်များ)**

| လုပ်ဆောင်ချက် ဖော်ပြချက် |
| --- |
| brin_summarize_new_values ( index regclass ) → integer သတ်မှတ်ထားတဲ့ BRIN index ကို scan လုပ်ပြီး — base table ထဲမှာ index က လောလောဆယ် summarize (အကျဉ်းချုပ်) မလုပ်ရသေးတဲ့ page ranges တွေကို ရှာပါတယ်; အဲဒီလို range တစ်ခုစီအတွက် — အဲဒီ table pages တွေကို scan လုပ်ပြီး summary index tuple အသစ်တစ်ခု ဖန်တီးပါတယ်။ Index ထဲကို ထည့်သွင်းလိုက်တဲ့ page range summaries အသစ် အရေအတွက်ကို ပြန်ပေးပါတယ်။ |

| gin_clean_pending_list ( index regclass ) → bigint သတ်မှတ်ထားတဲ့ GIN index ရဲ့ “pending” list ကို — အထဲက entries တွေကို အမြောက်အမြား (in bulk) — main GIN data structure ဆီ ရွှေ့ပြီး — သန့်ရှင်းပေးပါတယ်။ Pending list ကနေ ဖယ်ရှားလိုက်တဲ့ pages အရေအတွက်ကို ပြန်ပေးပါတယ်။ Argument က fastupdate option ကို disable လုပ်ပြီး တည်ဆောက်ထားတဲ့ GIN index တစ်ခုဆိုရင် — index မှာ pending list မရှိတာကြောင့် — ဘာမှ သန့်ရှင်းမှု မဖြစ်ဘဲ ရလဒ်က zero ဖြစ်ပါတယ်။ Pending list နဲ့ fastupdate option အကြောင်း အသေးစိတ်အတွက် အပိုင်း 65.4.4.1 နဲ့ အပိုင်း 65.4.5 ကို ကြည့်ပါ။ |

### 9.28.9. Generic File Access Functions (file access အထွေထွေ လုပ်ဆောင်ချက်များ)

ဇယား 9.108 မှာ ပြထားတဲ့ functions တွေက — server ကို host လုပ်ထားတဲ့ machine ပေါ်က files တွေကို မူရင်း (native) အတိုင်း ဝင်ရောက်ခွင့် ပေးပါတယ်။ User က superuser ဖြစ်နေရင် သို့မဟုတ် `pg_read_server_files` role ကို ပေးအပ်ခံထားရမှသာလွဲလို့ — database cluster directory နဲ့ `log_directory` အတွင်းက files တွေကိုပဲ ဝင်ရောက်နိုင်ပါတယ်။ Cluster directory ထဲက files တွေအတွက် relative path (ဆွေမျိုး လမ်းကြောင်း) တစ်ခုကို သုံးပြီး — log files တွေအတွက်တော့ `log_directory` configuration setting နဲ့ ကိုက်ညီတဲ့ path တစ်ခုကို သုံးပါ။

`pg_read_file()` ဒါမှမဟုတ် ဆက်စပ် functions တွေပေါ်မှာ users တွေကို `EXECUTE` privilege ပေးလိုက်ရင် — database server process ဖတ်နိုင်တဲ့ server ပေါ်က file တိုင်းကို ဖတ်နိုင်စွမ်း ရှိသွားစေတာကို သတိပြုပါ — ဒီ functions တွေက database အတွင်းက privilege စစ်ဆေးမှုတွေ အားလုံးကို ကျော်လွှားသွားလို့ပါ။ ဆိုလိုတာက — ဥပမာ — အဲဒီလို access ရှိတဲ့ user တစ်ယောက်က — authentication အချက်အလက်တွေ သိမ်းထားတဲ့ `pg_authid` table ရဲ့ ပါဝင်စရာတွေကိုရော — database ထဲက ဘယ် table data ကိုမဆိုပါ ဖတ်နိုင်ပါတယ်။ ဒါကြောင့် — ဒီ functions တွေဆီ access ပေးအပ်တာကို သေချာ စဉ်းစားသင့်ပါတယ်။

ဒီ functions တွေပေါ်မှာ privilege ပေးအပ်တဲ့အခါ — optional parameters တွေ ပြထားတဲ့ table entries တွေက — parameter lists မတူညီတဲ့ physical functions အများအပြားအနေနဲ့ implement လုပ်ထားတာ အများစု ဖြစ်တာကို သတိပြုပါ။ အဲဒီ function တစ်ခုချင်းစီကို သုံးမယ်ဆိုရင် — တစ်ခုချင်းစီပေါ်မှာ privilege ကို သီးခြားစီ ပေးအပ်ရပါမယ်။ တကယ့် function signatures တွေကို စစ်ဆေးဖို့ psql ရဲ့ `\df` command က အသုံးဝင်နိုင်ပါတယ်။

ဒီ functions တချို့က optional ဖြစ်တဲ့ `missing_ok` parameter တစ်ခုကို လက်ခံပြီး — file ဒါမှမဟုတ် directory မရှိတဲ့အခါ ဘယ်လို ပြုမူမယ်ဆိုတာကို သတ်မှတ်ပါတယ်။ `true` ဆိုရင် — function က သင့်လျော်သလို `NULL` ဒါမှမဟုတ် result set အလွတ်တစ်ခုကို ပြန်ပေးပါတယ်။ `false` ဆိုရင် error တစ်ခု ထုတ်ပါတယ်။ (“file not found” ကလွဲလို့ တခြား မအောင်မြင်မှု အခြေအနေတွေကို ဘယ်အခြေအနေမှာမဆို errors အဖြစ် အစီရင်ခံပါတယ်။) ပုံမှန်တန်ဖိုးက `false` ဖြစ်ပါတယ်။

**ဇယား 9.108. Generic File Access Functions (file access အထွေထွေ လုပ်ဆောင်ချက်များ)**

| လုပ်ဆောင်ချက် ဖော်ပြချက် |

### 9.28.10. Advisory Lock Functions (advisory lock လုပ်ဆောင်ချက်များ)

ဇယား 9.109 မှာ ပြထားတဲ့ functions တွေက advisory locks (application က သတ်မှတ်ထားသော resource များကို lock လုပ်ရန် သုံးသော locks) တွေကို စီမံခန့်ခွဲပါတယ်။ ဒီ functions တွေကို မှန်ကန်စွာ အသုံးပြုပုံ အသေးစိတ်အတွက် [အပိုင်း 13.3.5](/docs/postgresql/explicit-locking) ကို ကြည့်ပါ။

ဒီ functions တွေ အားလုံးကို — application က သတ်မှတ်ထားတဲ့ (application-defined) resources တွေကို lock လုပ်ဖို့ ရည်ရွယ်ပါတယ် — အဲဒီ resources တွေကို 64-bit key တန်ဖိုး တစ်ခုတည်း ဒါမှမဟုတ် 32-bit key တန်ဖိုး နှစ်ခုနဲ့ ခွဲခြားသတ်မှတ်နိုင်ပါတယ် (ဒီ key spaces နှစ်ခုက ထပ်တူမကျဘူးဆိုတာ သတိပြုပါ)။ တစ်ခြား session တစ်ခုက တူညီတဲ့ resource identifier ပေါ်မှာ conflicting lock တစ်ခုကို ကိုင်ထားပြီးသား ဆိုရင် — functions တွေက resource ရနိုင်တဲ့အထိ စောင့်မယ် ဒါမှမဟုတ် — function နဲ့ လိုက်ဖက်သလို — `false` ရလဒ်ကို ပြန်ပေးပါလိမ့်မယ်။ Locks တွေက shared ဒါမှမဟုတ် exclusive ဖြစ်နိုင်ပါတယ်: shared lock တစ်ခုက — တူညီတဲ့ resource ပေါ်က တခြား shared locks တွေနဲ့ မတိုက်ခိုက်ဘဲ — exclusive locks တွေနဲ့သာ တိုက်ခိုက်ပါတယ်။ Locks တွေကို session level မှာ ယူနိုင်ပါတယ် (ဒါဆိုရင် release လုပ်တဲ့အထိ သို့မဟုတ် session ဆုံးတဲ့အထိ ကိုင်ထားပါတယ်) ဒါမှမဟုတ် — transaction level မှာ ယူနိုင်ပါတယ် (ဒါဆိုရင် လက်ရှိ transaction ဆုံးတဲ့အထိ ကိုင်ထားပြီး — manual နည်းနဲ့ release လုပ်ဖို့ နည်းလမ်း မပါဝင်ပါဘူး)။ Session-level lock တောင်းဆိုချက် အများအပြားက stack (အထပ်လိုက် စုပုံ) လုပ်ပါတယ် — ဒါကြောင့် တူညီတဲ့ resource identifier ကို သုံးကြိမ် lock လုပ်ထားရင် — session မဆုံးခင် resource ကို လွှတ်ပေးဖို့ unlock တောင်းဆိုချက် သုံးကြိမ် ပြုလုပ်ရပါမယ်။

**ဇယား 9.109. Advisory Lock Functions (advisory lock လုပ်ဆောင်ချက်များ)**

| လုပ်ဆောင်ချက် ဖော်ပြချက် |
| --- |
| pg_advisory_lock ( key bigint ) → void pg_advisory_lock ( key1 integer, key2 integer ) → void လိုအပ်ရင် စောင့်ဆိုင်းပြီး — exclusive session-level advisory lock တစ်ခုကို ရယူပါတယ်။ |
| pg_advisory_lock_shared ( key bigint ) → void pg_advisory_lock_shared ( key1 integer, key2 integer ) → void လိုအပ်ရင် စောင့်ဆိုင်းပြီး — shared session-level advisory lock တစ်ခုကို ရယူပါတယ်။ |
| pg_advisory_unlock ( key bigint ) → boolean pg_advisory_unlock ( key1 integer, key2 integer ) → boolean ယခင် ရယူထားခဲ့တဲ့ exclusive session-level advisory lock တစ်ခုကို လွှတ်ပေးပါတယ်။ Lock ကို အောင်မြင်စွာ လွှတ်ပေးနိုင်ရင် true ပြန်ပေးပြီး — lock ကို ကိုင်ထားခြင်း မရှိခဲ့ဘူးဆိုရင် false ပြန်ပေးကာ — ထို့အပြင် server က SQL warning တစ်ခုကိုလည်း အစီရင်ခံပါလိမ့်မယ်။ |
| pg_advisory_unlock_all () → void လက်ရှိ session က ကိုင်ထားတဲ့ session-level advisory locks အားလုံးကို လွှတ်ပေးပါတယ်။ (ဒီ function ကို — client က ပုံမမှန်ဘဲ ချိတ်ဆက်မှု ဖြတ်တောက်သွားရင်တောင် — session အဆုံးမှာ သွယ်ဝိုက်၍ (implicitly) အလိုအလျောက် ခေါ်ပေးပါတယ်။) |
| pg_advisory_unlock_shared ( key bigint ) → boolean pg_advisory_unlock_shared ( key1 integer, key2 integer ) → boolean ယခင် ရယူထားခဲ့တဲ့ shared session-level advisory lock တစ်ခုကို လွှတ်ပေးပါတယ်။ Lock ကို အောင်မြင်စွာ လွှတ်ပေးနိုင်ရင် true ပြန်ပေးပြီး — lock ကို ကိုင်ထားခြင်း မရှိခဲ့ဘူးဆိုရင် false ပြန်ပေးကာ — ထို့အပြင် server က SQL warning တစ်ခုကိုလည်း အစီရင်ခံပါလိမ့်မယ်။ |
| pg_advisory_xact_lock ( key bigint ) → void pg_advisory_xact_lock ( key1 integer, key2 integer ) → void လိုအပ်ရင် စောင့်ဆိုင်းပြီး — exclusive transaction-level advisory lock တစ်ခုကို ရယူပါတယ်။ |
| pg_advisory_xact_lock_shared ( key bigint ) → void pg_advisory_xact_lock_shared ( key1 integer, key2 integer ) → void လိုအပ်ရင် စောင့်ဆိုင်းပြီး — shared transaction-level advisory lock တစ်ခုကို ရယူပါတယ်။ |
| pg_try_advisory_lock ( key bigint ) → boolean pg_try_advisory_lock ( key1 integer, key2 integer ) → boolean ရနိုင်မယ်ဆိုရင် exclusive session-level advisory lock တစ်ခုကို ရယူပါတယ်။ ဒါက lock ကို ချက်ချင်း ရယူပြီး true ပြန်ပေးမယ် — ဒါမှမဟုတ် lock ကို ချက်ချင်း မရယူနိုင်ရင် မစောင့်ဘဲ false ပြန်ပေးပါလိမ့်မယ်။ |
| pg_try_advisory_lock_shared ( key bigint ) → boolean pg_try_advisory_lock_shared ( key1 integer, key2 integer ) → boolean ရနိုင်မယ်ဆိုရင် shared session-level advisory lock တစ်ခုကို ရယူပါတယ်။ ဒါက lock ကို ချက်ချင်း ရယူပြီး true ပြန်ပေးမယ် — ဒါမှမဟုတ် lock ကို ချက်ချင်း မရယူနိုင်ရင် မစောင့်ဘဲ false ပြန်ပေးပါလိမ့်မယ်။ |
| pg_try_advisory_xact_lock ( key bigint ) → boolean pg_try_advisory_xact_lock ( key1 integer, key2 integer ) → boolean ရနိုင်မယ်ဆိုရင် exclusive transaction-level advisory lock တစ်ခုကို ရယူပါတယ်။ ဒါက lock ကို ချက်ချင်း ရယူပြီး true ပြန်ပေးမယ် — ဒါမှမဟုတ် lock ကို ချက်ချင်း မရယူနိုင်ရင် မစောင့်ဘဲ false ပြန်ပေးပါလိမ့်မယ်။ |
| pg_try_advisory_xact_lock_shared ( key bigint ) → boolean pg_try_advisory_xact_lock_shared ( key1 integer, key2 integer ) → boolean ရနိုင်မယ်ဆိုရင် shared transaction-level advisory lock တစ်ခုကို ရယူပါတယ်။ ဒါက lock ကို ချက်ချင်း ရယူပြီး true ပြန်ပေးမယ် — ဒါမှမဟုတ် lock ကို ချက်ချင်း မရယူနိုင်ရင် မစောင့်ဘဲ false ပြန်ပေးပါလိမ့်မယ်။ |
