## 19.9. Run-time Statistics (လုပ်ဆောင်ချိန် စာရင်းအင်းများ)

- **19.9.1. Cumulative Query and Index Statistics (query နှင့် index အတွက် စုစုပေါင်း စာရင်းအင်းများ)**
- **19.9.2. Statistics Monitoring (စာရင်းအင်း စောင့်ကြည့် စစ်ဆေးခြင်း)**

### 19.9.1. Cumulative Query and Index Statistics (query နှင့် index အတွက် စုစုပေါင်း စာရင်းအင်းများ)

ဒီ parameters တွေက server တစ်ခုလုံးအတွက် cumulative statistics စနစ်ကို ထိန်းချုပ်ပါတယ်။ Enable လုပ်ထားတဲ့အခါ — စုဆောင်းထားတဲ့ data ကို `pg_stat` နဲ့ `pg_statio` အုပ်စု (family) ရဲ့ system view များကနေ အသုံးပြုနိုင်ပါတယ်။ အသေးစိတ်အတွက် [အခန်း 27](https://www.postgresql.org/docs/current/monitoring.html) ကို ကြည့်ပါ။

- **track_activities (boolean)** — session တစ်ခုချင်းစီ လက်ရှိ လုပ်ဆောင်နေတဲ့ command အကြောင်း အချက်အလက်ကိုလည်းကောင်း — သူ့ identifier နဲ့ အဲဒီ command စတင် လုပ်ဆောင်ခဲ့တဲ့ အချိန်ကိုလည်းကောင်း စုဆောင်းခြင်းကို enable လုပ်ပါတယ်။ ဒီ parameter က default အားဖြင့် on ဖြစ်ပါတယ်။ Enable လုပ်ထားရင်တောင် — ဒီအချက်အလက်တွေက superuser များ၊ pg_read_all_stats role ရဲ့ privilege များ ရှိတဲ့ role များနှင့် အစီရင်ခံခံရတဲ့ session များကို ပိုင်ဆိုင်တဲ့ user (သူတို့သာ privilege ရှိတဲ့ role နဲ့ သက်ဆိုင်တဲ့ session များ အပါအဝင်) တို့သာ မြင်နိုင်တာကို သတိပြုပါ။ ဒါကြောင့် ဒါက security အန္တရာယ် မဖြစ်သင့်ပါဘူး။ Superuser များနှင့် သင့်လျော်တဲ့ SET privilege ရှိတဲ့ user များသာ ဒီ setting ကို ပြောင်းနိုင်ပါတယ်။
- **track_activity_query_size (integer)** — Active session တစ်ခုချင်းစီအတွက် လက်ရှိ လုပ်ဆောင်နေတဲ့ command ရဲ့ စာသားကို — `pg_stat_activity.query` field အတွက် — သိမ်းဆည်းဖို့ သီးသန့် ဖယ်ထားတဲ့ memory ပမာဏကို သတ်မှတ်ပါတယ်။ ဒီတန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် — byte အဖြစ် ယူဆပါတယ်။ Default တန်ဖိုးက 1024 byte ဖြစ်ပါတယ်။ ဒီ parameter ကို server start လုပ်ချိန်မှာသာ သတ်မှတ်နိုင်ပါတယ်။
- **track_counts (boolean)** — Database လုပ်ဆောင်မှု အပေါ် statistics စုဆောင်းခြင်းကို enable လုပ်ပါတယ်။ ဒီ parameter က default အားဖြင့် on ဖြစ်ပါတယ် — အကြောင်းကတော့ autovacuum daemon က စုဆောင်းထားတဲ့ အချက်အလက်ကို လိုအပ်လို့ပါ။ Superuser များနှင့် သင့်လျော်တဲ့ SET privilege ရှိတဲ့ user များသာ ဒီ setting ကို ပြောင်းနိုင်ပါတယ်။
- **track_cost_delay_timing (boolean)** — Cost-based vacuum delay ရဲ့ timing ကို enable လုပ်ပါတယ် (အပိုင်း 19.10.2 ကို ကြည့်ပါ)။ ဒီ parameter က default အားဖြင့် off ဖြစ်ပါတယ် — အကြောင်းကတော့ ဒါက လက်ရှိ အချိန်အတွက် operating system ကို ထပ်ခါတလဲလဲ query လုပ်မှာ ဖြစ်ပြီး — platform တချို့မှာ သိသာတဲ့ overhead ဖြစ်စေနိုင်လို့ပါ။ သင့် system ပေါ်မှာ timing ရဲ့ overhead ကို တိုင်းတာဖို့ `pg_test_timing` tool ကို သုံးနိုင်ပါတယ်။ Cost-based vacuum delay timing အချက်အလက်တွေကို `pg_stat_progress_vacuum`, `pg_stat_progress_analyze` တွေမှာလည်းကောင်း — `VERBOSE` option သုံးတဲ့အခါ `VACUUM` နဲ့ `ANALYZE` ရဲ့ output မှာလည်းကောင်း — `log_autovacuum_min_duration` သတ်မှတ်ထားတဲ့အခါ auto-vacuum နဲ့ auto-analyze များအတွက် autovacuum ကလည်းကောင်း ပြသပါတယ်။ Superuser များနှင့် သင့်လျော်တဲ့ SET privilege ရှိတဲ့ user များသာ ဒီ setting ကို ပြောင်းနိုင်ပါတယ်။
- **track_io_timing (boolean)** — Database I/O စောင့်ဆိုင်းမှုများ (waits) ရဲ့ timing ကို enable လုပ်ပါတယ်။ ဒီ parameter က default အားဖြင့် off ဖြစ်ပါတယ် — အကြောင်းကတော့ ဒါက လက်ရှိ အချိန်အတွက် operating system ကို ထပ်ခါတလဲလဲ query လုပ်မှာ ဖြစ်ပြီး — platform တချို့မှာ သိသာတဲ့ overhead ဖြစ်စေနိုင်လို့ပါ။ သင့် system ပေါ်မှာ timing ရဲ့ overhead ကို တိုင်းတာဖို့ `pg_test_timing` tool ကို သုံးနိုင်ပါတယ်။ I/O timing အချက်အလက်တွေကို `pg_stat_database`, `pg_stat_io` (`object` က `wal` မဟုတ်ရင်) တွေမှာလည်းကောင်း — `pg_stat_get_backend_io()` function ရဲ့ output (`object` က `wal` မဟုတ်ရင်) မှာလည်းကောင်း — `BUFFERS` option သုံးတဲ့အခါ `EXPLAIN` ရဲ့ output မှာလည်းကောင်း — `VERBOSE` option သုံးတဲ့အခါ `VACUUM` ရဲ့ output မှာလည်းကောင်း — `log_autovacuum_min_duration` သတ်မှတ်ထားတဲ့အခါ auto-vacuum နဲ့ auto-analyze များအတွက် autovacuum ကလည်းကောင်း — ပြီးတော့ `pg_stat_statements` ကလည်းကောင်း ပြသပါတယ်။ Superuser များနှင့် သင့်လျော်တဲ့ SET privilege ရှိတဲ့ user များသာ ဒီ setting ကို ပြောင်းနိုင်ပါတယ်။
- **track_wal_io_timing (boolean)** — WAL I/O စောင့်ဆိုင်းမှုများ ရဲ့ timing ကို enable လုပ်ပါတယ်။ ဒီ parameter က default အားဖြင့် off ဖြစ်ပါတယ် — အကြောင်းကတော့ ဒါက လက်ရှိ အချိန်အတွက် operating system ကို ထပ်ခါတလဲလဲ query လုပ်မှာ ဖြစ်ပြီး — platform တချို့မှာ သိသာတဲ့ overhead ဖြစ်စေနိုင်လို့ပါ။ သင့် system ပေါ်မှာ timing ရဲ့ overhead ကို တိုင်းတာဖို့ `pg_test_timing` tool ကို သုံးနိုင်ပါတယ်။ I/O timing အချက်အလက်တွေကို `object` က `wal` ဖြစ်တဲ့ `pg_stat_io` မှာလည်းကောင်း — `object` က `wal` ဖြစ်တဲ့ `pg_stat_get_backend_io()` function ရဲ့ output မှာလည်းကောင်း ပြသပါတယ်။ Superuser များနှင့် သင့်လျော်တဲ့ SET privilege ရှိတဲ့ user များသာ ဒီ setting ကို ပြောင်းနိုင်ပါတယ်။
- **track_functions (enum)** — Function ခေါ်သုံးမှု အရေအတွက်များနှင့် သုံးခဲ့တဲ့ အချိန်ကို ခြေရာခံခြင်းကို enable လုပ်ပါတယ်။ Procedural-language function များကိုသာ ခြေရာခံဖို့ `pl` ကို သတ်မှတ်ပါ; SQL နဲ့ C language function များပါ ခြေရာခံဖို့ `all` သတ်မှတ်ပါ။ Default က `none` ဖြစ်ပြီး — function statistics ခြေရာခံခြင်းကို disable လုပ်ပါတယ်။ Superuser များနှင့် သင့်လျော်တဲ့ SET privilege ရှိတဲ့ user များသာ ဒီ setting ကို ပြောင်းနိုင်ပါတယ်။

> **မှတ်ချက်:** ခေါ်သုံးတဲ့ query ထဲကို “inline” လုပ်နိုင်လောက်အောင် ရိုးရှင်းတဲ့ SQL-language function များကို — ဒီ setting ဘယ်လိုပဲ ဖြစ်ဖြစ် — ခြေရာခံမှာ မဟုတ်ပါဘူး။

- **stats_fetch_consistency (enum)** — Transaction တစ်ခုအတွင်း cumulative statistics များကို အကြိမ်များစွာ access လုပ်တဲ့အခါ ပြုမူပုံကို သတ်မှတ်ပါတယ်။ `none` သတ်မှတ်ရင် — access လုပ်တိုင်း counter များကို shared memory ကနေ ပြန်ယူ (re-fetch) ပါတယ်။ `cache` သတ်မှတ်ရင် — object တစ်ခုအတွက် statistics ကို ပထမဆုံး access လုပ်တဲ့အခါ `pg_stat_clear_snapshot()` ကို ခေါ်လိုက်တာ မဟုတ်ရင် — transaction အဆုံးအထိ အဲဒီ statistics များကို cache လုပ်ထားပါတယ်။ `snapshot` သတ်မှတ်ရင် — ပထမဆုံး statistics access က လက်ရှိ database ထဲမှာ access လုပ်နိုင်တဲ့ statistics အားလုံးကို — `pg_stat_clear_snapshot()` ကို ခေါ်လိုက်တာ မဟုတ်ရင် — transaction အဆုံးအထိ cache လုပ်ထားပါတယ်။ Transaction တစ်ခုအတွင်း ဒီ parameter ကို ပြောင်းရင် statistics snapshot ကို စွန့်ပစ်ပါတယ်။ Default က `cache` ဖြစ်ပါတယ်။

> **မှတ်ချက်:** `none` က monitoring system များအတွက် အသင့်လျော်ဆုံး ဖြစ်ပါတယ်။ တန်ဖိုးများကို တစ်ကြိမ်သာ access လုပ်ရင် — ဒါက အထိရောက်ဆုံး ဖြစ်ပါတယ်။ `cache` က ထပ်ခါတလဲလဲ access လုပ်မှုများက တူညီတဲ့ တန်ဖိုးများ ရစေကြောင်း သေချာစေပြီး — ဥပမာ self-join များပါဝင်တဲ့ query များအတွက် အရေးကြီးပါတယ်။ `snapshot` က statistics များကို interactively စစ်ဆေးတဲ့အခါ အသုံးဝင်နိုင်ပေမယ့် — overhead ပိုမြင့်ပါတယ် — အထူးသဖြင့် database object အများအပြား ရှိနေရင်ပါ။

### 19.9.2. Statistics Monitoring (စာရင်းအင်း စောင့်ကြည့် စစ်ဆေးခြင်း)

- **compute_query_id (enum)** — Query identifier တစ်ခုကို in-core တွက်ချက်ခြင်းကို enable လုပ်ပါတယ်။ Query identifier များကို `pg_stat_activity` view မှာ `EXPLAIN` သုံးပြီး ပြနိုင်သလို — `log_line_prefix` parameter ကတစ်ဆင့် configure လုပ်ထားရင် log ထဲမှာ ထုတ်လွှတ်နိုင်ပါတယ်။ `pg_stat_statements` extension ကလည်း query identifier တစ်ခု တွက်ချက်ဖို့ လိုအပ်ပါတယ်။ in-core query identifier တွက်ချက်တဲ့ နည်းလမ်းက လက်မခံနိုင်ရင်တော့ — အပြင်က module တစ်ခုကို အစားထိုး သုံးနိုင်တာကို သတိပြုပါ။ အဲဒီအခါ — in-core တွက်ချက်မှုကို အမြဲ disable လုပ်ထားရပါမယ်။ တရားဝင် (valid) တန်ဖိုးများက — `off` (အမြဲ disable), `on` (အမြဲ enable), `auto` — `pg_stat_statements` လိုမျိုး module များကို အလိုအလျောက် enable လုပ်ခွင့်ပေးတာ — နှင့် `regress` — `auto` နဲ့ အတူတူ effect ရှိပေမယ့် automated regression testing ကို အဆင်ပြေစေဖို့ `EXPLAIN` output မှာ query identifier ကို မပြဘူး ဆိုတဲ့ ကွာခြားချက်ရှိတာ ဖြစ်ပါတယ်။ Default က `auto` ဖြစ်ပါတယ်။

> **မှတ်ချက်:** Query identifier တစ်ခုသာ တွက်ချက်ပြီး ပြသ ဖြစ်စေရန် — query identifier များ တွက်ချက်တဲ့ extension များက query identifier တစ်ခု ရှိပြီး တွက်ချက်ပြီးသား ဖြစ်နေရင် error တစ်ခု ပစ်သင့်ပါတယ်။

- **log_statement_stats (boolean)**, **log_parser_stats (boolean)**, **log_planner_stats (boolean)**, **log_executor_stats (boolean)** — Query တစ်ခုချင်းစီအတွက် — သက်ဆိုင်ရာ module ရဲ့ performance statistics ကို server log ဆီ output ထုတ်ပါတယ်။ ဒါက Unix ရဲ့ `getrusage()` operating system facility နဲ့ ဆင်တူတဲ့ — အကြမ်းစား (crude) profiling instrument တစ်ခု ဖြစ်ပါတယ်။ `log_statement_stats` က စုစုပေါင်း statement statistics ကို အစီရင်ခံပြီး — ကျန်တာတွေက module တစ်ခုချင်းစီရဲ့ statistics ကို အစီရင်ခံပါတယ်။ `log_statement_stats` ကို per-module option တစ်ခုခုနဲ့ အတူ enable လုပ်လို့ မရပါဘူး။ ဒီ option အားလုံးက default အားဖြင့် disable လုပ်ထားပါတယ်။ Superuser များနှင့် သင့်လျော်တဲ့ SET privilege ရှိတဲ့ user များသာ ဒီ settings များကို ပြောင်းနိုင်ပါတယ်။
