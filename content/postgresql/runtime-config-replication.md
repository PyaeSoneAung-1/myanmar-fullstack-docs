## 19.6. Replication (ပုံတူပွားခြင်း)

- **19.6.1. Sending Servers (ပို့ဆောင်သည့် ဆာဗာများ)**
- **19.6.2. Primary Server (မူလ ဆာဗာ)**
- **19.6.3. Standby Servers (အရန် ဆာဗာများ)**
- **19.6.4. Subscribers (စာရင်းသွင်း လက်ခံသူများ)**

ဒီ setting တွေက built-in *streaming replication* (စီးဆင်းမှု ပုံစံ ပုံတူပွားခြင်း) feature ရဲ့ အပြုအမူကို ထိန်းချုပ်ပါတယ် ([အပိုင်း 26.2.5](/docs/postgresql/warm-standby) ကို ကြည့်ပါ)၊ ပြီးတော့ built-in *logical replication* (ယုတ္တိ ပုံတူပွားခြင်း) feature ကိုလည်း ထိန်းချုပ်ပါတယ် ([အခန်း 29](https://www.postgresql.org/docs/current/logical-replication.html) ကို ကြည့်ပါ)။

Streaming replication အတွက်ဆိုရင် — server တွေက primary ဒါမှမဟုတ် standby server အနေနဲ့ ရှိပါလိမ့်မယ်။ Primary တွေက data ပို့နိုင်ပြီး — standby တွေကတော့ replicate လုပ်ထားတဲ့ data ကို အမြဲတမ်း လက်ခံရရှိသူများ ဖြစ်ပါတယ်။ Cascading replication (အဆင့်ဆင့် ပုံတူပွားခြင်း — [အပိုင်း 26.2.7](/docs/postgresql/warm-standby) ကို ကြည့်ပါ) သုံးတဲ့အခါ — standby server တွေက လက်ခံရရှိသူအဖြစ်ရော ပို့ဆောင်သူအဖြစ်ပါ ဖြစ်နိုင်ပါတယ်။ Parameter တွေက ပို့ဆောင်တဲ့ server နဲ့ standby server အတွက် အဓိက ဖြစ်ပြီး — parameter တချို့ကတော့ primary server ပေါ်မှာပဲ အဓိပ္ပာယ် ရှိပါတယ်။ လိုအပ်ရင် — cluster တစ်ခုအတွင်းမှာ setting တွေ ကွဲပြားနိုင်ပြီး — ပြဿနာ မဖြစ်ပါဘူး။

Logical replication အတွက်ဆိုရင် — *publishers* (ထုတ်ဝေသူများ — [`CREATE PUBLICATION`](/docs/postgresql/sql-createpublication) ကို လုပ်ဆောင်တဲ့ server များ) က *subscribers* (စာရင်းသွင်း လက်ခံသူများ — [`CREATE SUBSCRIPTION`](/docs/postgresql/sql-createsubscription) ကို လုပ်ဆောင်တဲ့ server များ) ဆီ data ကို replicate လုပ်ပါတယ်။ Server တွေက publisher ရော subscriber ပါ တစ်ချိန်တည်း ဖြစ်နိုင်ပါတယ်။ မှတ်ချက်တစ်ခုက — အောက်ပါ section တွေမှာ publisher တွေကို "senders" (ပို့ဆောင်သူများ) လို့ ရည်ညွှန်းထားပါတယ်။ Logical replication configuration setting တွေ အကြောင်း ပိုမို အသေးစိတ်အတွက် [အပိုင်း 29.12](/docs/postgresql/logical-replication-config) ကို ကြည့်ပါ။

### 19.6.1. Sending Servers (ပို့ဆောင်သည့် ဆာဗာများ)

ဒီ parameter တွေကို standby server တစ်ခု ဒါမှမဟုတ် တစ်ခုထက်ပိုတဲ့ standby server များဆီ replication data ပို့မယ့် server တိုင်းမှာ သတ်မှတ်နိုင်ပါတယ်။ Primary က အမြဲတမ်း ပို့ဆောင်တဲ့ server ဖြစ်တာမို့ — ဒီ parameter တွေကို primary ပေါ်မှာ အမြဲ သတ်မှတ်ထားရပါမယ်။ Standby တစ်ခု primary ဖြစ်လာပြီးနောက်မှာလည်း ဒီ parameter တွေရဲ့ အခန်းကဏ္ဍနဲ့ အဓိပ္ပာယ်က မပြောင်းလဲပါဘူး။

- **max_wal_senders (integer)  #** — Standby server များ ဒါမှမဟုတ် streaming base backup client များကနေ လာတဲ့ concurrent connection အများဆုံး အရေအတွက်ကို သတ်မှတ်ပါတယ် (ဆိုလိုတာက — တစ်ချိန်တည်း run နေတဲ့ WAL sender process အများဆုံး အရေအတွက်ပါ)။ Default ကတော့ 10 ဖြစ်ပါတယ်။ တန်ဖိုး 0 ဆိုတာက replication ကို ပိတ်ထားတာ ဖြစ်ပါတယ်။ Streaming client တစ်ခု ရုတ်တရက် ချိတ်ဆက်မှု ပြတ်သွားတာက — timeout တစ်ခု မရောက်မချင်း orphaned connection slot တစ်ခုကို ကျန်ရစ်စေနိုင်တာမို့ — ချိတ်ဆက်မှု ပြတ်သွားတဲ့ client တွေ ချက်ချင်း ပြန်ချိတ်နိုင်ဖို့ — ဒီ parameter ကို မျှော်မှန်းထားတဲ့ client အများဆုံး အရေအတွက်ထက် အနည်းငယ် ပိုမြင့်အောင် သတ်မှတ်သင့်ပါတယ်။ ဒီ parameter ကို server စတင်ချိန်မှာပဲ သတ်မှတ်နိုင်ပါတယ်။ ဒါ့အပြင် — standby server များကနေ ချိတ်ဆက်မှုတွေ ခွင့်ပြုဖို့ wal_level ကို replica ဒါမှမဟုတ် အထက် သတ်မှတ်ထားရပါမယ်။
Standby server တစ်ခုကို run နေစဉ်မှာ — ဒီ parameter ကို primary server ပေါ်က တန်ဖိုးနဲ့ ညီအောင် ဒါမှမဟုတ် ပိုမြင့်အောင် သတ်မှတ်ရပါမယ်။ မဟုတ်ရင် — standby server မှာ query တွေကို ခွင့်ပြုမှာ မဟုတ်ပါဘူး။
- **max_replication_slots (integer)  #** — Server က ထောက်ပံ့နိုင်တဲ့ replication slot အများဆုံး အရေအတွက်ကို သတ်မှတ်ပါတယ် (အပိုင်း 26.2.6 ကို ကြည့်ပါ)။ Default ကတော့ 10 ဖြစ်ပါတယ်။ ဒီ parameter ကို server စတင်ချိန်မှာပဲ သတ်မှတ်နိုင်ပါတယ်။ လက်ရှိ ရှိနေတဲ့ replication slot အရေအတွက်ထက် နည်းတဲ့ တန်ဖိုးတစ်ခု သတ်မှတ်လိုက်ရင် — server က စတင် (start) လုပ်နိုင်မှာ မဟုတ်ပါဘူး။ ဒါ့အပြင် — replication slot များ သုံးနိုင်ဖို့ wal_level ကို replica ဒါမှမဟုတ် အထက် သတ်မှတ်ထားရပါမယ်။
- **output_plugin_libraries (string)  #** — replication client များက logical output plugin အဖြစ် သုံးဖို့ ယုံကြည်စိတ်ချရတဲ့ (trusted) — dynamic_library_path ထဲမှာ install လုပ်ထားတဲ့ — library များကို စာရင်းပြုစုပေးပါတယ်။ အခြား library များအတွက် logical decoding ဒါမှမဟုတ် replication request တွေကို ငြင်းပယ်ပါလိမ့်မယ်။ User အားလုံးက ဒီ ကန့်သတ်ချက်ကို ခံရပါတယ်။ Default ကတော့ 'pgoutput, test_decoding' ဖြစ်ပြီး — ဒါတွေက standard PostgreSQL distribution မှာ ပါဝင်တဲ့ logical output plugin နှစ်ခု ဖြစ်ပါတယ်။
Format က library နာမည်များကို comma နဲ့ ခွဲထားတဲ့ စာရင်း ဖြစ်ပြီး — နာမည် တစ်ခုချင်းစီကို LOAD command အတွက်လိုပဲ အဓိပ္ပာယ် ဖော်ပါတယ် (ဒါပေမယ့် logical decoding client များက — case ဒါမှမဟုတ် path structure မှာ ကွဲပြားမှု မရှိဘဲ — စာရင်းထဲက entry တစ်ခုနဲ့ အတိအကျ ကိုက်ညီတဲ့ plugin နာမည်ကို သတ်မှတ်ရပါမယ်)။ Entry များကြားက whitespace ကို လျစ်လျူရှုပါတယ်; နာမည်ထဲမှာ whitespace ဒါမှမဟုတ် comma ထည့်ချင်ရင် — library နာမည်ကို double quote နဲ့ ခြုံပါ။
ဒီ စာရင်းထဲ ထည့်ထားတဲ့ library များက server ထဲ load လုပ်တဲ့အခါ non-superuser များကို မရည်ရွယ်ဘဲ အပို privilege များ ပေးမိခြင်း မရှိစေဖို့ သေချာစေတာက server administrator ရဲ့ တာဝန် ဖြစ်ပါတယ်။

> **မှတ်ချက်:** output_plugin_libraries parameter မပါတဲ့ version တစ်ခုကနေ server ကို update လုပ်တဲ့အခါ — persistent logical replication slot အားလုံး လိုအပ်တဲ့ plugin စာရင်းကို တည်ဆောက်ဖို့ အောက်ပါ query က ကူညီနိုင်ပါတယ်:
>
> SELECT DISTINCT plugin FROM pg_replication_slots WHERE plugin IS NOT NULL;
>
> output_plugin_libraries ကို မချိန်ညှိခင် စာရင်းကို ဘေးကင်းမှုအတွက် သေချာစွာ ပြန်စစ်ပါ။
> အထက်ပါ query က — အတိတ်တစ်ချိန်ချိန်မှာ replication slot များဆီ အောင်မြင်စွာ ထည့်ခဲ့ဖူးတဲ့ plugin များကိုပဲ ပြသနိုင်ပါတယ်။ အသစ် ငြင်းပယ်ခံရတဲ့ request များကတော့ log များမှာ အောက်ပါ message နဲ့ ဆင်တူအဖြစ် ပေါ်လာပါလိမ့်မယ်:
>
> ERROR:  library "..." may not be used as an output plugin
> DETAIL:  The configuration parameter "output_plugin_libraries" (currently 'pgoutput, test_decoding') does not name this library as a trusted output plugin.
> HINT:  If it is safe for all REPLICATION users to use this library as an output plugin, add it to "output_plugin_libraries" and reload the server configuration.
- **wal_keep_size (integer)  #** — streaming replication အတွက် standby server တစ်ခု လိုအပ်တဲ့အခါ ဆွဲယူ (fetch) နိုင်ဖို့ — pg_wal directory ထဲမှာ ထိန်းသိမ်းထားတဲ့ အတိတ် WAL ဖိုင်များရဲ့ အနည်းဆုံး အရွယ်အစားကို သတ်မှတ်ပါတယ်။ ပို့ဆောင်တဲ့ server နဲ့ ချိတ်ဆက်ထားတဲ့ standby server တစ်ခုက wal_keep_size megabyte ထက် ပိုနောက်ကျသွားရင် — ပို့ဆောင်တဲ့ server က standby လိုအပ်နေဆဲ WAL segment တစ်ခုကို ဖျက်ပစ်နိုင်ပြီး — အဲဒီအခါ replication connection ကို ရပ်ဆိုင်းပါလိမ့်မယ်။ အကျိုးဆက်အနေနဲ့ — အောက်ပိုင်း (downstream) connection များလည်း နောက်ဆုံးမှာ ကျရှုံးပါလိမ့်မယ်။ (ဒါပေမယ့် — WAL archiving သုံးနေရင် — standby server က archive ကနေ segment ကို ဆွဲယူပြီး ပြန်လည် ကောင်းမွန်လာနိုင်ပါတယ်။)
ဒါက pg_wal ထဲမှာ ထိန်းသိမ်းထားတဲ့ segment များရဲ့ အနည်းဆုံး အရွယ်အစားကိုပဲ သတ်မှတ်ပါတယ်; WAL archival အတွက် ဒါမှမဟုတ် checkpoint တစ်ခုကနေ ပြန်လည် ကောင်းမွန်လာဖို့ system က segment များ ပိုထိန်းသိမ်းထားဖို့ လိုနိုင်ပါတယ်။ wal_keep_size က သုည (default) ဖြစ်ရင် — system က standby ရည်ရွယ်ချက်အတွက် အပို segment တွေ ထိန်းမထားဘူးဆိုတာမို့ — standby server များအတွက် ရနိုင်တဲ့ WAL segment အိုများရဲ့ အရေအတွက်က — အရင် checkpoint ရဲ့ တည်နေရာနဲ့ WAL archiving အခြေအနေပေါ် မူတည်ပါတယ်။ ဒီ တန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် — megabyte အနေနဲ့ ယူပါတယ်။ ဒီ parameter ကို postgresql.conf ဖိုင်ထဲမှာ ဒါမှမဟုတ် server command line မှာပဲ သတ်မှတ်နိုင်ပါတယ်။
- **max_slot_wal_keep_size (integer)  #** — checkpoint အချိန်မှာ replication slot များကို pg_wal directory ထဲမှာ ထိန်းသိမ်းခွင့်ပြုထားတဲ့ WAL ဖိုင်များရဲ့ အများဆုံး အရွယ်အစားကို သတ်မှတ်ပါတယ်။ max_slot_wal_keep_size က -1 (default) ဖြစ်ရင် — replication slot များက WAL ဖိုင်များကို အကန့်အသတ် မရှိ ထိန်းသိမ်းနိုင်ပါတယ်။ မဟုတ်ရင်တော့ — replication slot တစ်ခုရဲ့ restart_lsn က လက်ရှိ LSN ထက် ပေးထားတဲ့ အရွယ်အစားထက် ပိုနောက်ကျသွားရင် — slot ကို သုံးနေတဲ့ standby က လိုအပ်တဲ့ WAL ဖိုင်များ ဖျက်ခံရတာကြောင့် replication ကို ဆက်လုပ် နိုင်တော့မှာ မဟုတ်ပါဘူး။ Replication slot များရဲ့ WAL ရနိုင်မှုကို pg_replication_slots မှာ ကြည့်နိုင်ပါတယ်။ ဒီ တန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် — megabyte အနေနဲ့ ယူပါတယ်။ ဒီ parameter ကို postgresql.conf ဖိုင်ထဲမှာ ဒါမှမဟုတ် server command line မှာပဲ သတ်မှတ်နိုင်ပါတယ်။
- **idle_replication_slot_timeout (integer)  #** — ဒီ ကြာချိန်ထက် ပိုပြီး inactive (replication connection က မသုံးတဲ့) ဖြစ်နေတဲ့ replication slot များကို invalidate (အသုံးမပြုနိုင်အောင်) လုပ်ပါတယ်။ ဒီ တန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် — second အနေနဲ့ ယူပါတယ်။ တန်ဖိုး သုည (default) က idle timeout invalidation ယန္တရားကို ပိတ်ထားပါတယ်။ ဒီ parameter ကို postgresql.conf ဖိုင်ထဲမှာ ဒါမှမဟုတ် server command line မှာပဲ သတ်မှတ်နိုင်ပါတယ်။
Idle timeout ကြောင့် slot invalidation ဖြစ်တာက checkpoint အချိန်မှာ ဖြစ်ပါတယ်။ Checkpoint များက checkpoint_timeout အခြားတစ်ခုချင်း အကွာအဝေးတွေမှာ ဖြစ်တာမို့ — idle_replication_slot_timeout ကို ကျော်လွန်ခဲ့တဲ့ အချိန်နဲ့ နောက် checkpoint မှာ slot invalidation စတင် ဖြစ်တဲ့ အချိန်ကြားမှာ အနည်းငယ် နောက်ကျမှု ရှိနိုင်ပါတယ်။ ဒီလို နောက်ကျမှုတွေ မဖြစ်စေဖို့ — user များက inactive slot များကို အမြန် invalidate ဖြစ်စေဖို့ checkpoint တစ်ခုကို အတင်းအကျပ် လုပ်နိုင်ပါတယ်။ Slot inactive ဖြစ်နေတဲ့ ကြာချိန်ကို slot ရဲ့ pg_replication_slots.inactive_since တန်ဖိုးနဲ့ တွက်ချက်ပါတယ်။
Idle timeout invalidation ယန္တရားက — WAL ကို reserve မလုပ်တဲ့ slot များအတွက်ရော — primary server ကနေ sync လုပ်နေတဲ့ standby server ပေါ်က slot များ (ဆိုလိုတာက — pg_replication_slots.synced တန်ဖိုးက true ဖြစ်တဲ့ standby slot များ) အတွက်ပါ အသက်မဝင်ပါဘူး ဆိုတာ သတိပြုပါ။ Synced slot များက — ပြောင်းလဲမှုများ ထုတ်လုပ်ဖို့ logical decoding ကို မလုပ်တာကြောင့် — အမြဲတမ်း inactive ဖြစ်တယ်လို့ သတ်မှတ်ပါတယ်။
- **wal_sender_timeout (integer)  #** — ဒီ ကြာချိန်ထက် ပိုပြီး inactive ဖြစ်နေတဲ့ replication connection များကို ရပ်ဆိုင်းပါတယ်။ ဒါက ပို့ဆောင်တဲ့ server အတွက် standby crash ဒါမှမဟုတ် network ပြတ်တောက်မှုကို ရှာဖွေ ဖော်ထုတ်ဖို့ အသုံးဝင်ပါတယ်။ ဒီ တန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် — millisecond အနေနဲ့ ယူပါတယ်။ Default တန်ဖိုးကတော့ 60 second ဖြစ်ပါတယ်။ တန်ဖိုး သုည က timeout ယန္တရားကို ပိတ်ထားပါတယ်။
ပထဝီဝင် တည်နေရာ အများအပြားမှာ ဖြန့်ကျက်ထားတဲ့ cluster တစ်ခုနဲ့ဆိုရင် — တည်နေရာ တစ်ခုချင်းစီအတွက် တန်ဖိုးများ ကွဲပြားစွာ သုံးတာက cluster စီမံခန့်ခွဲမှုမှာ ပိုပြီး လိုက်လျောညီထွေ ဖြစ်စေပါတယ်။ latency နည်းတဲ့ network connection ရှိတဲ့ standby တစ်ခုအတွက် ပိုသေးတဲ့ တန်ဖိုးက ကျရှုံးမှုကို ပိုမြန်စွာ ရှာဖွေ ဖော်ထုတ်ဖို့ အသုံးဝင်ပြီး — latency မြင့်တဲ့ network connection ရှိတဲ့ အဝေးတစ်နေရာမှာ ရှိတဲ့ standby ရဲ့ ကျန်းမာရေးကို ပိုကောင်းစွာ အကဲဖြတ်ဖို့ ပိုကြီးတဲ့ တန်ဖိုးက ကူညီပါတယ်။
- **track_commit_timestamp (boolean)  #** — transaction များရဲ့ commit အချိန်ကို မှတ်တမ်းတင်ပါတယ်။ ဒီ parameter ကို server စတင်ချိန်မှာပဲ သတ်မှတ်နိုင်ပါတယ်။ Default တန်ဖိုးကတော့ off ဖြစ်ပါတယ်။

### 19.6.2. Primary Server (မူလ ဆာဗာ)

ဒီ parameter တွေကို standby server တစ်ခု ဒါမှမဟုတ် တစ်ခုထက်ပိုတဲ့ standby server များဆီ replication data ပို့မယ့် primary server ပေါ်မှာ သတ်မှတ်နိုင်ပါတယ်။ ဒီ parameter တွေအပြင် — primary server ပေါ်မှာ [wal_level](/docs/postgresql/runtime-config-wal) ကို သင့်လျော်စွာ သတ်မှတ်ထားရပါမယ်; ပြီးတော့ WAL archiving ကိုလည်း ရွေးချယ်စရာအနေနဲ့ ဖွင့်နိုင်ပါတယ် ([အပိုင်း 19.5.3](/docs/postgresql/runtime-config-wal) ကို ကြည့်ပါ)။ Standby server များပေါ်က ဒီ parameter တွေရဲ့ တန်ဖိုးများက အရေးမပါပါဘူး — ဒါပေမယ့် standby တစ်ခု primary ဖြစ်လာနိုင်တဲ့ ဖြစ်နိုင်ခြေအတွက် ကြိုတင် ပြင်ဆင်တဲ့အနေနဲ့ အဲဒီမှာ သတ်မှတ်ထားချင်လည်း သတ်မှတ်နိုင်ပါတယ်။

- **synchronous_standby_names (string)  #** — synchronous replication ကို ထောက်ပံ့နိုင်တဲ့ standby server များရဲ့ စာရင်းကို သတ်မှတ်ပါတယ် (အပိုင်း 26.2.8 တွင် ဖော်ပြထားသည့်အတိုင်း)။ တက်ကြွနေတဲ့ synchronous standby တစ်ခု ဒါမှမဟုတ် တစ်ခုထက်ပို ရှိပါလိမ့်မယ်; commit ကို စောင့်နေတဲ့ transaction များကို — အဲဒီ standby server များက သူတို့ရဲ့ data ကို လက်ခံရရှိကြောင်း အတည်ပြုပြီးမှ ဆက်လုပ်ခွင့်ပြုပါမယ်။ Synchronous standby များဆိုတာ — ဒီစာရင်းထဲမှာ နာမည် ပါဝင်ပြီး — လက်ရှိ ချိတ်ဆက်ထားကာ real-time အနေနဲ့ data ကို stream လုပ်နေတဲ့ (pg_stat_replication view မှာ state က streaming ဖြစ်နေတဲ့) သူများ ဖြစ်ပါတယ်။ Synchronous standby တစ်ခုထက်ပို သတ်မှတ်ခြင်းက — အလွန်မြင့်မားတဲ့ availability နဲ့ data ဆုံးရှုံးမှုမှ ကာကွယ်မှုကို ရရှိစေပါတယ်။
ဒီအတွက် standby server တစ်ခုရဲ့ နာမည်ဆိုတာ — standby ရဲ့ ချိတ်ဆက်မှု အချက်အလက်မှာ သတ်မှတ်ထားတဲ့ application_name setting ဖြစ်ပါတယ်။ Physical replication standby ဖြစ်ရင် — ဒါကို primary_conninfo setting မှာ သတ်မှတ်သင့်ပြီး — default ကတော့ cluster_name သတ်မှတ်ထားရင် အဲဒါ၊ မဟုတ်ရင် walreceiver ဖြစ်ပါတယ်။ Logical replication အတွက်ဆိုရင် — subscription ရဲ့ connection information မှာ သတ်မှတ်နိုင်ပြီး — default က subscription နာမည် ဖြစ်ပါတယ်။ အခြား replication stream consumer များအတွက်တော့ သူတို့ရဲ့ documentation ကို ကြည့်ပါ။
ဒီ parameter က အောက်ပါ syntax တစ်ခုခုကို သုံးပြီး standby server များရဲ့ စာရင်းကို သတ်မှတ်ပါတယ်:

[FIRST] num_sync ( standby_name [, ...] )
ANY num_sync ( standby_name [, ...] )
standby_name [, ...]

ဒီမှာ num_sync က transaction များက ပြန်စာ စောင့်ရမယ့် synchronous standby အရေအတွက် ဖြစ်ပြီး — standby_name က standby server တစ်ခုရဲ့ နာမည် ဖြစ်ပါတယ်။ num_sync က သုညထက် ကြီးတဲ့ integer တန်ဖိုး ဖြစ်ရပါမယ်။ FIRST နဲ့ ANY က စာရင်းထဲက server များထဲက synchronous standby များကို ရွေးချယ်တဲ့ method ကို သတ်မှတ်ပါတယ်။
FIRST keyword က num_sync နဲ့ တွဲဖက်သုံးတဲ့အခါ — priority အခြေခံ synchronous replication ကို သတ်မှတ်ပြီး — transaction commit များက သူတို့ရဲ့ priority အပေါ် မူတည်ပြီး ရွေးချယ်ထားတဲ့ num_sync synchronous standby များဆီ WAL record များ replicate ဖြစ်တဲ့အထိ စောင့်ပါတယ်။ ဥပမာ — FIRST 3 (s1, s2, s3, s4) ဆိုတဲ့ setting က — commit တစ်ခုချင်းစီကို standby server s1, s2, s3 နဲ့ s4 ထဲက ရွေးချယ်ထားတဲ့ priority ပိုမြင့်တဲ့ standby သုံးခုဆီက ပြန်စာ စောင့်စေပါမယ်။ စာရင်းထဲမှာ အစောပိုင်း ပေါ်တဲ့ နာမည်ရှိတဲ့ standby များကို priority ပိုမြင့်တယ်လို့ သတ်မှတ်ပြီး synchronous အဖြစ် သတ်မှတ်ပါမယ်။ ဒီစာရင်းထဲမှာ နောက်ပိုင်း ပေါ်တဲ့ အခြား standby server များက — ဖြစ်လာနိုင်တဲ့ (potential) synchronous standby များကို ကိုယ်စားပြုပါတယ်။ လက်ရှိ synchronous standby တစ်ခုခု ချိတ်ဆက်မှု ပြတ်သွားရင် (ဘယ်အကြောင်းကြောင့်ပဲ ဖြစ်ဖြစ်) — နောက် priority အမြင့်ဆုံး standby နဲ့ ချက်ချင်း အစားထိုးပါမယ်။ FIRST keyword က ရွေးချယ်စရာ (optional) ဖြစ်ပါတယ်။
ANY keyword က num_sync နဲ့ တွဲဖက်သုံးတဲ့အခါ — quorum အခြေခံ synchronous replication ကို သတ်မှတ်ပြီး — transaction commit များက စာရင်းထဲက standby အနည်းဆုံး num_sync ခုဆီ WAL record များ replicate ဖြစ်တဲ့အထိ စောင့်ပါတယ်။ ဥပမာ — ANY 3 (s1, s2, s3, s4) ဆိုတဲ့ setting က — s1, s2, s3 နဲ့ s4 ထဲက အနည်းဆုံး standby သုံးခု ပြန်စာ ရရှိပြီးတာနဲ့ commit တစ်ခုချင်းစီကို ဆက်လုပ်ခွင့်ပြုပါမယ်။
FIRST နဲ့ ANY က case-insensitive ဖြစ်ပါတယ်။ ဒီ keyword များကို standby server နာမည်အနေနဲ့ သုံးရင် — သူ့ရဲ့ standby_name ကို double-quote နဲ့ ခြုံရပါမယ်။
တတိယ syntax က PostgreSQL version 9.6 မတိုင်မီ သုံးခဲ့ပြီး — အခုထိ ထောက်ပံ့ဆဲ ဖြစ်ပါတယ်။ ဒါက FIRST နဲ့ num_sync ကို 1 သတ်မှတ်ထားတဲ့ ပထမ syntax နဲ့ အတူတူပါပဲ။ ဥပမာ — FIRST 1 (s1, s2) နဲ့ s1, s2 က အဓိပ္ပာယ် တူပါတယ်: s1 ဒါမှမဟုတ် s2 ကို synchronous standby အဖြစ် ရွေးချယ်ပါတယ်။
အထူး entry * က standby နာမည် မည်သည့်အရာနဲ့မဆို ကိုက်ညီပါတယ်။
Standby နာမည်များ ထပ်မနေစေဖို့ အတင်းအကျပ် လုပ်ဆောင်တဲ့ ယန္တရား မရှိပါဘူး။ ထပ်နေတဲ့အခါ — ကိုက်ညီတဲ့ standby တစ်ခုကို priority ပိုမြင့်တယ်လို့ သတ်မှတ်ပါမယ် — ဒါပေမယ့် ဘယ်တစ်ခုဆိုတာ အတိအကျ မဆိုနိုင်ပါဘူး။

> **မှတ်ချက်:** standby_name တစ်ခုချင်းစီက * မဟုတ်ရင် — မှန်ကန်တဲ့ SQL identifier ပုံစံ ရှိသင့်ပါတယ်။ လိုအပ်ရင် double-quoting သုံးနိုင်ပါတယ်။ ဒါပေမယ့် — standby_name များကို standby application name များနဲ့ case-insensitively နှိုင်းယှဉ်တာကို သတိပြုပါ — double-quote ခြုံထားသည်ဖြစ်စေ မခြုံသည်ဖြစ်စေ အတူတူပါပဲ။

ဒီမှာ synchronous standby နာမည် မသတ်မှတ်ထားရင် — synchronous replication ဖွင့်မထားဘူးလို့ အဓိပ္ပာယ်ရပြီး — transaction commit များက replication ကို စောင့်မှာ မဟုတ်ပါဘူး။ ဒါက default configuration ဖြစ်ပါတယ်။ Synchronous replication ဖွင့်ထားတဲ့အခါတောင် — transaction တစ်ခုချင်းစီကို synchronous_commit parameter ကို local ဒါမှမဟုတ် off သတ်မှတ်ပြီး replication ကို စောင့်မနေအောင် ပြင်ဆင်နိုင်ပါတယ်။
ဒီ parameter ကို postgresql.conf ဖိုင်ထဲမှာ ဒါမှမဟုတ် server command line မှာပဲ သတ်မှတ်နိုင်ပါတယ်။
- **synchronized_standby_slots (string)  #** — logical WAL sender process များ စောင့်ရမယ့် streaming replication standby server slot နာမည်များရဲ့ comma နဲ့ ခွဲထားတဲ့ စာရင်း ဖြစ်ပါတယ်။ Logical WAL sender process များက — သတ်မှတ်ထားတဲ့ replication slot များက WAL လက်ခံရရှိကြောင်း အတည်ပြုပြီးမှသာ — decode လုပ်ထားတဲ့ ပြောင်းလဲမှုများကို plugin များဆီ ပို့ပါမယ်။ ဒါက — logical replication failover slot များက — သက်ဆိုင်ရာ physical standby များဆီ အဲဒီပြောင်းလဲမှုများ လက်ခံရရှိပြီး flush ဖြစ်တဲ့အထိ — ပြောင်းလဲမှုများကို မစားသုံးစေတာ အာမခံပါတယ်။ Logical replication connection တစ်ခုက standby promote ဖြစ်ပြီးနောက် physical standby အဖြစ် ပြောင်းလဲသွားမယ်ဆိုရင် — အဲဒီ standby အတွက် physical replication slot ကို ဒီမှာ ထည့်သွင်းသင့်ပါတယ်။ synchronized_standby_slots မှာ သတ်မှတ်ထားတဲ့ slot များ မရှိရင် ဒါမှမဟုတ် invalidate ဖြစ်သွားရင် — logical replication ဆက်လုပ် နိုင်မှာ မဟုတ်ဘူးဆိုတာ သတိပြုပါ။ ဒါ့အပြင် — replication management function များဖြစ်တဲ့ pg_replication_slot_advance, pg_logical_slot_get_changes နဲ့ pg_logical_slot_peek_changes တို့က — logical failover slot များနဲ့ တွဲသုံးတဲ့အခါ — synchronized_standby_slots မှာ သတ်မှတ်ထားတဲ့ physical slot အားလုံး WAL လက်ခံရရှိကြောင်း အတည်ပြုတဲ့အထိ block ဖြစ်နေပါမယ်။
synchronized_standby_slots ထဲက physical replication slot များနဲ့ သက်ဆိုင်တဲ့ standby များက — primary ကနေ logical failover slot ပြောင်းလဲမှုများ လက်ခံရရှိနိုင်ဖို့ — sync_replication_slots = true ကို configure လုပ်ရပါမယ်။

### 19.6.3. Standby Servers (အရန် ဆာဗာများ)

ဒီ setting များက replication data လက်ခံရရှိမယ့် [standby server](/docs/postgresql/warm-standby) တစ်ခုရဲ့ အပြုအမူကို ထိန်းချုပ်ပါတယ်။ Primary server ပေါ်က သူတို့ရဲ့ တန်ဖိုးများက အရေးမပါပါဘူး။

- **primary_conninfo (string)  #** — ပို့ဆောင်တဲ့ server နဲ့ ချိတ်ဆက်ဖို့ standby server သုံးမယ့် connection string ကို သတ်မှတ်ပါတယ်။ ဒီ string က အပိုင်း 32.1.1 တွင် ဖော်ပြထားတဲ့ format အတိုင်း ဖြစ်ပါတယ်။ ဒီ string ထဲမှာ option တစ်ခုခု မသတ်မှတ်ထားရင် — သက်ဆိုင်ရာ environment variable ကို စစ်ပါတယ် (အပိုင်း 32.15 ကို ကြည့်ပါ)။ Environment variable ကိုလည်း မသတ်မှတ်ထားရင်တော့ — default များကို သုံးပါတယ်။
Connection string မှာ ပို့ဆောင်တဲ့ server ရဲ့ host name (ဒါမှမဟုတ် address) ကို သတ်မှတ်သင့်ပါတယ်; standby server ရဲ့ default နဲ့ မတူရင် port number ကိုလည်း သတ်မှတ်ပါ။ ဒါ့အပြင် — ပို့ဆောင်တဲ့ server ပေါ်က သင့်လျော်တဲ့ privilege ရှိတဲ့ role တစ်ခုနဲ့ သက်ဆိုင်တဲ့ user name ကိုလည်း သတ်မှတ်ပါ (အပိုင်း 26.2.5.1 ကို ကြည့်ပါ)။ ပို့ဆောင်သူက password authentication ကို တောင်းဆိုရင် — password ကိုလည်း ပေးရပါမယ်။ ဒါကို primary_conninfo string ထဲမှာ ဒါမှမဟုတ် standby server ပေါ်က သီးခြား ~/.pgpass ဖိုင်ထဲမှာ ပေးနိုင်ပါတယ် (database name အနေနဲ့ replication ကို သုံးပါ)။
Replication slot synchronization အတွက် (အပိုင်း 47.2.3 ကို ကြည့်ပါ) — primary_conninfo string ထဲမှာ မှန်ကန်တဲ့ dbname ကိုလည်း သတ်မှတ်ဖို့ လိုအပ်ပါတယ်။ ဒါကို slot synchronization အတွက်ပဲ သုံးပါမယ်။ Streaming အတွက်တော့ လျစ်လျူရှုပါတယ်။
ဒီ parameter ကို postgresql.conf ဖိုင်ထဲမှာ ဒါမှမဟုတ် server command line မှာပဲ သတ်မှတ်နိုင်ပါတယ်။ WAL receiver process run နေစဉ်မှာ ဒီ parameter ကို ပြောင်းရင် — အဲဒီ process ကို shut down လုပ်ဖို့ signal ပေးပြီး setting အသစ်နဲ့ ပြန်စတင် (restart) လုပ်မယ်လို့ မျှော်လင့်ပါတယ် (primary_conninfo က empty string ဖြစ်တဲ့ အခြေအနေကလွဲလို့)။ Server က standby mode မဟုတ်ရင် ဒီ setting က အကျိုးသက်ရောက်မှု မရှိပါဘူး။
- **primary_slot_name (string)  #** — Streaming replication မှတစ်ဆင့် ပို့ဆောင်တဲ့ server နဲ့ ချိတ်ဆက်တဲ့အခါ upstream node ပေါ်က resource ဖယ်ရှားမှုကို ထိန်းချုပ်ဖို့ သုံးမယ့် — ရှိပြီးသား replication slot တစ်ခုကို ရွေးချယ်စရာအနေနဲ့ သတ်မှတ်ပါတယ် (အပိုင်း 26.2.6 ကို ကြည့်ပါ)။ ဒီ parameter ကို postgresql.conf ဖိုင်ထဲမှာ ဒါမှမဟုတ် server command line မှာပဲ သတ်မှတ်နိုင်ပါတယ်။ WAL receiver process run နေစဉ်မှာ ဒီ parameter ကို ပြောင်းရင် — အဲဒီ process ကို shut down လုပ်ဖို့ signal ပေးပြီး setting အသစ်နဲ့ ပြန်စတင် လုပ်မယ်လို့ မျှော်လင့်ပါတယ်။ primary_conninfo မသတ်မှတ်ထားရင် ဒါမှမဟုတ် server က standby mode မဟုတ်ရင် ဒီ setting က အကျိုးသက်ရောက်မှု မရှိပါဘူး။
- **hot_standby (boolean)  #** — Recovery လုပ်နေစဉ်အတွင်း ချိတ်ဆက်ပြီး query များ run နိုင်သည် မဟုတ်သည် ကို သတ်မှတ်ပါတယ် (အပိုင်း 26.4 တွင် ဖော်ပြထားသည့်အတိုင်း)။ Default တန်ဖိုးကတော့ on ဖြစ်ပါတယ်။ ဒီ parameter ကို server စတင်ချိန်မှာပဲ သတ်မှတ်နိုင်ပါတယ်။ ဒါက archive recovery အတွင်းမှာ ဒါမှမဟုတ် standby mode မှာပဲ အကျိုးသက်ရောက်ပါတယ်။
- **max_standby_archive_delay (integer)  #** — Hot standby active ဖြစ်နေတဲ့အခါ — apply လုပ်တော့မယ့် WAL entry များနဲ့ ကွဲလွဲနေတဲ့ standby query များကို cancel မလုပ်ခင် standby server က ဘယ်လောက်ကြာ စောင့်သင့်တယ်ဆိုတာကို ဒီ parameter က သတ်မှတ်ပါတယ် (အပိုင်း 26.4.2 တွင် ဖော်ပြထားသည့်အတိုင်း)။ max_standby_archive_delay က WAL archive ကနေ WAL data ဖတ်နေတဲ့အခါ (ဒါကြောင့် current မဟုတ်တဲ့အခါ) အကျိုးသက်ရောက်ပါတယ်။ ဒီ တန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် — millisecond အနေနဲ့ ယူပါတယ်။ Default ကတော့ 30 second ဖြစ်ပါတယ်။ -1 တန်ဖိုးက ကွဲလွဲနေတဲ့ query များ ပြီးဆုံးဖို့ standby ကို အကန့်အသတ်မရှိ စောင့်ခွင့်ပြုပါတယ်။ ဒီ parameter ကို postgresql.conf ဖိုင်ထဲမှာ ဒါမှမဟုတ် server command line မှာပဲ သတ်မှတ်နိုင်ပါတယ်။
max_standby_archive_delay ဆိုတာ query တစ်ခု cancel မဖြစ်ခင် run နိုင်တဲ့ အများဆုံး ကြာချိန်နဲ့ မတူဘူးဆိုတာ သတိပြုပါ; ဒါက WAL segment တစ်ခုရဲ့ data ကို apply လုပ်ဖို့ ခွင့်ပြုထားတဲ့ အများဆုံး စုစုပေါင်း ကြာချိန် ဖြစ်ပါတယ်။ ဒါကြောင့် — query တစ်ခုက WAL segment ရဲ့ အစောပိုင်းမှာ သိသိသာသာ နောက်ကျမှု ဖြစ်စေခဲ့ရင် — နောက်ဆက်တွဲ ကွဲလွဲနေတဲ့ query များအတွက် grace time အများကြီး လျော့နည်းသွားပါလိမ့်မယ်။
- **max_standby_streaming_delay (integer)  #** — Hot standby active ဖြစ်နေတဲ့အခါ — apply လုပ်တော့မယ့် WAL entry များနဲ့ ကွဲလွဲနေတဲ့ standby query များကို cancel မလုပ်ခင် standby server က ဘယ်လောက်ကြာ စောင့်သင့်တယ်ဆိုတာကို ဒီ parameter က သတ်မှတ်ပါတယ် (အပိုင်း 26.4.2 တွင် ဖော်ပြထားသည့်အတိုင်း)။ max_standby_streaming_delay က streaming replication မှတစ်ဆင့် WAL data လက်ခံရရှိနေတဲ့အခါ အကျိုးသက်ရောက်ပါတယ်။ ဒီ တန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် — millisecond အနေနဲ့ ယူပါတယ်။ Default ကတော့ 30 second ဖြစ်ပါတယ်။ -1 တန်ဖိုးက ကွဲလွဲနေတဲ့ query များ ပြီးဆုံးဖို့ standby ကို အကန့်အသတ်မရှိ စောင့်ခွင့်ပြုပါတယ်။ ဒီ parameter ကို postgresql.conf ဖိုင်ထဲမှာ ဒါမှမဟုတ် server command line မှာပဲ သတ်မှတ်နိုင်ပါတယ်။
max_standby_streaming_delay ဆိုတာ query တစ်ခု cancel မဖြစ်ခင် run နိုင်တဲ့ အများဆုံး ကြာချိန်နဲ့ မတူဘူးဆိုတာ သတိပြုပါ; ဒါက primary server ကနေ WAL data လက်ခံရရှိပြီးနောက် apply လုပ်ဖို့ ခွင့်ပြုထားတဲ့ အများဆုံး စုစုပေါင်း ကြာချိန် ဖြစ်ပါတယ်။ ဒါကြောင့် — query တစ်ခုက သိသိသာသာ နောက်ကျမှု ဖြစ်စေခဲ့ရင် — standby server ပြန်လည် မီအောင် (caught up) လုပ်ပြီးတဲ့အထိ — နောက်ဆက်တွဲ ကွဲလွဲနေတဲ့ query များအတွက် grace time အများကြီး လျော့နည်းသွားပါလိမ့်မယ်။
- **wal_receiver_create_temp_slot (boolean)  #** — သုံးဖို့ permanent replication slot တစ်ခု (primary_slot_name ကို သုံးပြီး) configure မလုပ်ထားတဲ့အခါ — WAL receiver process က remote instance ပေါ်မှာ temporary replication slot တစ်ခု ဖန်တီးသင့် မသင့် ကို သတ်မှတ်ပါတယ်။ Default ကတော့ off ဖြစ်ပါတယ်။ ဒီ parameter ကို postgresql.conf ဖိုင်ထဲမှာ ဒါမှမဟုတ် server command line မှာပဲ သတ်မှတ်နိုင်ပါတယ်။ WAL receiver process run နေစဉ်မှာ ဒီ parameter ကို ပြောင်းရင် — အဲဒီ process ကို shut down လုပ်ဖို့ signal ပေးပြီး setting အသစ်နဲ့ ပြန်စတင် လုပ်မယ်လို့ မျှော်လင့်ပါတယ်။
- **wal_receiver_status_interval (integer)  #** — Standby ပေါ်က WAL receiver process က replication တိုးတက်မှု အချက်အလက်ကို primary ဒါမှမဟုတ် upstream standby ဆီ ပို့တဲ့ အနည်းဆုံး အကြိမ်အရေအတွက် (frequency) ကို သတ်မှတ်ပါတယ်; အဲဒီမှာ pg_stat_replication view ကို သုံးပြီး ကြည့်နိုင်ပါတယ်။ Standby က သူ ရေးခဲ့တဲ့ နောက်ဆုံး write-ahead log တည်နေရာ၊ disk ဆီ သူ flush လုပ်ခဲ့တဲ့ နောက်ဆုံး position နဲ့ သူ apply လုပ်ခဲ့တဲ့ နောက်ဆုံး position တို့ကို report လုပ်ပါလိမ့်မယ်။ ဒီ parameter ရဲ့ တန်ဖိုးက report များကြားက အများဆုံး ကြာချိန် ဖြစ်ပါတယ်။ Write ဒါမှမဟုတ် flush position ပြောင်းတိုင်း — ဒါမှမဟုတ် ဒီ parameter ကို သုညမဟုတ်တဲ့ တန်ဖိုး သတ်မှတ်ထားရင် အဲဒီ parameter သတ်မှတ်ထားသလောက် မကြာခဏ — update များ ပို့ပါတယ်။ ဒီ parameter ကို လျစ်လျူရှုပြီး update ပို့တဲ့ အခြေအနေများ ထပ်ရှိပါသေးတယ်; ဥပမာ — ရှိပြီးသား WAL ကို process လုပ်တာ ပြီးဆုံးတဲ့အခါ ဒါမှမဟုတ် synchronous_commit ကို remote_apply သတ်မှတ်ထားတဲ့အခါ ဖြစ်ပါတယ်။ ဒါကြောင့် — apply position က တကယ့် position ထက် အနည်းငယ် နောက်ကျနိုင်ပါတယ်။ ဒီ တန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် — second အနေနဲ့ ယူပါတယ်။ Default တန်ဖိုးကတော့ 10 second ဖြစ်ပါတယ်။ ဒီ parameter ကို postgresql.conf ဖိုင်ထဲမှာ ဒါမှမဟုတ် server command line မှာပဲ သတ်မှတ်နိုင်ပါတယ်။
- **hot_standby_feedback (boolean)  #** — Hot standby တစ်ခုက standby ပေါ်မှာ လက်ရှိ execute လုပ်နေတဲ့ query များအကြောင်း primary ဒါမှမဟုတ် upstream standby ဆီ feedback ပို့သည် မပို့သည် ကို သတ်မှတ်ပါတယ်။ ဒီ parameter ကို cleanup record များကြောင့် ဖြစ်တဲ့ query cancel များကို ဖယ်ရှားဖို့ သုံးနိုင်ပါတယ်; ဒါပေမယ့် workload တချို့အတွက် primary ပေါ်မှာ database bloat ဖြစ်စေနိုင်ပါတယ်။ Feedback message များကို wal_receiver_status_interval တစ်ခုလျှင် တစ်ကြိမ်ထက် ပိုမပို့ပါဘူး။ Default တန်ဖိုးကတော့ off ဖြစ်ပါတယ်။ ဒီ parameter ကို postgresql.conf ဖိုင်ထဲမှာ ဒါမှမဟုတ် server command line မှာပဲ သတ်မှတ်နိုင်ပါတယ်။
Cascaded replication သုံးနေရင် — feedback ကို နောက်ဆုံး primary ဆီ ရောက်တဲ့အထိ upstream ဆီ ဆက်ပြီး ပို့ပါတယ်။ Standby များက သူတို့ လက်ခံရရှိတဲ့ feedback ကို upstream ဆီ ပြန်ပို့တာ မှလွဲလို့ အခြား ဘာအတွက်မှ မသုံးပါဘူး။
Standby ပေါ်က clock ကို ရှေ့ ဒါမှမဟုတ် နောက် ရွှေ့လိုက်ရင် — feedback message ကို လိုအပ်တဲ့ interval အတိုင်း ပို့မချင်ရင် ပို့မိနိုင်ပါတယ် ဆိုတာ သတိပြုပါ။ အလွန်အမင်း အခြေအနေများမှာ — feedback ယန္တရားက timestamp များအပေါ် အခြေခံတာမို့ — primary ပေါ်မှာ dead row များကို အချိန်ကြာမြင့်စွာ ဖယ်မရှင်းဘဲ ဆက်လက် အန္တရာယ် ရှိနေနိုင်ပါတယ်။
- **wal_receiver_timeout (integer)  #** — ဒီ ကြာချိန်ထက် ပိုပြီး inactive ဖြစ်နေတဲ့ replication connection များကို ရပ်ဆိုင်းပါတယ်။ ဒါက လက်ခံတဲ့ standby server အတွက် primary node crash ဒါမှမဟုတ် network ပြတ်တောက်မှုကို ရှာဖွေ ဖော်ထုတ်ဖို့ အသုံးဝင်ပါတယ်။ ဒီ တန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် — millisecond အနေနဲ့ ယူပါတယ်။ Default တန်ဖိုးကတော့ 60 second ဖြစ်ပါတယ်။ တန်ဖိုး သုည က timeout ယန္တရားကို ပိတ်ထားပါတယ်။ ဒီ parameter ကို postgresql.conf ဖိုင်ထဲမှာ ဒါမှမဟုတ် server command line မှာပဲ သတ်မှတ်နိုင်ပါတယ်။
- **wal_retrieve_retry_interval (integer)  #** — WAL data ကို မည်သည့် source မှမဆို (streaming replication, local pg_wal ဒါမှမဟုတ် WAL archive) မရနိုင်တဲ့အခါ — WAL data ပြန်လည် ရယူဖို့ ထပ်မကြိုးစားခင် standby server က ဘယ်လောက်ကြာ စောင့်သင့်တယ်ဆိုတာကို သတ်မှတ်ပါတယ်။ ဒီ တန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် — millisecond အနေနဲ့ ယူပါတယ်။ Default တန်ဖိုးကတော့ 5 second ဖြစ်ပါတယ်။ ဒီ parameter ကို postgresql.conf ဖိုင်ထဲမှာ ဒါမှမဟုတ် server command line မှာပဲ သတ်မှတ်နိုင်ပါတယ်။
Recovery ထဲက node တစ်ခုက WAL data အသစ် ရနိုင်ဖို့ စောင့်ရမယ့် ကြာချိန်ကို ထိန်းချုပ်ဖို့ လိုအပ်တဲ့ configuration များမှာ ဒီ parameter က အသုံးဝင်ပါတယ်။ ဥပမာ — archive recovery မှာ WAL ဖိုင် အသစ်တစ်ခုကို ရှာဖွေ ဖော်ထုတ်မှု ပိုမြန်စေဖို့ ဒီ parameter ရဲ့ တန်ဖိုးကို လျှော့ချပြီး recovery ကို ပိုတုံ့ပြန်မြန်စေနိုင်ပါတယ်။ WAL activity နည်းတဲ့ system တစ်ခုမှာ — ဒါကို မြှင့်လိုက်ရင် WAL archive များကို access လုပ်ဖို့ လိုအပ်တဲ့ request အရေအတွက် လျော့နည်းသွားပါတယ်; ဥပမာ — infrastructure ကို access လုပ်တဲ့ အကြိမ်အရေအတွက်ကို ထည့်သွင်း စဉ်းစားတဲ့ cloud ပတ်ဝန်းကျင်များမှာ အသုံးဝင်ပါတယ်။
Logical replication မှာ — ဒီ parameter က ကျရှုံးနေတဲ့ replication apply worker ဒါမှမဟုတ် table synchronization worker ကို ဘယ်လောက် မကြာခဏ ပြန်လည် respawn လုပ်မယ်ဆိုတာကိုလည်း ကန့်သတ်ပါတယ်။
- **recovery_min_apply_delay (integer)  #** — Default အားဖြင့် — standby server တစ်ခုက ပို့ဆောင်တဲ့ server ကနေ WAL record များကို တတ်နိုင်သမျှ မြန်မြန် restore လုပ်ပါတယ်။ အချိန်နောက်ကျတဲ့ (time-delayed) data copy တစ်ခု ရှိတာက အသုံးဝင်နိုင်ပြီး — data ဆုံးရှုံးမှု အမှားများကို ပြင်ဆင်ဖို့ အခွင့်အလမ်းများ ပေးပါတယ်။ ဒီ parameter က recovery ကို သတ်မှတ်ထားတဲ့ ကြာချိန်တစ်ခုအထိ နောက်ကျစေခွင့်ပြုပါတယ်။ ဥပမာ — ဒီ parameter ကို 5min သတ်မှတ်ရင် — standby ပေါ်က system time က primary က report လုပ်တဲ့ commit time ကို အနည်းဆုံး ငါးမိနစ် ကျော်ပြီးမှသာ — standby က transaction commit တစ်ခုချင်းစီကို replay လုပ်ပါလိမ့်မယ်။ ဒီ တန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် — millisecond အနေနဲ့ ယူပါတယ်။ Default ကတော့ သုည ဖြစ်ပြီး — နောက်ကျမှု ဘာမှ မထည့်ပါဘူး။
Server များကြားက replication နောက်ကျမှုက ဒီ parameter ရဲ့ တန်ဖိုးထက် ကျော်လွန်နိုင်ပြီး — အဲဒီအခါ နောက်ကျမှု ဘာမှ မထည့်ပါဘူး။ ဒီ နောက်ကျမှုကို primary ပေါ်မှာ ရေးထားတဲ့ WAL timestamp နဲ့ standby ပေါ်က လက်ရှိ အချိန်ကြားမှာ တွက်ချက်တယ်ဆိုတာ သတိပြုပါ။ Network နောက်ကျမှု ဒါမှမဟုတ် cascading replication configuration များကြောင့် ဖြစ်တဲ့ transfer နောက်ကျမှုများက တကယ့် စောင့်ဆိုင်းချိန်ကို သိသိသာသာ လျှော့ချနိုင်ပါတယ်။ Primary နဲ့ standby ပေါ်က system clock များ sync မဖြစ်ရင် — ဒါက recovery က record များကို မျှော်လင့်ထားတာထက် စောပြီး apply လုပ်စေနိုင်ပါတယ်; ဒါပေမယ့် ဒါက အရေးကြီး ပြဿနာ မဟုတ်ပါဘူး — အကြောင်းက ဒီ parameter ရဲ့ အသုံးဝင်တဲ့ setting များက server များကြားက ပုံမှန် အချိန် ကွဲလွဲမှုများထက် အများကြီး ကြီးတာကြောင့် ဖြစ်ပါတယ်။
နောက်ကျမှုက transaction commit များအတွက် WAL record များမှာပဲ ဖြစ်ပါတယ်။ အခြား record များကို တတ်နိုင်သမျှ မြန်မြန် replay လုပ်ပါတယ်; ဒါက ပြဿနာ မဟုတ်ပါဘူး — အကြောင်းက MVCC visibility rule များက သက်ဆိုင်ရာ commit record ကို apply လုပ်ပြီးမှသာ သူတို့ရဲ့ အကျိုးသက်ရောက်မှုများ မြင်နိုင်အောင် အာမခံတာကြောင့် ဖြစ်ပါတယ်။
နောက်ကျမှုက — recovery ထဲက database က consistent state တစ်ခုကို ရောက်ပြီးမှ — standby promote ဒါမှမဟုတ် trigger ဖြစ်တဲ့အထိ ဖြစ်ပါတယ်။ အဲဒီနောက်မှာတော့ standby က နောက်ထပ် စောင့်ဆိုင်းမှု မရှိဘဲ recovery ကို အဆုံးသတ်ပါလိမ့်မယ်။
WAL record များကို apply ဖို့ အသင့်ဖြစ်တဲ့အထိ standby ပေါ်မှာ ထိန်းထားရပါမယ်။ ဒါကြောင့် — ကြာချိန် ပိုကြာတာက WAL ဖိုင်များ ပိုမို စုပုံလာစေပြီး — standby ရဲ့ pg_wal directory အတွက် disk space လိုအပ်ချက် တိုးလာစေပါတယ်။
ဒီ parameter ကို streaming replication deployment များနဲ့ တွဲသုံးဖို့ ရည်ရွယ်ထားပါတယ်; ဒါပေမယ့် — parameter ကို သတ်မှတ်ထားရင် — crash recovery ကလွဲလို့ အခြေအနေအားလုံးမှာ ဒါကို လိုက်နာပါမယ်။ ဒီ feature ကို သုံးတာကြောင့် hot_standby_feedback နောက်ကျသွားနိုင်ပြီး — primary ပေါ်မှာ bloat ဖြစ်စေနိုင်ပါတယ်; နှစ်ခုကို အတူတွဲသုံးရင် သတိထားပါ။

> **သတိပေးချက်:** synchronous_commit ကို remote_apply သတ်မှတ်ထားတဲ့အခါ — synchronous replication က ဒီ setting ကြောင့် သက်ရောက်ခံရပါတယ်; COMMIT တစ်ခုချင်းစီက apply ဖြစ်တဲ့အထိ စောင့်ရပါလိမ့်မယ်။

ဒီ parameter ကို postgresql.conf ဖိုင်ထဲမှာ ဒါမှမဟုတ် server command line မှာပဲ သတ်မှတ်နိုင်ပါတယ်။
- **sync_replication_slots (boolean)  #** — Physical standby တစ်ခုက primary server ကနေ logical failover slot များကို sync လုပ်နိုင်စေပြီး — failover ပြီးနောက် logical subscriber များက primary server အသစ်ကနေ replication ကို ပြန်လည် စတင်နိုင်စေပါတယ်။
Default အားဖြင့် disabled ဖြစ်ပါတယ်။ ဒီ parameter ကို postgresql.conf ဖိုင်ထဲမှာ ဒါမှမဟုတ် server command line မှာပဲ သတ်မှတ်နိုင်ပါတယ်။

### 19.6.4. Subscribers (စာရင်းသွင်း လက်ခံသူများ)

ဒီ setting များက logical replication subscriber တစ်ခုရဲ့ အပြုအမူကို ထိန်းချုပ်ပါတယ်။ Publisher ပေါ်က သူတို့ရဲ့ တန်ဖိုးများက အရေးမပါပါဘူး။ အသေးစိတ် ပိုမိုသိရှိဖို့ [အပိုင်း 29.12](/docs/postgresql/logical-replication-config) ကို ကြည့်ပါ။

- **max_active_replication_origins (integer)  #** — replication origin ဘယ်နှစ်ခုကို တစ်ပြိုင်နက် (simultaneously) ခြေရာခံနိုင်မလဲ ကို သတ်မှတ်ပါတယ် (အခန်း 48 ကို ကြည့်ပါ); ဒါက server ပေါ်မှာ logical replication subscription ဘယ်နှစ်ခု ဖန်တီးနိုင်မလဲ ဆိုတာကို ထိရောက်စွာ ကန့်သတ်ပါတယ်။ လက်ရှိ ခြေရာခံထားတဲ့ replication origin အရေအတွက် (pg_replication_origin_status မှာ ထင်ဟပ်နေတဲ့) ထက် နည်းတဲ့ တန်ဖိုးတစ်ခု သတ်မှတ်ရင် — server က စတင် လုပ်နိုင်မှာ မဟုတ်ပါဘူး။ Default ကတော့ 10 ဖြစ်ပါတယ်။ ဒီ parameter ကို server စတင်ချိန်မှာပဲ သတ်မှတ်နိုင်ပါတယ်။ max_active_replication_origins ကို subscriber ဆီ ထည့်မယ့် subscription အရေအတွက်အပြင် — table synchronization အတွက် အရန်အနေနဲ့ အနည်းငယ် — အနည်းဆုံး အဲဒီလောက် သတ်မှတ်ရပါမယ်။
- **max_logical_replication_workers (integer)  #** — logical replication worker အများဆုံး အရေအတွက်ကို သတ်မှတ်ပါတယ်။ ဒါမှာ leader apply worker များ၊ parallel apply worker များနဲ့ table synchronization worker များ ပါဝင်ပါတယ်။
Logical replication worker များကို max_worker_processes က သတ်မှတ်ထားတဲ့ pool ကနေ ယူပါတယ်။
Default တန်ဖိုးကတော့ 4 ဖြစ်ပါတယ်။ ဒီ parameter ကို server စတင်ချိန်မှာပဲ သတ်မှတ်နိုင်ပါတယ်။
- **max_sync_workers_per_subscription (integer)  #** — subscription တစ်ခုလျှင် synchronization worker အများဆုံး အရေအတွက် ဖြစ်ပါတယ်။ ဒီ parameter က subscription initialization လုပ်တဲ့အခါ ဒါမှမဟုတ် table အသစ်များ ထည့်တဲ့အခါ initial data copy ရဲ့ parallelism ပမာဏကို ထိန်းချုပ်ပါတယ်။
လက်ရှိမှာ table တစ်ခုလျှင် synchronization worker တစ်ခုပဲ ရှိနိုင်ပါတယ်။
Synchronization worker များကို max_logical_replication_workers က သတ်မှတ်ထားတဲ့ pool ကနေ ယူပါတယ်။
Default တန်ဖိုးကတော့ 2 ဖြစ်ပါတယ်။ ဒီ parameter ကို postgresql.conf ဖိုင်ထဲမှာ ဒါမှမဟုတ် server command line မှာပဲ သတ်မှတ်နိုင်ပါတယ်။
- **max_parallel_apply_workers_per_subscription (integer)  #** — subscription တစ်ခုလျှင် parallel apply worker အများဆုံး အရေအတွက် ဖြစ်ပါတယ်။ ဒီ parameter က subscription parameter streaming = parallel နဲ့ in-progress transaction များကို streaming လုပ်တဲ့အခါ parallelism ပမာဏကို ထိန်းချုပ်ပါတယ်။
Parallel apply worker များကို max_logical_replication_workers က သတ်မှတ်ထားတဲ့ pool ကနေ ယူပါတယ်။
Default တန်ဖိုးကတော့ 2 ဖြစ်ပါတယ်။ ဒီ parameter ကို postgresql.conf ဖိုင်ထဲမှာ ဒါမှမဟုတ် server command line မှာပဲ သတ်မှတ်နိုင်ပါတယ်။
