## 26.1. Comparison of Different Solutions (replication နည်းလမ်း အမျိုးမျိုး နှိုင်းယှဉ် ခြုံငုံ သုံးသပ်ချက်)

- **Shared Disk Failover (shared disk failover — မျှဝေသုံး disk failover)** — Shared disk failover က — database ရဲ့ copy တစ်ခုတည်းကိုပဲ ထားရှိတာမို့ — synchronization overhead (ထပ်တူပြု ချိန်ကိုက်မှု ဝန်ပိုး) ကို ရှောင်ရှားပါတယ်။ ဒါက server အများအပြားက မျှဝေသုံးတဲ့ disk array တစ်ခုတည်းကို အသုံးပြုပါတယ်။ ပင်မ database server (primary server) ကျရှုံးသွားခဲ့ရင် — standby server (အရန် server) က — database crash (database ပျက်ကျမှု) တစ်ခုကနေ recovery (ပြန်လည် ထူထောင်ခြင်း) လုပ်နေသလိုပဲ — database ကို mount လုပ်ပြီး စတင်နိုင်ပါတယ်။ ဒါက data ဆုံးရှုံးမှု မရှိဘဲ လျင်မြန်စွာ failover (primary ပြောင်းလဲ လွှဲပြောင်းမှု) လုပ်နိုင်စေပါတယ်။
Shared hardware (မျှဝေသုံး hardware) လုပ်ဆောင်ချက်က network storage devices (ကွန်ရက် သိုလှောင်မှု ကိရိယာများ) တွေမှာ အသုံးများပါတယ်။ Network file system (ကွန်ရက် ဖိုင်စနစ်) တစ်ခုကို သုံးတာလည်း ဖြစ်နိုင်ပေမယ့် — file system က POSIX behavior (POSIX အပြုအမူ) အပြည့်အဝ ရှိဖို့တော့ ဂရုစိုက်ရပါမယ် ([အပိုင်း 18.2.2.1](https://www.postgresql.org/docs/current/creating-cluster.html#CREATING-CLUSTER-NFS) ကို ကြည့်ပါ)။ ဒီနည်းလမ်းရဲ့ သိသာတဲ့ ကန့်သတ်ချက် တစ်ခုကတော့ — မျှဝေသုံး disk array က ကျရှုံးသွားတာ ဒါမှမဟုတ် ပျက်စီး (corrupt) သွားခဲ့ရင် — primary ရော standby server ပါ နှစ်ခုလုံး အလုပ်မလုပ်တော့တာ ဖြစ်ပါတယ်။ နောက်ထပ် ပြဿနာ တစ်ခုကတော့ — primary server run နေချိန်မှာ standby server က မျှဝေသုံး storage ကို ဘယ်တော့မှ ဝင်ရောက်လို့ မရဘူးဆိုတာ ဖြစ်ပါတယ်။
- **File System (Block Device) Replication (file system (block device) replication — ဖိုင်စနစ် ပုံတူပွားခြင်း)** — Shared hardware လုပ်ဆောင်ချက်ရဲ့ ပြုပြင်ထားတဲ့ ဗားရှင်း တစ်မျိုးကတော့ — file system replication ဖြစ်ပြီး — file system တစ်ခုပေါ်က ပြောင်းလဲမှု (changes) တွေ အားလုံးကို — အခြား ကွန်ပျူတာ တစ်ခုပေါ်မှာ တည်ရှိတဲ့ file system ဆီ mirror (ပုံတူပွား ကူးယူ) လုပ်ပေးပါတယ်။ တစ်ခုတည်းသော ကန့်သတ်ချက်ကတော့ — standby server မှာ file system ရဲ့ consistent copy (တစ်သမတ်တည်း မိတ္တူ) တစ်ခု ရှိစေမယ့် နည်းလမ်းနဲ့ mirroring ကို လုပ်ရမှာ ဖြစ်ပြီး — အထူးသဖြင့် — standby ဆီ ရေးသားမှု (writes) တွေကို primary ပေါ်က ရေးသားမှုတွေနဲ့ တူညီတဲ့ အစီအစဉ် (order) အတိုင်း လုပ်ဆောင်ရပါမယ်။ DRBD က Linux အတွက် လူကြိုက်များတဲ့ file system replication ဖြေရှင်းနည်း တစ်ခု ဖြစ်ပါတယ်။
- **Write-Ahead Log Shipping (write-ahead log (WAL) ပို့ဆောင်ခြင်း)** — write-ahead log (WAL) records (ဒေတာ မရေးသားမီ ကြိုတင် မှတ်တမ်းတင်သော log record များ) ရဲ့ stream (စီးကြောင်း) တစ်ခုကို ဖတ်ခြင်းအားဖြင့် — warm နဲ့ hot standby servers တွေကို နောက်ဆုံး အခြေအနေ (up-to-date) နဲ့ နီးကပ်နေအောင် ထိန်းသိမ်းထားနိုင်ပါတယ်။ ပင်မ server ကျရှုံးသွားရင် — standby ထဲမှာ ပင်မ server ရဲ့ data အားလုံးနီးပါး ပါဝင်နေတာမို့ — standby ကို primary database server အသစ် အဖြစ် လျင်မြန်စွာ ပြောင်းလဲနိုင်ပါတယ်။ ဒါက synchronous (synchronous — တစ်ပြိုင်နက် ထပ်တူပြု) ဒါမှမဟုတ် asynchronous (asynchronous — နောက်ကျမှ လုပ်ဆောင်သော) ဖြစ်နိုင်ပြီး — database server တစ်ခုလုံးအတွက်ပဲ လုပ်ဆောင်နိုင်ပါတယ်။
Standby server တစ်ခုကို — file-based log shipping (ဖိုင်အခြေပြု log ပို့ဆောင်ခြင်း — [အပိုင်း 26.2](https://www.postgresql.org/docs/current/warm-standby.html)) ဒါမှမဟုတ် streaming replication (streaming replication — စီးဆင်းမှု ပုံစံ replication; [အပိုင်း 26.2.5](https://www.postgresql.org/docs/current/warm-standby.html#STREAMING-REPLICATION) ကို ကြည့်ပါ) ဒါမှမဟုတ် နှစ်ခုလုံးရဲ့ ပေါင်းစပ်မှု ကို သုံးပြီး အကောင်အထည် ဖော်နိုင်ပါတယ်။ Hot standby အကြောင်း အချက်အလက်အတွက် [အပိုင်း 26.4](https://www.postgresql.org/docs/current/hot-standby.html) ကို ကြည့်ပါ။
- **Logical Replication (logical replication — ယုတ္တိ အဆင့် replication)** — Logical replication က database server တစ်ခုကို — data modifications (data ပြုပြင်မွမ်းမံမှုများ) တွေရဲ့ stream တစ်ခုကို အခြား server တစ်ခုဆီ ပို့ပေးနိုင်စေပါတယ်။ PostgreSQL ရဲ့ logical replication က WAL ကနေ logical data modifications တွေရဲ့ stream တစ်ခုကို တည်ဆောက်ပေးပါတယ်။ Logical replication က data ပြောင်းလဲမှုတွေကို table အလိုက် (per-table basis) replicate (ပုံတူပွား) လုပ်နိုင်စေပါတယ်။ ထို့အပြင် — ကိုယ့်ရဲ့ ပြောင်းလဲမှုတွေကို publish (ထုတ်ဝေ) လုပ်နေတဲ့ server တစ်ခုက — အခြား server တစ်ခုကနေ ပြောင်းလဲမှုတွေကို subscribe (စာရင်းသွင်း လက်ခံ) လုပ်နိုင်တာမို့ — data တွေကို ဦးတည်ချက် အမျိုးမျိုးနဲ့ စီးဆင်းစေနိုင်ပါတယ်။ Logical replication အကြောင်း နောက်ထပ် အချက်အလက်အတွက် [အခန်း 29](https://www.postgresql.org/docs/current/logical-replication.html) ကို ကြည့်ပါ။ Logical decoding interface (logical decoding interface — logical ကုဒ်ဖော်ခြင်း interface; [အခန်း 47](https://www.postgresql.org/docs/current/logicaldecoding.html)) ကနေတစ်ဆင့် — third-party extensions တွေကလည်း အလားတူ လုပ်ဆောင်ချက်တွေကို ပေးစွမ်းနိုင်ပါတယ်။
- **Trigger-Based Primary-Standby Replication (trigger အခြေပြု primary-standby replication)** — Trigger-based replication setup (trigger အခြေပြု replication စီစဉ်မှု) က ပုံမှန်အားဖြင့် — data modification queries (data ပြုပြင် မွမ်းမံမှု queries) တွေကို သတ်မှတ်ထားတဲ့ primary server တစ်ခုဆီ စုစည်း ပို့ဆောင်ပေးပါတယ်။ Table အလိုက် လုပ်ဆောင်ပြီး — primary server က data ပြောင်းလဲမှုတွေကို (ပုံမှန်အားဖြင့်) asynchronous အနေနဲ့ standby servers တွေဆီ ပို့ပေးပါတယ်။ Primary run နေချိန်မှာ standby servers တွေက queries တွေကို ဖြေဆိုနိုင်ပြီး — ဒေသတွင်း (local) data ပြောင်းလဲမှု ဒါမှမဟုတ် ရေးသားမှု လုပ်ဆောင်ချက် (write activity) တချို့ကိုလည်း ခွင့်ပြုနိုင်ပါတယ်။ ဒီ replication ပုံစံကို — ကြီးမားတဲ့ analytical (ခွဲခြမ်းစိတ်ဖြာ သုံးသပ်မှု) ဒါမှမဟုတ် data warehouse (ဒေတာ သိုလှောင်ရုံ) queries တွေကို offload (ဝန်လွှဲပြောင်း) လုပ်ဖို့ မကြာခဏ သုံးပါတယ်။
Slony-I က ဒီ replication အမျိုးအစားရဲ့ ဥပမာ တစ်ခု ဖြစ်ပြီး — per-table granularity (table အလိုက် သေးစိတ် ထိန်းချုပ်နိုင်မှု) နဲ့ standby server အများအပြားအတွက် ထောက်ပံ့မှု ရှိပါတယ်။ ဒါက standby server ကို asynchronous အနေနဲ့ (အစုလိုက် — batches လိုက်) update လုပ်တာမို့ — failover ဖြစ်စဉ် အတွင်းမှာ data ဆုံးရှုံးမှု ဖြစ်နိုင်ပါတယ်။
- **SQL-Based Replication Middleware (SQL အခြေပြု replication middleware)** — SQL-based replication middleware နဲ့ဆိုရင် — program တစ်ခုက SQL query တိုင်းကို ကြားဖြတ် ဖမ်းယူ (intercept) ပြီး — server တစ်ခု ဒါမှမဟုတ် အားလုံးဆီ ပို့ပေးပါတယ်။ Server တစ်ခုစီက သီးခြား လွတ်လပ်စွာ လည်ပတ်ပါတယ်။ Read-write (ရေးသား-ဖတ်ရှု) queries တွေကို server တွေ အားလုံးဆီ ပို့ပေးရမှာ ဖြစ်လို့ — server တိုင်းက ပြောင်းလဲမှု အားလုံးကို လက်ခံရရှိပါတယ်။ ဒါပေမယ့် — read-only (ဖတ်ရှုရုံသက်သက်) queries တွေကိုတော့ server တစ်ခုတည်းဆီပဲ ပို့နိုင်လို့ — read workload (ဖတ်ရှုမှု ဝန်အား) ကို server တွေကြားမှာ ခွဲဝေ ဖြန့်ဝေနိုင်ပါတယ်။
Query တွေကို ပြုပြင်မှု မရှိဘဲ broadcast (ထုတ်လွှင့်) လုပ်ရုံပဲ ဆိုရင် — random(), CURRENT_TIMESTAMP လို functions တွေနဲ့ sequences တွေက server တစ်ခုနဲ့ တစ်ခုမှာ မတူညီတဲ့ တန်ဖိုးတွေ ရှိနိုင်ပါတယ်။ ဒါက — server တစ်ခုစီက သီးခြား လွတ်လပ်စွာ လည်ပတ်တာရော — SQL queries တွေကို တကယ့် data ပြောင်းလဲမှုတွေ အစား broadcast လုပ်တာရော ကြောင့် ဖြစ်ပါတယ်။ ဒါက လက်မခံနိုင်ဘူးဆိုရင် — middleware ဒါမှမဟုတ် application က — အဲဒီလို တန်ဖိုးတွေကို အရင်းအမြစ် (source) တစ်ခုတည်းကနေ ဆုံးဖြတ်ပြီး — ရေးသားမှု (write) queries တွေထဲမှာ အဲဒီတန်ဖိုးတွေကို သုံးရပါမယ်။ Transaction တွေ အားလုံးက server တွေ အားလုံးပေါ်မှာ commit (transaction အတည်ပြု လုပ်ဆောင်မှု) ဖြစ်တာ ဒါမှမဟုတ် abort (ဖျက်သိမ်း) ဖြစ်တာ သေချာစေဖို့လည်း ဂရုစိုက်ရပြီး — two-phase commit (အဆင့်နှစ်ဆင့် commit) ကို သုံးနိုင်ပါတယ် (PREPARE TRANSACTION နဲ့ COMMIT PREPARED)။ Pgpool-II နဲ့ Continuent Tungsten တို့က ဒီ replication အမျိုးအစားရဲ့ ဥပမာတွေ ဖြစ်ပါတယ်။
- **Asynchronous Multimaster Replication (asynchronous multimaster replication — master server အများအပြား ပါဝင်သော asynchronous replication)** — ပုံမှန် ချိတ်ဆက်မထားတဲ့ ဒါမှမဟုတ် နှေးကွေးတဲ့ ဆက်သွယ်ရေး လိုင်းတွေ ရှိတဲ့ servers တွေအတွက် — ဥပမာ laptops (လက်ပ်တော့များ) ဒါမှမဟုတ် remote servers (ဝေးလံသော server များ) — server တွေကြားမှာ data တွေကို တစ်သမတ်တည်း ထားရှိတာက စိန်ခေါ်မှု တစ်ခု ဖြစ်ပါတယ်။ Asynchronous multimaster replication ကို သုံးတဲ့အခါ — server တစ်ခုစီက သီးခြား လုပ်ဆောင်ပြီး — conflict ဖြစ်နေတဲ့ (ကွဲလွဲနေသော) transactions တွေကို ဖော်ထုတ်ဖို့ — အခြား servers တွေနဲ့ အခါအားလျော်စွာ (periodically) ဆက်သွယ်ပါတယ်။ ဒီ conflicts တွေကို users တွေ ဒါမှမဟုတ် conflict resolution rules (conflict ဖြေရှင်းရေး စည်းမျဉ်းများ) က ဖြေရှင်းနိုင်ပါတယ်။ Bucardo က ဒီ replication အမျိုးအစားရဲ့ ဥပမာ တစ်ခု ဖြစ်ပါတယ်။
- **Synchronous Multimaster Replication (synchronous multimaster replication — master server အများအပြား ပါဝင်သော synchronous replication)** — Synchronous multimaster replication မှာ — server တိုင်းက write requests (ရေးသားမှု တောင်းဆိုချက်များ) တွေကို လက်ခံနိုင်ပြီး — transaction တစ်ခုစီ commit မလုပ်ခင် — ပြုပြင်ထားတဲ့ data ကို မူရင်း server ကနေ အခြား server တိုင်းဆီ ပို့ဆောင်ပေးပါတယ်။ ပြင်းထန်တဲ့ write activity (ရေးသားမှု လုပ်ဆောင်ချက်) တွေက locking (သော့ခတ်မှု) နဲ့ commit နှောင့်နှေးမှုတွေ အလွန်အကျွံ ဖြစ်စေပြီး — စွမ်းဆောင်ရည် ညံ့ဖျင်းစေနိုင်ပါတယ်။ Read requests (ဖတ်ရှုမှု တောင်းဆိုချက်များ) တွေကိုတော့ server ဘယ်ခုကိုမဆို ပို့နိုင်ပါတယ်။ Implementation တချို့က ဆက်သွယ်မှု overhead ကို လျှော့ချဖို့ shared disk ကို သုံးပါတယ်။ Synchronous multimaster replication က အများစု ဖတ်ရှုရတဲ့ workloads (mostly read workloads) တွေအတွက် အကောင်းဆုံး ဖြစ်ပေမယ့် — သူ့ရဲ့ အဓိက အားသာချက်ကတော့ — server ဘယ်ခုမဆို write requests တွေကို လက်ခံနိုင်တာ ဖြစ်ပါတယ် — primary နဲ့ standby servers တွေကြားမှာ workloads တွေကို ခွဲဝေစရာ (partition) မလိုတော့ဘဲ — data ပြောင်းလဲမှုတွေကို server တစ်ခုကနေ နောက်တစ်ခုဆီ ပို့ပေးတာမို့ — random() လို non-deterministic functions (ကြိုတင် မခန့်မှန်းနိုင်သော functions) တွေနဲ့ ပြဿနာ မရှိပါဘူး။
PostgreSQL က ဒီ replication အမျိုးအစားကိုတော့ မပေးအပ်ပါဘူး — ဒါပေမယ့် — PostgreSQL ရဲ့ two-phase commit (PREPARE TRANSACTION နဲ့ COMMIT PREPARED) ကို application code ဒါမှမဟုတ် middleware ထဲမှာ ဒါကို အကောင်အထည် ဖော်ဖို့ သုံးနိုင်ပါတယ်။

[ဇယား 26.1](https://www.postgresql.org/docs/current/different-replication-solutions.html#HIGH-AVAILABILITY-MATRIX) က အထက်မှာ စာရင်းပြုထားတဲ့ ဖြေရှင်းနည်း အမျိုးမျိုးရဲ့ စွမ်းရည် (capabilities) တွေကို အကျဉ်းချုပ် ဖော်ပြပါတယ်။

အထက်ပါ အမျိုးအစားတွေနဲ့ မကိုက်ညီတဲ့ ဖြေရှင်းနည်း အနည်းငယ်လည်း ရှိပါသေးတယ်:

- **Data Partitioning (data partitioning — ဒေတာ ပိုင်းခြားခြင်း)** — Data partitioning က tables တွေကို data sets (data အစုများ) တွေအဖြစ် ပိုင်းခြားပါတယ်။ Set တစ်ခုစီကို server တစ်ခုတည်းကပဲ ပြုပြင် မွမ်းမံနိုင်ပါတယ်။ ဥပမာ — data တွေကို ရုံး (office) အလိုက် ပိုင်းခြားနိုင်ပြီး — ဥပမာ London နဲ့ Paris — ရုံးတစ်ခုစီမှာ server တစ်ခုစီ ရှိပါတယ်။ London နဲ့ Paris ရဲ့ data တွေကို ပေါင်းစပ်တဲ့ queries တွေ လိုအပ်ရင် — application က server နှစ်ခုလုံးကို query လုပ်နိုင်သလို — server တစ်ခုစီပေါ်မှာ အခြား ရုံးရဲ့ data ရဲ့ read-only copy (ဖတ်ရှုရုံ copy) တစ်ခု ထားရှိဖို့ primary/standby replication ကိုလည်း သုံးနိုင်ပါတယ်။
- **Multiple-Server Parallel Query Execution (server အများအပြားဖြင့် parallel query လုပ်ဆောင်ခြင်း)** — အထက်က ဖြေရှင်းနည်း အများအပြားက — server အများအပြားနဲ့ queries အများအပြားကို ကိုင်တွယ်နိုင်စေပေမယ့် — query တစ်ခုတည်း ပိုမြန်မြန် ပြီးမြောက်ဖို့ server အများအပြားကို သုံးခွင့် ပြုတာတော့ ဘယ်ဟာမှ မရှိပါဘူး။ ဒီဖြေရှင်းနည်းကတော့ — query တစ်ခုတည်းပေါ်မှာ server အများအပြားကို တစ်ပြိုင်နက် (concurrently) အလုပ်လုပ်ခွင့် ပြုပါတယ်။ ဒါကို ပုံမှန်အားဖြင့် — data တွေကို server တွေကြားမှာ ပိုင်းခြားပြီး — server တစ်ခုစီက query ရဲ့ သူ့အပိုင်းကို execute (လုပ်ဆောင်) ပြီး — ရလဒ်တွေကို ပေါင်းစည်းပြီး user ဆီ ပြန်ပေးတဲ့ central server (ဗဟို server) တစ်ခုဆီ ပြန်ပို့ခြင်းအားဖြင့် အောင်မြင်စွာ လုပ်ဆောင်ပါတယ်။ ဒါကို PL/Proxy tool set ကို သုံးပြီး အကောင်အထည် ဖော်နိုင်ပါတယ်။

PostgreSQL က open source (အဖွင့် source) ဖြစ်ပြီး လွယ်ကူစွာ extension (တိုးချဲ့) လုပ်နိုင်တာမို့ — ကုမ္ပဏီ အများအပြားက PostgreSQL ကို အခြေခံပြီး — ထူးခြားတဲ့ failover, replication နဲ့ load balancing (load balancing — ဝန်အား ခွဲဝေခြင်း) စွမ်းရည်တွေ ရှိတဲ့ commercial closed-source (စီးပွားဖြစ် ပိတ်ထားသော source) ဖြေရှင်းနည်းတွေကို ဖန်တီးထားကြောင်းကိုလည်း သတိပြုသင့်ပါတယ်။ ဒါတွေကိုတော့ ဒီမှာ ဆွေးနွေးထားခြင်း မရှိပါဘူး။
