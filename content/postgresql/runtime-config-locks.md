## 19.12. Lock Management (lock စီမံခန့်ခွဲမှု)

- **deadlock_timeout (integer)** — ဒါက lock တစ်ခုအပေါ် စောင့်ဆိုင်းပြီး — deadlock အခြေအနေ ရှိမရှိ စစ်ဆေးဖို့ မစစ်ဆေးမီ — စောင့်ရမယ့် အချိန် ပမာဏ ဖြစ်ပါတယ်။ Deadlock စစ်ဆေးခြင်းက အတော်လေး ကုန်ကျစရိတ် ကြီးတာကြောင့် — server က lock တစ်ခုကို စောင့်တိုင်း အဲဒါကို run မလုပ်ပါဘူး။ Production application တွေမှာ deadlock ဖြစ်တာ အဖြစ်မများဘူးလို့ အကောင်းမြင်ယူဆပြီး — deadlock စစ်ဆေးဖို့ ဆုံးဖြတ်မီ lock အပေါ်မှာ ခဏ စောင့်ဆိုင်းထားပါတယ်။ ဒီတန်ဖိုးကို တိုးမြှင့်ခြင်းက — မလိုအပ်တဲ့ deadlock စစ်ဆေးမှုတွေမှာ ကုန်ဆုံးတဲ့ အချိန်ပမာဏကို လျှော့ချပေမယ့် — တကယ့် deadlock error တွေကို အစီရင်ခံတာကို နှေးစေပါတယ်။ ဒီတန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် — millisecond အဖြစ် ယူဆပါတယ်။ Default က တစ်စက္ကန့် (`1s`) ဖြစ်ပြီး — လက်တွေ့မှာ သင်လိုချင်မယ့် အနီးစပ်ဆုံး အငယ်ဆုံး တန်ဖိုးလို့ ဆိုနိုင်ပါတယ်။ အလွန်အမင်း အလုပ်များနေတဲ့ server တစ်ခုမှာ ဒါကို မြှင့်ချင်မြှင့်နိုင်ပါတယ်။ အကောင်းဆုံးအားဖြင့် — ဒီ setting က သင့်ရဲ့ ပုံမှန် transaction အချိန်ထက် ကျော်လွန်သင့်ပြီး — ဒါက waiter က deadlock စစ်ဆေးဖို့ ဆုံးဖြတ်မီ lock ပြန်လွှတ်ခံရဖို့ အလားအလာကို တိုးစေပါတယ်။ Superuser များနှင့် သင့်လျော်တဲ့ `SET` privilege ရှိတဲ့ user များသာ ဒီ setting ကို ပြောင်းနိုင်ပါတယ်။
[log_lock_waits](/docs/postgresql/runtime-config-logging) သတ်မှတ်ထားတဲ့အခါ — ဒီ parameter က lock စောင့်ဆိုင်းမှု အကြောင်း log message တစ်ခု ထုတ်မယ့်အခါ စောင့်ဆိုင်းရမယ့် အချိန် ပမာဏကိုလည်း ဆုံးဖြတ်ပါတယ်။ Locking delay တွေကို စူးစမ်းစစ်ဆေးဖို့ ကြိုးစားနေရင် — ပုံမှန်ထက် ပိုတိုတဲ့ `deadlock_timeout` ကို သတ်မှတ်ချင်နိုင်ပါတယ်။
- **max_locks_per_transaction (integer)** — Shared lock table မှာ server process ဒါမှမဟုတ် prepared transaction တစ်ခုချင်းစီအတွက် `max_locks_per_transaction` object (ဥပမာ — table) အတွက် နေရာ ရှိပါတယ်; ဒါကြောင့် တစ်ကြိမ်လျှင် ဒီအရေအတွက်ထက် ပိုတဲ့ ထူးခြားတဲ့ object တွေကို lock လုပ်လို့ မရပါဘူး။ ဒီ parameter က transaction တစ်ခုချင်းစီ အသုံးပြုတဲ့ object lock အရေအတွက် ပျမ်းမျှကို ကန့်သတ်ပါတယ်; transaction အားလုံးရဲ့ lock တွေ lock table ထဲ ဝင်ဆံ့သရွေ့ — တစ်ခုချင်း transaction တွေက object တွေကို ပိုပြီး lock လုပ်နိုင်ပါတယ်။ ဒါက lock လုပ်နိုင်တဲ့ row အရေအတွက် *မဟုတ်* ပါဘူး; အဲဒီတန်ဖိုးက အကန့်အသတ် မရှိပါဘူး။ Default ဖြစ်တဲ့ 64 က သမိုင်းကြောင်းအရ လုံလောက်ကြောင်း သက်သေပြထားပေမယ့် — တစ်ခုတည်းသော transaction ထဲမှာ မတူညီတဲ့ table အများအပြားကို ထိတွေ့တဲ့ query တွေ ရှိရင် (ဥပမာ — child အများအပြားရှိတဲ့ parent table တစ်ခုကို query လုပ်ခြင်း) — ဒီတန်ဖိုးကို မြှင့်ရနိုင်ပါတယ်။ ဒီ parameter ကို server start လုပ်ချိန်မှာသာ သတ်မှတ်နိုင်ပါတယ်။
Standby server တစ်ခု run နေတဲ့အခါ — ဒီ parameter ကို primary server ပေါ်က တန်ဖိုးနှင့် တူညီရမယ် ဒါမှမဟုတ် ပိုမြင့်ရပါမယ်။ မဟုတ်ရင် — standby server မှာ query တွေကို ခွင့်ပြုမှာ မဟုတ်ပါဘူး။
- **max_pred_locks_per_transaction (integer)** — Shared predicate lock table မှာ server process ဒါမှမဟုတ် prepared transaction တစ်ခုချင်းစီအတွက် `max_pred_locks_per_transaction` object (ဥပမာ — table) အတွက် နေရာ ရှိပါတယ်; ဒါကြောင့် တစ်ကြိမ်လျှင် ဒီအရေအတွက်ထက် ပိုတဲ့ ထူးခြားတဲ့ object တွေကို lock လုပ်လို့ မရပါဘူး။ ဒီ parameter က transaction တစ်ခုချင်းစီ အသုံးပြုတဲ့ object lock အရေအတွက် ပျမ်းမျှကို ကန့်သတ်ပါတယ်; transaction အားလုံးရဲ့ lock တွေ lock table ထဲ ဝင်ဆံ့သရွေ့ — တစ်ခုချင်း transaction တွေက object တွေကို ပိုပြီး lock လုပ်နိုင်ပါတယ်။ ဒါက lock လုပ်နိုင်တဲ့ row အရေအတွက် *မဟုတ်* ပါဘူး; အဲဒီတန်ဖိုးက အကန့်အသတ် မရှိပါဘူး။ Default ဖြစ်တဲ့ 64 က သမိုင်းကြောင်းအရ လုံလောက်ကြောင်း သက်သေပြထားပေမယ့် — တစ်ခုတည်းသော serializable transaction ထဲမှာ မတူညီတဲ့ table အများအပြားကို ထိတွေ့တဲ့ client တွေ ရှိရင် — ဒီတန်ဖိုးကို မြှင့်ရနိုင်ပါတယ်။ ဒီ parameter ကို server start လုပ်ချိန်မှာသာ သတ်မှတ်နိုင်ပါတယ်။
- **max_pred_locks_per_relation (integer)** — Relation တစ်ခုတည်းရဲ့ page ဒါမှမဟုတ် tuple ဘယ်နှစ်ခုကို predicate-lock လုပ်နိုင်ပြီးနောက် — lock က relation တစ်ခုလုံးကို လွှမ်းခြုံတဲ့အထိ promote လုပ်ခံရမလဲ ဆိုတာကို ဒါက ထိန်းချုပ်ပါတယ်။ သုည ဒါမှမဟုတ် သုညထက် ကြီးတဲ့ တန်ဖိုးတွေက absolute limit တစ်ခုကို ဆိုလိုပြီး — အနုတ်တန်ဖိုးတွေက ဒီ setting ရဲ့ absolute တန်ဖိုးနဲ့ စားထားတဲ့ [max_pred_locks_per_transaction](/docs/postgresql/runtime-config-locks) ကို ဆိုလိုပါတယ်။ Default က -2 ဖြစ်ပြီး — PostgreSQL ရဲ့ ယခင် ဗားရှင်းများက အပြုအမူကို ထိန်းသိမ်းထားပါတယ်။ ဒီ parameter ကို `postgresql.conf` file ထဲမှာ ဒါမှမဟုတ် server command line ပေါ်မှာသာ သတ်မှတ်နိုင်ပါတယ်။
- **max_pred_locks_per_page (integer)** — Page တစ်ခုတည်းပေါ်က row ဘယ်နှစ်ခုကို predicate-lock လုပ်နိုင်ပြီးနောက် — lock က page တစ်ခုလုံးကို လွှမ်းခြုံတဲ့အထိ promote လုပ်ခံရမလဲ ဆိုတာကို ဒါက ထိန်းချုပ်ပါတယ်။ Default က 2 ဖြစ်ပါတယ်။ ဒီ parameter ကို `postgresql.conf` file ထဲမှာ ဒါမှမဟုတ် server command line ပေါ်မှာသာ သတ်မှတ်နိုင်ပါတယ်။
