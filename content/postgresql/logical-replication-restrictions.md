## 29.8. Restrictions (ကန့်သတ်ချက်များ)

Logical replication မှာ လက်ရှိ အောက်ပါ ကန့်သတ်ချက်တွေ ဒါမှမဟုတ် လိုအပ်နေသေးတဲ့ လုပ်ဆောင်ချက်တွေ ရှိပါတယ်။ ဒါတွေကို အနာဂတ် release တွေမှာ ဖြေရှင်းပေါင်းနိုင်ပါတယ်။

- Database schema နဲ့ DDL command တွေကို replicate မလုပ်ပါဘူး။ အစပိုင်း schema ကို `pg_dump --schema-only` နဲ့ ကိုယ်တိုင် copy လုပ်နိုင်ပါတယ်။ နောက်ဆက်တွဲ schema ပြောင်းလဲမှုတွေကိုတော့ ကိုယ်တိုင် ထပ်တူကျအောင် ထိန်းသိမ်းထားဖို့ လိုပါလိမ့်မယ်။ (ဒါပေမယ့် — နှစ်ဖက်စလုံးက schema တွေ လုံးဝ တူညီနေဖို့ မလိုအပ်ဘူးဆိုတာ သတိပြုပါ။) Live database တစ်ခုမှာ schema သတ်မှတ်ချက်တွေ ပြောင်းလဲတဲ့အခါ logical replication က ခိုင်မာပါတယ် — ဆိုလိုတာက — publisher မှာ schema ပြောင်းပြီး — replicated data တွေ subscriber ဆီ စရောက်လာချိန်မှာ table schema နဲ့ မကိုက်ညီရင် — schema ကို update လုပ်သည်အထိ replication က error ဖြစ်ပါလိမ့်မယ်။ အခြေအနေ အများအပြားမှာ — ထပ်ဖြည့်တဲ့ (additive) schema ပြောင်းလဲမှုတွေကို subscriber ဘက်မှာ အရင် လုပ်ဆောင်ခြင်းအားဖြင့် — ကြားဖြတ် error တွေကို ရှောင်ရှားနိုင်ပါတယ်။
- Sequence data ကို replicate မလုပ်ပါဘူး။ sequence တွေကို အခြေခံထားတဲ့ serial ဒါမှမဟုတ် identity column တွေထဲက data တွေကတော့ table ရဲ့ တစ်စိတ်တစ်ပိုင်းအနေနဲ့ replicate လုပ်ပါလိမ့်မယ် — ဒါပေမယ့် sequence ကိုယ်တိုင်ကတော့ subscriber မှာ start value ကို ပြသနေဆဲ ဖြစ်ပါလိမ့်မယ်။ Subscriber ကို read-only database အနေနဲ့ သုံးမယ်ဆိုရင် — ဒါက ပုံမှန်အားဖြင့် ပြဿနာ မဟုတ်သင့်ပါဘူး။ ဒါပေမယ့် — subscriber database ဆီ switchover ဒါမှမဟုတ် failover လုပ်ဖို့ ရည်ရွယ်ထားရင်တော့ — sequence တွေကို နောက်ဆုံး တန်ဖိုးတွေအထိ update လုပ်ဖို့ လိုပါလိမ့်မယ် — publisher ဆီက လက်ရှိ data ကို copy လုပ်ခြင်းဖြင့် (ဥပမာ `pg_dump` သုံးပြီး) ဒါမှမဟုတ် table တွေကနေ လုံလောက်တဲ့ မြင့်မားတဲ့ တန်ဖိုးတစ်ခုကို ဆုံးဖြတ်ခြင်းဖြင့်ပါ။
- `TRUNCATE` command တွေရဲ့ replication ကို support လုပ်ထားပေမယ့် — foreign key တွေနဲ့ ချိတ်ဆက်ထားတဲ့ table အုပ်စုတွေကို truncate လုပ်တဲ့အခါ သတိထားဖို့ လိုပါတယ်။ truncate action တစ်ခုကို replicate လုပ်တဲ့အခါ — subscriber က — publisher မှာ truncate လုပ်ခဲ့တဲ့ table အုပ်စုတူ (တိုက်ရိုက် သတ်မှတ်ထားတာ ဒါမှမဟုတ် `CASCADE` ကတစ်ဆင့် သွယ်ဝိုက် စုဆောင်းထားတာ) ကို — subscription ထဲ မပါဝင်တဲ့ table တွေ ခြွင်းချက်နဲ့ — truncate လုပ်ပါတယ်။ Affected table အားလုံး subscription တစ်ခုတည်းမှာ ပါဝင်ရင် ဒါက မှန်ကန်စွာ အလုပ်လုပ်ပါလိမ့်မယ်။ ဒါပေမယ့် — subscriber မှာ truncate လုပ်ရမယ့် table တချို့က — အဲဒီ subscription တစ်ခုတည်းမှာ (ဒါမှမဟုတ် မည်သည့် subscription မှာမှ) မပါဝင်တဲ့ table တွေနဲ့ foreign-key ချိတ်ဆက်မှု ရှိနေရင်တော့ — subscriber ဘက်မှာ truncate action ကို သက်ရောက်တာက ကျရှုံးပါလိမ့်မယ်။
- Large object တွေ (အခန်း 33 ကို ကြည့်ပါ) ကို replicate မလုပ်ပါဘူး။ ဒါအတွက် — data တွေကို သာမန် table တွေမှာ သိမ်းဆည်းတာကလွဲရင် — အခြား ဖြေရှင်းနည်း မရှိပါဘူး။
- Replication ကို partitioned table တွေ အပါအဝင် — table တွေကသာ support လုပ်ပါတယ်။ view, materialized view ဒါမှမဟုတ် foreign table ကဲ့သို့ အခြား relation အမျိုးအစားတွေကို replicate လုပ်ဖို့ ကြိုးစားရင် error ဖြစ်ပါလိမ့်မယ်။
- Partitioned table တွေကြား replicate လုပ်တဲ့အခါ — တကယ့် replication က default အားဖြင့် publisher ပေါ်က leaf partition တွေကနေ စတင် ဖြစ်ပေါ်တာကြောင့် — publisher ပေါ်က partition တွေက subscriber မှာလည်း တရားဝင် target table တွေအနေနဲ့ ရှိရပါမယ်။ (၎င်းတို့က leaf partition တွေ ဖြစ်နိုင်သလို — ထပ်မံ subpartition လုပ်ထားတာလည်း ဖြစ်နိုင်ပြီး — သီးခြား table တွေလည်း ဖြစ်နိုင်ပါတယ်။) Publication တွေက — ပြောင်းလဲမှုတွေ အမှန်တကယ် ဖြစ်ပေါ်တဲ့ leaf partition တစ်ခုချင်းစီရဲ့ identity နဲ့ schema အစား — partitioned root table ရဲ့ identity နဲ့ schema ကို သုံးပြီး ပြောင်းလဲမှုတွေကို replicate လုပ်ဖို့လည်း သတ်မှတ်နိုင်ပါတယ် (`CREATE PUBLICATION` ရဲ့ `publish_via_partition_root` parameter ကို ကြည့်ပါ)။
- ထုတ်ဝေထားတဲ့ table တွေမှာ `REPLICA IDENTITY FULL` ကို သုံးတဲ့အခါ — အရေးကြီးတဲ့ အချက်တစ်ခုက — table တွေမှာ `point` ဒါမှမဟုတ် `box` ကဲ့သို့သော — B-tree ဒါမှမဟုတ် Hash အတွက် default operator class မရှိတဲ့ datatype တွေနဲ့ attribute တွေ ပါဝင်နေရင် — `UPDATE` နဲ့ `DELETE` operation တွေကို subscriber တွေဆီ သက်ရောက်နိုင်မှာ မဟုတ်ပါဘူး။ ဒါပေမယ့် — table အတွက် primary key ဒါမှမဟုတ် replica identity သတ်မှတ်ထားကြောင်း သေချာစေခြင်းအားဖြင့် — ဒီ ကန့်သတ်ချက်ကို ကျော်လွှားနိုင်ပါတယ်။
