## 19.10. Vacuuming (vacuuming ပြုလုပ်ခြင်း)

- **19.10.1. Automatic Vacuuming (အလိုအလျောက် vacuuming လုပ်ခြင်း)**
- **19.10.2. Cost-based Vacuum Delay (ကုန်ကျစရိတ် အခြေခံ vacuum နှောင့်နှေးမှု)**
- **19.10.3. Default Behavior (default အပြုအမူ)**
- **19.10.4. Freezing (freeze လုပ်ခြင်း)**

ဒီ parameter တွေက vacuuming အပြုအမူကို ထိန်းချုပ်ပါတယ်။ Vacuum ရဲ့ ရည်ရွယ်ချက်နဲ့ တာဝန်တွေအကြောင်း ပိုမိုသိရှိဖို့ [အပိုင်း 24.1](/docs/postgresql/routine-vacuuming) ကို ကြည့်ပါ။

### 19.10.1. Automatic Vacuuming (အလိုအလျောက် vacuuming လုပ်ခြင်း)

ဒီ setting တွေက *autovacuum* feature ရဲ့ အပြုအမူကို ထိန်းချုပ်ပါတယ်။ ပိုမိုသိရှိဖို့ [အပိုင်း 24.1.6](/docs/postgresql/routine-vacuuming) ကို ကြည့်ပါ။ ဒီ setting အများအပြားကို table တစ်ခုချင်းစီအလိုက် override လုပ်နိုင်တယ်ဆိုတာ သတိပြုပါ; [Storage Parameters](/docs/postgresql/sql-createtable) ကို ကြည့်ပါ။

- **autovacuum (boolean)** — Server က autovacuum launcher daemon ကို run သင့်/မသင့် ထိန်းချုပ်ပါတယ်။ ဒါက default အားဖြင့် on ဖြစ်ပါတယ်; ဒါပေမယ့် autovacuum အလုပ်လုပ်ဖို့ track_counts ကိုလည်း enable လုပ်ထားရပါမယ်။ ဒီ parameter ကို postgresql.conf ဖိုင်ထဲမှာ ဒါမှမဟုတ် server command line မှာပဲ သတ်မှတ်နိုင်ပါတယ်; ဒါပေမယ့် table storage parameter တွေ ပြောင်းခြင်းဖြင့် table တစ်ခုချင်းစီအတွက် autovacuuming ကို disable လုပ်နိုင်ပါတယ်။
ဒီ parameter ကို disable လုပ်ထားရင်တောင် transaction ID wraparound ကာကွယ်ဖို့ လိုအပ်တဲ့အခါ system က autovacuum process တွေ launch လုပ်ပါလိမ့်မယ် ဆိုတာ သတိပြုပါ။ ပိုမိုသိရှိဖို့ [အပိုင်း 24.1.5](/docs/postgresql/routine-vacuuming) ကို ကြည့်ပါ။
- **autovacuum_worker_slots (integer)** — autovacuum worker process တွေအတွက် ခွဲဝေထားမယ့် backend slot အရေအတွက်ကို သတ်မှတ်ပါတယ်။ Default က ပုံမှန်အားဖြင့် slot 16 ခု ဖြစ်ပေမယ့် — သင့် kernel setting တွေက မထောက်ပံ့နိုင်ရင် (initdb လုပ်တဲ့အခါ ဆုံးဖြတ်သည့်အတိုင်း) ပိုနည်းနိုင်ပါတယ်။ ဒီ parameter ကို server start လုပ်ချိန်မှာပဲ သတ်မှတ်နိုင်ပါတယ်။
ဒီတန်ဖိုးကို ပြောင်းတဲ့အခါ autovacuum_max_workers ကိုလည်း ချိန်ညှိဖို့ စဉ်းစားပါ။
- **autovacuum_max_workers (integer)** — (autovacuum launcher မှလွဲ၍) တစ်ချိန်တည်းမှာ run နိုင်တဲ့ autovacuum process အများဆုံး အရေအတွက်ကို သတ်မှတ်ပါတယ်။ Default က 3 ဖြစ်ပါတယ်။ ဒီ parameter ကို postgresql.conf ဖိုင်ထဲမှာ ဒါမှမဟုတ် server command line မှာပဲ သတ်မှတ်နိုင်ပါတယ်။
ဒီတန်ဖိုးအတွက် autovacuum_worker_slots ထက် မြင့်တဲ့ setting တစ်ခုက အကျိုးသက်ရောက်မှု ရှိမှာ မဟုတ်ပါဘူး — အကြောင်းကတော့ autovacuum worker တွေကို အဲဒီ setting က သတ်မှတ်ထားတဲ့ slot အစုအဝေးထဲကနေ ယူတာကြောင့်ပါ။
- **autovacuum_naptime (integer)** — ပေးထားတဲ့ database တစ်ခုပေါ်မှာ autovacuum run တွေကြား အနည်းဆုံး နှောင့်နှေးချိန်ကို သတ်မှတ်ပါတယ်။ အလှည့်တစ်ခုချင်းစီမှာ daemon က database ကို စစ်ဆေးပြီး အဲဒီ database ထဲက table တွေအတွက် လိုအပ်သလို VACUUM နဲ့ ANALYZE command တွေ ထုတ်ပေးပါတယ်။ ဒီတန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် — seconds အနေနဲ့ ယူပါတယ်။ Default က တစ်မိနစ် (1min) ဖြစ်ပါတယ်။ ဒီ parameter ကို postgresql.conf ဖိုင်ထဲမှာ ဒါမှမဟုတ် server command line မှာပဲ သတ်မှတ်နိုင်ပါတယ်။
- **autovacuum_vacuum_threshold (integer)** — table တစ်ခုအတွင်း VACUUM တစ်ခု trigger လုပ်ဖို့ လိုအပ်တဲ့ update ဒါမှမဟုတ် delete လုပ်ထားတဲ့ tuple အနည်းဆုံး အရေအတွက်ကို သတ်မှတ်ပါတယ်။ Default က tuple 50 ဖြစ်ပါတယ်။ ဒီ parameter ကို postgresql.conf ဖိုင်ထဲမှာ ဒါမှမဟုတ် server command line မှာပဲ သတ်မှတ်နိုင်ပါတယ်; ဒါပေမယ့် table storage parameter တွေ ပြောင်းခြင်းဖြင့် table တစ်ခုချင်းစီအတွက် setting ကို override လုပ်နိုင်ပါတယ်။
- **autovacuum_vacuum_insert_threshold (integer)** — table တစ်ခုအတွင်း VACUUM တစ်ခု trigger လုပ်ဖို့ လိုအပ်တဲ့ insert လုပ်ထားတဲ့ tuple အရေအတွက်ကို သတ်မှတ်ပါတယ်။ Default က tuple 1000 ဖြစ်ပါတယ်။ -1 သတ်မှတ်ရင် — autovacuum က insert အရေအတွက်အပေါ် အခြေခံပြီး ဘယ် table ပေါ်မှာမှ VACUUM operation ကို trigger လုပ်မှာ မဟုတ်ပါဘူး။ ဒီ parameter ကို postgresql.conf ဖိုင်ထဲမှာ ဒါမှမဟုတ် server command line မှာပဲ သတ်မှတ်နိုင်ပါတယ်; ဒါပေမယ့် table storage parameter တွေ ပြောင်းခြင်းဖြင့် table တစ်ခုချင်းစီအတွက် setting ကို override လုပ်နိုင်ပါတယ်။
- **autovacuum_analyze_threshold (integer)** — table တစ်ခုအတွင်း ANALYZE တစ်ခု trigger လုပ်ဖို့ လိုအပ်တဲ့ insert၊ update ဒါမှမဟုတ် delete လုပ်ထားတဲ့ tuple အနည်းဆုံး အရေအတွက်ကို သတ်မှတ်ပါတယ်။ Default က tuple 50 ဖြစ်ပါတယ်။ ဒီ parameter ကို postgresql.conf ဖိုင်ထဲမှာ ဒါမှမဟုတ် server command line မှာပဲ သတ်မှတ်နိုင်ပါတယ်; ဒါပေမယ့် table storage parameter တွေ ပြောင်းခြင်းဖြင့် table တစ်ခုချင်းစီအတွက် setting ကို override လုပ်နိုင်ပါတယ်။
- **autovacuum_vacuum_scale_factor (floating point)** — VACUUM တစ်ခု trigger လုပ်မလား ဆုံးဖြတ်တဲ့အခါ autovacuum_vacuum_threshold ကို ပေါင်းထည့်ဖို့ table size ရဲ့ အပိုင်းအခြား (fraction) တစ်ခုကို သတ်မှတ်ပါတယ်။ Default က 0.2 (table size ရဲ့ 20%) ဖြစ်ပါတယ်။ ဒီ parameter ကို postgresql.conf ဖိုင်ထဲမှာ ဒါမှမဟုတ် server command line မှာပဲ သတ်မှတ်နိုင်ပါတယ်; ဒါပေမယ့် table storage parameter တွေ ပြောင်းခြင်းဖြင့် table တစ်ခုချင်းစီအတွက် setting ကို override လုပ်နိုင်ပါတယ်။
- **autovacuum_vacuum_insert_scale_factor (floating point)** — VACUUM တစ်ခု trigger လုပ်မလား ဆုံးဖြတ်တဲ့အခါ autovacuum_vacuum_insert_threshold ကို ပေါင်းထည့်ဖို့ table ထဲက unfrozen page တွေရဲ့ အပိုင်းအခြား (fraction) တစ်ခုကို သတ်မှတ်ပါတယ်။ Default က 0.2 (table ထဲက unfrozen page တွေရဲ့ 20%) ဖြစ်ပါတယ်။ ဒီ parameter ကို postgresql.conf ဖိုင်ထဲမှာ ဒါမှမဟုတ် server command line မှာပဲ သတ်မှတ်နိုင်ပါတယ်; ဒါပေမယ့် table storage parameter တွေ ပြောင်းခြင်းဖြင့် table တစ်ခုချင်းစီအတွက် setting ကို override လုပ်နိုင်ပါတယ်။
- **autovacuum_analyze_scale_factor (floating point)** — ANALYZE တစ်ခု trigger လုပ်မလား ဆုံးဖြတ်တဲ့အခါ autovacuum_analyze_threshold ကို ပေါင်းထည့်ဖို့ table size ရဲ့ အပိုင်းအခြား (fraction) တစ်ခုကို သတ်မှတ်ပါတယ်။ Default က 0.1 (table size ရဲ့ 10%) ဖြစ်ပါတယ်။ ဒီ parameter ကို postgresql.conf ဖိုင်ထဲမှာ ဒါမှမဟုတ် server command line မှာပဲ သတ်မှတ်နိုင်ပါတယ်; ဒါပေမယ့် table storage parameter တွေ ပြောင်းခြင်းဖြင့် table တစ်ခုချင်းစီအတွက် setting ကို override လုပ်နိုင်ပါတယ်။
- **autovacuum_vacuum_max_threshold (integer)** — table တစ်ခုအတွင်း VACUUM တစ်ခု trigger လုပ်ဖို့ လိုအပ်တဲ့ update ဒါမှမဟုတ် delete လုပ်ထားတဲ့ tuple အများဆုံး အရေအတွက်ကို သတ်မှတ်ပါတယ်; ဆိုလိုတာက autovacuum_vacuum_threshold နဲ့ autovacuum_vacuum_scale_factor တို့နဲ့ တွက်ချက်တဲ့ တန်ဖိုးအပေါ် ကန့်သတ်ချက် တစ်ခုပါ။ Default က tuple 100,000,000 ဖြစ်ပါတယ်။ -1 သတ်မှတ်ရင် — autovacuum က VACUUM operation ကို trigger လုပ်မယ့် update ဒါမှမဟုတ် delete လုပ်ထားတဲ့ tuple အများဆုံး အရေအတွက်ကို ချမှတ်မှာ မဟုတ်ပါဘူး။ ဒီ parameter ကို postgresql.conf ဖိုင်ထဲမှာ ဒါမှမဟုတ် server command line မှာပဲ သတ်မှတ်နိုင်ပါတယ်; ဒါပေမယ့် storage parameter တွေ ပြောင်းခြင်းဖြင့် table တစ်ခုချင်းစီအတွက် setting ကို override လုပ်နိုင်ပါတယ်။
- **autovacuum_freeze_max_age (integer)** — table တစ်ခုအတွင်း transaction ID wraparound ကာကွယ်ဖို့ VACUUM operation တစ်ခုကို အတင်းအကျပ် (force) လုပ်ခင် — table ရဲ့ pg_class.relfrozenxid field က ရောက်ရှိနိုင်တဲ့ အများဆုံး အသက် (transaction အရေအတွက်) ကို သတ်မှတ်ပါတယ်။ autovacuum ကို အခြားနည်းနဲ့ disable လုပ်ထားရင်တောင် wraparound ကာကွယ်ဖို့ system က autovacuum process တွေ launch လုပ်ပါလိမ့်မယ် ဆိုတာ သတိပြုပါ။
Vacuum က pg_xact subdirectory ထဲက file ဟောင်းတွေကို ဖယ်ရှားခွင့်လည်း ပေးတာကြောင့် — default က transaction သန်း 200 ဆိုတဲ့ အတော်နည်းတဲ့ တန်ဖိုး ဖြစ်ပါတယ်။ ဒီ parameter ကို server start လုပ်ချိန်မှာပဲ သတ်မှတ်နိုင်ပေမယ့် — table storage parameter တွေ ပြောင်းခြင်းဖြင့် table တစ်ခုချင်းစီအတွက် setting ကို လျှော့နိုင်ပါတယ်။ ပိုမိုသိရှိဖို့ [အပိုင်း 24.1.5](/docs/postgresql/routine-vacuuming) ကို ကြည့်ပါ။
- **autovacuum_multixact_freeze_max_age (integer)** — table တစ်ခုအတွင်း multixact ID wraparound ကာကွယ်ဖို့ VACUUM operation တစ်ခုကို အတင်းအကျပ် (force) လုပ်ခင် — table ရဲ့ pg_class.relminmxid field က ရောက်ရှိနိုင်တဲ့ အများဆုံး အသက် (multixact အရေအတွက်) ကို သတ်မှတ်ပါတယ်။ autovacuum ကို အခြားနည်းနဲ့ disable လုပ်ထားရင်တောင် wraparound ကာကွယ်ဖို့ system က autovacuum process တွေ launch လုပ်ပါလိမ့်မယ် ဆိုတာ သတိပြုပါ။
Multixact တွေကို vacuuming လုပ်ခြင်းက pg_multixact/members နဲ့ pg_multixact/offsets subdirectory တွေထဲက file ဟောင်းတွေကို ဖယ်ရှားခွင့်လည်း ပေးတာကြောင့် — default က multixact သန်း 400 ဆိုတဲ့ အတော်နည်းတဲ့ တန်ဖိုး ဖြစ်ပါတယ်။ ဒီ parameter ကို server start လုပ်ချိန်မှာပဲ သတ်မှတ်နိုင်ပေမယ့် — table storage parameter တွေ ပြောင်းခြင်းဖြင့် table တစ်ခုချင်းစီအတွက် setting ကို လျှော့နိုင်ပါတယ်။ ပိုမိုသိရှိဖို့ [အပိုင်း 24.1.5.1](/docs/postgresql/routine-vacuuming) ကို ကြည့်ပါ။
- **autovacuum_vacuum_cost_delay (floating point)** — အလိုအလျောက် VACUUM operation တွေမှာ သုံးမယ့် cost delay တန်ဖိုးကို သတ်မှတ်ပါတယ်။ -1 သတ်မှတ်ရင် — ပုံမှန် vacuum_cost_delay တန်ဖိုးကို သုံးပါလိမ့်မယ်။ ဒီတန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် — milliseconds အနေနဲ့ ယူပါတယ်။ Default တန်ဖိုးက 2 milliseconds ဖြစ်ပါတယ်။ ဒီ parameter ကို postgresql.conf ဖိုင်ထဲမှာ ဒါမှမဟုတ် server command line မှာပဲ သတ်မှတ်နိုင်ပါတယ်; ဒါပေမယ့် table storage parameter တွေ ပြောင်းခြင်းဖြင့် table တစ်ခုချင်းစီအတွက် setting ကို override လုပ်နိုင်ပါတယ်။
- **autovacuum_vacuum_cost_limit (integer)** — အလိုအလျောက် VACUUM operation တွေမှာ သုံးမယ့် cost limit တန်ဖိုးကို သတ်မှတ်ပါတယ်။ -1 သတ်မှတ်ရင် (ဒါက default ဖြစ်ပါတယ်) — ပုံမှန် vacuum_cost_limit တန်ဖိုးကို သုံးပါလိမ့်မယ်။ တစ်ခုထက်ပိုရှိရင် — run နေတဲ့ autovacuum worker တွေအကြား ဒီတန်ဖိုးကို အချိုးကျ ခွဲဝေပေးတာကြောင့် — worker တစ်ခုချင်းစီအတွက် limit တွေရဲ့ ပေါင်းလဒ်က ဒီ variable ရဲ့ တန်ဖိုးကို မကျော်လွန်စေဘူးဆိုတာ သတိပြုပါ။ ဒီ parameter ကို postgresql.conf ဖိုင်ထဲမှာ ဒါမှမဟုတ် server command line မှာပဲ သတ်မှတ်နိုင်ပါတယ်; ဒါပေမယ့် table storage parameter တွေ ပြောင်းခြင်းဖြင့် table တစ်ခုချင်းစီအတွက် setting ကို override လုပ်နိုင်ပါတယ်။

### 19.10.2. Cost-based Vacuum Delay (ကုန်ကျစရိတ် အခြေခံ vacuum နှောင့်နှေးမှု)

[VACUUM](/docs/postgresql/sql-vacuum) နဲ့ [ANALYZE](/docs/postgresql/sql-analyze) command တွေ execute လုပ်နေစဉ်အတွင်း — system က လုပ်ဆောင်တဲ့ I/O operation အမျိုးမျိုးရဲ့ ခန့်မှန်း ကုန်ကျစရိတ်ကို ခြေရာခံတဲ့ internal counter တစ်ခုကို ထိန်းသိမ်းထားပါတယ်။ စုဆောင်းရရှိတဲ့ ကုန်ကျစရိတ်က (`vacuum_cost_limit` က သတ်မှတ်တဲ့) limit တစ်ခုကို ရောက်ရှိတဲ့အခါ — operation လုပ်ဆောင်နေတဲ့ process က `vacuum_cost_delay` က သတ်မှတ်တဲ့အတိုင်း အချိန်တိုလေး တစ်ခု sleep လုပ်ပါတယ်။ ပြီးရင် counter ကို reset လုပ်ပြီး execute လုပ်ခြင်းကို ဆက်လုပ်ပါတယ်။

ဒီ feature ရဲ့ ရည်ရွယ်ချက်က — တစ်ပြိုင်နက် ဖြစ်ပေါ်နေတဲ့ database လုပ်ဆောင်ချက်တွေအပေါ် ဒီ command တွေရဲ့ I/O သက်ရောက်မှုကို လျှော့ချနိုင်ဖို့ administrator တွေကို ခွင့်ပြုပေးဖို့ ဖြစ်ပါတယ်။ `VACUUM` နဲ့ `ANALYZE` ကဲ့သို့ maintenance command တွေ မြန်မြန် ပြီးဆုံးဖို့ အရေးမပါတဲ့ အခြေအနေ အများအပြား ရှိပါတယ်; ဒါပေမယ့် — ဒီ command တွေက system ရဲ့ အခြား database operation တွေ လုပ်ဆောင်နိုင်စွမ်းကို သိသိသာသာ နှောင့်ယှက်မှု မဖြစ်စေဖို့ကတော့ များသောအားဖြင့် အလွန် အရေးပါပါတယ်။ Cost-based vacuum delay က administrator တွေ ဒါကို အောင်မြင်စေဖို့ နည်းလမ်း တစ်ခု ပေးပါတယ်။

ဒီ feature က ကိုယ်တိုင် ထုတ်ပေးတဲ့ `VACUUM` command တွေအတွက် default အားဖြင့် disable ဖြစ်ပါတယ်။ ဒါကို enable လုပ်ဖို့ — `vacuum_cost_delay` variable ကို သုညမဟုတ်တဲ့ တန်ဖိုး သတ်မှတ်ပါ။

- **vacuum_cost_delay (floating point)** — cost limit ကျော်လွန်သွားတဲ့အခါ process sleep လုပ်မယ့် အချိန်ပမာဏ ဖြစ်ပါတယ်။ ဒီတန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် — milliseconds အနေနဲ့ ယူပါတယ်။ Default တန်ဖိုးက 0 ဖြစ်ပြီး — cost-based vacuum delay feature ကို disable လုပ်ပါတယ်။ အပေါင်းလက္ခဏာ တန်ဖိုးတွေက cost-based vacuuming ကို enable လုပ်ပါတယ်။
Cost-based vacuuming သုံးတဲ့အခါ — vacuum_cost_delay အတွက် သင့်လျော်တဲ့ တန်ဖိုးတွေက ပုံမှန်အားဖြင့် အတော်သေးငယ်ပြီး — 1 millisecond အောက် ဖြစ်နိုင်ပါတယ်။ vacuum_cost_delay ကို millisecond အပိုင်းအစ တန်ဖိုးတွေ သတ်မှတ်နိုင်ပေမယ့် — အဟောင်း platform တွေမှာ ဒီလို delay တွေကို တိကျစွာ တိုင်းတာနိုင်ခြင်း မရှိနိုင်ပါဘူး။ ဒီလို platform တွေမှာ 1ms မှာ ရရှိတာထက် ကျော်လွန်ပြီး VACUUM ရဲ့ throttle လုပ်ထားတဲ့ resource အသုံးပြုမှုကို တိုးချင်ရင် — အခြား vacuum cost parameter တွေကို ပြောင်းရပါလိမ့်မယ်။ ဒါပေမယ့် — သင့် platform က စဉ်ဆက်မပြတ် တိုင်းတာနိုင်သလောက် vacuum_cost_delay ကို သေးငယ်အောင် ထားသင့်ပါတယ်; ကြီးမားတဲ့ delay တွေက အထောက်အကူ မဖြစ်ပါဘူး။
- **vacuum_cost_page_hit (integer)** — shared buffer cache ထဲမှာ တွေ့တဲ့ buffer တစ်ခုကို vacuuming လုပ်ရာမှာ ခန့်မှန်း ကုန်ကျစရိတ် ဖြစ်ပါတယ်။ ဒါက buffer pool ကို lock လုပ်ခြင်း၊ shared hash table ကို lookup လုပ်ခြင်းနဲ့ page ရဲ့ အကြောင်းအရာကို scan လုပ်ခြင်းအတွက် ကုန်ကျစရိတ်ကို ကိုယ်စားပြုပါတယ်။ Default တန်ဖိုးက 1 ဖြစ်ပါတယ်။
- **vacuum_cost_page_miss (integer)** — disk ကနေ ဖတ်ရမယ့် buffer တစ်ခုကို vacuuming လုပ်ရာမှာ ခန့်မှန်း ကုန်ကျစရိတ် ဖြစ်ပါတယ်။ ဒါက buffer pool ကို lock လုပ်ခြင်း၊ shared hash table ကို lookup လုပ်ခြင်း၊ လိုချင်တဲ့ block ကို disk ကနေ ဖတ်သွင်းခြင်းနဲ့ သူ့အကြောင်းအရာကို scan လုပ်ခြင်းအတွက် အားထုတ်မှုကို ကိုယ်စားပြုပါတယ်။ Default တန်ဖိုးက 2 ဖြစ်ပါတယ်။
- **vacuum_cost_page_dirty (integer)** — vacuum က အရင် သန့်ရှင်းနေတဲ့ block တစ်ခုကို ပြင်ဆင်တဲ့အခါ ကောက်ခံတဲ့ ခန့်မှန်း ကုန်ကျစရိတ် ဖြစ်ပါတယ်။ ဒါက dirty block ကို disk ဆီ ပြန်ရေးသွင်းဖို့ လိုအပ်တဲ့ အပို I/O ကို ကိုယ်စားပြုပါတယ်။ Default တန်ဖိုးက 20 ဖြစ်ပါတယ်။
- **vacuum_cost_limit (integer)** — ဒါက vacuuming process ကို vacuum_cost_delay အချိန်ကြာ sleep ဖြစ်စေမယ့် စုဆောင်း ကုန်ကျစရိတ် ဖြစ်ပါတယ်။ Default က 200 ဖြစ်ပါတယ်။

> **မှတ်ချက်:** အလွန် အရေးကြီးတဲ့ lock တွေကို ကိုင်ထားပြီး အတတ်နိုင်ဆုံး မြန်မြန် ပြီးဆုံးသင့်တဲ့ operation တချို့ ရှိပါတယ်။ ဒီလို operation တွေအတွင်းမှာ cost-based vacuum delay များ ဖြစ်ပေါ်တာ မရှိပါဘူး။ ဒါကြောင့် — ကုန်ကျစရိတ်က သတ်မှတ်ထားတဲ့ limit ထက် အများကြီး ပိုမြင့်နိုင်ပါတယ်။ ဒီလို အခြေအနေတွေမှာ အသုံးမဝင်တဲ့ ရှည်လျားတဲ့ delay တွေ မဖြစ်စေဖို့ — အမှန်တကယ် delay ကို `vacuum_cost_delay` * `accumulated_balance` / `vacuum_cost_limit` အဖြစ် တွက်ချက်ပြီး — အများဆုံး `vacuum_cost_delay` * 4 အထိ ဖြစ်ပါတယ်။

### 19.10.3. Default Behavior (default အပြုအမူ)

- **vacuum_truncate (boolean)** — table ရဲ့ အဆုံးမှာ ရှိတဲ့ empty page တွေကို truncate လုပ်ဖို့ ကြိုးစားခြင်းကို vacuum အတွက် enable ဒါမှမဟုတ် disable လုပ်ပါတယ်။ Default တန်ဖိုးက true ဖြစ်ပါတယ်။ true ဖြစ်ရင် — VACUUM နဲ့ autovacuum က truncation ကို လုပ်ပြီး truncate လုပ်လိုက်တဲ့ page တွေအတွက် disk space ကို operating system ဆီ ပြန်ပေးပါတယ်။ truncation အတွက် table ပေါ်မှာ ACCESS EXCLUSIVE lock လိုအပ်တယ်ဆိုတာ သတိပြုပါ။ VACUUM ရဲ့ TRUNCATE parameter ကို သတ်မှတ်ထားရင် — ဒီ parameter ရဲ့ တန်ဖိုးကို override လုပ်ပါတယ်။ Setting ကို table storage parameter တွေ ပြောင်းခြင်းဖြင့်လည်း table တစ်ခုချင်းစီအတွက် override လုပ်နိုင်ပါတယ်။

### 19.10.4. Freezing (freeze လုပ်ခြင်း)

Transaction ID တွေ wrap around ဖြစ်သွားပြီးတဲ့နောက်မှာတောင် မှန်ကန်မှု ရှိစေဖို့ — PostgreSQL က လုံလောက်အောင် အိုမင်းနေပြီဖြစ်တဲ့ row တွေကို frozen အဖြစ် မှတ်သားပါတယ်။ ဒီ row တွေက လူတိုင်း မြင်နိုင်ပါတယ်; အခြား transaction တွေက visibility ကို ဆုံးဖြတ်ဖို့ သူတို့ insert လုပ်တဲ့ XID ကို စစ်ဆေးဖို့ မလိုပါဘူး။ `VACUUM` က row တွေကို frozen အဖြစ် မှတ်သားဖို့ တာဝန်ရှိပါတယ်။ အောက်ပါ setting တွေက `VACUUM` ရဲ့ freezing အပြုအမူကို ထိန်းချုပ်ပြီး — system ရဲ့ XID သုံးစွဲမှုနှုန်းနဲ့ အဓိက workload တွေရဲ့ data access pattern တွေအပေါ် အခြေခံပြီး ချိန်ညှိသင့်ပါတယ်။ Transaction ID wraparound နဲ့ ဒီ parameter တွေ ချိန်ညှိခြင်းအကြောင်း ပိုမိုသိရှိဖို့ [အပိုင်း 24.1.5](/docs/postgresql/routine-vacuuming) ကို ကြည့်ပါ။

- **vacuum_freeze_table_age (integer)** — table ရဲ့ pg_class.relfrozenxid field က ဒီ setting က သတ်မှတ်တဲ့ အသက်အထိ ရောက်ရှိရင် — VACUUM က aggressive scan တစ်ခုကို လုပ်ဆောင်ပါတယ်။ Aggressive scan က ပုံမှန် VACUUM နဲ့ ကွာခြားချက်က — dead tuple တွေ ပါနိုင်တဲ့ page တွေကိုပဲ မဟုတ်ဘဲ — unfrozen XID ဒါမှမဟုတ် MXID တွေ ပါနိုင်တဲ့ page တိုင်းကို လည်ပတ်စစ်ဆေးတာပါ။ Default က transaction သန်း 150 ဖြစ်ပါတယ်။ User တွေက ဒီတန်ဖိုးကို သုညကနေ ဘီလီယံ နှစ်ထောင် အထိ သတ်မှတ်နိုင်ပေမယ့် — table အတွက် anti-wraparound autovacuum တစ်ခု launch လုပ်ခင် periodic manual VACUUM တစ်ခု run ဖို့ အခွင့်အလမ်း ရှိစေဖို့ — VACUUM က effective တန်ဖိုးကို autovacuum_freeze_max_age ရဲ့ 95% အထိ တိတ်ဆိတ်စွာ ကန့်သတ်ပါတယ်။ ပိုမိုသိရှိဖို့ [အပိုင်း 24.1.5](/docs/postgresql/routine-vacuuming) ကို ကြည့်ပါ။
- **vacuum_freeze_min_age (integer)** — ပိုဟောင်းတဲ့ XID ရှိတဲ့ page တွေကို freeze လုပ်သင့်/မသင့် ဆုံးဖြတ်ဖို့ VACUUM သုံးသင့်တဲ့ cutoff အသက် (transaction အရေအတွက်) ကို သတ်မှတ်ပါတယ်။ Default က transaction သန်း 50 ဖြစ်ပါတယ်။ User တွေက ဒီတန်ဖိုးကို သုညကနေ ဘီလီယံ တစ်ထောင် အထိ သတ်မှတ်နိုင်ပေမယ့် — forced autovacuum တွေကြားမှာ မဆီလျော်လောက်အောင် တိုတောင်းတဲ့ အချိန် မဖြစ်စေဖို့ — VACUUM က effective တန်ဖိုးကို autovacuum_freeze_max_age ရဲ့ တစ်ဝက် အထိ တိတ်ဆိတ်စွာ ကန့်သတ်ပါတယ်။ ပိုမိုသိရှိဖို့ [အပိုင်း 24.1.5](/docs/postgresql/routine-vacuuming) ကို ကြည့်ပါ။
- **vacuum_failsafe_age (integer)** — system တစ်ခုလုံး transaction ID wraparound failure မဖြစ်စေဖို့ VACUUM က ထူးကဲတဲ့ အစီအမံတွေ လုပ်ဆောင်ခင် — table ရဲ့ pg_class.relfrozenxid field က ရောက်ရှိနိုင်တဲ့ အများဆုံး အသက် (transaction အရေအတွက်) ကို သတ်မှတ်ပါတယ်။ ဒါက VACUUM ရဲ့ နောက်ဆုံး အားထားရာ မဟာဗျူဟာ ဖြစ်ပါတယ်။ Failsafe က ပုံမှန်အားဖြင့် — transaction ID wraparound ကာကွယ်ဖို့ autovacuum တစ်ခုက အချိန်အတော်ကြာ run နေပြီးချိန်မှာ trigger ဖြစ်တတ်ပေမယ့် — VACUUM မည်သည့်အချိန်မှာမဆို failsafe trigger ဖြစ်နိုင်ပါတယ်။
Failsafe trigger ဖြစ်တဲ့အခါ — သက်ရောက်နေတဲ့ cost-based delay များကို ဆက်လက် မသုံးတော့ဘဲ၊ နောက်ထပ် မရှိမဖြစ်မဟုတ်တဲ့ maintenance task တွေ (ဥပမာ index vacuuming) ကို ကျော်လွှားပြီး၊ အသုံးပြုနေတဲ့ Buffer Access Strategy မည်သည်ကိုမဆို disable လုပ်လိုက်တာကြောင့် — VACUUM က shared buffer အားလုံးကို လွတ်လပ်စွာ အသုံးပြုနိုင်ပါတယ်။
Default က transaction 1.6 ဘီလီယံ ဖြစ်ပါတယ်။ User တွေက ဒီတန်ဖိုးကို သုညကနေ 2.1 ဘီလီယံ အထိ သတ်မှတ်နိုင်ပေမယ့် — VACUUM က effective တန်ဖိုးကို autovacuum_freeze_max_age ရဲ့ 105% ထက် မနည်းအောင် တိတ်ဆိတ်စွာ ချိန်ညှိပါတယ်။
- **vacuum_multixact_freeze_table_age (integer)** — table ရဲ့ pg_class.relminmxid field က ဒီ setting က သတ်မှတ်တဲ့ အသက်အထိ ရောက်ရှိရင် — VACUUM က aggressive scan တစ်ခုကို လုပ်ဆောင်ပါတယ်။ Aggressive scan က ပုံမှန် VACUUM နဲ့ ကွာခြားချက်က — dead tuple တွေ ပါနိုင်တဲ့ page တွေကိုပဲ မဟုတ်ဘဲ — unfrozen XID ဒါမှမဟုတ် MXID တွေ ပါနိုင်တဲ့ page တိုင်းကို လည်ပတ်စစ်ဆေးတာပါ။ Default က multixact သန်း 150 ဖြစ်ပါတယ်။ User တွေက ဒီတန်ဖိုးကို သုညကနေ ဘီလီယံ နှစ်ထောင် အထိ သတ်မှတ်နိုင်ပေမယ့် — table အတွက် anti-wraparound တစ်ခု launch လုပ်ခင် periodic manual VACUUM တစ်ခု run ဖို့ အခွင့်အလမ်း ရှိစေဖို့ — VACUUM က effective တန်ဖိုးကို autovacuum_multixact_freeze_max_age ရဲ့ 95% အထိ တိတ်ဆိတ်စွာ ကန့်သတ်ပါတယ်။ ပိုမိုသိရှိဖို့ [အပိုင်း 24.1.5.1](/docs/postgresql/routine-vacuuming) ကို ကြည့်ပါ။
- **vacuum_multixact_freeze_min_age (integer)** — ပိုဟောင်းတဲ့ multixact ID ရှိတဲ့ page တွေကို freeze လုပ်သင့်/မသင့် ဆုံးဖြတ်ဖို့ VACUUM သုံးသင့်တဲ့ cutoff အသက် (multixact အရေအတွက်) ကို သတ်မှတ်ပါတယ်။ Default က multixact သန်း 5 ဖြစ်ပါတယ်။ User တွေက ဒီတန်ဖိုးကို သုညကနေ ဘီလီယံ တစ်ထောင် အထိ သတ်မှတ်နိုင်ပေမယ့် — forced autovacuum တွေကြားမှာ မဆီလျော်လောက်အောင် တိုတောင်းတဲ့ အချိန် မဖြစ်စေဖို့ — VACUUM က effective တန်ဖိုးကို autovacuum_multixact_freeze_max_age ရဲ့ တစ်ဝက် အထိ တိတ်ဆိတ်စွာ ကန့်သတ်ပါတယ်။ ပိုမိုသိရှိဖို့ [အပိုင်း 24.1.5.1](/docs/postgresql/routine-vacuuming) ကို ကြည့်ပါ။
- **vacuum_multixact_failsafe_age (integer)** — system တစ်ခုလုံး multixact ID wraparound failure မဖြစ်စေဖို့ VACUUM က ထူးကဲတဲ့ အစီအမံတွေ လုပ်ဆောင်ခင် — table ရဲ့ pg_class.relminmxid field က ရောက်ရှိနိုင်တဲ့ အများဆုံး အသက် (multixact အရေအတွက်) ကို သတ်မှတ်ပါတယ်။ ဒါက VACUUM ရဲ့ နောက်ဆုံး အားထားရာ မဟာဗျူဟာ ဖြစ်ပါတယ်။ Failsafe က ပုံမှန်အားဖြင့် — transaction ID wraparound ကာကွယ်ဖို့ autovacuum တစ်ခုက အချိန်အတော်ကြာ run နေပြီးချိန်မှာ trigger ဖြစ်တတ်ပေမယ့် — VACUUM မည်သည့်အချိန်မှာမဆို failsafe trigger ဖြစ်နိုင်ပါတယ်။
Failsafe trigger ဖြစ်တဲ့အခါ — သက်ရောက်နေတဲ့ cost-based delay များကို ဆက်လက် မသုံးတော့ဘဲ၊ နောက်ထပ် မရှိမဖြစ်မဟုတ်တဲ့ maintenance task တွေ (ဥပမာ index vacuuming) ကို ကျော်လွှားပါတယ်။
Default က multixact 1.6 ဘီလီယံ ဖြစ်ပါတယ်။ User တွေက ဒီတန်ဖိုးကို သုညကနေ 2.1 ဘီလီယံ အထိ သတ်မှတ်နိုင်ပေမယ့် — VACUUM က effective တန်ဖိုးကို autovacuum_multixact_freeze_max_age ရဲ့ 105% ထက် မနည်းအောင် တိတ်ဆိတ်စွာ ချိန်ညှိပါတယ်။
- **vacuum_max_eager_freeze_failure_rate (floating point)** — eager scanning ကို disable လုပ်ခင် — VACUUM က scan လုပ်ပြီး visibility map ထဲမှာ all-frozen အဖြစ် သတ်မှတ်ဖို့ မအောင်မြင်နိုင်တဲ့ page အများဆုံး အရေအတွက်ကို (relation ထဲက စုစုပေါင်း page တွေရဲ့ အပိုင်းအခြား အဖြစ်) သတ်မှတ်ပါတယ်။ 0 တန်ဖိုးက eager scanning ကို လုံးလုံး disable လုပ်ပါတယ်။ Default က 0.03 (3%) ဖြစ်ပါတယ်။
Eager scanning enable ဖြစ်နေတဲ့အခါ — အောင်မြင်တဲ့ freezing တွေ မဟုတ်ဘဲ freeze failure တွေကပဲ cap အတွက် အရေးပါတယ်ဆိုတာ သတိပြုပါ။ အောင်မြင်တဲ့ page freeze တွေကို relation ထဲက all-visible ဖြစ်ပေမယ့် all-frozen မဟုတ်တဲ့ page တွေရဲ့ 20% အထိ internal အနေနဲ့ ကန့်သတ်ထားပါတယ်။ အောင်မြင်တဲ့ page freeze တွေကို ကန့်သတ်ခြင်းက — overhead ကို ပုံမှန် vacuum အများအပြားအပေါ် ဖြန့်ခွဲပေးဖို့ အထောက်အကူဖြစ်ပြီး — နောက် aggressive vacuum မတိုင်မီ ပြန်ပြင်ဆင်ခံရတဲ့ page တွေကို အလဟဿ eager freeze လုပ်မိတာရဲ့ ဖြစ်နိုင်တဲ့ ဆိုးကျိုးကို ကန့်သတ်ပေးပါတယ်။
ဒီ parameter ကို postgresql.conf ဖိုင်ထဲမှာ ဒါမှမဟုတ် server command line မှာပဲ သတ်မှတ်နိုင်ပါတယ်; ဒါပေမယ့် သက်ဆိုင်ရာ table storage parameter ကို ပြောင်းခြင်းဖြင့် table တစ်ခုချင်းစီအတွက် setting ကို override လုပ်နိုင်ပါတယ်။ Vacuum ရဲ့ freezing အပြုအမူ ချိန်ညှိခြင်းအကြောင်း ပိုမိုသိရှိဖို့ [အပိုင်း 24.1.5](/docs/postgresql/routine-vacuuming) ကို ကြည့်ပါ။
