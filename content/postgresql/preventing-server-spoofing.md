## 18.7. Preventing Server Spoofing (server spoofing ကို ကာကွယ်ခြင်း)

Server run နေတဲ့ အချိန်မှာတော့ — ဆိုးရွားတဲ့ ရည်ရွယ်ချက် ရှိသူ (malicious user) တစ်ယောက်က ပုံမှန် database server ရဲ့ နေရာကို ယူလို့ မရနိုင်ပါဘူး။ ဒါပေမယ့် — server ရပ်နေတဲ့ အချိန်မှာတော့ — local user တစ်ယောက်က သူ့ကိုယ်ပိုင် server တစ်ခုကို စတင်ခြင်းအားဖြင့် — ပုံမှန် server ကို spoof လုပ်ဖို့ (အစစ်အမှန် server အဖြစ် အတု ဟန်ဆောင်ဖို့) ဖြစ်နိုင်ပါတယ်။ Spoof server က clients တွေ ပို့လိုက်တဲ့ passwords တွေနဲ့ queries တွေကို ဖတ်နိုင်ပေမယ့် — `PGDATA` directory က directory permissions တွေကြောင့် လုံခြုံနေဆဲ ဖြစ်လို့ — ဘယ် data ကိုမှ ပြန်ပေးနိုင်မှာ မဟုတ်ပါဘူး။ ဘယ်သူမဆို database server တစ်ခုကို စတင်နိုင်လို့ spoofing လုပ်လို့ ရတာပါ; client တစ်ယောက်က — အထူး configure လုပ်ထားခြင်း မရှိဘူးဆိုရင် — invalid (မမှန်ကန်သော) server တစ်ခုကို ခွဲခြား သိရှိနိုင်မှာ မဟုတ်ပါဘူး။

`local` connections တွေရဲ့ spoofing ကို ကာကွယ်ဖို့ နည်းလမ်း တစ်ခုကတော့ — ယုံကြည်ရတဲ့ local user တစ်ယောက်တည်းအတွက်ပဲ write permission (ရေးသားခွင့်) ရှိတဲ့ — Unix domain socket directory တစ်ခုကို ([unix_socket_directories](https://www.postgresql.org/docs/current/runtime-config-connection.html#GUC-UNIX-SOCKET-DIRECTORIES)) သုံးတာပဲ ဖြစ်ပါတယ်။ ဒါက malicious user တစ်ယောက်က အဲဒီ directory ထဲမှာ သူ့ကိုယ်ပိုင် socket ဖိုင် ဖန်တီးခြင်းကနေ ကာကွယ်ပေးပါတယ်။ Application တချို့က socket ဖိုင်အတွက် `/tmp` ကိုပဲ ရည်ညွှန်းနေပြီး — spoofing ဒဏ်ကို ခံနိုင်ရည် အားနည်းနေမှာကို စိုးရိမ်တယ်ဆိုရင် — operating system startup လုပ်ချိန်မှာ — ရွှေ့ပြောင်းထားတဲ့ socket ဖိုင်ကို ညွှန်ပြတဲ့ — `/tmp/.s.PGSQL.5432` ဆိုတဲ့ symbolic link (သင်္ကေတ ချိတ်ဆက်မှု) တစ်ခုကို ဖန်တီးပါ။ Symbolic link ကို ဖယ်ရှားမခံရအောင် — သင့် `/tmp` cleanup script (ရှင်းလင်းရေး script) ကိုလည်း ပြုပြင် မွမ်းမံဖို့ လိုနိုင်ပါတယ်။

`local` connections တွေအတွက် နောက်ထပ် option တစ်ခုကတော့ — clients တွေက — socket နဲ့ ချိတ်ဆက်ထားတဲ့ server process ရဲ့ လိုအပ်တဲ့ ပိုင်ရှင် (owner) ကို သတ်မှတ်ဖို့ [`requirepeer`](https://www.postgresql.org/docs/current/libpq-connect.html#LIBPQ-CONNECT-REQUIREPEER) ကို သုံးတာပဲ ဖြစ်ပါတယ်။

TCP connections တွေပေါ်မှာ spoofing ကာကွယ်ဖို့ဆိုရင် — SSL certificates တွေကို သုံးပြီး — clients တွေက server ရဲ့ certificate ကို စစ်ဆေးအောင် သေချာ လုပ်ပါ — ဒါမှမဟုတ် — GSSAPI encryption (ကုဒ်ဝှက်စနစ်) ကို သုံးပါ (ဒါမှမဟုတ် — သီးခြား connections တွေပေါ်မှာဆိုရင် — နှစ်ခုလုံး သုံးနိုင်ပါတယ်)။

SSL နဲ့ spoofing ကာကွယ်ဖို့ဆိုရင် — server က `hostssl` connections တွေကိုပဲ လက်ခံဖို့ ([အပိုင်း 20.1](/docs/postgresql/auth-pg-hba-conf)) နဲ့ — SSL key နဲ့ certificate ဖိုင်တွေ ([အပိုင်း 18.9](/docs/postgresql/ssl-tcp)) ရှိဖို့ configure လုပ်ထားရပါမယ်။ TCP client က `sslmode=verify-ca` ဒါမှမဟုတ် `verify-full` သုံးပြီး connect လုပ်ရမယ့်အပြင် — သင့်လျော်တဲ့ root certificate ဖိုင်ကိုလည်း တပ်ဆင်ထားရပါမယ် ([အပိုင်း 32.19.1](https://www.postgresql.org/docs/current/libpq-ssl.html#LIBQ-SSL-CERTIFICATES))။ တနည်းအားဖြင့် — SSL implementation က သတ်မှတ်ထားတဲ့အတိုင်း — [system CA pool](https://www.postgresql.org/docs/current/libpq-connect.html#LIBPQ-CONNECT-SSLROOTCERT) ကို `sslrootcert=system` သုံးပြီး အသုံးပြုနိုင်ပါတယ်; ဒီကိစ္စမှာ — public CA တစ်ခုက လက်မှတ်ထိုးထားတဲ့ certificates တွေကို ရယူတာက ယေဘုယျအားဖြင့် လွယ်ကူတာမို့ — လုံခြုံရေး အတွက် `sslmode=verify-full` ကို အတင်းအကျပ် သုံးစေပါတယ်။

Network (ကွန်ရက်) ပေါ်မှာ [scram-sha-256](/docs/postgresql/auth-password) password authentication သုံးတဲ့အခါ server spoofing မဖြစ်အောင် ကာကွယ်ဖို့ဆိုရင် — SSL သုံးပြီး — အပေါ်က စာပိုဒ်မှာ ဖော်ပြထားတဲ့ anti-spoofing နည်းလမ်းတွေထဲက တစ်ခုခုနဲ့အတူ server ဆီ connect လုပ်ဖို့ သေချာ လုပ်သင့်ပါတယ်။ ထို့အပြင် — libpq ထဲက SCRAM implementation က authentication exchange (စစ်မှန်ကြောင်း စိစစ်မှု ဖလှယ်ခြင်း) တစ်ခုလုံးကို ကာကွယ်ပေးနိုင်စွမ်း မရှိပေမယ့် — `channel_binding=require` connection parameter ကို သုံးခြင်းက server spoofing ကို လျော့ပါးစေတဲ့ နည်းလမ်း (mitigation) တစ်ခု ထောက်ပံ့ပေးပါတယ်။ SCRAM exchange တစ်ခုကို ကြားဖြတ် ကြည့်ရှုဖို့ rogue server (လူဆိုး server) တစ်ခုကို သုံးတဲ့ တိုက်ခိုက်သူ (attacker) တစ်ယောက်က — offline analysis (အော့ဖ်လိုင်း ခွဲခြမ်း စိတ်ဖြာမှု) သုံးပြီး — client ဆီကနေ hashed password ကို ဖော်ထုတ်နိုင်ခြေ ရှိပါတယ်။

GSSAPI နဲ့ spoofing ကာကွယ်ဖို့ဆိုရင် — server က `hostgssenc` connections တွေကိုပဲ လက်ခံဖို့ ([အပိုင်း 20.1](/docs/postgresql/auth-pg-hba-conf)) configure လုပ်ထားပြီး — အဲဒီ connections တွေနဲ့အတူ `gss` authentication ကို သုံးရပါမယ်။ TCP client က `gssencmode=require` သုံးပြီး connect လုပ်ရပါမယ်။
