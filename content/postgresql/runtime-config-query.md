### 19.7.1. Planner Method Configuration (planner နည်းလမ်း configuration)

ဒီ configuration parameter တွေက query optimizer ရွေးချယ်တဲ့ query plan တွေကို အကြမ်းဖျင်း (crude) သက်ရောက်စေတဲ့ နည်းလမ်း တစ်ခု ပေးပါတယ်။ Query တစ်ခုအတွက် optimizer ရွေးချယ်တဲ့ default plan က အကောင်းဆုံး မဖြစ်ရင် — ဒီ configuration parameter တွေထဲက တစ်ခုကို သုံးပြီး optimizer ကို အခြား plan တစ်ခု ရွေးချယ်အောင် ယာယီ အတင်းအကျပ် (force) လုပ်တာက ယာယီ ဖြေရှင်းနည်း တစ်ခု ဖြစ်ပါတယ်။ Optimizer ရွေးချယ်တဲ့ plan တွေရဲ့ အရည်အသွေးကို မြှင့်တင်ဖို့ ပိုကောင်းတဲ့ နည်းလမ်းတွေကတော့ — planner cost constant တွေကို ချိန်ညှိခြင်း ([အပိုင်း 19.7.2](/docs/postgresql/runtime-config-query) ကို ကြည့်ပါ)၊ [`ANALYZE`](/docs/postgresql/sql-analyze) ကို ကိုယ်တိုင် run လုပ်ခြင်း၊ [default_statistics_target](/docs/postgresql/runtime-config-query) configuration parameter ရဲ့ တန်ဖိုးကို တိုးမြှင့်ခြင်း နဲ့ `ALTER TABLE SET STATISTICS` ကို သုံးပြီး သီးခြား column တွေအတွက် စုဆောင်းတဲ့ statistics ပမာဏကို တိုးမြှင့်ခြင်း တို့ ဖြစ်ပါတယ်။

- **enable_async_append (boolean)** — Async-aware append plan အမျိုးအစားတွေကို query planner သုံးတာကို enable ဒါမှမဟုတ် disable လုပ်ပါတယ်။ Default က on ဖြစ်ပါတယ်။
- **enable_bitmapscan (boolean)** — Bitmap-scan plan အမျိုးအစားတွေကို query planner သုံးတာကို enable ဒါမှမဟုတ် disable လုပ်ပါတယ်။ Default က on ဖြစ်ပါတယ်။
- **enable_distinct_reordering (boolean)** — Input path ရဲ့ pathkey တွေနဲ့ ကိုက်ညီအောင် DISTINCT key တွေကို အစီအစဉ် ပြန်စီ (reorder) လုပ်နိုင်တဲ့ query planner ရဲ့ စွမ်းရည်ကို enable ဒါမှမဟုတ် disable လုပ်ပါတယ်။ Default က on ဖြစ်ပါတယ်။
- **enable_gathermerge (boolean)** — Gather merge plan အမျိုးအစားတွေကို query planner သုံးတာကို enable ဒါမှမဟုတ် disable လုပ်ပါတယ်။ Default က on ဖြစ်ပါတယ်။
- **enable_group_by_reordering (boolean)** — Query planner က plan တစ်ခုရဲ့ child node (ဥပမာ — index scan) ရဲ့ key အစီအစဉ်အတိုင်း စီထားတဲ့ GROUP BY key တွေ ပေးမယ့် plan ကို ထုတ်လုပ်မလား ဆိုတာကို ထိန်းချုပ်ပါတယ်။ Disable လုပ်ထားရင် — query planner က GROUP BY key တွေကို (ရှိရင်) ORDER BY clause နဲ့ ကိုက်ညီအောင် စီထားတဲ့ plan ကိုသာ ထုတ်လုပ်ပါတယ်။ Enable လုပ်ထားရင် — planner က ပိုထိရောက်တဲ့ plan တစ်ခု ထုတ်လုပ်ဖို့ ကြိုးစားပါတယ်။ Default တန်ဖိုးက on ဖြစ်ပါတယ်။
- **enable_hashagg (boolean)** — Hashed aggregation plan အမျိုးအစားတွေကို query planner သုံးတာကို enable ဒါမှမဟုတ် disable လုပ်ပါတယ်။ Default က on ဖြစ်ပါတယ်။
- **enable_hashjoin (boolean)** — Hash-join plan အမျိုးအစားတွေကို query planner သုံးတာကို enable ဒါမှမဟုတ် disable လုပ်ပါတယ်။ Default က on ဖြစ်ပါတယ်။
- **enable_incremental_sort (boolean)** — Incremental sort အဆင့်များကို query planner သုံးတာကို enable ဒါမှမဟုတ် disable လုပ်ပါတယ်။ Default က on ဖြစ်ပါတယ်။
- **enable_indexscan (boolean)** — Index-scan နဲ့ index-only-scan plan အမျိုးအစားတွေကို query planner သုံးတာကို enable ဒါမှမဟုတ် disable လုပ်ပါတယ်။ Default က on ဖြစ်ပါတယ်။ enable_indexonlyscan ကိုလည်း ကြည့်ပါ။
- **enable_indexonlyscan (boolean)** — Index-only-scan plan အမျိုးအစားတွေကို query planner သုံးတာကို enable ဒါမှမဟုတ် disable လုပ်ပါတယ် ([အပိုင်း 11.9](/docs/postgresql/indexes-index-only-scans) ကို ကြည့်ပါ)။ Default က on ဖြစ်ပါတယ်။ Query planner က index-only-scan တွေကို စဉ်းစားစေဖို့ — enable_indexscan setting ကိုလည်း enable လုပ်ထားရပါမယ်။
- **enable_material (boolean)** — Materialization ကို query planner သုံးတာကို enable ဒါမှမဟုတ် disable လုပ်ပါတယ်။ Materialization ကို လုံးလုံး ဖိနှိပ် (suppress) လုပ်တာ မဖြစ်နိုင်ပါဘူး — ဒါပေမယ့် ဒီ variable ကို ပိတ်ထားခြင်းက — မှန်ကန်မှုအတွက် လိုအပ်တဲ့ အခြေအနေတွေမှာ ကလွဲပြီး — materialize node တွေ ထည့်သွင်းတာကို planner လုပ်တာကို တားဆီးပါတယ်။ Default က on ဖြစ်ပါတယ်။
- **enable_memoize (boolean)** — Nested-loop join တွေအတွင်း parameterized scan တွေရဲ့ result တွေကို cache လုပ်ဖို့ memoize plan တွေကို query planner သုံးတာကို enable ဒါမှမဟုတ် disable လုပ်ပါတယ်။ ဒီ plan အမျိုးအစားက — လက်ရှိ parameter တွေအတွက် result တွေ cache ထဲမှာ ရှိပြီးသား ဖြစ်နေရင် — အောက်ခံ plan တွေဆီ scan လုပ်တာကို ကျော်လွှားခွင့် ပေးပါတယ်။ Entry အသစ်တွေအတွက် နေရာ ပိုလိုအပ်လာတဲ့အခါ — အလွန်အသုံးနည်းတဲ့ result တွေကို cache ကနေ ဖယ်ထုတ် (evict) နိုင်ပါတယ်။ Default က on ဖြစ်ပါတယ်။
- **enable_mergejoin (boolean)** — Merge-join plan အမျိုးအစားတွေကို query planner သုံးတာကို enable ဒါမှမဟုတ် disable လုပ်ပါတယ်။ Default က on ဖြစ်ပါတယ်။
- **enable_nestloop (boolean)** — Nested-loop join plan တွေကို query planner သုံးတာကို enable ဒါမှမဟုတ် disable လုပ်ပါတယ်။ Nested-loop join တွေကို လုံးလုံး ဖိနှိပ် လုပ်တာ မဖြစ်နိုင်ပါဘူး — ဒါပေမယ့် ဒီ variable ကို ပိတ်ထားခြင်းက — အခြား နည်းလမ်းတွေ ရှိရင် — planner က nested-loop ကို သုံးတာကို တားဆီးပါတယ်။ Default က on ဖြစ်ပါတယ်။
- **enable_parallel_append (boolean)** — Parallel-aware append plan အမျိုးအစားတွေကို query planner သုံးတာကို enable ဒါမှမဟုတ် disable လုပ်ပါတယ်။ Default က on ဖြစ်ပါတယ်။
- **enable_parallel_hash (boolean)** — Parallel hash ပါတဲ့ hash-join plan အမျိုးအစားတွေကို query planner သုံးတာကို enable ဒါမှမဟုတ် disable လုပ်ပါတယ်။ Hash-join plan တွေကိုလည်း enable မလုပ်ထားရင် ဒါက အကျိုးသက်ရောက်မှု မရှိပါဘူး။ Default က on ဖြစ်ပါတယ်။
- **enable_partition_pruning (boolean)** — Query plan တွေကနေ partitioned table တစ်ခုရဲ့ partition တွေကို ဖယ်ရှားပစ်နိုင်တဲ့ query planner ရဲ့ စွမ်းရည်ကို enable ဒါမှမဟုတ် disable လုပ်ပါတယ်။ ဒါက — query execution အတွင်း partition တွေကို query executor ဖယ်ရှား (ignore) စေနိုင်တဲ့ query plan တွေ ထုတ်လုပ်နိုင်တဲ့ planner ရဲ့ စွမ်းရည်ကိုလည်း ထိန်းချုပ်ပါတယ်။ Default က on ဖြစ်ပါတယ်။ အသေးစိတ်အတွက် [အပိုင်း 5.12.4](/docs/postgresql/ddl-partitioning) ကို ကြည့်ပါ။
- **enable_partitionwise_join (boolean)** — Partitionwise join ကို query planner သုံးတာကို enable ဒါမှမဟုတ် disable လုပ်ပါတယ်; ဒါက — partitioned table နှစ်ခုကြားက join ကို — ကိုက်ညီတဲ့ partition တွေ join လုပ်ခြင်းဖြင့် လုပ်ဆောင်ခွင့် ပေးပါတယ်။ Partitionwise join က — join condition တွေမှာ partition key အားလုံး ပါဝင်တဲ့အခါသာ — လက်ရှိ အသုံးပြုနိုင်ပြီး — အဲဒီ partition key တွေက data type တူညီရမှာ ဖြစ်ကာ — child partition အစုများက one-to-one ကိုက်ညီရပါမယ်။ ဒီ setting ကို enable လုပ်ထားရင် — final plan ထဲမှာ work_mem က သူတို့ရဲ့ memory အသုံးပြုမှုကို ကန့်သတ်ထားတဲ့ node အရေအတွက်က — scan လုပ်နေတဲ့ partition အရေအတွက်အလိုက် line အလိုက် (linearly) တိုးလာနိုင်ပါတယ်။ ဒါက query execution အတွင်း စုစုပေါင်း memory သုံးစွဲမှုကို အများကြီး တိုးလာစေနိုင်ပါတယ်။ Query planning ကလည်း memory နဲ့ CPU အနေနဲ့ သိသိသာသာ ပိုကုန်ကျလာပါတယ်။ Default တန်ဖိုးက off ဖြစ်ပါတယ်။
- **enable_partitionwise_aggregate (boolean)** — Partitionwise grouping ဒါမှမဟုတ် aggregation ကို query planner သုံးတာကို enable ဒါမှမဟုတ် disable လုပ်ပါတယ်; ဒါက — partitioned table တွေပေါ်မှာ grouping ဒါမှမဟုတ် aggregation ကို partition တစ်ခုချင်းစီအတွက် သီးခြားစီ လုပ်ဆောင်ခွင့် ပေးပါတယ်။ GROUP BY clause မှာ partition key တွေ မပါဝင်ရင် — partition တစ်ခုချင်းအလိုက် တစ်စိတ်တစ်ပိုင်း aggregation ကိုသာ လုပ်ဆောင်နိုင်ပြီး — finalization ကို နောက်မှ လုပ်ဆောင်ရပါမယ်။ ဒီ setting ကို enable လုပ်ထားရင် — final plan ထဲမှာ work_mem က သူတို့ရဲ့ memory အသုံးပြုမှုကို ကန့်သတ်ထားတဲ့ node အရေအတွက်က — scan လုပ်နေတဲ့ partition အရေအတွက်အလိုက် line အလိုက် တိုးလာနိုင်ပါတယ်။ ဒါက query execution အတွင်း စုစုပေါင်း memory သုံးစွဲမှုကို အများကြီး တိုးလာစေနိုင်ပါတယ်။ Query planning ကလည်း memory နဲ့ CPU အနေနဲ့ သိသိသာသာ ပိုကုန်ကျလာပါတယ်။ Default တန်ဖိုးက off ဖြစ်ပါတယ်။
- **enable_presorted_aggregate (boolean)** — Query ရဲ့ ORDER BY / DISTINCT aggregate function တွေအတွက် လိုအပ်တဲ့ အစီအစဉ်အတိုင်း ကြိုတင် စီထားပြီး (presorted) row တွေ ပေးမယ့် plan ကို query planner ထုတ်လုပ်မလား ဆိုတာကို ထိန်းချုပ်ပါတယ်။ Disable လုပ်ထားရင် — query planner က — ORDER BY ဒါမှမဟုတ် DISTINCT clause ပါဝင်တဲ့ aggregate function တစ်ခုချင်းစီကို aggregation မလုပ်မီ — executor က sort တစ်ခု လုပ်ရမယ့် plan ကို အမြဲ ထုတ်လုပ်ပါတယ်။ Enable လုပ်ထားရင် — planner က — aggregate function တွေဆီ — သူတို့ aggregation အတွက် လိုအပ်တဲ့ အစီအစဉ်အတိုင်း ကြိုတင် စီထားတဲ့ input ပေးတဲ့ — ပိုထိရောက်တဲ့ plan တစ်ခု ထုတ်လုပ်ဖို့ ကြိုးစားပါတယ်။ Default တန်ဖိုးက on ဖြစ်ပါတယ်။
- **enable_self_join_elimination (boolean)** — Query tree ကို စိစစ်ပြီး self join တွေကို အဓိပ္ပာယ် တူညီတဲ့ single scan တွေနဲ့ အစားထိုးတဲ့ query planner ရဲ့ optimization ကို enable ဒါမှမဟုတ် disable လုပ်ပါတယ်။ ရိုးရိုး table တွေကိုသာ စဉ်းစားပါတယ်။ Default က on ဖြစ်ပါတယ်။
- **enable_seqscan (boolean)** — Sequential scan plan အမျိုးအစားတွေကို query planner သုံးတာကို enable ဒါမှမဟုတ် disable လုပ်ပါတယ်။ Sequential scan တွေကို လုံးလုံး ဖိနှိပ် လုပ်တာ မဖြစ်နိုင်ပါဘူး — ဒါပေမယ့် ဒီ variable ကို ပိတ်ထားခြင်းက — အခြား နည်းလမ်းတွေ ရှိရင် — planner က sequential scan ကို သုံးတာကို တားဆီးပါတယ်။ Default က on ဖြစ်ပါတယ်။
- **enable_sort (boolean)** — Explicit sort အဆင့်များကို query planner သုံးတာကို enable ဒါမှမဟုတ် disable လုပ်ပါတယ်။ Explicit sort တွေကို လုံးလုံး ဖိနှိပ် လုပ်တာ မဖြစ်နိုင်ပါဘူး — ဒါပေမယ့် ဒီ variable ကို ပိတ်ထားခြင်းက — အခြား နည်းလမ်းတွေ ရှိရင် — planner က explicit sort ကို သုံးတာကို တားဆီးပါတယ်။ Default က on ဖြစ်ပါတယ်။
- **enable_tidscan (boolean)** — TID scan plan အမျိုးအစားတွေကို query planner သုံးတာကို enable ဒါမှမဟုတ် disable လုပ်ပါတယ်။ Default က on ဖြစ်ပါတယ်။

### 19.7.2. Planner Cost Constants (planner ကုန်ကျစရိတ် ကိန်းသေများ)

ဒီ section မှာ ဖော်ပြထားတဲ့ *cost* variable တွေကို မထင်မှတ်တဲ့ စကေး (arbitrary scale) တစ်ခုပေါ်မှာ တိုင်းတာပါတယ်။ သူတို့ရဲ့ နှိုင်းရ (relative) တန်ဖိုးတွေကသာ အရေးကြီးတာမို့ — အားလုံးကို တူညီတဲ့ အချိုးနဲ့ အတူတူ အတိုးအလျှော့ လုပ်လိုက်ရင် — planner ရဲ့ ရွေးချယ်မှုတွေမှာ ပြောင်းလဲမှု မရှိပါဘူး။ Default အားဖြင့် — ဒီ cost variable တွေက sequential page fetch တွေရဲ့ ကုန်ကျစရိတ်ကို အခြေခံပါတယ်; ဆိုလိုတာက — `seq_page_cost` ကို သမားရိုးကျအားဖြင့် `1.0` သတ်မှတ်ပြီး — ကျန် cost variable တွေကို အဲဒါကို ရည်ညွှန်းပြီး သတ်မှတ်ပါတယ်။ ဒါပေမယ့် သင်ကြိုက်ရင် — သီးခြား machine တစ်ခုပေါ်က တကယ့် execution အချိန် (millisecond) ကဲ့သို့ — မတူတဲ့ စကေး တစ်ခုကို သုံးနိုင်ပါတယ်။

> **မှတ်ချက်:** ကံဆိုးစွာပဲ — cost variable တွေအတွက် စံပြ တန်ဖိုးတွေ သတ်မှတ်ဖို့ ကောင်းမွန်စွာ သတ်မှတ်ထားတဲ့ နည်းလမ်း မရှိပါဘူး။ သီးခြား installation တစ်ခု လက်ခံရမယ့် query အစုအဝေး တစ်ခုလုံးအပေါ် ပျမ်းမျှ (average) အဖြစ် သဘောထားတာက အကောင်းဆုံး ဖြစ်ပါတယ်။ ဆိုလိုတာက — စမ်းသပ်မှု အနည်းငယ်သာ အခြေခံပြီး သူတို့ကို ပြောင်းလဲတာက အလွန် အန္တရာယ် များပါတယ်။

- **seq_page_cost (floating point)** — တစ်ဆက်တည်း (sequential) fetch လုပ်တဲ့ အတွဲတစ်ခုရဲ့ အစိတ်အပိုင်း ဖြစ်တဲ့ disk page fetch တစ်ခုရဲ့ ကုန်ကျစရိတ်အပေါ် planner ရဲ့ ခန့်မှန်းချက်ကို သတ်မှတ်ပါတယ်။ Default က 1.0 ဖြစ်ပါတယ်။ ဒီတန်ဖိုးကို — သီးခြား tablespace တစ်ခုထဲက table နဲ့ index တွေအတွက် — အလားတူ နာမည်ရှိတဲ့ tablespace parameter ကို သတ်မှတ်ခြင်းဖြင့် override လုပ်နိုင်ပါတယ် ([ALTER TABLESPACE](/docs/postgresql/sql-altertablespace) ကို ကြည့်ပါ)။
- **random_page_cost (floating point)** — အစီအစဉ်တကျ မဟုတ်ဘဲ fetch လုပ်တဲ့ (non-sequentially-fetched) disk page တစ်ခုရဲ့ ကုန်ကျစရိတ်အပေါ် planner ရဲ့ ခန့်မှန်းချက်ကို သတ်မှတ်ပါတယ်။ Default က 4.0 ဖြစ်ပါတယ်။ ဒီတန်ဖိုးကို — သီးခြား tablespace တစ်ခုထဲက table နဲ့ index တွေအတွက် — အလားတူ နာမည်ရှိတဲ့ tablespace parameter ကို သတ်မှတ်ခြင်းဖြင့် override လုပ်နိုင်ပါတယ် ([ALTER TABLESPACE](/docs/postgresql/sql-altertablespace) ကို ကြည့်ပါ)။
ဒီတန်ဖိုးကို seq_page_cost နဲ့ နှိုင်းယှဉ်ပြီး လျှော့ချလိုက်ရင် — system က index scan တွေကို ပိုနှစ်သက်လာပါလိမ့်မယ်; တိုးမြှင့်လိုက်ရင် — index scan တွေက နှိုင်းရအားဖြင့် ပိုကုန်ကျတဲ့ပုံ ပေါ်လာပါလိမ့်မယ်။ တန်ဖိုး နှစ်ခုလုံးကို အတူတူ တိုး/လျှော့ လုပ်ခြင်းဖြင့် — အောက်ပါ parameter တွေနဲ့ ဖော်ပြထားတဲ့ CPU cost တွေနဲ့ နှိုင်းယှဉ်ရင် — disk I/O cost တွေရဲ့ အရေးပါမှုကို ပြောင်းလဲနိုင်ပါတယ်။
Durable storage ဆီ အစီအစဉ်မကျဘဲ (random) access လုပ်တာက — အစီအစဉ်တကျ access လုပ်တာထက် — ပုံမှန်အားဖြင့် လေးဆထက် အများကြီး ပိုကုန်ကျပါတယ်။ ဒါပေမယ့် — index ဖတ်ခြင်းကဲ့သို့ — storage ဆီ random access အများစုက cache ထဲမှာ ရှိတယ်လို့ ယူဆတာကြောင့် — နိမ့်တဲ့ default (4.0) ကို သုံးထားပါတယ်။ ထို့အပြင် — network-attached storage ရဲ့ latency က random access ရဲ့ နှိုင်းရ overhead ကို လျှော့ချပေးတတ်ပါတယ်။
Default တန်ဖိုး ထင်ဟပ်တာထက် caching က ပိုနည်းတယ်လို့ သင်ယုံကြည်ပြီး — network latency ကလည်း အနည်းဆုံး ဖြစ်ရင် — random storage read တွေရဲ့ တကယ့် cost ကို ပိုထင်ဟပ်စေဖို့ random_page_cost ကို တိုးမြှင့်နိုင်ပါတယ်။ Magnetic disk ကဲ့သို့ — sequential နဲ့ နှိုင်းယှဉ်ရင် random read cost ပိုမြင့်တဲ့ storage ကိုလည်း random_page_cost ရဲ့ ပိုမြင့်တဲ့ တန်ဖိုးနဲ့ ပိုကောင်းစွာ model လုပ်နိုင်ပါတယ်။ အလားတူပဲ — database က server memory စုစုပေါင်းထက် သေးတာကဲ့သို့ — သင့် data က cache ထဲမှာ လုံးလုံး ရှိနိုင်ခြေ များရင် ဒါမှမဟုတ် network latency မြင့်ရင် — random_page_cost ကို လျှော့ချတာက သင့်လျော်နိုင်ပါတယ်။

> **အကြံပြုချက်:** System က random_page_cost ကို seq_page_cost ထက် နည်းအောင် သတ်မှတ်ခွင့် ပေးပေမယ့် — အဲဒီလို လုပ်တာက ရုပ်ပိုင်းအရ (physically) အဓိပ္ပာယ် မရှိပါဘူး။ ဒါပေမယ့် — database က RAM ထဲမှာ လုံးလုံး cache ဖြစ်နေရင် — သူတို့ကို ညီအောင် (equal) သတ်မှတ်တာက အဓိပ္ပာယ် ရှိပါတယ်; အကြောင်းကတော့ အဲဒီအခြေအနေမှာ — page တွေကို အစီအစဉ်မကျဘဲ ထိတွေ့ (touch) လုပ်တာအတွက် ဒဏ်ကြေး မရှိလို့ပါ။ ထို့အပြင် — အလွန်အမင်း cache ဖြစ်နေတဲ့ database တစ်ခုမှာ — RAM ထဲမှာ ရှိပြီးသား page တစ်ခုကို fetch လုပ်တဲ့ cost က ပုံမှန် ဖြစ်နိုင်တာထက် အများကြီး သေးငယ်တာကြောင့် — CPU parameter တွေနဲ့ နှိုင်းယှဉ်ရင် တန်ဖိုး နှစ်ခုလုံးကို လျှော့ချသင့်ပါတယ်။
- **cpu_tuple_cost (floating point)** — Query တစ်ခုအတွင်း row တစ်ခုချင်းစီကို လုပ်ဆောင်တဲ့ ကုန်ကျစရိတ်အပေါ် planner ရဲ့ ခန့်မှန်းချက်ကို သတ်မှတ်ပါတယ်။ Default က 0.01 ဖြစ်ပါတယ်။
- **cpu_index_tuple_cost (floating point)** — Index scan တစ်ခုအတွင်း index entry တစ်ခုချင်းစီကို လုပ်ဆောင်တဲ့ ကုန်ကျစရိတ်အပေါ် planner ရဲ့ ခန့်မှန်းချက်ကို သတ်မှတ်ပါတယ်။ Default က 0.005 ဖြစ်ပါတယ်။
- **cpu_operator_cost (floating point)** — Query တစ်ခုအတွင်း execute လုပ်တဲ့ operator ဒါမှမဟုတ် function တစ်ခုချင်းစီကို လုပ်ဆောင်တဲ့ ကုန်ကျစရိတ်အပေါ် planner ရဲ့ ခန့်မှန်းချက်ကို သတ်မှတ်ပါတယ်။ Default က 0.0025 ဖြစ်ပါတယ်။
- **parallel_setup_cost (floating point)** — Parallel worker process တွေ စတင် လွှတ်တဲ့ (launching) ကုန်ကျစရိတ်အပေါ် planner ရဲ့ ခန့်မှန်းချက်ကို သတ်မှတ်ပါတယ်။ Default က 1000 ဖြစ်ပါတယ်။
- **parallel_tuple_cost (floating point)** — Parallel worker process တစ်ခုကနေ အခြား process တစ်ခုဆီ tuple တစ်ခု လွှဲပြောင်းတဲ့ ကုန်ကျစရိတ်အပေါ် planner ရဲ့ ခန့်မှန်းချက်ကို သတ်မှတ်ပါတယ်။ Default က 0.1 ဖြစ်ပါတယ်။
- **min_parallel_table_scan_size (integer)** — Parallel scan တစ်ခုကို စဉ်းစားဖို့ — scan လုပ်ရမယ့် table data ရဲ့ အနည်းဆုံး ပမာဏကို သတ်မှတ်ပါတယ်။ Parallel sequential scan တစ်ခုအတွက် — scan လုပ်တဲ့ table data ပမာဏက table ရဲ့ အရွယ်အစားနဲ့ အမြဲ ညီပါတယ် — ဒါပေမယ့် index တွေ သုံးတဲ့အခါ — scan လုပ်တဲ့ table data ပမာဏက ပုံမှန်အားဖြင့် ပိုနည်းပါလိမ့်မယ်။ ဒီတန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် — block တွေအဖြစ် — ဆိုလိုတာက BLCKSZ byte တွေ၊ ပုံမှန်အားဖြင့် 8kB — ယူပါတယ်။ Default က 8 megabyte (8MB) ဖြစ်ပါတယ်။
- **min_parallel_index_scan_size (integer)** — Parallel scan တစ်ခုကို စဉ်းစားဖို့ — scan လုပ်ရမယ့် index data ရဲ့ အနည်းဆုံး ပမာဏကို သတ်မှတ်ပါတယ်။ Parallel index scan တစ်ခုက ပုံမှန်အားဖြင့် index တစ်ခုလုံးကို ထိတွေ့မှာ မဟုတ်ကြောင်း သတိပြုပါ; scan က တကယ် ထိတွေ့မယ်လို့ planner ယုံကြည်တဲ့ page အရေအတွက်ကသာ သက်ဆိုင်ပါတယ်။ ဒီ parameter ကို — သီးခြား index တစ်ခုက parallel vacuum တစ်ခုမှာ ပါဝင်နိုင်မလား ဆုံးဖြတ်ဖို့လည်း သုံးပါတယ်။ [VACUUM](/docs/postgresql/sql-vacuum) ကို ကြည့်ပါ။ ဒီတန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် — block တွေအဖြစ် — ဆိုလိုတာက BLCKSZ byte တွေ၊ ပုံမှန်အားဖြင့် 8kB — ယူပါတယ်။ Default က 512 kilobyte (512kB) ဖြစ်ပါတယ်။
- **effective_cache_size (integer)** — Query တစ်ခုတည်းအတွက် ရရှိနိုင်တဲ့ disk cache ရဲ့ ထိရောက်တဲ့ အရွယ်အစား (effective size) အပေါ် planner ရဲ့ ယူဆချက် (assumption) ကို သတ်မှတ်ပါတယ်။ ဒါက index တစ်ခု သုံးတဲ့ ကုန်ကျစရိတ် ခန့်မှန်းချက်တွေမှာ ထည့်သွင်း စဉ်းစားပါတယ်; တန်ဖိုး မြင့်ရင် index scan တွေ သုံးနိုင်ခြေ ပိုများပြီး — တန်ဖိုး နိမ့်ရင် sequential scan တွေ သုံးနိုင်ခြေ ပိုများပါတယ်။ ဒီ parameter ကို သတ်မှတ်တဲ့အခါ — PostgreSQL ရဲ့ shared buffer တွေနဲ့ — PostgreSQL data file တွေအတွက် သုံးမယ့် kernel ရဲ့ disk cache အပိုင်း — နှစ်ခုလုံးကို စဉ်းစားသင့်ပါတယ် (data တချို့က နေရာ နှစ်ခုလုံးမှာ ရှိနိုင်ပေမယ့်လည်း)။ ထို့အပြင် — မတူတဲ့ table တွေပေါ်က တစ်ပြိုင်နက် (concurrent) query အရေအတွက် မျှော်မှန်းချက်ကိုလည်း ထည့်စဉ်းစားပါ — အကြောင်းကတော့ သူတို့က ရရှိနိုင်တဲ့ နေရာကို မျှဝေ သုံးရမှာမို့ပါ။ ဒီ parameter က PostgreSQL က ခွဲဝေပေးတဲ့ shared memory ရဲ့ အရွယ်အစားအပေါ် သက်ရောက်မှု မရှိသလို — kernel disk cache ကိုလည်း သိမ်းဆည်း (reserve) မထားပါဘူး; ဒါကို ခန့်မှန်းချက် ရည်ရွယ်ချက်အတွက်သာ သုံးပါတယ်။ System က query တွေကြားမှာ data က disk cache ထဲမှာ ကျန်နေတယ်လို့လည်း မယူဆပါဘူး။ ဒီတန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် — block တွေအဖြစ် — ဆိုလိုတာက BLCKSZ byte တွေ၊ ပုံမှန်အားဖြင့် 8kB — ယူပါတယ်။ Default က 4 gigabyte (4GB) ဖြစ်ပါတယ်။ (BLCKSZ က 8kB မဟုတ်ရင် — default တန်ဖိုးက အဲဒါနဲ့ အချိုးကျ (proportionally) ချိန်ညှိပါတယ်။)
- **jit_above_cost (floating point)** — (enable လုပ်ထားရင်) JIT compilation ကို စတင် အသက်သွင်းတဲ့ query cost အထက် သတ်မှတ်ပါတယ် ([အခန်း 30](https://www.postgresql.org/docs/current/jit.html) ကို ကြည့်ပါ)။ JIT လုပ်ဆောင်တာက planning time ကို ကုန်ကျစေပေမယ့် — query execution ကို အရှိန်မြှင့်နိုင်ပါတယ်။ ဒါကို -1 သတ်မှတ်ရင် JIT compilation ကို disable လုပ်ပါတယ်။ Default က 100000 ဖြစ်ပါတယ်။
- **jit_inline_above_cost (floating point)** — JIT compilation က function နဲ့ operator တွေကို inline လုပ်ဖို့ ကြိုးစားတဲ့ query cost အထက် သတ်မှတ်ပါတယ်။ Inlining က planning time ကို ထည့်ပေါင်းစေပေမယ့် — execution အရှိန်ကို တိုးတက်စေနိုင်ပါတယ်။ ဒါကို jit_above_cost ထက် နည်းအောင် သတ်မှတ်တာက အဓိပ္ပာယ် မရှိပါဘူး။ ဒါကို -1 သတ်မှတ်ရင် inlining ကို disable လုပ်ပါတယ်။ Default က 500000 ဖြစ်ပါတယ်။
- **jit_optimize_above_cost (floating point)** — JIT compilation က ကုန်ကျစရိတ် မြင့်တဲ့ optimization တွေကို သက်ရောက်စေတဲ့ query cost အထက် သတ်မှတ်ပါတယ်။ ဒီလို optimization က planning time ကို ထည့်ပေါင်းစေပေမယ့် — execution အရှိန်ကို တိုးတက်စေနိုင်ပါတယ်။ ဒါကို jit_above_cost ထက် နည်းအောင် သတ်မှတ်တာက အဓိပ္ပာယ် မရှိသလို — jit_inline_above_cost ထက် ပိုများအောင် သတ်မှတ်တာကလည်း အကျိုးရှိဖို့ မဖြစ်နိုင်ပါဘူး။ ဒါကို -1 သတ်မှတ်ရင် ကုန်ကျစရိတ် မြင့်တဲ့ optimization တွေကို disable လုပ်ပါတယ်။ Default က 500000 ဖြစ်ပါတယ်။

### 19.7.3. Genetic Query Optimizer (မျိုးရိုးဗီဇ query optimizer)

Genetic query optimizer (GEQO) ဆိုတာ — heuristic searching (ရှာဖွေမှု အတွေးအခေါ် အခြေပြု ရှာဖွေခြင်း) ကို သုံးပြီး query planning လုပ်တဲ့ algorithm တစ်ခု ဖြစ်ပါတယ်။ ဒါက — ရှုပ်ထွေးတဲ့ query တွေအတွက် (relation အများအပြားကို join လုပ်တဲ့ query တွေ) — planning time ကို လျှော့ချပေးပေမယ့် — ပုံမှန် exhaustive-search algorithm က ရှာတွေ့တဲ့ plan တွေထက် တခါတရံ ညံ့တဲ့ plan တွေ ထုတ်ပေးတဲ့ ကုန်ကျစရိတ် (cost) ရှိပါတယ်။ နောက်ထပ် အချက်အလက်အတွက် [အခန်း 61](https://www.postgresql.org/docs/current/geqo.html) ကို ကြည့်ပါ။

- **geqo (boolean)** — Genetic query optimization ကို enable ဒါမှမဟုတ် disable လုပ်ပါတယ်။ Default အားဖြင့် on ဖြစ်ပါတယ်။ Production မှာ ဒါကို ပိတ်တာ မလုပ်တာက ပုံမှန်အားဖြင့် အကောင်းဆုံး ဖြစ်ပါတယ်; geqo_threshold variable က GEQO ကို ပိုပြီး သေးငယ်တဲ့ အစိတ်အပိုင်းအလိုက် (granular) ထိန်းချုပ်မှု ပေးပါတယ်။
- **geqo_threshold (integer)** — အနည်းဆုံး ဒီလောက် FROM item တွေ ပါဝင်တဲ့ query တွေကို plan ရေးဆွဲဖို့ genetic query optimization ကို သုံးပါ။ (FULL OUTER JOIN construct တစ်ခုက FROM item တစ်ခုအဖြစ်သာ ရေတွက်ကြောင်း သတိပြုပါ။) Default က 12 ဖြစ်ပါတယ်။ ရိုးရှင်းတဲ့ query တွေအတွက်တော့ ပုံမှန် exhaustive-search planner ကို သုံးတာက အကောင်းဆုံး ဖြစ်ပါတယ် — ဒါပေမယ့် table အများအပြား ပါဝင်တဲ့ query တွေအတွက်တော့ exhaustive search က အလွန်ကြာလွန်းတတ်ပြီး — မကောင်းတဲ့ (suboptimal) plan တစ်ခုကို execute လုပ်တဲ့ ဒဏ်ကြေးထက်တောင် ပိုကြာတတ်ပါတယ်။ ဒါကြောင့် — query ရဲ့ အရွယ်အစားအပေါ် threshold တစ်ခု ထားတာက GEQO အသုံးပြုမှုကို စီမံဖို့ အဆင်ပြေတဲ့ နည်းလမ်း တစ်ခု ဖြစ်ပါတယ်။
- **geqo_effort (integer)** — GEQO မှာ planning time နဲ့ query plan အရည်အသွေး ကြားက ညှိနှိုင်းမှု (trade-off) ကို ထိန်းချုပ်ပါတယ်။ ဒီ variable က 1 ကနေ 10 အထိ အတိုင်းအတာအတွင်း ကိန်းပြည့် (integer) တစ်ခု ဖြစ်ရပါမယ်။ Default တန်ဖိုးက ငါး (5) ဖြစ်ပါတယ်။ တန်ဖိုး ကြီးလာရင် query planning လုပ်တဲ့ အချိန် တိုးလာပေမယ့် — ထိရောက်တဲ့ query plan တစ်ခု ရွေးချယ်ခံရနိုင်ခြေလည်း တိုးလာပါတယ်။
geqo_effort က တိုက်ရိုက် ဘာမှ မလုပ်ပါဘူး; GEQO အပြုအမူကို သက်ရောက်တဲ့ ကျန် variable တွေ (အောက်မှာ ဖော်ပြထားတဲ့) အတွက် default တန်ဖိုးတွေကို တွက်ချက်ဖို့သာ သုံးပါတယ်။ သင်ကြိုက်ရင် — အခြား parameter တွေကို ကိုယ်တိုင် သတ်မှတ်နိုင်ပါတယ်။
- **geqo_pool_size (integer)** — GEQO သုံးတဲ့ pool size — ဆိုလိုတာက genetic population ထဲက individual အရေအတွက် — ကို ထိန်းချုပ်ပါတယ်။ အနည်းဆုံး နှစ်ခု ဖြစ်ရပြီး — အသုံးဝင်တဲ့ တန်ဖိုးတွေက ပုံမှန်အားဖြင့် 100 ကနေ 1000 အထိ ဖြစ်ပါတယ်။ သုည (default setting) သတ်မှတ်ထားရင် — geqo_effort နဲ့ query ထဲက table အရေအတွက်အပေါ် အခြေခံပြီး သင့်လျော်တဲ့ တန်ဖိုး တစ်ခုကို ရွေးချယ်ပါတယ်။
- **geqo_generations (integer)** — GEQO သုံးတဲ့ generation အရေအတွက် — ဆိုလိုတာက algorithm ရဲ့ iteration အရေအတွက် — ကို ထိန်းချုပ်ပါတယ်။ အနည်းဆုံး တစ်ခု ဖြစ်ရပြီး — အသုံးဝင်တဲ့ တန်ဖိုးတွေက pool size နဲ့ တူညီတဲ့ အတိုင်းအတာအတွင်း ရှိပါတယ်။ သုည (default setting) သတ်မှတ်ထားရင် — geqo_pool_size အပေါ် အခြေခံပြီး သင့်လျော်တဲ့ တန်ဖိုး တစ်ခုကို ရွေးချယ်ပါတယ်။
- **geqo_selection_bias (floating point)** — GEQO သုံးတဲ့ selection bias ကို ထိန်းချုပ်ပါတယ်။ Selection bias ဆိုတာ population အတွင်း ရှိတဲ့ ရွေးချယ်မှု ဖိအား (selective pressure) ဖြစ်ပါတယ်။ တန်ဖိုးတွေက 1.50 ကနေ 2.00 အထိ ဖြစ်နိုင်ပြီး — နောက်ဆုံးတန်ဖိုးက default ဖြစ်ပါတယ်။
- **geqo_seed (floating point)** — Join order search space တစ်လျှောက် ကျပန်း (random) path တွေ ရွေးချယ်ဖို့ GEQO သုံးတဲ့ random number generator ရဲ့ ကနဦး တန်ဖိုးကို ထိန်းချုပ်ပါတယ်။ တန်ဖိုးက သုည (default) ကနေ တစ် အထိ အတိုင်းအတာ ရှိနိုင်ပါတယ်။ တန်ဖိုးကို ပြောင်းလဲတာက — စူးစမ်းတဲ့ join path အစုကို ပြောင်းလဲစေပြီး — ပိုကောင်းတဲ့ ဒါမှမဟုတ် ပိုညံ့တဲ့ အကောင်းဆုံး path တစ်ခု ရှာတွေ့တာကို ဖြစ်စေနိုင်ပါတယ်။

### 19.7.4. Other Planner Options (အခြား planner option များ)

- **default_statistics_target (integer)** — ALTER TABLE SET STATISTICS နဲ့ column-အလိုက် သီးခြား target သတ်မှတ်မထားတဲ့ table column တွေအတွက် default statistics target ကို သတ်မှတ်ပါတယ်။ တန်ဖိုး ကြီးလာရင် ANALYZE လုပ်ဖို့ လိုအပ်တဲ့ အချိန် တိုးလာပေမယ့် — planner ရဲ့ ခန့်မှန်းချက်တွေရဲ့ အရည်အသွေး တိုးတက်နိုင်ပါတယ်။ Default က 100 ဖြစ်ပါတယ်။ PostgreSQL query planner က statistics အသုံးပြုပုံနဲ့ ပတ်သက်ပြီး နောက်ထပ် အချက်အလက်အတွက် [အပိုင်း 14.2](/docs/postgresql/planner-stats) ကို ကိုးကားပါ။
- **constraint_exclusion (enum)** — Query တွေကို optimize လုပ်ဖို့ table constraint တွေကို query planner သုံးတာကို ထိန်းချုပ်ပါတယ်။ constraint_exclusion ရဲ့ ခွင့်ပြုတဲ့ တန်ဖိုးတွေကတော့ — on (table အားလုံးအတွက် constraint တွေကို စစ်ဆေးခြင်း)၊ off (constraint တွေကို ဘယ်တော့မှ မစစ်ဆေးခြင်း) နဲ့ partition (inheritance child table တွေနဲ့ UNION ALL subquery တွေအတွက်သာ constraint တွေ စစ်ဆေးခြင်း) တို့ ဖြစ်ပါတယ်။ partition က default setting ဖြစ်ပါတယ်။ ဒါကို သမားရိုးကျ inheritance tree တွေနဲ့ တွဲသုံးပြီး စွမ်းဆောင်ရည် တိုးတက်စေဖို့ မကြာခဏ သုံးပါတယ်။
ဒီ parameter က သီးခြား table တစ်ခုအတွက် ခွင့်ပြုတဲ့အခါ — planner က query condition တွေကို table ရဲ့ CHECK constraint တွေနဲ့ နှိုင်းယှဉ်ပြီး — condition တွေက constraint တွေနဲ့ ဆန့်ကျင်နေတဲ့ table တွေကို scan လုပ်တာ ချန်လှပ် (omit) ပါတယ်။ ဥပမာ —

CREATE TABLE parent(key integer, ...);
CREATE TABLE child1000(check (key between 1000 and 1999)) INHERITS(parent);
CREATE TABLE child2000(check (key between 2000 and 2999)) INHERITS(parent);
...
SELECT * FROM parent WHERE key = 2400;

Constraint exclusion enable လုပ်ထားရင် — ဒီ SELECT က child1000 ကို လုံးဝ scan လုပ်မှာ မဟုတ်ဘဲ — စွမ်းဆောင်ရည် တိုးတက်စေပါတယ်။
လက်ရှိအချိန်မှာ — constraint exclusion ကို — inheritance tree တွေကနေတစ်ဆင့် table partitioning အကောင်အထည်ဖော်ဖို့ မကြာခဏ သုံးတဲ့ အခြေအနေတွေအတွက်သာ — default အားဖြင့် enable လုပ်ထားပါတယ်။ Table အားလုံးအတွက် ဒါကို on လုပ်တာက — ရိုးရှင်းတဲ့ query တွေမှာ သိသာလောက်အောင် များတဲ့ အပို planning overhead ကို ထည့်ပေါင်းစေပြီး — ရိုးရှင်းတဲ့ query တွေအတွက် များသောအားဖြင့် အကျိုးအမြတ် ရရှိမှာ မဟုတ်ပါဘူး။ သမားရိုးကျ inheritance သုံးပြီး partition လုပ်ထားတဲ့ table တွေ မရှိရင် — ဒါကို လုံးလုံး ပိတ်တာကို သင်က ပိုနှစ်သက်နိုင်ပါတယ်။ (Partitioned table တွေအတွက် ညီမျှတဲ့ feature ကို — သီးခြား parameter တစ်ခု ဖြစ်တဲ့ enable_partition_pruning က ထိန်းချုပ်ကြောင်း သတိပြုပါ။)
Partitioning အကောင်အထည်ဖော်ဖို့ constraint exclusion အသုံးပြုပုံနဲ့ ပတ်သက်ပြီး နောက်ထပ် အချက်အလက်အတွက် [အပိုင်း 5.12.5](/docs/postgresql/ddl-partitioning) ကို ကိုးကားပါ။
- **cursor_tuple_fraction (floating point)** — Cursor တစ်ခုရဲ့ row တွေထဲက ပြန်လည် ရယူမယ့် အချိုးအစား (fraction) အပေါ် planner ရဲ့ ခန့်မှန်းချက်ကို သတ်မှတ်ပါတယ်။ Default က 0.1 ဖြစ်ပါတယ်။ ဒီ setting ရဲ့ တန်ဖိုး သေးလာရင် — cursor တွေအတွက် “fast start” plan တွေကို သုံးဖို့ planner ကို ယိမ်းစေပြီး — ပထမ row အနည်းငယ်ကို လျင်မြန်စွာ ရယူပေမယ့် — row အားလုံး fetch လုပ်ဖို့ အချိန် အများကြီး ကြာနိုင်ပါတယ်။ တန်ဖိုး ကြီးလာရင် — စုစုပေါင်း ခန့်မှန်းချိတ် အချိန်အပေါ် ပိုအလေးထားပါတယ်။ အများဆုံး 1.0 setting မှာ — cursor တွေကို — ပထမ row တွေ ဘယ်လောက် မြန်မြန် ရောက်လာနိုင်တာကို မစဉ်းစားဘဲ — စုစုပေါင်း ခန့်မှန်းချိတ် အချိန်ကိုသာ စဉ်းစားပြီး — ပုံမှန် query တွေလိုပဲ အတိအကျ plan ရေးဆွဲပါတယ်။
- **from_collapse_limit (integer)** — ရလာတဲ့ FROM list မှာ ဒီလောက် item အရေအတွက်ထက် မပိုရင် — planner က sub-query တွေကို အပေါ်အဆင့် (upper) query တွေထဲ ပေါင်းစည်း (merge) ပါလိမ့်မယ်။ တန်ဖိုး သေးလာရင် planning time လျှော့ချပေမယ့် — ညံ့တဲ့ query plan တွေ ရနိုင်ပါတယ်။ Default က ရှစ် (8) ဖြစ်ပါတယ်။ နောက်ထပ် အချက်အလက်အတွက် [အပိုင်း 14.3](/docs/postgresql/explicit-joins) ကို ကြည့်ပါ။
ဒီတန်ဖိုးကို geqo_threshold ဒါမှမဟုတ် အဲဒီထက် ပိုများအောင် သတ်မှတ်ရင် — GEQO planner ရဲ့ အသုံးပြုမှုကို စတင်စေနိုင်ပြီး — အကောင်းဆုံးမဟုတ်တဲ့ plan တွေ ဖြစ်လာနိုင်ပါတယ်။ [အပိုင်း 19.7.3](/docs/postgresql/runtime-config-query) ကို ကြည့်ပါ။
- **jit (boolean)** — (ရရှိနိုင်ရင်) PostgreSQL က JIT compilation ကို သုံးနိုင်မလား ဆုံးဖြတ်ပါတယ် ([အခန်း 30](https://www.postgresql.org/docs/current/jit.html) ကို ကြည့်ပါ)။ Default က on ဖြစ်ပါတယ်။
- **join_collapse_limit (integer)** — Planner က — ဒီလောက် item အရေအတွက်ထက် မပိုတဲ့ list တစ်ခု ရလာတိုင်း — တိကျ ဖော်ပြထားတဲ့ JOIN construct တွေကို (FULL JOIN တွေ ကလွဲပြီး) FROM item list တွေအဖြစ် ပြန်ရေးပါလိမ့်မယ်။ တန်ဖိုး သေးလာရင် planning time လျှော့ချပေမယ့် — ညံ့တဲ့ query plan တွေ ရနိုင်ပါတယ်။
Default အားဖြင့် — ဒီ variable ကို from_collapse_limit နဲ့ အတူတူ သတ်မှတ်ထားပြီး — အသုံးပြုမှု အများစုအတွက် သင့်လျော်ပါတယ်။ ဒါကို 1 သတ်မှတ်ရင် — တိကျ ဖော်ပြထားတဲ့ JOIN တွေကို ဘယ်လို အစီအစဉ် ပြန်စီတာမှ မလုပ်တော့ပါဘူး။ ဒါကြောင့် — query ထဲမှာ တိကျ ဖော်ပြထားတဲ့ join အစီအစဉ်က — relation တွေ တကယ် join လုပ်တဲ့ အစီအစဉ် ဖြစ်လာပါလိမ့်မယ်။ Query planner က အကောင်းဆုံး join အစီအစဉ်ကို အမြဲ ရွေးချယ်တာ မဟုတ်တာကြောင့် — အဆင့်မြင့် user တွေက ဒီ variable ကို ယာယီ 1 သတ်မှတ်ပြီး — သူတို့ လိုချင်တဲ့ join အစီအစဉ်ကို တိကျစွာ ဖော်ပြနိုင်ပါတယ်။ နောက်ထပ် အချက်အလက်အတွက် [အပိုင်း 14.3](/docs/postgresql/explicit-joins) ကို ကြည့်ပါ။
ဒီတန်ဖိုးကို geqo_threshold ဒါမှမဟုတ် အဲဒီထက် ပိုများအောင် သတ်မှတ်ရင် — GEQO planner ရဲ့ အသုံးပြုမှုကို စတင်စေနိုင်ပြီး — အကောင်းဆုံးမဟုတ်တဲ့ plan တွေ ဖြစ်လာနိုင်ပါတယ်။ [အပိုင်း 19.7.3](/docs/postgresql/runtime-config-query) ကို ကြည့်ပါ။
- **plan_cache_mode (enum)** — Prepared statement တွေကို (တိကျစွာ prepare လုပ်ထားတာ ဒါမှမဟုတ် — ဥပမာ PL/pgSQL ကဲ့သို့ — အလိုအလျောက် ထုတ်ပေးထားတာ) — custom ဒါမှမဟုတ် generic plan တွေနဲ့ execute လုပ်နိုင်ပါတယ်။ Custom plan တွေက — execute လုပ်တိုင်း — သူ့ရဲ့ သီးခြား parameter တန်ဖိုး အစုနဲ့ အသစ် ပြန်လည် ဖန်တီးပါတယ်; generic plan တွေကတော့ parameter တန်ဖိုးတွေအပေါ် မမှီခိုဘဲ — execution တွေကြားမှာ ပြန်သုံး (re-use) နိုင်ပါတယ်။ ဒါကြောင့် — generic plan သုံးတာက planning time ကို သက်သာစေပေမယ့် — ideal plan က parameter တန်ဖိုးတွေအပေါ် ပြင်းပြင်းထန်ထန် မှီခိုနေရင် — generic plan တစ်ခုက မထိရောက်နိုင်ပါဘူး။ ဒီ option တွေကြားက ရွေးချယ်မှုကို ပုံမှန်အားဖြင့် အလိုအလျောက် ပြုလုပ်ပါတယ် — ဒါပေမယ့် plan_cache_mode နဲ့ override လုပ်နိုင်ပါတယ်။ ခွင့်ပြုတဲ့ တန်ဖိုးတွေကတော့ auto (default)၊ force_custom_plan နဲ့ force_generic_plan တို့ ဖြစ်ပါတယ်။ ဒီ setting ကို — plan တစ်ခုကို prepare လုပ်တဲ့အခါ မဟုတ်ဘဲ — cached plan တစ်ခုကို execute လုပ်တော့မယ့်အခါမှာ စဉ်းစားပါတယ်။ နောက်ထပ် အချက်အလက်အတွက် [PREPARE](/docs/postgresql/sql-prepare) ကို ကြည့်ပါ။
- **recursive_worktable_factor (floating point)** — Recursive query တစ်ခုရဲ့ working table ရဲ့ ပျမ်းမျှ အရွယ်အစားအပေါ် planner ရဲ့ ခန့်မှန်းချက်ကို — query ရဲ့ ကနဦး non-recursive term ခန့်မှန်း အရွယ်အစားရဲ့ အဆ (multiple) အဖြစ် — သတ်မှတ်ပါတယ်။ ဒါက working table ကို query ရဲ့ အခြား table တွေနဲ့ join လုပ်ဖို့ အသင့်လျော်ဆုံး နည်းလမ်းကို planner ရွေးချယ်နိုင်ဖို့ ကူညီပါတယ်။ Default တန်ဖိုးက 10.0 ဖြစ်ပါတယ်။ 1.0 ကဲ့သို့ ပိုသေးတဲ့ တန်ဖိုးက — shortest-path query တွေကဲ့သို့ — အဆင့်တစ်ခုကနေ နောက်တစ်ခုဆီ ရောက်တဲ့ “fan-out” နည်းတဲ့ recursion မှာ အထောက်အကူ ဖြစ်နိုင်ပါတယ်။ Graph analytics query တွေက default ထက် ကြီးတဲ့ တန်ဖိုးတွေကနေ အကျိုးအမြတ် ရနိုင်ပါတယ်။
