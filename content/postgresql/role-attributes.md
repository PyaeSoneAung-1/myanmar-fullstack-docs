## 21.2. Role Attributes (role ၏ attribute များ)

Database role တစ်ခုမှာ — ၎င်းရဲ့ privileges (အခွင့်အရေးများ) တွေကို သတ်မှတ်ပြီး client authentication system (client အထောက်အထား စိစစ်ရေး စနစ်) နဲ့ ဆက်စပ် အလုပ်လုပ်တဲ့ — attribute (role ၏ သတ်မှတ်ချက်များ) အများအပြား ရှိနိုင်ပါတယ်။

- **login privilege (log in လုပ်ပိုင်ခွင့်)** — LOGIN attribute ရှိတဲ့ roles တွေကိုပဲ — database connection တစ်ခုရဲ့ ကနဦး role name (အစပြု role အမည်) အဖြစ် သုံးလို့ ရပါတယ်။ LOGIN attribute ပါတဲ့ role တစ်ခုကို “database user” တစ်ယောက်နဲ့ အတူတူပဲလို့ မှတ်ယူလို့ ရပါတယ်။ Login privilege ပါတဲ့ role တစ်ခု ဖန်တီးဖို့ဆိုရင် — အောက်ပါ နှစ်ခုထဲက တစ်ခုကို သုံးပါ:

CREATE ROLE name LOGIN;
CREATE USER name;

(CREATE USER က CREATE ROLE နဲ့ ညီမျှပါတယ် — ဒါပေမယ့် CREATE USER က LOGIN ကို ပုံမှန် default အနေနဲ့ ထည့်သွင်းပေးပြီး — CREATE ROLE ကတော့ မထည့်ပေးပါဘူး။)
- **superuser status (superuser အဆင့်အတန်း)** — Database superuser တစ်ယောက်က — log in လုပ်ပိုင်ခွင့်ကလွဲပြီး — permission check (ခွင့်ပြုချက် စစ်ဆေးမှု) တွေ အားလုံးကို bypass (ကျော်လွှား) လုပ်ပါတယ်။ ဒါက အန္တရာယ် ရှိတဲ့ privilege တစ်ခု ဖြစ်လို့ — ပေါ့ပေါ့ဆဆတော့ မသုံးသင့်ပါဘူး; superuser မဟုတ်တဲ့ role တစ်ခုအနေနဲ့ ကိုယ့်အလုပ်အများစုကို လုပ်တာက အကောင်းဆုံး ဖြစ်ပါတယ်။ Database superuser အသစ်တစ်ယောက် ဖန်တီးဖို့ — CREATE ROLE name SUPERUSER ကို သုံးပါ။ ဒါကို superuser ဖြစ်နေပြီးသား role တစ်ခုအနေနဲ့ပဲ လုပ်ရမှာ ဖြစ်ပါတယ်။
- **database creation (database ဖန်တီးခွင့်)** — Role တစ်ခုကို — database ဖန်တီးခွင့် အတိအကျ ပေးထားရပါမယ် (superusers တွေကလွဲပြီး — သူတို့က permission check တွေ အားလုံးကို bypass လုပ်လို့ပါ)။ အဲဒီလို role တစ်ခု ဖန်တီးဖို့ — CREATE ROLE name CREATEDB ကို သုံးပါ။
- **role creation (role ဖန်တီးခွင့်)** — Role တစ်ခုကို — role အသစ်တွေ ဖန်တီးခွင့် အတိအကျ ပေးထားရပါမယ် (superusers တွေကလွဲပြီး — သူတို့က permission check တွေ အားလုံးကို bypass လုပ်လို့ပါ)။ အဲဒီလို role တစ်ခု ဖန်တီးဖို့ — CREATE ROLE name CREATEROLE ကို သုံးပါ။ CREATEROLE privilege ရှိတဲ့ role တစ်ခုက — ADMIN option နဲ့ CREATEROLE user ဆီ grant (ပေးအပ်) ထားတဲ့ roles တွေကို — alter လုပ်လို့ ရသလို drop လုပ်လို့လည်း ရပါတယ်။ ဒီလို grant မျိုးက — superuser မဟုတ်တဲ့ CREATEROLE user တစ်ယောက်က role အသစ်တစ်ခု ဖန်တီးတဲ့အခါ — အလိုအလျောက် ဖြစ်ပေါ်တာမို့ — ပုံမှန်အားဖြင့် CREATEROLE user တစ်ယောက်က သူ ဖန်တီးထားတဲ့ roles တွေကို alter ရော drop ပါ လုပ်နိုင်ပါတယ်။ Role တစ်ခုကို alter လုပ်တာမှာ — ALTER ROLE သုံးပြီး လုပ်လို့ရတဲ့ ပြောင်းလဲမှု အများစု ပါဝင်ပြီး — ဥပမာ — password တွေ ပြောင်းလဲတာ အပါအဝင် ဖြစ်ပါတယ်။ COMMENT နဲ့ SECURITY LABEL commands တွေ သုံးပြီး role တစ်ခုအပေါ် လုပ်လို့ရတဲ့ ပြုပြင်မွမ်းမံမှုတွေလည်း ပါဝင်ပါတယ်။
ဒါပေမယ့် — CREATEROLE က SUPERUSER roles တွေ ဖန်တီးနိုင်စွမ်းကို မပေးပါဘူး၊ ရှိပြီးသား SUPERUSER roles တွေအပေါ်မှာလည်း ဘယ်လို အာဏာမှ မပေးပါဘူး။ ထို့ပြင် — CREATEROLE က REPLICATION users တွေ ဖန်တီးနိုင်စွမ်း၊ REPLICATION privilege ကို grant ဒါမှမဟုတ် revoke လုပ်နိုင်စွမ်း၊ ဒါမှမဟုတ် အဲဒီလို users တွေရဲ့ role properties တွေကို ပြုပြင်နိုင်စွမ်းတွေကိုလည်း မပေးပါဘူး။ ဒါပေမယ့် — REPLICATION roles တွေအပေါ်မှာတော့ — ALTER ROLE ... SET နဲ့ ALTER ROLE ... RENAME တွေကို သုံးခွင့် ပေးထားသလို — COMMENT ON ROLE, SECURITY LABEL ON ROLE နဲ့ DROP ROLE တွေကိုပါ သုံးခွင့် ပေးပါတယ်။ နောက်ဆုံးအနေနဲ့ — CREATEROLE က BYPASSRLS privilege ကို grant ဒါမှမဟုတ် revoke လုပ်နိုင်စွမ်းကိုလည်း မပေးပါဘူး။
- **initiating replication (replication စတင်ခွင့်)** — Role တစ်ခုကို — streaming replication (stream လုပ်နေစဉ် ပုံတူပွားခြင်း) စတင်ခွင့် အတိအကျ ပေးထားရပါမယ် (superusers တွေကလွဲပြီး — သူတို့က permission check တွေ အားလုံးကို bypass လုပ်လို့ပါ)။ Streaming replication အတွက် သုံးမယ့် role မှာ LOGIN permission လည်း ရှိရပါမယ်။ အဲဒီလို role တစ်ခု ဖန်တီးဖို့ — CREATE ROLE name REPLICATION LOGIN ကို သုံးပါ။
- **password (password — စကားဝှက်)** — Password က — client authentication method က database ဆီ connect လုပ်တဲ့အခါ user ဆီကနေ password တစ်ခု ပေးသွင်းဖို့ လိုအပ်မှသာ — အဓိပ္ပာယ် ရှိပါတယ်။ password နဲ့ md5 authentication methods တွေက password တွေကို အသုံးပြုပါတယ်။ Database password တွေက operating system password တွေနဲ့ သီးခြားစီ ဖြစ်ပါတယ်။ Role ဖန်တီးတဲ့အခါ — CREATE ROLE name PASSWORD 'string' နဲ့ password ကို သတ်မှတ်နိုင်ပါတယ်။
- **inheritance of privileges (privilege များ အမွေဆက်ခံခြင်း)** — Role တစ်ခုက — သူ အဖွဲ့ဝင် ဖြစ်နေတဲ့ roles တွေရဲ့ privileges တွေကို — ပုံမှန်အားဖြင့် — inherit (အမွေဆက်ခံ) လုပ်ပါတယ်။ ဒါပေမယ့် — ပုံမှန်အားဖြင့် privileges တွေ inherit မလုပ်တဲ့ role တစ်ခု ဖန်တီးချင်ရင်တော့ — CREATE ROLE name NOINHERIT ကို သုံးပါ။ တနည်းအားဖြင့် — inheritance ကို grant တစ်ခုချင်းစီအတွက် — WITH INHERIT TRUE ဒါမှမဟုတ် WITH INHERIT FALSE သုံးပြီး — ပြောင်းလဲ (override) လုပ်လို့လည်း ရပါတယ်။
- **bypassing row-level security (row-level security ကို ကျော်လွှားခြင်း)** — Role တစ်ခုကို — row-level security (RLS — row အလိုက် လုံခြုံရေး) policy တိုင်းကို ကျော်လွှားခွင့် အတိအကျ ပေးထားရပါမယ် (superusers တွေကလွဲပြီး — သူတို့က permission check တွေ အားလုံးကို bypass လုပ်လို့ပါ)။ အဲဒီလို role တစ်ခု ဖန်တီးဖို့ — superuser တစ်ယောက်အနေနဲ့ CREATE ROLE name BYPASSRLS ကို သုံးပါ။
- **connection limit (connection အရေအတွက် ကန့်သတ်ချက်)** — Connection limit က — role တစ်ခုက တစ်ပြိုင်နက် (concurrent) connection ဘယ်နှစ်ခု လုပ်နိုင်လဲ သတ်မှတ်ပေးနိုင်ပါတယ်။ -1 (ပုံမှန် default) က ကန့်သတ်ချက် မရှိဘူးလို့ ဆိုလိုပါတယ်။ Role ဖန်တီးတဲ့အခါ connection limit သတ်မှတ်ဖို့ — CREATE ROLE name CONNECTION LIMIT 'integer' ကို သုံးပါ။

Role တစ်ခုရဲ့ attributes တွေကို ဖန်တီးပြီးနောက်မှာ `ALTER ROLE` နဲ့ ပြုပြင်မွမ်းမံလို့ ရပါတယ်။ အသေးစိတ်အတွက် [CREATE ROLE](/docs/postgresql/sql-createrole) နဲ့ [ALTER ROLE](/docs/postgresql/sql-alterrole) commands တွေရဲ့ reference pages တွေကို ကြည့်ပါ။

Role တစ်ခုမှာ — [အခန်း 19](https://www.postgresql.org/docs/current/runtime-config.html) မှာ ဖော်ပြထားတဲ့ run-time configuration settings (run နေစဉ် ပြောင်းလဲနိုင်သော ဆက်တင်များ) အများအပြားအတွက် — role-specific (role တစ်ခုချင်းစီ သီးသန့်) default တန်ဖိုးတွေလည်း ရှိနိုင်ပါတယ်။ ဥပမာ — တစ်ချို့ အကြောင်းကြောင်းကြောင့် index scans တွေကို ပိတ်ထားချင်တယ်ဆိုရင် (အရိပ်အမြွက်: ဒါက ကောင်းတဲ့ အကြံ မဟုတ်ပါဘူး) — connect လုပ်တိုင်း အောက်ပါအတိုင်း သုံးနိုင်ပါတယ်:

```sql
ALTER ROLE myname SET enable_indexscan TO off;
```

ဒါက setting ကို သိမ်းဆည်းပေးမှာ ဖြစ်ပြီး (ချက်ချင်းတော့ set လုပ်မပေးပါဘူး)။ ဒီ role နဲ့ နောက်ပိုင်း connection တွေမှာ — session မစတင်ခင် ခဏလေးမှာ `SET enable_indexscan TO off` ကို execute လုပ်ခဲ့သလိုမျိုး ပေါ်လာပါလိမ့်မယ်။ ဒီ setting ကို session အတွင်းမှာတော့ ဆက်ပြီး ပြောင်းလဲလို့ ရသေးပါတယ်; အဲဒါက default အနေနဲ့ပဲ ရှိနေမှာ ဖြစ်ပါတယ်။ Role-specific default setting တစ်ခုကို ဖယ်ရှားဖို့ — `ALTER ROLE rolename RESET varname` ကို သုံးပါ။ `LOGIN` privilege မရှိတဲ့ roles တွေမှာ ချိတ်ထားတဲ့ role-specific defaults တွေက — ဘယ်တော့မှ ခေါ်ယူ အသုံးပြုခံရမှာ မဟုတ်လို့ — အတော်လေး အသုံးမဝင်ဘူးဆိုတာ သတိပြုပါ။

Superuser မဟုတ်တဲ့သူတစ်ယောက်က `CREATEROLE` privilege သုံးပြီး role တစ်ခု ဖန်တီးတဲ့အခါ — ဖန်တီးလိုက်တဲ့ role ကို — bootstrap superuser (system စတင် တည်ဆောက်ချိန် ကနဦး superuser) က `GRANT created_user TO creating_user WITH ADMIN TRUE, SET FALSE, INHERIT FALSE` ဆိုတဲ့ command ကို execute လုပ်ခဲ့သလိုပဲ — ဖန်တီးသူ (creating user) ဆီကို အလိုအလျောက် ပြန်လည် grant လုပ်ပေးပါတယ်။ `CREATEROLE` user တစ်ယောက်က — ရှိပြီးသား role တစ်ခုအပေါ်မှာ သူ့မှာ `ADMIN OPTION` ရှိမှသာ — အထူး privileges တွေကို သုံးစွဲနိုင်တာမို့ — ဒီ grant က `CREATEROLE` user တစ်ယောက်ကို သူ ဖန်တီးထားတဲ့ roles တွေကို စီမံခန့်ခွဲခွင့် ပြုဖို့ အတိအကျ လုံလောက်ပါတယ်။ ဒါပေမယ့် — အဲဒါကို `INHERIT FALSE, SET FALSE` နဲ့ ဖန်တီးထားလို့ — `CREATEROLE` user က ဖန်တီးလိုက်တဲ့ role ရဲ့ privileges တွေကို inherit မလုပ်ရသလို — `SET ROLE` သုံးပြီးတော့လည်း အဲဒီ role ရဲ့ privileges တွေကို ဝင်ရောက် သုံးစွဲလို့ မရပါဘူး။ ဒါပေမယ့် — role တစ်ခုအပေါ်မှာ `ADMIN OPTION` ရှိတဲ့ user တိုင်းက အဲဒီ role ထဲက membership ကို တခြား user တိုင်းဆီ grant လုပ်နိုင်တာမို့ — `CREATEROLE` user က အဲဒီ role ကို `INHERIT` နဲ့/သို့မဟုတ် `SET` options တွေနဲ့ ကိုယ့်ကိုယ်ကိုယ် ပြန် grant လုပ်ရုံနဲ့တင် — ဖန်တီးထားတဲ့ role ဆီကို ဝင်ရောက်ခွင့် ရနိုင်ပါတယ်။ ဒါကြောင့် — privileges တွေကို ပုံမှန်အားဖြင့် inherit မလုပ်ရတာ ရော `SET ROLE` ကိုပါ ပုံမှန်အားဖြင့် grant မလုပ်ပေးတာရဲ့ အချက်ကတော့ — လုံခြုံရေး အင်္ဂါရပ် (security feature) တစ်ခု မဟုတ်ဘဲ — မတော်တဆ ဖြစ်ရပ်တွေကနေ ကာကွယ်ပေးတဲ့ အစောင့်အရှောက် (safeguard) တစ်ခုပဲ ဖြစ်ပါတယ်။ ဒါ့အပြင် — ဒီအလိုအလျောက် grant ကို bootstrap superuser က ပေးအပ်ထားတာမို့ — `CREATEROLE` user က ဖယ်ရှားလို့ရော ပြောင်းလဲလို့ပါ မရဘူးဆိုတာလည်း သတိပြုပါ; ဒါပေမယ့် — superuser တစ်ယောက်ယောက်ကတော့ အဲဒါကို revoke လုပ်တာ၊ ပြုပြင်တာ၊ နဲ့/သို့မဟုတ် တခြား `CREATEROLE` users တွေဆီ ဒီလို ထပ်ဆောင်း grants တွေ ထုတ်ပေးတာတွေ လုပ်နိုင်ပါတယ်။ ဘယ်အချိန်မှာမဆို — role တစ်ခုအပေါ်မှာ `ADMIN OPTION` ရှိနေတဲ့ `CREATEROLE` users တွေ ဘယ်သူမဆို — အဲဒီ role ကို စီမံခန့်ခွဲနိုင်ပါတယ်။
