### 19.5.1. Settings (ဆက်တင်များ)

- **wal_level (enum)** — `wal_level` က WAL ထဲကို အချက်အလက် ဘယ်လောက် ရေးသားမလဲ ဆိုတာ ဆုံးဖြတ်ပါတယ်။ Default တန်ဖိုးက `replica` ဖြစ်ပြီး — WAL archiving နဲ့ replication ကို ထောက်ပံ့ဖို့ လုံလောက်တဲ့ data ကို ရေးသားပေးပါတယ် — standby server ပေါ်မှာ read-only query များ run ခြင်းအပါအဝင်ပါ။ `minimal` ကတော့ crash ဒါမှမဟုတ် immediate shutdown ကနေ ပြန်လည် ကုစားဖို့ လိုအပ်တဲ့ အချက်အလက်မှလွဲပြီး log အားလုံးကို ဖယ်ရှားပါတယ်။ နောက်ဆုံးအနေနဲ့ `logical` က logical decoding ကို ထောက်ပံ့ဖို့ လိုအပ်တဲ့ အချက်အလက်ကို ထပ်ထည့်ပေးပါတယ်။ level တစ်ခုချင်းစီမှာ အောက် level များအားလုံးမှာ log လုပ်တဲ့ အချက်အလက်များ ပါဝင်ပါတယ်။ ဒီ parameter ကို server စတင်တဲ့အခါမှသာ သတ်မှတ်နိုင်ပါတယ်။
`minimal` level က WAL ပမာဏ အနည်းဆုံး ထုတ်လုပ်ပါတယ်။ permanent relation တွေကို ဖန်တီးတဲ့ ဒါမှမဟုတ် ပြန်လည် ရေးသားတဲ့ transaction များမှာ — အဲဒီ relation များအတွက် row အချက်အလက်ကို log မလုပ်ပါဘူး။ ဒါက လုပ်ဆောင်ချက်များကို အများကြီး ပိုမြန်စေနိုင်ပါတယ် (အပိုင်း 14.4.7 ကို ကြည့်ပါ)။ ဒီ optimization ကို စတင်စေတဲ့ လုပ်ဆောင်ချက်များ ပါဝင်တာက:
- `ALTER ... SET TABLESPACE`
- `CLUSTER`
- `CREATE TABLE`
- `REFRESH MATERIALIZED VIEW` (without `CONCURRENTLY`)
- `REINDEX`
- `TRUNCATE`
ဒါပေမယ့် — minimal WAL မှာ point-in-time recovery အတွက် လုံလောက်တဲ့ အချက်အလက် မပါဝင်ပါဘူး; ဒါကြောင့် continuous archiving (`archive_mode`) နဲ့ streaming binary replication ကို enable လုပ်ဖို့ `replica` ဒါမှမဟုတ် အထက် level ကို သုံးရပါမယ်။ တကယ်တော့ — `max_wal_senders` က သုည မဟုတ်ရင် — server က ဒီ mode နဲ့ စတောင် မစတင်နိုင်ပါဘူး။ `wal_level` ကို `minimal` သို့ ပြောင်းလဲခြင်းက — အရင် base backup များကို point-in-time recovery နဲ့ standby server များအတွက် အသုံးမဝင် ဖြစ်စေပါတယ် ဆိုတာ သတိပြုပါ။
`logical` level မှာ — `replica` နဲ့ အတူတူ အချက်အလက်ကို log လုပ်ပြီး — WAL ကနေ logical change set များ ထုတ်ယူဖို့ လိုအပ်တဲ့ အချက်အလက်ကို ထပ်ထည့်ပါတယ်။ `logical` level ကို သုံးခြင်းက WAL ပမာဏကို တိုးစေပါတယ် — အထူးသဖြင့် table အများအပြားကို `REPLICA IDENTITY FULL` အတွက် configure လုပ်ထားပြီး `UPDATE` နဲ့ `DELETE` statement အများအပြား လုပ်ဆောင်တဲ့အခါ ပိုတိုးပါတယ်။
9.6 မတိုင်မီ release များမှာ — ဒီ parameter က `archive` နဲ့ `hot_standby` တန်ဖိုးများကိုလည်း ခွင့်ပြုခဲ့ပါတယ်။ ဒါတွေကို လက်ခံနေဆဲ ဖြစ်ပေမယ့် `replica` သို့ map လုပ်ထားပါတယ်။
- **fsync (boolean)** — ဒီ parameter က on ဖြစ်နေရင် — PostgreSQL server က `fsync()` system call များ ဒါမှမဟုတ် သူနဲ့ တူညီတဲ့ နည်းလမ်းအမျိုးမျိုး (`wal_sync_method` ကို ကြည့်ပါ) ထုတ်ပြီး — update များကို disk ဆီ တကယ် ရေးသားကြောင်း သေချာအောင် ကြိုးစားပါတယ်။ ဒါက operating system ဒါမှမဟုတ် hardware crash ဖြစ်ပြီးနောက် database cluster ကို ညီညွတ်တဲ့ အခြေအနေ (consistent state) ဆီ ပြန်လည် ကုစားနိုင်ကြောင်း အာမခံပါတယ်။
`fsync` ကို ပိတ်ခြင်းက performance အကျိုးအမြတ် ဖြစ်တတ်ပေမယ့် — ပါဝါ ပြတ်တောက်မှု ဒါမှမဟုတ် system crash ဖြစ်တဲ့အခါ — ပြန်လည် ကုစားလို့ မရနိုင်တဲ့ data ပျက်စီးမှု (unrecoverable data corruption) ဖြစ်စေနိုင်ပါတယ်။ ဒါကြောင့် — သင့် database တစ်ခုလုံးကို ပြင်ပ data ကနေ အလွယ်တကူ ပြန်လည် ဖန်တီးနိုင်မှသာ `fsync` ကို ပိတ်သင့်ပါတယ်။
`fsync` ပိတ်ဖို့ လုံခြုံတဲ့ အခြေအနေ ဥပမာများမှာ — backup file ကနေ database cluster အသစ်တစ်ခုကို ကနဦး load လုပ်ခြင်း၊ ပြီးရင် ဖျက်ပြီး ပြန်ဖန်တီးမယ့် data အစုတစ်ခုကို လုပ်ဆောင်ဖို့ database cluster တစ်ခုကို အသုံးပြုခြင်း၊ ဒါမှမဟုတ် — မကြာခဏ ပြန်လည် ဖန်တီးပြီး failover အတွက် မသုံးတဲ့ read-only database clone တစ်ခုအတွက် အသုံးပြုခြင်း တို့ ပါဝင်ပါတယ်။ အရည်အသွေး မြင့်မားတဲ့ hardware ကောင်းတာတစ်ခုတည်းနဲ့တော့ `fsync` ပိတ်ဖို့ လုံလောက်တဲ့ အကြောင်းပြချက် မဟုတ်ပါဘူး။
`fsync` ကို off ကနေ on ပြောင်းတဲ့အခါ ယုံကြည်စိတ်ချရတဲ့ recovery ရဖို့ — kernel ထဲက ပြင်ဆင်ထားတဲ့ buffer အားလုံးကို durable storage ဆီ အတင်းအကျပ် ရောက်စေဖို့ လိုပါတယ်။ ဒါကို cluster ပိတ်ထားချိန် ဒါမှမဟုတ် `fsync` on ဖြစ်နေချိန်မှာ — `initdb --sync-only` run ခြင်း၊ `sync` run ခြင်း၊ file system ကို unmount လုပ်ခြင်း၊ ဒါမှမဟုတ် server ကို reboot လုပ်ခြင်းဖြင့် လုပ်နိုင်ပါတယ်။
အခြေအနေ အများအပြားမှာ — အရေးမကြီးတဲ့ transaction များအတွက် `synchronous_commit` ကို ပိတ်ခြင်းက — `fsync` ပိတ်ခြင်းရဲ့ performance အကျိုးအမြတ် အများအပြားကို — data ပျက်စီးမှု အန္တရာယ်များ မပါဘဲ — ပေးနိုင်ပါတယ်။
`fsync` ကို `postgresql.conf` file ထဲမှာ ဒါမှမဟုတ် server command line ပေါ်မှာသာ သတ်မှတ်နိုင်ပါတယ်။ ဒီ parameter ကို ပိတ်ထားရင် — `full_page_writes` ကိုလည်း ပိတ်ဖို့ စဉ်းစားပါ။
- **synchronous_commit (enum)** — Database server က client ဆီ “success” အချက်ပြ မပြန်မီ — WAL လုပ်ဆောင်မှု ဘယ်လောက် ပြီးစီးရမလဲ ဆိုတာ သတ်မှတ်ပါတယ်။ ဖြစ်နိုင်တဲ့ တန်ဖိုးများက `remote_apply`၊ `on` (default)၊ `remote_write`၊ `local` နဲ့ `off` ဖြစ်ပါတယ်။
`synchronous_standby_names` က အလွတ် (empty) ဖြစ်နေရင် — အဓိပ္ပာယ် ရှိတဲ့ setting များက `on` နဲ့ `off` ပဲ ဖြစ်ပါတယ်; `remote_apply`၊ `remote_write` နဲ့ `local` တို့က `on` နဲ့ အတူတူ local synchronization အဆင့်ကို ပေးပါတယ်။ `off` မဟုတ်တဲ့ mode အားလုံးရဲ့ local အပြုအမူက — WAL ကို disk ဆီ locally flush လုပ်တာကို စောင့်ဆိုင်းခြင်း ဖြစ်ပါတယ်။ `off` mode မှာတော့ စောင့်ဆိုင်းတာ မရှိပါဘူး; ဒါကြောင့် — client ဆီ success သတင်းပို့တဲ့ အချိန်နဲ့ — transaction က server crash ကို ခံနိုင်တယ်လို့ နောက်ပိုင်း အာမခံနိုင်တဲ့ အချိန် အကြားမှာ နှောင့်နှေးမှု ရှိနိုင်ပါတယ်။ (အများဆုံး နှောင့်နှေးမှုက `wal_writer_delay` ရဲ့ သုံးဆ ဖြစ်ပါတယ်။) `fsync` နဲ့ မတူဘဲ — ဒီ parameter ကို `off` သတ်မှတ်ခြင်းက database မညီညွတ်မှု အန္တရာယ် မဖြစ်စေပါဘူး: operating system ဒါမှမဟုတ် database crash ဖြစ်ရင် — commit ဖြစ်ပြီလို့ ဆိုထားတဲ့ မကြာသေးမီ transaction အချို့ ဆုံးရှုံးနိုင်ပေမယ့် — database အခြေအနေက အဲဒီ transaction များကို သန့်ရှင်းစွာ abort လုပ်ခဲ့သလိုပဲ ဖြစ်ပါလိမ့်မယ်။ ဒါကြောင့် — transaction တစ်ခုရဲ့ တည်မြဲမှု (durability) ကို အတိအကျ သေချာစေတာထက် performance ကို ပိုအရေးထားတဲ့အခါ — `synchronous_commit` ကို off လုပ်ခြင်းက အသုံးဝင်တဲ့ အစားထိုး နည်းလမ်း ဖြစ်နိုင်ပါတယ်။ ပိုမို ဆွေးနွေးချက်အတွက် အပိုင်း 28.4 ကို ကြည့်ပါ။
`synchronous_standby_names` က အလွတ် မဟုတ်ရင် — `synchronous_commit` က — transaction commit များက standby server(s) ပေါ်မှာ သူတို့ရဲ့ WAL record များ လုပ်ဆောင်ပြီးတဲ့အထိ စောင့်ဆိုင်းမလား ဆိုတာကိုလည်း ထိန်းချုပ်ပါတယ်။
`remote_apply` လို့ သတ်မှတ်ထားတဲ့အခါ — commit များက — လက်ရှိ synchronous standby(s) ဆီကနေ — transaction ရဲ့ commit record ကို လက်ခံရရှိပြီး သူ့ကို apply လုပ်ပြီးကြောင်း (ဒါကြောင့် standby(s) ပေါ်က query များအတွက် မြင်နိုင်ဖြစ်လာပြီး standbys ပေါ်က durable storage ဆီလည်း ရေးသားပြီးကြောင်း) အကြောင်းပြန်တဲ့အထိ စောင့်ဆိုင်းပါတယ်။ ဒါက WAL replay ကို စောင့်ဆိုင်းတာမို့ — အရင် setting များထက် commit နှောင့်နှေးမှု အများကြီး ပိုကြီးစေပါတယ်။ `on` လို့ သတ်မှတ်ထားတဲ့အခါ — commit များက — လက်ရှိ synchronous standby(s) ဆီကနေ — transaction ရဲ့ commit record ကို လက်ခံရရှိပြီး durable storage ဆီ flush လုပ်ပြီးကြောင်း အကြောင်းပြန်တဲ့အထိ စောင့်ဆိုင်းပါတယ်။ ဒါက — primary ရော synchronous standby အားလုံးပါ သူတို့ရဲ့ database storage ပျက်စီးမှု (corruption) မခံရရင် — transaction ဆုံးရှုံးမှာ မဟုတ်ကြောင်း အာမခံပါတယ်။ `remote_write` လို့ သတ်မှတ်ထားတဲ့အခါ — commit များက — လက်ရှိ synchronous standby(s) ဆီကနေ — transaction ရဲ့ commit record ကို လက်ခံရရှိပြီး သူတို့ရဲ့ file system ဆီ ရေးသားပြီးကြောင်း အကြောင်းပြန်တဲ့အထိ စောင့်ဆိုင်းပါတယ်။ ဒီ setting က — PostgreSQL ရဲ့ standby instance တစ်ခု crash ဖြစ်ရင် data ထိန်းသိမ်းမှုကို အာမခံပေမယ့် — standby က operating-system အဆင့် crash ခံရရင်တော့ မအာမခံပါဘူး — အကြောင်းကတော့ data က standby ပေါ်က durable storage ဆီ မရောက်သေးနိုင်လို့ပါ။ `local` setting က — commit များကို disk ဆီ local flush လုပ်တာအထိ စောင့်ဆိုင်းစေပေမယ့် — replication အတွက် မစောင့်ဆိုင်းပါဘူး။ ဒါက synchronous replication သုံးနေတဲ့အခါ ပုံမှန်အားဖြင့် မလိုလားအပ်ပေမယ့် — ပြည့်စုံစေဖို့ ပေးထားတာပါ။
ဒီ parameter ကို အချိန်မရွေး ပြောင်းနိုင်ပါတယ်; transaction တစ်ခုအတွက် အပြုအမူက — သူ commit လုပ်တဲ့အခါ အာဏာတည်နေတဲ့ setting က ဆုံးဖြတ်ပါတယ်။ ဒါကြောင့် — transaction အချို့ကို synchronously နဲ့ တချို့ကို asynchronously commit လုပ်စေတာ ဖြစ်နိုင်ပြီး အသုံးဝင်ပါတယ်။ ဥပမာ — default က ဆန့်ကျင်ဘက် ဖြစ်နေချိန်မှာ — multistatement transaction တစ်ခုတည်းကို asynchronously commit စေဖို့ — transaction အတွင်းမှာ `SET LOCAL synchronous_commit TO OFF` ကို ထုတ်ပါ။

- **wal_sync_method (enum)** — WAL update များကို disk ဆီ အတင်းအကျပ် ထုတ်ရေးဖို့ သုံးတဲ့ နည်းလမ်း ဖြစ်ပါတယ်။ `fsync` က off ဖြစ်နေရင် — WAL file update များကို လုံးဝ အတင်းအကျပ် မထုတ်ရေးတာမို့ — ဒီ setting က အရေးမပါတော့ပါဘူး။ ဖြစ်နိုင်တဲ့ တန်ဖိုးများက:
- `open_datasync` (WAL file များကို `open()` ရဲ့ `O_DSYNC` option နဲ့ ရေးသားခြင်း)
- `fdatasync` (commit တစ်ခုချင်းစီမှာ `fdatasync()` ကို ခေါ်ခြင်း)
- `fsync` (commit တစ်ခုချင်းစီမှာ `fsync()` ကို ခေါ်ခြင်း)
- `fsync_writethrough` (commit တစ်ခုချင်းစီမှာ `fsync()` ကို ခေါ်ပြီး — disk write cache ရှိသမျှကို write-through အတင်းအကျပ် လုပ်ခြင်း)
- `open_sync` (WAL file များကို `open()` ရဲ့ `O_SYNC` option နဲ့ ရေးသားခြင်း)
ဒီရွေးချယ်မှု အားလုံးက platform အားလုံးမှာ ရနိုင်တာ မဟုတ်ပါဘူး။ Default က — platform က ထောက်ပံ့တဲ့ — အပေါ်စာရင်းထဲက ပထမဆုံး နည်းလမ်း ဖြစ်ပါတယ် — ဒါပေမယ့် Linux နဲ့ FreeBSD မှာတော့ `fdatasync` က default ဖြစ်ပါတယ်။ Default က အကောင်းဆုံး ဖြစ်ချင်မှ ဖြစ်ပါလိမ့်မယ်; crash-safe configuration တစ်ခု ဖန်တီးဖို့ ဒါမှမဟုတ် အကောင်းဆုံး performance ရဖို့ — ဒီ setting ဒါမှမဟုတ် သင့် system configuration ရဲ့ အခြား အချက်များကို ပြောင်းလဲဖို့ လိုအပ်နိုင်ပါတယ်။ ဒီအချက်များကို အပိုင်း 28.1 မှာ ဆွေးနွေးထားပါတယ်။ ဒီ parameter ကို `postgresql.conf` file ထဲမှာ ဒါမှမဟုတ် server command line ပေါ်မှာသာ သတ်မှတ်နိုင်ပါတယ်။
- **full_page_writes (boolean)** — ဒီ parameter က on ဖြစ်နေရင် — PostgreSQL server က — checkpoint တစ်ခုပြီးနောက် page တစ်ခုကို ပထမဆုံး ပြင်ဆင်တဲ့အခါ — disk page တစ်ခုချင်းစီရဲ့ အကြောင်းအရာ တစ်ခုလုံးကို WAL ဆီ ရေးသားပါတယ်။ Operating system crash ဖြစ်နေစဉ်အတွင်း လုပ်ဆောင်နေတဲ့ page write တစ်ခုက တစ်စိတ်တစ်ပိုင်းသာ ပြီးစီးခဲ့နိုင်ပြီး — disk ပေါ်က page မှာ data အဟောင်းနဲ့ အသစ် ရောနှောနေနိုင်တာမို့ ဒါက လိုအပ်ပါတယ်။ WAL မှာ ပုံမှန် သိမ်းဆည်းတဲ့ row-level change data က — crash ပြီးနောက် recovery အတွင်း — ဒီလို page ကို လုံးဝ ပြန်လည် ရယူဖို့ မလုံလောက်ပါဘူး။ Full page image ကို သိမ်းဆည်းခြင်းက page ကို မှန်ကန်စွာ ပြန်လည် ရယူနိုင်ကြောင်း အာမခံပေမယ့် — WAL ဆီ ရေးရမယ့် data ပမာဏ တိုးလာတဲ့ အဖိုးအခနဲ့ပါ။ (WAL replay က checkpoint ကနေ အမြဲ စတာမို့ — checkpoint တစ်ခုပြီးနောက် page တစ်ခုချင်းစီရဲ့ ပထမဆုံး ပြောင်းလဲမှုအတွင်း ဒါကို လုပ်ရုံနဲ့ လုံလောက်ပါတယ်။ ဒါကြောင့် — full-page write များရဲ့ ကုန်ကျစရိတ်ကို လျှော့ချဖို့ နည်းလမ်းတစ်ခုက checkpoint interval parameter များကို တိုးခြင်း ဖြစ်ပါတယ်။)
ဒီ parameter ကို ပိတ်ခြင်းက ပုံမှန် လည်ပတ်မှုကို မြန်စေပေမယ့် — system ပျက်ကွက်မှု (failure) တစ်ခုပြီးနောက် — ပြန်လည် ကုစားလို့ မရနိုင်တဲ့ data ပျက်စီးမှု ဒါမှမဟုတ် တိတ်ဆိတ်စွာ ဖြစ်ပွားတဲ့ data ပျက်စီးမှု (silent data corruption) ကို ဖြစ်စေနိုင်ပါတယ်။ အန္တရာယ်များက `fsync` ပိတ်ခြင်းနဲ့ ဆင်တူပေမယ့် ပိုငယ်ပါတယ်; ပြီးတော့ အဲဒီ parameter အတွက် အကြံပြုထားတဲ့ အခြေအနေမျိုးမှာသာ ဒါကို ပိတ်သင့်ပါတယ်။
ဒီ parameter ကို ပိတ်ခြင်းက — point-in-time recovery (PITR) အတွက် WAL archiving အသုံးပြုခြင်းကို မသက်ရောက်ပါဘူး (အပိုင်း 25.3 ကို ကြည့်ပါ)။
ဒီ parameter ကို `postgresql.conf` file ထဲမှာ ဒါမှမဟုတ် server command line ပေါ်မှာသာ သတ်မှတ်နိုင်ပါတယ်။ Default က `on` ဖြစ်ပါတယ်။
- **wal_log_hints (boolean)** — ဒီ parameter က on ဖြစ်နေရင် — PostgreSQL server က — checkpoint တစ်ခုပြီးနောက် page တစ်ခုကို ပထမဆုံး ပြင်ဆင်တဲ့အခါ — hint bit လို့ ခေါ်တဲ့ အရေးမကြီးတဲ့ ပြင်ဆင်မှုများအတွက်တောင် — disk page တစ်ခုချင်းစီရဲ့ အကြောင်းအရာ တစ်ခုလုံးကို WAL ဆီ ရေးသားပါတယ်။
Data checksum များ enable ဖြစ်ထားရင် — hint bit update များကို အမြဲ WAL-log လုပ်ပြီး ဒီ setting ကို လျစ်လျူရှုပါတယ်။ သင့် database မှာ data checksum enable ထားခဲ့ရင် WAL-logging အပို ဘယ်လောက် ဖြစ်လာမလဲ စမ်းသပ်ဖို့ ဒီ setting ကို သုံးနိုင်ပါတယ်။
ဒီ parameter ကို server စတင်တဲ့အခါမှသာ သတ်မှတ်နိုင်ပါတယ်။ Default တန်ဖိုးက `off` ဖြစ်ပါတယ်။
- **wal_compression (enum)** — ဒီ parameter က သတ်မှတ်ထားတဲ့ compression method ကို သုံးပြီး WAL ကို compress လုပ်ခြင်းကို enable လုပ်ပါတယ်။ Enable လုပ်ထားရင် — PostgreSQL server က WAL ဆီ ရေးသားတဲ့ full page image များကို compress လုပ်ပါတယ် (ဥပမာ — `full_page_writes` on ဖြစ်နေချိန်၊ base backup လုပ်နေစဉ် စသည်)။ Compress လုပ်ထားတဲ့ page image ကို WAL replay အတွင်း decompress လုပ်ပါလိမ့်မယ်။ ထောက်ပံ့တဲ့ နည်းလမ်းများက `pglz`၊ `lz4` (PostgreSQL ကို `--with-lz4` နဲ့ compile လုပ်ခဲ့ရင်) နဲ့ `zstd` (PostgreSQL ကို `--with-zstd` နဲ့ compile လုပ်ခဲ့ရင်) ဖြစ်ပါတယ်။ `on` တန်ဖိုးက `pglz` ရဲ့ သမိုင်းဝင် စာလုံးပေါင်း ဖြစ်ပါတယ်။ Default တန်ဖိုးက `off` ဖြစ်ပါတယ်။ သင့်လျော်တဲ့ `SET` privilege ရှိတဲ့ superuser များနဲ့ user များသာ ဒီ setting ကို ပြောင်းနိုင်ပါတယ်။
Compression enable လုပ်ခြင်းက — ပြန်လည် ကုစားလို့ မရနိုင်တဲ့ data ပျက်စီးမှု အန္တရာယ် မတိုးစေဘဲ — WAL ပမာဏကို လျော့ချနိုင်ပါတယ် — ဒါပေမယ့် WAL logging အတွင်း compression အတွက်ရော WAL replay အတွင်း decompression အတွက်ပါ အပို CPU အနည်းငယ် ကုန်ကျတဲ့ အပေးအယူနဲ့ပါ။
- **wal_init_zero (boolean)** — `on` (default) လို့ သတ်မှတ်ထားရင် — ဒီ option က WAL file အသစ်များကို သုည (zeroes) နဲ့ ဖြည့်စေပါတယ်။ File system တချို့မှာ — ဒါက WAL record များ မရေးမီ နေရာ (space) ကို ကြိုတင် ခွဲဝေထားကြောင်း သေချာစေပါတယ်။ ဒါပေမယ့် — Copy-On-Write (COW) file system များက ဒီနည်းပညာကနေ အကျိုးအမြတ် မရနိုင်ပါဘူး; ဒါကြောင့် မလိုအပ်တဲ့ အလုပ်ကို ကျော်လွှားဖို့ ဒီ option ကို ပေးထားတာပါ။ `off` လို့ သတ်မှတ်ထားရင် — file ဖန်တီးတဲ့အခါ နောက်ဆုံး byte ကိုသာ ရေးသားပြီး — မျှော်မှန်းထားတဲ့ အရွယ်အစား ရှိစေပါတယ်။
- **wal_recycle (boolean)** — `on` (default) လို့ သတ်မှတ်ထားရင် — ဒီ option က WAL file များကို နာမည်ပြောင်းခြင်းဖြင့် recycle လုပ်စေပြီး — အသစ်များ ဖန်တီးရ မလိုတော့ပါဘူး။ COW file system များမှာ အသစ် ဖန်တီးတာက ပိုမြန်နိုင်တာမို့ — ဒီအပြုအမူကို disable လုပ်ဖို့ ဒီ option ကို ပေးထားတာပါ။
- **wal_buffers (integer)** — Disk ဆီ မရေးရသေးတဲ့ WAL data အတွက် သုံးတဲ့ shared memory ပမာဏ ဖြစ်ပါတယ်။ Default setting ဖြစ်တဲ့ -1 က — `shared_buffers` ရဲ့ 1/32 (၃% ခန့်) နဲ့ ညီတဲ့ အရွယ်အစားကို ရွေးပေမယ့် — `64kB` ထက် မနည်းစေဘဲ — WAL segment တစ်ခုရဲ့ အရွယ်အစား (ပုံမှန်အားဖြင့် `16MB`) ထက် မပိုစေပါဘူး။ အလိုအလျောက် ရွေးချယ်မှုက အရမ်းကြီး ဒါမှမဟုတ် အရမ်းငယ်နေရင် — ဒီတန်ဖိုးကို လက်ဖြင့် သတ်မှတ်နိုင်ပေမယ့် — `32kB` ထက် ငယ်တဲ့ အပေါင်း တန်ဖိုး တစ်ခုခုကို `32kB` လို့ သဘောထားပါတယ်။ ဒီတန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် WAL block များ (ဆိုလိုတာက `XLOG_BLCKSZ` bytes၊ ပုံမှန်အားဖြင့် 8kB) လို့ ယူပါတယ်။ ဒီ parameter ကို server စတင်တဲ့အခါမှသာ သတ်မှတ်နိုင်ပါတယ်။
WAL buffer များရဲ့ အကြောင်းအရာများကို transaction commit တိုင်းမှာ disk ဆီ ရေးသားတာမို့ — အလွန်အမင်း ကြီးတဲ့ တန်ဖိုးများက သိသာတဲ့ အကျိုးအမြတ် ပေးနိုင်ခြေ မရှိပါဘူး။ ဒါပေမယ့် — ဒီတန်ဖိုးကို အနည်းဆုံး megabyte အနည်းငယ်အထိ သတ်မှတ်ခြင်းက — client အများအပြား တစ်ပြိုင်နက် commit လုပ်နေတဲ့ အလုပ်ရှုပ်တဲ့ server ပေါ်မှာ write performance ကို တိုးတက်စေနိုင်ပါတယ်။ Default setting ဖြစ်တဲ့ -1 က ရွေးချယ်တဲ့ auto-tuning က အခြေအနေ အများစုမှာ သင့်လျော်တဲ့ ရလဒ် ပေးသင့်ပါတယ်။
- **wal_writer_delay (integer)** — WAL writer က WAL ကို ဘယ်နှစ်ခါတစ်ကြိမ် flush လုပ်မလဲ (အချိန်အားဖြင့်) သတ်မှတ်ပါတယ်။ WAL ကို flush လုပ်ပြီးနောက် — asynchronously commit လုပ်နေတဲ့ transaction တစ်ခုက စောစော နှိုးမလာရင် — writer က `wal_writer_delay` ပေးတဲ့ အချိန်အတိုင်း အိပ်ပါတယ်။ နောက်ဆုံး flush လုပ်ခဲ့တာ `wal_writer_delay` ထက် နည်းပြီး — ထိုကတည်းက `wal_writer_flush_after` ပမာဏထက် WAL နည်းနည်းသာ ထုတ်လုပ်ခဲ့ရင် — WAL ကို operating system ဆီသာ ရေးသားပြီး disk ဆီ flush မလုပ်ပါဘူး။ ဒီတန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် milliseconds လို့ ယူပါတယ်။ Default တန်ဖိုးက 200 milliseconds (`200ms`) ဖြစ်ပါတယ်။ System တချို့မှာ sleep delay ရဲ့ ထိရောက်တဲ့ resolution က 10 milliseconds ဖြစ်တယ်ဆိုတာ သတိပြုပါ; `wal_writer_delay` ကို 10 ရဲ့ ဆတိုး မဟုတ်တဲ့ တန်ဖိုးတစ်ခု သတ်မှတ်တာက — 10 ရဲ့ နောက် ပိုကြီးတဲ့ ဆတိုးကို သတ်မှတ်သလိုပဲ ရလဒ် ဖြစ်နိုင်ပါတယ်။ ဒီ parameter ကို `postgresql.conf` file ထဲမှာ ဒါမှမဟုတ် server command line ပေါ်မှာသာ သတ်မှတ်နိုင်ပါတယ်။
- **wal_writer_flush_after (integer)** — WAL writer က WAL ကို ဘယ်နှစ်ခါတစ်ကြိမ် flush လုပ်မလဲ (ပမာဏအားဖြင့်) သတ်မှတ်ပါတယ်။ နောက်ဆုံး flush လုပ်ခဲ့တာ `wal_writer_delay` ထက် နည်းပြီး — ထိုကတည်းက `wal_writer_flush_after` ပမာဏထက် WAL နည်းနည်းသာ ထုတ်လုပ်ခဲ့ရင် — WAL ကို operating system ဆီသာ ရေးသားပြီး disk ဆီ flush မလုပ်ပါဘူး။ `wal_writer_flush_after` ကို 0 သတ်မှတ်ထားရင် — WAL data ကို အမြဲ ချက်ချင်း flush လုပ်ပါတယ်။ ဒီတန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် WAL block များ (ဆိုလိုတာက `XLOG_BLCKSZ` bytes၊ ပုံမှန်အားဖြင့် 8kB) လို့ ယူပါတယ်။ Default က `1MB` ဖြစ်ပါတယ်။ ဒီ parameter ကို `postgresql.conf` file ထဲမှာ ဒါမှမဟုတ် server command line ပေါ်မှာသာ သတ်မှတ်နိုင်ပါတယ်။
- **wal_skip_threshold (integer)** — `wal_level` က `minimal` ဖြစ်ပြီး — transaction တစ်ခုက permanent relation တစ်ခုကို ဖန်တီးပြီး ဒါမှမဟုတ် ပြန်လည် ရေးသားပြီးနောက် commit လုပ်တဲ့အခါ — ဒီ setting က data အသစ်ကို ဘယ်လို တည်မြဲအောင် (persist) လုပ်မလဲ ဆုံးဖြတ်ပါတယ်။ Data က ဒီ setting ထက် ငယ်ရင် — WAL log ဆီ ရေးသားပါ; မဟုတ်ရင် — သက်ဆိုင်တဲ့ file များကို `fsync` လုပ်ပါ။ သင့် storage ရဲ့ ဂုဏ်သတ္တိများပေါ် မူတည်ပြီး — ဒီလို commit များက concurrent transaction များကို နှေးကွေးစေနေရင် — ဒီတန်ဖိုးကို တင်ခြင်း ဒါမှမဟုတ် လျှော့ခြင်းက အထောက်အကူ ဖြစ်နိုင်ပါတယ်။ ဒီတန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် kilobytes လို့ ယူပါတယ်။ Default က two megabytes (`2MB`) ဖြစ်ပါတယ်။
- **commit_delay (integer)** — `commit_delay` သတ်မှတ်ခြင်းက — WAL flush မစတင်မီ — အချိန် နှောင့်နှေးမှု (time delay) တစ်ခု ထည့်ပါတယ်။ System load က မြင့်လွန်းလို့ သတ်မှတ်ထားတဲ့ ကာလအတွင်း နောက် transaction များ commit လုပ်ဖို့ အသင့် ဖြစ်လာနိုင်ရင် — ဒါက transaction အရေအတွက် ပိုများတာကို WAL flush တစ်ကြိမ်တည်းနဲ့ commit လုပ်စေခြင်းဖြင့် group commit throughput ကို တိုးတက်စေနိုင်ပါတယ်။ ဒါပေမယ့် — WAL flush တစ်ကြိမ်ချင်းစီအတွက် latency ကို `commit_delay` အထိ တိုးစေပါတယ်။ အခြား transaction များ commit လုပ်ဖို့ အသင့် မဖြစ်လာရင် delay က အလဟသ ဖြစ်တာမို့ — flush စတင်ခါနီးမှာ အနည်းဆုံး `commit_siblings` အရေအတွက် အခြား transaction များ active ဖြစ်နေမှသာ delay ကို လုပ်ပါတယ်။ ထို့အပြင် — `fsync` disable ဖြစ်နေရင် delay များ လုပ်တာ မရှိပါဘူး။ ဒီတန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် microseconds လို့ ယူပါတယ်။ Default `commit_delay` က သုည (delay မရှိ) ဖြစ်ပါတယ်။ သင့်လျော်တဲ့ `SET` privilege ရှိတဲ့ superuser များနဲ့ user များသာ ဒီ setting ကို ပြောင်းနိုင်ပါတယ်။
PostgreSQL 9.3 မတိုင်မီ release များမှာ — `commit_delay` က ကွဲပြားစွာ ပြုမူခဲ့ပြီး အများကြီး ထိရောက်မှု နည်းခဲ့ပါတယ်: ဒါက WAL flush အားလုံးအစား commit များကိုသာ သက်ရောက်ခဲ့ပြီး — WAL flush က စောစော ပြီးစီးခဲ့ရင်တောင် — သတ်မှတ်ထားတဲ့ delay တစ်ခုလုံးကို စောင့်ဆိုင်းခဲ့ပါတယ်။ PostgreSQL 9.3 ကစပြီး — flush လုပ်ဖို့ အသင့် ဖြစ်လာတဲ့ ပထမဆုံး process က သတ်မှတ်ထားတဲ့ ကာလကို စောင့်ဆိုင်းပြီး — နောက်ဆက်တွဲ process များကတော့ leader က flush လုပ်ဆောင်ချက် ပြီးဆုံးတဲ့အထိသာ စောင့်ဆိုင်းပါတယ်။
- **commit_siblings (integer)** — `commit_delay` delay ကို မလုပ်မီ — လိုအပ်တဲ့ concurrent open transaction အနည်းဆုံး အရေအတွက် ဖြစ်ပါတယ်။ ပိုကြီးတဲ့ တန်ဖိုးက — delay ကာလအတွင်း အနည်းဆုံး အခြား transaction တစ်ခု commit လုပ်ဖို့ အသင့် ဖြစ်လာနိုင်ခြေကို ပိုများစေပါတယ်။ Default က transaction ငါးခု ဖြစ်ပါတယ်။

### 19.5.2. Checkpoints (checkpoint များ)

- **checkpoint_timeout (integer)** — အလိုအလျောက် WAL checkpoint များကြားထဲက အများဆုံး အချိန် ဖြစ်ပါတယ်။ ဒီတန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် seconds လို့ ယူပါတယ်။ ခွင့်ပြုတဲ့ အပိုင်းအခြားက စက္ကန့် 30 ကနေ တစ်ရက် အထိ ဖြစ်ပါတယ်။ Default က ငါးမိနစ် (`5min`) ဖြစ်ပါတယ်။ ဒီ parameter ကို တိုးခြင်းက crash recovery အတွက် လိုအပ်တဲ့ အချိန်ကို တိုးစေနိုင်ပါတယ်။ ဒီ parameter ကို `postgresql.conf` file ထဲမှာ ဒါမှမဟုတ် server command line ပေါ်မှာသာ သတ်မှတ်နိုင်ပါတယ်။
- **checkpoint_completion_target (floating point)** — checkpoint ပြီးစီးမှုရဲ့ ပစ်မှတ်ကို — checkpoint များကြားထဲက စုစုပေါင်း အချိန်ရဲ့ အပိုင်းကိန်း (fraction) အနေနဲ့ — သတ်မှတ်ပါတယ်။ Default က 0.9 ဖြစ်ပြီး — ဒါက checkpoint ကို ရနိုင်တဲ့ interval အားလုံးနီးပါး အနှံ့ ဖြန့်ကျက်ပေးကာ — I/O load ကို အတော်အသင့် တည်ငြိမ်စေပြီး — checkpoint ပြီးစီးမှုအတွက် overhead အတွက်လည်း အချိန်နည်းနည်း ချန်ထားပေးပါတယ်။ ဒီ parameter ကို လျှော့ချတာ မအကြံပြုပါဘူး — အကြောင်းကတော့ checkpoint ကို ပိုမြန်စွာ ပြီးစီးစေတာမို့ပါ။ ဒါက checkpoint အတွင်း I/O နှုန်း ပိုမြင့်စေပြီး — checkpoint ပြီးစီးမှုနဲ့ နောက် စီစဉ်ထားတဲ့ checkpoint အကြားမှာ I/O နည်းတဲ့ ကာလ တစ်ခု လိုက်လာစေပါတယ်။ ဒီ parameter ကို `postgresql.conf` file ထဲမှာ ဒါမှမဟုတ် server command line ပေါ်မှာသာ သတ်မှတ်နိုင်ပါတယ်။
- **checkpoint_flush_after (integer)** — checkpoint လုပ်နေစဉ်အတွင်း ဒီပမာဏထက် ပိုပြီး data ရေးသားပြီးတိုင်း — OS ကို ဒီရေးသားမှုများကို အရင်းအမြစ် storage ဆီ ထုတ်ရန် အတင်းအကျပ် ကြိုးစားစေပါတယ်။ ဒါက kernel ရဲ့ page cache ထဲက dirty data ပမာဏကို ကန့်သတ်ပေးပြီး — checkpoint အဆုံးမှာ fsync ထုတ်ချိန် ဒါမှမဟုတ် OS က data များကို နောက်ခံမှာ ပိုကြီးတဲ့ batch များနဲ့ ပြန်ရေးချိန်မှာ — နှောင့်နှေးမှုများ (stalls) ဖြစ်နိုင်ခြေကို လျှော့ချပေးပါတယ်။ များသောအားဖြင့် ဒါက transaction latency ကို အများကြီး လျော့ချပေးပါလိမ့်မယ် — ဒါပေမယ့် အချို့အခြေအနေများ — အထူးသဖြင့် `shared_buffers` ထက် ကြီးပေမယ့် OS ရဲ့ page cache ထက် ငယ်တဲ့ workload များမှာ — performance ကျဆင်းနိုင်ပါတယ်။ ဒီ setting က platform တချို့မှာ အကျိုးသက်ရောက်မှု မရှိနိုင်ပါဘူး။ ဒီတန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် blocks — ဆိုလိုတာက `BLCKSZ` bytes၊ ပုံမှန်အားဖြင့် 8kB — လို့ ယူပါတယ်။ ခွင့်ပြုတဲ့ အပိုင်းအခြားက — အတင်းအကျပ် writeback ကို disable လုပ်တဲ့ 0 ကနေ 2MB အထိ ဖြစ်ပါတယ်။ Default က Linux မှာ 256kB ဖြစ်ပြီး — အခြားနေရာများမှာ 0 ဖြစ်ပါတယ်။ (`BLCKSZ` က 8kB မဟုတ်ရင် — default နဲ့ အများဆုံး တန်ဖိုးများက သူ့အလိုက် အချိုးကျ တိုးလာပါတယ်။) ဒီ parameter ကို `postgresql.conf` file ထဲမှာ ဒါမှမဟုတ် server command line ပေါ်မှာသာ သတ်မှတ်နိုင်ပါတယ်။
- **checkpoint_warning (integer)** — WAL segment file များ ပြည့်တာကြောင့် ဖြစ်ပေါ်တဲ့ checkpoint များက ဒီအချိန်ပမာဏထက် ပိုနီးကပ်စွာ ဖြစ်ပေါ်ရင် (ဒါက `max_wal_size` ကို တင်သင့်ကြောင်း အရိပ်အမြွက် ပြပါတယ်) — server log ဆီ စာတစ်စောင် ရေးသားပါတယ်။ ဒီတန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် seconds လို့ ယူပါတယ်။ Default က စက္ကန့် 30 (`30s`) ဖြစ်ပါတယ်။ သုည သတ်မှတ်ရင် သတိပေးချက် (warning) ကို disable လုပ်ပါတယ်။ `checkpoint_timeout` က `checkpoint_warning` ထက် ငယ်နေရင် သတိပေးချက် ဘာမှ ထုတ်ပေးမှာ မဟုတ်ပါဘူး။ ဒီ parameter ကို `postgresql.conf` file ထဲမှာ ဒါမှမဟုတ် server command line ပေါ်မှာသာ သတ်မှတ်နိုင်ပါတယ်။
- **max_wal_size (integer)** — အလိုအလျောက် checkpoint များအတွင်း WAL ကို ကြီးထွားခွင့်ပြုမယ့် အများဆုံး အရွယ်အစား ဖြစ်ပါတယ်။ ဒါက ပျော့ပြောင်းတဲ့ ကန့်သတ်ချက် (soft limit) ဖြစ်ပါတယ်; အထူးအခြေအနေများ — ဥပမာ — အလုပ်ပမာဏ များခြင်း၊ `archive_command` ဒါမှမဟုတ် `archive_library` ကျရှုံးခြင်း ဒါမှမဟုတ် `wal_keep_size` setting မြင့်နေခြင်း — မှာ WAL အရွယ်အစားက `max_wal_size` ကို ကျော်လွှားနိုင်ပါတယ်။ ဒီတန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် megabytes လို့ ယူပါတယ်။ Default က 1 GB ဖြစ်ပါတယ်။ ဒီ parameter ကို တိုးခြင်းက crash recovery အတွက် လိုအပ်တဲ့ အချိန်ကို တိုးစေနိုင်ပါတယ်။ ဒီ parameter ကို `postgresql.conf` file ထဲမှာ ဒါမှမဟုတ် server command line ပေါ်မှာသာ သတ်မှတ်နိုင်ပါတယ်။
- **min_wal_size (integer)** — WAL disk အသုံးပြုမှုက ဒီ setting အောက် ရှိနေသရွေ့ — WAL file အဟောင်းများကို ဖယ်ရှားမယ့်အစား — checkpoint တစ်ခုမှာ နောက်ထပ် အသုံးပြုဖို့ အမြဲ recycle လုပ်ပါတယ်။ ဒါကို — ဥပမာ — အလုပ်ပမာဏ ကြီးတဲ့ batch job များ လုပ်ဆောင်ချိန်မှာ WAL အသုံးပြုမှု မြင့်တက်မှုများကို ကိုင်တွယ်ဖို့ — လုံလောက်တဲ့ WAL နေရာ သီးသန့် ဖယ်ထားကြောင်း သေချာစေရန် အသုံးပြုနိုင်ပါတယ်။ ဒီတန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် megabytes လို့ ယူပါတယ်။ Default က 80 MB ဖြစ်ပါတယ်။ ဒီ parameter ကို `postgresql.conf` file ထဲမှာ ဒါမှမဟုတ် server command line ပေါ်မှာသာ သတ်မှတ်နိုင်ပါတယ်။

### 19.5.3. Archiving (မော်ကွန်း သိမ်းဆည်းခြင်း)

- **archive_mode (enum)** — `archive_mode` enable ဖြစ်နေရင် — ပြီးစီးသွားတဲ့ WAL segment များကို `archive_command` ဒါမှမဟုတ် `archive_library` သတ်မှတ်ခြင်းဖြင့် archive storage ဆီ ပို့ပါတယ်။ Disable လုပ်တဲ့ `off` အပြင် — mode နှစ်ခု ရှိပါတယ်: `on` နဲ့ `always`။ ပုံမှန် လည်ပတ်မှုအတွင်း mode နှစ်ခုကြား ခြားနားမှု မရှိပါဘူး — ဒါပေမယ့် `always` သတ်မှတ်ထားရင် — archive recovery ဒါမှမဟုတ် standby mode အတွင်းမှာလည်း WAL archiver ကို enable လုပ်ပါတယ်။ `always` mode မှာ — archive ကနေ ပြန်လည် ရယူခဲ့တဲ့ ဒါမှမဟုတ် streaming replication နဲ့ stream လုပ်ခဲ့တဲ့ file အားလုံးကို (ထပ်မံ) archive လုပ်ပါလိမ့်မယ်။ အသေးစိတ်အတွက် အပိုင်း 26.2.9 ကို ကြည့်ပါ။
`archive_mode` က `archive_command` နဲ့ `archive_library` ကနေ သီးခြား setting တစ်ခု ဖြစ်ပါတယ် — ဒါမှ archiving mode မှ မထွက်ဘဲ `archive_command` နဲ့ `archive_library` ကို ပြောင်းလဲနိုင်မှာ ဖြစ်ပါတယ်။ ဒီ parameter ကို server စတင်တဲ့အခါမှသာ သတ်မှတ်နိုင်ပါတယ်။ `wal_level` ကို `minimal` သတ်မှတ်ထားရင် `archive_mode` ကို enable လုပ်လို့ မရပါဘူး။
- **archive_command (string)** — ပြီးစီးသွားတဲ့ WAL file segment တစ်ခုကို archive လုပ်ဖို့ run ရမယ့် local shell command ဖြစ်ပါတယ်။ String ထဲက `%p` တိုင်းကို archive လုပ်ရမယ့် file ရဲ့ path name နဲ့ အစားထိုးပြီး — `%f` တိုင်းကို file name သက်သက်နဲ့ အစားထိုးပါတယ်။ (Path name က server ရဲ့ working directory — ဆိုလိုတာက cluster ရဲ့ data directory — ကို ဆက်စပ်တဲ့ အနေနဲ့ ဖြစ်ပါတယ်။) Command ထဲမှာ တကယ့် `%` အက္ခရာ ထည့်ဖို့ `%%` ကို သုံးပါ။ Command က အောင်မြင်မှသာ သုည exit status ပြန်ပေးတာ အရေးကြီးပါတယ်။ ပိုမို အချက်အလက်အတွက် အပိုင်း 25.3.1 ကို ကြည့်ပါ။
ဒီ parameter ကို `postgresql.conf` file ထဲမှာ ဒါမှမဟုတ် server command line ပေါ်မှာသာ သတ်မှတ်နိုင်ပါတယ်။ ဒါကို — `archive_mode` ကို server စတင်တဲ့အခါ enable လုပ်ခဲ့ပြီး `archive_library` ကို အလွတ် string သတ်မှတ်ထားမှသာ အသုံးပြုပါတယ်။ `archive_command` ရော `archive_library` ပါ သတ်မှတ်ထားရင် error ထုတ်ပါလိမ့်မယ်။ `archive_mode` enable ဖြစ်နေချိန် (`archive_library` ကို အလွတ် string သတ်မှတ်ထားချိန်) — `archive_command` က အလွတ် string (default) ဖြစ်နေရင် — WAL archiving ကို ယာယီ disable လုပ်ထားပေမယ့် — မကြာမီ command တစ်ခု ပေးလာလိမ့်မယ်လို့ မျှော်မှန်းပြီး — server က WAL segment file များကို ဆက်လက် စုဆောင်းနေပါတယ်။ `archive_command` ကို `true` သာ ပြန်ပေးတဲ့ ဘာမှ မလုပ်တဲ့ command — ဥပမာ — `/bin/true` (Windows မှာ `REM`) — သတ်မှတ်ခြင်းက archiving ကို ထိရောက်စွာ disable လုပ်ပေမယ့် — archive recovery အတွက် လိုအပ်တဲ့ WAL file ကွင်းဆက် (chain) ကိုလည်း ချိုးဖျက်တာမို့ — ပုံမှန်မဟုတ်တဲ့ အခြေအနေများမှာသာ သုံးသင့်ပါတယ်။
- **archive_library (string)** — ပြီးစီးသွားတဲ့ WAL file segment များကို archive လုပ်ဖို့ သုံးမယ့် library ဖြစ်ပါတယ်။ အလွတ် string (default) သတ်မှတ်ထားရင် — shell ကနေ archiving ကို enable လုပ်ပြီး `archive_command` ကို အသုံးပြုပါတယ်။ `archive_command` ရော `archive_library` ပါ သတ်မှတ်ထားရင် error ထုတ်ပါလိမ့်မယ်။ မဟုတ်ရင် — သတ်မှတ်ထားတဲ့ shared library ကို archiving အတွက် အသုံးပြုပါတယ်။ ဒီ parameter ပြောင်းလဲတဲ့အခါ WAL archiver process ကို postmaster က ပြန်စ (restart) ပါတယ်။ ပိုမို အချက်အလက်အတွက် အပိုင်း 25.3.1 နဲ့ အခန်း 49 ကို ကြည့်ပါ။
ဒီ parameter ကို `postgresql.conf` file ထဲမှာ ဒါမှမဟုတ် server command line ပေါ်မှာသာ သတ်မှတ်နိုင်ပါတယ်။
- **archive_timeout (integer)** — `archive_command` ဒါမှမဟုတ် `archive_library` ကို ပြီးစီးသွားတဲ့ WAL segment များအတွက်သာ ခေါ်ပါတယ်။ ဒါကြောင့် — သင့် server က WAL traffic နည်းနည်းသာ ထုတ်လုပ်ရင် (ဒါမှမဟုတ် နည်းတဲ့ ကာလများ ရှိရင်) — transaction တစ်ခု ပြီးစီးမှုနဲ့ archive storage ထဲ လုံခြုံစွာ မှတ်တမ်းတင်မှုကြားမှာ ကြာမြင့်တဲ့ နှောင့်နှေးမှု ရှိနိုင်ပါတယ်။ မမော်ကွန်းရသေးတဲ့ data က ဘယ်လောက် အိုမင်းနိုင်မလဲ ကန့်သတ်ဖို့ — server ကို အခါအားလျော်စွာ WAL segment file အသစ်တစ်ခုဆီ ပြောင်းရန် အတင်းအကျပ် လုပ်စေဖို့ `archive_timeout` ကို သတ်မှတ်နိုင်ပါတယ်။ ဒီ parameter က သုညထက် ကြီးနေရင် — နောက်ဆုံး segment file ပြောင်းလဲမှုကတည်းက ဒီအချိန် ကုန်ဆုံးပြီး — database activity တစ်ခုခု (checkpoint တစ်ခုတည်းပါ ပါဝင်ပြီး — database activity မရှိရင် checkpoint များကို ကျော်လွှားပါတယ်) ရှိခဲ့ရင် — server က segment file အသစ်တစ်ခုဆီ ပြောင်းပါလိမ့်မယ်။ အတင်းအကျပ် ပြောင်းလဲမှုကြောင့် စောစော ပိတ်လိုက်ရတဲ့ archive file များက လုံးဝ ပြည့်နေတဲ့ file များနဲ့ အရှည်တူနေဆဲ ဖြစ်တယ်ဆိုတာ သတိပြုပါ။ ဒါကြောင့် — အလွန်တိုတောင်းတဲ့ `archive_timeout` ကို သုံးတာ ပညာမဲ့ရာ ကျပါတယ် — ဒါက သင့် archive storage ကို ဖောင်းပွစေပါလိမ့်မယ်။ တစ်မိနစ်ခန့် `archive_timeout` setting များက ပုံမှန်အားဖြင့် သင့်လျော်ပါတယ်။ ဒီထက် ပိုမြန်စွာ primary server ကနေ data ကို ကူးယူချင်ရင် archiving အစား streaming replication ကို သုံးတာ စဉ်းစားသင့်ပါတယ်။ ဒီတန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် seconds လို့ ယူပါတယ်။ ဒီ parameter ကို `postgresql.conf` file ထဲမှာ ဒါမှမဟုတ် server command line ပေါ်မှာသာ သတ်မှတ်နိုင်ပါတယ်။

### 19.5.4. Recovery (ပြန်လည် ကုစားခြင်း)

ဒီ section က recovery အတွေ့အကြုံ အထွေထွေအတွက် သက်ဆိုင်တဲ့ setting များကို ဖော်ပြပါတယ် — crash recovery၊ streaming replication နဲ့ archive-based replication များကို သက်ရောက်ပါတယ်။

- **recovery_prefetch (enum)** — recovery အတွင်း buffer pool ထဲ မရောက်သေးတဲ့ — WAL ထဲမှာ ရည်ညွှန်းထားတဲ့ block များကို ကြိုတင် ဆွဲယူ (prefetch) ရန် ကြိုးစားမလား ဆိုတာ ဖြစ်ပါတယ်။ ဖြစ်နိုင်တဲ့ တန်ဖိုးများက `off`၊ `on` နဲ့ `try` (default) ဖြစ်ပါတယ်။ `try` setting က — operating system က read-ahead advice ထုတ်ပေးမှုကို ထောက်ပံ့ရင်သာ prefetching ကို enable လုပ်ပါတယ်။
မကြာမီ လိုအပ်လာမယ့် block များကို ကြိုတင် ဆွဲယူခြင်းက — workload တချို့မှာ recovery အတွင်း I/O စောင့်ဆိုင်းချိန်များကို လျော့ချနိုင်ပါတယ်။ prefetching လုပ်ဆောင်ချက်ကို ကန့်သတ်တဲ့ `wal_decode_buffer_size` နဲ့ `maintenance_io_concurrency` setting များကိုလည်း ကြည့်ပါ။
- **wal_decode_buffer_size (integer)** — block များ ရှာဖွေဖို့ — server က WAL ထဲမှာ ဘယ်လောက် ရှေ့ကို ကြည့်နိုင်မလဲ ဆိုတဲ့ ကန့်သတ်ချက် ဖြစ်ပါတယ်။ ဒီတန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် bytes လို့ ယူပါတယ်။ Default က 512kB ဖြစ်ပါတယ်။ ဒီ parameter ကို server စတင်တဲ့အခါမှသာ သတ်မှတ်နိုင်ပါတယ်။

### 19.5.5. Archive Recovery (မော်ကွန်းမှ ပြန်လည် ကုစားခြင်း)

ဒီ section က recovery ကာလ အတွင်းမှာသာ သက်ဆိုင်တဲ့ setting များကို ဖော်ပြပါတယ်။ နောက်ဆက်တွဲ recovery တစ်ခု လုပ်ဆောင်လိုရင် ဒီ setting များကို ပြန်လည် သတ်မှတ် (reset) ရပါမယ်။

“Recovery” ဆိုတာ server ကို standby အဖြစ် အသုံးပြုခြင်း ဒါမှမဟုတ် targeted recovery တစ်ခု လုပ်ဆောင်ခြင်းကို ခြုံငုံပါတယ်။ ပုံမှန်အားဖြင့် — standby mode ကို high availability နဲ့/ဒါမှမဟုတ် read scalability ပေးဖို့ အသုံးပြုပြီး — targeted recovery ကိုတော့ data ဆုံးရှုံးမှုကနေ ပြန်လည် ကုစားဖို့ အသုံးပြုပါတယ်။

Server ကို standby mode နဲ့ စတင်ဖို့ — data directory ထဲမှာ `standby.signal` ဆိုတဲ့ file တစ်ခု ဖန်တီးပါ။ Server က recovery ထဲ ဝင်သွားပြီး — archive လုပ်ထားတဲ့ WAL အဆုံးကို ရောက်တဲ့အခါ recovery ကို ရပ်မပစ်ဘဲ — `primary_conninfo` setting က သတ်မှတ်ထားတဲ့ sending server ဆီ ချိတ်ဆက်ခြင်း နဲ့/ဒါမှမဟုတ် `restore_command` သုံးပြီး WAL segment အသစ်များ ဆွဲယူခြင်းဖြင့် recovery ကို ဆက်လုပ်ဖို့ ဆက်လက် ကြိုးစားပါလိမ့်မယ်။ ဒီ mode အတွက် — ဒီ section က parameter များနဲ့ [အပိုင်း 19.6.3](/docs/postgresql/runtime-config-replication) က parameter များ အရေးပါပါတယ်။ [အပိုင်း 19.5.6](/docs/postgresql/runtime-config-wal) က parameter များကိုလည်း အသုံးပြုပါလိမ့်မယ် — ဒါပေမယ့် ဒီ mode မှာ ပုံမှန်အားဖြင့် အသုံးမဝင်ပါဘူး။

Targeted recovery mode နဲ့ server စတင်ဖို့ — data directory ထဲမှာ `recovery.signal` ဆိုတဲ့ file တစ်ခု ဖန်တီးပါ။ `standby.signal` ရော `recovery.signal` ပါ ဖန်တီးထားရင် — standby mode က ဦးစားပေး ဖြစ်ပါတယ်။ Targeted recovery mode က archive လုပ်ထားတဲ့ WAL ကို အပြည့်အဝ replay လုပ်ပြီးတဲ့အခါ — ဒါမှမဟုတ် `recovery_target` ကို ရောက်တဲ့အခါ — ပြီးဆုံးပါတယ်။ ဒီ mode မှာ — ဒီ section ရော [အပိုင်း 19.5.6](/docs/postgresql/runtime-config-wal) ပါ က parameter များကို အသုံးပြုပါလိမ့်မယ်။

- **restore_command (string)** — WAL file အစဉ် (series) ရဲ့ archive လုပ်ထားတဲ့ segment တစ်ခုကို ပြန်လည် ရယူဖို့ run ရမယ့် local shell command ဖြစ်ပါတယ်။ ဒီ parameter က archive recovery အတွက် လိုအပ်ပြီး — streaming replication အတွက်တော့ optional ဖြစ်ပါတယ်။ String ထဲက `%f` တိုင်းကို archive ကနေ ပြန်လည် ရယူရမယ့် file ရဲ့ နာမည်နဲ့ အစားထိုးပြီး — `%p` တိုင်းကို server ပေါ်က copy destination path name နဲ့ အစားထိုးပါတယ်။ (Path name က လက်ရှိ working directory — ဆိုလိုတာက cluster ရဲ့ data directory — ကို ဆက်စပ်တဲ့ အနေနဲ့ ဖြစ်ပါတယ်။) `%r` တိုင်းကို နောက်ဆုံး တရားဝင် restart point ပါဝင်တဲ့ file ရဲ့ နာမည်နဲ့ အစားထိုးပါတယ်။ ဒါက — restore တစ်ခုကို restartable ဖြစ်စေဖို့ သိမ်းထားရမယ့် အစောဆုံး file ဖြစ်တာမို့ — လက်ရှိ restore ကနေ ပြန်စတာ (restarting) ကို ထောက်ပံ့ဖို့ လိုအပ်တဲ့ အနည်းဆုံး ပမာဏအထိသာ archive ကို ဖြတ်တောက် (truncate) ဖို့ ဒီအချက်အလက်ကို အသုံးပြုနိုင်ပါတယ်။ `%r` ကို warm-standby configuration များမှာသာ ပုံမှန်အားဖြင့် အသုံးပြုပါတယ် (အပိုင်း 26.2 ကို ကြည့်ပါ)။ တကယ့် `%` အက္ခရာ ထည့်ဖို့ `%%` ကို ရေးပါ။
Command က အောင်မြင်မှသာ သုည exit status ပြန်ပေးတာ အရေးကြီးပါတယ်။ Archive ထဲမှာ မရှိတဲ့ file နာမည်များကိုလည်း command ကို မေးပါလိမ့်မယ်; အဲလို မေးတဲ့အခါ သုည မဟုတ်တဲ့ တန်ဖိုး ပြန်ရပါမယ်။ ဥပမာများ:

restore_command = 'cp /mnt/server/archivedir/%f "%p"'
restore_command = 'copy "C:\\server\\archivedir\\%f" "%p"'  # Windows

ခြွင်းချက် တစ်ခုကတော့ — command ကို signal တစ်ခုနဲ့ ရပ်လိုက်ရရင် (database server shutdown ရဲ့ တစ်စိတ်တစ်ပိုင်းအဖြစ် သုံးတဲ့ SIGTERM မှလွဲ၍) ဒါမှမဟုတ် shell ရဲ့ error တစ်ခုကြောင့် (ဥပမာ — command not found) ရပ်သွားရရင် — recovery က abort ဖြစ်ပြီး server က စတင် (start up) မှာ မဟုတ်ပါဘူး။
ဒီ parameter ကို `postgresql.conf` file ထဲမှာ ဒါမှမဟုတ် server command line ပေါ်မှာသာ သတ်မှတ်နိုင်ပါတယ်။

- **archive_cleanup_command (string)** — ဒီ optional parameter က restartpoint တိုင်းမှာ run လုပ်မယ့် shell command တစ်ခုကို သတ်မှတ်ပါတယ်။ `archive_cleanup_command` ရဲ့ ရည်ရွယ်ချက်က — standby server က မလိုအပ်တော့တဲ့ archive လုပ်ထားတဲ့ WAL file အဟောင်းများကို ရှင်းလင်းဖို့ ယန္တရား တစ်ခု ပေးဖို့ ဖြစ်ပါတယ်။ `%r` တိုင်းကို နောက်ဆုံး တရားဝင် restart point ပါဝင်တဲ့ file ရဲ့ နာမည်နဲ့ အစားထိုးပါတယ်။ ဒါက — restore တစ်ခုကို restartable ဖြစ်စေဖို့ သိမ်းထားရမယ့် အစောဆုံး file ဖြစ်တာမို့ — `%r` ထက် အစောတဲ့ file အားလုံးကို ဘေးကင်းစွာ ဖယ်ရှားနိုင်ပါတယ်။ ဒီအချက်အလက်ကို — လက်ရှိ restore ကနေ ပြန်စတာကို ထောက်ပံ့ဖို့ လိုအပ်တဲ့ အနည်းဆုံး ပမာဏအထိ — archive ကို ဖြတ်တောက်ဖို့ အသုံးပြုနိုင်ပါတယ်။ `pg_archivecleanup` module ကို single-standby configuration များအတွက် `archive_cleanup_command` မှာ မကြာခဏ အသုံးပြုပါတယ် — ဥပမာ:
archive_cleanup_command = 'pg_archivecleanup /mnt/server/archivedir %r'
ဒါပေမယ့် — standby server အများအပြားက archive directory တစ်ခုတည်းကနေ ပြန်လည် ကုစားနေရင် — server တစ်ခုခုက မလိုအပ်တော့တဲ့အထိ WAL file များကို ဖျက်မပစ်ကြောင်း သေချာစေဖို့ လိုအပ်ပါလိမ့်မယ်။ `archive_cleanup_command` ကို warm-standby configuration တစ်ခုမှာ ပုံမှန်အားဖြင့် အသုံးပြုပါလိမ့်မယ် (အပိုင်း 26.2 ကို ကြည့်ပါ)။ Command ထဲမှာ တကယ့် `%` အက္ခရာ ထည့်ဖို့ `%%` ကို ရေးပါ။
Command က သုည မဟုတ်တဲ့ exit status ပြန်ရင် — သတိပေးချက် (warning) log message တစ်ခု ရေးသားပါလိမ့်မယ်။ ခြွင်းချက် တစ်ခုကတော့ — command ကို signal တစ်ခုနဲ့ ဒါမှမဟုတ် shell ရဲ့ error တစ်ခုကြောင့် (ဥပမာ — command not found) ရပ်လိုက်ရရင် — fatal error တစ်ခု ထုတ်ပါလိမ့်မယ်။
ဒီ parameter ကို `postgresql.conf` file ထဲမှာ ဒါမှမဟုတ် server command line ပေါ်မှာသာ သတ်မှတ်နိုင်ပါတယ်။

- **recovery_end_command (string)** — ဒီ parameter က recovery အဆုံးမှာ တစ်ကြိမ်သာ run လုပ်မယ့် shell command တစ်ခုကို သတ်မှတ်ပါတယ်။ ဒီ parameter က optional ဖြစ်ပါတယ်။ `recovery_end_command` ရဲ့ ရည်ရွယ်ချက်က — replication ဒါမှမဟုတ် recovery အပြီးမှာ ရှင်းလင်းရေးအတွက် ယန္တရား တစ်ခု ပေးဖို့ ဖြစ်ပါတယ်။ `%r` တိုင်းကို — `archive_cleanup_command` မှာလိုပဲ — နောက်ဆုံး တရားဝင် restart point ပါဝင်တဲ့ file ရဲ့ နာမည်နဲ့ အစားထိုးပါတယ်။
Command က သုည မဟုတ်တဲ့ exit status ပြန်ရင် — သတိပေးချက် log message တစ်ခု ရေးသားပြီး — database က စတင်တာ (startup) ကို ဆက်လုပ် ပါလိမ့်မယ်။ ခြွင်းချက် တစ်ခုကတော့ — command ကို signal တစ်ခုနဲ့ ဒါမှမဟုတ် shell ရဲ့ error တစ်ခုကြောင့် (ဥပမာ — command not found) ရပ်လိုက်ရရင် — database က startup ကို ဆက်လုပ်မှာ မဟုတ်ပါဘူး။
ဒီ parameter ကို `postgresql.conf` file ထဲမှာ ဒါမှမဟုတ် server command line ပေါ်မှာသာ သတ်မှတ်နိုင်ပါတယ်။

### 19.5.6. Recovery Target (ပြန်လည် ကုစားရမည့် ပစ်မှတ်)

Default အားဖြင့် — recovery က WAL log ရဲ့ အဆုံးအထိ ပြန်လည် ကုစားပါလိမ့်မယ်။ အောက်ပါ parameter များကို စောစော ရပ်တန့်မယ့် အမှတ် (earlier stopping point) သတ်မှတ်ဖို့ အသုံးပြုနိုင်ပါတယ်။ `recovery_target`၊ `recovery_target_lsn`၊ `recovery_target_name`၊ `recovery_target_time` ဒါမှမဟုတ် `recovery_target_xid` တို့ထဲက အများဆုံး တစ်ခုကိုသာ အသုံးပြုနိုင်ပါတယ်; configuration file ထဲမှာ ဒီထဲက တစ်ခုထက်ပိုပြီး သတ်မှတ်ထားရင် error ထုတ်ပါလိမ့်မယ်။ ဒီ parameter များကို server စတင်တဲ့အခါမှသာ သတ်မှတ်နိုင်ပါတယ်။

- **recovery_target = 'immediate'** — ဒီ parameter က — ညီညွတ်တဲ့ အခြေအနေ (consistent state) ရောက်တာနဲ့ — ဆိုလိုတာက အတတ်နိုင်ဆုံး စောစောစီးစီး — recovery ပြီးဆုံးသင့်ကြောင်း သတ်မှတ်ပါတယ်။ Online backup ကနေ ပြန်လည် ကုစားတဲ့အခါ — ဒါက backup ရိုက်တာ (taking the backup) ပြီးဆုံးတဲ့ အမှတ်ကို ဆိုလိုပါတယ်။
Technically — ဒါက string parameter တစ်ခု ဖြစ်ပေမယ့် `'immediate'` က လက်ရှိမှာ ခွင့်ပြုတဲ့ တစ်ခုတည်းသော တန်ဖိုး ဖြစ်ပါတယ်။
- **recovery_target_name (string)** — ဒီ parameter က recovery ဆက်လုပ်မယ့် — `pg_create_restore_point()` နဲ့ ဖန်တီးထားတဲ့ named restore point — ကို သတ်မှတ်ပါတယ်။
- **recovery_target_time (timestamp)** — ဒီ parameter က recovery ဆက်လုပ်မယ့် အချိန်အထိ timestamp ကို သတ်မှတ်ပါတယ်။ တိကျတဲ့ ရပ်တန့်မှု အမှတ်ကို `recovery_target_inclusive` ကလည်း သက်ရောက်ပါတယ်။
ဒီ parameter ရဲ့ တန်ဖိုးက — `timestamp with time zone` data type က လက်ခံတဲ့ format အတူတူ ရှိတဲ့ time stamp တစ်ခု ဖြစ်ပါတယ် — ဒါပေမယ့် time zone အတိုကောက် (abbreviation) ကို မသုံးနိုင်ပါဘူး (configuration file ထဲမှာ `timezone_abbreviations` variable ကို အစောတင် သတ်မှတ်ထားခဲ့ရင်တော့ ခြွင်းချက်)။ နှစ်သက်ရာ ပုံစံက UTC ကနေ ကိန်းဂဏန်း offset သုံးတာပါ; ဒါမှမဟုတ် time zone နာမည် အပြည့်အစုံကို ရေးနိုင်ပါတယ် — ဥပမာ — EEST မဟုတ်ဘဲ Europe/Helsinki။
- **recovery_target_xid (string)** — ဒီ parameter က recovery ဆက်လုပ်မယ့် transaction ID အထိ ကို သတ်မှတ်ပါတယ်။ Transaction ID များက transaction စတင်တဲ့အခါ အစဉ်လိုက် (sequentially) သတ်မှတ်ပေမယ့် — transaction များက ကွဲပြားတဲ့ ကိန်းဂဏန်း အစဉ်နဲ့ ပြီးဆုံးနိုင်တယ်ဆိုတာ သတိရပါ။ ပြန်လည် ကုစားခံရမယ့် transaction များက — သတ်မှတ်ထားတဲ့ တစ်ခုမတိုင်မီ (ပြီးတော့ optional အနေနဲ့ တစ်ခုအပါအဝင်) commit လုပ်ခဲ့တဲ့ transaction များ ဖြစ်ပါတယ်။ တိကျတဲ့ ရပ်တန့်မှု အမှတ်ကို `recovery_target_inclusive` ကလည်း သက်ရောက်ပါတယ်။
- **recovery_target_lsn (pg_lsn)** — ဒီ parameter က recovery ဆက်လုပ်မယ့် — write-ahead log တည်နေရာ (location) ရဲ့ LSN — ကို သတ်မှတ်ပါတယ်။ တိကျတဲ့ ရပ်တန့်မှု အမှတ်ကို `recovery_target_inclusive` ကလည်း သက်ရောက်ပါတယ်။ ဒီ parameter ကို system data type `pg_lsn` သုံးပြီး parse လုပ်ပါတယ်။

အောက်ပါ option များက recovery target ကို ထပ်မံ သတ်မှတ်ပေးပြီး — target ကို ရောက်တဲ့အခါ ဘာဖြစ်မလဲကို သက်ရောက်ပါတယ်:

- **recovery_target_inclusive (boolean)** — သတ်မှတ်ထားတဲ့ recovery target ပြီးနောက် ချက်ချင်း (`on`) ရပ်မလား — ဒါမှမဟုတ် recovery target မတိုင်မီ ချက်ချင်း (`off`) ရပ်မလား သတ်မှတ်ပါတယ်။ `recovery_target_lsn`၊ `recovery_target_time` ဒါမှမဟုတ် `recovery_target_xid` သတ်မှတ်ထားတဲ့အခါ သက်ဆိုင်ပါတယ်။ ဒီ setting က — target WAL location (LSN)၊ commit time ဒါမှမဟုတ် transaction ID အတိအက် ရှိတဲ့ transaction များကို အသီးသီး recovery ထဲ ထည့်မလား ဆိုတာကို ထိန်းချုပ်ပါတယ်။ Default က `on` ဖြစ်ပါတယ်။
- **recovery_target_timeline (string)** — timeline တစ်ခုဆီ ပြန်လည် ကုစားမှုကို သတ်မှတ်ပါတယ်။ တန်ဖိုးက ကိန်းဂဏန်း timeline ID တစ်ခု ဒါမှမဟုတ် အထူး တန်ဖိုး တစ်ခု ဖြစ်နိုင်ပါတယ်။ `current` ဆိုတဲ့ တန်ဖိုးက — base backup ရိုက်တဲ့အခါ လက်ရှိ ဖြစ်ခဲ့တဲ့ timeline အတူတူအတိုင်း ပြန်လည် ကုစားပါတယ်။ `latest` ဆိုတဲ့ တန်ဖိုးက — archive ထဲမှာ တွေ့တဲ့ နောက်ဆုံး timeline ဆီ ပြန်လည် ကုစားပြီး — standby server တစ်ခုမှာ အသုံးဝင်ပါတယ်။ `latest` က default ဖြစ်ပါတယ်။
Timeline ID ကို hexadecimal နဲ့ သတ်မှတ်ဖို့ (ဥပမာ — WAL file နာမည် ဒါမှမဟုတ် history file ကနေ ထုတ်ယူခဲ့ရင်) — ရှေ့မှာ `0x` ထည့်ပါ။ ဥပမာ — WAL file နာမည်က `00000011000000A10000004F` ဖြစ်ရင် timeline ID က `0x11` (ဒါမှမဟုတ် ဒသမ 17) ဖြစ်ပါတယ်။
ဒီ parameter ကို — point-in-time recovery အပြီးမှ ရောက်ခဲ့တဲ့ အခြေအနေတစ်ခုဆီ ပြန်သွားဖို့ လိုအပ်တဲ့ — ရှုပ်ထွေးတဲ့ re-recovery အခြေအနေများမှာသာ ပုံမှန်အားဖြင့် သတ်မှတ်ဖို့ လိုပါတယ်။ ဆွေးနွေးချက်အတွက် အပိုင်း 25.3.6 ကို ကြည့်ပါ။
- **recovery_target_action (enum)** — recovery target ကို ရောက်တဲ့အခါ server က ဘယ်လို လုပ်ဆောင်ချက် ယူရမလဲ သတ်မှတ်ပါတယ်။ Default က `pause` ဖြစ်ပြီး — ဆိုလိုတာက recovery ကို ရပ်ဆိုင်း (pause) လုပ်ပါလိမ့်မယ်။ `promote` ကတော့ recovery လုပ်ငန်းစဉ် ပြီးဆုံးပြီး server က ချိတ်ဆက်မှုများ လက်ခံတာ စတင်ပါလိမ့်မယ်။ နောက်ဆုံး `shutdown` က recovery target ရောက်ပြီးနောက် server ကို ရပ်ပါလိမ့်မယ်။
`pause` setting ရဲ့ ရည်ရွယ်ထားတဲ့ အသုံးပြုမှုက — ဒီ recovery target က recovery အတွက် အနှစ်သက်ဆုံး အမှတ် ဟုတ်မဟုတ် စစ်ဆေးဖို့ database အပေါ် query များ run နိုင်စေဖို့ ဖြစ်ပါတယ်။ ရပ်ဆိုင်းထားတဲ့ အခြေအနေကို `pg_wal_replay_resume()` (ဇယား 9.99 ကို ကြည့်ပါ) သုံးပြီး ပြန်လည် စတင်နိုင်ပြီး — ဒါက recovery ကို ပြီးဆုံးစေပါတယ်။ ဒီ recovery target က လိုချင်တဲ့ ရပ်တန့်မှု အမှတ် မဟုတ်ရင် — server ကို ရပ်ပြီး — recovery target setting များကို နောက်ကျတဲ့ target တစ်ခုသို့ ပြောင်းကာ — recovery ဆက်လုပ်ဖို့ ပြန်စ (restart) ပါ။
`shutdown` setting က — instance ကို လိုချင်တဲ့ replay အမှတ်အတိအကျမှာ အသင့် ဖြစ်နေစေဖို့ အသုံးဝင်ပါတယ်။ Instance က WAL record များကို ထပ်မံ replay လုပ်နိုင်ဆဲ ဖြစ်ပါလိမ့်မယ် (ပြီးတော့ တကယ်တော့ — နောက်တစ်ကြိမ် စတင်တဲ့အခါ — နောက်ဆုံး checkpoint ကတည်းက WAL record များကို replay လုပ်ရပါလိမ့်မယ်)။
`recovery.signal` ကို `recovery_target_action` ကို `shutdown` သတ်မှတ်တဲ့အခါ ဖယ်ရှားမှာ မဟုတ်တာမို့ — configuration ကို ပြောင်းခြင်း ဒါမှမဟုတ် `recovery.signal` file ကို လက်ဖြင့် ဖယ်ရှားခြင်း မလုပ်ရင် — နောက်ဆက်တွဲ start မှန်သမျှက immediate shutdown နဲ့ အဆုံးသတ်ပါလိမ့်မယ် ဆိုတာ သတိပြုပါ။
Recovery target သတ်မှတ်မထားရင် ဒီ setting က အကျိုးသက်ရောက်မှု မရှိပါဘူး။ `hot_standby` ကို enable မလုပ်ထားရင် — `pause` setting က `shutdown` နဲ့ အတူတူ ပြုမူပါလိမ့်မယ်။ Promotion တစ်ခု လုပ်နေစဉ်အတွင်း recovery target ကို ရောက်ရင် — `pause` setting က `promote` နဲ့ အတူတူ ပြုမူပါလိမ့်မယ်။
ဘယ်လိုပဲ ဖြစ်ဖြစ် — recovery target ကို configure လုပ်ထားပေမယ့် target ကို မရောက်မီ archive recovery ပြီးဆုံးသွားရင် — server က fatal error နဲ့ ရပ်သွားပါလိမ့်မယ်။

### 19.5.7. WAL Summarization (WAL အနှစ်ချုပ် ပြုလုပ်ခြင်း)

ဒီ setting များက — [incremental backup (တိုးချဲ့ backup)](/docs/postgresql/continuous-archiving) တစ်ခု လုပ်ဆောင်ဖို့ enable လုပ်ရမယ့် — WAL summarization ကို ထိန်းချုပ်ပါတယ်။

- **summarize_wal (boolean)** — WAL summarizer process ကို enable လုပ်ပါတယ်။ WAL summarization ကို primary ပေါ်မှာရော standby ပေါ်မှာပါ enable လုပ်နိုင်တယ်ဆိုတာ သတိပြုပါ။ ဒီ parameter ကို `postgresql.conf` file ထဲမှာ ဒါမှမဟုတ် server command line ပေါ်မှာသာ သတ်မှတ်နိုင်ပါတယ်။ Default က `off` ဖြစ်ပါတယ်။
`wal_level` ကို `minimal` သတ်မှတ်ထားရင် — server ကို `summarize_wal=on` နဲ့ စတင် (start) လို့ မရပါဘူး။ `wal_level=minimal` ဖြစ်နေချိန် server start ပြီးနောက်မှ `summarize_wal=on` configure လုပ်ရင် — summarizer က run ပေမယ့် — `wal_level=minimal` နဲ့ ထုတ်လုပ်တဲ့ WAL အတွက် summary file များ ထုတ်ဖို့ ငြင်းပယ်ပါလိမ့်မယ်။
- **wal_summary_keep_time (integer)** — WAL summarizer က WAL summary အဟောင်းများကို အလိုအလျောက် ဖယ်ရှားမယ့် — အချိန်ပမာဏ — ကို configure လုပ်ပါတယ်။ ဘယ် file များက ဖယ်ရှားဖို့ လုံလောက်အောင် အိုနေပြီလဲ ဆုံးဖြတ်ဖို့ file timestamp ကို အသုံးပြုပါတယ်။ ပုံမှန်အားဖြင့် — backup တစ်ခုနဲ့ သူ့အပေါ် မှီခိုတဲ့ နောက်ဆက်တွဲ incremental backup တစ်ခုကြား ကုန်ဆုံးနိုင်တဲ့ အချိန်ထက် — ဒီတန်ဖိုးကို သက်သောင့်သက်သာ ပိုမြင့်အောင် သတ်မှတ်သင့်ပါတယ်။ WAL summary များက — ရှေ့ backup နဲ့ ရိုက်နေတဲ့ အသစ် backup အကြားက WAL record အပိုင်းအခြား တစ်ခုလုံးအတွက် ရနိုင်ရပါမယ်; မရရင် incremental backup ကျရှုံးပါလိမ့်မယ်။ ဒီ parameter ကို သုည သတ်မှတ်ရင် — WAL summary များကို အလိုအလျောက် ဖျက်မှာ မဟုတ်ပေမယ့် — အနာဂတ် incremental backup များအတွက် မလိုအပ်တော့ဘူးလို့ သင်သိတဲ့ file များကို လက်ဖြင့် ဖယ်ရှားတာ ဘေးကင်းပါတယ်။ ဒီ parameter ကို `postgresql.conf` file ထဲမှာ ဒါမှမဟုတ် server command line ပေါ်မှာသာ သတ်မှတ်နိုင်ပါတယ်။ ဒီတန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် minutes လို့ ယူပါတယ်။ Default က 10 days ဖြစ်ပါတယ်။ `summarize_wal = off` ဖြစ်ရင် — WAL summarizer run မလုပ်တာမို့ — ဒီ parameter ရဲ့ တန်ဖိုး ဘယ်လိုပဲ ဖြစ်ဖြစ် — ရှိပြီးသား WAL summary များကို ဖယ်ရှားမှာ မဟုတ်ပါဘူး။
