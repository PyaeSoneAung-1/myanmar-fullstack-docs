PostgreSQL က — အချိန် အားလုံးမှာ — cluster ရဲ့ data directory ရဲ့ `pg_wal/` subdirectory (အတွင်းဖိုင်တွဲ) ထဲမှာ *write ahead log* (WAL) တစ်ခုကို ထိန်းသိမ်းထားပါတယ်။ ဒီ log က database ရဲ့ data files တွေဆီ ပြုလုပ်တဲ့ ပြောင်းလဲမှု (change) တိုင်းကို မှတ်တမ်းတင်ပါတယ်။ ဒီ log ရဲ့ အဓိက ရည်ရွယ်ချက်က crash-safety (system ပျက်ကျမှုမှ ကာကွယ်ရေး) အတွက် ဖြစ်ပါတယ်: system တစ်ခု ပျက်ကျသွားခဲ့ရင် — နောက်ဆုံး checkpoint နောက်ပိုင်း ပြုလုပ်ခဲ့တဲ့ log entries တွေကို “replay” (ပြန်လည် ဖွင့်သုံး) လုပ်ခြင်းအားဖြင့် — database ကို တသမတ်တည်း (consistent) အခြေအနေဆီ ပြန်လည် ရောက်ရှိစေနိုင်လို့ပါ။ ဒါပေမယ့် — ဒီ log ရှိနေတာကြောင့် — databases တွေကို backup လုပ်ဖို့ တတိယ နည်းဗျူဟာ တစ်ခုကို သုံးနိုင်ပါတယ်: file-system-level backup တစ်ခုကို WAL ဖိုင်တွေရဲ့ backup နဲ့ ပေါင်းစပ် သုံးနိုင်ပါတယ်။ Recovery (ပြန်လည် ရယူခြင်း) လိုအပ်ခဲ့ရင် — file system backup ကို ပြန်လည် တည်ဆောက်ပြီး — system ကို လက်ရှိ အခြေအနေဆီ ရောက်ရှိစေဖို့ — backup လုပ်ထားတဲ့ WAL ဖိုင်တွေကနေ replay လုပ်ပါတယ်။ ဒီနည်းလမ်းက အရင်က ဖော်ပြခဲ့တဲ့ နည်းလမ်း နှစ်ခုထက် စီမံခန့်ခွဲရတာ ပိုရှုပ်ထွေးပေမယ့် — အရေးပါတဲ့ အကျိုးကျေးဇူးတွေ အတော်များများ ရှိပါတယ်:

- စမှတ်အဖြစ် လုံးဝ consistent ဖြစ်တဲ့ file system backup တစ်ခု မလိုအပ်ပါဘူး။ Backup ထဲမှာ ရှိတဲ့ ဘယ် internal inconsistency (အတွင်းပိုင်း ကိုက်ညီမှု မရှိမှု) ကိုမဆို — log replay က ပြုပြင် ပေးပါလိမ့်မယ် (ဒါက crash recovery (crash ပျက်ကျပြီးနောက် ပြန်လည် ရယူခြင်း) အတွင်း ဖြစ်ပျက်တာနဲ့ သိသိသာသာ မကွာခြားပါဘူး)။ ဒါကြောင့် — file system snapshot စွမ်းရည် (capability) မလိုဘဲ — tar ဒါမှမဟုတ် အလားတူ archiving tool တစ်ခုပဲ လုံလောက်ပါတယ်။
- Replay အတွက် WAL ဖိုင်တွေရဲ့ အဆုံးမရှိ ရှည်လျားတဲ့ sequence တစ်ခုကို ပေါင်းစပ် သုံးနိုင်တာမို့ — WAL ဖိုင်တွေကို ဆက်တိုက် archive လုပ်နေရုံနဲ့ — continuous backup (စဉ်ဆက်မပြတ် backup) ကို ရရှိနိုင်ပါတယ်။ ဒါက — အပြည့်အဝ backup တစ်ခုကို မကြာခဏ ယူရတာ အဆင်မပြေနိုင်တဲ့ — ကြီးမားတဲ့ databases တွေအတွက် အထူး အဖိုးတန်ပါတယ်။
- WAL entries တွေကို အဆုံးအထိ အမြဲတမ်း replay လုပ်ဖို့ မလိုအပ်ပါဘူး။ Replay ကို ဘယ်အမှတ်မှာမဆို ရပ်တန့်ပြီး — အဲဒီအချိန်က ရှိခဲ့တဲ့အတိုင်း — database ရဲ့ consistent snapshot (တသမတ်တည်း ဖြစ်သော ပုံရိပ်) တစ်ခုကို ရရှိနိုင်ပါတယ်။ ဒါကြောင့် — ဒီ technique က point-in-time recovery (PITR — သတ်မှတ် အချိန်ကာလသို့ ပြန်လည် ရယူခြင်း) ကို ထောက်ပံ့ပေးပါတယ်: base backup ယူပြီးကတည်းက — ဘယ်အချိန်မဆို — database ရဲ့ အခြေအနေဆီ ပြန်လည် တည်ဆောက်ဖို့ ဖြစ်နိုင်ပါတယ်။
- WAL ဖိုင်တွေရဲ့ အစီအစဉ်ကို — တူညီတဲ့ base backup ဖိုင်တွေ တင်ထားပြီးသား — အခြား machine တစ်ခုဆီ စဉ်ဆက်မပြတ် ပို့ဆောင်နေမယ်ဆိုရင် — warm standby system (warm standby — စဉ်ဆက်မပြတ် run နေသော အရန် system) တစ်ခု ရှိပါတယ်: ဘယ်အချိန်မဆို ဒုတိယ machine ကို တက်လို့ရပြီး — database ရဲ့ လက်ရှိအချိန်နဲ့ နီးစပ်တဲ့ မိတ္တူ (copy) တစ်ခု ရှိမှာ ဖြစ်ပါတယ်။

> **မှတ်ချက်:** pg_dump နဲ့ pg_dumpall တို့က file-system-level backups တွေကို ထုတ်လုပ်ပေးတာ မဟုတ်ဘဲ — continuous-archiving solution (စဉ်ဆက်မပြတ် archiving ဖြေရှင်းချက်) တစ်ခုရဲ့ အစိတ်အပိုင်း အဖြစ် သုံးလို့ မရပါဘူး။ အဲဒီလို dumps တွေက logical (ယုတ္တိ အဆင့်) ဖြစ်ပြီး — WAL replay က သုံးဖို့ လုံလောက်တဲ့ အချက်အလက် မပါဝင်ပါဘူး။

သာမန် file-system-backup technique လိုပဲ — ဒီနည်းလမ်းကလည်း database cluster တစ်ခုလုံးကိုပဲ restore လုပ်တာကို ထောက်ပံ့နိုင်ပြီး — အစိတ်အပိုင်း (subset) တစ်ခုကိုတော့ မထောက်ပံ့ပါဘူး။ ထို့အပြင် — archival storage (မှတ်တမ်း သိုလှောင်မှု) အများကြီး လိုအပ်ပါတယ်: base backup က ကြီးမားနိုင်ပြီး — busy (လုပ်ငန်းရှုပ်ထွေးသော) system တစ်ခုက — archive လုပ်ရမယ့် — WAL traffic megabytes များစွာကို ထုတ်ပေးပါလိမ့်မယ်။ ဒါပေမယ့် — မြင့်မားတဲ့ ယုံကြည်စိတ်ချရမှု (high reliability) လိုအပ်တဲ့ အခြေအနေ များစွာမှာတော့ — ဒါက ဦးစားပေး backup technique ဖြစ်နေဆဲပါ။

Continuous archiving (database vendors အများစုက “online backup” လို့လည်း ခေါ်ကြပါတယ်) ကို သုံးပြီး အောင်မြင်စွာ recover (ပြန်လည် ရယူ) လုပ်ဖို့ဆိုရင် — သင့် backup ရဲ့ စတင်ချိန် (start time) အထိ အနည်းဆုံး နောက်ပြန် ရောက်ရှိတဲ့ — archived WAL ဖိုင်တွေရဲ့ စဉ်ဆက်မပြတ် sequence တစ်ခု လိုအပ်ပါတယ်။ ဒါကြောင့် — စတင်လုပ်ဖို့ — ပထမဆုံး base backup မယူခင် — WAL ဖိုင်တွေကို archive လုပ်တဲ့ လုပ်ငန်းစဉ်ကို သတ်မှတ်ပြီး စမ်းသပ်ထားသင့်ပါတယ်။ ဒါနဲ့အညီ — WAL ဖိုင်တွေကို archive လုပ်ခြင်းရဲ့ ယန္တရားကို အရင်ဆုံး ဆွေးနွေးပါမယ်။
### 25.3.1. Setting Up WAL Archiving (WAL archiving ကို ပြင်ဆင် သတ်မှတ်ခြင်း)

စိတ်ကူးယဉ်ဆန်တဲ့ (abstract) အဓိပ္ပာယ်အရ — run နေတဲ့ PostgreSQL system တစ်ခုက WAL records တွေရဲ့ အဆုံးမရှိ ရှည်လျားတဲ့ sequence တစ်ခုကို ထုတ်လုပ်ပါတယ်။ System က ဒီ sequence ကို — ပုံမှန်အားဖြင့် တစ်ခုလျှင် 16MB ရှိတဲ့ — WAL *segment files* တွေအဖြစ် ရုပ်ပိုင်းဆိုင်ရာအရ ပိုင်းခြားပါတယ် (segment size ကို initdb အတွင်း ပြောင်းလဲနိုင်ပေမယ့်)။ Segment files တွေကို — abstract WAL sequence ထဲမှာ သူတို့ရဲ့ နေရာကို ထင်ဟပ်စေတဲ့ — ဂဏန်း (numeric) အမည်တွေနဲ့ ပေးထားပါတယ်။ WAL archiving မသုံးတဲ့အခါ — system က ပုံမှန်အားဖြင့် segment files အနည်းငယ်ကိုပဲ ဖန်တီးပြီး — မလိုအပ်တော့တဲ့ segment files တွေကို ပိုမြင့်တဲ့ segment နံပါတ်တွေဆီ အမည်ပြောင်းခြင်းအားဖြင့် “recycle” (ပြန်လည် အသုံးပြု) လုပ်ပါတယ်။ နောက်ဆုံး checkpoint ထက် ရှေ့ကျတဲ့ ပါဝင်စရာတွေ ရှိတဲ့ segment files တွေကို စိတ်ဝင်စားစရာ မလိုတော့ဘူးလို့ ယူဆပြီး — recycle လုပ်နိုင်တယ်လို့ ယူဆထားပါတယ်။

WAL data တွေကို archive လုပ်တဲ့အခါ — segment file တစ်ခုစီရဲ့ ပါဝင်စရာတွေကို — ၎င်း ပြည့်သွားတာနဲ့ — ဖမ်းယူ (capture) ပြီး — segment file ကို ပြန်လည် အသုံးပြုဖို့ recycle မလုပ်ခင် — အဲဒီ data တွေကို တစ်နေရာရာမှာ သိမ်းဆည်းထားဖို့ လိုအပ်ပါတယ်။ Application နဲ့ ရနိုင်တဲ့ hardware ပေါ် မူတည်ပြီး — “data တွေကို တစ်နေရာရာမှာ သိမ်းဆည်းခြင်း” အတွက် နည်းလမ်း အမျိုးမျိုး ရှိနိုင်ပါတယ်: segment files တွေကို အခြား machine တစ်ခုပေါ်က NFS-mounted directory (NFS ဖြင့် တပ်ဆင်ထားသော directory) ဆီ ကူးယူနိုင်သလို — tape drive (တိပ်ခွေ drive) ပေါ်ကို ရေးသားနိုင်ပါတယ် (ဖိုင်တစ်ခုချင်းစီရဲ့ မူရင်း အမည်ကို ခွဲခြားသိဖို့ နည်းလမ်း ရှိစေရပါမယ်) — ဒါမှမဟုတ် — ၎င်းတို့ကို စုပေါင်းပြီး CDs တွေပေါ် မီးရှို့ (burn) သွင်းနိုင်ပါတယ် — ဒါမှမဟုတ် လုံးဝ အခြား နည်းလမ်း တစ်ခုခုနဲ့လည်း ဖြစ်နိုင်ပါတယ်။ Database administrator ကို လိုက်လျောညီထွေမှု (flexibility) ပေးဖို့ — archiving ကို ဘယ်လို လုပ်မလဲဆိုတာနဲ့ ပတ်သက်ပြီး — PostgreSQL က ဘာ assumptions (ယူဆချက်များ) မှ မလုပ်ဖို့ ကြိုးစားပါတယ်။ အဲဒီအစား — PostgreSQL က administrator ကို — ပြီးသွားတဲ့ segment file တစ်ခုကို လိုအပ်တဲ့ နေရာဆီ ကူးယူဖို့ — shell command တစ်ခု ဒါမှမဟုတ် archive library (archive စာကြည့်တိုက်) တစ်ခုကို သတ်မှတ်ခွင့် ပြုပါတယ်။ ဒါက `cp` ကို သုံးတဲ့ ရိုးရှင်းတဲ့ shell command တစ်ခုလောက် ရိုးရှင်းနိုင်သလို — ရှုပ်ထွေးတဲ့ C function တစ်ခုကို ခေါ်ယူတာလည်း ဖြစ်နိုင်ပါတယ် — အကုန်လုံး သင်အပေါ်မှာ မူတည်ပါတယ်။

WAL archiving ကို enable (ဖွင့်) လုပ်ဖို့ — [wal_level](https://www.postgresql.org/docs/current/runtime-config-wal.html#GUC-WAL-LEVEL) configuration parameter ကို `replica` ဒါမှမဟုတ် ဒီထက် မြင့်တဲ့ အဆင့်ဆီ၊ [archive_mode](https://www.postgresql.org/docs/current/runtime-config-wal.html#GUC-ARCHIVE-MODE) ကို `on` ဆီ သတ်မှတ်ပြီး — [archive_command](https://www.postgresql.org/docs/current/runtime-config-wal.html#GUC-ARCHIVE-COMMAND) configuration parameter ထဲမှာ သုံးရမယ့် shell command ကို သတ်မှတ်ပါ ဒါမှမဟုတ် [archive_library](https://www.postgresql.org/docs/current/runtime-config-wal.html#GUC-ARCHIVE-LIBRARY) configuration parameter ထဲမှာ သုံးရမယ့် library ကို သတ်မှတ်ပါ။ လက်တွေ့မှာတော့ ဒီ settings တွေကို `postgresql.conf` ဖိုင်ထဲမှာ အမြဲ ထားလေ့ ရှိပါတယ်။

`archive_command` ထဲမှာ — `%p` ကို archive လုပ်ရမယ့် ဖိုင်ရဲ့ path name (လမ်းကြောင်း အမည်) နဲ့ အစားထိုးပြီး — `%f` ကိုတော့ ဖိုင် အမည်နဲ့ပဲ အစားထိုးပါတယ်။ (Path name က လက်ရှိ working directory — ဆိုလိုတာက cluster ရဲ့ data directory — နဲ့ ဆက်စပ်နေပါတယ်။) Command ထဲမှာ တကယ့် `%` character တစ်ခု ထည့်သွင်းဖို့ လိုအပ်ရင် `%%` ကို သုံးပါ။ အသုံးဝင်ဆုံး ရိုးရှင်းတဲ့ command က ဒီလိုမျိုး ဖြစ်ပါတယ်:

```sql
archive_command = 'test ! -f /mnt/server/archivedir/%f && cp %p /mnt/server/archivedir/%f'  # Unix
archive_command = 'copy "%p" "C:\\server\\archivedir\\%f"'  # Windows
```

အဲဒါက archivable WAL segments တွေကို `/mnt/server/archivedir` directory ဆီ ကူးယူပေးမှာ ဖြစ်ပါတယ်။ (ဒါက ဥပမာတစ်ခုပဲ ဖြစ်ပြီး — အကြံပြုချက် မဟုတ်ပါဘူး — platform တိုင်းမှာလည်း အလုပ်လုပ်ချင်မှ လုပ်ပါလိမ့်မယ်။) `%p` နဲ့ `%f` parameters တွေ အစားထိုးခံရပြီးနောက် — တကယ် execute လုပ်တဲ့ command က ဒီလိုမျိုး ဖြစ်နေနိုင်ပါတယ်:

```sql
test ! -f /mnt/server/archivedir/00000001000000A900000065 && cp pg_wal/00000001000000A900000065 /mnt/server/archivedir/00000001000000A900000065
```

Archive လုပ်ရမယ့် ဖိုင်အသစ် တစ်ခုစီအတွက် အလားတူ command တစ်ခုကို ထုတ်ပေးပါလိမ့်မယ်။

Archive command ကို — PostgreSQL server က run နေတဲ့ user နဲ့ အတူတူ — အဲဒီ user ရဲ့ ပိုင်ဆိုင်မှုအောက်မှာ execute လုပ်ပါလိမ့်မယ်။ Archive လုပ်နေတဲ့ WAL ဖိုင်တွေရဲ့ sequence ထဲမှာ သင့် database ထဲက အရာအားလုံး နီးပါး ပါဝင်တာမို့ — archived data တွေကို မလိုလားသူတွေရဲ့ မျက်စိကနေ ကာကွယ်ထားဖို့ သေချာစေချင်ပါလိမ့်မယ်; ဥပမာ — group ဒါမှမဟုတ် world read access (ဖတ်ခွင့်) မရှိတဲ့ directory တစ်ခုထဲကို archive လုပ်ပါ။

Archive command က အောင်မြင်တဲ့အခါမှသာ — zero exit status (ထွက်ပေါက် အခြေအနေ) ကို ပြန်ပေးဖို့ လိုအပ်တာ အရေးကြီးပါတယ်။ Zero ရလဒ် ရတဲ့အခါ — PostgreSQL က ဖိုင်ကို အောင်မြင်စွာ archive လုပ်ပြီးပြီလို့ ယူဆပြီး — ဖိုင်ကို ဖယ်ရှား ဒါမှမဟုတ် recycle လုပ်ပါလိမ့်မယ်။ ဒါပေမယ့် — nonzero status က ဖိုင်ကို archive မလုပ်ရသေးဘူးလို့ PostgreSQL ကို ပြောပြတာမို့ — အောင်မြင်တဲ့အထိ ကာလအလိုက် ထပ်ကြိုးစားပါလိမ့်မယ်။

Archive လုပ်ဖို့ နောက်တစ်နည်း ကတော့ — custom archive module တစ်ခုကို `archive_library` အဖြစ် သုံးတာ ဖြစ်ပါတယ်။ အဲဒီလို modules တွေကို `C` နဲ့ ရေးထားတာမို့ — ကိုယ်ပိုင် တစ်ခု ဖန်တီးတာက shell command တစ်ခု ရေးတာထက် အားထုတ်မှု သိသိသာသာ ပိုလိုနိုင်ပါတယ်။ ဒါပေမယ့် — archive modules တွေက shell ကတစ်ဆင့် archive လုပ်တာထက် ပိုပြီး ထိရောက်မှု (performance) မြင့်မားနိုင်ပြီး — အသုံးဝင်တဲ့ server resources တွေ အများအပြားကိုလည်း ဝင်ရောက် သုံးခွင့် ရှိပါလိမ့်မယ်။ Archive modules အကြောင်း နောက်ထပ် အချက်အလက်အတွက် [အခန်း 49](https://www.postgresql.org/docs/current/archive-modules.html) ကို ကြည့်ပါ။

Archive command ကို signal တစ်ခုက ရပ်တန့်စေတဲ့အခါ (server shutdown ရဲ့ အစိတ်အပိုင်း အဖြစ် သုံးတဲ့ SIGTERM ကလွဲရင်) — ဒါမှမဟုတ် shell ရဲ့ error တစ်ခုက 125 ထက် ပိုမြင့်တဲ့ exit status နဲ့ ဖြစ်ပေါ်ရင် (command not found — command ရှာမတွေ့ — လိုမျိုး) — ဒါမှမဟုတ် archive function က `ERROR` ဒါမှမဟုတ် `FATAL` တစ်ခုကို ထုတ်လွှတ်ရင် — archiver process က ရပ်ဆိုင်းသွားပြီး — postmaster က ပြန်လည် စတင်ပေးပါတယ်။ အဲဒီလို အခြေအနေမျိုးမှာ — ဒီ failure ကို [pg_stat_archiver](https://www.postgresql.org/docs/current/monitoring-stats.html#PG-STAT-ARCHIVER-VIEW) view ထဲမှာ သတင်းပို့ မထားပါဘူး။

Archive commands နဲ့ libraries တွေက ယေဘုယျအားဖြင့် — ရှိပြီးသား archive ဖိုင်တစ်ခုခုကို overwrite (အစားထိုး ရေးသား) လုပ်ဖို့ ငြင်းဆန်အောင် ဒီဇိုင်းလုပ်ထားသင့်ပါတယ်။ ဒါက — administrator error (administrator ၏ အမှား) ဖြစ်ရင် (ဥပမာ — server နှစ်ခုရဲ့ output တွေကို archive directory တစ်ခုတည်းဆီ ပို့လိုက်တာမျိုး) — သင့် archive ရဲ့ ခိုင်မာမှု (integrity) ကို ထိန်းသိမ်းဖို့ အရေးကြီးတဲ့ ဘေးကင်းရေး feature တစ်ခု ဖြစ်ပါတယ်။ သင်ခန့်မှန်းထားတဲ့ archive library က ရှိပြီးသား ဖိုင်တစ်ခုကို overwrite မလုပ်ဘူးဆိုတာ သေချာစေဖို့ — ၎င်းကို စမ်းသပ်ကြည့်ဖို့ အကြံပြုလိုပါတယ်။

ရှားရှားပါးပါး အခြေအနေတွေမှာ — PostgreSQL က အရင်က archive လုပ်ပြီးသား WAL ဖိုင်တစ်ခုကို ပြန်လည် archive လုပ်ဖို့ ကြိုးစားနိုင်ပါတယ်။ ဥပမာ — server က archival success ရဲ့ ကြာရှည်ခံတဲ့ (durable) မှတ်တမ်းတစ်ခုကို မလုပ်နိုင်ခင် system က ပျက်ကျသွားခဲ့ရင် — server က (archiving ကို ဆက် enable လုပ်ထားသေးရင်) restart လုပ်ပြီးနောက် ဖိုင်ကို ထပ်မံ archive လုပ်ဖို့ ကြိုးစားပါလိမ့်မယ်။ Archive command ဒါမှမဟုတ် library တစ်ခုက ရှိပြီးသား ဖိုင်တစ်ခုကို တွေ့တဲ့အခါ — WAL ဖိုင်ရဲ့ ပါဝင်စရာတွေက ရှိပြီးသား archive နဲ့ တူညီပြီး — ရှိပြီးသား archive က storage ပေါ်မှာ အပြည့်အဝ persist (ထာဝရ သိမ်းဆည်း) လုပ်ပြီးသား ဖြစ်ရင် — archive command က zero status ကို ပြန်ပေးရပါမယ် — archive library ကတော့ `true` ကို ပြန်ပေးရပါမယ်။ ရှိပြီးသား ဖိုင်တစ်ခုထဲမှာ archive လုပ်နေတဲ့ WAL ဖိုင်ရဲ့ ပါဝင်စရာတွေနဲ့ မတူညီတဲ့ ပါဝင်စရာတွေ ပါနေရင် — archive command က nonzero status ကို ပြန်ပေးရမှာ ဖြစ်ပြီး — archive library ကတော့ `false` ကို ပြန်ပေးရပါမယ်။

Unix အတွက် အပေါ်က ဥပမာ command က — သီးခြား `test` အဆင့် တစ်ခု ထည့်သွင်းခြင်းအားဖြင့် — ရှိပြီးသား archive တစ်ခုကို overwrite လုပ်တာကို ရှောင်ပါတယ်။ Unix platform တချို့မှာ — `cp` မှာ အဲဒီလို လုပ်ဖို့ — `-i` လို — စကားလုံး နည်းနည်းနဲ့ လုပ်နိုင်တဲ့ switches တွေ ရှိပေမယ့် — မှန်ကန်တဲ့ exit status ကို ပြန်ပေးတာ သေချာအောင် စစ်ဆေးခြင်း မရှိဘဲ — အဲဒါတွေကို အားမကိုးသင့်ပါဘူး။ (အထူးသဖြင့် — GNU `cp` က `-i` သုံးပြီး target ဖိုင် ရှိပြီးသား ဖြစ်နေရင် — status zero ကို ပြန်ပေးပါတယ် — အဲဒါက လိုချင်တဲ့ အပြုအမူ မဟုတ်ပါဘူး။)

သင့် archiving setup ကို ဒီဇိုင်းလုပ်နေတုန်း — archive command ဒါမှမဟုတ် library က — operator (လည်ပတ်သူ) ရဲ့ ဝင်ရောက် စွက်ဖက်မှု တစ်ခုခု လိုအပ်တာ ဒါမှမဟုတ် archive မှာ နေရာ ကုန်သွားတာလိုမျိုး — အကြောင်းရင်းတစ်ခုခုကြောင့် — ထပ်ခါထပ်ခါ ကျရှုံးနေရင် ဘာဖြစ်မလဲဆိုတာကို စဉ်းစားပါ။ ဥပမာ — autochanger (အလိုအလျောက် ပြောင်းစက်) မပါဘဲ tape ပေါ် ရေးနေတယ်ဆိုရင် — ဒီလို ဖြစ်နိုင်ပါတယ်: tape ပြည့်သွားတဲ့အခါ — tape ကို လဲလှယ်မပေးမချင်း — ဘာမှ ဆက် archive လုပ်လို့ မရတော့ပါဘူး။ Error condition ဒါမှမဟုတ် လူသား operator တစ်ယောက်ဆီက တောင်းဆိုမှု ဘယ်ဟာမဆို — အခြေအနေကို ကျိုးကြောင်းဆီလျော်လောက်အောင် မြန်မြန် ဖြေရှင်းနိုင်အောင် — သင့်လျော်စွာ သတင်းပို့ခံရဖို့ သေချာစေသင့်ပါတယ်။ အခြေအနေ ဖြေရှင်းမချင်း — `pg_wal/` directory ထဲမှာ WAL segment files တွေ ဆက်ပြီး ပြည့်လာနေမှာ ဖြစ်ပါတယ်။ (`pg_wal/` ပါဝင်တဲ့ file system ပြည့်သွားခဲ့ရင် — PostgreSQL က PANIC shutdown လုပ်ပါလိမ့်မယ်။ Commit လုပ်ပြီးသား transactions တွေ ဘာမှ မဆုံးရှုံးပေမယ့် — နေရာ လွတ်အောင် မလုပ်ပေးမချင်း — database က offline ဖြစ်နေမှာ ဖြစ်ပါတယ်။)

Archive command ဒါမှမဟုတ် library ရဲ့ မြန်နှုန်းက — သင့် server က WAL data တွေကို ထုတ်လုပ်တဲ့ ပျမ်းမျှ နှုန်းကို လိုက်မီနေသရွေ့တော့ — အရေးမကြီးပါဘူး။ Archiving process က အနည်းငယ် နောက်ကျနေရင်တောင် — ပုံမှန် လည်ပတ်မှု ဆက်လက် ဖြစ်ပေါ်နေပါတယ်။ Archiving က သိသိသာသာ နောက်ကျနေမယ်ဆိုရင် — ဘေးအန္တရာယ် (disaster) တစ်ခု ဖြစ်ခဲ့ရင် ဆုံးရှုံးသွားမယ့် data ပမာဏကို တိုးစေပါလိမ့်မယ်။ ထို့အပြင် — `pg_wal/` directory ထဲမှာ — archive မလုပ်ရသေးတဲ့ segment files အများအပြား ပါဝင်လာပြီး — နောက်ဆုံးမှာ ရနိုင်တဲ့ disk space ထက် ကျော်လွန်သွားနိုင်ပါတယ်။ Archiving process က သင်ရည်ရွယ်ထားတဲ့အတိုင်း အလုပ်လုပ်နေဖို့ — စောင့်ကြည့် (monitor) လုပ်ဖို့ အကြံပြုလိုပါတယ်။

သင့် archive command ဒါမှမဟုတ် library ကို ရေးတဲ့အခါ — archive လုပ်ရမယ့် ဖိုင် အမည်တွေက အလျား 64 characters အထိ ရှိနိုင်ပြီး — ASCII letters (စာလုံးများ), digits (ဂဏန်းများ) နဲ့ dots (အစက်များ) ရဲ့ ဘယ်ပေါင်းစပ်မှုမဆို ပါဝင်နိုင်တယ်လို့ ယူဆထားသင့်ပါတယ်။ မူရင်း relative path (`%p`) ကို ထိန်းသိမ်း စရာ မလိုပေမယ့် — ဖိုင် အမည် (`%f`) ကိုတော့ ထိန်းသိမ်း ဖို့ လိုအပ်ပါတယ်။

WAL archiving က သင့် PostgreSQL database ထဲက data တွေဆီ ပြုလုပ်တဲ့ ပြုပြင်မွမ်းမံမှု တွေကို ပြန်လည် တည်ဆောက်ခွင့် ပေးပေမယ့် — configuration ဖိုင်တွေ (ဆိုလိုတာက `postgresql.conf`, `pg_hba.conf` နဲ့ `pg_ident.conf`) ဆီ ပြုလုပ်တဲ့ ပြောင်းလဲမှုတွေကိုတော့ ပြန်လည် တည်ဆောက်ပေးမှာ မဟုတ်ဘူးဆိုတာ သတိပြုပါ — အကြောင်းကတော့ အဲဒါတွေကို SQL operations တွေကတစ်ဆင့် မဟုတ်ဘဲ — လက်နဲ့ တည်းဖြတ်လို့ပါ။ Configuration ဖိုင်တွေကို — သင့် ပုံမှန် file system backup လုပ်ငန်းစဉ်တွေနဲ့ backup ခံရမယ့် — နေရာတစ်ခုမှာ ထားချင်နိုင်ပါတယ်။ Configuration ဖိုင်တွေကို ဘယ်လို ပြောင်းရွှေ့ရမလဲဆိုတာအတွက် [အပိုင်း 19.2](https://www.postgresql.org/docs/current/runtime-config-file-locations.html) ကို ကြည့်ပါ။

Archive command ဒါမှမဟုတ် function ကို — ပြီးမြောက်သွားတဲ့ WAL segments တွေပေါ်မှာပဲ ခေါ်ယူပါတယ်။ ဒါကြောင့် — သင့် server က WAL traffic အနည်းငယ်ပဲ ထုတ်လုပ်ရင် (ဒါမှမဟုတ် အဲဒီလို ဖြစ်တဲ့ အချိန်လပ် (slack periods) တွေ ရှိရင်) — transaction တစ်ခု ပြီးမြောက်တာနဲ့ — archive storage ထဲမှာ ၎င်းကို ဘေးကင်းစွာ မှတ်တမ်းတင်ခံရတာကြားမှာ — ကြာမြင့်ချိန် ရှည်လျားနိုင်ပါတယ်။ Archive မလုပ်ရသေးတဲ့ data ဘယ်လောက် ရှေးကျနိုင်လဲဆိုတာ ကန့်သတ်ချက် တစ်ခု ထားဖို့ — [archive_timeout](https://www.postgresql.org/docs/current/runtime-config-wal.html#GUC-ARCHIVE-TIMEOUT) ကို သတ်မှတ်ပြီး — server က အနည်းဆုံး အဲဒီလောက် ကြာတိုင်း WAL segment file အသစ်တစ်ခုဆီ switch လုပ်အောင် အတင်းအကျပ် လုပ်နိုင်ပါတယ်။ အတင်းအကျပ် switch လုပ်မှုကြောင့် စောစော archive ခံရတဲ့ ဖိုင်တွေက — လုံးဝ ပြည့်နေတဲ့ ဖိုင်တွေနဲ့ တူညီတဲ့ အလျား ရှိနေဆဲပဲ ဆိုတာ သတိပြုပါ။ ဒါကြောင့် — အလွန် တိုတောင်းတဲ့ `archive_timeout` တစ်ခုကို သတ်မှတ်တာ မပညာရှိရာပါဘူး — အဲဒါက သင့် archive storage ကို ဖောင်းပွစေပါလိမ့်မယ်။ တစ်မိနစ်လောက် ရှိတဲ့ `archive_timeout` settings တွေက များသောအားဖြင့် ကျိုးကြောင်းဆီလျော်ပါတယ်။

ထို့အပြင် — အခုနက ပြီးစီးသွားတဲ့ transaction တစ်ခုကို ဖြစ်နိုင်သမျှ မြန်မြန် archive လုပ်ခံရစေချင်ရင် — `pg_switch_wal` နဲ့ segment switch တစ်ခုကို လက်နဲ့လည်း အတင်းအကျပ် လုပ်နိုင်ပါတယ်။ WAL management နဲ့ ဆက်စပ်တဲ့ တခြား utility functions တွေကို [ဇယား 9.97](https://www.postgresql.org/docs/current/functions-admin.html#FUNCTIONS-ADMIN-BACKUP-TABLE) မှာ စာရင်းပြုထားပါတယ်။

`wal_level` က `minimal` ဖြစ်နေတဲ့အခါ — [အပိုင်း 14.4.7](https://www.postgresql.org/docs/current/populate.html#POPULATE-PITR) မှာ ဖော်ပြထားသလို — SQL commands တချို့က WAL logging ကို ရှောင်ဖို့ optimize လုပ်ထားပါတယ်။ အဲဒီ statements တွေထဲက တစ်ခု execute လုပ်နေတဲ့ အချိန်အတွင်း archiving ဒါမှမဟုတ် streaming replication ကို ဖွင့်ထားခဲ့မယ်ဆိုရင် — WAL ထဲမှာ archive recovery အတွက် လုံလောက်တဲ့ အချက်အလက် ပါဝင်မှာ မဟုတ်ပါဘူး။ (Crash recovery ကိုတော့ ထိခိုက်မှု မရှိပါဘူး။) ဒီအကြောင်းကြောင့် — `wal_level` ကို server စတင်ချိန်မှာပဲ ပြောင်းလဲနိုင်ပါတယ်။ ဒါပေမယ့် — `archive_command` နဲ့ `archive_library` တို့ကိုတော့ configuration ဖိုင် reload တစ်ခုနဲ့ ပြောင်းလဲနိုင်ပါတယ်။ Shell ကတစ်ဆင့် archive လုပ်နေပြီး — archiving ကို ယာယီ ရပ်တန့်ချင်ရင် — နည်းလမ်းတစ်ခုက `archive_command` ကို empty string (`''`) အဖြစ် သတ်မှတ်တာ ဖြစ်ပါတယ်။ ဒါက — အလုပ်လုပ်တဲ့ `archive_command` တစ်ခု ပြန်လည် တည်ဆောက်မချင်း — WAL ဖိုင်တွေ `pg_wal/` ထဲမှာ စုပုံလာစေပါလိမ့်မယ်။
### 25.3.2. Making a Base Backup (base backup တစ်ခု ပြုလုပ်ခြင်း)

Base backup တစ်ခုကို လုပ်ဆောင်ဖို့ အလွယ်ဆုံး နည်းလမ်းကတော့ [pg_basebackup](https://www.postgresql.org/docs/current/app-pgbasebackup.html) tool ကို သုံးတာ ဖြစ်ပါတယ်။ ၎င်းက base backup တစ်ခုကို — သာမန် ဖိုင်တွေ (regular files) အနေနဲ့ ဒါမှမဟုတ် tar archive တစ်ခုအနေနဲ့ — ဖန်တီးနိုင်ပါတယ်။ [pg_basebackup](https://www.postgresql.org/docs/current/app-pgbasebackup.html) ပေးနိုင်တာထက် ပိုပြီး လိုက်လျောညီထွေမှု လိုအပ်ရင် — low level API ကို သုံးပြီးလည်း base backup တစ်ခု လုပ်နိုင်ပါတယ် ([အပိုင်း 25.3.4](https://www.postgresql.org/docs/current/continuous-archiving.html#BACKUP-LOWLEVEL-BASE-BACKUP) ကို ကြည့်ပါ)။

Base backup တစ်ခု ယူဖို့ ကြာမြင့်တဲ့ အချိန် ပမာဏနဲ့ ပတ်သက်ပြီး စိုးရိမ်စရာ မလိုပါဘူး။ ဒါပေမယ့် — server ကို `full_page_writes` disabled (ပိတ်ထား) ပြီး ပုံမှန် run လုပ်နေတယ်ဆိုရင် — backup mode အတွင်းမှာ `full_page_writes` က ထိရောက်စွာ force (အတင်းအကျပ်) ဖွင့်ခံထားရလို့ — backup run နေတဲ့ အချိန်အတွင်း performance ကျဆင်းမှုကို သတိထားမိနိုင်ပါတယ်။

Backup ကို အသုံးပြုဖို့ — file system backup အတွင်း နဲ့ နောက်ပိုင်းမှာ ထုတ်လုပ်ခဲ့တဲ့ WAL segment files တွေ အားလုံးကို ထိန်းသိမ်းထားဖို့ လိုအပ်ပါလိမ့်မယ်။ ဒါကို ကူညီဖို့ — base backup လုပ်ငန်းစဉ်က *backup history file* (backup သမိုင်း ဖိုင်) တစ်ခုကို ဖန်တီးပြီး — ၎င်းကို WAL archive area ထဲမှာ ချက်ချင်း သိမ်းဆည်းပါတယ်။ ဒီဖိုင်ကို — file system backup အတွက် လိုအပ်တဲ့ ပထမဆုံး WAL segment file ရဲ့ အမည်နဲ့အညီ — အမည်ပေးပါတယ်။ ဥပမာ — စတင်တဲ့ WAL ဖိုင်က `0000000100001234000055CD` ဆိုရင် — backup history file ကို `0000000100001234000055CD.007C9330.backup` လိုမျိုး အမည်တစ်ခုနဲ့ ပေးမှာ ဖြစ်ပါတယ်။ (ဖိုင် အမည်ရဲ့ ဒုတိယ အပိုင်းက WAL ဖိုင်အတွင်းက တိကျတဲ့ နေရာကို ကိုယ်စားပြုပြီး — သာမန်အားဖြင့် လျစ်လျူရှုနိုင်ပါတယ်။) File system backup နဲ့ backup အတွင်း သုံးခဲ့တဲ့ WAL segment files တွေကို (backup history file ထဲမှာ သတ်မှတ်ထားတဲ့အတိုင်း) ဘေးကင်းစွာ archive လုပ်ပြီးတာနဲ့ — file system backup ကို recover လုပ်ဖို့ — ဂဏန်းအရ ပိုငယ်တဲ့ အမည်တွေ ရှိတဲ့ archived WAL segments တွေ အားလုံး မလိုအပ်တော့ဘဲ — ဖျက်ပစ်နိုင်ပါတယ်။ ဒါပေမယ့် — သင့် data တွေကို ပြန်လည် ရယူနိုင်ဖို့ လုံးဝ သေချာစေဖို့ — backup sets (backup အစုအဝေးများ) များစွာကို ထိန်းသိမ်းထားဖို့ စဉ်းစားသင့်ပါတယ်။

Backup history file က သေးငယ်တဲ့ text ဖိုင်တစ်ခုပဲ ဖြစ်ပါတယ်။ ၎င်းထဲမှာ [pg_basebackup](https://www.postgresql.org/docs/current/app-pgbasebackup.html) ကို သင်ပေးခဲ့တဲ့ label string (အညွှန်း string) ရော — backup ရဲ့ စတင်ချိန် နဲ့ ပြီးဆုံးချိန် နဲ့ WAL segments တွေပါ ပါဝင်ပါတယ်။ ဆက်စပ်နေတဲ့ dump ဖိုင်ကို ခွဲခြားသိဖို့ label ကို သုံးခဲ့မယ်ဆိုရင် — archive လုပ်ထားတဲ့ history ဖိုင်က — ဘယ် dump ဖိုင်ကို restore လုပ်ရမယ်ဆိုတာ ပြောပြဖို့ လုံလောက်ပါတယ်။

နောက်ဆုံး base backup အထိ နောက်ပြန် — archived WAL ဖိုင်တွေ အားလုံးကို ထိန်းသိမ်းထားရမှာ ဖြစ်လို့ — base backups တွေကြားက ကြားကာလ (interval) ကို — archived WAL ဖိုင်တွေပေါ်မှာ သင်ဘယ်လောက် storage သုံးစွဲချင်လဲဆိုတာကို အခြေခံပြီး — ပုံမှန်အားဖြင့် ရွေးချယ်သင့်ပါတယ်။ Recovery လိုအပ်ခဲ့ရင် — ပြန်လည် ရယူဖို့ အချိန် ဘယ်လောက် သုံးစွဲဖို့ ပြင်ဆင်ထားလဲဆိုတာကိုလည်း စဉ်းစားသင့်ပါတယ် — system က အဲဒီ WAL segments တွေ အားလုံးကို replay လုပ်ရမှာ ဖြစ်ပြီး — နောက်ဆုံး base backup ကတည်းက အချိန် အတော်ကြာသွားပြီဆိုရင် — အဲဒါက အချိန် အတော်ကြာနိုင်ပါတယ်။

### 25.3.3. Making an Incremental Backup (incremental backup တစ်ခု ပြုလုပ်ခြင်း)

[pg_basebackup](https://www.postgresql.org/docs/current/app-pgbasebackup.html) ကို `--incremental` option သတ်မှတ်ပြီး သုံးခြင်းအားဖြင့် incremental backup (incremental backup — ယခင် backup နောက်ပိုင်း ပြောင်းလဲမှုများသာ ပါဝင်သော backup) တစ်ခုကို ယူနိုင်ပါတယ်။ `--incremental` ရဲ့ argument အဖြစ် — server တစ်ခုတည်းကနေ အရင်က ယူထားတဲ့ backup တစ်ခုရဲ့ backup manifest (backup စာရင်းချုပ်) ကို ထောက်ပံ့ပေးရပါမယ်။ ရလဒ် backup ထဲမှာ — relation မဟုတ်တဲ့ ဖိုင်တွေကို အပြည့်အဝ ထည့်သွင်းပေမယ့် — relation ဖိုင်တချို့ကို — အရင် backup နောက်ပိုင်း ပြောင်းလဲသွားတဲ့ blocks တွေနဲ့ ဖိုင်ရဲ့ လက်ရှိ version ကို ပြန်လည် တည်ဆောက်ဖို့ လုံလောက်တဲ့ metadata တွေပဲ ပါဝင်တဲ့ — ပိုသေးငယ်တဲ့ incremental ဖိုင်တွေနဲ့ အစားထိုးခံရနိုင်ပါတယ်။

ဘယ် blocks တွေကို backup လုပ်ဖို့ လိုလဲ ဆုံးဖြတ်ဖို့ — server က WAL summaries (WAL အကျဉ်းချုပ်များ) တွေကို သုံးပါတယ် — အဲဒါတွေကို data directory ထဲက `pg_wal/summaries` directory ထဲမှာ သိမ်းဆည်းထားပါတယ်။ လိုအပ်တဲ့ summary ဖိုင်တွေ မရှိဘူးဆိုရင် — incremental backup တစ်ခု ယူဖို့ ကြိုးစားမှုက ကျရှုံးပါလိမ့်မယ်။ ဒီ directory ထဲမှာ ရှိနေတဲ့ summaries တွေက — အရင် backup ရဲ့ start LSN (စတင် LSN) ကနေ လက်ရှိ backup ရဲ့ start LSN အထိ — LSNs အားလုံးကို လွှမ်းခြုံ (cover) ထားရပါမယ်။ Server က — လက်ရှိ backup ရဲ့ start LSN ကို တည်ဆောက်ပြီးတာနဲ့ ချက်ချင်း — WAL summaries တွေကို ရှာဖွေတာမို့ — လိုအပ်တဲ့ summary ဖိုင်တွေက disk ပေါ်မှာ ချက်ချင်း ရှိနေချင်မှ ရှိမှာ ဖြစ်ပေမယ့် — ပျောက်နေတဲ့ ဖိုင်တွေ ပေါ်လာတာကို server က စောင့်ဆိုင်းပေးပါလိမ့်မယ်။ WAL summarization process က နောက်ကျနေရင်လည်း ဒါက ကူညီပေးပါတယ်။ ဒါပေမယ့် — လိုအပ်တဲ့ ဖိုင်တွေကို ဖယ်ရှားလိုက်ပြီးသား ဖြစ်နေရင် — ဒါမှမဟုတ် WAL summarizer က လုံလောက်လောက်အောင် မြန်မြန် လိုက်မီမသွားရင် — incremental backup က ကျရှုံးပါလိမ့်မယ်။

Incremental backup တစ်ခုကို restore လုပ်တဲ့အခါ — incremental backup ကိုယ်တိုင် တစ်ခုတည်း မကဘဲ — incremental backup ထဲကနေ ချန်လှပ်ထားတဲ့ blocks တွေကို ထောက်ပံ့ဖို့ လိုအပ်တဲ့ — အစောပိုင်း backups တွေ အားလုံးလည်း ရှိဖို့ လိုအပ်ပါလိမ့်မယ်။ ဒီလိုအပ်ချက်အကြောင်း နောက်ထပ် အချက်အလက်အတွက် [pg_combinebackup](https://www.postgresql.org/docs/current/app-pgcombinebackup.html) ကို ကြည့်ပါ။ Cluster ရဲ့ checksum status ကို ပြောင်းလဲထားတဲ့အခါ `pg_combinebackup` ကို သုံးခြင်းမှာ ကန့်သတ်ချက်တွေ ရှိနေတာ သတိပြုပါ; [pg_combinebackup limitations](https://www.postgresql.org/docs/current/app-pgcombinebackup.html#APP-PGCOMBINEBACKUP-LIMITATIONS) ကို ကြည့်ပါ။

Full backup တစ်ခုကို အသုံးပြုခြင်းအတွက် လိုအပ်ချက်တွေ အားလုံးက incremental backup တစ်ခုအတွက်လည်း သက်ဆိုင်တယ်ဆိုတာ သတိပြုပါ။ ဥပမာ — file system backup အတွင်း နဲ့ နောက်ပိုင်းမှာ ထုတ်လုပ်ခဲ့တဲ့ WAL segment files တွေ အားလုံး နဲ့ သက်ဆိုင်တဲ့ WAL history ဖိုင်တွေ အားလုံး ဆက်လက် လိုအပ်နေဆဲပါ။ ထို့အပြင် — [အပိုင်း 25.3.5](https://www.postgresql.org/docs/current/continuous-archiving.html#BACKUP-PITR-RECOVERY) မှာ ဖော်ပြထားသလို — `recovery.signal` (ဒါမှမဟုတ် `standby.signal`) ကို ဖန်တီးပြီး recovery လုပ်ဆောင်ဖို့လည်း ဆက်လက် လိုအပ်ပါတယ်။ Restore လုပ်ချိန်မှာ အစောပိုင်း backups တွေ ရနိုင်ဖို့ လိုအပ်ချက်နဲ့ `pg_combinebackup` ကို သုံးဖို့ လိုအပ်ချက်က — တခြား လိုအပ်ချက်တွေ အားလုံးရဲ့ အပေါ်မှာ ထပ်ဆောင်း လိုအပ်ချက် ဖြစ်ပါတယ်။ နောက်ပိုင်း incremental backups တွေကို restore လုပ်ဖို့ အခြေခံ အဖြစ် — ဘယ် backups တွေ ဆက်လက် လိုအပ်နေသေးလဲဆိုတာကို ဆုံးဖြတ်ပေးမယ့် built-in (ထည့်သွင်းပြီးသား) ယန္တရား တစ်ခုခု PostgreSQL မှာ မရှိဘူးဆိုတာ သတိရပါ။ သင့် full နဲ့ incremental backups တွေကြားက ဆက်စပ်မှုတွေကို ကိုယ်တိုင် ခြေရာခံ ထားရမှာ ဖြစ်ပြီး — နောက်ပိုင်း incremental backups တွေကို restore လုပ်တဲ့အခါ လိုအပ်နိုင်တာမို့ — အစောပိုင်း backups တွေကို ဖယ်ရှားမိမှာ မဟုတ်အောင် သေချာစေရပါမယ်။

Incremental backups တွေက ပုံမှန်အားဖြင့် — data တွေရဲ့ သိသိသာသာ အစိတ်အပိုင်းက မပြောင်းလဲဘဲ ရှိနေတဲ့ ဒါမှမဟုတ် ဖြည်းညှင်းစွာသာ ပြောင်းလဲတဲ့ — ကြီးမားတဲ့ databases တွေအတွက်သာ အဓိပ္ပာယ် ရှိပါတယ်။ Database ငယ်တစ်ခုအတွက်ဆိုရင် — incremental backups တွေ ရှိနေတာကို လျစ်လျူရှုပြီး — စီမံခန့်ခွဲရ ပိုရိုးရှင်းတဲ့ — full backups တွေကိုပဲ ယူတာက ပိုရိုးရှင်းပါတယ်။ အစိတ်အပိုင်း အားလုံး ပြင်းပြင်းထန်ထန် ပြုပြင်ခံနေရတဲ့ ကြီးမားတဲ့ database တစ်ခုအတွက်ဆိုရင် — incremental backups တွေက full backups တွေထက် သိပ်မငယ်ပါဘူး။

Incremental backup တစ်ခုက — replay က — ၎င်း မှီခိုနေတဲ့ အရင် backup အတွက်ထက် — နောက်ပိုင်း checkpoint တစ်ခုကနေ စတင်မှသာ ဖြစ်နိုင်ပါတယ်။ Primary (ပင်မ server) ပေါ်မှာ incremental backup ကို ယူတယ်ဆိုရင် — ဒီအခြေအနေက အမြဲ ကျေနပ်ပါတယ် — အကြောင်းကတော့ backup တစ်ခုစီက checkpoint အသစ်တစ်ခုကို ဖြစ်ပေါ်စေလို့ပါ။ Standby (အရန် server) တစ်ခုပေါ်မှာတော့ — replay က နောက်အကျဆုံး restartpoint (restartpoint — standby ပေါ်ရှိ checkpoint နှင့် ဆင်တူသော အမှတ်) ကနေ စတင်ပါတယ်။ ဒါကြောင့် — standby server တစ်ခုရဲ့ incremental backup က — အရင် backup နောက်ပိုင်း လုပ်ဆောင်မှု အလွန် နည်းခဲ့မယ်ဆိုရင် — restartpoint အသစ် တစ်ခု မဖန်တီးနိုင်တာကြောင့် — ကျရှုံးနိုင်ပါတယ်။
### 25.3.4. Making a Base Backup Using the Low Level API (low level API သုံးပြီး base backup ပြုလုပ်ခြင်း)

[pg_basebackup](https://www.postgresql.org/docs/current/app-pgbasebackup.html) ကို သုံးပြီး full ဒါမှမဟုတ် incremental base backup တစ်ခု ယူမည့်အစား — low-level API ကို သုံးပြီးလည်း base backup တစ်ခု ယူနိုင်ပါတယ်။ ဒီလုပ်ငန်းစဉ်မှာ pg_basebackup နည်းလမ်းထက် အဆင့် အနည်းငယ် ပိုများပေမယ့် — အတော်လေး ရိုးရှင်းပါတယ်။ ဒီအဆင့်တွေကို အစီအစဉ်တကျ လုပ်ဆောင်ဖို့ နဲ့ — နောက်အဆင့်တစ်ခုဆီ မရွေ့ခင် — အဆင့်တစ်ခုရဲ့ အောင်မြင်မှုကို စစ်ဆေးအတည်ပြုဖို့ အလွန် အရေးကြီးပါတယ်။

Backup အများအပြားကို တစ်ပြိုင်နက် (concurrently) run လုပ်နိုင်ပါတယ် (ဒီ backup API ကို သုံးပြီး စတင်တာတွေရော — [pg_basebackup](https://www.postgresql.org/docs/current/app-pgbasebackup.html) ကို သုံးပြီး စတင်တာတွေပါ)။

1. WAL archiving ကို enable လုပ်ပြီး အလုပ်လုပ်နေကြောင်း သေချာပါစေ။
2. Server ဆီကို — pg_backup_start ကို run လုပ်ဖို့ အခွင့်အရေး ရှိတဲ့ user တစ်ယောက်အနေနဲ့ (superuser ဒါမှမဟုတ် function ပေါ်မှာ EXECUTE ခွင့်ပြုချက် ရရှိထားတဲ့ user — database ဘယ်ခု ဖြစ်ဖြစ် အရေးမကြီးပါဘူး) connect လုပ်ပြီး — အောက်ပါ command ကို ထုတ်ပြန်ပါ:
  
  SELECT pg_backup_start(label => 'label', fast => false);
  
  ဒီမှာ label က — ဒီ backup လုပ်ငန်းကို သီးခြား ခွဲခြားသိဖို့ သင်သုံးချင်တဲ့ ဘယ် string မဆို ဖြစ်ပါတယ်။ pg_backup_start ကို ခေါ်ယူထားတဲ့ connection ကို backup ပြီးဆုံးတဲ့အထိ ထိန်းသိမ်းထားရပါမယ် — မဟုတ်ရင် backup က အလိုအလျောက် ရပ်ဆိုင်း (abort) သွားပါလိမ့်မယ်။
  Online backups တွေက checkpoint တစ်ခုရဲ့ အစမှာ အမြဲ စတင်ပါတယ်။ Default အနေနဲ့ — pg_backup_start က နောက်ထပ် ပုံမှန် စီစဉ်ထားတဲ့ checkpoint တစ်ခု ပြီးမြောက်တာကို စောင့်ပါလိမ့်မယ် — အဲဒါက အချိန် အတော်ကြာနိုင်ပါတယ် (checkpoint_timeout နဲ့ checkpoint_completion_target configuration parameters တွေကို ကြည့်ပါ)။ ဒါက run နေတဲ့ system အပေါ် သက်ရောက်မှုကို အနည်းဆုံး ဖြစ်စေလို့ — များသောအားဖြင့် ပိုနှစ်သက်စရာ ကောင်းပါတယ်။ Backup ကို ဖြစ်နိုင်သမျှ မြန်မြန် စတင်ချင်ရင် — pg_backup_start ဆီ ဒုတိယ parameter အဖြစ် true ကို ပေးလိုက်ပါ — အဲဒါက ဖြစ်နိုင်သမျှ I/O အများဆုံး သုံးပြီး ဖြစ်နိုင်သမျှ မြန်မြန် ပြီးမြောက်မယ့် — ချက်ချင်း checkpoint တစ်ခုကို တောင်းဆိုပါလိမ့်မယ်။
3. tar ဒါမှမဟုတ် cpio လို — အဆင်ပြေတဲ့ file-system-backup tool ဘယ်ခုကိုမဆို သုံးပြီး — backup ကို လုပ်ဆောင်ပါ (pg_dump ဒါမှမဟုတ် pg_dumpall မဟုတ်ပါဘူး)။ ဒါကို လုပ်နေတဲ့ အချိန်အတွင်း database ရဲ့ ပုံမှန် လည်ပတ်မှုကို ရပ်တန့်ဖို့ မလိုအပ်သလို — ရပ်တန့်တာက မလိုလားအပ်ပါဘူး။ ဒီ backup အတွင်း စဉ်းစားရမယ့် အချက်တွေအတွက် အပိုင်း 25.3.4.1 ကို ကြည့်ပါ။
4. အရင်ကလိုပဲ connection တစ်ခုတည်းမှာပဲ — အောက်ပါ command ကို ထုတ်ပြန်ပါ:
  
  SELECT * FROM pg_backup_stop(wait_for_archive => true);
  
  ဒါက backup mode ကို အဆုံးသတ်ပါတယ်။ Primary တစ်ခုပေါ်မှာဆိုရင် — နောက် WAL segment တစ်ခုဆီ အလိုအလျောက် switch လုပ်ပေးပါတယ်။ Standby တစ်ခုပေါ်မှာတော့ — WAL segments တွေကို အလိုအလျောက် switch လုပ်ဖို့ မဖြစ်နိုင်လို့ — primary ပေါ်မှာ pg_switch_wal ကို run လုပ်ပြီး — manual switch တစ်ခု လုပ်ချင်နိုင်ပါတယ်။ Switch လုပ်ရတဲ့ အကြောင်းရင်းက — backup ကြားကာလ အတွင်း ရေးသားခဲ့တဲ့ နောက်ဆုံး WAL segment file ကို archive လုပ်ဖို့ အသင့် ဖြစ်စေဖို့ ပါ။
  pg_backup_stop က တန်ဖိုး သုံးခု ပါတဲ့ row တစ်ခုကို ပြန်ပေးပါလိမ့်မယ်။ ဒီ field တွေထဲက ဒုတိယ တစ်ခုကို backup ရဲ့ root directory ထဲမှာ backup_label လို့ အမည်ရတဲ့ ဖိုင်တစ်ခုထဲကို ရေးသားသင့်ပြီး — တတိယ field ကို — field က empty (ဗလာ) မဟုတ်ရင် — tablespace_map လို့ အမည်ရတဲ့ ဖိုင်တစ်ခုထဲကို ရေးသားသင့်ပါတယ်။ ဒီဖိုင်တွေက backup အလုပ်လုပ်ဖို့ အသက်သွေးကြော ဖြစ်ပြီး — ပြုပြင်မွမ်းမံမှု မရှိဘဲ byte တစ်လုံးချင်းအလိုက် (byte for byte) ရေးသားရပါမယ် — အဲဒါက ဖိုင်ကို binary mode နဲ့ ဖွင့်ဖို့ လိုအပ်စေနိုင်ပါတယ်။
5. Backup အတွင်း သက်ဝင်ခဲ့တဲ့ (active) WAL segment files တွေ archive လုပ်ခံရပြီးတာနဲ့ — ပြီးပါပြီ။ pg_backup_stop ရဲ့ ပထမ return value က ခွဲခြားသတ်မှတ်ပေးတဲ့ ဖိုင်က — ပြည့်စုံတဲ့ backup ဖိုင်အစု တစ်ခု ဖွဲ့စည်းဖို့ လိုအပ်တဲ့ နောက်ဆုံး segment ပဲ ဖြစ်ပါတယ်။ Primary တစ်ခုပေါ်မှာ — archive_mode က enable ဖြစ်ပြီး wait_for_archive parameter က true ဆိုရင် — နောက်ဆုံး segment archive လုပ်ခံရသည်အထိ pg_backup_stop က ပြန်မလာပါဘူး။ Standby တစ်ခုပေါ်မှာတော့ — pg_backup_stop က စောင့်ဆိုင်းဖို့ဆိုရင် — archive_mode က always ဖြစ်ရပါမယ်။ archive_command ဒါမှမဟုတ် archive_library ကို သင်ပြင်ဆင် သတ်မှတ်ပြီးသား ဖြစ်လို့ — ဒီဖိုင်တွေရဲ့ archiving က အလိုအလျောက် ဖြစ်ပေါ်ပါတယ်။ အခြေအနေ အများစုမှာ ဒါက မြန်ဆန်စွာ ဖြစ်ပေမယ့် — နှောင့်နှေးမှုတွေ မရှိဘူးဆိုတာ သေချာစေဖို့ — သင့် archive system ကို စောင့်ကြည့်ဖို့ အကြံပြုလိုပါတယ်။ Archive command ဒါမှမဟုတ် library ရဲ့ ကျရှုံးမှုတွေကြောင့် archive process က နောက်ကျနေရင် — archive အောင်မြင်ပြီး backup ပြီးမြောက်သည်အထိ — ထပ်ခါထပ်ခါ ကြိုးစားနေပါလိမ့်မယ်။ pg_backup_stop ရဲ့ လုပ်ဆောင်မှုပေါ်မှာ အချိန် ကန့်သတ်ချက် တစ်ခု ထားချင်ရင် — သင့်လျော်တဲ့ statement_timeout တန်ဖိုး တစ်ခုကို သတ်မှတ်ပါ — ဒါပေမယ့် — ဒီကြောင့် pg_backup_stop က အဆုံးသတ်သွားခဲ့ရင် — သင့် backup က valid (အသုံးပြုနိုင်သော) မဖြစ်နိုင်ဘူးဆိုတာ မှတ်သားထားပါ။
  Backup process က — backup အတွက် လိုအပ်တဲ့ WAL segment files တွေ အားလုံး အောင်မြင်စွာ archive လုပ်ခံရတာကို စောင့်ကြည့် သေချာစေနိုင်ရင် — wait_for_archive parameter (default က true ပါ) ကို false အဖြစ် သတ်မှတ်ပြီး — stop backup record ကို WAL ထဲ ရေးသားလိုက်တာနဲ့ — pg_backup_stop က ချက်ချင်း ပြန်လာစေနိုင်ပါတယ်။ Default အနေနဲ့တော့ — pg_backup_stop က WAL အားလုံး archive လုပ်ခံရသည်အထိ စောင့်မှာ ဖြစ်ပြီး — အဲဒါက အချိန် အတော်ကြာနိုင်ပါတယ်။ ဒီ option ကို သတိထားပြီး သုံးရပါမယ်: WAL archiving ကို မှန်ကန်စွာ စောင့်ကြည့် မလုပ်ထားရင် — backup ထဲမှာ WAL ဖိုင်တွေ အားလုံး ပါဝင်ချင်မှ ပါဝင်မှာ ဖြစ်လို့ — backup က မပြည့်စုံဘဲ — restore လုပ်လို့ မရနိုင်တော့ပါဘူး။

#### 25.3.4.1. Backing Up the Data Directory (data directory ကို backup လုပ်ခြင်း)

File system backup tools တချို့က — သူတို့ ကူးယူဖို့ ကြိုးစားနေတဲ့ ဖိုင်တွေ ကူးယူမှု ဆက်လုပ်နေတုန်း ပြောင်းလဲသွားရင် — warnings (သတိပေးချက်များ) ဒါမှမဟုတ် errors တွေကို ထုတ်ပေးပါတယ်။ သက်ဝင်နေတဲ့ (active) database တစ်ခုရဲ့ base backup ကို ယူတဲ့အခါ — ဒီအခြေအနေက သာမန် ဖြစ်ပြီး — error မဟုတ်ပါဘူး။ ဒါပေမယ့် — ဒီလိုမျိုး တိုင်ကြားချက်တွေကို တကယ့် errors တွေနဲ့ ခွဲခြားနိုင်ဖို့ သေချာစေရပါမယ်။ ဥပမာ — rsync ရဲ့ version တချို့က “vanished source files” (ကွယ်ပျောက်သွားသော source ဖိုင်များ) အတွက် သီးခြား exit code တစ်ခုကို ပြန်ပေးပြီး — ဒီ exit code ကို error မဟုတ်တဲ့ အမှု (non-error case) အဖြစ် လက်ခံတဲ့ driver script တစ်ခုကို သင်ရေးနိုင်ပါတယ်။ ထို့အပြင် — GNU tar ရဲ့ version တချို့က — tar က ဖိုင်တစ်ခုကို ကူးယူနေတုန်း အဲဒီဖိုင် truncated (ဖြတ်တောက်ခံရ) ခဲ့ရင် — fatal error တစ်ခုနဲ့ ခွဲခြားလို့ မရတဲ့ error code တစ်ခုကို ပြန်ပေးပါတယ်။ ကံကောင်းစွာပဲ — GNU tar version 1.16 နဲ့ နောက်ပိုင်းတွေက — backup အတွင်း ဖိုင်တစ်ခု ပြောင်းလဲခဲ့ရင် 1 နဲ့ — တခြား errors တွေအတွက်တော့ 2 နဲ့ — exit လုပ်ပါတယ်။ GNU tar version 1.23 နဲ့ နောက်ပိုင်းတွေမှာတော့ — ဆက်စပ်တဲ့ warning messages တွေကို ဖျောက်ဖို့ `--warning=no-file-changed --warning=no-file-removed` ဆိုတဲ့ warning options တွေကို သုံးနိုင်ပါတယ်။

သင့် backup ထဲမှာ — database cluster directory (ဥပမာ — `/usr/local/pgsql/data`) အောက်က ဖိုင်တွေ အားလုံး ပါဝင်ကြောင်း သေချာပါစေ။ ဒီ directory ရဲ့ အောက်မှာ မတည်ရှိတဲ့ tablespaces တွေ သုံးနေတယ်ဆိုရင် — အဲဒါတွေကိုပါ ထည့်သွင်းဖို့ သတိထားပါ (ပြီးတော့ — သင့် backup က symbolic links တွေကို links အဖြစ် archive လုပ်ကြောင်း သေချာပါစေ — မဟုတ်ရင် restore က သင့် tablespaces တွေကို ပျက်စီးစေပါလိမ့်မယ်)။

ဒါပေမယ့် — cluster ရဲ့ `pg_wal/` subdirectory ထဲက ဖိုင်တွေကိုတော့ backup ထဲကနေ ချန်လှပ်ထားသင့်ပါတယ်။ ဒီ အနည်းငယ် ချိန်ညှိမှုက — restore လုပ်တဲ့အခါ အမှားတွေ ဖြစ်နိုင်ခြေကို လျှော့ချပေးလို့ — တန်ဖိုး ရှိပါတယ်။ `pg_wal/` က cluster directory ရဲ့ အပြင်ဘက် တစ်နေရာရာကို ညွှန်ပြတဲ့ symbolic link တစ်ခု ဆိုရင် — ဒါက စီစဉ်ဖို့ လွယ်ကူပါတယ် — performance အကြောင်းပြချက်တွေကြောင့် ဘာပဲဖြစ်ဖြစ် ဒါက သာမန် setup တစ်ခုလည်း ဖြစ်ပါတယ်။ ထို့အပြင် — run နေတဲ့ postmaster အကြောင်း အချက်အလက်တွေကို မှတ်တမ်းတင်ထားတဲ့ — `postmaster.pid` နဲ့ `postmaster.opts` တို့ကိုလည်း ဖယ်ထုတ်ချင်နိုင်ပါတယ် — အဲဒါတွေက နောက်ဆုံးမှာ ဒီ backup ကို သုံးမယ့် postmaster အကြောင်း မဟုတ်ပါဘူး။ (ဒီဖိုင်တွေက pg_ctl ကို ရှုပ်ထွေးစေနိုင်ပါတယ်။)

Cluster ရဲ့ `pg_replslot/` directory ထဲက ဖိုင်တွေကိုလည်း backup ထဲကနေ ချန်လှပ်ထားတာက မကြာခဏ ကောင်းတဲ့ အကြံတစ်ခု ဖြစ်ပါတယ် — ဒါမှ primary ပေါ်မှာ ရှိနေတဲ့ replication slots (ပုံတူပွား ဒေတာ လွှဲပြောင်းမှုအတွက် slot များ) တွေ backup ရဲ့ အစိတ်အပိုင်း မဖြစ်သွားမှာ ပါ။ မဟုတ်ရင် — backup ကို သုံးပြီး standby တစ်ခု ဖန်တီးတာက — standby ပေါ်မှာ WAL ဖိုင်တွေကို အကန့်အသတ်မရှိ ထိန်းသိမ်းထားရတာ ဖြစ်ပေါ်စေနိုင်ပြီး — hot standby feedback ကို enable လုပ်ထားရင် — primary ပေါ်မှာ bloat (မလိုအပ်ဘဲ ကြီးထွားမှု) ဖြစ်စေနိုင်ပါတယ် — အကြောင်းကတော့ အဲဒီ replication slots တွေကို သုံးနေတဲ့ clients တွေက standby မဟုတ်ဘဲ — primary ပေါ်က slots တွေဆီပဲ ဆက်ပြီး connect လုပ်ပြီး update လုပ်နေဦးမှာ မို့ပါ။ Backup က primary အသစ်တစ်ခု ဖန်တီးဖို့အတွက်ပဲ ရည်ရွယ်ထားတာတောင် — replication slots တွေကို ကူးယူတာက အထူး အသုံးဝင်မယ်လို့ မမျှော်လင့်ရပါဘူး — အကြောင်းကတော့ primary အသစ် online ဖြစ်လာတဲ့ အချိန်မှာ — အဲဒီ slots တွေရဲ့ ပါဝင်စရာတွေက ဖွယ်ရှု ဆိုးရွားစွာ ခေတ်နောက်ကျနေဦးမှာ မို့ပါ။

`pg_dynshmem/`, `pg_notify/`, `pg_serial/`, `pg_snapshots/`, `pg_stat_tmp/` နဲ့ `pg_subtrans/` ဆိုတဲ့ directories တွေရဲ့ ပါဝင်စရာတွေ (directories တွေ ကိုယ်တိုင်ကတော့ မဟုတ်ပါဘူး) ကို — postmaster startup မှာ ၎င်းတို့ကို initialize (ကနဦး ပြင်ဆင်) လုပ်မှာ ဖြစ်လို့ — backup ထဲကနေ ချန်လှပ်ထားနိုင်ပါတယ်။

`pgsql_tmp` နဲ့ စတင်တဲ့ ဖိုင် ဒါမှမဟုတ် directory ဘယ်ခုကိုမဆို backup ထဲကနေ ချန်လှပ်ထားနိုင်ပါတယ်။ ဒီဖိုင်တွေကို postmaster စတင်ချိန်မှာ ဖယ်ရှားပြီး — directories တွေကို လိုအပ်သလို ပြန်လည် ဖန်တီးပါတယ်။

`pg_internal.init` ဖိုင်တွေကို — အဲဒီနာမည်နဲ့ ဖိုင်တစ်ခု တွေ့ရတိုင်း — backup ထဲကနေ ချန်လှပ်ထားနိုင်ပါတယ်။ ဒီဖိုင်တွေထဲမှာ — recovery လုပ်တဲ့အခါ အမြဲ ပြန်လည် တည်ဆောက်ခံရတဲ့ — relation cache data တွေ ပါဝင်ပါတယ်။

Backup label ဖိုင်ထဲမှာ — သင် `pg_backup_start` ကို ပေးခဲ့တဲ့ label string ရော — `pg_backup_start` run လုပ်ခဲ့တဲ့ အချိန် ရော — စတင်တဲ့ WAL ဖိုင်ရဲ့ အမည်ပါ ပါဝင်ပါတယ်။ ရှုပ်ထွေးမှု ဖြစ်ခဲ့ရင် — backup ဖိုင်တစ်ခုရဲ့ အတွင်းကို ကြည့်ပြီး — dump ဖိုင်က ဘယ် backup session ကနေ လာတယ်ဆိုတာ အတိအကျ ဆုံးဖြတ်နိုင်ပါတယ်။ Tablespace map ဖိုင်ထဲမှာတော့ — `pg_tblspc/` directory ထဲမှာ ရှိနေတဲ့အတိုင်း — symbolic link အမည်တွေ ရော — symbolic link တစ်ခုချင်းစီရဲ့ full path ပါ ပါဝင်ပါတယ်။ ဒီဖိုင်တွေက သင်သိဖို့အတွက်ပဲ မဟုတ်ပါဘူး; သူတို့ရဲ့ တည်ရှိမှုနဲ့ ပါဝင်စရာတွေက system ရဲ့ recovery process မှန်ကန်စွာ အလုပ်လုပ်ဖို့ အရေးပါပါတယ်။

Server ရပ်တန့်ထားတဲ့ အချိန်မှာလည်း backup တစ်ခု လုပ်ဖို့ ဖြစ်နိုင်ပါတယ်။ ဒီကိစ္စမှာ — `pg_backup_start` ဒါမှမဟုတ် `pg_backup_stop` ကို သုံးလို့ မရနိုင်တာ သိသာပြီး — ဒါကြောင့် — ဘယ် backup က ဘယ်ဟာလဲ နဲ့ ဆက်စပ်နေတဲ့ WAL ဖိုင်တွေ ဘယ်လောက် နောက်ပြန် ရောက်လဲဆိုတာကို ခြေရာခံဖို့ — ကိုယ့်ဘာသာ နည်းလမ်းရှာရမှာ ဖြစ်ပါတယ်။ အပေါ်မှာ ဖော်ပြခဲ့တဲ့ continuous archiving လုပ်ငန်းစဉ်ကို လိုက်နာတာက ယေဘုယျအားဖြင့် ပိုကောင်းပါတယ်။
### 25.3.5. Recovering Using a Continuous Archive Backup (continuous archive backup ဖြင့် ပြန်လည် ရယူခြင်း)

အဆိုးဆုံး အခြေအနေ ဖြစ်သွားပြီ — သင့် backup ကနေ recover (ပြန်လည် ရယူ) လုပ်ဖို့ လိုအပ်နေပါပြီ။ လုပ်ငန်းစဉ်ကတော့ ဒီလိုပါ:

1. Server run နေတယ်ဆိုရင် — ရပ်တန့်လိုက်ပါ။
2. နေရာ လုံလောက်ရင် — cluster data directory တစ်ခုလုံး နဲ့ tablespaces တွေ အားလုံးကို — နောက်ပိုင်း လိုအပ်ချင်ရင် သုံးနိုင်အောင် — ယာယီ နေရာတစ်ခုဆီ ကူးယူထားပါ။ ဒီ ကြိုတင် ကာကွယ်မှုက — သင့် system ပေါ်မှာ — သင့် database ရဲ့ မိတ္တူ နှစ်စောင် ထားဖို့ လုံလောက်တဲ့ — free space ရှိဖို့ လိုအပ်တယ်ဆိုတာ သတိပြုပါ။ နေရာ မလုံလောက်ဘူးဆိုရင် — cluster ရဲ့ pg_wal subdirectory ရဲ့ ပါဝင်စရာတွေကိုတော့ အနည်းဆုံး သိမ်းဆည်းထားသင့်ပါတယ် — အကြောင်းကတော့ system မကျဆင်းခင် archive မလုပ်ရသေးတဲ့ WAL ဖိုင်တွေ အဲဒီထဲမှာ ရှိနေနိုင်လို့ပါ။
3. Cluster data directory အောက်မှာ နဲ့ — သင်သုံးနေတဲ့ tablespaces တွေရဲ့ root directories တွေအောက်မှာ ရှိနေတဲ့ — ဖိုင်တွေ နဲ့ subdirectories တွေ အားလုံးကို ဖယ်ရှားလိုက်ပါ။
4. Full backup တစ်ခုကို restore လုပ်နေတယ်ဆိုရင် — database ဖိုင်တွေကို target directories တွေထဲကို တိုက်ရိုက် ပြန်လည် ထည့်သွင်းနိုင်ပါတယ်။ ၎င်းတို့ကို မှန်ကန်တဲ့ ပိုင်ဆိုင်မှု (ownership — database system user ဖြစ်ရမယ်၊ root မဟုတ်ဘူး!) နဲ့ မှန်ကန်တဲ့ permissions (ခွင့်ပြုချက်များ) တွေနဲ့ ပြန်လည် တည်ဆောက်ခံရကြောင်း သေချာပါစေ။ Tablespaces တွေ သုံးနေတယ်ဆိုရင် — `pg_tblspc/` ထဲက symbolic links တွေကို မှန်ကန်စွာ ပြန်လည် တည်ဆောက်ခဲ့လားဆိုတာ စစ်ဆေးသင့်ပါတယ်။
5. Incremental backup တစ်ခုကို restore လုပ်နေတယ်ဆိုရင် — incremental backup ရော — ၎င်း တိုက်ရိုက် ဒါမှမဟုတ် သွယ်ဝိုက်၍ မှီခိုနေတဲ့ အစောပိုင်း backups တွေ အားလုံးကိုပါ — restore လုပ်နေတဲ့ machine ဆီ ပြန်လည် ထည့်သွင်းဖို့ လိုအပ်ပါလိမ့်မယ်။ ဒီ backups တွေကို — run နေတဲ့ server ရှိစေချင်တဲ့ target directories တွေမဟုတ်ဘဲ — သီးခြား directories တွေထဲမှာ ထားရပါမယ်။ ပြီးတာနဲ့ — full backup နဲ့ နောက်ပိုင်း incremental backups တွေ အားလုံးကနေ data တွေကို ဆွဲထုတ်ပြီး — target directories တွေထဲကို synthetic (ပေါင်းစပ် ဖန်တီးထားသော) full backup တစ်ခုအဖြစ် ရေးထုတ်ဖို့ — pg_combinebackup ကို သုံးပါ။ အပေါ်မှာ ဖော်ပြခဲ့သလိုပဲ — permissions နဲ့ tablespace links တွေ မှန်ကန်ကြောင်း စစ်ဆေးပါ။
6. `pg_wal/` ထဲမှာ ရှိနေတဲ့ ဖိုင်တွေ အားလုံးကို ဖယ်ရှားပါ; ဒါတွေက file system backup ထဲကနေ လာတာမို့ — လက်ရှိ ဖြစ်တာထက် ခေတ်နောက်ကျနေဖွယ် ရှိပါတယ်။ `pg_wal/` ကို လုံးဝ archive မလုပ်ခဲ့ဘူးဆိုရင် — ၎င်းကို မှန်ကန်တဲ့ permissions တွေနဲ့ ပြန်လည် ဖန်တီးပြီး — အရင်က symbolic link အနေနဲ့ တည်ဆောက်ထားခဲ့တယ်ဆိုရင် — symbolic link အဖြစ် ပြန်လည် တည်ဆောက်ဖို့ သေချာပါစေ။
7. အဆင့် 2 မှာ သင်သိမ်းဆည်းထားခဲ့တဲ့ — archive မလုပ်ရသေးတဲ့ WAL segment files တွေ ရှိရင် — ၎င်းတို့ကို `pg_wal/` ထဲကို ကူးယူထည့်ပါ။ (ရွှေ့ပြောင်း (move) လုပ်တာထက် ကူးယူ (copy) လုပ်တာက အကောင်းဆုံးပါ — ပြဿနာ တစ်ခုခု ဖြစ်ပြီး ပြန်စရမယ်ဆိုရင် — မပြုပြင်ရသေးတဲ့ ဖိုင်တွေ ရှိနေဦးမှာ မို့ပါ။)
8. postgresql.conf ထဲမှာ recovery configuration settings တွေကို သတ်မှတ်ပြီး (အပိုင်း 19.5.5 ကို ကြည့်ပါ) — cluster data directory ထဲမှာ recovery.signal ဆိုတဲ့ ဖိုင်တစ်ခု ဖန်တီးပါ။ Recovery အောင်မြင်ကြောင်း သေချာမသိမချင်း — သာမန် users တွေ connect လုပ်လို့ မရအောင် — pg_hba.conf ကို ယာယီ ပြုပြင်ချင်နိုင်ပါတယ်။
9. Server ကို စတင်ပါ။ Server က recovery mode ထဲကို ဝင်ပြီး — သူလိုအပ်တဲ့ archived WAL ဖိုင်တွေကို ဖတ်သွားပါလိမ့်မယ်။ Recovery က ပြင်ပ error တစ်ခုကြောင့် အဆုံးသတ်ခံခဲ့ရရင် — server ကို ပြန်လည် restart လုပ်ရုံပဲ ဖြစ်ပြီး — recovery ကို ဆက်လုပ်ပါလိမ့်မယ်။ Recovery process ပြီးမြောက်တာနဲ့ — server က recovery.signal ကို ဖယ်ရှားပြီး (နောက်ပိုင်း မတော်တဆ recovery mode ထဲ ပြန်မဝင်အောင်) — ပုံမှန် database လည်ပတ်မှုတွေကို စတင်ပါလိမ့်မယ်။
10. လိုချင်တဲ့ အခြေအနေဆီ recover လုပ်ပြီးကြောင်း သေချာစေဖို့ — database ရဲ့ ပါဝင်စရာတွေကို စစ်ဆေးပါ။ မဟုတ်ရင် — အဆင့် 1 ဆီ ပြန်သွားပါ။ အားလုံး အဆင်ပြေရင် — pg_hba.conf ကို ပုံမှန် အနေအထားဆီ ပြန်လည် တည်ဆောက်ပြီး — သင့် users တွေကို connect လုပ်ခွင့် ပြုပါ။

ဒီအားလုံးရဲ့ အဓိက အစိတ်အပိုင်းကတော့ — ဘယ်လို recover လုပ်ချင်လဲ နဲ့ recovery ကို ဘယ်လောက်အထိ run စေချင်လဲဆိုတာကို ဖော်ပြတဲ့ — recovery configuration တစ်ခုကို တည်ဆောက်ဖို့ ဖြစ်ပါတယ်။ သင်လုံးဝ သတ်မှတ်ပေးရမယ့် အရာတစ်ခုကတော့ — archived WAL file segments တွေကို ဘယ်လို ပြန်လည် ရယူရမယ်ဆိုတာ PostgreSQL ကို ပြောပြတဲ့ — `restore_command` ပဲ ဖြစ်ပါတယ်။ `archive_command` လိုပဲ — ဒါက shell command string တစ်ခု ဖြစ်ပါတယ်။ ၎င်းထဲမှာ — လိုချင်တဲ့ WAL ဖိုင်ရဲ့ အမည်နဲ့ အစားထိုးခံရတဲ့ `%f` ရော — WAL ဖိုင်ကို ကူးယူရမယ့် path name နဲ့ အစားထိုးခံရတဲ့ `%p` ရော ပါဝင်နိုင်ပါတယ်။ (Path name က လက်ရှိ working directory — ဆိုလိုတာက cluster ရဲ့ data directory — နဲ့ ဆက်စပ်နေပါတယ်။) Command ထဲမှာ တကယ့် `%` character တစ်ခု ထည့်သွင်းဖို့ လိုအပ်ရင် `%%` ကို ရေးပါ။ အသုံးဝင်ဆုံး ရိုးရှင်းတဲ့ command က ဒီလိုမျိုး ဖြစ်ပါတယ်:

```sql
restore_command = 'cp /mnt/server/archivedir/%f %p'
```

အဲဒါက အရင်က archive လုပ်ထားတဲ့ WAL segments တွေကို `/mnt/server/archivedir` directory ကနေ ကူးယူပေးမှာ ဖြစ်ပါတယ်။ ဟုတ်ပါတယ် — ဒီထက် အများကြီး ပိုရှုပ်ထွေးတဲ့ အရာတစ်ခုကိုလည်း သုံးနိုင်ပါတယ် — သင့်လျော်တဲ့ tape တစ်ခုကို တပ်ဆင်ပေးဖို့ operator ကို တောင်းဆိုတဲ့ shell script တစ်ခုတောင် ဖြစ်နိုင်ပါတယ်။

Command က ကျရှုံးမှုပေါ်မှာ nonzero exit status ကို ပြန်ပေးဖို့ အရေးကြီးပါတယ်။ Command ကို — archive ထဲမှာ မရှိတဲ့ ဖိုင်တွေကို တောင်းဆိုပြီး ခေါ်ယူပါလိမ့်မယ်; အဲဒီလို တောင်းခံတဲ့အခါ nonzero ကို ပြန်ပေးရပါမယ်။ ဒါက error condition မဟုတ်ပါဘူး။ ခြွင်းချက်တစ်ခုကတော့ — command ကို signal တစ်ခုက ရပ်တန့်စေခဲ့ရင် (database server shutdown ရဲ့ အစိတ်အပိုင်း အဖြစ် သုံးတဲ့ SIGTERM ကလွဲရင်) ဒါမှမဟုတ် shell ရဲ့ error တစ်ခု (command not found လိုမျိုး) ဖြစ်ခဲ့ရင် — recovery က ရပ်ဆိုင်းသွားပြီး — server က စတင်မှာ မဟုတ်ပါဘူး။

တောင်းဆိုခံရတဲ့ ဖိုင်တွေ အားလုံးက WAL segment files တွေ မဟုတ်ပါဘူး; `.history` ဆိုတဲ့ suffix ရှိတဲ့ ဖိုင်တွေအတွက် တောင်းဆိုမှုတွေကိုလည်း မျှော်လင့်ထားသင့်ပါတယ်။ ထို့အပြင် — `%p` path ရဲ့ base name က `%f` နဲ့ မတူဘူးဆိုတာ သတိထားပါ; ၎င်းတို့ကို အပြန်အလှန် အစားထိုး သုံးလို့ရတယ်လို့ မမျှော်လင့်ပါနဲ့။

Archive ထဲမှာ ရှာမတွေ့တဲ့ WAL segments တွေကို `pg_wal/` ထဲမှာ ရှာဖွေပါလိမ့်မယ်; ဒါက — မကြာသေးခင်က archive မလုပ်ရသေးတဲ့ segments တွေကို သုံးခွင့် ပြုပါတယ်။ ဒါပေမယ့် — archive ကနေ ရနိုင်တဲ့ segments တွေကို `pg_wal/` ထဲက ဖိုင်တွေထက် ဦးစားပေး သုံးပါလိမ့်မယ်။

ပုံမှန်အားဖြင့် — recovery က ရနိုင်တဲ့ WAL segments တွေ အားလုံးကို ဖြတ်သန်း သွားပြီး — ဒါကြောင့် — database ကို လက်ရှိ အချိန်အမှတ် (ရနိုင်တဲ့ WAL segments တွေအရ ဖြစ်နိုင်သမျှ အနီးစပ်ဆုံး) ဆီ ပြန်လည် တည်ဆောက်ပေးပါလိမ့်မယ်။ ဒါကြောင့် — သာမန် recovery တစ်ခုက “file not found” (ဖိုင် ရှာမတွေ့) message တစ်ခုနဲ့ အဆုံးသတ်မှာ ဖြစ်ပြီး — error message ရဲ့ တိကျတဲ့ စာသားက သင့် `restore_command` ရွေးချယ်မှုပေါ်မှာ မူတည်ပါတယ်။ Recovery ရဲ့ အစမှာလည်း — `00000001.history` လိုမျိုး အမည်ရှိတဲ့ ဖိုင်တစ်ခုအတွက် error message တစ်ခုကို မြင်ရနိုင်ပါတယ်။ ဒါလည်း သာမန်ပဲ ဖြစ်ပြီး — ရိုးရှင်းတဲ့ recovery အခြေအနေတွေမှာ ပြဿနာတစ်ခုကို ညွှန်ပြတာ မဟုတ်ပါဘူး; ဆွေးနွေးချက်အတွက် [အပိုင်း 25.3.6](https://www.postgresql.org/docs/current/continuous-archiving.html#BACKUP-TIMELINES) ကို ကြည့်ပါ။

အရင်က အချိန်ကာလ တစ်ခုခုဆီ recover လုပ်ချင်ရင် (ဥပမာ — အငယ်တန်း (junior) DBA တစ်ယောက်က သင့် အဓိက transaction table ကို မဖျက်ခင် အချိန်တို လောက်ဆီ) — လိုအပ်တဲ့ [stopping point](https://www.postgresql.org/docs/current/runtime-config-wal.html#RUNTIME-CONFIG-WAL-RECOVERY-TARGET) (ရပ်တန့်ရမည့် အမှတ်) ကို သတ်မှတ်လိုက်ရုံပါပဲ။ “Recovery target” (recovery ပစ်မှတ်) လို့ သိကြတဲ့ ဒီ stop point ကို — ရက်စွဲ/အချိန် (date/time)၊ အမည်ပေးထားတဲ့ restore point (restore အမှတ်) ဒါမှမဟုတ် တိကျတဲ့ transaction ID တစ်ခုရဲ့ ပြီးမြောက်မှုအားဖြင့် — သတ်မှတ်နိုင်ပါတယ်။ ဒီစာရေးနေတဲ့ အချိန်အထိ — ဘယ် transaction ID ကို သုံးရမယ်ဆိုတာ တိကျစွာ ခွဲခြားသိဖို့ ကူညီပေးမယ့် tools တွေ မရှိသေးလို့ — date/time နဲ့ named restore point options တွေပဲ အသုံးပြုလို့ အဆင်ပြေတာ ဖြစ်ပါတယ်။

> **မှတ်ချက်:** Stop point က base backup ရဲ့ ပြီးဆုံးချိန် — ဆိုလိုတာက `pg_backup_stop` ရဲ့ အဆုံးချိန် — နောက်ပိုင်းမှာ ဖြစ်ရပါမယ်။ Backup လုပ်ဆောင်နေတဲ့ အချိန်တစ်ခုဆီ recover လုပ်ဖို့ base backup တစ်ခုကို သုံးလို့ မရပါဘူး။ (အဲဒီလို အချိန်တစ်ခုဆီ recover လုပ်ဖို့ဆိုရင် — သင့် အရင် base backup ဆီ ပြန်သွားပြီး — အဲဒီကနေ roll forward (ရှေ့သို့ ဆင့်ပွား) လုပ်ရပါမယ်။)

Recovery က ပျက်စီးနေတဲ့ (corrupted) WAL data တွေကို တွေ့ရှိရင် — recovery က အဲဒီအမှတ်မှာ ရပ်တန့်သွားပြီး — server က စတင်မှာ မဟုတ်ပါဘူး။ အဲဒီလို အခြေအနေမျိုးမှာ — recovery process ကို အစကနေ ပြန်လည် run လုပ်ပြီး — recovery ပုံမှန်အတိုင်း ပြီးမြောက်နိုင်အောင် — ပျက်စီးမှု ဖြစ်တဲ့ အမှတ်ထက် ရှေ့ကျတဲ့ “recovery target” တစ်ခုကို သတ်မှတ်နိုင်ပါတယ်။ Recovery က ပြင်ပ အကြောင်းရင်းတစ်ခုကြောင့် ကျရှုံးခဲ့ရင် — ဥပမာ — system crash ဒါမှမဟုတ် WAL archive က ဝင်ရောက်လို့ မရတော့တာမျိုး — recovery ကို ရိုးရှင်းစွာ ပြန်လည် restart လုပ်နိုင်ပြီး — ၎င်း ကျရှုံးခဲ့တဲ့ နေရာကနေ နီးနီးလေး ပြန်စပါလိမ့်မယ်။ Recovery restart က ပုံမှန် လည်ပတ်မှုထဲက checkpointing နဲ့ အတော်လေး ဆင်တူပါတယ်: server က ကာလအလိုက် သူ့ရဲ့ state တွေ အားလုံးကို disk ဆီ force လုပ်ပြီး — လုပ်ဆောင်ပြီးသား (already-processed) WAL data တွေကို ပြန်လည် scan လုပ်စရာ မလိုတော့ဘူးဆိုတာ ညွှန်ပြဖို့ — `pg_control` ဖိုင်ကို update လုပ်ပါတယ်။
### 25.3.6. Timelines (timelines — အချိန် မျဉ်းကြောင်းများ)

Database ကို အရင် အချိန်ကာလ တစ်ခုဆီ ပြန်လည် တည်ဆောက်နိုင်တဲ့ စွမ်းရည်က — အချိန် ခရီးသွားခြင်း (time travel) နဲ့ parallel universes (အပြိုင် စကြာဝဠာများ) အကြောင်း သိပ္ပံ-စိတ်ကူးယဉ် ဇာတ်လမ်းတွေနဲ့ တူတဲ့ — ရှုပ်ထွေးမှုတွေ အချို့ကို ဖန်တီးပေးပါတယ်။ ဥပမာ — database ရဲ့ မူရင်း သမိုင်းကြောင်း (original history) ထဲမှာ — အင်္ဂါနေ့ ညနေ 5:15 မှာ သင်က အရေးကြီးတဲ့ table တစ်ခုကို ဖျက်လိုက်ပြီး — ဒါပေမယ့် ဗုဒ္ဓဟူးနေ့ မွန်းတည့်အထိ သင့်အမှားကို သဘောမပေါက်မိခဲ့ဘူးဆိုပါစို့။ စိတ်မပျက်ဘဲ — သင့် backup ကို ထုတ်ပြီး — အင်္ဂါနေ့ ညနေ 5:14PM အချိန်ကာလဆီ restore လုပ်လိုက်တယ် — system က ပြန်အလုပ်လုပ်နေပြီ။ ဒီ database စကြာဝဠာရဲ့ သမိုင်းကြောင်းထဲမှာ — သင်ဟာ အဲဒီ table ကို ဘယ်တုန်းကမှ မဖျက်ခဲ့ပါဘူး။ ဒါပေမယ့် — နောက်ပိုင်းမှာ ဒါက သိပ်ကောင်းတဲ့ အကြံတစ်ခု မဟုတ်ဘူးလို့ သဘောပေါက်ပြီး — မူရင်း သမိုင်းကြောင်းထဲက ဗုဒ္ဓဟူးနေ့ မနက်ခင်း တစ်ချိန်ချိန်ဆီ ပြန်သွားချင်တယ်ဆိုပါစို့။ သင့် database က up-and-running ဖြစ်နေတုန်း — အခု သင်ပြန်ရောက်ချင်တဲ့ အချိန်ဆီ ဦးတည်စေတဲ့ WAL segment files တချို့ကို ပြန်ရေးသား (overwrite) လုပ်မိခဲ့မယ်ဆိုရင် — သင်ပြန်လို့ မရနိုင်တော့ပါဘူး။ ဒါကြောင့် — ဒါကို ရှောင်ဖို့ — point-in-time recovery တစ်ခု လုပ်ပြီးနောက်မှာ ထုတ်လုပ်ခဲ့တဲ့ WAL records တွေရဲ့ အစီအစဉ်ကို — မူရင်း database သမိုင်းကြောင်းထဲမှာ ထုတ်လုပ်ခဲ့တဲ့ အစီအစဉ်ကနေ — ခွဲခြား သိဖို့ လိုအပ်ပါတယ်။

ဒီပြဿနာကို ကိုင်တွယ်ဖို့ — PostgreSQL မှာ *timelines* (timeline — အချိန် မျဉ်းကြောင်း) ဆိုတဲ့ အယူအဆတစ်ခု ရှိပါတယ်။ Archive recovery တစ်ခု ပြီးမြောက်တိုင်း — အဲဒီ recovery နောက်ပိုင်း ထုတ်လုပ်တဲ့ WAL records တွေရဲ့ အစီအစဉ်ကို ခွဲခြားသိဖို့ — timeline အသစ်တစ်ခုကို ဖန်တီးပါတယ်။ Timeline ID နံပါတ်က WAL segment ဖိုင် အမည်တွေရဲ့ အစိတ်အပိုင်း တစ်ခု ဖြစ်လို့ — timeline အသစ်တစ်ခုက အရင် timelines တွေ ထုတ်လုပ်ထားတဲ့ WAL data တွေကို overwrite မလုပ်ပါဘူး။ ဥပမာ — `0000000100001234000055CD` ဆိုတဲ့ WAL ဖိုင် အမည်ထဲမှာ — ရှေ့ဆုံးက `00000001` က hexadecimal နဲ့ ရေးထားတဲ့ timeline ID ပဲ ဖြစ်ပါတယ်။ (Server log messages လို — အခြား အကြောင်းအရာတွေမှာတော့ — timeline IDs တွေကို များသောအားဖြင့် decimal နဲ့ ရိုက်နှိပ်ဖော်ပြပါတယ်ဆိုတာ သတိပြုပါ။)

တကယ်တော့ — timeline အမျိုးမျိုး အများအပြားကို archive လုပ်ဖို့ ဖြစ်နိုင်ပါတယ်။ ဒါက အသုံးမကျတဲ့ feature တစ်ခုလို ထင်ရနိုင်ပေမယ့် — မကြာခဏဆိုသလို — အသက်ကယ်ဆယ်သူ (lifesaver) တစ်ယောက် ဖြစ်ပါတယ်။ ဒီအခြေအနေကို စဉ်းစားကြည့်ပါ — ဘယ် point-in-time ဆီ recover လုပ်ရမလဲဆိုတာ သင်မသေချာဘူး — ဒါကြောင့် — သမိုင်းကြောင်း အဟောင်းကနေ ခွဲထွက်ဖို့ အကောင်းဆုံး နေရာကို မတွေ့သည့်အထိ — trial and error (စမ်းပြီး အမှားရှာ) နည်းနဲ့ — point-in-time recoveries တွေ အများအပြား လုပ်ရမယ့် အခြေအနေမျိုးပါ။ Timelines မရှိရင် — ဒီလုပ်ငန်းစဉ်က မကြာခင်မှာ စီမံခန့်ခွဲလို့ မရတဲ့ ရှုပ်ထွေးမှု (unmanageable mess) တစ်ခု ဖြစ်သွားပါလိမ့်မယ်။ Timelines ရှိနေရင်တော့ — အရင်က စွန့်လွှတ်ခဲ့တဲ့ timeline branches (timeline အကိုင်းအခက်များ) ထဲက အခြေအနေတွေ အပါအဝင် — အရင် state တစ်ခုခုဆီကိုမဆို recover လုပ်နိုင်ပါတယ်။

Timeline အသစ်တစ်ခု ဖန်တီးတိုင်း — PostgreSQL က — ဘယ် timeline ကနေ ဘယ်အချိန်မှာ ခွဲထွက်ခဲ့လဲဆိုတာ ပြသပေးတဲ့ — “timeline history” (timeline သမိုင်း) ဖိုင်တစ်ခုကို ဖန်တီးပါတယ်။ ဒီ history ဖိုင်တွေက — timelines အများအပြား ပါဝင်တဲ့ archive တစ်ခုကနေ recovery လုပ်တဲ့အခါ — မှန်ကန်တဲ့ WAL segment files တွေကို ရွေးချယ်ဖို့ system ကို ခွင့်ပြုဖို့ — လိုအပ်ပါတယ်။ ဒါကြောင့် — ၎င်းတို့ကို WAL segment files တွေလိုပဲ — WAL archive area ထဲကို archive လုပ်ပါတယ်။ History ဖိုင်တွေက သေးငယ်တဲ့ text ဖိုင်တွေပဲ ဖြစ်လို့ — (ကြီးမားတဲ့ segment files တွေနဲ့ မတူဘဲ) ၎င်းတို့ကို အကန့်အသတ်မရှိ ထိန်းသိမ်းထားတာက ဈေးပေါပြီး သင့်လျော်ပါတယ်။ သင်ဆန္ဒရှိရင် — ဒီ timeline တစ်ခုချင်းစီကို ဘယ်လို ဘာကြောင့် ဖန်တီးခဲ့လဲဆိုတဲ့ — ကိုယ်ပိုင် မှတ်စုတွေ မှတ်တမ်းတင်ဖို့ — history ဖိုင်တစ်ခုထဲကို comments တွေ ထည့်နိုင်ပါတယ်။ စမ်းသပ်မှုတွေရဲ့ ရလဒ်ကြောင့် timeline အမျိုးမျိုး ထူထပ်စွာ (thicket) ရှိနေတဲ့အခါ — အဲဒီလို comments တွေက အထူး တန်ဖိုးရှိပါလိမ့်မယ်။

Recovery ရဲ့ default အပြုအမူက — archive ထဲမှာ တွေ့ရတဲ့ နောက်အကျဆုံး timeline ဆီ recover လုပ်တာ ဖြစ်ပါတယ်။ Base backup ယူခဲ့တဲ့ အချိန်က လက်ရှိ ဖြစ်နေခဲ့တဲ့ timeline ဆီ ဒါမှမဟုတ် တိကျတဲ့ child timeline (ကလေး timeline) တစ်ခုဆီ recover လုပ်ချင်ရင် (ဆိုလိုတာက — recovery ကြိုးစားမှုတစ်ခုရဲ့ နောက်ပိုင်းမှာ ကိုယ်တိုင် ထုတ်လုပ်ခဲ့တဲ့ state တစ်ခုခုဆီ ပြန်သွားချင်ရင်) — [recovery_target_timeline](https://www.postgresql.org/docs/current/runtime-config-wal.html#GUC-RECOVERY-TARGET-TIMELINE) ထဲမှာ `current` ဒါမှမဟုတ် ပစ်မှတ် timeline ID ကို သတ်မှတ်ဖို့ လိုအပ်ပါတယ်။ Base backup ထက် စောပြီး ခွဲထွက်ခဲ့တဲ့ timelines တွေဆီကိုတော့ recover လုပ်လို့ မရပါဘူး။

### 25.3.7. Tips and Examples (အကြံပြုချက်များနှင့် ဥပမာများ)

Continuous archiving ကို ပြင်ဆင် သတ်မှတ်ခြင်းအတွက် အကြံပြုချက်တချို့ကို ဒီမှာ ဖော်ပြထားပါတယ်။

#### 25.3.7.1. Standalone Hot Backups (standalone hot backup များ)

PostgreSQL ရဲ့ backup facilities (backup စွမ်းဆောင်ချက်များ) တွေကို သုံးပြီး — standalone hot backups (သီးခြား hot backup များ) တွေကို ထုတ်လုပ်ဖို့ ဖြစ်နိုင်ပါတယ်။ ဒါတွေက point-in-time recovery အတွက် သုံးလို့ မရတဲ့ backups တွေ ဖြစ်ပေမယ့် — pg_dump dumps တွေထက် backup ရော restore ရော လုပ်ရတာ ပုံမှန်အားဖြင့် အများကြီး ပိုမြန်ပါတယ်။ (ဒါတွေက pg_dump dumps တွေထက်လည်း အများကြီး ပိုကြီးတာမို့ — အခြေအနေ တချို့မှာ — မြန်နှုန်း အားသာချက်က ပျက်ပြယ်သွားနိုင်ပါတယ်။)

Base backups တွေလိုပဲ — standalone hot backup တစ်ခုကို ထုတ်လုပ်ဖို့ အလွယ်ဆုံး နည်းလမ်းကတော့ [pg_basebackup](https://www.postgresql.org/docs/current/app-pgbasebackup.html) tool ကို သုံးတာ ဖြစ်ပါတယ်။ ၎င်းကို ခေါ်ယူတဲ့အခါ `-X` parameter ကို ထည့်သွင်းရင် — backup ကို သုံးဖို့ လိုအပ်တဲ့ write-ahead log တွေ အားလုံး — backup ထဲမှာ အလိုအလျောက် ပါဝင်သွားပြီး — backup ကို restore လုပ်ဖို့ အထူး ဆောင်ရွက်ချက် တစ်ခုခု မလိုအပ်ပါဘူး။

#### 25.3.7.2. Compressed Archive Logs (ချုံ့ထားသော archive log များ)

Archive storage အရွယ်အစားက စိုးရိမ်စရာ ဖြစ်နေရင် — archive ဖိုင်တွေကို ချုံ့ဖို့ gzip ကို သုံးနိုင်ပါတယ်:

```sql
archive_command = 'gzip < %p > /mnt/server/archivedir/%f.gz'
```

ပြီးရင် — recovery အတွင်း gunzip ကို သုံးဖို့ လိုအပ်ပါလိမ့်မယ်:

```sql
restore_command = 'gunzip < /mnt/server/archivedir/%f.gz > %p'
```

#### 25.3.7.3. `archive_command` Scripts (`archive_command` script များ)

လူအများစုက — သူတို့ရဲ့ `archive_command` ကို သတ်မှတ်ဖို့ scripts တွေ သုံးလေ့ ရှိကြပါတယ် — ဒါကြောင့် သူတို့ရဲ့ `postgresql.conf` entry က အရမ်း ရိုးရှင်းပုံ ရပါတယ်:

```sql
archive_command = 'local_backup_script.sh "%p" "%f"'
```

Archiving လုပ်ငန်းစဉ်ထဲမှာ command တစ်ခုထက်ပိုပြီး သုံးချင်တဲ့ အချိန်တိုင်းမှာ — သီးခြား script ဖိုင် တစ်ခုကို သုံးတာ သင့်လျော်ပါတယ်။ ဒါက ရှုပ်ထွေးမှုတွေ အားလုံးကို script ထဲမှာ စီမံခန့်ခွဲဖို့ ခွင့်ပြုပြီး — bash ဒါမှမဟုတ် perl လို — လူကြိုက်များတဲ့ scripting language တစ်ခုခုနဲ့ ရေးနိုင်ပါတယ်။

Script တစ်ခုထဲမှာ ဖြေရှင်းနိုင်မယ့် လိုအပ်ချက်တွေရဲ့ ဥပမာတွေကတော့:

- Data တွေကို လုံခြုံတဲ့ off-site data storage (site ပြင်ပ သိုလှောင်မှု) တစ်ခုဆီ ကူးယူခြင်း
- WAL ဖိုင်တွေကို တစ်ခုချင်းစီ လွှဲပြောင်းမည့်အစား — သုံးနာရီ တစ်ကြိမ် လွှဲပြောင်းဖို့ — batch (အစုလိုက် စုပေါင်း) လုပ်ခြင်း
- တခြား backup နဲ့ recovery software တွေနဲ့ ချိတ်ဆက် ဆက်သွယ်ခြင်း
- Errors တွေကို သတင်းပို့ဖို့ — monitoring software တွေနဲ့ ချိတ်ဆက် ဆက်သွယ်ခြင်း

> **အကြံပြုချက်:** `archive_command` script တစ်ခုကို သုံးတဲ့အခါ — [logging_collector](https://www.postgresql.org/docs/current/runtime-config-logging.html#GUC-LOGGING-COLLECTOR) ကို enable (ဖွင့်) လုပ်ထားတာ နှစ်လိုဖွယ် ကောင်းပါတယ်။ အဲဒါဆိုရင် — script ကနေ stderr ဆီ ရေးသားတဲ့ message တွေ ဘယ်ဟာမဆို — database server log ထဲမှာ ပေါ်လာပြီး — ရှုပ်ထွေးတဲ့ configurations တွေ ကျရှုံးခဲ့ရင် — အလွယ်တကူ ရောဂါ စစ်ဆေး ဖော်ထုတ်နိုင်စေပါတယ်။
### 25.3.8. Caveats (သတိထား ရမည့် အချက်များ)

ဒီစာရေးနေတဲ့ အချိန်မှာ — continuous archiving technique ရဲ့ ကန့်သတ်ချက်တွေ အများအပြား ရှိပါတယ်။ ဒါတွေကို အနာဂတ် release တွေမှာ ဖြေရှင်းဖို့ ဖြစ်နိုင်ခြေ ရှိပါတယ်:

- Base backup တစ်ခု ယူနေတဲ့ အချိန်အတွင်း CREATE DATABASE command တစ်ခုကို execute လုပ်ပြီး — base backup ဆက်လက် လုပ်ဆောင်နေတုန်း — CREATE DATABASE က မိတ္တူကူးယူခဲ့တဲ့ template database ကို ပြုပြင်မွမ်းမံလိုက်ရင် — recovery က အဲဒီ ပြုပြင်မွမ်းမံမှုတွေကို ဖန်တီးလိုက်တဲ့ database ထဲကိုပါ ပျံ့နှံ့ (propagate) စေနိုင်ပါတယ်။ ဒါက တကယ့်ကို မလိုလားအပ်တဲ့ အရာပါ။ ဒီအန္တရာယ်ကို ရှောင်ဖို့ — base backup ယူနေတဲ့ အချိန်အတွင်း — template databases တွေကို ဘယ်တစ်ခုကိုမှ ပြုပြင်မွမ်းမံတာ အကောင်းဆုံး ဖြစ်ပါတယ်။
- CREATE TABLESPACE commands တွေကို literal absolute path (စာသားအတိုင်း ရှိတဲ့ absolute path) နဲ့ WAL-log လုပ်ပြီး — ဒါကြောင့် — တူညီတဲ့ absolute path နဲ့ tablespace တွေ ဖန်တီးမှုအဖြစ် — replay လုပ်ခံရမှာ ဖြစ်ပါတယ်။ WAL ကို machine အခြားတစ်ခုပေါ်မှာ replay လုပ်နေရင် — ဒါက မလိုလားအပ်တာ ဖြစ်နိုင်ပါတယ်။ WAL ကို machine တစ်ခုတည်းပေါ်မှာပဲ replay လုပ်နေပေမယ့် — data directory အသစ်တစ်ခုထဲကို ဆိုရင်တောင် — အန္တရာယ် ရှိနိုင်ပါတယ်: replay က မူရင်း tablespace ရဲ့ ပါဝင်စရာတွေကို ဆက်လက် overwrite လုပ်နေဦးမှာ ဖြစ်လို့ပါ။ ဒီလိုမျိုး ဖြစ်နိုင်ခြေ ရှိတဲ့ ပြဿနာတွေ (gotchas) ကို ရှောင်ဖို့ — အကောင်းဆုံး လုပ်ဆောင်ချက်ကတော့ — tablespaces တွေ ဖန်တီးပြီး ဒါမှမဟုတ် ဖျက်ပြီးနောက် — base backup အသစ်တစ်ခု ယူတာ ဖြစ်ပါတယ်။

ထို့အပြင် — default WAL format က disk page snapshots (disk စာမျက်နှာ ပုံရိပ်များ) အများအပြား ပါဝင်လို့ — အတော်လေး ကြီးမား (bulky) တယ်ဆိုတာလည်း မှတ်သားထားသင့်ပါတယ်။ ဒီ page snapshots တွေက — တစ်စိတ်တစ်ပိုင်းပဲ ရေးသားပြီးတဲ့ disk pages တွေကို ပြုပြင်ဖို့ လိုအပ်နိုင်လို့ — crash recovery ကို ထောက်ပံ့ဖို့ ဒီဇိုင်းလုပ်ထားတာ ဖြစ်ပါတယ်။ သင့် system ရဲ့ hardware နဲ့ software ပေါ် မူတည်ပြီး — partial writes (တစ်စိတ်တစ်ပိုင်း ရေးသားမှုများ) ရဲ့ အန္တရာယ်က လျစ်လျူရှုလောက်အောင် ငယ်နေနိုင်ပြီး — အဲဒီလို ဆိုရင် — [full_page_writes](https://www.postgresql.org/docs/current/runtime-config-wal.html#GUC-FULL-PAGE-WRITES) parameter ကို သုံးပြီး page snapshots တွေကို ပိတ်လိုက်ခြင်းအားဖြင့် — archive လုပ်ထားတဲ့ WAL ဖိုင်တွေရဲ့ စုစုပေါင်း ထုထည် (volume) ကို သိသိသာသာ လျှော့ချနိုင်ပါတယ်။ (ဒါကို မလုပ်ခင် — [အခန်း 28](https://www.postgresql.org/docs/current/wal.html) ထဲက notes နဲ့ warnings တွေကို ဖတ်ပါ။) Page snapshots တွေကို ပိတ်လိုက်တာက PITR operations တွေအတွက် WAL ကို သုံးတာကို တားဆီးမပေးပါဘူး။ အနာဂတ် ဖွံ့ဖြိုးတိုးတက်မှုအတွက် နယ်ပယ်တစ်ခုကတော့ — `full_page_writes` ဖွင့်ထားချိန်မှာတောင် — မလိုအပ်တဲ့ page copies တွေကို ဖယ်ရှားခြင်းအားဖြင့် — archive လုပ်ထားတဲ့ WAL data တွေကို ချုံ့ဖို့ ဖြစ်ပါတယ်။ ဒီအချိန်အတောအတွင်းမှာတော့ — administrators တွေက — checkpoint interval parameters တွေကို ဖြစ်နိုင်သမျှ တိုးမြှင့်ခြင်းအားဖြင့် — WAL ထဲမှာ ပါဝင်တဲ့ page snapshots အရေအတွက်ကို လျှော့ချချင်နိုင်ပါတယ်။
