### 19.4.1. Memory (မှတ်ဉာဏ်)

- **shared_buffers (integer)** — Database server က shared memory buffer တွေအတွက် အသုံးပြုတဲ့ memory ပမာဏကို သတ်မှတ်ပါတယ်။ Default ကတော့ ပုံမှန်အားဖြင့် 128 megabytes (128MB) ဖြစ်ပေမယ့် — သင့် kernel setting တွေက မထောက်ပံ့နိုင်ရင် (initdb လုပ်တဲ့အခါ ဆုံးဖြတ်သည့်အတိုင်း) ပိုနည်းနိုင်ပါတယ်။ ဒီ setting က အနည်းဆုံး 128 kilobytes ရှိရပါမယ်။ ဒါပေမယ့် — ကောင်းမွန်တဲ့ performance အတွက် အနည်းဆုံးထက် သိသိသာသာ မြင့်တဲ့ setting တွေ ပုံမှန်အားဖြင့် လိုအပ်ပါတယ်။ ဒီတန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် — blocks အနေနဲ့ ယူပါတယ်၊ ဆိုလိုတာက BLCKSZ bytes ဖြစ်ပြီး — ပုံမှန်အားဖြင့် 8kB ပါ။ (BLCKSZ ရဲ့ non-default တန်ဖိုးတွေက အနည်းဆုံးတန်ဖိုးကို ပြောင်းလဲစေပါတယ်။) ဒီ parameter ကို server start လုပ်ချိန်မှာပဲ သတ်မှတ်နိုင်ပါတယ်။

RAM 1GB ဒါမှမဟုတ် ထိုထက်ပိုရှိတဲ့ dedicated database server တစ်ခု ရှိရင် — shared_buffers အတွက် သင့်လျော်တဲ့ စတင်တန်ဖိုးက သင့် system ထဲက memory ရဲ့ 25% ဖြစ်ပါတယ်။ shared_buffers အတွက် ထိုထက်ပိုကြီးတဲ့ setting တွေ ထိရောက်တဲ့ workload တချို့လည်း ရှိပါတယ် — ဒါပေမယ့် PostgreSQL က operating system cache ကိုလည်း မှီခိုတာကြောင့် — RAM ရဲ့ 40% ကျော်ကို shared_buffers အတွက် ခွဲဝေခြင်းက ပိုနည်းတဲ့ ပမာဏထက် ပိုကောင်းလာနိုင်ခြေ မရှိပါဘူး။ shared_buffers အတွက် ပိုကြီးတဲ့ setting တွေက — အသစ် ဒါမှမဟုတ် ပြောင်းလဲထားတဲ့ data အမြောက်အများကို ရေးသားတဲ့ လုပ်ငန်းစဉ်ကို အချိန်ကာလ ပိုရှည်တစ်ခုအထိ ဖြန့်ကျက်ဖို့ — max_wal_size ကို ဆက်စပ်စွာ တိုးရပါတယ်။

RAM 1GB အောက် ရှိတဲ့ system တွေမှာတော့ — operating system အတွက် လုံလောက်တဲ့ နေရာ ချန်ထားဖို့ — RAM ရဲ့ ပိုနည်းတဲ့ ရာခိုင်နှုန်း သင့်လျော်ပါတယ်။

- **huge_pages (enum)** — Main shared memory area အတွက် huge pages တောင်းခံမလားဆိုတာ ထိန်းချုပ်ပါတယ်။ ဖြစ်နိုင်တဲ့ တန်ဖိုးတွေက try (default)၊ on နဲ့ off ဖြစ်ပါတယ်။ ဒီ parameter ကို server start လုပ်ချိန်မှာပဲ သတ်မှတ်နိုင်ပါတယ်။ huge_pages ကို try သတ်မှတ်ထားရင် — server က huge pages တောင်းခံဖို့ ကြိုးစားပေမယ့် — မအောင်မြင်ရင် default ကို ပြန်ကျသွားပါတယ်။ on ဖြစ်ရင် — huge pages တောင်းခံမှု မအောင်မြင်ခြင်းက server ကို စတင်ခြင်းမှ တားဆီးပါလိမ့်မယ်။ off ဖြစ်ရင် — huge pages တောင်းခံမှာ မဟုတ်ပါဘူး။ Huge pages တွေရဲ့ အမှန်တကယ် အခြေအနေကို huge_pages_status ဆိုတဲ့ server variable က ဖော်ပြပါတယ်။

လက်ရှိအချိန်မှာ ဒီ setting ကို Linux နဲ့ Windows မှာပဲ ထောက်ပံ့ပါတယ်။ အခြား system တွေမှာ try သတ်မှတ်ထားရင် ဒီ setting ကို လျစ်လျူရှုပါတယ်။ Linux မှာတော့ shared_memory_type ကို mmap (default) သတ်မှတ်ထားတဲ့အခါမှပဲ ထောက်ပံ့ပါတယ်။

Huge pages အသုံးပြုခြင်းက page table တွေ ပိုသေးစေပြီး — memory management အတွက် ကုန်ဆုံးတဲ့ CPU time ကို လျှော့ချကာ — performance ကို မြှင့်တင်ပေးပါတယ်။ Linux မှာ huge pages အသုံးပြုခြင်းအကြောင်း အသေးစိတ်အတွက် [အပိုင်း 18.4.5](/docs/postgresql/kernel-resources) ကို ကြည့်ပါ။

Windows မှာ huge pages ကို large pages လို့ ခေါ်ပါတယ်။ သူတို့ကို အသုံးပြုဖို့ — PostgreSQL ကို run လုပ်တဲ့ Windows user account အတွက် “Lock pages in memory” ဆိုတဲ့ user right ကို သတ်မှတ်ပေးရပါမယ်။ “Lock pages in memory” user right ကို သတ်မှတ်ဖို့ Windows Group Policy tool (gpedit.msc) ကို သုံးနိုင်ပါတယ်။ Database server ကို Windows service အနေနဲ့ မဟုတ်ဘဲ — standalone process အနေနဲ့ command prompt ကနေ စတင်ဖို့ — command prompt ကို administrator အနေနဲ့ run ရပါမယ်၊ ဒါမှမဟုတ် User Access Control (UAC) ကို disable လုပ်ထားရပါမယ်။ UAC enable ဖြစ်နေရင် — ပုံမှန် command prompt ကို စတင်တဲ့အခါ “Lock pages in memory” user right ကို ရုပ်သိမ်းပါတယ်။

ဒီ setting က main shared memory area ကိုပဲ သက်ရောက်တယ်ဆိုတာ သတိပြုပါ။ Linux၊ FreeBSD နဲ့ Illumos ကဲ့သို့ operating system တွေက — PostgreSQL ဆီက တိုက်ရိုက် တောင်းဆိုမှု မပါဘဲ — ပုံမှန် memory allocation အတွက် huge pages (“super” pages ဒါမှမဟုတ် “large” pages လို့လည်း ခေါ်) ကို အလိုအလျောက် သုံးနိုင်ပါတယ်။ Linux မှာ ဒါကို “transparent huge pages” (THP) လို့ ခေါ်ပါတယ်။ ဒီ feature က Linux version တချို့မှာ user တချို့အတွက် PostgreSQL နဲ့ performance ကျဆင်းမှု ဖြစ်စေတယ်လို့ သိရတာကြောင့် — လက်ရှိအချိန်မှာ သူ့ကို အသုံးပြုခြင်းကို မအားပေးပါဘူး (huge_pages ကို တိုက်ရိုက် အသုံးပြုခြင်းနဲ့ မတူဘဲ)။

- **huge_page_size (integer)** — huge_pages နဲ့ enable လုပ်ထားတဲ့အခါ — huge pages တွေရဲ့ အရွယ်အစားကို ထိန်းချုပ်ပါတယ်။ Default က သုည (0) ဖြစ်ပါတယ်။ 0 သတ်မှတ်ရင် — system ရဲ့ default huge page size ကို သုံးပါလိမ့်မယ်။ ဒီ parameter ကို server start လုပ်ချိန်မှာပဲ သတ်မှတ်နိုင်ပါတယ်။

ခေတ်သစ် 64 bit server architecture တွေမှာ အသုံးများတဲ့ page size တချို့မှာ — 2MB နဲ့ 1GB (Intel နဲ့ AMD)၊ 16MB နဲ့ 16GB (IBM POWER)၊ နဲ့ 64kB၊ 2MB၊ 32MB နဲ့ 1GB (ARM) တို့ ပါဝင်ပါတယ်။ အသုံးပြုမှုနဲ့ ထောက်ပံ့မှုအကြောင်း ပိုမိုသိရှိဖို့ [အပိုင်း 18.4.5](/docs/postgresql/kernel-resources) ကို ကြည့်ပါ။

Non-default setting တွေကို လက်ရှိအချိန်မှာ Linux မှာပဲ ထောက်ပံ့ပါတယ်။

- **temp_buffers (integer)** — Database session တစ်ခုချင်းစီအတွင်း temporary buffer တွေအတွက် အသုံးပြုတဲ့ memory အများဆုံး ပမာဏကို သတ်မှတ်ပါတယ်။ ဒါတွေက temporary table တွေကို ဝင်ရောက်ဖို့ပဲ သုံးတဲ့ session-local buffer တွေ ဖြစ်ပါတယ်။ ဒီတန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် — blocks အနေနဲ့ ယူပါတယ်၊ ဆိုလိုတာက BLCKSZ bytes ဖြစ်ပြီး — ပုံမှန်အားဖြင့် 8kB ပါ။ Default က ရှစ် megabytes (8MB) ဖြစ်ပါတယ်။ (BLCKSZ က 8kB မဟုတ်ရင် — default တန်ဖိုးက သူ့အလိုက် အချိုးကျ ပြောင်းလဲပါတယ်။) ဒီ setting ကို session တစ်ခုချင်းစီအတွင်း ပြောင်းနိုင်ပေမယ့် — session အတွင်း temporary table တွေကို ပထမဆုံး အသုံးမပြုမီမှာပဲ ပြောင်းနိုင်ပါတယ်; နောက်ပိုင်း ပြောင်းဖို့ ကြိုးစားမှုတွေက အဲဒီ session အပေါ် သက်ရောက်မှု ရှိမှာ မဟုတ်ပါဘူး။

Session တစ်ခုက — temp_buffers က ပေးထားတဲ့ limit အထိ — လိုအပ်သလို temporary buffer တွေ ခွဲဝေပါလိမ့်မယ်။ temporary buffer အများကြီး တကယ် မလိုအပ်တဲ့ session တွေမှာ ကြီးမားတဲ့ တန်ဖိုး သတ်မှတ်ခြင်းရဲ့ ကုန်ကျမှုက — temp_buffers တိုးတိုင်း buffer descriptor တစ်ခု ဒါမှမဟုတ် 64 bytes ခန့်ပဲ ဖြစ်ပါတယ်။ ဒါပေမယ့် buffer တစ်ခုကို တကယ် အသုံးပြုရင် — သူ့အတွက် ထပ်ဆောင်း 8192 bytes (သို့မဟုတ် ယေဘုယျအားဖြင့် BLCKSZ bytes) ကုန်ဆုံးပါလိမ့်မယ်။

- **max_prepared_transactions (integer)** — တစ်ပြိုင်နက် “prepared” အခြေအနေမှာ ရှိနိုင်တဲ့ transaction အများဆုံး အရေအတွက်ကို သတ်မှတ်ပါတယ် (PREPARE TRANSACTION ကို ကြည့်ပါ)။ ဒီ parameter ကို သုည (default ဖြစ်တဲ့) သတ်မှတ်ခြင်းက prepared-transaction feature ကို disable လုပ်ပါတယ်။ ဒီ parameter ကို server start လုပ်ချိန်မှာပဲ သတ်မှတ်နိုင်ပါတယ်။

Prepared transaction တွေကို အသုံးပြုဖို့ အစီအစဉ် မရှိရင် — မတော်တဆ prepared transaction ဖန်တီးခြင်းကို တားဆီးဖို့ ဒီ parameter ကို သုည သတ်မှတ်သင့်ပါတယ်။ Prepared transaction တွေ အသုံးပြုနေရင် — session တိုင်း prepared transaction တစ်ခု pending ရှိနိုင်ဖို့ — max_prepared_transactions ကို အနည်းဆုံး max_connections လောက် ရှိစေချင်ပါလိမ့်မယ်။

Standby server တစ်ခု run နေစဉ် — ဒီ parameter ကို primary server ထက် တူတူ ဒါမှမဟုတ် ပိုမြင့်တဲ့ တန်ဖိုး သတ်မှတ်ရပါမယ်။ မဟုတ်ရင် — standby server မှာ query တွေကို ခွင့်ပြုမှာ မဟုတ်ပါဘူး။

- **work_mem (integer)** — Temporary disk file တွေဆီ မရေးသားမီ — query operation တစ်ခု (ဥပမာ sort ဒါမှမဟုတ် hash table) အသုံးပြုမယ့် အခြေခံ memory အများဆုံး ပမာဏကို သတ်မှတ်ပါတယ်။ ဒီတန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် — kilobytes အနေနဲ့ ယူပါတယ်။ Default တန်ဖိုးက လေး megabytes (4MB) ဖြစ်ပါတယ်။ ရှုပ်ထွေးတဲ့ query တစ်ခုက sort နဲ့ hash operation များစွာကို တစ်ချိန်တည်းမှာ လုပ်ဆောင်နိုင်ပြီး — operation တစ်ခုချင်းစီက ပုံမှန်အားဖြင့် temporary file တွေထဲ data မရေးသားမီ ဒီတန်ဖိုး သတ်မှတ်ထားသလောက် memory ကို အသုံးပြုခွင့် ရတယ်ဆိုတာ သတိပြုပါ။ ဒါ့အပြင် — run နေတဲ့ session များစွာက ဒီလို operation တွေကို တစ်ပြိုင်နက် လုပ်ဆောင်နိုင်ပါတယ်။ ဒါကြောင့် — အသုံးပြုတဲ့ စုစုပေါင်း memory က work_mem တန်ဖိုးထက် အဆများစွာ ပိုနိုင်ပါတယ်; တန်ဖိုး ရွေးချယ်တဲ့အခါ ဒီအချက်ကို စိတ်ထဲမှာ ထားရပါမယ်။ Sort operation တွေကို ORDER BY၊ DISTINCT နဲ့ merge join တွေအတွက် သုံးပါတယ်။ Hash table တွေကို hash join၊ hash-based aggregation၊ memoize node နဲ့ IN subquery တွေရဲ့ hash-based processing တို့မှာ သုံးပါတယ်။

Hash-based operation တွေက — သူတို့နဲ့ ညီမျှတဲ့ sort-based operation တွေထက် — memory ရရှိနိုင်မှုအပေါ် ယေဘုယျအားဖြင့် ပိုပြီး ထိခိုက်လွယ်ပါတယ်။ Hash table တစ်ခုအတွက် memory limit ကို work_mem ကို hash_mem_multiplier နဲ့ မြှောက်ခြင်းဖြင့် တွက်ချက်ပါတယ်။ ဒါက — hash-based operation တွေကို ပုံမှန် work_mem အခြေခံ ပမာဏထက် ကျော်လွန်တဲ့ memory ပမာဏကို အသုံးပြုနိုင်စေပါတယ်။

- **hash_mem_multiplier (floating point)** — Hash-based operation တွေ အသုံးပြုနိုင်တဲ့ memory အများဆုံး ပမာဏကို တွက်ချက်ဖို့ သုံးပါတယ်။ နောက်ဆုံး limit ကို work_mem ကို hash_mem_multiplier နဲ့ မြှောက်ခြင်းဖြင့် သတ်မှတ်ပါတယ်။ Default တန်ဖိုးက 2.0 ဖြစ်ပြီး — hash-based operation တွေကို ပုံမှန် work_mem အခြေခံ ပမာဏရဲ့ နှစ်ဆ သုံးစေပါတယ်။

Query operation တွေက spill လုပ်တာ ပုံမှန် ဖြစ်နေတဲ့ ပတ်ဝန်းကျင်တွေမှာ — အထူးသဖြင့် work_mem ကို ရိုးရိုး တိုးလိုက်တာက memory pressure ဖြစ်စေတဲ့အခါ (memory pressure က ပုံမှန်အားဖြင့် ရံဖန်ရံခါ ပေါ်တဲ့ out of memory error အသွင်နဲ့ လာတတ်ပါတယ်) — hash_mem_multiplier ကို တိုးဖို့ စဉ်းစားပါ။ Default setting 2.0 က mixed workload တွေမှာ မကြာခဏ ထိရောက်ပါတယ်။ 2.0 - 8.0 ဒါမှမဟုတ် ထိုထက်ပိုတဲ့ အပိုင်းအခြားထဲက မြင့်တဲ့ setting တွေက — work_mem ကို 40MB ဒါမှမဟုတ် ထိုထက်ပို တိုးပြီးသား ပတ်ဝန်းကျင်တွေမှာ ထိရောက်နိုင်ပါတယ်။

- **maintenance_work_mem (integer)** — VACUUM၊ CREATE INDEX နဲ့ ALTER TABLE ADD FOREIGN KEY ကဲ့သို့ maintenance operation တွေ အသုံးပြုမယ့် memory အများဆုံး ပမာဏကို သတ်မှတ်ပါတယ်။ ဒီတန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် — kilobytes အနေနဲ့ ယူပါတယ်။ Default က 64 megabytes (64MB) ဖြစ်ပါတယ်။ ဒီ operation တွေထဲက တစ်ခုကိုပဲ database session တစ်ခုက တစ်ချိန်တည်းမှာ execute လုပ်နိုင်တာကြောင့် — installation တစ်ခုမှာ အဲဒါတွေ တစ်ပြိုင်နက် run နေတာ ပုံမှန်အားဖြင့် မများတာကြောင့် — ဒီတန်ဖိုးကို work_mem ထက် သိသိသာသာ ပိုကြီးအောင် သတ်မှတ်တာ လုံခြုံပါတယ်။ ပိုကြီးတဲ့ setting တွေက vacuuming လုပ်ခြင်းနဲ့ database dump တွေ restore လုပ်ခြင်းအတွက် performance ကို တိုးတက်စေနိုင်ပါတယ်။

autovacuum run တဲ့အခါ — ဒီ memory ရဲ့ autovacuum_max_workers အဆအထိ ခွဲဝေနိုင်တာကြောင့် — default တန်ဖိုးကို အလွန်အကျွံ မမြင့်အောင် သတိထားပါ။ autovacuum_work_mem ကို သီးခြား သတ်မှတ်ခြင်းဖြင့် ဒါကို ထိန်းချုပ်တာ အသုံးဝင်နိုင်ပါတယ်။

- **autovacuum_work_mem (integer)** — autovacuum worker process တစ်ခုချင်းစီ အသုံးပြုမယ့် memory အများဆုံး ပမာဏကို သတ်မှတ်ပါတယ်။ ဒီတန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် — kilobytes အနေနဲ့ ယူပါတယ်။ Default က -1 ဖြစ်ပြီး — အဲဒါက maintenance_work_mem ရဲ့ တန်ဖိုးကို အစားထိုး သုံးသင့်တယ်ဆိုတာ ဖော်ပြပါတယ်။ ဒီ setting က အခြား အခြေအနေတွေမှာ run တဲ့ VACUUM ရဲ့ အပြုအမူအပေါ် သက်ရောက်မှု မရှိပါဘူး။ ဒီ parameter ကို postgresql.conf ဖိုင်ထဲမှာ ဒါမှမဟုတ် server command line မှာပဲ သတ်မှတ်နိုင်ပါတယ်။

- **vacuum_buffer_usage_limit (integer)** — VACUUM နဲ့ ANALYZE command တွေ အသုံးပြုတဲ့ Buffer Access Strategy ရဲ့ အရွယ်အစားကို သတ်မှတ်ပါတယ်။ 0 သတ်မှတ်ခြင်းက — operation ကို shared_buffers မည်သည့် အရေအတွက်မဆို အသုံးပြုခွင့် ပြုပါတယ်။ မဟုတ်ရင် — တရားဝင် အရွယ်အစားတွေက 128 kB ကနေ 16 GB အထိ ရှိပါတယ်။ သတ်မှတ်ထားတဲ့ အရွယ်အစားက shared_buffers ရဲ့ 1/8 ကို ကျော်လွန်ရင် — အရွယ်အစားကို အဲဒီတန်ဖိုးအထိ တိတ်ဆိတ်စွာ ကန့်သတ်ပါတယ်။ Default တန်ဖိုးက 2MB ဖြစ်ပါတယ်။ ဒီတန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် — kilobytes အနေနဲ့ ယူပါတယ်။ ဒီ parameter ကို အချိန်မရွေး သတ်မှတ်နိုင်ပါတယ်။ BUFFER_USAGE_LIMIT option ကို ပေးပို့တဲ့အခါ VACUUM နဲ့ ANALYZE အတွက် ဒါကို override လုပ်နိုင်ပါတယ်။ မြင့်တဲ့ setting တွေက VACUUM နဲ့ ANALYZE ကို ပိုမြန်စွာ run စေနိုင်ပေမယ့် — setting အလွန်ကြီးရင် အသုံးဝင်တဲ့ အခြား page တွေ shared buffer ထဲကနေ အလွန်အကျွံ ဖယ်ရှားခံရနိုင်ပါတယ်။

- **logical_decoding_work_mem (integer)** — Decoded change တချို့ကို local disk ဆီ မရေးသားမီ — logical decoding အသုံးပြုမယ့် memory အများဆုံး ပမာဏကို သတ်မှတ်ပါတယ်။ ဒါက logical streaming replication connection တွေ အသုံးပြုတဲ့ memory ပမာဏကို ကန့်သတ်ပါတယ်။ Default က 64 megabytes (64MB) ဖြစ်ပါတယ်။ Replication connection တစ်ခုချင်းစီက ဒီအရွယ်အစားရှိ buffer တစ်ခုကိုပဲ သုံးတာကြောင့် — installation တစ်ခုမှာ အဲဒီလို connection တွေ တစ်ပြိုင်နက် များစွာ ရှိတာ ပုံမှန်အားဖြင့် မရှိတာကြောင့် (max_wal_senders က ကန့်သတ်သည့်အတိုင်း) — ဒီတန်ဖိုးကို work_mem ထက် သိသိသာသာ ပိုမြင့်အောင် သတ်မှတ်တာ လုံခြုံပြီး — disk ဆီ ရေးသားတဲ့ decoded change ပမာဏကို လျှော့ချပေးပါတယ်။

- **commit_timestamp_buffers (integer)** — pg_commit_ts ရဲ့ အကြောင်းအရာတွေကို cache လုပ်ဖို့ အသုံးပြုတဲ့ memory ပမာဏကို သတ်မှတ်ပါတယ် (ဇယား 66.1 ကို ကြည့်ပါ)။ ဒီတန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် — blocks အနေနဲ့ ယူပါတယ်၊ ဆိုလိုတာက BLCKSZ bytes ဖြစ်ပြီး — ပုံမှန်အားဖြင့် 8kB ပါ။ Default တန်ဖိုးက 0 ဖြစ်ပြီး — shared_buffers/512 ကို blocks 1024 အထိ တောင်းခံပေမယ့် blocks 16 ထက် မနည်းပါဘူး။ ဒီ parameter ကို server start လုပ်ချိန်မှာပဲ သတ်မှတ်နိုင်ပါတယ်။

- **multixact_member_buffers (integer)** — pg_multixact/members ရဲ့ အကြောင်းအရာတွေကို cache လုပ်ဖို့ အသုံးပြုတဲ့ shared memory ပမာဏကို သတ်မှတ်ပါတယ် (ဇယား 66.1 ကို ကြည့်ပါ)။ ဒီတန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် — blocks အနေနဲ့ ယူပါတယ်၊ ဆိုလိုတာက BLCKSZ bytes ဖြစ်ပြီး — ပုံမှန်အားဖြင့် 8kB ပါ။ Default တန်ဖိုးက 32 ဖြစ်ပါတယ်။ ဒီ parameter ကို server start လုပ်ချိန်မှာပဲ သတ်မှတ်နိုင်ပါတယ်။

- **multixact_offset_buffers (integer)** — pg_multixact/offsets ရဲ့ အကြောင်းအရာတွေကို cache လုပ်ဖို့ အသုံးပြုတဲ့ shared memory ပမာဏကို သတ်မှတ်ပါတယ် (ဇယား 66.1 ကို ကြည့်ပါ)။ ဒီတန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် — blocks အနေနဲ့ ယူပါတယ်၊ ဆိုလိုတာက BLCKSZ bytes ဖြစ်ပြီး — ပုံမှန်အားဖြင့် 8kB ပါ။ Default တန်ဖိုးက 16 ဖြစ်ပါတယ်။ ဒီ parameter ကို server start လုပ်ချိန်မှာပဲ သတ်မှတ်နိုင်ပါတယ်။

- **notify_buffers (integer)** — pg_notify ရဲ့ အကြောင်းအရာတွေကို cache လုပ်ဖို့ အသုံးပြုတဲ့ shared memory ပမာဏကို သတ်မှတ်ပါတယ် (ဇယား 66.1 ကို ကြည့်ပါ)။ ဒီတန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် — blocks အနေနဲ့ ယူပါတယ်၊ ဆိုလိုတာက BLCKSZ bytes ဖြစ်ပြီး — ပုံမှန်အားဖြင့် 8kB ပါ။ Default တန်ဖိုးက 16 ဖြစ်ပါတယ်။ ဒီ parameter ကို server start လုပ်ချိန်မှာပဲ သတ်မှတ်နိုင်ပါတယ်။

- **serializable_buffers (integer)** — pg_serial ရဲ့ အကြောင်းအရာတွေကို cache လုပ်ဖို့ အသုံးပြုတဲ့ shared memory ပမာဏကို သတ်မှတ်ပါတယ် (ဇယား 66.1 ကို ကြည့်ပါ)။ ဒီတန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် — blocks အနေနဲ့ ယူပါတယ်၊ ဆိုလိုတာက BLCKSZ bytes ဖြစ်ပြီး — ပုံမှန်အားဖြင့် 8kB ပါ။ Default တန်ဖိုးက 32 ဖြစ်ပါတယ်။ ဒီ parameter ကို server start လုပ်ချိန်မှာပဲ သတ်မှတ်နိုင်ပါတယ်။

- **subtransaction_buffers (integer)** — pg_subtrans ရဲ့ အကြောင်းအရာတွေကို cache လုပ်ဖို့ အသုံးပြုတဲ့ shared memory ပမာဏကို သတ်မှတ်ပါတယ် (ဇယား 66.1 ကို ကြည့်ပါ)။ ဒီတန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် — blocks အနေနဲ့ ယူပါတယ်၊ ဆိုလိုတာက BLCKSZ bytes ဖြစ်ပြီး — ပုံမှန်အားဖြင့် 8kB ပါ။ Default တန်ဖိုးက 0 ဖြစ်ပြီး — shared_buffers/512 ကို blocks 1024 အထိ တောင်းခံပေမယ့် blocks 16 ထက် မနည်းပါဘူး။ ဒီ parameter ကို server start လုပ်ချိန်မှာပဲ သတ်မှတ်နိုင်ပါတယ်။

- **transaction_buffers (integer)** — pg_xact ရဲ့ အကြောင်းအရာတွေကို cache လုပ်ဖို့ အသုံးပြုတဲ့ shared memory ပမာဏကို သတ်မှတ်ပါတယ် (ဇယား 66.1 ကို ကြည့်ပါ)။ ဒီတန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် — blocks အနေနဲ့ ယူပါတယ်၊ ဆိုလိုတာက BLCKSZ bytes ဖြစ်ပြီး — ပုံမှန်အားဖြင့် 8kB ပါ။ Default တန်ဖိုးက 0 ဖြစ်ပြီး — shared_buffers/512 ကို blocks 1024 အထိ တောင်းခံပေမယ့် blocks 16 ထက် မနည်းပါဘူး။ ဒီ parameter ကို server start လုပ်ချိန်မှာပဲ သတ်မှတ်နိုင်ပါတယ်။

- **max_stack_depth (integer)** — Server ရဲ့ execution stack အများဆုံး လုံခြုံတဲ့ အနက်ကို သတ်မှတ်ပါတယ်။ ဒီ parameter အတွက် အကောင်းဆုံး setting က — kernel က ချမှတ်တဲ့ အမှန်တကယ် stack size limit (ulimit -s ဒါမှမဟုတ် local equivalent နဲ့ သတ်မှတ်တဲ့အတိုင်း) ကနေ တစ် megabyte ခန့် safety margin နုတ်ထားတဲ့ တန်ဖိုး ဖြစ်ပါတယ်။ Safety margin က လိုအပ်တာက — stack depth ကို server ထဲက routine တိုင်းမှာ စစ်ဆေးတာ မဟုတ်ဘဲ — recursive ဖြစ်နိုင်ခြေရှိတဲ့ အဓိက routine တွေမှာပဲ စစ်ဆေးတာကြောင့်ပါ။ ဒီတန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် — kilobytes အနေနဲ့ ယူပါတယ်။ Default setting က နှစ် megabytes (2MB) ဖြစ်ပြီး — ရှေးရိုးဆန်စွာ သေးငယ်ကာ crash ဖြစ်နိုင်ခြေ နည်းပါတယ်။ ဒါပေမယ့် — ရှုပ်ထွေးတဲ့ function တွေ execute လုပ်ဖို့ သေးလွန်းနိုင်ပါတယ်။ Superuser နဲ့ သင့်လျော်တဲ့ SET privilege ရှိတဲ့ user တွေပဲ ဒီ setting ကို ပြောင်းနိုင်ပါတယ်။

max_stack_depth ကို အမှန်တကယ် kernel limit ထက် မြင့်အောင် သတ်မှတ်ခြင်းက — ထိန်းမရတဲ့ recursive function တစ်ခုက backend process တစ်ခုကို crash ဖြစ်စေနိုင်ပါတယ်။ PostgreSQL က kernel limit ကို ဆုံးဖြတ်နိုင်တဲ့ platform တွေမှာ — server က ဒီ variable ကို မလုံခြုံတဲ့ တန်ဖိုးအဖြစ် သတ်မှတ်ခွင့် ပြုမှာ မဟုတ်ပါဘူး။ ဒါပေမယ့် — platform အားလုံး ဒီအချက်အလက်ကို ပေးတာ မဟုတ်တာကြောင့် — တန်ဖိုး ရွေးချယ်တဲ့အခါ သတိထားဖို့ အကြံပြုပါတယ်။

- **shared_memory_type (enum)** — PostgreSQL ရဲ့ shared buffer တွေနဲ့ အခြား shared data တွေကို ထိန်းသိမ်းထားတဲ့ main shared memory region အတွက် server သုံးသင့်တဲ့ shared memory implementation ကို သတ်မှတ်ပါတယ်။ ဖြစ်နိုင်တဲ့ တန်ဖိုးတွေက mmap (mmap သုံးပြီး ခွဲဝေတဲ့ anonymous shared memory အတွက်)၊ sysv (shmget ကတစ်ဆင့် ခွဲဝေတဲ့ System V shared memory အတွက်) နဲ့ windows (Windows shared memory အတွက်) ဖြစ်ပါတယ်။ တန်ဖိုးအားလုံးကို platform အားလုံးမှာ ထောက်ပံ့တာ မဟုတ်ပါဘူး; ပထမဆုံး ထောက်ပံ့တဲ့ option က အဲဒီ platform အတွက် default ဖြစ်ပါတယ်။ Platform ဘယ်တစ်ခုမှာမှ default မဟုတ်တဲ့ sysv option ကို အသုံးပြုခြင်းကို — ကြီးမားတဲ့ allocation တွေ ခွင့်ပြုဖို့ non-default kernel setting တွေ ပုံမှန်အားဖြင့် လိုအပ်တာကြောင့် — ယေဘုယျအားဖြင့် မအားပေးပါဘူး ([အပိုင်း 18.4.1](/docs/postgresql/kernel-resources) ကို ကြည့်ပါ)။ ဒီ parameter ကို server start လုပ်ချိန်မှာပဲ သတ်မှတ်နိုင်ပါတယ်။

- **dynamic_shared_memory_type (enum)** — Server သုံးသင့်တဲ့ dynamic shared memory implementation ကို သတ်မှတ်ပါတယ်။ ဖြစ်နိုင်တဲ့ တန်ဖိုးတွေက posix (shm_open သုံးပြီး ခွဲဝေတဲ့ POSIX shared memory အတွက်)၊ sysv (shmget ကတစ်ဆင့် ခွဲဝေတဲ့ System V shared memory အတွက်)၊ windows (Windows shared memory အတွက်) နဲ့ mmap (data directory ထဲ သိမ်းထားတဲ့ memory-mapped file တွေကို သုံးပြီး shared memory ကို တုပဖို့) ဖြစ်ပါတယ်။ တန်ဖိုးအားလုံးကို platform အားလုံးမှာ ထောက်ပံ့တာ မဟုတ်ပါဘူး; ပထမဆုံး ထောက်ပံ့တဲ့ option က အဲဒီ platform အတွက် default ဖြစ်ပါတယ်။ Platform ဘယ်တစ်ခုမှာမှ default မဟုတ်တဲ့ mmap option ကို အသုံးပြုခြင်းကို — operating system က ပြောင်းလဲထားတဲ့ page တွေကို disk ဆီ အကြိမ်ကြိမ် ပြန်ရေးနိုင်ကာ system I/O load ကို တိုးစေတာကြောင့် — ယေဘုယျအားဖြင့် မအားပေးပါဘူး; ဒါပေမယ့် — debug လုပ်တဲ့အခါ၊ pg_dynshmem directory ကို RAM disk ပေါ်မှာ သိမ်းတဲ့အခါ၊ ဒါမှမဟုတ် အခြား shared memory အထောက်အကူတွေ မရနိုင်တဲ့အခါ — ဒါက အသုံးဝင်နိုင်ပါတယ်။ ဒီ parameter ကို server start လုပ်ချိန်မှာပဲ သတ်မှတ်နိုင်ပါတယ်။

- **min_dynamic_shared_memory (integer)** — Parallel query တွေ အသုံးပြုဖို့ server startup မှာ ခွဲဝေသင့်တဲ့ memory ပမာဏကို သတ်မှတ်ပါတယ်။ ဒီ memory region က မလုံလောက်တဲ့အခါ ဒါမှမဟုတ် တစ်ပြိုင်နက် query တွေက ကုန်ဆုံးစေတဲ့အခါ — parallel query အသစ်တွေက dynamic_shared_memory_type နဲ့ configure လုပ်ထားတဲ့ နည်းလမ်းကို သုံးပြီး operating system ဆီကနေ ယာယီ ထပ်ဆောင်း shared memory ခွဲဝေဖို့ ကြိုးစားပါတယ်; ဒါက memory management ရဲ့ overhead တွေကြောင့် ပိုနှေးနိုင်ပါတယ်။ min_dynamic_shared_memory နဲ့ startup မှာ ခွဲဝေတဲ့ memory က — ထောက်ပံ့တဲ့ operating system တွေမှာ huge_pages setting ရဲ့ သက်ရောက်မှုကို ခံရပြီး — အလိုအလျောက် စီမံတဲ့ operating system တွေမှာ ပိုကြီးတဲ့ page တွေကနေ အကျိုးအမြတ် ရနိုင်ခြေ ပိုများပါတယ်။ Default တန်ဖိုးက 0 (none) ဖြစ်ပါတယ်။ ဒီ parameter ကို server start လုပ်ချိန်မှာပဲ သတ်မှတ်နိုင်ပါတယ်။

### 19.4.2. Disk (ဒစ်)

- **temp_file_limit (integer)** — Sort နဲ့ hash temporary file များ၊ ဒါမှမဟုတ် ထိန်းသိမ်းထားတဲ့ cursor အတွက် storage file ကဲ့သို့ temporary file များအတွက် process တစ်ခု အသုံးပြုနိုင်တဲ့ disk space အများဆုံး ပမာဏကို သတ်မှတ်ပါတယ်။ ဒီ limit ကို ကျော်လွန်ဖို့ ကြိုးစားတဲ့ transaction ကို cancel လုပ်ပါလိမ့်မယ်။ ဒီတန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် — kilobytes အနေနဲ့ ယူပါတယ်။ -1 (default) ဆိုတာက limit မရှိဘူးလို့ ဆိုလိုပါတယ်။ Superuser နဲ့ သင့်လျော်တဲ့ SET privilege ရှိတဲ့ user တွေပဲ ဒီ setting ကို ပြောင်းနိုင်ပါတယ်။
ဒီ setting က — PostgreSQL process တစ်ခုက အသုံးပြုတဲ့ temporary file အားလုံးက — အချိန်တစ်ချိန်မှာ အသုံးပြုတဲ့ စုစုပေါင်း space ကို ကန့်သတ်ပါတယ်။ Query execution အတွင်း နောက်ကွယ်ကနေ အသုံးပြုတဲ့ temporary file များနဲ့ မတူဘဲ — explicit temporary table များအတွက် အသုံးပြုတဲ့ disk space က ဒီ limit နဲ့ မတွက်ပါဘူးဆိုတာ သတိပြုသင့်ပါတယ်။

- **file_copy_method (enum)** — File များ copy လုပ်ရာမှာ သုံးတဲ့ နည်းလမ်းကို သတ်မှတ်ပါတယ်။ ဖြစ်နိုင်တဲ့ တန်ဖိုးတွေက COPY (default) နဲ့ CLONE (operating support ရနိုင်ရင်) ဖြစ်ပါတယ်။
ဒီ parameter က သက်ရောက်တာတွေက —

CREATE DATABASE ... STRATEGY=FILE_COPY

ALTER DATABASE ... SET TABLESPACE ...

CLONE က copy_file_range() (Linux, FreeBSD) ဒါမှမဟုတ် copyfile (macOS) system call များကို သုံးပြီး — kernel ကို disk block များ ခွဲဝေသုံးစွဲခွင့် ဒါမှမဟုတ် file system တချို့မှာ အလုပ်တွေကို အောက်လွှာများဆီ ပို့ချခွင့် ပေးပါတယ်။

- **file_extend_method (enum)** — COPY ကဲ့သို့ bulk operation များအတွင်း data file များကို extend လုပ်ရာမှာ သုံးတဲ့ နည်းလမ်းကို သတ်မှတ်ပါတယ်။ Operating system အပေါ် မူတည်ပြီး — ပထမဆုံး ရနိုင်တဲ့ option ကို default အဖြစ် သုံးပါတယ် —

posix_fallocate (Unix) က disk space ခွဲဝေဖို့ စံ POSIX interface ကို သုံးပါတယ်၊ ဒါပေမယ့် system တချို့မှာ မပါရှိပါဘူး။ ဒါက ရှိပေမယ့် အောက်ခံ file system က မထောက်ပံ့ရင် — ဒီ option က write_zeros ဆီ တိတ်ဆိတ်စွာ ပြန်ကျပါတယ်။ BTRFS ရဲ့ လက်ရှိ version များက ဒီ option ကို သုံးတဲ့အခါ compression ကို disable လုပ်တယ်လို့ သိရပါတယ်။ ဒါက function ရှိတဲ့ system များအတွက် default ဖြစ်ပါတယ်။

write_zeros က file များကို zero byte block များ ရေးထုတ်ခြင်းဖြင့် extend လုပ်ပါတယ်။ ဒါက posix_fallocate function မရှိတဲ့ system များအတွက် default ဖြစ်ပါတယ်။

Data file များကို block ရှစ်ခု ဒါမှမဟုတ် ထိုထက်နည်းတဲ့ ပမာဏဖြင့် extend လုပ်တဲ့အခါ write_zeros နည်းလမ်းကို အမြဲ သုံးပါတယ်။

- **max_notify_queue_pages (integer)** — NOTIFY / LISTEN queue အတွက် ခွဲဝေပေးတဲ့ page အများဆုံး ပမာဏကို သတ်မှတ်ပါတယ်။ Default တန်ဖိုးက 1048576 ဖြစ်ပါတယ်။ 8 KB page များအတွက် — disk space 8 GB အထိ သုံးစွဲခွင့် ပြုပါတယ်။ ဒီ parameter ကို server start လုပ်ချိန်မှာပဲ သတ်မှတ်နိုင်ပါတယ်။

### 19.4.3. Kernel Resource Usage (Kernel resource အသုံးပြုမှု)

- **max_files_per_process (integer)** — Server subprocess တစ်ခုချင်းစီ တစ်ပြိုင်နက် ဖွင့်နိုင်တဲ့ open file အများဆုံး အရေအတွက်ကို သတ်မှတ်ပါတယ်; postmaster မှာ ဖွင့်ပြီးသား file များက ဒီ limit နဲ့ မတွက်ပါဘူး။ Default က file တစ်ထောင် ဖြစ်ပါတယ်။
Kernel က လုံခြုံတဲ့ per-process limit ကို ကျင့်သုံးနေရင် — ဒီ setting အတွက် စိုးရိမ်ဖို့ မလိုပါဘူး။ ဒါပေမယ့် platform တချို့မှာ (အထူးသဖြင့် BSD system အများစုမှာ) — process အများအပြားက file အများအပြား ဖွင့်ဖို့ ကြိုးစားရင် — kernel က process တစ်ခုချင်းစီကို system အမှန်တကယ် ထောက်ပံ့နိုင်တာထက် ပိုများတဲ့ file အရေအတွက် ဖွင့်ခွင့် ပြုပါလိမ့်မယ်။ “Too many open files” failure များ တွေ့နေရရင် — ဒီ setting ကို လျှော့ချကြည့်ပါ။ ဒီ parameter ကို server start လုပ်ချိန်မှာပဲ သတ်မှတ်နိုင်ပါတယ်။

### 19.4.4. Background Writer (နောက်ခံ writer)

*background writer* လို့ခေါ်တဲ့ သီးခြား server process တစ်ခု ရှိပြီး — သူ့တာဝန်က “dirty” (အသစ် ဒါမှမဟုတ် ပြောင်းလဲထားတဲ့) shared buffer များကို ရေးသွင်းမှုများ ထုတ်ပေးခြင်း ဖြစ်ပါတယ်။ Clean shared buffer အရေအတွက် မလုံလောက်ပုံရတဲ့အခါ — background writer က dirty buffer တချို့ကို file system ဆီ ရေးပြီး clean အဖြစ် မှတ်သားပါတယ်။ ဒါက — user query များကို ကိုင်တွယ်တဲ့ server process များ clean buffer များ ရှာမတွေ့နိုင်ဘဲ dirty buffer များကို သူတို့ဘာသာ ရေးရမယ့် ဖြစ်နိုင်ခြေကို လျှော့ချပေးပါတယ်။ ဒါပေမယ့် — background writer က I/O load ကို အလုံးစုံ သိသိသာသာ တိုးစေပါတယ် — အကြောင်းကတော့ — ထပ်ခါတလဲလဲ dirty ဖြစ်နေတဲ့ page တစ်ခုကို checkpoint interval တစ်ခုစီမှာ တစ်ကြိမ်ပဲ ရေးဖို့ ဖြစ်နိုင်ပေမယ့် — background writer က အဲဒီ interval အတွင်း dirty ဖြစ်သလိုကို အကြိမ်ကြိမ် ရေးနိုင်တာကြောင့်ပါ။ ဒီ subsection မှာ ဆွေးနွေးတဲ့ parameter များကို — local လိုအပ်ချက်များအတွက် အပြုအမူကို tune လုပ်ဖို့ သုံးနိုင်ပါတယ်။

- **bgwriter_delay (integer)** — Background writer ရဲ့ activity round များကြား delay ကို သတ်မှတ်ပါတယ်။ round တစ်ခုစီမှာ writer က dirty buffer အချို့အတွက် ရေးသွင်းမှုများ ထုတ်ပါတယ် (နောက်လာတဲ့ parameter များနဲ့ ထိန်းချုပ်နိုင်ပါတယ်)။ ပြီးရင် bgwriter_delay ကြာချိန် sleep လုပ်ပြီး ထပ်လုပ်ပါတယ်။ ဒါပေမယ့် buffer pool ထဲမှာ dirty buffer မရှိရင် — bgwriter_delay ကို ဂရုမစိုက်ဘဲ ပိုရှည်တဲ့ sleep ထဲ ရောက်သွားပါတယ်။ ဒီတန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် — milliseconds အနေနဲ့ ယူပါတယ်။ Default တန်ဖိုးက 200 milliseconds (200ms) ဖြစ်ပါတယ်။ System တချို့မှာ sleep delay များရဲ့ ထိရောက်တဲ့ resolution က 10 milliseconds ဖြစ်တာကို သတိပြုပါ; bgwriter_delay ကို 10 ရဲ့ ဆတိုးမဟုတ်တဲ့ တန်ဖိုးတစ်ခု သတ်မှတ်ခြင်းက — နောက်တစ်ဆင့်မြင့်တဲ့ 10 ရဲ့ ဆတိုးကို သတ်မှတ်သလို ရလဒ်မျိုး ဖြစ်နိုင်ပါတယ်။ ဒီ parameter ကို postgresql.conf ဖိုင်ထဲမှာ ဒါမှမဟုတ် server command line မှာပဲ သတ်မှတ်နိုင်ပါတယ်။
- **bgwriter_lru_maxpages (integer)** — Round တစ်ခုစီမှာ background writer က ဒီအရေအတွက်ထက် ပိုတဲ့ buffer များကို ရေးမှာ မဟုတ်ပါဘူး။ ဒါကို သုည သတ်မှတ်ခြင်းက background writing ကို disable လုပ်ပါတယ်။ (သီးခြား dedicated auxiliary process တစ်ခုက စီမံတဲ့ checkpoint များကတော့ သက်ရောက်မှု မရှိပါဘူးဆိုတာ သတိပြုပါ။) Default တန်ဖိုးက buffer 100 ခု ဖြစ်ပါတယ်။ ဒီ parameter ကို postgresql.conf ဖိုင်ထဲမှာ ဒါမှမဟုတ် server command line မှာပဲ သတ်မှတ်နိုင်ပါတယ်။
- **bgwriter_lru_multiplier (floating point)** — Round တစ်ခုစီမှာ ရေးတဲ့ dirty buffer အရေအတွက်က — မကြာသေးမီ round များအတွင်း server process များ လိုအပ်ခဲ့တဲ့ buffer အသစ် အရေအတွက်အပေါ် အခြေခံပါတယ်။ မကြာသေးမီ လိုအပ်ချက် ပျမ်းမျှကို bgwriter_lru_multiplier နဲ့ မြှောက်ပြီး — နောက် round အတွင်း လိုအပ်လာမယ့် buffer အရေအတွက် ခန့်မှန်းချက်ကို ရပါတယ်။ အဲဒီအရေအတွက်အထိ clean၊ ပြန်သုံးနိုင်တဲ့ buffer များ ရနိုင်တဲ့အထိ dirty buffer များကို ရေးပါတယ်။ (ဒါပေမယ့် round တစ်ခုစီမှာ bgwriter_lru_maxpages buffer ထက် ပိုရေးမှာ မဟုတ်ပါဘူး။) ဒါကြောင့် 1.0 setting ဆိုတာက — လိုအပ်မယ်လို့ ခန့်မှန်းထားတဲ့ buffer အရေအတွက်ကို အတိအကျ ရေးတဲ့ “just in time” policy ကို ကိုယ်စားပြုပါတယ်။ ပိုကြီးတဲ့ တန်ဖိုးများက ဝယ်လိုအား ရုတ်တရက် တက်လာမှုအတွက် အနည်းငယ် ကူရန် ချန်ထားပေးပြီး — ပိုသေးတဲ့ တန်ဖိုးများကတော့ ရေးသားမှုများကို server process များက လုပ်ဖို့ တမင်တကာ ချန်ထားပါတယ်။ Default က 2.0 ဖြစ်ပါတယ်။ ဒီ parameter ကို postgresql.conf ဖိုင်ထဲမှာ ဒါမှမဟုတ် server command line မှာပဲ သတ်မှတ်နိုင်ပါတယ်။
- **bgwriter_flush_after (integer)** — Background writer က ဒီပမာဏထက် ပိုတဲ့ data ကို ရေးပြီးတိုင်း — OS ကို အဲဒီ ရေးသားမှုများကို အောက်ခံ storage ဆီ ထုတ်ပေးဖို့ အတင်းအကျပ် ကြိုးစားပါတယ်။ ဒါက kernel ရဲ့ page cache ထဲက dirty data ပမာဏကို ကန့်သတ်ပေးပြီး — checkpoint အဆုံးမှာ fsync ထုတ်တဲ့အခါ ဒါမှမဟုတ် OS က data ကို နောက်ခံမှာ ပိုကြီးတဲ့ batch များနဲ့ ပြန်ရေးတဲ့အခါ ဖြစ်နိုင်တဲ့ stall များရဲ့ ဖြစ်နိုင်ခြေကို လျှော့ချပေးပါတယ်။ မကြာခဏတော့ ဒါက transaction latency ကို အလွန်အမင်း လျှော့ချပေးပါလိမ့်မယ် — ဒါပေမယ့် — အထူးသဖြင့် shared_buffers ထက် ပိုကြီးပေမယ့် OS ရဲ့ page cache ထက် သေးတဲ့ workload များမှာ — performance ကျဆင်းနိုင်တဲ့ အခြေအနေများလည်း ရှိပါတယ်။ ဒီ setting က platform တချို့မှာ အကျိုးသက်ရောက်မှု မရှိနိုင်ပါဘူး။ ဒီတန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် — blocks အနေနဲ့ ယူပါတယ်၊ ဆိုလိုတာက BLCKSZ bytes ဖြစ်ပြီး — ပုံမှန်အားဖြင့် 8kB ပါ။ တရားဝင် အပိုင်းအခြားက — forced writeback ကို disable လုပ်တဲ့ 0 နဲ့ 2MB ကြား ဖြစ်ပါတယ်။ Default က Linux မှာ 512kB၊ အခြားနေရာများမှာ 0 ဖြစ်ပါတယ်။ (BLCKSZ က 8kB မဟုတ်ရင် — default နဲ့ အများဆုံး တန်ဖိုးများက အဲဒါနဲ့ အချိုးကျ ပြောင်းလဲပါတယ်။) ဒီ parameter ကို postgresql.conf ဖိုင်ထဲမှာ ဒါမှမဟုတ် server command line မှာပဲ သတ်မှတ်နိုင်ပါတယ်။

`bgwriter_lru_maxpages` နဲ့ `bgwriter_lru_multiplier` ရဲ့ ပိုသေးတဲ့ တန်ဖိုးများက — background writer ကြောင့် ဖြစ်တဲ့ အပို I/O load ကို လျှော့ချပေးပေမယ့် — server process များ သူတို့ဘာသာ ရေးသားမှုများ ထုတ်ရမယ့် ဖြစ်နိုင်ခြေကို ပိုများစေပြီး — interactive query များကို နှောင့်နှေးစေပါတယ်။

### 19.4.5. I/O (I/O)

- **backend_flush_after (integer)** — Backend တစ်ခုတည်းက ဒီပမာဏထက် ပိုတဲ့ data ကို ရေးပြီးတိုင်း — OS ကို အဲဒီ ရေးသားမှုများကို အောက်ခံ storage ဆီ ထုတ်ပေးဖို့ အတင်းအကျပ် ကြိုးစားပါတယ်။ ဒါက kernel ရဲ့ page cache ထဲက dirty data ပမာဏကို ကန့်သတ်ပေးပြီး — checkpoint အဆုံးမှာ fsync ထုတ်တဲ့အခါ ဒါမှမဟုတ် OS က data ကို နောက်ခံမှာ ပိုကြီးတဲ့ batch များနဲ့ ပြန်ရေးတဲ့အခါ ဖြစ်နိုင်တဲ့ stall များရဲ့ ဖြစ်နိုင်ခြေကို လျှော့ချပေးပါတယ်။ မကြာခဏတော့ ဒါက transaction latency ကို အလွန်အမင်း လျှော့ချပေးပါလိမ့်မယ် — ဒါပေမယ့် — အထူးသဖြင့် shared_buffers ထက် ပိုကြီးပေမယ့် OS ရဲ့ page cache ထက် သေးတဲ့ workload များမှာ — performance ကျဆင်းနိုင်တဲ့ အခြေအနေများလည်း ရှိပါတယ်။ ဒီ setting က platform တချို့မှာ အကျိုးသက်ရောက်မှု မရှိနိုင်ပါဘူး။ ဒီတန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် — blocks အနေနဲ့ ယူပါတယ်၊ ဆိုလိုတာက BLCKSZ bytes ဖြစ်ပြီး — ပုံမှန်အားဖြင့် 8kB ပါ။ တရားဝင် အပိုင်းအခြားက — forced writeback ကို disable လုပ်တဲ့ 0 နဲ့ 2MB ကြား ဖြစ်ပါတယ်။ Default က 0 ဖြစ်ပြီး — ဆိုလိုတာက forced writeback မရှိပါဘူး။ (BLCKSZ က 8kB မဟုတ်ရင် — အများဆုံး တန်ဖိုးက အဲဒါနဲ့ အချိုးကျ ပြောင်းလဲပါတယ်။)
- **effective_io_concurrency (integer)** — PostgreSQL က တစ်ပြိုင်နက် execute လုပ်နိုင်မယ်လို့ မျှော်လင့်တဲ့ concurrent storage I/O operation အရေအတွက်ကို သတ်မှတ်ပါတယ်။ ဒီတန်ဖိုးကို မြှင့်ခြင်းက — PostgreSQL session တစ်ခုချင်းစီ parallel initiate လုပ်ဖို့ ကြိုးစားတဲ့ I/O operation အရေအတွက်ကို တိုးစေပါတယ်။ ခွင့်ပြုတဲ့ အပိုင်းအခြားက 1 ကနေ 1000 အထိ ဖြစ်ပြီး — 0 က asynchronous I/O request များ ထုတ်ခြင်းကို disable လုပ်ပါတယ်။ Default က 16 ဖြစ်ပါတယ်။
ပိုမြင့်တဲ့ တန်ဖိုးများက — query များ သိသာတဲ့ I/O stall များ ကြုံရတဲ့ higher latency storage များနဲ့ high IOPs ရှိတဲ့ device များမှာ အများဆုံး သက်ရောက်မှု ရှိပါလိမ့်မယ်။ မလိုအပ်ဘဲ မြင့်လွန်းတဲ့ တန်ဖိုးများက system ပေါ်က query အားလုံးအတွက် I/O latency ကို တိုးစေနိုင်ပါတယ်။
Prefetch advice support ရှိတဲ့ system များမှာ — effective_io_concurrency က prefetch distance ကိုလည်း ထိန်းချုပ်ပါတယ်။
ဒီတန်ဖိုးကို — tablespace တစ်ခုထဲက table များအတွက် အမည်တူ tablespace parameter သတ်မှတ်ခြင်းဖြင့် — override လုပ်နိုင်ပါတယ် (ALTER TABLESPACE ကို ကြည့်ပါ)။
- **maintenance_io_concurrency (integer)** — effective_io_concurrency နဲ့ ဆင်တူပေမယ့် — client session အများအပြား ကိုယ်စား လုပ်ဆောင်တဲ့ maintenance work အတွက် သုံးပါတယ်။
Default က 16 ဖြစ်ပါတယ်။ ဒီတန်ဖိုးကို — tablespace တစ်ခုထဲက table များအတွက် အမည်တူ tablespace parameter သတ်မှတ်ခြင်းဖြင့် — override လုပ်နိုင်ပါတယ် (ALTER TABLESPACE ကို ကြည့်ပါ)။
- **io_max_combine_limit (integer)** — I/O ကို ပေါင်းစပ်တဲ့ operation များမှာ အကြီးဆုံး I/O size ကို ထိန်းချုပ်ပြီး — user သတ်မှတ်နိုင်တဲ့ io_combine_limit parameter ကို တိတ်ဆိတ်စွာ ကန့်သတ်ပါတယ်။ ဒီ parameter ကို server start လုပ်ချိန်မှာပဲ သတ်မှတ်နိုင်ပါတယ်။ ဒီတန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် — blocks အနေနဲ့ ယူပါတယ်၊ ဆိုလိုတာက BLCKSZ bytes ဖြစ်ပြီး — ပုံမှန်အားဖြင့် 8kB ပါ။ ဖြစ်နိုင်တဲ့ အများဆုံး size က operating system နဲ့ block size အပေါ် မူတည်ပေမယ့် — ပုံမှန်အားဖြင့် Unix မှာ 1MB၊ Windows မှာ 128kB ဖြစ်ပါတယ်။ Default က 128kB ဖြစ်ပါတယ်။
- **io_combine_limit (integer)** — I/O ကို ပေါင်းစပ်တဲ့ operation များမှာ အကြီးဆုံး I/O size ကို ထိန်းချုပ်ပါတယ်။ io_max_combine_limit parameter ထက် မြင့်အောင် သတ်မှတ်ရင် — ပိုနည်းတဲ့ တန်ဖိုးကို တိတ်ဆိတ်စွာ အစားထိုး သုံးပါလိမ့်မယ်၊ ဒါကြောင့် I/O size ကို တိုးဖို့ နှစ်ခုလုံးကို မြှင့်ရန် လိုနိုင်ပါတယ်။ ဒီတန်ဖိုးကို unit မပါဘဲ သတ်မှတ်ရင် — blocks အနေနဲ့ ယူပါတယ်၊ ဆိုလိုတာက BLCKSZ bytes ဖြစ်ပြီး — ပုံမှန်အားဖြင့် 8kB ပါ။ ဖြစ်နိုင်တဲ့ အများဆုံး size က operating system နဲ့ block size အပေါ် မူတည်ပေမယ့် — ပုံမှန်အားဖြင့် Unix မှာ 1MB၊ Windows မှာ 128kB ဖြစ်ပါတယ်။ Default က 128kB ဖြစ်ပါတယ်။
- **io_max_concurrency (integer)** — Process တစ်ခု တစ်ပြိုင်နက် execute လုပ်နိုင်တဲ့ I/O operation အများဆုံး အရေအတွက်ကို ထိန်းချုပ်ပါတယ်။
-1 ဆိုတဲ့ default setting က — shared_buffers နဲ့ process အများဆုံး အရေအတွက် (max_connections၊ autovacuum_worker_slots၊ max_worker_processes နဲ့ max_wal_senders) အပေါ် အခြေခံတဲ့ နံပါတ်တစ်ခုကို ရွေးချယ်ပေမယ့် — 64 ထက် မပိုပါဘူး။
ဒီ parameter ကို server start လုပ်ချိန်မှာပဲ သတ်မှတ်နိုင်ပါတယ်။
- **io_method (enum)** — Asynchronous I/O execute လုပ်ဖို့ နည်းလမ်းကို ရွေးချယ်ပါတယ်။ ဖြစ်နိုင်တဲ့ တန်ဖိုးများက —

- worker (worker process များကို သုံးပြီး asynchronous I/O ကို execute လုပ်ခြင်း)
- io_uring (io_uring ကို သုံးပြီး asynchronous I/O ကို execute လုပ်ခြင်း၊ --with-liburing / -Dliburing နဲ့ build လုပ်ထားရန် လိုအပ်ပါတယ်)
- sync (asynchronous-eligible I/O ကို synchronously execute လုပ်ခြင်း)

Default က worker ဖြစ်ပါတယ်။
ဒီ parameter ကို server start လုပ်ချိန်မှာပဲ သတ်မှတ်နိုင်ပါတယ်။
- **io_workers (integer)** — အသုံးပြုမယ့် I/O worker process အရေအတွက်ကို ရွေးချယ်ပါတယ်။ Default က 3 ဖြစ်ပါတယ်။ ဒီ parameter ကို postgresql.conf ဖိုင်ထဲမှာ ဒါမှမဟုတ် server command line မှာပဲ သတ်မှတ်နိုင်ပါတယ်။
io_method ကို worker သတ်မှတ်ထားမှသာ အကျိုးသက်ရောက်မှု ရှိပါတယ်။

### 19.4.6. Worker Processes (Worker process များ)

- **max_worker_processes (integer)** — Cluster က ထောက်ပံ့နိုင်တဲ့ background process အများဆုံး အရေအတွက်ကို သတ်မှတ်ပါတယ်။ ဒီ parameter ကို server start လုပ်ချိန်မှာပဲ သတ်မှတ်နိုင်ပါတယ်။ Default က 8 ဖြစ်ပါတယ်။
Standby server တစ်ခု run နေရင် — ဒီ parameter ကို primary server ပေါ်က တန်ဖိုးထက် တူညီတာ ဒါမှမဟုတ် ပိုမြင့်တာ သတ်မှတ်ရပါမယ်။ မဟုတ်ရင် — standby server မှာ query များကို ခွင့်ပြုမှာ မဟုတ်ပါဘူး။
ဒီတန်ဖိုးကို ပြောင်းတဲ့အခါ — max_parallel_workers၊ max_parallel_maintenance_workers နဲ့ max_parallel_workers_per_gather တို့ကိုလည်း ချိန်ညှိဖို့ စဉ်းစားပါ။
- **max_parallel_workers_per_gather (integer)** — Gather ဒါမှမဟုတ် Gather Merge node တစ်ခုတည်းက စတင်နိုင်တဲ့ worker အများဆုံး အရေအတွက်ကို သတ်မှတ်ပါတယ်။ Parallel worker များကို max_worker_processes က ချမှတ်ထားတဲ့ process pool ထဲကနေ ယူပြီး — max_parallel_workers က ကန့်သတ်ပါတယ်။ တောင်းဆိုထားတဲ့ worker အရေအတွက်က run time မှာ တကယ် မရနိုင်တာ ဖြစ်နိုင်တာကို သတိပြုပါ။ ဒီလို ဖြစ်ရင် — plan က မျှော်လင့်တာထက် နည်းတဲ့ worker များနဲ့ run မှာ ဖြစ်ပြီး — ဒါက ထိရောက်မှု မရှိနိုင်ပါဘူး။ Default တန်ဖိုးက 2 ဖြစ်ပါတယ်။ ဒီတန်ဖိုးကို 0 သတ်မှတ်ခြင်းက parallel query execution ကို disable လုပ်ပါတယ်။
Parallel query များက non-parallel query များထက် အရင်းအမြစ်များကို သိသိသာသာ ပိုမို သုံးစွဲနိုင်တာကို သတိပြုပါ — အကြောင်းကတော့ worker process တစ်ခုချင်းစီဟာ လုံးလုံး သီးခြား process တစ်ခု ဖြစ်ပြီး — system ပေါ်မှာ အပို user session တစ်ခုလိုပဲ သက်ရောက်မှု ရှိတာကြောင့်ပါ။ ဒါကို — ဒီ setting အတွက် တန်ဖိုး ရွေးတဲ့အခါမှာလည်းကောင်း — work_mem ကဲ့သို့ resource အသုံးပြုမှုကို ထိန်းချုပ်တဲ့ အခြား setting များကို configure လုပ်တဲ့အခါမှာလည်းကောင်း — ထည့်သွင်း စဉ်းစားသင့်ပါတယ်။ work_mem ကဲ့သို့ resource limit များက worker တစ်ခုချင်းစီအပေါ် သီးခြား သက်ရောက်တာကြောင့် — စုစုပေါင်း အသုံးပြုမှုက process တစ်ခုတည်းအတွက် ပုံမှန် ဖြစ်နိုင်တာထက် process အားလုံးအတွက် အများကြီး ပိုမြင့်နိုင်ပါတယ်။ ဥပမာ — worker 4 ခု သုံးတဲ့ parallel query တစ်ခုက CPU time၊ memory၊ I/O bandwidth စတာတွေကို worker လုံးဝ မသုံးတဲ့ query တစ်ခုထက် အဆ 5 အထိ ပိုသုံးနိုင်ပါတယ်။
Parallel query အကြောင်း အသေးစိတ်အတွက် — [အပိုင်း 15](https://www.postgresql.org/docs/current/parallel-query.html) ကို ကြည့်ပါ။
- **max_parallel_maintenance_workers (integer)** — utility command တစ်ခုတည်းက စတင်နိုင်တဲ့ parallel worker အများဆုံး အရေအတွက်ကို သတ်မှတ်ပါတယ်။ လက်ရှိအချိန်မှာ — parallel worker များ အသုံးပြုခြင်းကို ထောက်ပံ့တဲ့ parallel utility command များက — B-tree၊ GIN ဒါမှမဟုတ် BRIN index တစ်ခု တည်ဆောက်တဲ့အခါ CREATE INDEX နဲ့ — FULL option မပါတဲ့ VACUUM ဖြစ်ပါတယ်။ Parallel worker များကို max_worker_processes က ချမှတ်ထားတဲ့ process pool ထဲကနေ ယူပြီး — max_parallel_workers က ကန့်သတ်ပါတယ်။ တောင်းဆိုထားတဲ့ worker အရေအတွက်က run time မှာ တကယ် မရနိုင်တာ ဖြစ်နိုင်တာကို သတိပြုပါ။ ဒီလို ဖြစ်ရင် — utility operation က မျှော်လင့်တာထက် နည်းတဲ့ worker များနဲ့ run မှာ ဖြစ်ပါတယ်။ Default တန်ဖိုးက 2 ဖြစ်ပါတယ်။ ဒီတန်ဖိုးကို 0 သတ်မှတ်ခြင်းက utility command များက parallel worker များ အသုံးပြုခြင်းကို disable လုပ်ပါတယ်။
Parallel utility command များက — ညီမျှတဲ့ non-parallel operation များထက် memory သိသိသာသာ ပိုသုံးစွဲသင့်တာ မဟုတ်ပါဘူး။ ဒီ strategy က parallel query ရဲ့ strategy နဲ့ မတူပါဘူး — parallel query မှာတော့ resource limit များက worker process တစ်ခုချင်းစီအပေါ် ယေဘုယျအားဖြင့် သက်ရောက်ပါတယ်။ Parallel utility command များက maintenance_work_mem resource limit ကို — parallel worker process အရေအတွက် ဘယ်လောက်ပဲ ရှိပါစေ — utility command တစ်ခုလုံးအပေါ် သက်ရောက်တဲ့ limit အဖြစ် သတ်မှတ်ပါတယ်။ ဒါပေမယ့် — parallel utility command များက CPU resource နဲ့ I/O bandwidth ကို သိသိသာသာ ပိုသုံးစွဲနိုင်ပါသေးတယ်။
- **max_parallel_workers (integer)** — Cluster က parallel operation များအတွက် ထောက်ပံ့နိုင်တဲ့ worker အများဆုံး အရေအတွက်ကို သတ်မှတ်ပါတယ်။ Default တန်ဖိုးက 8 ဖြစ်ပါတယ်။ ဒီတန်ဖိုးကို တိုး ဒါမှမဟုတ် လျှော့တဲ့အခါ — max_parallel_maintenance_workers နဲ့ max_parallel_workers_per_gather တို့ကိုလည်း ချိန်ညှိဖို့ စဉ်းစားပါ။ ထို့အပြင် — ဒီတန်ဖိုးအတွက် max_worker_processes ထက် မြင့်တဲ့ setting တစ်ခုက အကျိုးသက်ရောက်မှု ရှိမှာ မဟုတ်ပါဘူး — အကြောင်းကတော့ parallel worker များကို အဲဒီ setting က ချမှတ်ထားတဲ့ worker process pool ထဲကနေ ယူတာကြောင့်ပါ။
- **parallel_leader_participation (boolean)** — leader process ကို — worker process များကို စောင့်မနေဘဲ — Gather နဲ့ Gather Merge node များ အောက်မှာ query plan ကို execute လုပ်ခွင့် ပြုပါတယ်။ Default က on ဖြစ်ပါတယ်။ ဒီတန်ဖိုးကို off သတ်မှတ်ခြင်းက — leader က tuple များကို လုံလောက်အောင် လျင်မြန်စွာ မဖတ်တာကြောင့် worker များ ပိတ်ဆို့ (blocked) ဖြစ်နိုင်ခြေကို လျှော့ချပေးပေမယ့် — ပထမဆုံး tuple များ မထုတ်နိုင်မီ worker process များ စတင်လာတဲ့အထိ leader process က စောင့်ရန် လိုအပ်ပါတယ်။ Leader က performance ကို ကူညီနိုင်တဲ့ ဒါမှမဟုတ် နှောင့်နှေးစေနိုင်တဲ့ အတိုင်းအတာက — plan အမျိုးအစား၊ worker အရေအတွက်နဲ့ query ကြာချိန် အပေါ် မူတည်ပါတယ်။
