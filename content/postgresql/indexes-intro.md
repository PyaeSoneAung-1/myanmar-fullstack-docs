## 11.1. Introduction (index မိတ်ဆက်)

ဒီလိုမျိုး ဆင်တူတဲ့ table တစ်ခု ရှိတယ်ဆိုပါစို့ —

```sql
CREATE TABLE test1 (
    id integer,
    content varchar
);
```

ပြီးတော့ — application က ဒီပုံစံမျိုး query တွေကို အများအပြား လုပ်ဆောင်နေတယ်ဆိုပါစို့ —

```sql
SELECT content FROM test1 WHERE id = constant;
```

ကြိုတင်ပြင်ဆင်မှု ဘာမှ မရှိဘူးဆိုရင် — ကိုက်ညီတဲ့ entry တွေ အားလုံးကို ရှာဖွေဖို့အတွက် system က `test1` table တစ်ခုလုံးကို row တစ်ကြောင်းချင်းစီ scan (စဉ်ဆက်မပြတ် စစ်ဆေးဖတ်ရှုခြင်း) လုပ်ရပါလိမ့်မယ်။ `test1` ထဲမှာ row တွေ အများကြီး ရှိပြီး — အဲဒီလို query တစ်ခုက ပြန်ပေးမယ့် row တွေက အနည်းငယ်သာ (သုည ဒါမှမဟုတ် တစ်ခုလောက်) ရှိမယ်ဆိုရင် — ဒီနည်းလမ်းက ထိရောက်မှု မရှိဘူးဆိုတာ ထင်ရှားပါတယ်။ ဒါပေမယ့် — system ကို `id` column အပေါ်မှာ index (အညွှန်း) တစ်ခု ထိန်းသိမ်းထားဖို့ ညွှန်ကြားထားမယ်ဆိုရင် — ကိုက်ညီတဲ့ row တွေကို ရှာဖွေတဲ့အခါ ပိုပြီး ထိရောက်တဲ့ နည်းလမ်းကို သုံးနိုင်ပါတယ်။ ဥပမာ — search tree (ရှာဖွေရေး tree) ထဲကို အဆင့် အနည်းငယ်လောက်သာ ဆင်းသွားရတာမျိုး ဖြစ်နိုင်ပါတယ်။

ဒီနည်းလမ်းမျိုးကိုပဲ — non-fiction (အချက်အလက် အခြေပြု) စာအုပ် အများစုမှာလည်း တွေ့ရပါတယ် — စာဖတ်သူတွေ မကြာခဏ ရှာဖတ်လေ့ရှိတဲ့ ဝေါဟာရ (term) တွေနဲ့ အယူအဆ (concept) တွေကို စာအုပ်ရဲ့ အဆုံးမှာ အက္ခရာစဉ်အတိုင်း စီထားတဲ့ index (အညွှန်း) တစ်ခုအနေနဲ့ စုစည်းထားလေ့ ရှိပါတယ်။ စိတ်ဝင်စားတဲ့ စာဖတ်သူကတော့ — စာအုပ်တစ်အုပ်လုံးကို ဖတ်ရှာစရာ မလိုဘဲ — index ကို မြန်မြန်ဆန်ဆန် ကြည့်ရှုပြီး သက်ဆိုင်ရာ စာမျက်နှာ(များ)ကို လှန်ဖတ်နိုင်ပါတယ်။ စာရေးသူရဲ့ တာဝန်က စာဖတ်သူတွေ ရှာဖတ်ဖွယ် ရှိတဲ့ အကြောင်းအရာတွေကို ကြိုတင် မှန်းဆရသလိုပဲ — database programmer (ဒေတာဘေ့စ် ပရိုဂရမ်မာ) ရဲ့ တာဝန်ကလည်း ဘယ် index တွေက အသုံးဝင်မလဲဆိုတာကို ကြိုမြင်ရခြင်းပဲ ဖြစ်ပါတယ်။

`id` column အပေါ်မှာ index တစ်ခု ဖန်တီးဖို့အတွက် — အထက်မှာ ဆွေးနွေးခဲ့တဲ့အတိုင်း — အောက်ပါ command ကို သုံးနိုင်ပါတယ် —

```sql
CREATE INDEX test1_id_index ON test1 (id);
```

`test1_id_index` ဆိုတဲ့ နာမည်ကို ကြိုက်သလို ရွေးချယ်နိုင်ပါတယ် — ဒါပေမယ့် ဒီ index က ဘာအတွက်လဲဆိုတာကို နောက်ပိုင်းမှာ ပြန်မှတ်မိနိုင်မယ့် နာမည်မျိုး ရွေးထားသင့်ပါတယ်။

Index တစ်ခုကို ဖယ်ရှားဖို့ဆိုရင် `DROP INDEX` command ကို သုံးပါတယ်။ Index တွေကို အချိန်မရွေး table တွေထဲကို ထည့်နိုင်သလို — table တွေကနေ ဖယ်ရှားလို့လည်း ရပါတယ်။

Index တစ်ခု ဖန်တီးပြီးတာနဲ့ — နောက်ထပ် ဝင်ရောက် လုပ်ဆောင်စရာ မလိုတော့ပါဘူး — table ကို ပြုပြင်မွမ်းမံလိုက်တိုင်း system က index ကို သူ့အလိုအလျောက် update လုပ်ပေးပြီး — sequential table scan (table တစ်ခုလုံးကို row အလိုက် စဉ်ဆက်တိုက် ဖတ်ခြင်း) ထက် index သုံးတာက ပိုပြီး ထိရောက်မယ်လို့ ယူဆရတဲ့ query တွေမှာ index ကို သုံးပါတယ်။ ဒါပေမယ့် — query planner (query တစ်ခုအတွက် အကောင်းဆုံး လုပ်ဆောင်မှု အစီအစဉ်ကို ရွေးချယ်ပေးတဲ့ အစိတ်အပိုင်း) က သင့်လျော်တဲ့ ဆုံးဖြတ်ချက် ချနိုင်ဖို့ — statistics (စာရင်းအင်း အချက်အလက်များ) တွေကို update လုပ်ပေးဖို့အတွက် `ANALYZE` command ကို ပုံမှန် run ရဖို့ လိုအပ်နိုင်ပါတယ်။ Index တစ်ခုကို တကယ် အသုံးပြုသလား — ဘယ်အချိန်တွေမှာ ဘာကြောင့် planner က index ကို အသုံးမပြုဖို့ ရွေးချယ်နိုင်သလဲဆိုတာ ဘယ်လို သိနိုင်မလဲဆိုတဲ့ အချက်အလက်တွေအတွက် [အခန်း 14](https://www.postgresql.org/docs/current/performance-tips.html) ကို ကြည့်ပါ။

Index တွေက search condition (ရှာဖွေရေး အခြေအနေ) တွေ ပါဝင်တဲ့ `UPDATE` နဲ့ `DELETE` command တွေအတွက်လည်း အကျိုးရှိစေပါတယ်။ ဒါ့အပြင် — index တွေကို join လုပ်ပြီး ရှာဖွေတဲ့ query တွေမှာလည်း သုံးနိုင်ပါတယ်။ ဒါကြောင့် — join condition (join လုပ်ရာမှာ အသုံးပြုတဲ့ အခြေအနေ) ရဲ့ အစိတ်အပိုင်း တစ်ခု ဖြစ်တဲ့ column ပေါ်မှာ သတ်မှတ်ထားတဲ့ index ကလည်း — join တွေ ပါတဲ့ query တွေကို သိသိသာသာ မြန်ဆန်စေနိုင်ပါတယ်။

ယေဘုယျအားဖြင့် — PostgreSQL index တွေက အောက်ပါပုံစံ ရှိတဲ့ `WHERE` ဒါမှမဟုတ် `JOIN` clause တစ်ခု ဒါမှမဟုတ် တစ်ခုထက်ပိုပြီး ပါဝင်တဲ့ query တွေကို optimize (ပိုမို ထိရောက်အောင် ပြုလုပ်ခြင်း) လုပ်ဖို့ သုံးနိုင်ပါတယ် —

```sql
indexed-column indexable-operator comparison-value
```

ဒီမှာ — `indexed-column` ဆိုတာ index ကို သတ်မှတ်ထားတဲ့ column ဒါမှမဟုတ် expression ပဲ ဖြစ်ပါတယ်။ `indexable-operator` ကတော့ — index လုပ်ထားတဲ့ column အတွက် index ရဲ့ *operator class* (operator အုပ်စု) ထဲမှာ ပါဝင်တဲ့ operator တစ်ခု ဖြစ်ပါတယ်။ (ဒီအကြောင်းကို အောက်မှာ ထပ်ပြီး အသေးစိတ် ဖော်ပြပါမယ်။) `comparison-value` ကတော့ — volatile (ခေါ်ယူသည့် အခါတိုင်း တန်ဖိုး ပြောင်းလဲနိုင်သော) မဟုတ်တဲ့ — ပြီးတော့ index ရဲ့ table ကို ရည်ညွှန်းခြင်း မရှိတဲ့ — expression တစ်ခုခု ဖြစ်နိုင်ပါတယ်။

တချို့ အခြေအနေတွေမှာ — query planner က ဒီပုံစံ ရှိတဲ့ indexable clause (index သုံးလို့ရတဲ့ clause) တစ်ခုကို တခြား SQL construct တစ်ခုကနေ ထုတ်ယူနိုင်ပါတယ်။ ရိုးရှင်းတဲ့ ဥပမာတစ်ခုကတော့ — မူလ clause က အောက်ပါအတိုင်း ဆိုရင်

```sql
comparison-value operator indexed-column
```

မူလ `operator` မှာ — index ရဲ့ operator class ထဲမှာ ပါဝင်တဲ့ commutator operator (operand နေရာချင်း လဲလှယ်လိုက်ချိန်မှာ ညီမျှစွာ အသုံးပြုနိုင်တဲ့ operator) တစ်ခု ရှိမယ်ဆိုရင် — အဲဒီ clause ကို လှန်လိုက်ပြီး indexable ပုံစံအနေနဲ့ သုံးလို့ရပါတယ်။

Table အကြီးကြီးတစ်ခုပေါ်မှာ index ဖန်တီးတာက အချိန် အတော်ကြာနိုင်ပါတယ်။ ပုံမှန်အားဖြင့် — PostgreSQL က index ဖန်တီးနေချိန်မှာ table ပေါ်မှာ read (`SELECT` statement) တွေ အပြိုင် ဖြစ်ပေါ်ခွင့် ပြုပါတယ် — ဒါပေမယ့် write (`INSERT`၊ `UPDATE`၊ `DELETE`) တွေကတော့ index build (index တည်ဆောက်မှု) ပြီးဆုံးတဲ့အထိ ပိတ်ပင်ထားပါတယ်။ Production environment (လက်တွေ့ လည်ပတ်နေတဲ့ ပတ်ဝန်းကျင်) တွေမှာ ဒါက မကြာခဏဆိုသလို လက်ခံလို့ မရနိုင်တဲ့ အခြေအနေပါ။ Index ဖန်တီးမှုနဲ့ အပြိုင် write တွေ ဖြစ်ပေါ်ခွင့် ပြုတာကတော့ ဖြစ်နိုင်ပါတယ် — ဒါပေမယ့် သတိထားရမယ့် caveat (သတိပြုစရာ အချက်) တွေ အများအပြား ရှိပါတယ် — အသေးစိတ်ကို [Index တွေကို တစ်ပြိုင်နက် တည်ဆောက်ခြင်း (Building Indexes Concurrently)](https://www.postgresql.org/docs/current/sql-createindex.html#SQL-CREATEINDEX-CONCURRENTLY) မှာ ကြည့်ပါ။

Index တစ်ခု ဖန်တီးပြီးတာနဲ့ — system က index ကို table နဲ့ တစ်ပြေးညီဖြစ်နေအောင် ထိန်းသိမ်းထားရပါတယ်။ ဒါက data manipulation (ဒေတာ ပြုပြင်မွမ်းမံခြင်း) operation တွေအပေါ်မှာ overhead (အပိုဝန်ထုပ်) တစ်ခု ထပ်တိုးစေပါတယ်။ ဒါ့အပြင် — index တွေက [heap-only tuples](https://www.postgresql.org/docs/current/storage-hot.html) (heap စာမျက်နှာ အတွင်းမှာသာ သီးသန့် ဖြစ်ပေါ်နိုင်သော tuple အမျိုးအစား) တွေ ဖန်တီးခြင်းကိုလည်း တားဆီးနိုင်ပါတယ်။ ဒါကြောင့် — query တွေမှာ ရံဖန်ရံခါပဲ သုံးတဲ့ ဒါမှမဟုတ် ဘယ်တော့မှ မသုံးတဲ့ index တွေကို ဖယ်ရှားပစ်သင့်ပါတယ်။
