## 28.1. Reliability (ယုံကြည်စိတ်ချရမှု)

ယုံကြည်စိတ်ချရမှု (reliability) ဆိုတာ အလေးအနက် ထားရတဲ့ database system တိုင်းအတွက် အရေးပါတဲ့ ဂုဏ်သတ္တိ တစ်ခု ဖြစ်ပြီး — PostgreSQL က ယုံကြည်စိတ်ချရတဲ့ လည်ပတ်မှု (reliable operation) ကို အာမခံဖို့ အတတ်နိုင်ဆုံး လုပ်ဆောင်ပေးပါတယ်။ ယုံကြည်စိတ်ချရတဲ့ လည်ပတ်မှုရဲ့ အချက် တစ်ချက်ကတော့ — commit လုပ်ပြီးသား transaction (အတည်ပြုပြီးသော အလုပ်အစု) တစ်ခုက မှတ်တမ်းတင်ထားတဲ့ data အားလုံးဟာ — ပါဝါ ပြတ်တောက်မှု (power loss), operating system ကျရှုံးမှု နဲ့ hardware ကျရှုံးမှုတွေကနေ လုံခြုံတဲ့ nonvolatile (ပါဝါ မလိုဘဲ ထိန်းသိမ်းထားနိုင်တဲ့) နေရာတစ်ခုမှာ သိမ်းဆည်းထားသင့်တယ် ဆိုတာပါ (nonvolatile နေရာကိုယ်တိုင် ကျရှုံးတာကတော့ ခြွင်းချက် ဖြစ်ပါတယ်)။ ဒီ data ကို ကွန်ပျူတာရဲ့ အမြဲတမ်း သိုလှောင်ရာ (permanent storage — disk drive ဒါမှမဟုတ် အလားတူ အရာ) ဆီ အောင်မြင်စွာ ရေးသားနိုင်တာက ဒီလိုအပ်ချက်ကို ပုံမှန်အားဖြင့် ဖြည့်ဆည်းပေးပါတယ်။ တကယ်တော့ — ကွန်ပျူတာ တစ်လုံး အကြီးအကျယ် ပျက်စီးသွားရင်တောင် — disk drive တွေ ကျန်ရစ်ခဲ့မယ်ဆိုရင် — အလားတူ hardware ရှိတဲ့ အခြား ကွန်ပျူတာ တစ်လုံးဆီ ရွှေ့ပြောင်းနိုင်ပြီး — commit လုပ်ပြီးသား transaction အားလုံး ပကတိ အတိုင်း ကျန်ရှိနေပါလိမ့်မယ်။

Data တွေကို disk platter (disk ပြား) တွေဆီ အခါအားလျော်စွာ အတင်းအကျပ် ရေးသွင်း (force) လုပ်တာက ရိုးရှင်းတဲ့ လုပ်ဆောင်ချက် တစ်ခု လို့ ထင်ရပေမယ့် — တကယ်တော့ မဟုတ်ပါဘူး။ Disk drive တွေက main memory နဲ့ CPU တွေထက် အလွန်အမင်း နှေးကွေးတာကြောင့် — ကွန်ပျူတာရဲ့ main memory နဲ့ disk platter တွေကြားမှာ caching (ကက်ရှ် သိမ်းဆည်းခြင်း) အလွှာ အများအပြား ရှိပါတယ်။ ပထမဆုံးအနေနဲ့ — operating system ရဲ့ buffer cache (ကြားခံ ကက်ရှ်) ရှိပြီး — ဒါက မကြာခဏ တောင်းဆိုခံရတဲ့ disk block တွေကို ကက်ရှ် လုပ်ပေးကာ — disk ရေးသားမှုတွေကို စုစည်းပေးပါတယ်။ ကံကောင်းထောက်မစွာပဲ — operating system အားလုံးက application တွေကို buffer cache ကနေ disk ဆီ ရေးသားမှုတွေကို အတင်းအကျပ် လုပ်ခွင့်ပေးတဲ့ နည်းလမ်း ပေးထားပြီး — PostgreSQL က အဲဒီ လုပ်ဆောင်ချက်တွေကို အသုံးပြုပါတယ်။ (ဒါကို ဘယ်လို လုပ်ဆောင်မလဲ ချိန်ညှိဖို့ [wal_sync_method](https://www.postgresql.org/docs/current/runtime-config-wal.html#GUC-WAL-SYNC-METHOD) parameter ကို ကြည့်ပါ။)

ပြီးရင် — disk drive controller (disk drive ထိန်းချုပ်ကိရိယာ) ထဲမှာ cache တစ်ခု ရှိနိုင်ပြီး — ဒါက RAID controller card တွေပေါ်မှာ အထူးသဖြင့် အဖြစ်များပါတယ်။ ဒီ cache တချို့က *write-through* (ချက်ချင်း ရေးသွင်းသည့် ပုံစံ) ဖြစ်ပြီး — ရေးသားမှုတွေ ရောက်ရှိတာနဲ့ ချက်ချင်း drive ဆီ ပို့ပေးပါတယ်။ အခြားတချို့ကတော့ *write-back* (နောက်မှ ရေးသွင်းသည့် ပုံစံ) ဖြစ်ပြီး — data တွေကို နောက်ပိုင်း အချိန်တစ်ခုမှ drive ဆီ ပို့ပါတယ်။ ဒီလို cache တွေက ယုံကြည်စိတ်ချရမှုအတွက် အန္တရာယ် ဖြစ်နိုင်ပါတယ် — အကြောင်းကတော့ disk controller cache ထဲက memory က volatile (မတည်မြဲသော) ဖြစ်ပြီး — ပါဝါ ပြတ်တောက်မှုမှာ သူ့အကြောင်းအရာတွေ ဆုံးရှုံးသွားမှာမို့ပါ။ ပိုကောင်းတဲ့ controller card တွေမှာ *battery-backup units* (BBU — ဘက်ထရီ အရန် ယူနစ်) ပါဝင်ပြီး — ဆိုလိုတာက — system ပါဝါ ပြတ်တောက်သွားရင် — cache ဆီ ပါဝါ ဆက်ထိန်းပေးတဲ့ ဘက်ထရီ တစ်လုံး card မှာ ရှိတာပါ။ ပါဝါ ပြန်လည် ရရှိပြီးတဲ့နောက် — data တွေကို disk drive တွေဆီ ရေးသွားပါလိမ့်မယ်။

နောက်ဆုံးအနေနဲ့ — disk drive အများစုမှာ cache တွေ ရှိပါတယ်။ တချို့က write-through ဖြစ်ပြီး — တချို့က write-back ဖြစ်ကာ — disk controller cache တွေမှာ ရှိသလို data ဆုံးရှုံးမှု စိုးရိမ်ရတဲ့ ကိစ္စမျိုးပဲ write-back drive cache တွေမှာလည်း ရှိပါတယ်။ Consumer-grade (သုံးစွဲသူ အဆင့်) IDE နဲ့ SATA drive တွေမှာ ပါဝါ ပြတ်တောက်မှုကို ခံနိုင်ရည် မရှိတဲ့ write-back cache တွေ ပါဝင်နိုင်ခြေ အထူးများပါတယ်။ Solid-state drive (SSD) အများအပြားမှာလည်း volatile write-back cache တွေ ရှိပါတယ်။

ဒီ cache တွေကို ပုံမှန်အားဖြင့် disable (ပိတ်) လုပ်နိုင်ပါတယ်; ဒါပေမယ့် — ဒါကို လုပ်ဆောင်တဲ့ နည်းလမ်းက operating system နဲ့ drive အမျိုးအစားပေါ် မူတည်ပြီး ကွဲပြားပါတယ်:

- Linux မှာ — IDE နဲ့ SATA drive တွေကို `hdparm -I` နဲ့ စစ်ဆေး (query) နိုင်ပါတယ်; Write cache ရဲ့ ဘေးမှာ `*` ရှိရင် write caching enable ဖြစ်နေပါတယ်။ `hdparm -W 0` ကို သုံးပြီး write caching ကို ပိတ်နိုင်ပါတယ်။ SCSI drive တွေကို `sdparm` နဲ့ စစ်ဆေးနိုင်ပါတယ်။ Write cache enable ဖြစ်မဖြစ် စစ်ဖို့ `sdparm --get=WCE` ကို သုံးပြီး — disable လုပ်ဖို့ `sdparm --clear=WCE` ကို သုံးပါ။
- FreeBSD မှာ — IDE drive တွေကို `camcontrol identify` နဲ့ စစ်ဆေးနိုင်ပြီး — `/boot/loader.conf` ထဲမှာ `hw.ata.wc=0` သတ်မှတ်ခြင်းဖြင့် write caching ကို ပိတ်နိုင်ပါတယ်; SCSI drive တွေကို `camcontrol identify` နဲ့ စစ်ဆေးနိုင်ပြီး — `sdparm` ရနိုင်တဲ့အခါ — write cache ကို စစ်ဆေးရော ပြောင်းလဲရော လုပ်နိုင်ပါတယ်။
- Solaris မှာ — disk write cache ကို `format -e` နဲ့ ထိန်းချုပ်ပါတယ်။ (Solaris ZFS file system က သူ့ဘာသာ disk cache flush command တွေ ထုတ်ပေးတာကြောင့် — disk write-cache enable ဖြစ်နေရင်လည်း လုံခြုံပါတယ်။)
- Windows မှာ — `wal_sync_method` က `open_datasync` (default) ဖြစ်ရင် — My Computer\Open\disk drive\Properties\Hardware\Properties\Policies\Enable write caching on the disk ကို အမှန်ခြစ် ဖြုတ်ခြင်းဖြင့် write caching ကို disable လုပ်နိုင်ပါတယ်။ တနည်းအားဖြင့် — write caching ကို တားဆီးပေးတဲ့ `fdatasync` (NTFS သက်သက်) ဒါမှမဟုတ် `fsync` ကို `wal_sync_method` အဖြစ် သတ်မှတ်နိုင်ပါတယ်။
- macOS မှာ — `wal_sync_method` ကို `fsync_writethrough` အဖြစ် သတ်မှတ်ခြင်းဖြင့် write caching ကို တားဆီးနိုင်ပါတယ်။

မကြာသေးမီက SATA drive တွေ (ATAPI-6 နဲ့ အထက် လိုက်နာတဲ့ အတွေ့တွေ) က drive cache flush command (`FLUSH CACHE EXT`) ကို ပေးအပ်ပြီး — SCSI drive တွေကတော့ အလားတူ command ဖြစ်တဲ့ `SYNCHRONIZE CACHE` ကို ကြာမြင့်စွာကတည်းက ထောက်ပံ့ထားပါတယ်။ ဒီ command တွေက PostgreSQL အတွက် တိုက်ရိုက် အသုံးပြုနိုင်တာ မဟုတ်ပေမယ့် — file system တချို့ (ဥပမာ ZFS, ext4) က write-back enable ထားတဲ့ drive တွေမှာ data တွေကို platter တွေဆီ flush လုပ်ဖို့ ဒီ command တွေကို သုံးနိုင်ပါတယ်။ ကံဆိုးစွာပဲ — ဒီလို file system တွေက battery-backup unit (BBU) disk controller တွေနဲ့ တွဲသုံးတဲ့အခါ အကောင်းဆုံး အခြေအနေအောက် လည်ပတ်တတ်ပါတယ်။ ဒီလို setup တွေမှာ — synchronize command က controller cache ထဲက data အားလုံးကို disk တွေဆီ အတင်းအကျပ် ပို့တာကြောင့် — BBU ရဲ့ အကျိုးကျေးဇူး အများအပြား ဆုံးရှုံးသွားပါတယ်။ သင်က ဒါကြောင့် ထိခိုက်ခံရမခံရ သိချင်ရင် [pg_test_fsync](https://www.postgresql.org/docs/current/pgtestfsync.html) program ကို run ကြည့်နိုင်ပါတယ်။ ထိခိုက်ခံရတယ်ဆိုရင် — file system ထဲက write barrier တွေကို ပိတ်ခြင်းဖြင့် ဖြစ်စေ — ဖြစ်နိုင်ရင် disk controller ကို ပြန်လည် configure လုပ်ခြင်းဖြင့် ဖြစ်စေ — BBU ရဲ့ performance အကျိုးကျေးဇူးတွေကို ပြန်လည် ရယူနိုင်ပါတယ်။ Write barrier တွေ ပိတ်ထားရင် — ဘက်ထရီ ကောင်းမွန်နေဆဲ ဖြစ်ကြောင်း သေချာပါစေ; ချို့ယွင်းနေတဲ့ ဘက်ထရီက data ဆုံးရှုံးမှုအထိ ဖြစ်စေနိုင်ပါတယ်။ File system နဲ့ disk controller ဒီဇိုင်နာတွေက ဒီ အကောင်းဆုံးမဟုတ်တဲ့ အပြုအမူကို နောက်ဆုံးမှာ ဖြေရှင်းပေးလိမ့်မယ်လို့ မျှော်လင့်ပါတယ်။

Operating system က storage hardware ဆီ write request တစ်ခု ပို့တဲ့အခါ — data တွေ တကယ့် non-volatile storage နေရာဆီ ရောက်ရှိပြီလား ဆိုတာ သေချာစေဖို့ — သူလုပ်နိုင်တာ သိပ်မရှိပါဘူး။ ဒါကြောင့် — storage အစိတ်အပိုင်း အားလုံးက data နဲ့ file-system metadata နှစ်မျိုးလုံးအတွက် ခိုင်မာမှု (integrity) ရှိစေကြောင်း သေချာစေဖို့က administrator ရဲ့ တာဝန် ဖြစ်ပါတယ်။ ဘက်ထရီ အားဖြည့် မထားတဲ့ write cache ရှိတဲ့ disk controller တွေကို ရှောင်ပါ။ Drive အဆင့်မှာ — drive က shutdown မလုပ်ခင် data ရေးပြီးသား ဖြစ်မယ် ဆိုတာ အာမခံနိုင်ခြင်း မရှိရင် — write-back caching ကို disable လုပ်ပါ။ SSD တွေ သုံးရင် — အများအပြားက cache flush command တွေကို default အားဖြင့် လိုက်နာတာ မရှိဘူးဆိုတာ သတိထားပါ။ ယုံကြည်စိတ်ချရတဲ့ I/O subsystem အပြုအမူ ရှိမရှိကို [`diskchecker.pl`](https://brad.livejournal.com/2116715.html) နဲ့ စမ်းသပ်နိုင်ပါတယ်။

Data ဆုံးရှုံးမှုအတွက် နောက်ထပ် အန္တရာယ် တစ်ခုကို disk platter ရဲ့ ရေးသားမှု လုပ်ငန်းစဉ်တွေကိုယ်တိုင် ဖြစ်ပေါ်စေပါတယ်။ Disk platter တွေကို sector တွေအဖြစ် ပိုင်းခြားထားပြီး — ပုံမှန်အားဖြင့် တစ်ခုကို 512 byte ဖြစ်ပါတယ်။ ရုပ်ပိုင်းဆိုင်ရာ ဖတ်ခြင်း ဒါမှမဟုတ် ရေးခြင်း လုပ်ဆောင်မှု တိုင်းက sector တစ်ခုလုံးကို လုပ်ဆောင်ပါတယ်။ Write request တစ်ခု drive ဆီ ရောက်ရှိတဲ့အခါ — ဒါက 512 byte ရဲ့ ဆတိုးတစ်ခု ဖြစ်နိုင်ပြီး (PostgreSQL က ပုံမှန်အားဖြင့် တစ်ကြိမ်လျှင် 8192 byte သို့မဟုတ် sector ၁၆ ခု ရေးပါတယ်) — ရေးသားမှု လုပ်ငန်းစဉ်က ပါဝါ ပြတ်တောက်မှုကြောင့် အချိန်မရွေး ပျက်ကွက်နိုင်ကာ — ဆိုလိုတာက 512-byte sector တချို့ ရေးပြီးသွားပြီး အခြားတချို့ မရေးရသေးတာ ဖြစ်နိုင်ပါတယ်။ ဒီလို ပျက်ကွက်မှုတွေကို ကာကွယ်ဖို့ — PostgreSQL က disk ပေါ်က အမှန်တကယ် page ကို မပြင်ဆင်မီ — full page image တွေကို အမြဲတမ်း WAL storage ဆီ အခါအားလျော်စွာ ရေးသားပါတယ်။ ဒီလို လုပ်ခြင်းအားဖြင့် — crash recovery အတွင်း — PostgreSQL က တစ်စိတ်တစ်ပိုင်း ရေးပြီးသား page တွေကို WAL ကနေ ပြန်လည် ရယူနိုင်ပါတယ်။ တစ်စိတ်တစ်ပိုင်း page ရေးသားမှုကို တားဆီးပေးတဲ့ file-system software (ဥပမာ ZFS) ရှိရင် — [full_page_writes](https://www.postgresql.org/docs/current/runtime-config-wal.html#GUC-FULL-PAGE-WRITES) parameter ကို ပိတ်ခြင်းဖြင့် ဒီ page imaging ကို ပိတ်နိုင်ပါတယ်။ Battery-Backed Unit (BBU) disk controller တွေက — data ကို BBU ဆီ full (8kB) page အဖြစ် ရေးသားကြောင်း အာမခံထားခြင်း မရှိရင် — တစ်စိတ်တစ်ပိုင်း page ရေးသားမှုကို တားဆီးပေးတာ မဟုတ်ပါဘူး။

PostgreSQL က — အချိန်ကြာလာတဲ့အခါ hardware အမှားတွေ ဒါမှမဟုတ် media ပျက်စီးမှုကြောင့် ဖြစ်ပေါ်နိုင်တဲ့ — storage device တွေပေါ်က data ပျက်စီးမှု (corruption) အချို့ကိုလည်း ကာကွယ်ပေးပါတယ် — ဥပမာ — အညစ်အကြေး data (garbage data) ဖတ်ခြင်း/ရေးခြင်း မျိုးပါ။

- WAL file ထဲက record တစ်ခုချင်းစီကို CRC-32C (32-bit) check နဲ့ ကာကွယ်ထားပြီး — ဒါက record ရဲ့ အကြောင်းအရာ မှန်ကန်မှု ရှိမရှိ ပြောနိုင်စေပါတယ်။ CRC တန်ဖိုးကို WAL record တစ်ခုချင်းစီ ရေးတဲ့အခါ သတ်မှတ်ပြီး — crash recovery, archive recovery နဲ့ replication အတွင်းမှာ စစ်ဆေးပါတယ်။
- Data page တွေကို default အားဖြင့် checksum လုပ်ထားပြီး — WAL record တွေမှာ မှတ်တမ်းတင်ထားတဲ့ full page image တွေကို အမြဲ checksum ကာကွယ်ထားပါတယ်။
- `pg_xact`, `pg_subtrans`, `pg_multixact`, `pg_serial`, `pg_notify`, `pg_stat`, `pg_snapshots` ကဲ့သို့ internal data structure တွေကို တိုက်ရိုက် checksum လုပ်ထားတာ မဟုတ်သလို — page တွေကိုလည်း full page write နဲ့ ကာကွယ်ထားတာ မဟုတ်ပါဘူး။ ဒါပေမယ့် — ဒီလို data structure တွေ persistent (တည်မြဲ) ဖြစ်တဲ့ အခါမှာ — crash recovery မှာ မကြာသေးမီ ပြောင်းလဲမှုတွေကို တိကျစွာ ပြန်လည် တည်ဆောက်နိုင်စေတဲ့ WAL record တွေ ရေးသားထားပြီး — အဲဒီ WAL record တွေကို အပေါ်မှာ ဆွေးနွေးခဲ့သလို ကာကွယ်ထားပါတယ်။
- `pg_twophase` ထဲက state file တစ်ခုချင်းစီကို CRC-32C နဲ့ ကာကွယ်ထားပါတယ်။
- ကြီးမားတဲ့ SQL query တွေမှာ sort, materialization နဲ့ intermediate result တွေအတွက် သုံးတဲ့ temporary data file တွေကို လက်ရှိအချိန်မှာ checksum လုပ်ထားတာ မဟုတ်သလို — ဒီ file တွေရဲ့ ပြောင်းလဲမှုတွေအတွက် WAL record တွေလည်း ရေးသားမှာ မဟုတ်ပါဘူး။

PostgreSQL က ပြုပြင်နိုင်တဲ့ memory error တွေကို ကာကွယ်ပေးတာ မဟုတ်ဘဲ — စက်မှုလုပ်ငန်း စံ Error Correcting Codes (ECC) ဒါမှမဟုတ် ပိုကောင်းတဲ့ အကာအကွယ် သုံးထားတဲ့ RAM နဲ့ လည်ပတ်မယ်လို့ ယူဆထားပါတယ်။
