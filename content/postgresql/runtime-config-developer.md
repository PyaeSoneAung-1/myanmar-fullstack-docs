## 19.17. Developer Options (developer အတွက် ရွေးချယ်စရာများ)

အောက်ပါ parameter များကို developer testing အတွက် ရည်ရွယ်ထားပြီး — production database တစ်ခုပေါ်မှာ ဘယ်တော့မှ မသုံးသင့်ပါဘူး။ ဒါပေမယ့် — တချို့ကို အလွန်အမင်း ပျက်စီးနေတဲ့ database များကို ပြန်လည် ရယူရာမှာ အထောက်အကူ ပြုဖို့ သုံးနိုင်ပါတယ်။ ဒါကြောင့် — ဒီ parameter တွေကို နမူနာ `postgresql.conf` file ထဲကနေ ဖယ်ထားပါတယ်။ သတိပြုရမှာက — ဒီ parameter အများအပြားက အလုပ်လုပ်ဖို့ source compilation flag အထူးတွေ လိုအပ်ပါတယ်။

- **allow_in_place_tablespaces (boolean)** — `CREATE TABLESPACE` command ဆီ — location string အလွတ်တစ်ခုကို ပေးလိုက်တဲ့အခါ — tablespace များကို `pg_tblspc` အတွင်းက directory များအဖြစ် ဖန်တီးခွင့် ပြုပါတယ်။ ဒါက — primary နဲ့ standby server များ တစ်စက်တည်းမှာ run နေတဲ့ replication အခြေအနေများကို စမ်းသပ်ခွင့်ပြုဖို့ ရည်ရွယ်ပါတယ်။ ဒီလို directory များက — အဲဒီနေရာမှာ symbolic link များသာ ရှိမယ်လို့ မျှော်လင့်တဲ့ backup tool များကို ရှုပ်ထွေးစေနိုင်ပါတယ်။ Superuser များနှင့် သင့်လျော်တဲ့ `SET` privilege ရှိတဲ့ user များသာ ဒီ setting ကို ပြောင်းနိုင်ပါတယ်။
- **allow_system_table_mods (boolean)** — System table များ၏ ဖွဲ့စည်းပုံကို ပြုပြင်ခြင်းအပြင် — system table များပေါ်က အန္တရာယ်ရှိတဲ့ အခြား လုပ်ဆောင်ချက် တချို့ကိုပါ ခွင့်ပြုပါတယ်။ မဟုတ်ရင် — superuser များအတွက်တောင် ဒါကို ခွင့်မပြုပါဘူး။ ဒီ setting ကို မဆင်မခြင် သုံးမိတာက — ပြန်လည် ရယူလို့ မရနိုင်တဲ့ data ဆုံးရှုံးမှုကို ဖြစ်စေနိုင်သလို — database system ကို ပြင်းထန်စွာ ပျက်စီးစေနိုင်ပါတယ်။ Superuser များနှင့် သင့်လျော်တဲ့ `SET` privilege ရှိတဲ့ user များသာ ဒီ setting ကို ပြောင်းနိုင်ပါတယ်။
- **backtrace_functions (string)** — ဒီ parameter မှာ C function နာမည်များကို comma နဲ့ ခြားထားတဲ့ list တစ်ခု ပါဝင်ပါတယ်။ Error တစ်ခု ဖြစ်ပေါ်ပြီး — error ဖြစ်တဲ့ internal C function ရဲ့ နာမည်က list ထဲက တန်ဖိုးတစ်ခုနဲ့ ကိုက်ညီရင် — error message နဲ့အတူ backtrace တစ်ခုကို server log ဆီ ရေးသားပါတယ်။ ဒါကို source code ရဲ့ သီးခြား နေရာတွေကို debug လုပ်ဖို့ သုံးနိုင်ပါတယ်။
Backtrace support က platform အားလုံးမှာ မရနိုင်ပါဘူး; backtrace များရဲ့ အရည်အသွေးက compilation option များပေါ် မူတည်ပါတယ်။
Superuser များနှင့် သင့်လျော်တဲ့ `SET` privilege ရှိတဲ့ user များသာ ဒီ setting ကို ပြောင်းနိုင်ပါတယ်။
- **debug_copy_parse_plan_trees (boolean)** — ဒါကို enable လုပ်ခြင်းက — parse tree နဲ့ plan tree အားလုံးကို `copyObject()` ကတစ်ဆင့် ဖြတ်သွားစေပြီး — `copyObject()` ထဲက error များနဲ့ ချန်လှပ်မှုများကို ဖမ်းမိနိုင်ဖို့ အထောက်အကူ ပြုပါတယ်။ Default က off ဖြစ်ပါတယ်။
ဒီ parameter က — compile လုပ်ချိန်မှာ `DEBUG_NODE_TESTS_ENABLED` ကို define လုပ်ထားမှသာ (configure option `--enable-cassert` ကို သုံးတဲ့အခါ အလိုအလျောက် ဖြစ်လာပါတယ်) ရနိုင်ပါတယ်။
- **debug_discard_caches (integer)** — 1 သတ်မှတ်ထားတဲ့အခါ — system catalog cache entry တစ်ခုချင်းစီကို — ၎င်းကို invalid ဖြစ်စေမယ့် တစ်ခုခု တကယ် ဖြစ်ခဲ့သည်ဖြစ်စေ မဖြစ်ခဲ့သည်ဖြစ်စေ — ဖြစ်နိုင်တဲ့ ပထမဆုံး အခွင့်အရေးမှာ invalidate လုပ်ပါတယ်။ ရလဒ်အနေနဲ့ system catalog caching က လက်တွေ့အားဖြင့် disable ဖြစ်သွားတာကြောင့် — server က အလွန်အမင်း နှေးကွေးစွာ run ပါလိမ့်မယ်။ ပိုမြင့်တဲ့ တန်ဖိုးများက cache invalidation ကို recursive လုပ်ပြီး — ဒါက ပိုတောင် နှေးကွေးကာ cache logic ကိုယ်တိုင်ကို စမ်းသပ်ဖို့သာ အသုံးဝင်ပါတယ်။ Default တန်ဖိုး 0 က ပုံမှန် catalog caching အပြုအမူကို ရွေးချယ်ပါတယ်။
ဒီ parameter က — catalog ပြောင်းလဲမှုများ တစ်ပြိုင်နက် ဖြစ်ပေါ်နေတဲ့ — ပြန်ဖန်တီးရ ခက်တဲ့ bug များကို ဖော်ထုတ်ဖို့ ကြိုးစားတဲ့အခါ အလွန် အထောက်အကူ ဖြစ်နိုင်ပါတယ် — ဒါပေမယ့် မဟုတ်ရင် ဒါကို သိပ်မလိုအပ်ပါဘူး။ အသေးစိတ်အတွက် source code file များဖြစ်တဲ့ `inval.c` နဲ့ `pg_config_manual.h` ကို ကြည့်ပါ။
ဒီ parameter က — compile လုပ်ချိန်မှာ `DISCARD_CACHES_ENABLED` ကို define လုပ်ထားမှသာ (configure option `--enable-cassert` ကို သုံးတဲ့အခါ အလိုအလျောက် ဖြစ်လာပါတယ်) ထောက်ပံ့ပါတယ်။ Production build များမှာ — ၎င်းရဲ့ တန်ဖိုးက အမြဲ 0 ဖြစ်ပြီး — အခြားတန်ဖိုးတစ်ခုကို သတ်မှတ်ဖို့ ကြိုးစားတာက error တစ်ခု ထုတ်ပါလိမ့်မယ်။
- **debug_io_direct (string)** — `O_DIRECT` (Unix-like system အများစု)၊ `F_NOCACHE` (macOS) ဒါမှမဟုတ် `FILE_FLAG_NO_BUFFERING` (Windows) ကို သုံးပြီး — relation data နဲ့ WAL file များအတွက် caching သက်ရောက်မှုများကို အနည်းဆုံး ဖြစ်စေဖို့ kernel ကို တောင်းဆိုပါတယ်။
Direct I/O အသုံးပြုမှုကို disable လုပ်ဖို့ string အလွတ်တစ်ခု (default) သတ်မှတ်နိုင်ပြီး — ဒါမှမဟုတ် direct I/O သုံးသင့်တဲ့ operation များကို comma နဲ့ ခြားထားတဲ့ list တစ်ခု သတ်မှတ်နိုင်ပါတယ်။ တရားဝင် option များက — main data file များအတွက် `data`၊ WAL file များအတွက် `wal`၊ နဲ့ အစပိုင်း allocate လုပ်တဲ့အခါ WAL file များအတွက် `wal_init` တို့ ဖြစ်ပါတယ်။ ဒီ parameter ကို server start လုပ်ချိန်မှာသာ သတ်မှတ်နိုင်ပါတယ်။
Operating system နဲ့ file system တချို့က direct I/O ကို မထောက်ပံ့ပါဘူး — ဒါကြောင့် default မဟုတ်တဲ့ setting များကို startup မှာ ငြင်းပယ်ခံရနိုင်သလို error များ ဖြစ်စေနိုင်ပါတယ်။
လက်ရှိမှာ ဒီ feature က performance ကို လျော့ကျစေတာကြောင့် — developer testing အတွက်သာ ရည်ရွယ်ထားပါတယ်။
- **debug_parallel_query (enum)** — Performance အကျိုးအမြတ် မမျှော်လင့်ရတဲ့ အခြေအနေများမှာတောင် — စမ်းသပ်ရေး ရည်ရွယ်ချက်အတွက် parallel query များကို သုံးခွင့်ပြုပါတယ်။ `debug_parallel_query` ရဲ့ ခွင့်ပြုထားတဲ့ တန်ဖိုးများက — `off` (performance တိုးတက်စေမယ်လို့ မျှော်လင့်တဲ့အခါမှသာ parallel mode သုံးခြင်း)၊ `on` (ဘေးကင်းတယ်လို့ ယူဆရတဲ့ query အားလုံးအတွက် parallel query ကို အတင်းအကျပ် လုပ်ခြင်း) နဲ့ `regress` (`on` လိုပဲ — ဒါပေမယ့် အောက်မှာ ရှင်းပြထားတဲ့ ထပ်ဆောင်း အပြုအမူ ပြောင်းလဲမှုများနဲ့အတူ) တို့ ဖြစ်ပါတယ်။
ပိုတိကျစွာ ဆိုရရင် — ဒီတန်ဖိုးကို `on` သတ်မှတ်ခြင်းက — ဘေးကင်းတယ်လို့ ထင်ရတဲ့ query plan တိုင်းရဲ့ ထိပ်မှာ `Gather` node တစ်ခုကို ထည့်ပေးပြီး — query က parallel worker တစ်ခုအတွင်းမှာ run စေပါတယ်။ Parallel worker တစ်ခု မရနိုင်တဲ့အခါ ဒါမှမဟုတ် မသုံးနိုင်တဲ့အခါတွင်တောင် — parallel query context မှာ တားမြစ်ထားတဲ့ subtransaction စတင်ခြင်းကဲ့သို့ operation များကို — planner က ဒါက query ကို fail ဖြစ်စေမယ်လို့ မယုံကြည်ရင် — တားမြစ်ထားပါလိမ့်မယ်။ ဒီ option သတ်မှတ်ထားချိန်မှာ failure များ ဒါမှမဟုတ် မမျှော်လင့်တဲ့ ရလဒ်များ ဖြစ်ပေါ်ရင် — query က သုံးတဲ့ function တချို့ကို `PARALLEL UNSAFE` (ဒါမှမဟုတ် `PARALLEL RESTRICTED` ဖြစ်နိုင်ပါတယ်) အဖြစ် mark လုပ်ဖို့ လိုအပ်နိုင်ပါတယ်။
ဒီတန်ဖိုးကို `regress` သတ်မှတ်ခြင်းက — `on` သတ်မှတ်ခြင်းရဲ့ သက်ရောက်မှု အားလုံးအပြင် — automated regression testing ကို အထောက်အကူ ပြုဖို့ ရည်ရွယ်တဲ့ ထပ်ဆောင်း သက်ရောက်မှု တချို့ ရှိပါတယ်။ ပုံမှန်အားဖြင့် — parallel worker ဆီက message များမှာ ဒါကို ဖော်ပြတဲ့ context line တစ်ခု ပါဝင်ပါတယ် — ဒါပေမယ့် `regress` setting က ဒီ line ကို ဖိနှိပ်ထားတာကြောင့် — output က parallel မဟုတ်တဲ့ execution မှာ ရရှိမယ့် output နဲ့ တူညီပါတယ်။ ထို့အပြင် — ဒီ setting က plan များဆီ ထည့်တဲ့ `Gather` node များကို `EXPLAIN` output မှာ ဖျောက်ထားတာကြောင့် — output က ဒီ setting ကို ပိတ်ထားရင် ရမယ့် output နဲ့ ကိုက်ညီပါတယ်။
- **debug_raw_expression_coverage_test (boolean)** — ဒါကို enable လုပ်ခြင်းက — DML statement များအတွက် raw parse tree အားလုံးကို `raw_expression_tree_walker()` နဲ့ scan ဖတ်စေပြီး — အဲဒီ function ထဲက error များနဲ့ ချန်လှပ်မှုများကို ဖမ်းမိနိုင်ဖို့ အထောက်အကူ ပြုပါတယ်။ Default က off ဖြစ်ပါတယ်။
ဒီ parameter က — compile လုပ်ချိန်မှာ `DEBUG_NODE_TESTS_ENABLED` ကို define လုပ်ထားမှသာ (configure option `--enable-cassert` ကို သုံးတဲ့အခါ အလိုအလျောက် ဖြစ်လာပါတယ်) ရနိုင်ပါတယ်။
- **debug_write_read_parse_plan_trees (boolean)** — ဒါကို enable လုပ်ခြင်းက — parse tree နဲ့ plan tree အားလုံးကို `outfuncs.c`/`readfuncs.c` ကတစ်ဆင့် ဖြတ်သွားစေပြီး — အဲဒီ module များထဲက error များနဲ့ ချန်လှပ်မှုများကို ဖမ်းမိနိုင်ဖို့ အထောက်အကူ ပြုပါတယ်။ Default က off ဖြစ်ပါတယ်။

- **ignore_checksum_failure (boolean)** — [data checksums](/docs/postgresql/checksums) ကို enable လုပ်ထားမှသာ သက်ရောက်မှု ရှိပါတယ်။
ဖတ်တဲ့အခါ checksum ပျက်ကွက်မှုကို တွေ့ရှိတာက — ပုံမှန်အားဖြင့် PostgreSQL က error တစ်ခု အစီရင်ခံပြီး — လက်ရှိ transaction ကို abort လုပ်စေပါတယ်။ `ignore_checksum_failure` ကို `on` သတ်မှတ်ခြင်းက — system က ပျက်ကွက်မှုကို လျစ်လျူရှုပြီး (ဒါပေမယ့် warning တစ်ခု ဆက်ပြီး အစီရင်ခံပါတယ်) — ဆက်လက် လုပ်ဆောင်စေပါတယ်။ ဒီအပြုအမူက — crash များ ဖြစ်စေနိုင်သလို — corruption ကို ပျံ့နှံ့စေခြင်း ဒါမှမဟုတ် ဖုံးကွယ်ခြင်း — ဒါမှမဟုတ် အခြား ပြင်းထန်တဲ့ ပြဿနာများ ဖြစ်စေနိုင်ပါတယ်။ ဒါပေမယ့် — block header က ကောင်းမွန်နေသေးရင် — error ကို ကျော်လွှားပြီး — table ထဲမှာ ကျန်ရှိနိုင်သေးတဲ့ မပျက်စီးတဲ့ tuple များကို ပြန်ရယူနိုင်ဖို့ ဒါက ခွင့်ပြုနိုင်ပါတယ်။ Header ပျက်စီးနေရင်တော့ — ဒီ option enable လုပ်ထားရင်တောင် error တစ်ခု အစီရင်ခံပါလိမ့်မယ်။ Default setting က off ဖြစ်ပါတယ်။ Superuser များနှင့် သင့်လျော်တဲ့ `SET` privilege ရှိတဲ့ user များသာ ဒီ setting ကို ပြောင်းနိုင်ပါတယ်။
- **zero_damaged_pages (boolean)** — ပျက်စီးနေတဲ့ page header ကို တွေ့ရှိတာက — ပုံမှန်အားဖြင့် PostgreSQL က error တစ်ခု အစီရင်ခံပြီး — လက်ရှိ transaction ကို abort လုပ်စေပါတယ်။ `zero_damaged_pages` ကို `on` သတ်မှတ်ခြင်းက — system က အဲဒီအစား warning တစ်ခု အစီရင်ခံပြီး — memory ထဲက ပျက်စီးနေတဲ့ page ကို သုည ဖြစ်စေ (zero out) ကာ — ဆက်လက် လုပ်ဆောင်စေပါတယ်။ ဒီအပြုအမူက data ကို ဖျက်ဆီးပါလိမ့်မယ် — ဆိုလိုတာက ပျက်စီးနေတဲ့ page ပေါ်က row အားလုံးပါ။ ဒါပေမယ့် — error ကို ကျော်လွှားပြီး — table ထဲမှာ ရှိနိုင်သေးတဲ့ မပျက်စီးတဲ့ page များကနေ row များကို ပြန်ရယူနိုင်ဖို့ ဒါက ခွင့်ပြုပါတယ်။ Hardware ဒါမှမဟုတ် software error ကြောင့် corruption ဖြစ်ခဲ့ရင် data ကို ပြန်လည် ရယူဖို့ ဒါက အသုံးဝင်ပါတယ်။ Table တစ်ခုရဲ့ ပျက်စီးနေတဲ့ page များကနေ data ကို ပြန်လည် ရယူနိုင်မယ့် မျှော်လင့်ချက်ကို စွန့်လွှတ်ပြီးမှသာ — ဒါကို ယေဘုယျအားဖြင့် on မသတ်မှတ်သင့်ပါဘူး။ Zeroed-out page များကို disk ဆီ အတင်းအကျပ် မရေးသားတာကြောင့် — ဒီ parameter ကို ပြန်ပိတ်မီ — table ဒါမှမဟုတ် index ကို ပြန်ဖန်တီးဖို့ အကြံပြုပါတယ်။ Default setting က off ဖြစ်ပါတယ်။ Superuser များနှင့် သင့်လျော်တဲ့ `SET` privilege ရှိတဲ့ user များသာ ဒီ setting ကို ပြောင်းနိုင်ပါတယ်။
- **ignore_invalid_pages (boolean)** — `off` (default) သတ်မှတ်ထားရင် — recovery အတွင်း invalid page များဆီ reference များ ပါဝင်တဲ့ WAL record များကို တွေ့ရှိတာက — PostgreSQL ကို PANIC အဆင့် error တစ်ခု ဖြစ်စေပြီး — recovery ကို abort လုပ်စေပါတယ်။ `ignore_invalid_pages` ကို `on` သတ်မှတ်ခြင်းက — system က WAL record များထဲက invalid page reference များကို လျစ်လျူရှုပြီး (ဒါပေမယ့် warning တစ်ခု ဆက်ပြီး အစီရင်ခံပါတယ်) — recovery ကို ဆက်လက် လုပ်ဆောင်စေပါတယ်။ ဒီအပြုအမူက — crash များ၊ data ဆုံးရှုံးမှု၊ corruption ပျံ့နှံ့ခြင်း ဒါမှမဟုတ် ဖုံးကွယ်ခြင်း — ဒါမှမဟုတ် အခြား ပြင်းထန်တဲ့ ပြဿနာများ ဖြစ်စေနိုင်ပါတယ်။ ဒါပေမယ့် — PANIC အဆင့် error ကို ကျော်လွှားပြီး — recovery ကို အပြီးသတ်ကာ — server ကို စတင်နိုင်ဖို့ ဒါက ခွင့်ပြုနိုင်ပါတယ်။ ဒီ parameter ကို server start လုပ်ချိန်မှာသာ သတ်မှတ်နိုင်ပါတယ်။ ဒါက recovery အတွင်း ဒါမှမဟုတ် standby mode မှာသာ သက်ရောက်မှု ရှိပါတယ်။
- **jit_debugging_support (boolean)** — LLVM မှာ လိုအပ်တဲ့ functionality ရှိရင် — ထုတ်လုပ်လိုက်တဲ့ function များကို GDB နဲ့ register လုပ်ပါတယ်။ ဒါက debugging ကို ပိုလွယ်စေပါတယ်။ Default setting က off ဖြစ်ပါတယ်။ Superuser များနှင့် သင့်လျော်တဲ့ `SET` privilege ရှိတဲ့ user များသာ — session စတင်ချိန်မှာ ဒီ parameter ကို ပြောင်းနိုင်ပြီး — session အတွင်းမှာတော့ လုံးဝ ပြောင်းလဲလို့ မရပါဘူး။
- **jit_dump_bitcode (boolean)** — ထုတ်လုပ်လိုက်တဲ့ LLVM IR ကို — [data_directory](/docs/postgresql/runtime-config-file-locations) အတွင်းရှိ — file system ဆီ ရေးသားပါတယ်။ ဒါက JIT implementation ရဲ့ internals များပေါ်မှာ အလုပ်လုပ်ဖို့သာ အသုံးဝင်ပါတယ်။ Default setting က off ဖြစ်ပါတယ်။ Superuser များနှင့် သင့်လျော်တဲ့ `SET` privilege ရှိတဲ့ user များသာ ဒီ setting ကို ပြောင်းနိုင်ပါတယ်။
- **jit_expressions (boolean)** — JIT compilation ကို activate လုပ်တဲ့အခါ ([အပိုင်း 30.2](/docs/postgresql/jit-decision) ကို ကြည့်ပါ) — expression များကို JIT compile လုပ်မလား ဆိုတာကို ဆုံးဖြတ်ပါတယ်။ Default က on ဖြစ်ပါတယ်။
- **jit_profiling_support (boolean)** — LLVM မှာ လိုအပ်တဲ့ functionality ရှိရင် — `perf` ကို JIT က ထုတ်လုပ်တဲ့ function များကို profile လုပ်ခွင့်ပြုဖို့ လိုအပ်တဲ့ data ကို ထုတ်ပါတယ်။ ဒါက `~/.debug/jit/` ဆီ file များ ရေးထုတ်ပါတယ်; လိုချင်တဲ့အခါ cleanup လုပ်ဖို့က user ရဲ့ တာဝန် ဖြစ်ပါတယ်။ Default setting က off ဖြစ်ပါတယ်။ Superuser များနှင့် သင့်လျော်တဲ့ `SET` privilege ရှိတဲ့ user များသာ — session စတင်ချိန်မှာ ဒီ parameter ကို ပြောင်းနိုင်ပြီး — session အတွင်းမှာတော့ လုံးဝ ပြောင်းလဲလို့ မရပါဘူး။
- **jit_tuple_deforming (boolean)** — JIT compilation ကို activate လုပ်တဲ့အခါ ([အပိုင်း 30.2](/docs/postgresql/jit-decision) ကို ကြည့်ပါ) — tuple deforming ကို JIT compile လုပ်မလား ဆိုတာကို ဆုံးဖြတ်ပါတယ်။ Default က on ဖြစ်ပါတယ်။
- **remove_temp_files_after_crash (boolean)** — `on` (default) သတ်မှတ်ထားတဲ့အခါ — PostgreSQL က backend crash ဖြစ်ပြီးနောက် temporary file များကို အလိုအလျောက် ဖယ်ရှားပါလိမ့်မယ်။ Disable လုပ်ထားရင် — file များကို သိမ်းထားပြီး — ဥပမာ — debugging အတွက် သုံးနိုင်ပါတယ်။ ဒါပေမယ့် — ထပ်ခါထပ်ခါ crash ဖြစ်တာက — အသုံးမဝင်တဲ့ file များ စုပုံလာစေနိုင်ပါတယ်။ ဒီ parameter ကို `postgresql.conf` file ထဲမှာ ဒါမှမဟုတ် server command line ပေါ်မှာသာ သတ်မှတ်နိုင်ပါတယ်။
- **send_abort_for_crash (boolean)** — Default အားဖြင့် — backend crash ဖြစ်ပြီးနောက် — postmaster က ကျန်ရှိတဲ့ child process များကို `SIGQUIT` signal များ ပို့ပြီး ရပ်တန့်စေတာက — သူတို့ကို အတော်အသင့် ညင်သာစွာ ထွက်ခွင့်ပြုပါတယ်။ ဒီ option ကို `on` သတ်မှတ်ထားတဲ့အခါ — အဲဒီအစား `SIGABRT` ကို ပို့ပါတယ်။ ဒါက ပုံမှန်အားဖြင့် — အဲဒီလို child process တစ်ခုစီအတွက် core dump file တစ်ခု ထုတ်လုပ်စေပါတယ်။ ဒါက — crash ဖြစ်ပြီးနောက် အခြား process များရဲ့ အခြေအနေများကို စူးစမ်းစစ်ဆေးဖို့ အဆင်ပြေနိုင်ပါတယ်။ ထပ်ခါထပ်ခါ crash ဖြစ်တဲ့အခါ disk space အများအပြား သုံးစွဲနိုင်တာကြောင့် — သေချာစွာ စောင့်ကြည့်မထားတဲ့ system များပေါ်မှာ ဒါကို enable မလုပ်ပါနဲ့။ Core file(s) များကို အလိုအလျောက် ရှင်းလင်းဖို့ support မရှိဘူးဆိုတာ သတိထားပါ။ ဒီ parameter ကို `postgresql.conf` file ထဲမှာ ဒါမှမဟုတ် server command line ပေါ်မှာသာ သတ်မှတ်နိုင်ပါတယ်။
- **send_abort_for_kill (boolean)** — Default အားဖြင့် — child process တစ်ခုကို `SIGQUIT` နဲ့ ရပ်တန့်ဖို့ ကြိုးစားပြီးနောက် — postmaster က ငါးစက္ကန့် စောင့်ပြီး — ချက်ချင်း ရပ်စဲဖို့ `SIGKILL` ကို ပို့ပါတယ်။ ဒီ option ကို `on` သတ်မှတ်ထားတဲ့အခါ — `SIGKILL` အစား `SIGABRT` ကို ပို့ပါတယ်။ ဒါက ပုံမှန်အားဖြင့် — အဲဒီလို child process တစ်ခုစီအတွက် core dump file တစ်ခု ထုတ်လုပ်စေပါတယ်။ ဒါက — “ပိတ်မိနေတဲ့” (stuck) child process များရဲ့ အခြေအနေများကို စူးစမ်းစစ်ဆေးဖို့ အဆင်ပြေနိုင်ပါတယ်။ ထပ်ခါထပ်ခါ crash ဖြစ်တဲ့အခါ disk space အများအပြား သုံးစွဲနိုင်တာကြောင့် — သေချာစွာ စောင့်ကြည့်မထားတဲ့ system များပေါ်မှာ ဒါကို enable မလုပ်ပါနဲ့။ Core file(s) များကို အလိုအလျောက် ရှင်းလင်းဖို့ support မရှိဘူးဆိုတာ သတိထားပါ။ ဒီ parameter ကို `postgresql.conf` file ထဲမှာ ဒါမှမဟုတ် server command line ပေါ်မှာသာ သတ်မှတ်နိုင်ပါတယ်။
- **debug_logical_replication_streaming (enum)** — ခွင့်ပြုထားတဲ့ တန်ဖိုးများက `buffered` နဲ့ `immediate` ဖြစ်ပါတယ်။ Default က `buffered` ဖြစ်ပါတယ်။ ဒီ parameter က — ကြီးမားတဲ့ transaction များရဲ့ logical decoding နဲ့ replication ကို စမ်းသပ်ဖို့ သုံးဖို့ ရည်ရွယ်ပါတယ်။ `debug_logical_replication_streaming` ရဲ့ သက်ရောက်မှုက — publisher နဲ့ subscriber အတွက် မတူညီပါဘူး:
Publisher ဘက်မှာ — `debug_logical_replication_streaming` က logical decoding မှာ ပြောင်းလဲမှုများကို ချက်ချင်း streaming ဒါမှမဟုတ် serializing လုပ်ခွင့်ပြုပါတယ်။ `immediate` သတ်မှတ်ထားတဲ့အခါ — [CREATE SUBSCRIPTION](/docs/postgresql/sql-createsubscription) ရဲ့ [streaming](/docs/postgresql/sql-createsubscription) option enable ဖြစ်နေရင် ပြောင်းလဲမှုတစ်ခုစီကို stream လုပ်ပြီး — မဟုတ်ရင် ပြောင်းလဲမှုတစ်ခုစီကို serialize လုပ်ပါတယ်။ `buffered` သတ်မှတ်ထားတဲ့အခါ — `logical_decoding_work_mem` ပြည့်တဲ့အခါမှ decoding က ပြောင်းလဲမှုများကို stream ဒါမှမဟုတ် serialize လုပ်ပါလိမ့်မယ်။
Subscriber ဘက်မှာ — streaming option ကို `parallel` သတ်မှတ်ထားရင် — `debug_logical_replication_streaming` ကို — leader apply worker က ပြောင်းလဲမှုများကို shared memory queue ဆီ ပို့စေဖို့ ဒါမှမဟုတ် ပြောင်းလဲမှုအားလုံးကို file ဆီ serialize လုပ်စေဖို့ — ညွှန်ကြားရန် သုံးနိုင်ပါတယ်။ `buffered` သတ်မှတ်ထားတဲ့အခါ — leader က ပြောင်းလဲမှုများကို shared memory queue ကတစ်ဆင့် parallel apply worker များဆီ ပို့ပါတယ်။ `immediate` သတ်မှတ်ထားတဲ့အခါ — leader က ပြောင်းလဲမှုအားလုံးကို file များဆီ serialize လုပ်ပြီး — transaction အဆုံးမှာ ၎င်းတို့ကို ဖတ်ပြီး apply လုပ်ဖို့ parallel apply worker များကို အသိပေးပါတယ်။
