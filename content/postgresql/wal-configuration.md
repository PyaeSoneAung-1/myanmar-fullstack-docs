## 28.5. WAL Configuration (WAL ပြင်ဆင်သတ်မှတ်ခြင်း)

WAL နဲ့ ဆက်စပ်တဲ့ configuration parameter တွေ အတော်များများ ရှိပြီး — သူတို့က database performance ကို သက်ရောက်မှု ရှိပါတယ်။ ဒီ section မှာ သူတို့ရဲ့ အသုံးပြုပုံကို ရှင်းပြထားပါတယ်။ Server configuration parameter တွေ သတ်မှတ်ခြင်းဆိုင်ရာ ယေဘုယျ အချက်အလက်တွေအတွက် [အပိုင်း 19](https://www.postgresql.org/docs/current/runtime-config.html) ကို ကြည့်ပါ။

*Checkpoints* (checkpoint များ) ဆိုတာ transaction အစီအစဉ်အတွင်းက အမှတ်တစ်ခု ဖြစ်ပြီး — အဲဒီ checkpoint မတိုင်မီ ရေးသားခဲ့သမျှ အချက်အလက်အားလုံးနဲ့အတူ heap နဲ့ index data file တွေ update ဖြစ်ပြီးသား ဖြစ်ကြောင်း အာမခံထားတဲ့ အမှတ် ဖြစ်ပါတယ်။ Checkpoint ဖြစ်တဲ့အချိန်မှာ dirty data page အားလုံးကို disk ဆီ flush လုပ်ပြီး — အထူး checkpoint record တစ်ခုကို WAL file ဆီ ရေးသားပါတယ်။ (ပြောင်းလဲမှု record တွေကို အရင်ကတည်းက WAL file တွေဆီ flush လုပ်ပြီးသား ဖြစ်ပါတယ်။) Crash ဖြစ်တဲ့အခါ — crash recovery လုပ်ငန်းစဉ်က နောက်ဆုံး checkpoint record ကို ကြည့်ပြီး — REDO လုပ်ဆောင်ချက်ကို စတင်သင့်တဲ့ WAL အမှတ် (redo record လို့ သိကြပါတယ်) ကို ဆုံးဖြတ်ပါတယ်။ အဲဒီအမှတ်မတိုင်မီ data file တွေအပေါ် လုပ်ခဲ့တဲ့ ပြောင်းလဲမှုအားလုံးက disk ပေါ်မှာ ရှိပြီးသား ဖြစ်ကြောင်း အာမခံထားပါတယ်။ ဒါကြောင့် — checkpoint တစ်ခုပြီးတဲ့နောက် — redo record ပါဝင်တဲ့ WAL segment အရှေ့က segment တွေကို မလိုအပ်တော့ဘဲ — recycle လုပ်နိုင် ဒါမှမဟုတ် ဖယ်ရှားနိုင်ပါတယ်။ (WAL archiving လုပ်နေတဲ့အခါမှာတော့ WAL segment တွေကို recycle လုပ်ခြင်း ဒါမှမဟုတ် ဖယ်ရှားခြင်း မပြုမီ archive လုပ်ရပါမယ်။)

Dirty data page အားလုံးကို disk ဆီ flush လုပ်ရမယ်ဆိုတဲ့ checkpoint ရဲ့ လိုအပ်ချက်က ကြီးမားတဲ့ I/O load ကို ဖြစ်စေနိုင်ပါတယ်။ ဒီအတွက်ကြောင့် — checkpoint လုပ်ဆောင်မှုကို throttle (အရှိန် ထိန်း) လုပ်ထားပြီး — I/O က checkpoint စတင်ချိန်မှာ စပြီး နောက် checkpoint စတင်မယ့်အချိန် မတိုင်မီ ပြီးစီးအောင် လုပ်ပါတယ်; ဒါက checkpoint တွေအတွင်း performance ကျဆင်းမှုကို အနည်းဆုံး ဖြစ်စေပါတယ်။

Server ရဲ့ checkpointer process က checkpoint ကို အခါအားလျော်စွာ အလိုအလျောက် လုပ်ဆောင်ပါတယ်။ [checkpoint_timeout](https://www.postgresql.org/docs/current/runtime-config-wal.html#GUC-CHECKPOINT-TIMEOUT) စက္ကန့်တိုင်း — ဒါမှမဟုတ် [max_wal_size](https://www.postgresql.org/docs/current/runtime-config-wal.html#GUC-MAX-WAL-SIZE) ကို ကျော်လွန်တော့မယ့် အခြေအနေမှာ — နှစ်ခုထဲက အစောဆုံး ဖြစ်တာ အတိုင်း — checkpoint တစ်ခု စတင်ပါတယ်။ Default သတ်မှတ်ချက်တွေက အသီးသီး 5 မိနစ်နဲ့ 1 GB ဖြစ်ပါတယ်။ ယခင် checkpoint ကတည်းက WAL ရေးသားထားခြင်း မရှိရင် — `checkpoint_timeout` ကျော်သွားပေမယ့်လည်း — checkpoint အသစ်တွေကို ကျော်လွှားပါလိမ့်မယ်။ (WAL archiving သုံးနေပြီး — ဖြစ်နိုင်တဲ့ data ဆုံးရှုံးမှုကို ကန့်သတ်ဖို့ — file တွေ archive လုပ်တဲ့ အကြိမ်အရေအတွက်အပေါ် အနိမ့်ဆုံး ကန့်သတ်ချက် သတ်မှတ်ချင်ရင် — checkpoint parameter တွေအစား [archive_timeout](https://www.postgresql.org/docs/current/runtime-config-wal.html#GUC-ARCHIVE-TIMEOUT) parameter ကို ချိန်ညှိသင့်ပါတယ်။) `CHECKPOINT` SQL command ကို သုံးပြီးလည်း checkpoint ကို အတင်းအကျပ် လုပ်နိုင်ပါတယ်။

`checkpoint_timeout` နဲ့/ဒါမှမဟုတ် `max_wal_size` ကို လျှော့ချခြင်းက checkpoint တွေ ပိုမကြာခဏ ဖြစ်စေပါတယ်။ ဒါက — ပြန်လုပ်ရမယ့် အလုပ်တွေ နည်းသွားတာကြောင့် — crash ပြီးနောက် recovery ကို ပိုမြန်စေပါတယ်။ ဒါပေမယ့် — dirty data page တွေကို ပိုမကြာခဏ flush လုပ်ရတဲ့ ကုန်ကျစရိတ် တိုးလာမှုနဲ့ ချိန်ညှိ (balance) ရပါမယ်။ [full_page_writes](https://www.postgresql.org/docs/current/runtime-config-wal.html#GUC-FULL-PAGE-WRITES) သတ်မှတ်ထားရင် (default အတိုင်းဆိုရင်) — ထည့်သွင်း စဉ်းစားစရာ နောက်အချက် တစ်ခု ရှိပါသေးတယ်။ Data page ရဲ့ လုံခြုံမှု (consistency) ကို သေချာစေဖို့ — checkpoint တစ်ခုပြီးတိုင်း data page တစ်ခုကို ပထမဆုံး ပြင်ဆင်တဲ့အခါ — page အကြောင်းအရာ တစ်ခုလုံးကို log လုပ်ပါတယ်။ အဲဒီအခြေအနေမှာ — checkpoint ကြားကာလ သေးငယ်ခြင်းက WAL ဆီ ထွက်ရှိတဲ့ ပမာဏကို တိုးစေပြီး — ကြားကာလ သေးငယ်တာကို သုံးခြင်းရဲ့ ရည်မှန်းချက်ကို တစ်စိတ်တစ်ပိုင်း ပျက်ပြယ်စေကာ — ဘယ်လိုပဲဖြစ်ဖြစ် disk I/O ပိုများစေပါတယ်။

Checkpoint တွေက — ပထမ — လက်ရှိ dirty buffer အားလုံးကို ရေးထုတ်ရတာကြောင့်လည်းကောင်း — ဒုတိယ — အထက်မှာ ဆွေးနွေးခဲ့သလို နောက်ဆက်တွဲ WAL traffic အပိုတွေ ဖြစ်စေတာကြောင့်လည်းကောင်း — အတော်လေး ကုန်ကျစရိတ် များပါတယ်။ ဒါကြောင့် checkpointing parameter တွေကို — checkpoint တွေ သိပ်မကြာခဏ မဖြစ်အောင် — လုံလောက်အောင် မြင့်မြင့် သတ်မှတ်တာ ပညာရှိရာ ကျပါတယ်။ သင့် checkpointing parameter တွေအပေါ် ရိုးရှင်းတဲ့ sanity check တစ်ခု လုပ်ချင်ရင် — [checkpoint_warning](https://www.postgresql.org/docs/current/runtime-config-wal.html#GUC-CHECKPOINT-WARNING) parameter ကို သတ်မှတ်နိုင်ပါတယ်။ Checkpoint တွေက `checkpoint_warning` စက္ကန့်ထက် ပိုနီးကပ်စွာ ဖြစ်ရင် — `max_wal_size` ကို တိုးဖို့ အကြံပြုတဲ့ message တစ်ခုကို server log ဆီ ထုတ်ပေးပါလိမ့်မယ်။ ဒီလို message ရံဖန်ရံခါ ပေါ်လာတာက စိုးရိမ်စရာ မဟုတ်ပေမယ့် — မကြာခဏ ပေါ်လာရင်တော့ checkpoint control parameter တွေကို တိုးသင့်ပါတယ်။ ကြီးမားတဲ့ `COPY` transfer တွေလို bulk operation တွေက — `max_wal_size` ကို လုံလောက်အောင် မမြင့်ထားရင် — ဒီလို warning တွေ အများအပြား ပေါ်လာစေနိုင်ပါတယ်။

I/O system ကို page write တွေ တစ်ခါတည်း စုပြီး ရေးချခြင်းနဲ့ လွှမ်းမိုးမခံရအောင် — checkpoint အတွင်း dirty buffer ရေးသားခြင်းကို အချိန်ကာလ တစ်ခုအထိ ဖြန့်ကျက် လုပ်ဆောင်ပါတယ်။ အဲဒီ ကာလကို [checkpoint_completion_target](https://www.postgresql.org/docs/current/runtime-config-wal.html#GUC-CHECKPOINT-COMPLETION-TARGET) က ထိန်းချုပ်ပြီး — ဒါကို checkpoint ကြားကာလ (`checkpoint_timeout` သုံးပြီး configure လုပ်ထားတဲ့) ရဲ့ အပိုင်းအခြား (fraction) အဖြစ် ပေးထားပါတယ်။ `checkpoint_timeout` စက္ကန့်ရဲ့ သတ်မှတ်ထားတဲ့ အပိုင်းအခြား ကုန်ဆုံးချိန် — ဒါမှမဟုတ် `max_wal_size` ကျော်လွန်ခြင်း မတိုင်မီ — နှစ်ခုထဲက အစောဆုံး အချိန်မှာ checkpoint ပြီးစီးအောင် I/O rate ကို ချိန်ညှိပါတယ်။ Default တန်ဖိုး 0.9 နဲ့ဆိုရင် — PostgreSQL က checkpoint တစ်ခုချင်းစီကို — နောက် စီစဉ်ထားတဲ့ checkpoint မတိုင်မီ နည်းနည်း (နောက်ဆုံး checkpoint ရဲ့ ကြာချိန် 90% လောက်မှာ) — ပြီးစီးလိမ့်မယ်လို့ မျှော်လင့်နိုင်ပါတယ်။ ဒါက I/O ကို တတ်နိုင်သလောက် ဖြန့်ကျက်ပေးတာကြောင့် — checkpoint ကြားကာလ တစ်လျှောက်လုံး checkpoint I/O load က တသမတ်တည်း ဖြစ်နေပါတယ်။ ဒါရဲ့ အားနည်းချက်ကတော့ — checkpoint တွေကို ရှည်ကြာစေခြင်းက recovery အချိန်ကို သက်ရောက်စေတာပါ — အကြောင်းကတော့ recovery မှာ ဖြစ်နိုင်တဲ့ အသုံးပြုမှုအတွက် WAL segment တွေ ပိုများများ သိမ်းထားရမှာမို့ပါ။ Recovery အတွက် လိုအပ်တဲ့ အချိန်အပေါ် စိုးရိမ်တဲ့ user တစ်ဦးက — checkpoint တွေ ပိုမကြာခဏ ဖြစ်ပေမယ့် I/O ကို checkpoint ကြားကာလ တစ်လျှောက် ဖြန့်ကျက်နေတုန်းပဲ ဖြစ်စေဖို့ — `checkpoint_timeout` ကို လျှော့ချချင် လျှော့ချနိုင်ပါတယ်။ တနည်းအားဖြင့် — `checkpoint_completion_target` ကို လျှော့နိုင်ပေမယ့် — ဒါက I/O ပိုပြင်းထန်တဲ့ အချိန်တွေ (checkpoint အတွင်း) နဲ့ I/O ပိုနည်းတဲ့ အချိန်တွေ (checkpoint ပြီးသွားပြီး နောက် စီစဉ်ထားတဲ့ checkpoint မတိုင်မီ) ကို ဖြစ်စေမှာမို့ — အကြံပြု မလုပ်ပါဘူး။ `checkpoint_completion_target` ကို 1.0 အထိ မြင့်မြင့် သတ်မှတ်နိုင်ပေမယ့် — checkpoint တွေမှာ dirty buffer ရေးသားခြင်းအပြင် အခြား လုပ်ဆောင်ချက်တွေလည်း ပါဝင်တာကြောင့် — 0.9 (default) ထက် မမြင့်အောင် သတ်မှတ်ဖို့ ပုံမှန်အားဖြင့် အကြံပြုပါတယ်။ 1.0 သတ်မှတ်ချက်က checkpoint တွေ အချိန်မှန် ပြီးစီးမှု မရှိနိုင်ခြေ များပြီး — လိုအပ်တဲ့ WAL segment အရေအတွက် မမျှော်လင့်ဘဲ ပြောင်းလဲမှုကြောင့် performance ဆုံးရှုံးမှု ဖြစ်စေနိုင်ပါတယ်။

Linux နဲ့ POSIX platform တွေမှာ [checkpoint_flush_after](https://www.postgresql.org/docs/current/runtime-config-wal.html#GUC-CHECKPOINT-FLUSH-AFTER) က — checkpoint က ရေးသားတဲ့ OS page တွေကို — configure လုပ်နိုင်တဲ့ byte အရေအတွက် ပြည့်တဲ့နောက် disk ဆီ flush လုပ်ဖို့ အတင်းအကျပ် လုပ်စေနိုင်ပါတယ်။ ဒါ မလုပ်ရင် — ဒီ page တွေက OS ရဲ့ page cache ထဲမှာ ကျန်နေနိုင်ပြီး — checkpoint အဆုံးမှာ `fsync` ထုတ်တဲ့အခါ ရပ်တန့် (stall) မှုကို ဖြစ်စေပါတယ်။ ဒီ setting က transaction latency ကို လျှော့ချဖို့ မကြာခဏ အထောက်အကူ ဖြစ်ပေမယ့် — performance အပေါ် ဆိုးကျိုး (adverse effect) လည်း ရှိနိုင်ပါတယ်; အထူးသဖြင့် [shared_buffers](https://www.postgresql.org/docs/current/runtime-config-resource.html#GUC-SHARED-BUFFERS) ထက် ကြီးပေမယ့် OS ရဲ့ page cache ထက် သေးတဲ့ workload တွေအတွက်ပါ။

`pg_wal` directory ထဲက WAL segment file အရေအတွက်က `min_wal_size`, `max_wal_size` နဲ့ — ယခင် checkpoint cycle တွေမှာ ထုတ်လုပ်ခဲ့တဲ့ WAL ပမာဏ — တို့အပေါ် မူတည်ပါတယ်။ WAL segment file အဟောင်းတွေ မလိုအပ်တော့တဲ့အခါ — ဖယ်ရှားခြင်း ဒါမှမဟုတ် recycle လုပ်ခြင်း (ဆိုလိုတာက — အမှတ်စဉ် (numbered sequence) ထဲက အနာဂတ် segment တွေ ဖြစ်လာအောင် နာမည် ပြန်ပြောင်းခြင်း) လုပ်ပါတယ်။ WAL output rate ရဲ့ ကာလတို အမြင့်ဆုံးအခြေအနေကြောင့် `max_wal_size` ကျော်လွန်သွားရင် — system က ဒီ ကန့်သတ်ချက် အောက် ပြန်ရောက်တဲ့အထိ — မလိုအပ်တဲ့ segment file တွေကို ဖယ်ရှားပါလိမ့်မယ်။ အဲဒီ ကန့်သတ်ချက် အောက်မှာတော့ — system က နောက် checkpoint အထိ ခန့်မှန်းလိုအပ်ချက်ကို ဖြည့်ဆည်းဖို့ လုံလောက်တဲ့ WAL file တွေကို recycle လုပ်ပြီး — ကျန်တာတွေကို ဖယ်ရှားပါတယ်။ ခန့်မှန်းချက်က ယခင် checkpoint cycle တွေမှာ သုံးခဲ့တဲ့ WAL file အရေအတွက်ရဲ့ ရွေ့လျားပျမ်းမျှ (moving average) အပေါ် အခြေခံပါတယ်။ တကယ့် အသုံးပြုမှုက ခန့်မှန်းချက်ကို ကျော်လွန်သွားရင် moving average ကို ချက်ချင်း တိုးပေးတာကြောင့် — ပျမ်းမျှ အသုံးပြုမှုအစား အမြင့်ဆုံး အသုံးပြုမှုကို အတိုင်းအတာ တစ်ခုအထိ လိုက်လျောညီထွေ ဖြစ်စေပါတယ်။ `min_wal_size` က အနာဂတ် အသုံးပြုမှုအတွက် recycle လုပ်တဲ့ WAL file ပမာဏအပေါ် အနိမ့်ဆုံး ကန့်သတ်ချက် သတ်မှတ်ပေးပါတယ်; ဆိုလိုတာက — system အားလပ်နေပြီး WAL အသုံးပြုမှု ခန့်မှန်းချက်က WAL နည်းနည်းပဲ လိုတယ်လို့ ညွှန်ပြနေရင်တောင် — အဲဒီ WAL ပမာဏကို အနာဂတ် အသုံးပြုမှုအတွက် အမြဲ recycle လုပ်ထားပါတယ်။

`max_wal_size` နဲ့ သီးခြားစီ — နောက်ဆုံး [wal_keep_size](https://www.postgresql.org/docs/current/runtime-config-replication.html#GUC-WAL-KEEP-SIZE) megabyte ရှိတဲ့ WAL file တွေအပြင် WAL file တစ်ခု ထပ်ပေါင်း (အမြဲ) သိမ်းထားပါတယ်။ ဒါ့အပြင် — WAL archiving သုံးရင် — segment အဟောင်းတွေကို archive လုပ်ပြီးမှသာ ဖယ်ရှားခြင်း ဒါမှမဟုတ် recycle လုပ်ခြင်း ပြုလုပ်နိုင်ပါတယ်။ WAL archiving က WAL ထုတ်လုပ်တဲ့ အရှိန်နဲ့ မလိုက်နိုင်ရင် — ဒါမှမဟုတ် `archive_command` ဒါမှမဟုတ် `archive_library` က ထပ်ခါတလဲလဲ ပျက်ကွက်ရင် — အခြေအနေ ပြေလည်တဲ့အထိ WAL file အဟောင်းတွေက `pg_wal` ထဲမှာ စုပုံလာပါလိမ့်မယ်။ Replication slot သုံးတဲ့ နှေးကွေး ဒါမှမဟုတ် ပျက်ကွက်နေတဲ့ standby server ကလည်း အလားတူ သက်ရောက်မှု ရှိပါတယ် ([အပိုင်း 26.2.6](/docs/postgresql/warm-standby) ကို ကြည့်ပါ)။ အလားတူပဲ — [WAL summarization](https://www.postgresql.org/docs/current/runtime-config-wal.html#RUNTIME-CONFIG-WAL-SUMMARIZATION) enable ဖြစ်နေရင် — segment အဟောင်းတွေကို summarization လုပ်ပြီးမှသာ သိမ်းထားပါတယ်။

Archive recovery ဒါမှမဟုတ် standby mode မှာ — server က အခါအားလျော်စွာ *restartpoints* (restartpoint များ) ကို လုပ်ဆောင်ပြီး — ဒါတွေက ပုံမှန် လည်ပတ်မှုမှာ checkpoint တွေနဲ့ ဆင်တူပါတယ်: server က သူ့ state အားလုံးကို disk ဆီ အတင်းအကျပ် ရေးပြီး — လုပ်ဆောင်ပြီးသား WAL data ကို ထပ်မံ စစ်ဆေး (scan) ရန် မလိုအပ်ကြောင်း ဖော်ပြဖို့ `pg_control` file ကို update လုပ်ကာ — ပြီးရင် `pg_wal` directory ထဲက WAL segment file အဟောင်းတွေကို recycle လုပ်ပါတယ်။ Restartpoint တွေက checkpoint record တွေမှာပဲ လုပ်ဆောင်နိုင်တာကြောင့် — primary ပေါ်က checkpoint တွေထက် ပိုမကြာခဏ လုပ်ဆောင်လို့ မရပါဘူး။ Restartpoint ကို schedule တစ်ခုကနေ ဒါမှမဟုတ် ပြင်ပ request တစ်ခုကနေ တောင်းဆိုနိုင်ပါတယ်။ [`pg_stat_checkpointer`](/docs/postgresql/monitoring-stats) view ထဲက `restartpoints_timed` counter က ပထမအမျိုးအစားကို ရေတွက်ပြီး `restartpoints_req` က ဒုတိယအမျိုးအစားကို ရေတွက်ပါတယ်။ နောက်ဆုံး လုပ်ဆောင်ခဲ့တဲ့ restartpoint ကတည်းက [checkpoint_timeout](https://www.postgresql.org/docs/current/runtime-config-wal.html#GUC-CHECKPOINT-TIMEOUT) စက္ကန့် အနည်းဆုံး ကုန်ဆုံးပြီးသား ဖြစ်တဲ့အခါ — ဒါမှမဟုတ် ယခင် restartpoint လုပ်ဆောင်ရန် ကြိုးစားမှု ပျက်ကွက်ခဲ့တဲ့အခါ — checkpoint record တစ်ခုဆီ ရောက်တဲ့အခါ schedule အရ restartpoint တစ်ခု စတင်ပါတယ်။ နောက်ဆုံး အခြေအနေမှာတော့ — နောက် restartpoint ကို 15 စက္ကန့်အတွင်း စီစဉ်ပါလိမ့်မယ်။ Restartpoint ကို checkpoint နဲ့ ဆင်တူတဲ့ အကြောင်းရင်းတွေကြောင့် request အရ စတင်ပေမယ့် — အများအားဖြင့် WAL အရွယ်အစားက [max_wal_size](https://www.postgresql.org/docs/current/runtime-config-wal.html#GUC-MAX-WAL-SIZE) ကို ကျော်လွန်တော့မယ့်အခါ ဖြစ်ပါတယ်။ ဒါပေမယ့် — restartpoint ကို လုပ်ဆောင်နိုင်တဲ့ အချိန်အပေါ် ကန့်သတ်ချက်တွေ ရှိတာကြောင့် — recovery အတွင်း `max_wal_size` ကို မကြာခဏ ကျော်လွန်တတ်ပြီး — checkpoint cycle တစ်ခုရဲ့ WAL ပမာဏအထိ ဖြစ်နိုင်ပါတယ်။ (ဘယ်လိုပဲဖြစ်ဖြစ် `max_wal_size` က တင်းကျပ်တဲ့ (hard) ကန့်သတ်ချက် မဟုတ်တာကြောင့် — disk space ကုန်ဆုံးခြင်းကို ရှောင်ဖို့ အမြဲတမ်း လုံလောက်တဲ့ headroom ချန်ထားသင့်ပါတယ်။) [`pg_stat_checkpointer`](/docs/postgresql/monitoring-stats) view ထဲက `restartpoints_done` counter က တကယ် လုပ်ဆောင်ခဲ့ပြီးသား restartpoint တွေကို ရေတွက်ပါတယ်။

တချို့ အခြေအနေတွေမှာ — ဥပမာ ကြီးမားတဲ့ `INSERT` လုပ်နေစဉ်လို — primary ပေါ်က WAL အရွယ်အစား လျင်မြန်စွာ တိုးလာတဲ့အခါ — standby ပေါ်က `restartpoints_req` counter က အမြင့်ဆုံး (peak) ကို တိုးလာတာ ပြနိုင်ပါတယ်။ ဒါက WAL အသုံးပြုမှု တိုးလာမှုကြောင့် restartpoint အသစ် ဖန်တီးဖို့ request တွေကို — နောက်ဆုံး restartpoint ကတည်းက လုံခြုံတဲ့ (safe) checkpoint record ကို standby ပေါ်မှာ ပြန်လည် replay လုပ်ပြီးသား မဖြစ်သေးတာကြောင့် — လုပ်ဆောင်နိုင်ခြင်း မရှိတာကြောင့် ဖြစ်ပါတယ်။ ဒီအပြုအမူက ပုံမှန် ဖြစ်ပြီး — system resource အသုံးပြုမှု တိုးလာခြင်းကို မဖြစ်စေပါဘူး။ Restartpoint နဲ့ ဆက်စပ်တဲ့ counter တွေထဲမှာ `restartpoints_done` counter တစ်ခုတည်းကသာ — သိသာတဲ့ system resource တွေ အသုံးပြုခဲ့ပြီး ဖြစ်ကြောင်း ညွှန်ပြပါတယ်။

အသုံးများတဲ့ internal WAL function နှစ်ခု ရှိပါတယ်: `XLogInsertRecord` နဲ့ `XLogFlush`။ `XLogInsertRecord` ကို shared memory ထဲက WAL buffer တွေထဲ မှတ်တမ်း (record) အသစ် တစ်ခု ထည့်ဖို့ သုံးပါတယ်။ မှတ်တမ်းအသစ်အတွက် နေရာ မရှိရင် — `XLogInsertRecord` က ပြည့်နေတဲ့ WAL buffer တချို့ကို ရေးသား (kernel cache ဆီ ရွှေ့) ရပါမယ်။ ဒါက မလိုလားအပ်ပါ — အကြောင်းကတော့ `XLogInsertRecord` ကို database ရဲ့ အဆင့်နိမ့် ပြောင်းလဲမှု တိုင်း (ဥပမာ row insertion) — သက်ရောက်တဲ့ data page တွေပေါ် exclusive lock ကိုင်ထားချိန်မှာ — သုံးတာမို့ — လုပ်ဆောင်ချက်က တတ်နိုင်သလောက် မြန်ရမှာ ဖြစ်ပါတယ်။ ပိုဆိုးတာက — WAL buffer ရေးသားခြင်းက WAL segment အသစ် ဖန်တီးခြင်းကိုလည်း အတင်းအကျပ် ဖြစ်စေနိုင်ပြီး — ဒါက အချိန် ပိုယူပါသေးတယ်။ ပုံမှန်အားဖြင့် — WAL buffer တွေကို `XLogFlush` request တစ်ခုက ရေးသားပြီး flush လုပ်သင့်ပြီး — ဒီ request ကို — အများစု — transaction commit ချိန်မှာ လုပ်ပြီး — transaction record တွေကို အမြဲတမ်း သိုလှောင်ရာဆီ flush ဖြစ်ကြောင်း သေချာစေပါတယ်။ WAL output မြင့်တဲ့ system တွေမှာ — `XLogInsertRecord` က ရေးသားခြင်း မလုပ်ရအောင် `XLogFlush` request တွေ လုံလောက်အောင် မကြာခဏ ဖြစ်ပေါ်ခြင်း မရှိနိုင်ပါဘူး။ အဲဒီလို system တွေမှာ [wal_buffers](https://www.postgresql.org/docs/current/runtime-config-wal.html#GUC-WAL-BUFFERS) parameter ကို ပြင်ဆင်ခြင်းအားဖြင့် WAL buffer အရေအတွက်ကို တိုးသင့်ပါတယ်။ [full_page_writes](https://www.postgresql.org/docs/current/runtime-config-wal.html#GUC-FULL-PAGE-WRITES) သတ်မှတ်ထားပြီး system အလွန် အလုပ်များနေတဲ့အခါ — `wal_buffers` ကို မြင့်မြင့် သတ်မှတ်ခြင်းက checkpoint တစ်ခုပြီးတိုင်း ချက်ချင်း လာမယ့် ကာလအတွင်း response time တွေကို ညီညာစေဖို့ အထောက်အကူ ဖြစ်ပါလိမ့်မယ်။

[commit_delay](https://www.postgresql.org/docs/current/runtime-config-wal.html#GUC-COMMIT-DELAY) parameter က — group commit leader process တစ်ခုက `XLogFlush` အတွင်း lock တစ်ခု ရယူပြီးနောက် — group commit follower တွေ leader နောက်မှာ တန်းစီနေစဉ် — ဘယ်နှစ် microsecond အိပ်မလဲ ဆိုတာကို သတ်မှတ်ပါတယ်။ ဒီ ကြန့်ကြာမှု (delay) က အခြား server process တွေက သူတို့ရဲ့ commit record တွေကို WAL buffer တွေထဲ ထည့်နိုင်စေပြီး — အားလုံးကို leader ရဲ့ နောက်ဆုံး sync လုပ်ဆောင်ချက်က flush လုပ်ပေးပါလိမ့်မယ်။ [fsync](https://www.postgresql.org/docs/current/runtime-config-wal.html#GUC-FSYNC) enable မဖြစ်ရင် — ဒါမှမဟုတ် လက်ရှိ active transaction တွေထဲမှာ အခြား session [commit_siblings](https://www.postgresql.org/docs/current/runtime-config-wal.html#GUC-COMMIT-SIBLINGS) ခုထက် နည်းနေရင် — အိပ်ခြင်း ဖြစ်မှာ မဟုတ်ပါဘူး; ဒါက အခြား session မကြာမီ commit လုပ်နိုင်ခြေ နည်းတဲ့အခါ အိပ်ခြင်းကို ရှောင်ပါတယ်။ တချို့ platform တွေမှာ — sleep request တစ်ခုရဲ့ resolution က ဆယ် millisecond ဖြစ်တာကြောင့် — 1 နဲ့ 10000 microsecond ကြားက သုည မဟုတ်တဲ့ `commit_delay` setting တိုင်းက အကျိုးသက်ရောက်မှု တူပါတယ် ဆိုတာ သတိပြုပါ။ ဒါ့အပြင် — တချို့ platform တွေမှာ sleep လုပ်ဆောင်ချက်တွေက parameter က တောင်းဆိုတာထက် အနည်းငယ် ပိုကြာနိုင်ပါတယ်။

`commit_delay` ရဲ့ ရည်ရွယ်ချက်က — flush လုပ်ဆောင်ချက် တစ်ခုချင်းစီရဲ့ ကုန်ကျစရိတ်ကို — တစ်ပြိုင်နက် commit လုပ်နေတဲ့ transaction တွေအကြား ခွဲဝေပေးဖို့ (transaction latency ကို ပေးဆပ်ရနိုင်ပေမယ့်) ဖြစ်တာကြောင့် — setting ကို ပညာရှိစွာ ရွေးချယ်နိုင်မီ — အဲဒီ ကုန်ကျစရိတ်ကို အရေအတွက် သတ်မှတ် (quantify) ဖို့ လိုပါတယ်။ အဲဒီ ကုန်ကျစရိတ် မြင့်လေလေ — `commit_delay` က transaction throughput ကို တိုးမြှင့်ရာမှာ ပိုထိရောက်လေလေ ဖြစ်ပါတယ် (အထိ အချက်တစ်ခုအထိ)။ WAL flush လုပ်ဆောင်ချက် တစ်ကြိမ်ရဲ့ ပျမ်းမျှ အချိန်ကို microsecond နဲ့ တိုင်းတာဖို့ [pg_test_fsync](https://www.postgresql.org/docs/current/pgtestfsync.html) program ကို သုံးနိုင်ပါတယ်။ Program က တစ်ကြိမ် 8kB write လုပ်ဆောင်ချက်ပြီးနောက် flush လုပ်ဖို့ ကြာတယ်လို့ အစီရင်ခံတဲ့ ပျမ်းမျှ အချိန်ရဲ့ တစ်ဝက်တန်ဖိုးက `commit_delay` အတွက် မကြာခဏ အတိကျဆုံး setting ဖြစ်တာကြောင့် — ဒီတန်ဖိုးကို — သီးခြား workload တစ်ခုအတွက် optimize လုပ်တဲ့အခါ — စတင်ရန် အချက်အဖြစ် အကြံပြုပါတယ်။ `commit_delay` ကို tuning လုပ်ခြင်းက WAL ကို high-latency rotating disk တွေပေါ် သိမ်းထားတဲ့အခါ အထူး အသုံးဝင်ပေမယ့် — solid-state drive ဒါမှမဟုတ် battery-backed write cache ပါတဲ့ RAID array လို sync အချိန် အလွန်မြန်တဲ့ storage media တွေမှာတောင် အကျိုးကျေးဇူးတွေ သိသာနိုင်ပါတယ်; ဒါပေမယ့် — ဒါကို ကိုယ်စားပြုတဲ့ workload တစ်ခုနဲ့ အမှန်တကယ် စမ်းသပ် သင့်ပါတယ်။ ဒီလို အခြေအနေတွေမှာ `commit_siblings` တန်ဖိုး မြင့်မြင့် သုံးသင့်ပြီး — higher latency media တွေမှာတော့ `commit_siblings` တန်ဖိုး သေးသေး သုံးတာ မကြာခဏ အထောက်အကူ ဖြစ်ပါတယ်။ `commit_delay` setting အလွန်မြင့်ခြင်းက transaction latency ကို — စုစုပေါင်း transaction throughput ကျဆင်းသွားလောက်အောင် — အလွန်အကျွံ တိုးစေနိုင်ခြေ အတော်အသင့် ရှိတယ်ဆိုတာ သတိပြုပါ။

`commit_delay` ကို သုည (default) သတ်မှတ်တဲ့အခါ — group commit တစ်မျိုး ဖြစ်ပေါ်နိုင်သေးပေမယ့် — group တစ်ခုချင်းစီမှာ — ယခင် flush လုပ်ဆောင်ချက် (ရှိရင်) ဖြစ်ပေါ်နေတဲ့ အချိန်ကာလ (window) အတွင်း သူတို့ရဲ့ commit record တွေကို flush လုပ်ဖို့ လိုတဲ့အထိ ရောက်တဲ့ session တွေနဲ့ပဲ ဖွဲ့စည်းပါလိမ့်မယ်။ Client အရေအတွက် များတဲ့အခါ “gangway effect” တစ်မျိုး ဖြစ်ပေါ်တတ်တာကြောင့် — `commit_delay` သုည ဖြစ်နေရင်တောင် group commit ရဲ့ အကျိုးသက်ရောက်မှုတွေ သိသာလာပြီး — ဒါကြောင့် `commit_delay` ကို ပြတ်ပြတ်သားသား သတ်မှတ်ခြင်းက အထောက်အကူ နည်းလာတတ်ပါတယ်။ `commit_delay` သတ်မှတ်ခြင်းက (1) တစ်ပြိုင်နက် commit လုပ်နေတဲ့ transaction တွေ ရှိတဲ့အခါ — နဲ့ (2) throughput က commit rate ကြောင့် အတိုင်းအတာ တစ်ခုအထိ ကန့်သတ်ခံရတဲ့အခါ — မှသာ အထောက်အကူ ဖြစ်နိုင်ပါတယ်; ဒါပေမယ့် — rotational latency မြင့်တဲ့အခါ — ဒီ setting က client နှစ်ခုအထိ (ဆိုလိုတာက — commit လုပ်နေတဲ့ client တစ်ခုနဲ့ sibling transaction တစ်ခု) နဲ့တင် transaction throughput ကို တိုးမြှင့်ရာမှာ ထိရောက်နိုင်ပါတယ်။

[wal_sync_method](https://www.postgresql.org/docs/current/runtime-config-wal.html#GUC-WAL-SYNC-METHOD) parameter က PostgreSQL က — WAL update တွေကို disk ဆီ အတင်းအကျပ် ထုတ်ပို့ဖို့ — kernel ကို ဘယ်လို တောင်းဆိုမလဲ ဆိုတာကို သတ်မှတ်ပါတယ်။ Option အားလုံးက ယုံကြည်စိတ်ချရမှုအရ တူသင့်ပါတယ် — `fsync_writethrough` က ခြွင်းချက်ဖြစ်ပြီး — ဒါက တခြား option တွေ မလုပ်တဲ့အခါတွေမှာတောင် disk cache ကို flush လုပ်ရန် တခါတရံ အတင်းအကျပ် လုပ်စေနိုင်ပါတယ်။ ဒါပေမယ့် — ဘယ် option က အမြန်ဆုံးလဲ ဆိုတာက platform အလိုက် ကွဲပြားပါတယ်။ [pg_test_fsync](https://www.postgresql.org/docs/current/pgtestfsync.html) program ကို သုံးပြီး မတူညီတဲ့ option တွေရဲ့ အရှိန်ကို စမ်းသပ်နိုင်ပါတယ်။ `fsync` ပိတ်ထားရင် ဒီ parameter က အရေးမပါဘူး ဆိုတာ သတိပြုပါ။

[wal_debug](https://www.postgresql.org/docs/current/runtime-config-developer.html#GUC-WAL-DEBUG) configuration parameter ကို enable လုပ်ခြင်း (PostgreSQL ကို ဒါအတွက် ထောက်ပံ့မှုနဲ့ compile လုပ်ထားတယ် ဆိုရင်) က — `XLogInsertRecord` နဲ့ `XLogFlush` WAL ခေါ်ဆိုမှု တစ်ခုချင်းစီကို server log ဆီ log လုပ်စေပါလိမ့်မယ်။ ဒီ option ကို အနာဂတ်မှာ ပိုယေဘုယျကျတဲ့ ယန္တရား တစ်ခုနဲ့ အစားထိုးနိုင်ပါတယ်။

WAL data ကို disk ဆီ ရေးသားဖို့ internal function နှစ်ခု ရှိပါတယ်: `XLogWrite` နဲ့ `issue_xlog_fsync`။ [track_wal_io_timing](https://www.postgresql.org/docs/current/runtime-config-statistics.html#GUC-TRACK-WAL-IO-TIMING) enable ဖြစ်တဲ့အခါ — `XLogWrite` က WAL data ရေးသားတဲ့ စုစုပေါင်း အချိန်နဲ့ `issue_xlog_fsync` က WAL data ကို disk ဆီ sync လုပ်တဲ့ စုစုပေါင်း အချိန်ကို — [pg_stat_io](/docs/postgresql/monitoring-stats) ထဲမှာ `object` အတွက် `wal` အနေနဲ့ — အသီးသီး `write_time` နဲ့ `fsync_time` အဖြစ် ရေတွက်ပါတယ်။ `XLogWrite` ကို — ပုံမှန်အားဖြင့် — `XLogInsertRecord` (WAL buffer တွေထဲ မှတ်တမ်းအသစ်အတွက် နေရာ မရှိတဲ့အခါ)၊ `XLogFlush` နဲ့ WAL writer တို့က ခေါ်ပြီး — WAL buffer တွေကို disk ဆီ ရေးသားဖို့နဲ့ `issue_xlog_fsync` ကို ခေါ်ဖို့ လုပ်ပါတယ်။ `issue_xlog_fsync` ကို — ပုံမှန်အားဖြင့် — `XLogWrite` က ခေါ်ပြီး — WAL file တွေကို disk ဆီ sync လုပ်ပါတယ်။ `wal_sync_method` က `open_datasync` ဒါမှမဟုတ် `open_sync` ဖြစ်ရင် — `XLogWrite` ထဲက write လုပ်ဆောင်ချက်က ရေးသားထားတဲ့ WAL data ကို disk ဆီ sync ဖြစ်ကြောင်း အာမခံပြီး `issue_xlog_fsync` က ဘာမှ မလုပ်ပါဘူး။ `wal_sync_method` က `fdatasync`, `fsync`, ဒါမှမဟုတ် `fsync_writethrough` ဖြစ်ရင် — write လုပ်ဆောင်ချက်က WAL buffer တွေကို kernel cache ဆီ ရွှေ့ပြီး — `issue_xlog_fsync` က သူတို့ကို disk ဆီ sync လုပ်ပါတယ်။ `track_wal_io_timing` ရဲ့ setting ဘယ်လိုပဲ ဖြစ်ပါစေ — `XLogWrite` က WAL data ရေးသားတဲ့ အကြိမ်အရေအတွက်နဲ့ `issue_xlog_fsync` က WAL data ကို disk ဆီ sync လုပ်တဲ့ အကြိမ်အရေအတွက်ကို — `pg_stat_io` ထဲမှာ `object` အတွက် `wal` အနေနဲ့ — အသီးသီး `writes` နဲ့ `fsyncs` အဖြစ် ရေတွက်ပါတယ်။

[recovery_prefetch](https://www.postgresql.org/docs/current/runtime-config-wal.html#GUC-RECOVERY-PREFETCH) parameter ကို — PostgreSQL ရဲ့ buffer pool ထဲမှာ လက်ရှိ မရှိပေမယ့် မကြာမီ လိုအပ်လာမယ့် disk block တွေကို ဖတ်ရှုဖို့ kernel ကို ညွှန်ကြားခြင်းအားဖြင့် — recovery အတွင်း I/O စောင့်ဆိုင်းချိန်တွေကို လျှော့ချဖို့ သုံးနိုင်ပါတယ်။ [maintenance_io_concurrency](https://www.postgresql.org/docs/current/runtime-config-resource.html#GUC-MAINTENANCE-IO-CONCURRENCY) နဲ့ [wal_decode_buffer_size](https://www.postgresql.org/docs/current/runtime-config-wal.html#GUC-WAL-DECODE-BUFFER-SIZE) setting တွေက prefetching concurrency နဲ့ အကွာအဝေးကို အသီးသီး ကန့်သတ်ပါတယ်။ ပုံမှန်အားဖြင့် — ဒါကို `try` သတ်မှတ်ထားပြီး — read-ahead အကြံပြုချက် (advice) ထုတ်ခြင်းကို ထောက်ပံ့တဲ့ system တွေမှာ ဒီ feature ကို enable လုပ်ပေးပါတယ်။
