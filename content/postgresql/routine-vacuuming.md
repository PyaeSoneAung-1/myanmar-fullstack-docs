## 24.1. Routine Vacuuming (ပုံမှန် vacuuming ပြုလုပ်ခြင်း)

- **24.1.1. Vacuuming Basics (vacuuming အခြေခံများ)**
- **24.1.2. Recovering Disk Space (disk space ပြန်လည် ရယူခြင်း)**
- **24.1.3. Updating Planner Statistics (planner statistics များ update လုပ်ခြင်း)**
- **24.1.4. Updating the Visibility Map (visibility map update လုပ်ခြင်း)**

- **24.1.6. The Autovacuum Daemon (Autovacuum Daemon)**

PostgreSQL databases တွေက *vacuuming* လို့ ခေါ်တဲ့ — အခါအားလျော်စွာ ပြုလုပ်ပေးရတဲ့ — maintenance (ထိန်းသိမ်းမှု) တစ်ခု လိုအပ်ပါတယ်။ Installation (တပ်ဆင်မှု) အများအပြားအတွက်ဆိုရင် — [အပိုင်း 24.1.6](/docs/postgresql/routine-vacuuming) မှာ ဖော်ပြထားတဲ့ *autovacuum daemon* က vacuuming ကို လုပ်ဆောင်ပေးတာနဲ့ပဲ လုံလောက်ပါတယ်။ သင့်ရဲ့ အခြေအနေအတွက် အကောင်းဆုံး ရလဒ်တွေ ရဖို့ — အဲဒီမှာ ဖော်ပြထားတဲ့ autovacuuming parameters တွေကို ညှိပြင်ဖို့ လိုအပ်နိုင်ပါတယ်။ Database administrators တချို့ကတော့ — daemon ရဲ့ လုပ်ဆောင်ချက်တွေကို — cron ဒါမှမဟုတ် Task Scheduler scripts တွေနဲ့ အချိန်ဇယား အတိုင်း ပုံမှန် execute လုပ်လေ့ ရှိတဲ့ — manually-managed (လူကိုယ်တိုင် စီမံခန့်ခွဲသော) `VACUUM` commands တွေနဲ့ ဖြည့်စွက် ဒါမှမဟုတ် အစားထိုး ချင်ကြပါတယ်။ Manually-managed vacuuming ကို မှန်ကန်စွာ သတ်မှတ်ဖို့ဆိုရင် — နောက် subsection အနည်းငယ်မှာ ဆွေးနွေးထားတဲ့ ကိစ္စရပ်တွေကို နားလည်ဖို့ မရှိမဖြစ် လိုအပ်ပါတယ်။ Autovacuuming ကိုပဲ အားကိုးတဲ့ administrators တွေကလည်း — autovacuuming ကို နားလည်ပြီး ညှိပြင်နိုင်ဖို့အတွက် — ဒီအကြောင်းအရာတွေကို အကြမ်းဖျင်း ဖတ်ကြည့်ချင်နိုင်ပါတယ်။

### 24.1.1. Vacuuming Basics (vacuuming အခြေခံများ)

PostgreSQL ရဲ့ [`VACUUM`](/docs/postgresql/sql-vacuum) command က table တစ်ခုချင်းစီကို အကြောင်းရင်း များစွာကြောင့် ပုံမှန် process လုပ်ပေးရပါတယ်:

1. Updated ဒါမှမဟုတ် deleted လုပ်လိုက်တဲ့ row တွေ သိမ်းပိုက်ထားတဲ့ disk space ကို ပြန်လည် ရယူရန် ဒါမှမဟုတ် ပြန်လည် အသုံးပြုရန်။
2. PostgreSQL query planner သုံးတဲ့ data statistics တွေကို update လုပ်ရန်။
3. [index-only scans](/docs/postgresql/indexes-index-only-scans) တွေကို မြန်ဆန်စေတဲ့ visibility map ကို update လုပ်ရန်။
4. *Transaction ID wraparound* (transaction ID ပြန်ရစ်ခြင်း) ဒါမှမဟုတ် *multixact ID wraparound* (multixact ID ပြန်ရစ်ခြင်း) ကြောင့် အလွန် အသက်ကြီးတဲ့ data တွေ ဆုံးရှုံးမှုကနေ ကာကွယ်ရန်။

ဒီအကြောင်းရင်း တစ်ခုချင်းစီကလည်း — အောက်က subsection တွေမှာ ရှင်းပြထားသလိုပဲ — ကြိမ်နှုန်းနဲ့ အတိုင်းအတာ အမျိုးမျိုး ရှိတဲ့ `VACUUM` operations တွေကို လုပ်ဆောင်ဖို့ ညွှန်ပြနေပါတယ်။

`VACUUM` မှာ variant (ပုံစံကွဲ) နှစ်မျိုး ရှိပါတယ်: standard `VACUUM` နဲ့ `VACUUM FULL` ပါ။ `VACUUM FULL` က disk space ပိုပြီး ပြန်လည် ရယူနိုင်ပေမယ့် — အများကြီး ပိုနှေးကွေးစွာ run ပါတယ်။ ဒါ့အပြင် — standard ပုံစံ `VACUUM` က production database operations တွေနဲ့ အပြိုင် run လို့ ရပါတယ်။ (`SELECT`, `INSERT`, `UPDATE` နဲ့ `DELETE` လို commands တွေက ပုံမှန်အတိုင်း ဆက်လက် လုပ်ဆောင်နေမှာ ဖြစ်ပေမယ့် — table တစ်ခုကို vacuum လုပ်နေတဲ့ အချိန်အတောအတွင်းမှာ — `ALTER TABLE` လို commands တွေနဲ့ — table တစ်ခုရဲ့ definition ကိုတော့ ပြုပြင်မွမ်းမံလို့ မရနိုင်ပါဘူး။) `VACUUM FULL` က သူ အလုပ်လုပ်နေတဲ့ table ပေါ်မှာ `ACCESS EXCLUSIVE` lock တစ်ခု လိုအပ်တာမို့ — table ကို တခြား အသုံးပြုမှုတွေနဲ့ အပြိုင် လုပ်ဆောင်လို့ မရပါဘူး။ ဒါကြောင့် — ယေဘုယျအားဖြင့် — administrators တွေက standard `VACUUM` ကို သုံးပြီး — `VACUUM FULL` ကို ရှောင်ရှားဖို့ ကြိုးစားသင့်ပါတယ်။

`VACUUM` က သိသိသာသာ များပြားတဲ့ I/O traffic ကို ဖန်တီးပြီး — တခြား active sessions တွေရဲ့ performance ကို ဆိုးရွားစေနိုင်ပါတယ်။ Background vacuuming ရဲ့ performance သက်ရောက်မှုကို လျှော့ချဖို့ ညှိပြင်လို့ ရတဲ့ configuration parameters တွေ ရှိပါတယ် — [အပိုင်း 19.10.2](https://www.postgresql.org/docs/current/runtime-config-vacuum.html#RUNTIME-CONFIG-RESOURCE-VACUUM-COST) ကို ကြည့်ပါ။

### 24.1.2. Recovering Disk Space (disk space ပြန်လည် ရယူခြင်း)

PostgreSQL မှာ row တစ်ခုကို `UPDATE` ဒါမှမဟုတ် `DELETE` လုပ်တာက — row ရဲ့ version အဟောင်းကို ချက်ချင်း ဖယ်ရှားမပေးပါဘူး။ ဒီနည်းလမ်းက multiversion concurrency control (MVCC — row version အမျိုးမျိုးကို ထိန်းသိမ်းထားတဲ့ concurrency control နည်းပညာ — [အခန်း 13](https://www.postgresql.org/docs/current/mvcc.html)) ရဲ့ အကျိုးကျေးဇူးတွေ ရရှိဖို့ မရှိမဖြစ် လိုအပ်ပါတယ်: row version က — တခြား transactions တွေအတွက် မြင်နိုင်ခြေ ရှိနေသရွေ့ — ဖျက်ပစ်လို့ မရပါဘူး။ ဒါပေမယ့် — နောက်ဆုံးမှာတော့ — outdated (ခေတ်နောက်ကျ) ဖြစ်နေတဲ့ ဒါမှမဟုတ် deleted လုပ်ထားတဲ့ row version တစ်ခုက ဘယ် transaction အတွက်မှ အရေးပါတော့မှာ မဟုတ်ပါဘူး။ သူ သိမ်းပိုက်ထားတဲ့ space ကို — disk space လိုအပ်ချက် အကန့်အသတ်မရှိ ကြီးထွားမသွားအောင် — row အသစ်တွေက ပြန်လည် အသုံးပြုနိုင်ဖို့ ပြန်လည် ရယူပေးရပါတယ်။ ဒါကို `VACUUM` run ခြင်းဖြင့် လုပ်ဆောင်ပါတယ်။

`VACUUM` ရဲ့ standard ပုံစံက tables နဲ့ indexes တွေထဲက dead row versions (ဖျက်လိုက်သော သို့မဟုတ် update ကြောင့် အသုံးမလိုတော့သော row version များ) တွေကို ဖယ်ရှားပြီး — space ကို နောင်အတွက် ပြန်လည် အသုံးပြုနိုင်အောင် အမှတ်အသား လုပ်ပေးပါတယ်။ ဒါပေမယ့် — table တစ်ခုရဲ့ အဆုံးမှာ ရှိတဲ့ page တစ်ခု ဒါမှမဟုတ် တစ်ခုထက်ပိုတဲ့ pages တွေ လုံးဝ လွတ်သွားပြီး — exclusive table lock တစ်ခုကို လွယ်ကူစွာ ရယူနိုင်တဲ့ အထူး အခြေအနေမျိုးကလွဲရင် — space ကို operating system ဆီ ပြန်ပေးမှာ မဟုတ်ပါဘူး။ ဆန့်ကျင်ဘက်အနေနဲ့ — `VACUUM FULL` ကတော့ — dead space မပါတဲ့ table file ရဲ့ version အသစ် တစ်ခုလုံးကို ရေးသားခြင်းအားဖြင့် tables တွေကို ပြင်းပြင်းထန်ထန် compact (ကျစ်လျစ်စွာ စုစည်း) လုပ်ပေးပါတယ်။ ဒါက table ရဲ့ အရွယ်အစားကို အနည်းဆုံး ဖြစ်စေပေမယ့် — အချိန် အတော်ကြာ ကြာနိုင်ပါတယ်။ ဒါ့အပြင် — operation ပြီးမြောက်တဲ့အထိ — table ရဲ့ မိတ္တူအသစ်အတွက် — ထပ်ဆောင်း disk space လည်း လိုအပ်ပါတယ်။

Routine vacuuming (ပုံမှန် vacuuming) ရဲ့ ရည်မှန်းချက်ကတော့ — `VACUUM FULL` မလိုအပ်အောင် — standard `VACUUM` တွေကို မကြာခဏ လုံလောက်စွာ လုပ်ဆောင်ဖို့ ဖြစ်ပါတယ်။ Autovacuum daemon က ဒီနည်းအတိုင်း အလုပ်လုပ်ဖို့ ကြိုးစားပြီး — တကယ်တော့ — `VACUUM FULL` ကို ဘယ်တော့မှ ထုတ်ပြန်မှာ မဟုတ်ပါဘူး။ ဒီနည်းလမ်းမှာ — အယူအဆက tables တွေကို သူတို့ရဲ့ အနည်းဆုံး အရွယ်အစားမှာ ထားဖို့ မဟုတ်ဘဲ — disk space ရဲ့ steady-state (တည်ငြိမ်သော အခြေအနေ) အသုံးပြုမှုကို ထိန်းသိမ်းဖို့ ဖြစ်ပါတယ်: table တစ်ခုစီက — သူ့ရဲ့ အနည်းဆုံး အရွယ်အစားနဲ့ ညီမျှတဲ့ space ပေါင်း — vacuum run တွေကြားမှာ သုံးစွဲသွားတဲ့ space ပမာဏလောက်ကို သိမ်းပိုက်ထားပါတယ်။ `VACUUM FULL` က table တစ်ခုကို သူ့ရဲ့ အနည်းဆုံး အရွယ်အစားဆီ ပြန်ကျုံ့စေပြီး disk space ကို operating system ဆီ ပြန်ပေးဖို့ သုံးနိုင်ပေမယ့် — table က နောင်မှာ ထပ်ကြီးထွားမယ်ဆိုရင် ဒါက အကျိုးမထူးပါဘူး။ ဒါကြောင့် — heavily-updated (update များပြားစွာ ပြုလုပ်နေသော) tables တွေကို ထိန်းသိမ်းရာမှာ — မကြာခဏ မဟုတ်တဲ့ `VACUUM FULL` runs တွေထက် — သင့်တင့်လောက်တဲ့ ကြိမ်နှုန်းနဲ့ လုပ်တဲ့ standard `VACUUM` runs တွေက ပိုကောင်းတဲ့ နည်းလမ်း ဖြစ်ပါတယ်။

Administrators တချို့က vacuuming ကို ကိုယ်တိုင် အချိန်ဇယား ဆွဲဖို့ နှစ်သက်ကြပါတယ် — ဥပမာ — load နည်းတဲ့အချိန် ညဘက်မှာ အလုပ်အားလုံးကို လုပ်တာမျိုးပါ။ ပုံသေ အချိန်ဇယား အတိုင်း vacuuming လုပ်တာရဲ့ အခက်အခဲကတော့ — table တစ်ခုမှာ update လုပ်ဆောင်မှု မမျှော်လင့်ဘဲ မြင့်တက်လာတဲ့ spike (ရုတ်တရက် မြင့်တက်မှု) တစ်ခု ရှိခဲ့ရင် — space ပြန်လည် ရယူဖို့ `VACUUM FULL` တကယ် လိုအပ်တဲ့အထိ — table က bloat (ဖောင်းပွ) သွားနိုင်လို့ပါ။ Autovacuum daemon ကို သုံးတာက ဒီပြဿနာကို သက်သာစေပါတယ် — အကြောင်းကတော့ daemon က update လုပ်ဆောင်မှုကို တုံ့ပြန်ပြီး vacuuming ကို ပြောင်းလဲနေတဲ့ ပုံစံ (dynamically) နဲ့ အချိန်ဇယား ဆွဲလို့ပါ။ သင့်မှာ အလွန် ခန့်မှန်းလို့ ရတဲ့ (extremely predictable) workload တစ်ခု မရှိဘူးဆိုရင် — daemon ကို လုံးဝ disable လုပ်တာက မပညာရှိပါဘူး။ ဖြစ်နိုင်တဲ့ အပေးအယူ တစ်ခုကတော့ — daemon ရဲ့ parameters တွေကို — ပုံမှန် မဟုတ်တဲ့ ပြင်းထန်တဲ့ update လုပ်ဆောင်မှုကိုပဲ တုံ့ပြန်လာအောင် သတ်မှတ်ပြီး — load ပုံမှန် ဖြစ်တဲ့အခါ — အလုပ်ရဲ့ အများစုကို စီစဉ်ထားတဲ့ `VACUUM` တွေက လုပ်ဆောင်ဖို့ မျှော်လင့်ထားရင်း — အခြေအနေတွေ ထိန်းမရအောင် မဖြစ်အောင် ထိန်းထားတာမျိုးပါ။

Autovacuum မသုံးတဲ့သူတွေအတွက်တော့ — ပုံမှန် နည်းလမ်းတစ်ခုကတော့ — load နည်းတဲ့ အချိန်ကာလ အတွင်း တစ်နေ့ တစ်ကြိမ် — database တစ်ခုလုံး (database-wide) `VACUUM` တစ်ခုကို အချိန်ဇယား ဆွဲပြီး — လိုအပ်သလို — heavily-updated tables တွေကို ပိုမကြာခဏ vacuum လုပ်တာနဲ့ ဖြည့်စွက်တာ ဖြစ်ပါတယ်။ (Update နှုန်း အလွန် မြင့်တဲ့ installation တချို့က — သူတို့ရဲ့ အလုပ်အများဆုံး (busiest) tables တွေကို မိနစ် အနည်းငယ်တိုင်း အကြိမ်တိုင်း vacuum လုပ်ကြပါတယ်။) Cluster တစ်ခုထဲမှာ databases အများအပြား ရှိရင် — database တစ်ခုချင်းစီကိုပါ `VACUUM` လုပ်ဖို့ မမေ့ပါနဲ့; [vacuumdb](https://www.postgresql.org/docs/current/app-vacuumdb.html) ဆိုတဲ့ program က အထောက်အကူ ဖြစ်နိုင်ပါတယ်။

> **အကြံပြုချက်:** Table တစ်ခုမှာ — ကြီးမားတဲ့ update ဒါမှမဟုတ် delete လုပ်ဆောင်မှုကြောင့် — dead row versions အများအပြား ပါဝင်နေရင် — Plain `VACUUM` က ကျေနပ်လောက်မှာ မဟုတ်ပါဘူး။ ဒီလို table တစ်ခု ရှိပြီး — သူ သိမ်းပိုက်ထားတဲ့ ပိုနေတဲ့ disk space ကို ပြန်လည် ရယူချင်တယ်ဆိုရင် — `VACUUM FULL` ကို သုံးဖို့ ဒါမှမဟုတ် — တနည်းအားဖြင့် — [`CLUSTER`](/docs/postgresql/sql-cluster) ဒါမှမဟုတ် [`ALTER TABLE`](/docs/postgresql/sql-altertable) ရဲ့ table-rewriting (table ကို ပြန်လည် ရေးသားသော) variant တစ်ခုခုကို သုံးဖို့ လိုအပ်ပါလိမ့်မယ်။ ဒီ commands တွေက table ရဲ့ မိတ္တူအသစ် တစ်ခုလုံးကို ပြန်လည် ရေးသားပြီး — ၎င်းအတွက် indexes အသစ်တွေကိုပါ တည်ဆောက်ပါတယ်။ ဒီ options တွေ အားလုံးက `ACCESS EXCLUSIVE` lock တစ်ခု လိုအပ်ပါတယ်။ ဒါ့အပြင် — table နဲ့ indexes ရဲ့ မိတ္တူအဟောင်းတွေကို — အသစ်တွေ ပြီးမြောက်တဲ့အထိ — မလွှတ်ပေးနိုင်တာမို့ — ယာယီအနေနဲ့ — table ရဲ့ အရွယ်အစားနဲ့ ခန့်မှန်းခြေ ညီမျှတဲ့ — ထပ်ဆောင်း disk space ကိုလည်း သုံးစွဲတယ်ဆိုတာ သတိပြုပါ။

> **အကြံပြုချက်:** သင့်မှာ — တစ်ခုလုံးရဲ့ အကြောင်းအရာတွေကို အခါအားလျော်စွာ ဖျက်ပစ်လေ့ ရှိတဲ့ table တစ်ခု ရှိရင် — `DELETE` ပြီးတော့ `VACUUM` လုပ်တာထက် — [`TRUNCATE`](/docs/postgresql/sql-truncate) နဲ့ လုပ်ဖို့ စဉ်းစားပါ။ `TRUNCATE` က table ရဲ့ အကြောင်းအရာ တစ်ခုလုံးကို ချက်ချင်း ဖယ်ရှားပြီး — အခု အသုံးမပြုတော့တဲ့ disk space ကို ပြန်လည် ရယူဖို့ — နောက်ပိုင်း `VACUUM` ဒါမှမဟုတ် `VACUUM FULL` တစ်ခု လိုအပ်မှာ မဟုတ်ပါဘူး။ အားနည်းချက်ကတော့ — တင်းကျပ်တဲ့ MVCC semantics တွေကို ချိုးဖောက်လိုက်တာ ဖြစ်ပါတယ်။

### 24.1.3. Updating Planner Statistics (planner statistics များ update လုပ်ခြင်း)

PostgreSQL query planner က — queries တွေအတွက် ကောင်းမွန်တဲ့ plans တွေ ထုတ်လုပ်နိုင်ဖို့ — tables တွေရဲ့ အကြောင်းအရာတွေအကြောင်း statistical information (ကိန်းဂဏန်း အချက်အလက်များ) ပေါ်မှာ မှီခိုပါတယ်။ ဒီ statistics တွေကို [`ANALYZE`](/docs/postgresql/sql-analyze) command က စုဆောင်းပေးပြီး — အဲဒါကို သူ့ဘာသာ သပ်သပ်စီ ခေါ်နိုင်သလို — `VACUUM` ရဲ့ optional အဆင့်တစ်ခုအနေနဲ့လည်း ခေါ်နိုင်ပါတယ်။ ကျိုးကြောင်းဆီလျော်လောက်အောင် တိကျတဲ့ statistics တွေ ရှိဖို့က အရေးကြီးပါတယ် — မဟုတ်ရင် — plans တွေ ညံ့ဖျင်းစွာ ရွေးချယ်မိတာတွေက database ရဲ့ performance ကို ကျဆင်းစေနိုင်လို့ပါ။

Autovacuum daemon က enable လုပ်ထားရင် — table တစ်ခုရဲ့ အကြောင်းအရာ လုံလောက်လောက် ပြောင်းလဲသွားတိုင်း — `ANALYZE` commands တွေကို အလိုအလျောက် ထုတ်ပြန်ပေးပါတယ်။ ဒါပေမယ့် — administrators တွေက — အထူးသဖြင့် — table တစ်ခုပေါ်က update လုပ်ဆောင်မှုက “စိတ်ဝင်စားစရာ” (interesting) columns တွေရဲ့ statistics တွေကို သက်ရောက်မှာ မဟုတ်ဘူးဆိုတာ သိရရင် — manually-scheduled (လူကိုယ်တိုင် အချိန်ဇယား ဆွဲထားသော) `ANALYZE` operations တွေကိုပဲ အားကိုးချင်နိုင်ပါတယ်။ Daemon က `ANALYZE` ကို — insert ဒါမှမဟုတ် update လုပ်လိုက်တဲ့ row အရေအတွက်ရဲ့ လုပ်ဆောင်ချက် (function) တစ်ခုအနေနဲ့ပဲ တင်းကြပ်စွာ အချိန်ဇယား ဆွဲပါတယ်; အဲဒါက အဓိပ္ပာယ် ရှိတဲ့ statistical ပြောင်းလဲမှုတွေ ဖြစ်ပေါ်စေနိုင်မလားဆိုတာကိုတော့ ဘာမှ မသိပါဘူး။

Partitions တွေနဲ့ inheritance children တွေထဲမှာ ပြောင်းလဲသွားတဲ့ tuples တွေက parent table ပေါ်မှာ analyze ကို trigger မဖြစ်စေပါဘူး။ Parent table က ဗလာ ဒါမှမဟုတ် ရှားရှားပါးပါးသာ ပြောင်းလဲတယ်ဆိုရင် — သူ့ကို autovacuum က ဘယ်တော့မှ process မလုပ်ဖြစ်နိုင်ပြီး — inheritance tree တစ်ခုလုံးအတွက် statistics တွေကို စုဆောင်းလို့ ရမှာ မဟုတ်ပါဘူး။ Statistics တွေကို နောက်ဆုံး အခြေအနေမှာ ထိန်းထားဖို့ — parent table ပေါ်မှာ `ANALYZE` ကို လူကိုယ်တိုင် run ဖို့ လိုအပ်ပါတယ်။

Space ပြန်လည် ရယူခြင်းအတွက် vacuuming လုပ်သလိုပဲ — statistics update လုပ်တာကလည်း — ရှားရှားပါးပါး update လုပ်တဲ့ tables တွေထက် — heavily-updated tables တွေအတွက် ပိုအသုံးဝင်ပါတယ်။ ဒါပေမယ့် — heavily-updated table တစ်ခုအတွက်တောင် — data ရဲ့ statistical distribution (ကိန်းဂဏန်း ပြန့်ကျဲမှု ပုံစံ) သိသိသာသာ ပြောင်းလဲမနေဘူးဆိုရင် — statistics update တွေ မလိုအပ်ဘဲ နေလို့ ရနိုင်ပါတယ်။ လက်မစည်းမျဉ်း (rule of thumb) ရိုးရိုးတစ်ခုကတော့ — table ထဲက columns တွေရဲ့ အနည်းဆုံးနဲ့ အများဆုံး တန်ဖိုးတွေ ဘယ်လောက် ပြောင်းလဲလဲဆိုတာကို စဉ်းစားကြည့်ဖို့ပါ။ ဥပမာ — row update အချိန်ကို သိမ်းထားတဲ့ `timestamp` column တစ်ခုက — rows တွေ ထည့်သွင်း/update လုပ်တာနဲ့အမျှ — အမြဲတမ်း တိုးပွားနေတဲ့ အများဆုံး တန်ဖိုး (constantly-increasing maximum value) တစ်ခု ရှိပါလိမ့်မယ်; ဒီလို column မျိုးက — ဥပမာ — website တစ်ခုပေါ်မှာ ဝင်ရောက်ကြည့်ရှုခဲ့တဲ့ pages တွေအတွက် URLs တွေ ပါဝင်တဲ့ column တစ်ခုထက် — statistics update တွေ ပိုမကြာခဏ လိုအပ်ဖွယ် ရှိပါတယ်။ URL column က ထိုနှုန်းလောက်ပဲ မကြာခဏ ပြောင်းလဲမှု လက်ခံရနိုင်ပေမယ့် — သူ့ရဲ့ တန်ဖိုးတွေရဲ့ statistical distribution ကတော့ နှိုင်းယှဉ်လျှင် နှေးကွေးစွာသာ ပြောင်းလဲဖွယ် ရှိပါတယ်။

`ANALYZE` ကို သတ်မှတ်ထားတဲ့ tables တွေပေါ်မှာ — table တစ်ခုရဲ့ column တချို့ပေါ်မှာတောင် run လို့ ရတာမို့ — သင့် application က လိုအပ်ရင် — statistics တချို့ကို တခြားဟာတွေထက် ပိုမကြာခဏ update လုပ်နိုင်တဲ့ ပြောင်းလွယ်မှု (flexibility) ရှိပါတယ်။ ဒါပေမယ့် — လက်တွေ့မှာတော့ — database တစ်ခုလုံးကိုပဲ analyze လုပ်တာက များသောအားဖြင့် အကောင်းဆုံးပါ — အကြောင်းကတော့ အဲဒါက မြန်ဆန်တဲ့ operation တစ်ခု ဖြစ်လို့ပါ။ `ANALYZE` က table ရဲ့ row တိုင်းကို ဖတ်မယ့်အစား — rows တွေရဲ့ statistically random sample (ကျပန်း နမူနာ) တစ်ခုကို အသုံးပြုပါတယ်။

> **အကြံပြုချက်:** `ANALYZE` ရဲ့ ကြိမ်နှုန်းကို column အလိုက် ညှိပြင်တာက သိပ် အကျိုးမထူးနိုင်ပေမယ့် — `ANALYZE` က စုဆောင်းတဲ့ statistics တွေရဲ့ အသေးစိတ် အဆင့် (level of detail) ကို column အလိုက် ညှိပြင်တာကတော့ — အကျိုးရှိတယ်လို့ သင်တွေ့ရှိနိုင်ပါတယ်။ `WHERE` clauses တွေမှာ အသုံးများပြီး — အလွန် ပုံမှန် မဟုတ်တဲ့ (highly irregular) data distributions တွေ ရှိတဲ့ columns တွေက — တခြား columns တွေထက် — ပိုမို သေးစိတ်ကျတဲ့ (finer-grain) data histogram တစ်ခု လိုအပ်နိုင်ပါတယ်။ `ALTER TABLE SET STATISTICS` ကို ကြည့်ပါ — ဒါမှမဟုတ် — [default_statistics_target](https://www.postgresql.org/docs/current/runtime-config-query.html#GUC-DEFAULT-STATISTICS-TARGET) configuration parameter သုံးပြီး — database တစ်ခုလုံး အတိုင်းအတာ (database-wide) default ကို ပြောင်းလဲပါ။
>
> ထို့အပြင် — default အားဖြင့် — functions တွေရဲ့ selectivity (ရွေးချယ် စစ်ထုတ်နိုင်မှု အတိုင်းအတာ) အကြောင်း အချက်အလက် အကန့်အသတ်ပဲ ရနိုင်ပါတယ်။ ဒါပေမယ့် — function call တစ်ခုကို သုံးတဲ့ statistics object တစ်ခု ဒါမှမဟုတ် expression index တစ်ခုကို သင်ဖန်တီးလိုက်ရင် — အဲဒီ function အကြောင်း အသုံးဝင်တဲ့ statistics တွေ စုဆောင်းခံရပြီး — expression index ကို သုံးတဲ့ query plans တွေကို များစွာ တိုးတက်ကောင်းမွန်စေနိုင်ပါတယ်။

> **အကြံပြုချက်:** Autovacuum daemon က foreign tables တွေအတွက် `ANALYZE` commands တွေကို ထုတ်ပြန်မပေးပါဘူး — အကြောင်းကတော့ — အဲဒါ ဘယ်နှစ်ကြိမ် လုပ်ရင် အသုံးဝင်မလဲဆိုတာ ဆုံးဖြတ်ဖို့ သူ့မှာ နည်းလမ်း မရှိလို့ပါ။ သင့်ရဲ့ queries တွေက မှန်ကန်တဲ့ planning အတွက် foreign tables တွေပေါ်က statistics တွေ လိုအပ်တယ်ဆိုရင် — သင့်လျော်တဲ့ အချိန်ဇယား တစ်ခုနဲ့ — အဲဒီ tables တွေပေါ်မှာ manually-managed `ANALYZE` commands တွေကို run ဖို့ ကောင်းပါတယ်။

> **အကြံပြုချက်:** Autovacuum daemon က partitioned tables တွေအတွက် `ANALYZE` commands တွေကို ထုတ်ပြန်မပေးပါဘူး။ Inheritance parents တွေကို — parent ကိုယ်တိုင် ပြောင်းလဲမှသာ — analyze လုပ်ပါလိမ့်မယ် — child tables တွေရဲ့ ပြောင်းလဲမှုတွေက parent table ပေါ်မှာ autoanalyze ကို trigger မဖြစ်စေပါဘူး။ သင့်ရဲ့ queries တွေက မှန်ကန်တဲ့ planning အတွက် parent tables တွေပေါ်က statistics တွေ လိုအပ်တယ်ဆိုရင် — statistics တွေ နောက်ဆုံး အခြေအနေမှာ ရှိနေဖို့ — အဲဒီ tables တွေပေါ်မှာ manual `ANALYZE` တစ်ခုကို အခါအားလျော်စွာ run ဖို့ လိုအပ်ပါတယ်။

### 24.1.4. Updating the Visibility Map (visibility map update လုပ်ခြင်း)

Vacuum က table တစ်ခုချင်းစီအတွက် [visibility map](https://www.postgresql.org/docs/current/storage-vm.html) (မြင်နိုင်မှု မြေပုံ) တစ်ခုကို ထိန်းသိမ်းပြီး — ဘယ် pages တွေမှာ — active transactions တွေ အားလုံး (ပြီးတော့ — page ကို နောက်တစ်ကြိမ် ပြုပြင်မွမ်းမံသည့်အထိ — အနာဂတ် transactions တွေ အားလုံးပါ) အတွက် မြင်နိုင်တယ်လို့ သိရတဲ့ tuples တွေပဲ ပါဝင်လားဆိုတာ ခြေရာခံပါတယ်။ ဒါမှာ ရည်ရွယ်ချက် နှစ်ခု ရှိပါတယ်။ ပထမက — vacuum ကိုယ်တိုင်က — နောက်တစ်ကြိမ် run တဲ့အခါ — ဒီလို pages တွေကို skip လုပ်နိုင်ပါတယ် — အကြောင်းကတော့ ရှင်းလင်းဖို့ ဘာမှ မရှိလို့ပါ။

ဒုတိယအချက်က — ဒါက PostgreSQL ကို — underlying table ကို ရည်ညွှန်းစရာ မလိုဘဲ — index တစ်ခုတည်းကိုပဲ သုံးပြီး query တချို့ကို ဖြေဆိုနိုင်စေပါတယ်။ PostgreSQL indexes တွေမှာ tuple visibility information (tuple မြင်နိုင်မှု အချက်အလက်) မပါဝင်တာမို့ — normal index scan တစ်ခုက — index entry တစ်ခုချင်းစီအတွက် — လက်ရှိ transaction က မြင်သင့်မလား စစ်ဆေးဖို့ — heap tuple ကို ယူဆောင်လာပါတယ်။ တစ်ဖက်မှာ — [*index-only scan*](/docs/postgresql/indexes-index-only-scans) (index သီးသန့် scan) တစ်ခုကတော့ — visibility map ကို အရင်ဆုံး စစ်ဆေးပါတယ်။ Page ပေါ်က tuples တွေ အားလုံး visible ဖြစ်တယ်လို့ သိရရင် — heap fetch ကို ကျော်သွားလို့ ရပါတယ်။ ဒါက — visibility map က disk accesses တွေကို တားဆီးပေးနိုင်တဲ့ — data set ကြီးကြီးတွေပေါ်မှာ အသုံးဝင်ဆုံး ဖြစ်ပါတယ်။ Visibility map က heap ထက် အများကြီး သေးငယ်တာမို့ — heap အလွန် ကြီးမားနေတဲ့အခါတောင်မှ — လွယ်ကူစွာ cache လုပ်ထားနိုင်ပါတယ်။

### 24.1.5. Preventing Transaction ID Wraparound Failures (transaction ID wraparound failure များ ကာကွယ်ခြင်း)

PostgreSQL ရဲ့ [MVCC](/docs/postgresql/mvcc-intro) transaction semantics တွေက transaction ID (XID) နံပါတ်တွေကို နှိုင်းယှဉ်နိုင်စွမ်းအပေါ်မှာ မှီခိုပါတယ်: insertion XID က လက်ရှိ transaction ရဲ့ XID ထက် ကြီးနေတဲ့ row version တစ်ခုက “အနာဂတ်မှာ” ရှိတာလို့ သတ်မှတ်ပြီး — လက်ရှိ transaction က မြင်ရမှာ မဟုတ်ပါဘူး။ ဒါပေမယ့် — transaction IDs တွေက အရွယ်အစား အကန့်အသတ် ရှိတာမို့ (32 bits — bit ၃၂ ခု) — အချိန် အတော်ကြာ (transaction ပေါင်း 4 ဘီလီယံ ကျော်) run နေတဲ့ cluster တစ်ခုမှာ *transaction ID wraparound* (transaction ID ပြန်ရစ်ခြင်း) ဆိုတာ ကြုံရပါလိမ့်မယ်: XID counter က သုညဆီ ပြန်ရစ်ပြီး — ရုတ်တရက်ဆိုသလို — အရင်က ရှိခဲ့တဲ့ (အတိတ်က) transactions တွေက အနာဂတ်မှာ ရှိနေသလို ပေါ်လာပါတယ် — ဆိုလိုတာက သူတို့ရဲ့ output တွေ မမြင်ရတော့ဘူး ဖြစ်ပါတယ်။ အတိုချုပ်ပြောရရင် — ကပ်ဆိုက်စေနိုင်တဲ့ data ဆုံးရှုံးမှု (catastrophic data loss) ဖြစ်ပါတယ်။ (တကယ်တော့ data တွေက ရှိနေဆဲပါ — ဒါပေမယ့် သင်မရောက်ရှိနိုင်ဘူးဆိုရင် အဲဒါက နှစ်သိမ့်မှု အနည်းငယ်မျှသာ ပေးနိုင်ပါတယ်။) ဒါကို ရှောင်ဖို့ — database တိုင်းထဲက table တိုင်းကို — transaction ပေါင်း နှစ်ဘီလီယံ တစ်ကြိမ်နှုန်း အနည်းဆုံး vacuum လုပ်ဖို့ လိုအပ်ပါတယ်။

အခါအားလျော်စွာ vacuuming လုပ်တာက ပြဿနာကို ဖြေရှင်းပေးတဲ့ အကြောင်းရင်းကတော့ — `VACUUM` က rows တွေကို frozen (အေးခဲ) အဖြစ် အမှတ်အသား လုပ်ပေးလို့ပါ — ဆိုလိုတာက — အဲဒီ rows တွေကို insert လုပ်ခဲ့တဲ့ transaction က လုံလောက်လောက် ရှေးကျတဲ့ အချိန်က commit လုပ်ပြီးသား ဖြစ်လို့ — အဲဒီ inserting transaction ရဲ့ သက်ရောက်မှုတွေက — လက်ရှိနဲ့ အနာဂတ် transactions တွေ အားလုံးအတွက် မြင်နိုင်တာ သေချာပြီလို့ ညွှန်ပြနေပါတယ်။ Normal XIDs တွေကို modulo-2³² ဂဏန်းသင်္ချာ (modulo-2³² arithmetic — 2 ၏ 32 ထပ်ကိန်း ဖြင့် အကြွင်း တွက်ချက်သော ဂဏန်းသင်္ချာ) သုံးပြီး နှိုင်းယှဉ်ပါတယ်။ ဒါက ဆိုလိုတာက — normal XID တစ်ခုစီအတွက် — “ပိုအသက်ကြီးတဲ့” (older) XID နှစ်ဘီလီယံ နဲ့ “ပိုအသစ်တဲ့” (newer) XID နှစ်ဘီလီယံ ရှိပါတယ်; တနည်းပြောရရင် — normal XID space က — အဆုံးမှတ် မရှိတဲ့ — စက်ဝိုင်းပုံ ဖြစ်ပါတယ်။ ဒါကြောင့် — row version တစ်ခုကို သတ်မှတ်ထားတဲ့ normal XID တစ်ခုနဲ့ ဖန်တီးလိုက်တာနဲ့ — ဘယ် normal XID အကြောင်း ပြောနေပါစေ — နောက် transaction နှစ်ဘီလီယံအတွက် — အဲဒီ row version က “အတိတ်မှာ” ရှိနေသလို ပေါ်ပါလိမ့်မယ်။ Row version က transaction နှစ်ဘီလီယံ ကျော်ပြီးတဲ့အထိ တည်ရှိနေသေးရင် — ရုတ်တရက် အနာဂတ်မှာ ရှိနေသလို ပေါ်လာပါလိမ့်မယ်။ ဒါကို ကာကွယ်ဖို့ — PostgreSQL က `FrozenTransactionId` ဆိုတဲ့ — normal XID နှိုင်းယှဉ်မှု စည်းမျဉ်းတွေကို မလိုက်နာဘဲ — normal XID တိုင်းထက် အသက်ကြီးတယ်လို့ အမြဲတမ်း သတ်မှတ်ခံရတဲ့ — အထူး XID တစ်ခုကို သီးသန့် ထားပါတယ်။ Frozen row versions တွေကို — inserting XID က `FrozenTransactionId` ဖြစ်နေသလိုမျိုး သဘောထားပါတယ် — ဒါကြောင့် — wraparound ကိစ္စရပ်တွေ ဘယ်လိုပဲ ရှိရှိ — normal transactions တွေ အားလုံးအတွက် “အတိတ်မှာ” ရှိနေသလို ပေါ်လာပြီး — အဲဒီလို row versions တွေက — ဘယ်လောက်ကြာကြာ ဖြစ်ပါစေ — ဖျက်ပစ်လိုက်တဲ့အထိ — valid (တရားဝင်) ဖြစ်နေပါလိမ့်မယ်။

> **မှတ်ချက်:** PostgreSQL version 9.4 မတိုင်ခင်က — freezing ကို — row တစ်ခုရဲ့ insertion XID ကို `FrozenTransactionId` နဲ့ တကယ် အစားထိုးခြင်းအားဖြင့် အကောင်အထည် ဖော်ခဲ့ပြီး — အဲဒါက row ရဲ့ `xmin` system column ထဲမှာ မြင်ရပါတယ်။ ဗားရှင်း အသစ်တွေကတော့ flag bit တစ်ခုကိုပဲ သတ်မှတ်ပြီး — row ရဲ့ မူရင်း `xmin` ကို နောက်နောင်တွင် စစ်ဆေး အသုံးပြုနိုင်ဖို့ (forensic use) ထိန်းသိမ်းထားပါတယ်။ ဒါပေမယ့် — pre-9.4 versions တွေကနေ pg_upgrade လုပ်ထားတဲ့ databases တွေမှာ — `xmin` က `FrozenTransactionId` (2) နဲ့ ညီမျှတဲ့ rows တွေကို တွေ့ရနိုင်ပါသေးတယ်။
>
> ထို့အပြင် — system catalogs တွေမှာ — `xmin` က `BootstrapTransactionId` (1) နဲ့ ညီမျှတဲ့ — initdb ရဲ့ ပထမ အဆင့်အတွင်း ထည့်သွင်းခဲ့တာတွေကို ညွှန်ပြတဲ့ — rows တွေ ပါဝင်နိုင်ပါတယ်။ `FrozenTransactionId` လိုပဲ — ဒီ အထူး XID ကိုလည်း — normal XID တိုင်းထက် အသက်ကြီးတယ်လို့ သတ်မှတ်ပါတယ်။

[vacuum_freeze_min_age](https://www.postgresql.org/docs/current/runtime-config-vacuum.html#GUC-VACUUM-FREEZE-MIN-AGE) က — အဲဒီ XID ကို သယ်ဆောင်ထားတဲ့ rows တွေ freeze မလုပ်ခင် — XID တန်ဖိုး တစ်ခုက ဘယ်လောက် အသက်ကြီးရမလဲဆိုတာကို ထိန်းချုပ်ပါတယ်။ ဒီ setting ကို တိုးပေးတာက — freeze လုပ်ခံရမယ့် rows တွေက မကြာခင်မှာ နောက်တစ်ကြိမ် ပြုပြင်မွမ်းမံခံရဖွယ် ရှိနေရင် — မလိုအပ်တဲ့ အလုပ်တွေကို ရှောင်ရှားပေးနိုင်ပေမယ့် — setting ကို လျှော့ချတာကတော့ — table ကို နောက်တစ်ကြိမ် ထပ် vacuum မလုပ်ခင် — ကုန်ဆုံးသွားလို့ ရတဲ့ transactions အရေအတွက်ကို တိုးစေပါတယ်။

`VACUUM` က [visibility map](https://www.postgresql.org/docs/current/storage-vm.html) ကို သုံးပြီး — table တစ်ခုရဲ့ ဘယ် pages တွေကို scan လုပ်ရမလဲ ဆုံးဖြတ်ပါတယ်။ ပုံမှန်အားဖြင့် — dead row versions မရှိတဲ့ pages တွေကို skip လုပ်ပါလိမ့်မယ် — အဲဒီ pages တွေမှာ XID တန်ဖိုး အဟောင်းတွေနဲ့ row versions တွေ ရှိနေနိုင်သေးရင်တောင် ဖြစ်ပါတယ်။ ဒါကြောင့် — normal `VACUUM` တွေက table ထဲက row version အဟောင်း တိုင်းကို အမြဲတမ်း freeze လုပ်ပေးမှာ မဟုတ်ပါဘူး။ အဲဒီလို ဖြစ်လာတဲ့အခါ — `VACUUM` က နောက်ဆုံးမှာ *aggressive vacuum* (ပြင်းထန်သော vacuum) တစ်ခုကို လုပ်ဆောင်ဖို့ လိုအပ်ပါလိမ့်မယ် — အဲဒါက — all-visible ဖြစ်ပေမယ့် all-frozen မဟုတ်သေးတဲ့ pages တွေက ပါဝင်တဲ့ — freeze လုပ်လို့ ရတဲ့ unfrozen XID နဲ့ MXID တန်ဖိုးတွေ အားလုံးကို freeze လုပ်ပေးပါတယ်။

Table တစ်ခုမှာ all-visible ဖြစ်ပေမယ့် all-frozen မဟုတ်တဲ့ pages တွေ နောက်ကြောင်း စုပုံ (backlog) လာနေရင် — normal vacuum တစ်ခုက — သူတို့ကို freeze လုပ်ဖို့ ကြိုးစားအားထုတ်မှုအနေနဲ့ — skip လုပ်လို့ ရတဲ့ pages တွေကိုပါ scan လုပ်ဖို့ ရွေးချယ်နိုင်ပါတယ်။ အဲဒီလို လုပ်တာက — နောက် aggressive vacuum တစ်ခု scan လုပ်ရမယ့် pages အရေအတွက်ကို လျှော့ချပေးပါတယ်။ ဒါတွေကို *eagerly scanned* pages (စိတ်အားထက်သန်စွာ scan လုပ်သော pages) လို့ ခေါ်ပါတယ်။ [vacuum_max_eager_freeze_failure_rate](https://www.postgresql.org/docs/current/runtime-config-vacuum.html#GUC-VACUUM-MAX-EAGER-FREEZE-FAILURE-RATE) ကို တိုးပေးခြင်းအားဖြင့် — all-visible pages တွေကို ပိုပြီး freeze လုပ်ဖို့ ကြိုးစားအောင် — eager scanning ကို ညှိပြင်နိုင်ပါတယ်။ Eager scanning က all-visible ဖြစ်ပေမယ့် all-frozen မဟုတ်တဲ့ pages အရေအတွက်ကို အနည်းဆုံး အဆင့်မှာ ထိန်းထားနိုင်ခဲ့ရင်တောင် — tables အများစုက အခါအားလျော်စွာ aggressive vacuuming လုပ်ဖို့တော့ လိုအပ်နေပါသေးတယ်။ ဒါပေမယ့် — eager freeze လုပ်အောင်မြင်ခဲ့တဲ့ pages တွေကို aggressive vacuum အတွင်းမှာ skip လုပ်နိုင်တာမို့ — eager freezing က aggressive vacuums တွေရဲ့ overhead (ထပ်ဆောင်း စရိတ်) ကို အနည်းဆုံး ဖြစ်အောင် လျှော့ချပေးနိုင်ပါတယ်။

[vacuum_freeze_table_age](https://www.postgresql.org/docs/current/runtime-config-vacuum.html#GUC-VACUUM-FREEZE-TABLE-AGE) က table တစ်ခုကို ဘယ်အချိန်မှာ aggressive ပုံစံနဲ့ vacuum လုပ်မလဲဆိုတာကို ထိန်းချုပ်ပါတယ်။ နောက်ဆုံး ဒီလို scan လုပ်ခဲ့ချိန်ကစပြီး ကုန်ဆုံးသွားတဲ့ transactions အရေအတွက်က `vacuum_freeze_table_age` အနုတ် `vacuum_freeze_min_age` ထက် ပိုများသွားရင် — all-visible ဖြစ်ပေမယ့် all-frozen မဟုတ်တဲ့ pages တွေ အားလုံးကို scan လုပ်ပါတယ်။ `vacuum_freeze_table_age` ကို 0 လို့ သတ်မှတ်လိုက်တာက — `VACUUM` ကို သူ့ရဲ့ aggressive strategy ကို အမြဲတမ်း သုံးဖို့ အတင်းအကျပ် လုပ်ပါတယ်။

Table တစ်ခု vacuum မလုပ်ဘဲ နေလို့ ရတဲ့ အများဆုံး အချိန်က — နောက်ဆုံး aggressive vacuum လုပ်ခဲ့ချိန်က `vacuum_freeze_min_age` တန်ဖိုးကို နှုတ်လိုက်တဲ့ — transaction နှစ်ဘီလီယံ ဖြစ်ပါတယ်။ အဲဒါထက် ပိုကြာအောင် vacuum မလုပ်ဘဲ နေခဲ့မယ်ဆိုရင် — data ဆုံးရှုံးမှု ဖြစ်ပေါ်နိုင်ပါတယ်။ ဒါ မဖြစ်အောင် သေချာစေဖို့အတွက် — XIDs တွေက [autovacuum_freeze_max_age](https://www.postgresql.org/docs/current/runtime-config-vacuum.html#GUC-AUTOVACUUM-FREEZE-MAX-AGE) configuration parameter က သတ်မှတ်ထားတဲ့ အသက်ထက် ပိုအသက်ကြီးတဲ့ — unfrozen rows တွေ ပါဝင်နိုင်ခြေ ရှိတဲ့ table ဘယ်ခုမဆိုပေါ်မှာ autovacuum ကို ခေါ်ပါတယ်။ (ဒါက autovacuum ကို disable လုပ်ထားရင်တောင် ဖြစ်ပါတယ်။)

ဒါက ဆိုလိုတာက — table တစ်ခုကို တခြား နည်းနဲ့ vacuum မလုပ်ရဘူးဆိုရင် — `autovacuum_freeze_max_age` အနုတ် `vacuum_freeze_min_age` transaction တိုင်း — ခန့်မှန်းခြေ တစ်ကြိမ်နှုန်း — အဲဒီ table ပေါ်မှာ autovacuum ကို ခေါ်ပါလိမ့်မယ်။ Space ပြန်လည် ရယူခြင်းအတွက် ပုံမှန် vacuum လုပ်နေတဲ့ tables တွေအတွက်တော့ — ဒါက အရေးပါမှု အနည်းငယ်သာ ရှိပါတယ်။ ဒါပေမယ့် — static tables (inserts တွေ လက်ခံရပေမယ့် updates ဒါမှမဟုတ် deletes တွေ မရှိတဲ့ tables တွေ အပါအဝင်) တွေအတွက်တော့ — space ပြန်လည် ရယူဖို့ vacuum လုပ်ဖို့ မလိုအပ်တာမို့ — အလွန် ကြီးမားတဲ့ static tables တွေပေါ်မှာ — အတင်းအကျပ် လုပ်ရတဲ့ autovacuums တွေကြားက ကြားကာလ (interval) ကို အများဆုံး ဖြစ်အောင် ကြိုးစားတာက အသုံးဝင်နိုင်ပါတယ်။ သိသာတာက — ဒါကို `autovacuum_freeze_max_age` ကို တိုးပေးခြင်း ဒါမှမဟုတ် `vacuum_freeze_min_age` ကို လျှော့ချပေးခြင်းအားဖြင့် တစ်နည်းနည်းနဲ့ လုပ်လို့ ရပါတယ်။

`vacuum_freeze_table_age` အတွက် ထိရောက်တဲ့ အများဆုံး (effective maximum) က 0.95 * `autovacuum_freeze_max_age` ဖြစ်ပါတယ်; အဲဒါထက် ပိုမြင့်တဲ့ setting တစ်ခုကို အများဆုံးတန်ဖိုးမှာ အကန့်အသတ် (cap) လုပ်ပါလိမ့်မယ်။ `autovacuum_freeze_max_age` ထက် ပိုမြင့်တဲ့ တန်ဖိုးတစ်ခုက အဓိပ္ပာယ် ရှိမှာ မဟုတ်ပါဘူး — အကြောင်းကတော့ anti-wraparound autovacuum တစ်ခုက အဲဒီအချိန်မှာ ဘာပဲဖြစ်ဖြစ် trigger ဖြစ်သွားမှာ ဖြစ်ပြီး — 0.95 မြှောက်ဖော်ကိန်း (multiplier) က — အဲဒါ မဖြစ်ခင် — manual `VACUUM` တစ်ခု run ဖို့ — အသက်ရှူခွင့် နေရာ (breathing room) အနည်းငယ် ချန်ထားပေးလို့ပါ။ လက်မစည်းမျဉ်းအနေနဲ့ — `vacuum_freeze_table_age` ကို `autovacuum_freeze_max_age` ရဲ့ အနည်းငယ် အောက်မှာ သတ်မှတ်ပြီး — ပုံမှန် အချိန်ဇယား ဆွဲထားတဲ့ `VACUUM` တစ်ခု ဒါမှမဟုတ် ပုံမှန် delete နဲ့ update လုပ်ဆောင်မှုကြောင့် trigger ဖြစ်တဲ့ autovacuum တစ်ခု အဲဒီ window အတွင်းမှာ run ဖြစ်လောက်အောင် — လုံလောက်တဲ့ ကွာဟချက် (gap) ချန်ထားသင့်ပါတယ်။ အရမ်း နီးကပ်အောင် သတ်မှတ်လိုက်ရင် — table ကို space ပြန်လည် ရယူဖို့ မကြာသေးမီက vacuum လုပ်ထားခဲ့ရင်တောင် — anti-wraparound autovacuums တွေ ဖြစ်ပေါ်စေနိုင်ပြီး — တန်ဖိုး နိမ့်နေတာတွေကတော့ — aggressive vacuuming တွေ ပိုမကြာခဏ ဖြစ်စေပါတယ်။

`autovacuum_freeze_max_age` ကို တိုးပေးခြင်းရဲ့ (သူနဲ့အတူ `vacuum_freeze_table_age` ပါ) တစ်ခုတည်းသော အားနည်းချက်ကတော့ — database cluster ရဲ့ `pg_xact` နဲ့ `pg_commit_ts` subdirectories တွေက နေရာ ပိုယူပါလိမ့်မယ် — အကြောင်းကတော့ — `autovacuum_freeze_max_age` horizon အထိ နောက်ကြောင်း ပြန်ရှိတဲ့ transactions တွေ အားလုံးရဲ့ commit status နဲ့ — (`track_commit_timestamp` ကို enable လုပ်ထားရင်) timestamp တွေကို သိမ်းဆည်းထားရလို့ပါ။ Commit status က transaction တစ်ခုစီအတွက် bit နှစ်ခု သုံးပါတယ် — ဒါကြောင့် — `autovacuum_freeze_max_age` ကို သူ့ရဲ့ ခွင့်ပြုထားတဲ့ အများဆုံး တန်ဖိုးဖြစ်တဲ့ နှစ်ဘီလီယံမှာ သတ်မှတ်ထားရင် — `pg_xact` က gigabyte ဝက်ခန့် ကြီးထွားဖို့ မျှော်လင့်နိုင်ပြီး — `pg_commit_ts` က 20GB ဝန်းကျင် ရှိလာနိုင်ပါတယ်။ ဒါက သင့်ရဲ့ database စုစုပေါင်း အရွယ်အစားနဲ့ ယှဉ်ရင် နည်းပါးတယ်ဆိုရင် — `autovacuum_freeze_max_age` ကို သူ့ရဲ့ ခွင့်ပြုထားတဲ့ အများဆုံး တန်ဖိုးမှာ သတ်မှတ်ဖို့ အကြံပြုပါတယ်။ မဟုတ်ရင် — `pg_xact` နဲ့ `pg_commit_ts` storage အတွက် ဘာကို ခွင့်ပြုချင်လဲဆိုတာပေါ် မူတည်ပြီး သတ်မှတ်ပါ။ (Default ဖြစ်တဲ့ transaction သန်း 200 က — `pg_xact` storage 50MB ဝန်းကျင် နဲ့ `pg_commit_ts` storage 2GB ဝန်းကျင်လောက်နဲ့ ညီမျှပါတယ်။)

`vacuum_freeze_min_age` ကို လျှော့ချခြင်းရဲ့ အားနည်းချက် တစ်ခုကတော့ — `VACUUM` ကို အလဟသ အလုပ်တွေ လုပ်စေနိုင်လို့ပါ: row version တစ်ခုကို freeze လုပ်တာက — အဲဒီ row က မကြာခင်မှာ နောက်တစ်ကြိမ် ပြုပြင်မွမ်းမံခံရရင် (အဲဒါက XID အသစ်တစ်ခု ရစေတာမို့) — အချိန် အလဟသ ကုန်ဆုံးစေတာပါ။ ဒါကြောင့် — rows တွေ နောက်ထပ် ပြောင်းလဲနိုင်ခြေ နည်းပါးတဲ့အထိ freeze မလုပ်ဖြစ်အောင် — setting က လုံလောက်လောက် ကြီးနေသင့်ပါတယ်။

Database တစ်ခုထဲမှာ အသက်အကြီးဆုံး unfrozen XIDs တွေရဲ့ အသက်ကို ခြေရာခံဖို့ — `VACUUM` က XID statistics တွေကို `pg_class` နဲ့ `pg_database` system tables တွေထဲမှာ သိမ်းဆည်းပါတယ်။ အထူးသဖြင့် — table တစ်ခုရဲ့ `pg_class` row ထဲက `relfrozenxid` column က — `relfrozenxid` ကို အောင်မြင်စွာ ရှေ့သို့ တိုးခဲ့တဲ့ (ပုံမှန်အားဖြင့် နောက်ဆုံး aggressive VACUUM ဖြစ်တဲ့) — မကြာသေးမီက `VACUUM` တစ်ခုရဲ့ အဆုံးမှာ — ကျန်ရှိနေတဲ့ အသက်အကြီးဆုံး unfrozen XID ကို ပါဝင်စေပါတယ်။ အလားတူပဲ — database တစ်ခုရဲ့ `pg_database` row ထဲက `datfrozenxid` column က — အဲဒီ database ထဲမှာ ပေါ်လာတဲ့ unfrozen XIDs တွေအတွက် — အောက်ကန့်သတ်ချက် (lower bound) တစ်ခု ဖြစ်ပါတယ် — ဆိုလိုတာက — database အတွင်းက per-table `relfrozenxid` တန်ဖိုးတွေရဲ့ အနည်းဆုံးပဲ ဖြစ်ပါတယ်။ ဒီအချက်အလက်ကို စစ်ဆေးဖို့ အဆင်ပြေတဲ့ နည်းလမ်းတစ်ခုကတော့ — ဒီလို queries တွေ execute လုပ်တာပါ:

```sql
SELECT c.oid::regclass as table_name,
       greatest(age(c.relfrozenxid),age(t.relfrozenxid)) as age
FROM pg_class c
LEFT JOIN pg_class t ON c.reltoastrelid = t.oid
WHERE c.relkind IN ('r', 'm');

SELECT datname, age(datfrozenxid) FROM pg_database;
```

`age` column က — cutoff XID ကနေ လက်ရှိ transaction ရဲ့ XID အထိ — transactions အရေအတွက်ကို တိုင်းတာပါတယ်။

> **အကြံပြုချက်:** `VACUUM` command ရဲ့ `VERBOSE` parameter ကို သတ်မှတ်ထားတဲ့အခါ — `VACUUM` က table အကြောင်း statistics အမျိုးမျိုးကို ပုံနှိပ်ထုတ်ပေးပါတယ်။ ဒါမှာ — `relfrozenxid` နဲ့ `relminmxid` ဘယ်လို ရှေ့သို့ တိုးခဲ့လဲဆိုတဲ့ အချက်အလက် နဲ့ — အသစ် freeze လုပ်လိုက်တဲ့ pages အရေအတွက်တွေ ပါဝင်ပါတယ်။ Autovacuum က လုပ်ဆောင်တဲ့ `VACUUM` operation တစ်ခုအကြောင်း — autovacuum logging ([log_autovacuum_min_duration](https://www.postgresql.org/docs/current/runtime-config-logging.html#GUC-LOG-AUTOVACUUM-MIN-DURATION) က ထိန်းချုပ်ထားတဲ့) က အစီရင်ခံတဲ့အခါ — အလားတူ အသေးစိတ် အချက်အလက်တွေ server log ထဲမှာ ပေါ်ပါတယ်။

`VACUUM` က နောက်ဆုံး vacuum လုပ်ပြီးကတည်းက ပြုပြင်မွမ်းမံခဲ့တဲ့ pages တွေကို အများအားဖြင့် scan လုပ်ပေမယ့် — သူတို့ကို freeze လုပ်ဖို့ ကြိုးစားမှုအနေနဲ့ — all-visible ဖြစ်ပေမယ့် all-frozen မဟုတ်တဲ့ pages တချို့ကိုလည်း စိတ်အားထက်သန်စွာ (eagerly) scan လုပ်နိုင်ပါတယ် — ဒါပေမယ့် — table ရဲ့ unfrozen XIDs ပါဝင်နိုင်ခြေ ရှိတဲ့ page တိုင်းကို scan လုပ်လိုက်တဲ့အခါမှသာ — `relfrozenxid` ကို ရှေ့သို့ တိုးပေးမှာ ဖြစ်ပါတယ်။ ဒါက — `relfrozenxid` က `vacuum_freeze_table_age` transactions ထက် ပိုအသက်ကြီးသွားတဲ့အခါ၊ `VACUUM` ရဲ့ `FREEZE` option ကို သုံးထားတဲ့အခါ၊ ဒါမှမဟုတ် — all-frozen မဟုတ်သေးတဲ့ pages တွေ အားလုံးက — dead row versions တွေ ဖယ်ရှားဖို့ vacuum လိုအပ်ချက်နဲ့ ကြုံတိုက်ဆိုင်နေတဲ့အခါတွေမှာ ဖြစ်ပါတယ်။ `VACUUM` က all-frozen မဟုတ်သေးတဲ့ table ထဲက page တိုင်းကို scan လုပ်တဲ့အခါ — `age(relfrozenxid)` ကို — အသုံးပြုခဲ့တဲ့ `vacuum_freeze_min_age` setting ထက် နည်းနည်းလေးပဲ ပိုတဲ့ တန်ဖိုးတစ်ခုမှာ ထားသင့်ပါတယ် (`VACUUM` စတင်ပြီးကတည်းက စတင်ခဲ့တဲ့ transactions အရေအတွက်လောက် ပိုပါတယ်)။ `VACUUM` က `relfrozenxid` ကို table ထဲမှာ ကျန်ရှိနေတဲ့ အသက်အကြီးဆုံး XID မှာ သတ်မှတ်ပေးမှာ ဖြစ်လို့ — နောက်ဆုံး တန်ဖိုးက တင်းကြပ်စွာ လိုအပ်တာထက် အများကြီး ပိုသစ်နေနိုင်ပါတယ်။ Table ပေါ်မှာ `autovacuum_freeze_max_age` ရောက်ရှိသည့်အထိ — `relfrozenxid`-ကို-ရှေ့သို့-တိုးပေးတဲ့ `VACUUM` တစ်ခုကို ထုတ်ပြန်ခြင်း မရှိဘူးဆိုရင် — အဲဒီ table အတွက် autovacuum တစ်ခုကို မကြာခင်မှာ အတင်းအကျပ် လုပ်ပါလိမ့်မယ်။

တစ်နည်းနည်းနဲ့ autovacuum က table တစ်ခုကနေ XID အဟောင်းတွေကို ရှင်းလင်းဖို့ ပျက်ကွက်ခဲ့ရင် — database ရဲ့ အသက်အကြီးဆုံး XIDs တွေက wraparound အမှတ်ကနေ transaction သန်း ၄၀ အကွာကို ရောက်ရှိလာတဲ့အခါ — system က ဒီလို warning messages တွေ ထုတ်လွှတ်တော့မှာ ဖြစ်ပါတယ်:

```sql
WARNING:  database "mydb" must be vacuumed within 39985967 transactions
HINT:  To avoid XID assignment failures, execute a database-wide VACUUM in that database.
```

(ဒီ hint က အကြံပြုထားသလို — manual `VACUUM` တစ်ခုက ပြဿနာကို ဖြေရှင်းပေးသင့်ပါတယ်; ဒါပေမယ့် — `VACUUM` ကို superuser တစ်ယောက်က လုပ်ဆောင်သင့်တယ်ဆိုတာ သတိပြုပါ — မဟုတ်ရင် — database ရဲ့ `datfrozenxid` ကို ရှေ့သို့ တိုးပေးနိုင်စွမ်းကို တားဆီးထားတဲ့ — system catalogs တွေကို process လုပ်ဖို့ ပျက်ကွက်မှာ ဖြစ်လို့ပါ။) ဒီ warnings တွေကို လျစ်လျူရှုထားမယ်ဆိုရင် — wraparound မတိုင်ခင် transaction သုံးသန်းအောက်ပဲ ကျန်တော့တဲ့အခါ — system က XID အသစ်တွေ သတ်မှတ်ပေးဖို့ ငြင်းပယ်ပါလိမ့်မယ်:

```sql
ERROR:  database is not accepting commands that assign new transaction IDs to avoid wraparound data loss in database "mydb"
HINT:  Execute a database-wide VACUUM in that database.
```

ဒီအခြေအနေမှာ — လုပ်ဆောင်နေပြီးသား transactions တွေက ဆက်လုပ်နိုင်ပေမယ့် — read-only transactions တွေကိုပဲ စတင်လို့ ရပါတော့တယ်။ Database records တွေကို ပြုပြင်မွမ်းမံတဲ့ ဒါမှမဟုတ် relations တွေကို truncate လုပ်တဲ့ operations တွေက မအောင်မြင်ပါဘူး။ `VACUUM` command ကတော့ ပုံမှန်အတိုင်း run လို့ ရနေဆဲ ဖြစ်ပါတယ်။ အစောပိုင်း releases တွေမှာ တစ်ခါတစ်ရံ အကြံပြုခဲ့တာတွေနဲ့ ဆန့်ကျင်ဘက်ကို သတိပြုပါ — ပုံမှန် လည်ပတ်မှု ပြန်လည် ရရှိဖို့ — postmaster ကို ရပ်တန့်ဖို့ ဒါမှမဟုတ် single-user mode ထဲ ဝင်ဖို့ မလိုအပ်သလို — မသင့်လျော်လည်း ဖြစ်ပါတယ်။ အဲဒီအစား — ဒီအဆင့်တွေကို လိုက်နာပါ:

1. ရှေးကျတဲ့ prepared transactions တွေကို ဖြေရှင်းပါ။ [`pg_prepared_xacts`](https://www.postgresql.org/docs/current/view-pg-prepared-xacts.html) ထဲမှာ `age(transactionid)` ကြီးမားတဲ့ rows တွေကို စစ်ဆေးခြင်းအားဖြင့် ဒါတွေကို ရှာတွေ့နိုင်ပါတယ်။ ဒီလို transactions တွေကို commit ဒါမှမဟုတ် roll back လုပ်သင့်ပါတယ်။
2. အချိန် အတော်ကြာ run နေတဲ့ (long-running) open transactions တွေကို အဆုံးသတ်ပါ။ [`pg_stat_activity`](https://www.postgresql.org/docs/current/monitoring-stats.html#MONITORING-PG-STAT-ACTIVITY-VIEW) ထဲမှာ `age(backend_xid)` ဒါမှမဟုတ် `age(backend_xmin)` ကြီးမားတဲ့ rows တွေကို စစ်ဆေးခြင်းအားဖြင့် ဒါတွေကို ရှာတွေ့နိုင်ပါတယ်။ ဒီလို transactions တွေကို commit ဒါမှမဟုတ် roll back လုပ်သင့်ပါတယ် — ဒါမှမဟုတ် — session ကို `pg_terminate_backend` သုံးပြီး အဆုံးသတ်နိုင်ပါတယ်။
3. Replication slots အဟောင်းတွေကို ဖျက်ပစ်ပါ။ `age(xmin)` ဒါမှမဟုတ် `age(catalog_xmin)` ကြီးမားတဲ့ slots တွေကို ရှာဖို့ [`pg_replication_slots`](https://www.postgresql.org/docs/current/view-pg-replication-slots.html) ကို သုံးပါ။ ဖြစ်ရပ် အများအပြားမှာ — ဒီလို slots တွေက — မရှိတော့တဲ့ ဒါမှမဟုတ် အချိန် အတော်ကြာ ရပ်နေခဲ့တဲ့ servers တွေဆီ replication လုပ်ဖို့ ဖန်တီးထားခဲ့တာတွေ ဖြစ်ပါတယ်။ ရှိနေဆဲ ဖြစ်ပြီး — အဲဒီ slot ဆီ connect ဖို့ ကြိုးစားနိုင်သေးတဲ့ server တစ်ခုအတွက် slot တစ်ခုကို ဖျက်လိုက်ရင် — အဲဒီ replica ကို ပြန်လည် တည်ဆောက် (rebuild) ဖို့ လိုအပ်နိုင်ပါတယ်။
4. Target database ထဲမှာ `VACUUM` ကို execute လုပ်ပါ။ Database တစ်ခုလုံး အတိုင်းအတာ `VACUUM` တစ်ခုက အရိုးရှင်းဆုံး ဖြစ်ပါတယ်; လိုအပ်တဲ့ အချိန်ကို လျှော့ချဖို့ — `relminxid` အသက်အကြီးဆုံး ဖြစ်တဲ့ tables တွေပေါ်မှာ manual `VACUUM` commands တွေ ထုတ်ပြန်တာလည်း ဖြစ်နိုင်ပါတယ်။ ဒီအခြေအနေမျိုးမှာ `VACUUM FULL` ကို မသုံးပါနဲ့ — အကြောင်းကတော့ — အဲဒါက XID တစ်ခု လိုအပ်လို့ မအောင်မြင်နိုင်လို့ပါ — superuser mode မှာတော့ သူက XID တစ်ခုကို သုံးစွဲပြီး — transaction ID wraparound ရဲ့ အန္တရာယ်ကို တိုးစေမှာ ဖြစ်လို့ပါ။ `VACUUM FREEZE` ကိုလည်း မသုံးပါနဲ့ — အကြောင်းကတော့ — ပုံမှန် လည်ပတ်မှု ပြန်လည် ရရှိဖို့ လိုအပ်တဲ့ အနည်းဆုံး အလုပ်ပမာဏထက် ပိုပြီး လုပ်ဆောင်မှာ ဖြစ်လို့ပါ။
5. ပုံမှန် လည်ပတ်မှု ပြန်လည် ရရှိပြီးတာနဲ့ — နောင်ပြဿနာတွေ မဖြစ်အောင် — target database မှာ autovacuum ကို သင့်လျော်စွာ configure လုပ်ထားကြောင်း သေချာစေပါ။

> **မှတ်ချက်:** အစောပိုင်း versions တွေမှာ — postmaster ကို ရပ်တန့်ပြီး — single-user mode မှာ database ကို `VACUUM` လုပ်ဖို့ တစ်ခါတစ်ရံ လိုအပ်ခဲ့ပါတယ်။ ပုံမှန် အခြေအနေတွေမှာ — ဒါ မလိုအပ်တော့ဘဲ — system ကို ချပစ်ရတာ ပါဝင်တာမို့ — တတ်နိုင်သမျှ ရှောင်သင့်ပါတယ်။ ဒါ့အပြင် — data ဆုံးရှုံးမှုကို ကာကွယ်ဖို့ ဒီဇိုင်း လုပ်ထားတဲ့ transaction ID wraparound အကာအကွယ် ယန္တရားတွေကို disable လုပ်လိုက်တာမို့ — ပိုပြီး အန္တရာယ် များပါတယ်။ ဒီအခြေအနေမျိုးမှာ single-user mode သုံးဖို့ တစ်ခုတည်းသော အကြောင်းရင်းက — မလိုအပ်တော့တဲ့ tables တွေကို `VACUUM` လုပ်စရာ မလိုအောင် — `TRUNCATE` ဒါမှမဟုတ် `DROP` လုပ်ချင်တာမျိုးဆိုရင်ပဲ ဖြစ်ပါတယ်။ သုံးသန်း transaction ရဲ့ safety margin (လုံခြုံမှု အနားသတ်) က ဒါကို administrator လုပ်နိုင်ဖို့အတွက် တည်ရှိနေတာပါ။ Single-user mode အသုံးပြုခြင်းအကြောင်း အသေးစိတ်အတွက် [postgres](https://www.postgresql.org/docs/current/app-postgres.html) reference page ကို ကြည့်ပါ။

#### 24.1.5.1. Multixacts and Wraparound (Multixacts နှင့် Wraparound)

*Multixact IDs* (multixact ID များ) ကို — transactions အများအပြားက row တစ်ခုကို lock (သော့ခတ်) လုပ်တာကို ထောက်ပံ့ဖို့ သုံးပါတယ်။ Tuple header ထဲမှာ lock information သိမ်းဖို့ နေရာ အကန့်အသတ်ပဲ ရှိတာမို့ — transactions တစ်ခုထက်ပိုပြီး row တစ်ခုကို တစ်ပြိုင်နက် lock လုပ်နေတဲ့အခါတိုင်း — အဲဒီ အချက်အလက်ကို “multiple transaction ID” — အတိုကောက် multixact ID — အဖြစ် encode (ကုဒ် သွင်း) လုပ်ပါတယ်။ Multixact ID တစ်ခုခုထဲမှာ ဘယ် transaction IDs တွေ ပါဝင်လားဆိုတဲ့ အချက်အလက်ကို `pg_multixact` subdirectory ထဲမှာ သီးခြား သိမ်းဆည်းပြီး — tuple header ထဲက `xmax` field ထဲမှာတော့ multixact ID တစ်ခုတည်းပဲ ပေါ်လာပါတယ်။ Transaction IDs တွေလိုပဲ — multixact IDs တွေကို 32-bit counter (bit ၃၂ ပါဝင်သော ရေတွက်ကိရိယာ) နဲ့ သက်ဆိုင်ရာ storage အဖြစ် အကောင်အထည် ဖော်ထားပြီး — အဲဒါ အားလုံးက ဂရုတစိုက် aging management (သက်တမ်း စီမံခန့်ခွဲမှု)၊ storage cleanup နဲ့ wraparound ကိုင်တွယ်မှု လိုအပ်ပါတယ်။ Multixact တစ်ခုစီထဲက members စာရင်းကို ကိုင်ထားတဲ့ သီးခြား storage area တစ်ခုလည်း ရှိပြီး — အဲဒါကလည်း 32-bit counter ကို သုံးပြီး — စီမံခန့်ခွဲရပါတယ်။ [ဇယား 9.84](/docs/postgresql/functions-info) မှာ ဖော်ပြထားတဲ့ `pg_get_multixact_members()` system function ကို — multixact ID တစ်ခုနဲ့ ဆက်စပ်နေတဲ့ transaction IDs တွေကို စစ်ဆေးဖို့ သုံးနိုင်ပါတယ်။

`VACUUM` က table တစ်ခုရဲ့ ဘယ် အစိတ်အပိုင်းကိုမဆို scan လုပ်တိုင်း — [vacuum_multixact_freeze_min_age](https://www.postgresql.org/docs/current/runtime-config-vacuum.html#GUC-VACUUM-MULTIXACT-FREEZE-MIN-AGE) ထက် ပိုအသက်ကြီးတဲ့ — သူ ကြုံတွေ့ရတဲ့ multixact ID တိုင်းကို — တန်ဖိုး သုည၊ transaction ID တစ်ခုတည်း၊ ဒါမှမဟုတ် multixact ID အသစ်တစ်ခု ဖြစ်နိုင်တဲ့ — မတူညီတဲ့ တန်ဖိုးတစ်ခုနဲ့ အစားထိုးပါလိမ့်မယ်။ Table တစ်ခုချင်းစီအတွက် — `pg_class`.`relminmxid` က — အဲဒီ table ရဲ့ tuple တစ်ခုခုထဲမှာ ပေါ်နေဆဲ ဖြစ်တဲ့ — ဖြစ်နိုင်သမျှ အသက်အကြီးဆုံး multixact ID ကို သိမ်းဆည်းပါတယ်။ ဒီတန်ဖိုးက [vacuum_multixact_freeze_table_age](https://www.postgresql.org/docs/current/runtime-config-vacuum.html#GUC-VACUUM-MULTIXACT-FREEZE-TABLE-AGE) ထက် ပိုအသက်ကြီးနေရင် — aggressive vacuum တစ်ခုကို အတင်းအကျပ် လုပ်ပါတယ်။ အရင် section မှာ ဆွေးနွေးခဲ့သလိုပဲ — aggressive vacuum ဆိုတာ — all-frozen ဖြစ်တယ်လို့ သိရတဲ့ pages တွေကိုပဲ skip လုပ်မယ်ဆိုတဲ့ အဓိပ္ပာယ် ဖြစ်ပါတယ်။ `pg_class`.`relminmxid` ရဲ့ အသက်ကို ရှာဖို့ `mxid_age()` ကို သုံးနိုင်ပါတယ်။

Aggressive `VACUUM` တွေက — ဘာကြောင့် ဖြစ်ရပါစေ — table ရဲ့ `relminmxid` ကို ရှေ့သို့ တိုးပေးနိုင်တာ အာမခံပါတယ်။ နောက်ဆုံးမှာ — databases တွေ အားလုံးထဲက tables တွေ အားလုံးကို scan လုပ်ပြီး — သူတို့ရဲ့ အသက်အကြီးဆုံး multixact တန်ဖိုးတွေကို ရှေ့သို့ တိုးပေးလိုက်တာနဲ့အမျှ — multixact အဟောင်းတွေအတွက် on-disk storage ကို ဖယ်ရှားလို့ ရပါတယ်။

လုံခြုံရေး ယန္တရား တစ်ခုအနေနဲ့ — multixact-age က [autovacuum_multixact_freeze_max_age](https://www.postgresql.org/docs/current/runtime-config-vacuum.html#GUC-AUTOVACUUM-MULTIXACT-FREEZE-MAX-AGE) ထက် ပိုကြီးတဲ့ table ဘယ်ခုအတွက်မဆို — aggressive vacuum scan တစ်ခု ဖြစ်ပေါ်ပါလိမ့်မယ်။ ထို့အပြင် — multixact members တွေ သိမ်းပိုက်ထားတဲ့ storage က 10GB ဝန်းကျင် ကျော်လွန်သွားရင် — multixact-age အသက်အကြီးဆုံး tables တွေကနေ စပြီး — tables တွေ အားလုံးအတွက် aggressive vacuum scans တွေ ပိုမကြာခဏ ဖြစ်ပေါ်ပါလိမ့်မယ်။ ဒီ aggressive scans အမျိုးအစား နှစ်ခုလုံးက — autovacuum ကို အမည်ခံအားဖြင့် (nominally) disable လုပ်ထားရင်တောင် ဖြစ်ပေါ်ပါလိမ့်မယ်။ Members storage area က wraparound မရောက်ခင် 20GB ဝန်းကျင်အထိ ကြီးထွားနိုင်ပါတယ်။

XID ကိစ္စနဲ့ ဆင်တူပြီး — autovacuum က table တစ်ခုကနေ MXID အဟောင်းတွေကို ရှင်းလင်းဖို့ ပျက်ကွက်ခဲ့ရင် — database ရဲ့ အသက်အကြီးဆုံး MXIDs တွေက wraparound အမှတ်ကနေ transaction သန်း ၄၀ အကွာကို ရောက်ရှိလာတဲ့အခါ — system က warning messages တွေ ထုတ်လွှတ်တော့မှာ ဖြစ်ပါတယ်။ ပြီးတော့ — XID ကိစ္စမှာလိုပဲ — ဒီ warnings တွေကို လျစ်လျူရှုထားမယ်ဆိုရင် — wraparound မတိုင်ခင် သုံးသန်းအောက်ပဲ ကျန်တော့တဲ့အခါ — system က MXID အသစ်တွေ ထုတ်လုပ်ပေးဖို့ ငြင်းပယ်ပါလိမ့်မယ်။

MXIDs တွေ ကုန်ဆုံးသွားတဲ့အခါ ပုံမှန် လည်ပတ်မှုကို — XIDs တွေ ကုန်ဆုံးတဲ့အခါ ပြန်လည် ရယူသလိုမျိုး — နည်းလမ်း အတော်များများ အတူတူပဲ ပြန်လည် ရယူလို့ ရပါတယ်။ အရင် section က အဆင့်တွေ အတိုင်းပဲ လုပ်ဆောင်ပါ — ဒါပေမယ့် — ဒီခြားနားချက်တွေနဲ့ အတူ ဖြစ်ပါတယ်:

1. Run နေတဲ့ transactions တွေနဲ့ prepared transactions တွေက — သူတို့ multixact တစ်ခုထဲမှာ ပေါ်လာနိုင်ခြေ မရှိဘူးဆိုရင် — လျစ်လျူရှုလို့ ရပါတယ်။
2. Transaction ID wraparound နဲ့ မတူတာက — replication slots တွေက multixact cleanup ကို တိုက်ရိုက် နှောင့်နှေး မထားပါဘူး။ ဒါကြောင့် — stale replication slots တွေကို ဖျက်ပစ်တာက — multixact ID wraparound ပြဿနာတွေကို ဖြေရှင်းရာမှာ ပုံမှန်အားဖြင့် သက်ဆိုင်မှု မရှိပါဘူး။
3. MXID information တွေက `pg_stat_activity` လို system views တွေထဲမှာ တိုက်ရိုက် မြင်ရမှာ မဟုတ်ပါဘူး; ဒါပေမယ့် — XID အဟောင်းတွေကို ရှာဖွေတာက — ဘယ် transactions တွေက MXID wraparound ပြဿနာတွေကို ဖြစ်စေနေလဲ ဆုံးဖြတ်ဖို့ နည်းလမ်းကောင်း တစ်ခု ဖြစ်နေဆဲပါ။
4. XID ကုန်ဆုံးမှုက write transactions တွေ အားလုံးကို ပိတ်ဆို့ပေမယ့် — MXID ကုန်ဆုံးမှုကတော့ — write transactions တွေရဲ့ အစိတ်အပိုင်း တစ်ခုကိုပဲ ပိတ်ဆို့ပါတယ် — အထူးသဖြင့် — MXID တစ်ခု လိုအပ်တဲ့ row locks တွေ ပါဝင်တဲ့ transactions တွေကိုပဲ ဖြစ်ပါတယ်။

### 24.1.6. The Autovacuum Daemon (Autovacuum Daemon)

PostgreSQL မှာ *autovacuum* လို့ ခေါ်တဲ့ — optional ဖြစ်ပေမယ့် အလွန် အကြံပြုထားတဲ့ — feature တစ်ခု ရှိပြီး — သူ့ရဲ့ ရည်ရွယ်ချက်က `VACUUM` နဲ့ `ANALYZE` commands တွေရဲ့ လုပ်ဆောင်မှုကို အလိုအလျောက် လုပ်ပေးဖို့ ဖြစ်ပါတယ်။ Enable လုပ်ထားတဲ့အခါ — autovacuum က inserted, updated ဒါမှမဟုတ် deleted လုပ်ထားတဲ့ tuples အရေအတွက် များပြားနေတဲ့ tables တွေအတွက် စစ်ဆေးပါတယ်။ ဒီစစ်ဆေးမှုတွေက statistics collection facility ကို အသုံးပြုပါတယ်; ဒါကြောင့် — [track_counts](https://www.postgresql.org/docs/current/runtime-config-statistics.html#GUC-TRACK-COUNTS) ကို `true` လို့ သတ်မှတ်မထားရင် autovacuum ကို သုံးလို့ မရပါဘူး။ Default configuration မှာ — autovacuuming ကို enable လုပ်ထားပြီး — ဆက်စပ်တဲ့ configuration parameters တွေကိုလည်း သင့်လျော်စွာ သတ်မှတ်ထားပါတယ်။

“Autovacuum daemon” က တကယ်တော့ process အများအပြားနဲ့ ဖွဲ့စည်းထားပါတယ်။ *Autovacuum launcher* လို့ ခေါ်တဲ့ — persistent daemon process တစ်ခု ရှိပြီး — သူက databases တွေ အားလုံးအတွက် *autovacuum worker* processes တွေကို စတင်ပေးဖို့ တာဝန် ရှိပါတယ်။ Launcher က အလုပ်တွေကို အချိန် အတိုင်းအတာ တစ်ခုပေါ်မှာ ဖြန့်ဝေပြီး — database တစ်ခုချင်းစီအတွင်း — [autovacuum_naptime](https://www.postgresql.org/docs/current/runtime-config-vacuum.html#GUC-AUTOVACUUM-NAPTIME) စက္ကန့်တိုင်းမှာ worker တစ်ခုနှုန်း စတင်ဖို့ ကြိုးစားပါတယ်။ (ဒါကြောင့် — installation မှာ databases `N` ခု ရှိရင် — worker အသစ်တစ်ခုကို `autovacuum_naptime`/`N` စက္ကန့်တိုင်းမှာ စတင်ပါလိမ့်မယ်။) [autovacuum_max_workers](https://www.postgresql.org/docs/current/runtime-config-vacuum.html#GUC-AUTOVACUUM-MAX-WORKERS) အထိ worker processes တွေကို တစ်ချိန်တည်းမှာ run ခွင့် ပြုထားပါတယ်။ Process လုပ်ရမယ့် databases တွေက `autovacuum_max_workers` ထက် ပိုများနေရင် — ပထမ worker ပြီးဆုံးတာနဲ့ — နောက် database ကို ချက်ချင်း process လုပ်ပါလိမ့်မယ်။ Worker process တစ်ခုစီက သူ့ရဲ့ database အတွင်းက table တစ်ခုချင်းစီကို စစ်ဆေးပြီး — လိုအပ်သလို `VACUUM` နဲ့/သို့မဟုတ် `ANALYZE` ကို execute လုပ်ပါတယ်။ Autovacuum workers တွေရဲ့ လုပ်ဆောင်ချက်တွေကို စောင့်ကြည့်ဖို့ [log_autovacuum_min_duration](https://www.postgresql.org/docs/current/runtime-config-logging.html#GUC-LOG-AUTOVACUUM-MIN-DURATION) ကို သတ်မှတ်နိုင်ပါတယ်။

Table ကြီးများစွာက အချိန် တိုတောင်းတဲ့ ကာလအတွင်းမှာ vacuuming လုပ်ဖို့ အရည်အချင်း ပြည့်မီလာခဲ့ရင် — autovacuum workers တွေ အားလုံးက အဲဒီ tables တွေကို vacuum လုပ်နေတာနဲ့ပဲ — အချိန် အတော်ကြာ သိမ်းပိုက်ခံထားရနိုင်ပါတယ်။ ဒါက — တခြား tables နဲ့ databases တွေကို — worker တစ်ခု ရနိုင်တဲ့အထိ — vacuum မလုပ်ဖြစ်ဘဲ ဖြစ်စေပါလိမ့်မယ်။ Database တစ်ခုတည်းထဲမှာ workers ဘယ်နှစ်ယောက် ရှိနိုင်လဲဆိုတဲ့ ကန့်သတ်ချက် မရှိပါဘူး — ဒါပေမယ့် — workers တွေက တခြား workers တွေ လုပ်ပြီးသား အလုပ်တွေကို ထပ်မလုပ်မိအောင် ရှောင်ဖို့ ကြိုးစားပါတယ်။ Run နေတဲ့ workers အရေအတွက်က [max_connections](https://www.postgresql.org/docs/current/runtime-config-connection.html#GUC-MAX-CONNECTIONS) ဒါမှမဟုတ် [superuser_reserved_connections](https://www.postgresql.org/docs/current/runtime-config-connection.html#GUC-SUPERUSER-RESERVED-CONNECTIONS) ကန့်သတ်ချက်တွေဆီ ရေတွက်မသွားဘူးဆိုတာ သတိပြုပါ။

`relfrozenxid` တန်ဖိုးက [autovacuum_freeze_max_age](https://www.postgresql.org/docs/current/runtime-config-vacuum.html#GUC-AUTOVACUUM-FREEZE-MAX-AGE) transactions ထက် ပိုအသက်ကြီးတဲ့ tables တွေကို အမြဲတမ်း vacuum လုပ်ပါတယ် (ဒါက — freeze max age ကို storage parameters တွေကနေတစ်ဆင့် ပြုပြင်ထားတဲ့ tables တွေအတွက်လည်း သက်ရောက်ပါတယ်; အောက်မှာ ကြည့်ပါ)။ မဟုတ်ရင် — နောက်ဆုံး `VACUUM` ကတည်းက obsolete (အသုံးမလိုတော့) ဖြစ်သွားတဲ့ tuples အရေအတွက်က “vacuum threshold” ကို ကျော်လွန်နေရင် — table ကို vacuum လုပ်ပါတယ်။ Vacuum threshold ကို ဒီလို သတ်မှတ်ပါတယ်:

```sql
vacuum threshold = Minimum(vacuum max threshold, vacuum base threshold + vacuum scale factor * number of tuples)
```

ဒီမှာ vacuum max threshold က [autovacuum_vacuum_max_threshold](https://www.postgresql.org/docs/current/runtime-config-vacuum.html#GUC-AUTOVACUUM-VACUUM-MAX-THRESHOLD)၊ vacuum base threshold က [autovacuum_vacuum_threshold](https://www.postgresql.org/docs/current/runtime-config-vacuum.html#GUC-AUTOVACUUM-VACUUM-THRESHOLD)၊ vacuum scale factor က [autovacuum_vacuum_scale_factor](https://www.postgresql.org/docs/current/runtime-config-vacuum.html#GUC-AUTOVACUUM-VACUUM-SCALE-FACTOR) ဖြစ်ပြီး — number of tuples က `pg_class`.`reltuples` ဖြစ်ပါတယ်။

ထို့အပြင် — နောက်ဆုံး vacuum ကတည်းက inserted လုပ်လိုက်တဲ့ tuples အရေအတွက်က — သတ်မှတ်ထားတဲ့ insert threshold ကို ကျော်လွန်သွားရင်လည်း — table ကို vacuum လုပ်ပါတယ် — အဲဒါကို ဒီလို သတ်မှတ်ပါတယ်:

```sql
vacuum insert threshold = vacuum base insert threshold + vacuum insert scale factor * number of tuples * percent of table not frozen
```

ဒီမှာ vacuum insert base threshold က [autovacuum_vacuum_insert_threshold](https://www.postgresql.org/docs/current/runtime-config-vacuum.html#GUC-AUTOVACUUM-VACUUM-INSERT-THRESHOLD)၊ vacuum insert scale factor က [autovacuum_vacuum_insert_scale_factor](https://www.postgresql.org/docs/current/runtime-config-vacuum.html#GUC-AUTOVACUUM-VACUUM-INSERT-SCALE-FACTOR) ဖြစ်ပြီး — number of tuples က `pg_class`.`reltuples`၊ table မှာ frozen မဖြစ်တဲ့ ရာခိုင်နှုန်း (percent of the table not frozen) က `1 - pg_class.relallfrozen / pg_class.relpages` ဖြစ်ပါတယ်။ ဒီလို vacuums တွေက table ရဲ့ အစိတ်အပိုင်းတွေကို *all visible* (အားလုံး မြင်နိုင်) အဖြစ် အမှတ်အသား လုပ်ခွင့် ပေးနိုင်ပြီး — tuples တွေကိုလည်း frozen ဖြစ်စေနိုင်ပါတယ် — အဲဒါက နောက်ပိုင်း vacuums တွေမှာ လိုအပ်တဲ့ အလုပ်တွေကို လျှော့ချပေးနိုင်ပါတယ်။ `INSERT` operations တွေ လက်ခံရပေမယ့် `UPDATE`/`DELETE` operations တွေ မရှိ ဒါမှမဟုတ် လုံးဝနီးပါး မရှိတဲ့ tables တွေအတွက်ဆိုရင် — table ရဲ့ [autovacuum_freeze_min_age](/docs/postgresql/sql-createtable) ကို လျှော့ချပေးတာက အကျိုးရှိနိုင်ပါတယ် — အကြောင်းကတော့ အဲဒါက tuples တွေကို ပိုစောတဲ့ vacuums တွေမှာတင် frozen ဖြစ်စေနိုင်လို့ပါ။ Obsolete tuples အရေအတွက် နဲ့ inserted tuples အရေအတွက်တွေကို cumulative statistics system ကနေ ရယူပါတယ်; အဲဒါက `UPDATE`, `DELETE` နဲ့ `INSERT` operation တစ်ခုချင်းစီက update လုပ်ပေးတဲ့ — eventually-consistent (နောက်ဆုံးမှာ ညီညွတ်သွားသော) ရေတွက်မှု တစ်ခု ဖြစ်ပါတယ်။ Table ရဲ့ `relfrozenxid` တန်ဖိုးက `vacuum_freeze_table_age` transactions ထက် ပိုအသက်ကြီးနေရင် — tuples အဟောင်းတွေကို freeze လုပ်ပြီး `relfrozenxid` ကို ရှေ့သို့ တိုးဖို့ — aggressive vacuum တစ်ခုကို လုပ်ဆောင်ပါတယ်။

Analyze အတွက်လည်း — ဆင်တူတဲ့ အခြေအနေ တစ်ခုကို သုံးပါတယ်: ဒီလို သတ်မှတ်ထားတဲ့ threshold ကို:

```sql
analyze threshold = analyze base threshold + analyze scale factor * number of tuples
```

နောက်ဆုံး `ANALYZE` ကတည်းက inserted, updated ဒါမှမဟုတ် deleted လုပ်လိုက်တဲ့ tuples စုစုပေါင်း အရေအတွက်နဲ့ နှိုင်းယှဉ်ပါတယ်။

Partitioned tables တွေက tuples တွေကို တိုက်ရိုက် သိမ်းဆည်းမထားတာမို့ — autovacuum က သူတို့ကို process မလုပ်ပါဘူး။ (Autovacuum က table partitions တွေကိုတော့ တခြား tables တွေလိုပဲ process လုပ်ပါတယ်။) ကံမကောင်းတာက — ဒါက ဆိုလိုတာက — autovacuum က partitioned tables တွေပေါ်မှာ `ANALYZE` ကို run မပေးဘူး ဖြစ်ပြီး — ဒါက partitioned table statistics တွေကို ရည်ညွှန်းတဲ့ queries တွေအတွက် — အကောင်းဆုံး မဟုတ်တဲ့ (suboptimal) plans တွေကို ဖြစ်စေနိုင်ပါတယ်။ Partitioned tables တွေကို ပထမဆုံး data ဖြည့်တဲ့အခါ — ပြီးတော့ — သူတို့ရဲ့ partitions တွေထဲက data ရဲ့ ပြန့်ကျဲမှု (distribution) သိသိသာသာ ပြောင်းလဲတိုင်းလည်း — partitioned tables တွေပေါ်မှာ `ANALYZE` ကို လူကိုယ်တိုင် run ခြင်းအားဖြင့် ဒီပြဿနာကို ရှောင်ရှားနိုင်ပါတယ်။

Temporary tables တွေကို autovacuum က ဝင်ရောက်လို့ မရပါဘူး။ ဒါကြောင့် — သင့်လျော်တဲ့ vacuum နဲ့ analyze operations တွေကို session SQL commands တွေကနေတစ်ဆင့် လုပ်ဆောင်သင့်ပါတယ်။

Default thresholds တွေနဲ့ scale factors တွေကို `postgresql.conf` ကနေ ယူပါတယ် — ဒါပေမယ့် — သူတို့ကို (တခြား autovacuum control parameters အများအပြားကိုပါ) table တစ်ခုချင်းစီ အလိုက် override (ကျော်လွန် သတ်မှတ်) လုပ်ဖို့ ဖြစ်နိုင်ပါတယ်; အသေးစိတ်အတွက် [Storage Parameters](/docs/postgresql/sql-createtable) ကို ကြည့်ပါ။ Setting တစ်ခုကို table တစ်ခုရဲ့ storage parameters ကနေတစ်ဆင့် ပြောင်းလဲထားရင် — အဲဒီ table ကို process လုပ်တဲ့အခါ အဲဒီ တန်ဖိုးကို သုံးပါတယ်; မဟုတ်ရင် — global settings တွေကို သုံးပါတယ်။ Global settings တွေရဲ့ အသေးစိတ် ပိုမိုသိရှိဖို့ [အပိုင်း 19.10.1](https://www.postgresql.org/docs/current/runtime-config-vacuum.html#RUNTIME-CONFIG-AUTOVACUUM) ကို ကြည့်ပါ။

Workers အများအပြား run နေတဲ့အခါ — autovacuum cost delay parameters တွေကို (အပိုင်း [19.10.2](https://www.postgresql.org/docs/current/runtime-config-vacuum.html#RUNTIME-CONFIG-RESOURCE-VACUUM-COST) ကို ကြည့်ပါ) — run နေတဲ့ workers တွေ အားလုံးကြားမှာ “ချိန်ခွင်လျှာ ညှိပေး” (balanced) ပါတယ် — ဒါကြောင့် — တကယ် run နေတဲ့ workers အရေအတွက် ဘယ်လောက်ပဲ ရှိရှိ — system ပေါ်က စုစုပေါင်း I/O သက်ရောက်မှုက အတူတူပဲ ဖြစ်ပါတယ်။ ဒါပေမယ့် — per-table `autovacuum_vacuum_cost_delay` ဒါမှမဟုတ် `autovacuum_vacuum_cost_limit` storage parameters တွေ သတ်မှတ်ထားတဲ့ tables တွေကို process လုပ်နေတဲ့ workers တွေကတော့ — ချိန်ခွင်လျှာ ညှိပေးတဲ့ algorithm ထဲမှာ ထည့်သွင်း စဉ်းစားမခံရပါဘူး။

Autovacuum workers တွေက ယေဘုယျအားဖြင့် တခြား commands တွေကို ပိတ်ဆို့မထားပါဘူး။ Process တစ်ခုက — autovacuum က ကိုင်ထားတဲ့ `SHARE UPDATE EXCLUSIVE` lock နဲ့ ပဋိပက္ခ ဖြစ်တဲ့ lock တစ်ခုကို ရယူဖို့ ကြိုးစားရင် — lock acquisition က autovacuum ကို ကြားဖြတ် ရပ်တန့်စေပါတယ်။ ပဋိပက္ခ ဖြစ်တတ်တဲ့ lock modes တွေအတွက် — [ဇယား 13.2](/docs/postgresql/explicit-locking) ကို ကြည့်ပါ။ ဒါပေမယ့် — autovacuum က transaction ID wraparound ကို ကာကွယ်ဖို့ run နေတာဆိုရင် (ဆိုလိုတာက — `pg_stat_activity` view ထဲက autovacuum query name က `(to prevent wraparound)` နဲ့ အဆုံးသတ်နေရင်) — autovacuum ကို အလိုအလျောက် ကြားဖြတ် ရပ်တန့်တာ မလုပ်ပါဘူး။

> **သတိပေးချက်:** `SHARE UPDATE EXCLUSIVE` lock တစ်ခုနဲ့ ပဋိပက္ခ ဖြစ်တဲ့ locks တွေကို ရယူတဲ့ commands တွေ (ဥပမာ — ANALYZE) ကို ပုံမှန် run နေတာက — autovacuums တွေကို ဘယ်တော့မှ ပြီးမြောက်အောင် မလုပ်နိုင်အောင် ထိရောက်စွာ တားဆီးနိုင်ပါတယ်။
