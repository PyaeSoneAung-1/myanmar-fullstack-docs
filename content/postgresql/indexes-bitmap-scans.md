## 11.5. Combining Multiple Indexes (index များစွာ ပေါင်းစပ်အသုံးပြုခြင်း)

Index scan တစ်ခုတည်းက သုံးလို့ရတာက — index ရဲ့ column တွေကို ၎င်းရဲ့ operator class ထဲက operator တွေနဲ့ သုံးပြီး `AND` နဲ့ ချိတ်ဆက်ထားတဲ့ query clause တွေပဲ ဖြစ်ပါတယ်။ ဥပမာ — `(a, b)` ပေါ်မှာ index တစ်ခု ရှိနေရင် `WHERE a = 5 AND b = 6` လို query condition က index ကို သုံးနိုင်ပေမယ့် — `WHERE a = 5 OR b = 6` လို query ကတော့ index ကို တိုက်ရိုက် သုံးလို့ မရပါဘူး။

ကံကောင်းချင်တော့ — PostgreSQL မှာ index scan တစ်ခုတည်းနဲ့ အကောင်အထည် ဖော်လို့ မရတဲ့ အခြေအနေတွေကို ကိုင်တွယ်ဖို့ — index အများအပြားကို ပေါင်းစပ်အသုံးပြုနိုင်တဲ့ (တူညီတဲ့ index ကိုယ်တိုင်ကို အကြိမ်ကြိမ် သုံးတာ အပါအဝင်) စွမ်းရည် ရှိပါတယ်။ System က index scan အများအပြားကို ဖြတ်ပြီး `AND` နဲ့ `OR` condition တွေကို တည်ဆောက်နိုင်ပါတယ်။ ဥပမာ — `WHERE x = 42 OR x = 47 OR x = 53 OR x = 99` လို query တစ်ခုကို — `x` ပေါ်က index တစ်ခုကို scan လေးခု သီးခြားစီ လုပ်ပြီး — scan တစ်ခုချင်းစီက query clause တစ်ခုစီကို သုံးတဲ့ ပုံစံနဲ့ ခွဲခြမ်းလို့ ရပါတယ်။ ပြီးတော့ ဒီ scan တွေရဲ့ ရလဒ်တွေကို အတူတကွ OR လုပ်ပြီး နောက်ဆုံး ရလဒ်ကို ထုတ်ပေးပါတယ်။ နောက်ထပ် ဥပမာတစ်ခုက — `x` နဲ့ `y` ပေါ်မှာ သီးခြား index တွေ ရှိနေရင် — `WHERE x = 5 AND y = 6` လို query တစ်ခုကို အကောင်အထည် ဖော်ဖို့ ဖြစ်နိုင်တဲ့ နည်းလမ်းတစ်ခုက — index တစ်ခုချင်းစီကို သင့်လျော်တဲ့ query clause နဲ့ သုံးပြီး — ရလဒ် row တွေကို ခွဲခြားသတ်မှတ်နိုင်ဖို့ index ရလဒ်တွေကို အတူတကွ AND လုပ်တာ ဖြစ်ပါတယ်။

Index အများအပြားကို ပေါင်းစပ်ဖို့အတွက် — system က လိုအပ်တဲ့ index တစ်ခုချင်းစီကို scan လုပ်ပြီး — အဲဒီ index ရဲ့ condition တွေနဲ့ ကိုက်ညီတယ်လို့ သတင်းပို့ထားတဲ့ table row တွေရဲ့ တည်နေရာတွေကို ဖော်ပြတဲ့ *bitmap* (ရုပ်ပုံမြေပုံ) တစ်ခုကို memory ထဲမှာ ပြင်ဆင်ပါတယ်။ ပြီးတော့ bitmap တွေကို query က လိုအပ်သလို အတူတကွ AND ဒါမှမဟုတ် OR လုပ်ပါတယ်။ နောက်ဆုံးမှာတော့ တကယ့် table row တွေကို သွားရောက်ပြီး ပြန်ပေးပါတယ်။ Table row တွေကို physical order (ရုပ်ပိုင်း အစီအစဉ်) နဲ့ သွားရောက်ပါတယ် — bitmap ကို အဲဒီပုံစံအတိုင်း စီစဉ်ထားလို့ပါ; ဆိုလိုတာက — မူလ index တွေရဲ့ ဘယ်အစီအစဉ်မဆို ပျောက်ဆုံးသွားပြီး — query မှာ `ORDER BY` clause ပါရင် သီးခြား sort step (စီစဉ်သည့် အဆင့်) တစ်ခု လိုအပ်လာမှာ ဖြစ်ပါတယ်။ ဒီအကြောင်းကြောင့်ရော — index scan တစ်ခုစီ ထပ်တိုင်း အချိန် ပိုယူလို့ပါ — planner က တခါတရံမှာ — အပိုဆောင်း index တွေ ရှိနေပြီး အဲဒါတွေကိုပါ သုံးလို့ ရနိုင်ပေမယ့်လည်း — ရိုးရှင်းတဲ့ index scan တစ်ခုကိုပဲ သုံးဖို့ ရွေးချယ်တတ်ပါတယ်။

အရိုးရှင်းဆုံး application တွေကလွဲလို့ ကျန်တာ အားလုံးမှာ — အသုံးဝင်နိုင်တဲ့ index ပေါင်းစပ်မှု အမျိုးမျိုး ရှိတတ်ပြီး — database developer က ဘယ် index တွေကို ထောက်ပံ့ပေးမလဲ ဆုံးဖြတ်ဖို့ အပေးအယူ (trade-off) တွေ လုပ်ရပါတယ်။ တခါတရံ multicolumn index တွေက အကောင်းဆုံး ဖြစ်ပေမယ့် — တခါတရံမှာတော့ index တွေကို သီးခြားစီ ဖန်တီးပြီး index ပေါင်းစပ်ခြင်း feature ကို အားကိုးတာ ပိုကောင်းပါတယ်။ ဥပမာ — သင့် workload ထဲမှာ တခါတရံ column `x` တစ်ခုတည်းပဲ ပါဝင်တဲ့ query၊ တခါတရံ column `y` တစ်ခုတည်းပဲ ပါဝင်တဲ့ query၊ တခါတရံ column နှစ်ခုလုံး ပါဝင်တဲ့ query တွေ ရောနှော ပါဝင်နေရင် — column နှစ်ခုလုံး သုံးတဲ့ query တွေကို process လုပ်ဖို့ index ပေါင်းစပ်မှုကို အားကိုးပြီး — `x` နဲ့ `y` ပေါ်မှာ သီးခြား index နှစ်ခု ဖန်တီးဖို့ ရွေးချယ်နိုင်ပါတယ်။ `(x, y)` ပေါ်မှာ multicolumn index တစ်ခုကိုလည်း ဖန်တီးလို့ ရပါတယ်။ ဒီ index က column နှစ်ခုလုံး ပါဝင်တဲ့ query တွေအတွက် index ပေါင်းစပ်မှုထက် ပုံမှန်အားဖြင့် ပိုထိရောက်ပေမယ့် — [အပိုင်း 11.3](/docs/postgresql/indexes-multicolumn) မှာ ဆွေးနွေးခဲ့သလိုပဲ — column `y` တစ်ခုတည်းပဲ ပါဝင်တဲ့ query တွေအတွက်တော့ အသုံးဝင်မှု နည်းပါတယ်။ ဘယ်လောက် အသုံးဝင်လဲဆိုတာက B-tree index ရဲ့ skip scan optimization (ခုန်ကျော် scan ပြုလုပ်ခြင်း ဆိုတဲ့ ပိုမိုကောင်းမွန်အောင် ပြုလုပ်မှု) ဘယ်လောက် ထိရောက်လဲပေါ်မှာ မူတည်ပါတယ်; `x` မှာ distinct value ရာဂဏန်း ထက်မပိုရင် — skip scan က တိကျတဲ့ `y` တန်ဖိုးတွေအတွက် ရှာဖွေမှုတွေကို ကျိုးကြောင်းဆီလျော်စွာ ထိရောက်အောင် execute လုပ်ပေးနိုင်ပါလိမ့်မယ်။ `(x, y)` ပေါ်က multicolumn index တစ်ခုနဲ့ `y` ပေါ်က သီးခြား index တစ်ခုရဲ့ ပေါင်းစပ်မှုကလည်း အတော်အသင့် ကောင်းကောင်း ဆောင်ရွက်ပေးနိုင်ပါတယ်။ Column `x` တစ်ခုတည်းပဲ ပါဝင်တဲ့ query တွေအတွက်တော့ — multicolumn index ကို သုံးလို့ ရပေမယ့် — `x` တစ်ခုတည်းပေါ်က index ထက် ပိုကြီးပြီး ဒါကြောင့် ပိုနှေးတာကြောင့် — အဲဒီလောက် မကောင်းပါဘူး။ နောက်ဆုံး ရွေးစရာကတော့ index သုံးခုလုံး ဖန်တီးတာပါ — ဒါပေမယ့် table ကို update လုပ်တာထက် search လုပ်တာ ပိုများပြီး — query အမျိုးအစား သုံးခုလုံး အဖြစ်များမှသာ ဒါက ကျိုးကြောင်းဆီလျော်နိုင်ပါတယ်။ Query အမျိုးအစား တစ်ခုက တခြားဟာတွေထက် အများကြီး အဖြစ်နည်းနေရင် — အဖြစ်များတဲ့ query အမျိုးအစားတွေနဲ့ အကောင်းဆုံး ကိုက်ညီတဲ့ index နှစ်ခုကိုပဲ ဖန်တီးလိုက်ရုံနဲ့ ကျေနပ်နေဖို့ ဖြစ်နိုင်ပါတယ်။
