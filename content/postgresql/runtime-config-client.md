### 19.11.1. Statement Behavior (statement အပြုအမူ)

- **client_min_messages (enum)** — Client ဆီ ပို့မယ့် message level တွေကို ထိန်းချုပ်ပါတယ်။ တရားဝင် တန်ဖိုးတွေက DEBUG5, DEBUG4, DEBUG3, DEBUG2, DEBUG1, LOG, NOTICE, WARNING နဲ့ ERROR တို့ ဖြစ်ပါတယ်။ Level တစ်ခုချင်းစီက သူ့နောက်မှာ လိုက်လာတဲ့ level အားလုံးကို ပါဝင်စေပါတယ်။ Level နောက်ကျလေလေ — ပို့တဲ့ message နည်းလေလေ ဖြစ်ပါတယ်။ Default က NOTICE ဖြစ်ပါတယ်။ log_min_messages ထဲကနဲ့ မတူဘဲ — ဒီနေရာမှာ LOG ရဲ့ အဆင့် (rank) က ကွာခြားပါတယ် ဆိုတာ သတိပြုပါ။
INFO level message တွေကို client ဆီ အမြဲ ပို့ပါတယ်။
- **search_path (string)** — ဒီ variable က — schema မသတ်မှတ်ဘဲ simple name တစ်ခုနဲ့ object (table, data type, function စသည်) တစ်ခုကို ရည်ညွှန်းတဲ့အခါ — schema တွေကို ရှာဖွေမယ့် အစီအစဉ်ကို သတ်မှတ်ပါတယ်။ Schema မတူညီတဲ့ နေရာတွေမှာ အမည်တူ object တွေ ရှိနေရင် — search path ထဲမှာ ပထမဆုံး တွေ့တဲ့ object ကို သုံးပါတယ်။ Search path ထဲက schema တစ်ခုမှာမှ မပါဝင်တဲ့ object ကို — သူ့ကို ပါဝင်တဲ့ schema ကို qualified (အစက်ချ) name နဲ့ သတ်မှတ်ပြီးမှသာ ရည်ညွှန်းနိုင်ပါတယ်။
search_path ရဲ့ တန်ဖိုးက comma နဲ့ ခွဲထားတဲ့ schema name တွေရဲ့ စာရင်း ဖြစ်ရပါမယ်။ ရှိပြီးသား schema မဟုတ်တဲ့ အမည်၊ ဒါမှမဟုတ် user က USAGE permission မရှိတဲ့ schema တစ်ခုရဲ့ အမည်ကို တိတ်တဆိတ် လျစ်လျူရှုပါတယ်။
စာရင်းထဲက item တစ်ခုက $user ဆိုတဲ့ အထူး အမည် ဖြစ်ရင် — CURRENT_USER က ပြန်ပေးတဲ့ အမည်ရှိတဲ့ schema ကို အစားထိုးပါတယ် — အဲဒီလို schema ရှိပြီး user မှာ USAGE permission ရှိရင်ပါ။ (မရှိရင် $user ကို လျစ်လျူရှုပါတယ်။)
System catalog schema ဖြစ်တဲ့ pg_catalog ကို path ထဲ ဖော်ပြထားသည်ဖြစ်စေ မဖော်ပြထားသည်ဖြစ်စေ — အမြဲ ရှာဖွေပါတယ်။ Path ထဲ ဖော်ပြထားရင် — သတ်မှတ်ထားတဲ့ အစီအစဉ်အတိုင်း ရှာပါတယ်။ pg_catalog က path ထဲ မပါရင် — path item တွေကို မရှာမီ အရင်ဆုံး ရှာပါတယ်။
အလားတူပဲ — လက်ရှိ session ရဲ့ temporary-table schema ဖြစ်တဲ့ pg_temp_nnn ကို ရှိရင် အမြဲ ရှာပါတယ်။ pg_temp ဆိုတဲ့ alias ကို သုံးပြီး path ထဲမှာ အတိအကျ ထည့်သွင်း ဖော်ပြနိုင်ပါတယ်။ Path ထဲ မထည့်ထားရင် — (pg_catalog မတိုင်မီအထိ) အရင်ဆုံး ရှာပါတယ်။ ဒါပေမယ့် temporary schema ကို relation (table, view, sequence စသည်) နဲ့ data type အမည်တွေအတွက်သာ ရှာပါတယ်။ function ဒါမှမဟုတ် operator အမည်တွေအတွက် ရှာတာ ဘယ်တော့မှ မရှိပါဘူး။
Object တွေကို target schema သတ်မှတ်မထားဘဲ ဖန်တီးတဲ့အခါ — search_path ထဲမှာ ပထမဆုံး တရားဝင်တဲ့ schema ထဲမှာ ထည့်သွားပါတယ်။ Search path က ဗလာ ဖြစ်နေရင် error တင်ပြပါတယ်။
ဒီ parameter ရဲ့ default တန်ဖိုးက "$user", public ဖြစ်ပါတယ်။ ဒီ setting က — (user တွေမှာ private schema မရှိဘဲ အားလုံး public ကို မျှဝေ သုံးတဲ့) database ကို မျှဝေ အသုံးပြုမှု၊ user တစ်ဦးချင်း သီးသန့် private schema တွေ၊ ဒါတွေ ပေါင်းစပ်မှုကို ထောက်ပံ့ပါတယ်။ Global အနေနဲ့ဖြစ်စေ per-user အနေနဲ့ဖြစ်စေ default search path setting ကို ပြောင်းခြင်းဖြင့် အခြား သက်ရောက်မှုတွေ ရနိုင်ပါတယ်။
Schema ကိုင်တွယ်မှု အကြောင်း ပိုမို သိရှိရန် [အပိုင်း 5.10](/docs/postgresql/ddl-schemas) ကို ကြည့်ပါ။ အထူးသဖြင့် — default configuration က database မှာ user တစ်ဦးတည်း ဒါမှမဟုတ် အပြန်အလှန် ယုံကြည်ကြတဲ့ user အနည်းငယ်သာ ရှိတဲ့အခါမှသာ သင့်လျော်ပါတယ်။
Search path ရဲ့ လက်ရှိ အာနိသင် ရှိတဲ့ (effective) တန်ဖိုးကို SQL function ဖြစ်တဲ့ current_schemas နဲ့ စစ်ဆေးကြည့်နိုင်ပါတယ် ([အပိုင်း 9.27](/docs/postgresql/functions-info) ကို ကြည့်ပါ)။ ဒါက search_path ရဲ့ တန်ဖိုးကို စစ်ကြည့်တာနဲ့ အတိအကျ မတူပါဘူး — အကြောင်းက current_schemas က search_path ထဲ ပါဝင်တဲ့ item တွေ ဘယ်လို ဖြေရှင်း (resolve) ခဲ့တာကို ပြတာမို့ပါ။
- **row_security (boolean)** — ဒီ variable က row security policy တစ်ခုကို အသုံးချမယ့်အစား error တင်မလား ဆိုတာကို ထိန်းချုပ်ပါတယ်။ on သတ်မှတ်ရင် — policy တွေ ပုံမှန်အတိုင်း အသုံးချပါတယ်။ off သတ်မှတ်ရင် — အနည်းဆုံး policy တစ်ခု အသုံးချရမယ့် query တွေ ကျရှုံး (fail) ပါတယ်။ Default က on ဖြစ်ပါတယ်။ Row visibility ကန့်သတ်ထားမှုက မှားယွင်းတဲ့ ရလဒ်တွေ ဖြစ်စေနိုင်တဲ့ နေရာတွေမှာ off ကို ပြောင်းပါ; ဥပမာ — pg_dump က default အားဖြင့် အဲဒီလို ပြောင်းပါတယ်။ ဒီ variable က row security policy အားလုံးကို ကျော်ဖြတ်တဲ့ role တွေ — ဆိုလိုတာက superuser တွေနဲ့ BYPASSRLS attribute ရှိတဲ့ role တွေ — အပေါ် သက်ရောက်မှု မရှိပါဘူး။
Row security policy တွေ အကြောင်း ပိုမို သိရှိရန် [CREATE POLICY](/docs/postgresql/sql-createpolicy) ကို ကြည့်ပါ။
- **default_table_access_method (string)** — CREATE command က access method ကို အတိအကျ မသတ်မှတ်တဲ့အခါ — ဒါမှမဟုတ် table access method သတ်မှတ်ခွင့် မပြုတဲ့ SELECT ... INTO ကို သုံးတဲ့အခါ — table ဒါမှမဟုတ် materialized view တွေ ဖန်တီးရာမှာ သုံးမယ့် default table access method ကို ဒီ parameter က သတ်မှတ်ပါတယ်။ Default က heap ဖြစ်ပါတယ်။
- **default_tablespace (string)** — CREATE command က tablespace ကို အတိအကျ မသတ်မှတ်တဲ့အခါ — object (table နဲ့ index) တွေ ဖန်တီးရမယ့် default tablespace ကို ဒီ variable က သတ်မှတ်ပါတယ်။
တန်ဖိုးက tablespace တစ်ခုရဲ့ အမည် ဒါမှမဟုတ် — လက်ရှိ database ရဲ့ default tablespace ကို သုံးဖို့ သတ်မှတ်တဲ့ empty string တစ်ခု ဖြစ်ပါတယ်။ တန်ဖိုးက ရှိပြီးသား tablespace တစ်ခုရဲ့ အမည်နဲ့ မကိုက်ညီရင် — PostgreSQL က လက်ရှိ database ရဲ့ default tablespace ကို အလိုအလျောက် သုံးပါလိမ့်မယ်။ default မဟုတ်တဲ့ tablespace တစ်ခုကို သတ်မှတ်ရင် — user မှာ အဲဒါအတွက် CREATE privilege ရှိရပါမယ်; မရှိရင် ဖန်တီးမှု ကြိုးပမ်းချက်တွေ ကျရှုံးပါလိမ့်မယ်။
ဒီ variable ကို temporary table တွေအတွက် မသုံးပါဘူး; အဲဒါတွေအတွက်တော့ temp_tablespaces ကို အစားထိုး ကြည့်ပါတယ်။
Database တွေ ဖန်တီးတဲ့အခါလည်း ဒီ variable ကို မသုံးပါဘူး။ Default အားဖြင့် — database အသစ်တစ်ခုက သူ ကူးယူတဲ့ template database ဆီက tablespace setting ကို အမွေခံပါတယ်။
Partitioned table တစ်ခု ဖန်တီးတဲ့အခါ ဒီ parameter ကို empty string မဟုတ်တဲ့ တန်ဖိုးတစ်ခု သတ်မှတ်ထားရင် — partitioned table ရဲ့ tablespace ကို အဲဒီတန်ဖိုးအဖြစ် သတ်မှတ်ပါလိမ့်မယ်; နောက်ပိုင်း ဖန်တီးမယ့် partition တွေအတွက် default tablespace အဖြစ် သုံးမှာ ဖြစ်ပြီး — အဲဒီနောက်ပိုင်း default_tablespace ပြောင်းသွားရင်တောင်မှ အဲဒီတန်ဖိုးကို သုံးပါလိမ့်မယ်။
Tablespace တွေ အကြောင်း ပိုမို သိရှိရန် [အပိုင်း 22.6](/docs/postgresql/manage-ag-tablespaces) ကို ကြည့်ပါ။
- **default_toast_compression (enum)** — ဒီ variable က compressible column တွေရဲ့ တန်ဖိုးတွေအတွက် default TOAST compression method ကို သတ်မှတ်ပါတယ်။ (CREATE TABLE ဒါမှမဟုတ် ALTER TABLE ထဲမှာ COMPRESSION column option ကို သတ်မှတ်ခြင်းဖြင့် column တစ်ခုချင်းစီအတွက် ဒါကို ကျော်လွှား (override) နိုင်ပါတယ်။) ထောက်ပံ့တဲ့ compression method တွေက pglz နဲ့ (PostgreSQL ကို --with-lz4 နဲ့ compile လုပ်ထားရင်) lz4 ဖြစ်ပါတယ်။ Default က pglz ဖြစ်ပါတယ်။
- **temp_tablespaces (string)** — CREATE command က tablespace ကို အတိအကျ မသတ်မှတ်တဲ့အခါ — temporary object (temp table တွေနဲ့ temp table တွေပေါ်က index တွေ) ဖန်တီးရမယ့် tablespace တွေကို ဒီ variable က သတ်မှတ်ပါတယ်။ ဒေတာ အစုအဝေး ကြီးတွေကို sort လုပ်တာလို ရည်ရွယ်ချက်တွေအတွက် temporary file တွေလည်း ဒီ tablespace တွေထဲမှာ ဖန်တီးပါတယ်။
တန်ဖိုးက tablespace အမည်တွေရဲ့ စာရင်းတစ်ခု ဖြစ်ပါတယ်။ စာရင်းထဲမှာ အမည်တစ်ခုထက် ပိုရှိရင် — temporary object တစ်ခု ဖန်တီးတိုင်း PostgreSQL က စာရင်းထဲက member တစ်ခုကို ကျပန်း (random) ရွေးပါတယ်; ဒါပေမယ့် transaction တစ်ခုအတွင်းမှာတော့ — ဆက်တိုက် ဖန်တီးတဲ့ temporary object တွေကို စာရင်းထဲက tablespace တွေဆီ အစဉ်လိုက် ထည့်ပါတယ်။ ရွေးလိုက်တဲ့ စာရင်း element က empty string ဖြစ်ရင် — PostgreSQL က လက်ရှိ database ရဲ့ default tablespace ကို အလိုအလျောက် အစားထိုး သုံးပါလိမ့်မယ်။
temp_tablespaces ကို interactive အနေနဲ့ သတ်မှတ်တဲ့အခါ — မရှိတဲ့ tablespace တစ်ခုကို သတ်မှတ်တာက error ဖြစ်ပြီး — user မှာ CREATE privilege မရှိတဲ့ tablespace သတ်မှတ်တာလည်း error ဖြစ်ပါတယ်။ ဒါပေမယ့် — ယခင် သတ်မှတ်ထားပြီးသား တန်ဖိုးကို သုံးတဲ့အခါ — မရှိတဲ့ tablespace တွေကို လျစ်လျူရှုပြီး — user မှာ CREATE privilege မရှိတဲ့ tablespace တွေကိုလည်း လျစ်လျူရှုပါတယ်။ အထူးသဖြင့် — postgresql.conf ထဲမှာ သတ်မှတ်ထားတဲ့ တန်ဖိုးကို သုံးတဲ့အခါ ဒီစည်းမျဉ်း သက်ရောက်ပါတယ်။
Default တန်ဖိုးက empty string ဖြစ်ပြီး — ရလဒ်အနေနဲ့ temporary object အားလုံးကို လက်ရှိ database ရဲ့ default tablespace ထဲမှာ ဖန်တီးပါတယ်။
default_tablespace ကိုလည်း ကြည့်ပါ။
- **check_function_bodies (boolean)** — ဒီ parameter က ပုံမှန်အားဖြင့် on ဖြစ်ပါတယ်။ off သတ်မှတ်ရင် — CREATE FUNCTION နဲ့ CREATE PROCEDURE လုပ်တဲ့အခါ routine body string ကို validation လုပ်တာကို ပိတ်ပါတယ်။ Validation ပိတ်ထားခြင်းက validation လုပ်ငန်းစဉ်ရဲ့ side effect တွေကို ရှောင်ရှားပေးပြီး — အထူးသဖြင့် forward reference လို ပြဿနာတွေကြောင့် ဖြစ်တဲ့ false positive တွေကို တားဆီးပေးပါတယ်။ အခြား user တွေကိုယ်စား function တွေ load မလုပ်မီ ဒီ parameter ကို off သတ်မှတ်ပါ; pg_dump က အလိုအလျောက် အဲဒီလို လုပ်ပါတယ်။
- **default_transaction_isolation (enum)** — SQL transaction တစ်ခုချင်းစီမှာ isolation level တစ်ခု ရှိပြီး — အဲဒါက “read uncommitted”, “read committed”, “repeatable read” ဒါမှမဟုတ် “serializable” ဖြစ်နိုင်ပါတယ်။ ဒီ parameter က transaction အသစ် တစ်ခုချင်းစီရဲ့ default isolation level ကို ထိန်းချုပ်ပါတယ်။ Default က “read committed” ဖြစ်ပါတယ်။
ပိုမို သိရှိရန် [အခန်း 13](https://www.postgresql.org/docs/current/mvcc.html) နဲ့ [SET TRANSACTION](/docs/postgresql/sql-set-transaction) ကို ကြည့်ပါ။
- **default_transaction_read_only (boolean)** — Read-only SQL transaction တစ်ခုက non-temporary table တွေကို ပြောင်းလဲနိုင်မှာ မဟုတ်ပါဘူး။ ဒီ parameter က transaction အသစ် တစ်ခုချင်းစီရဲ့ default read-only အခြေအနေကို ထိန်းချုပ်ပါတယ်။ Default က off (read/write) ဖြစ်ပါတယ်။
ပိုမို သိရှိရန် [SET TRANSACTION](/docs/postgresql/sql-set-transaction) ကို ကြည့်ပါ။
- **default_transaction_deferrable (boolean)** — Serializable isolation level မှာ run နေတဲ့အခါ — deferrable read-only SQL transaction တစ်ခုကို ဆက်လက် လုပ်ဆောင်ခွင့် မပြုမီ နှောင့်နှေးစေနိုင်ပါတယ်။ ဒါပေမယ့် — စတင် လုပ်ဆောင်ပြီးတာနဲ့ — serializability သေချာစေဖို့ လိုအပ်တဲ့ overhead တွေထဲက ဘာတစ်ခုမှ မကျခံရတာမို့ — serialization code က concurrent update တွေကြောင့် ဒါကို abort လုပ်ဖို့ အကြောင်း မရှိတော့ပါဘူး; ဒါကြောင့် ဒီ option က ကြာကြာ run တဲ့ read-only transaction တွေအတွက် သင့်လျော်ပါတယ်။
ဒီ parameter က transaction အသစ် တစ်ခုချင်းစီရဲ့ default deferrable အခြေအနေကို ထိန်းချုပ်ပါတယ်။ လက်ရှိအချိန်မှာ read-write transaction တွေ ဒါမှမဟုတ် serializable ထက် နိမ့်တဲ့ isolation level တွေမှာ လည်ပတ်တဲ့ အရာတွေအပေါ် သက်ရောက်မှု မရှိပါဘူး။ Default က off ဖြစ်ပါတယ်။
ပိုမို သိရှိရန် [SET TRANSACTION](/docs/postgresql/sql-set-transaction) ကို ကြည့်ပါ။
- **transaction_isolation (enum)** — ဒီ parameter က လက်ရှိ transaction ရဲ့ isolation level ကို ထင်ဟပ်ပြပါတယ်။ Transaction တစ်ခုချင်းစီရဲ့ အစမှာ — default_transaction_isolation ရဲ့ လက်ရှိ တန်ဖိုးအဖြစ် သတ်မှတ်ပါတယ်။ နောက်ပိုင်း ဒါကို ပြောင်းလဲဖို့ ကြိုးပမ်းမှုတိုင်းက SET TRANSACTION command နဲ့ အတူတူပါပဲ။
- **transaction_read_only (boolean)** — ဒီ parameter က လက်ရှိ transaction ရဲ့ read-only အခြေအနေကို ထင်ဟပ်ပြပါတယ်။ Transaction တစ်ခုချင်းစီရဲ့ အစမှာ — default_transaction_read_only ရဲ့ လက်ရှိ တန်ဖိုးအဖြစ် သတ်မှတ်ပါတယ်။ နောက်ပိုင်း ဒါကို ပြောင်းလဲဖို့ ကြိုးပမ်းမှုတိုင်းက SET TRANSACTION command နဲ့ အတူတူပါပဲ။
- **transaction_deferrable (boolean)** — ဒီ parameter က လက်ရှိ transaction ရဲ့ deferrability အခြေအနေကို ထင်ဟပ်ပြပါတယ်။ Transaction တစ်ခုချင်းစီရဲ့ အစမှာ — default_transaction_deferrable ရဲ့ လက်ရှိ တန်ဖိုးအဖြစ် သတ်မှတ်ပါတယ်။ နောက်ပိုင်း ဒါကို ပြောင်းလဲဖို့ ကြိုးပမ်းမှုတိုင်းက SET TRANSACTION command နဲ့ အတူတူပါပဲ။
- **session_replication_role (enum)** — လက်ရှိ session အတွက် replication ဆိုင်ရာ trigger တွေနဲ့ rule တွေ ဖြစ်ပေါ်မှုကို ထိန်းချုပ်ပါတယ်။ ဖြစ်နိုင်တဲ့ တန်ဖိုးတွေက origin (default), replica နဲ့ local ဖြစ်ပါတယ်။ ဒီ parameter ကို သတ်မှတ်ခြင်းက — ယခင် cache လုပ်ထားတဲ့ query plan တွေကို ဖျက်ပစ်စေပါတယ်။ Superuser တွေနဲ့ သင့်လျော်တဲ့ SET privilege ရှိတဲ့ user တွေသာ ဒီ setting ကို ပြောင်းနိုင်ပါတယ်။
ဒီ setting ရဲ့ ရည်ရွယ်ထားတဲ့ အသုံးပြုမှုက — logical replication system တွေက ပုံတူကူး ပြောင်းလဲမှုတွေကို apply လုပ်နေတဲ့အခါ ဒါကို replica အဖြစ် သတ်မှတ်တာပါ။ အဲဒါရဲ့ အကျိုးသက်ရောက်မှုက — (default configuration ကနေ ပြောင်းလဲမထားတဲ့) trigger တွေနဲ့ rule တွေ replica ပေါ်မှာ ဖြစ်ပေါ်မှာ မဟုတ်တာပါ။ ပိုမို သိရှိရန် ALTER TABLE clause တွေဖြစ်တဲ့ ENABLE TRIGGER နဲ့ ENABLE RULE ကို ကြည့်ပါ။
PostgreSQL က origin နဲ့ local setting တွေကို အတွင်းပိုင်းမှာ အတူတူပဲ သဘောထားပါတယ်။ Third-party replication system တွေက ဒီတန်ဖိုး နှစ်ခုကို သူတို့ရဲ့ အတွင်းပိုင်း ရည်ရွယ်ချက်တွေအတွက် သုံးနိုင်ပါတယ် — ဥပမာ — ပြောင်းလဲမှုတွေကို ပုံတူမကူးသင့်တဲ့ session တစ်ခုကို သတ်မှတ်ဖို့ local ကို သုံးတာမျိုးပါ။
Foreign key တွေကို trigger တွေအဖြစ် implement လုပ်ထားတာမို့ — ဒီ parameter ကို replica သတ်မှတ်ခြင်းက foreign key စစ်ဆေးမှု အားလုံးကိုလည်း ပိတ်စေပြီး — မသင့်လျော်စွာ သုံးရင် ဒေတာကို မကိုက်ညီတဲ့ အခြေအနေမှာ ထားခဲ့နိုင်ပါတယ်။
- **statement_timeout (integer)** — သတ်မှတ်ထားတဲ့ အချိန်ထက် ပိုကြာတဲ့ statement တိုင်းကို ရပ်ပစ်ပါ။ log_min_error_statement ကို ERROR ဒါမှမဟုတ် အောက်ပိုင်း သတ်မှတ်ထားရင် — timeout ဖြစ်သွားတဲ့ statement ကိုလည်း log မှတ်ပါလိမ့်မယ်။ ဒီတန်ဖိုးကို unit မသတ်မှတ်ဘဲ ပေးရင် — millisecond အဖြစ် ယူပါတယ်။ သုည (default) က timeout ကို ပိတ်ပါတယ်။
Timeout ကို — command တစ်ခု server ဆီ ရောက်လာချိန်ကနေ server က ပြီးဆုံးစေချိန်အထိ တိုင်းတာပါတယ်။ Simple-query message တစ်ခုတည်းထဲမှာ SQL statement အများအပြား ပါလာရင် — timeout ကို statement တစ်ခုချင်းစီအတွက် သီးခြားစီ အသုံးချပါတယ်။ (PostgreSQL ဗားရှင်း 13 မတိုင်မီက — timeout ကို query string တစ်ခုလုံးအပေါ် အသုံးချတယ်လို့ များသောအားဖြင့် သဘောထားပါတယ်။) Extended query protocol ထဲမှာ — timeout က query ဆိုင်ရာ message တစ်ခုခု (Parse, Bind, Execute, Describe) ရောက်တာနဲ့ စတင် လည်ပတ်ပြီး — Execute ဒါမှမဟုတ် Sync message ပြီးဆုံးတာနဲ့ ပယ်ဖျက်ပါတယ်။
postgresql.conf ထဲမှာ statement_timeout သတ်မှတ်တာကို မအကြံပြုပါဘူး — အကြောင်းက session အားလုံးအပေါ် သက်ရောက်မှာ မို့ပါ။
- **transaction_timeout (integer)** — Transaction တစ်ခုအတွင်း သတ်မှတ်ထားတဲ့ အချိန်ထက် ပိုကြာကြာ တည်ရှိနေတဲ့ session တိုင်းကို ရပ်ဆိုင်းပါ။ ဒီကန့်သတ်ချက်က — (BEGIN နဲ့ စတင်တဲ့) explicit transaction တွေအပြင် — statement တစ်ခုတည်းနဲ့ သက်ဆိုင်တဲ့ implicit အနေနဲ့ စတင်တဲ့ transaction တွေအပေါ်လည်း သက်ရောက်ပါတယ်။ ဒီတန်ဖိုးကို unit မသတ်မှတ်ဘဲ ပေးရင် — millisecond အဖြစ် ယူပါတယ်။ သုည (default) က timeout ကို ပိတ်ပါတယ်။
transaction_timeout က idle_in_transaction_session_timeout ဒါမှမဟုတ် statement_timeout ထက် တိုတာ ဒါမှမဟုတ် ညီတာ ဖြစ်ရင် — ပိုရှည်တဲ့ timeout ကို လျစ်လျူရှုပါတယ်။
postgresql.conf ထဲမှာ transaction_timeout သတ်မှတ်တာကို မအကြံပြုပါဘူး — အကြောင်းက session အားလုံးအပေါ် သက်ရောက်မှာ မို့ပါ။

> **မှတ်ချက်:** Prepared transaction တွေက ဒီ timeout ရဲ့ သက်ရောက်မှုကို မခံရပါဘူး။
- **lock_timeout (integer)** — Table, index, row ဒါမှမဟုတ် အခြား database object တစ်ခုပေါ်မှာ lock ရယူဖို့ ကြိုးစားနေစဉ် သတ်မှတ်ထားတဲ့ အချိန်ထက် ပိုကြာစွာ စောင့်ရတဲ့ statement တိုင်းကို ရပ်ပစ်ပါ။ အချိန် ကန့်သတ်ချက်က lock ရယူဖို့ ကြိုးစားမှု တစ်ခုချင်းစီအတွက် သီးခြားစီ သက်ရောက်ပါတယ်။ ဒီကန့်သတ်ချက်က — (LOCK TABLE, ဒါမှမဟုတ် NOWAIT မပါတဲ့ SELECT FOR UPDATE လို) explicit locking request တွေအပြင် — implicit အနေနဲ့ ရရှိတဲ့ lock တွေအပေါ်လည်း သက်ရောက်ပါတယ်။ ဒီတန်ဖိုးကို unit မသတ်မှတ်ဘဲ ပေးရင် — millisecond အဖြစ် ယူပါတယ်။ သုည (default) က timeout ကို ပိတ်ပါတယ်။
statement_timeout နဲ့ မတူဘဲ — ဒီ timeout က lock တွေကို စောင့်နေစဉ်မှာသာ ဖြစ်ပေါ်နိုင်ပါတယ်။ statement_timeout က သုည မဟုတ်ရင် — lock_timeout ကို အဲဒီအတူတူ ဒါမှမဟုတ် ပိုကြီးတဲ့ တန်ဖိုး သတ်မှတ်တာက သိပ်အဓိပ္ပာယ် မရှိပါဘူး — အကြောင်းက statement timeout က အမြဲ အရင် trigger ဖြစ်မှာ မို့ပါ။ log_min_error_statement ကို ERROR ဒါမှမဟုတ် အောက်ပိုင်း သတ်မှတ်ထားရင် — timeout ဖြစ်သွားတဲ့ statement ကို log မှတ်ပါလိမ့်မယ်။
postgresql.conf ထဲမှာ lock_timeout သတ်မှတ်တာကို မအကြံပြုပါဘူး — အကြောင်းက session အားလုံးအပေါ် သက်ရောက်မှာ မို့ပါ။
- **idle_in_transaction_session_timeout (integer)** — ဖွင့်ထားတဲ့ transaction တစ်ခုအတွင်း (ဆိုလိုတာက client query တစ်ခုကို စောင့်နေတာ) သတ်မှတ်ထားတဲ့ အချိန်ထက် ပိုကြာကြာ idle ဖြစ်နေတဲ့ session တိုင်းကို ရပ်ဆိုင်းပါ။ ဒီတန်ဖိုးကို unit မသတ်မှတ်ဘဲ ပေးရင် — millisecond အဖြစ် ယူပါတယ်။ သုည (default) က timeout ကို ပိတ်ပါတယ်။
ဒီ option ကို — idle session တွေက lock တွေကို မသင့်လျော်တဲ့ အချိန်ကြာကြာ ကိုင်ထားမနေစေဖို့ သေချာစေရန် သုံးနိုင်ပါတယ်။ အရေးပါတဲ့ lock တွေ မကိုင်ထားတဲ့အခါမှာတောင် — ဖွင့်ထားတဲ့ transaction တစ်ခုက ဒီ transaction အတွက်သာ မြင်နိုင်တဲ့ recently-dead tuple တွေကို vacuum လုပ်ဖို့ တားဆီးထားပါတယ်; ဒါကြောင့် ကြာကြာ idle နေခြင်းက table bloat ဖြစ်စေနိုင်ပါတယ်။ အသေးစိတ်အတွက် [အပိုင်း 24.1](/docs/postgresql/routine-vacuuming) ကို ကြည့်ပါ။
- **idle_session_timeout (integer)** — ဖွင့်ထားတဲ့ transaction တစ်ခုအတွင်း မဟုတ်ဘဲ (ဆိုလိုတာက client query တစ်ခုကို စောင့်နေတာ) သတ်မှတ်ထားတဲ့ အချိန်ထက် ပိုကြာကြာ idle ဖြစ်နေတဲ့ session တိုင်းကို ရပ်ဆိုင်းပါ။ ဒီတန်ဖိုးကို unit မသတ်မှတ်ဘဲ ပေးရင် — millisecond အဖြစ် ယူပါတယ်။ သုည (default) က timeout ကို ပိတ်ပါတယ်။
ဖွင့်ထားတဲ့ transaction ရှိတဲ့ အခြေအနေနဲ့ မတူဘဲ — transaction မပါတဲ့ idle session တစ်ခုက server အပေါ် ကြီးမားတဲ့ ကုန်ကျစရိတ် တစ်ခုမှ မသက်ရောက်စေတာမို့ — idle_in_transaction_session_timeout လောက် ဒီ timeout ကို ဖွင့်ထားဖို့ လိုအပ်မှု နည်းပါတယ်။
Connection-pooling software ဒါမှမဟုတ် အခြား middleware ကတစ်ဆင့် ချိတ်ဆက်တဲ့ connection တွေအပေါ် ဒီ timeout ကို ကြပ်မတ် (enforce) တာကို သတိထားပါ — အကြောင်းက အဲဒီလို အလွှာတွေက မမျှော်လင့်တဲ့ connection ပိတ်ခြင်းကို ကောင်းကောင်း တုံ့ပြန်ချင်မှ တုံ့ပြန်ပါလိမ့်မယ်။ ဒီ timeout ကို interactive session တွေအတွက်သာ — ဥပမာ — အချို့ user တွေအပေါ်မှာသာ အသုံးချပြီး ဖွင့်ထားတာ အကျိုးရှိနိုင်ပါတယ်။
- **bytea_output (enum)** — bytea အမျိုးအစား တန်ဖိုးတွေအတွက် output format ကို သတ်မှတ်ပါတယ်။ တရားဝင် တန်ဖိုးတွေက hex (default) နဲ့ escape (ရိုးရာ PostgreSQL format) ဖြစ်ပါတယ်။ ပိုမို သိရှိရန် [အပိုင်း 8.4](/docs/postgresql/datatype-binary) ကို ကြည့်ပါ။ ဒီ setting ဘယ်လိုဖြစ်ပါစေ — bytea အမျိုးအစားက input မှာ format နှစ်မျိုးလုံးကို အမြဲ လက်ခံပါတယ်။
- **xmlbinary (enum)** — XML ထဲမှာ binary တန်ဖိုးတွေကို ဘယ်လို encode လုပ်မလဲ ဆိုတာ သတ်မှတ်ပါတယ်။ ဒါက — ဥပမာ — bytea တန်ဖိုးတွေကို xmlelement ဒါမှမဟုတ် xmlforest function တွေနဲ့ XML အဖြစ် ပြောင်းတဲ့အခါ သက်ရောက်ပါတယ်။ ဖြစ်နိုင်တဲ့ တန်ဖိုးတွေက base64 နဲ့ hex ဖြစ်ပြီး — နှစ်မျိုးလုံးကို XML Schema standard မှာ သတ်မှတ်ထားပါတယ်။ Default က base64 ဖြစ်ပါတယ်။ XML ဆိုင်ရာ function တွေ အကြောင်း ပိုမို သိရှိရန် [အပိုင်း 9.15](/docs/postgresql/functions-xml) ကို ကြည့်ပါ။
ဒီနေရာမှာ တကယ့် ရွေးချယ်မှုက အများအားဖြင့် အရသာ (taste) ပြဿနာသာ ဖြစ်ပြီး — client application တွေရဲ့ ဖြစ်နိုင်တဲ့ ကန့်သတ်ချက်တွေကသာ ကန့်သတ်ထားပါတယ်။ နည်းလမ်း နှစ်မျိုးလုံးက ဖြစ်နိုင်တဲ့ တန်ဖိုးအားလုံးကို ထောက်ပံ့ပေမယ့် — hex encoding က base64 encoding ထက် အနည်းငယ် ပိုကြီးပါလိမ့်မယ်။
- **xmloption (enum)** — XML နဲ့ character string တန်ဖိုးတွေကြား ပြောင်းလဲတဲ့အခါ DOCUMENT ဒါမှမဟုတ် CONTENT ကို implicit အနေနဲ့ ထားမလား ဆိုတာ သတ်မှတ်ပါတယ်။ ဒါရဲ့ ဖော်ပြချက်အတွက် [အပိုင်း 8.13](/docs/postgresql/datatype-xml) ကို ကြည့်ပါ။ တရားဝင် တန်ဖိုးတွေက DOCUMENT နဲ့ CONTENT ဖြစ်ပါတယ်။ Default က CONTENT ဖြစ်ပါတယ်။
SQL standard အရ — ဒီ option ကို သတ်မှတ်တဲ့ command က

SET XML OPTION { DOCUMENT | CONTENT };

ဒီ syntax ကို PostgreSQL မှာလည်း ရနိုင်ပါတယ်။
- **gin_pending_list_limit (integer)** — fastupdate enable ဖြစ်တဲ့အခါ သုံးတဲ့ GIN index တစ်ခုရဲ့ pending list ရဲ့ အများဆုံး အရွယ်အစားကို သတ်မှတ်ပါတယ်။ စာရင်းက ဒီအများဆုံး အရွယ်အစားထက် ကြီးလာရင် — စာရင်းထဲက entry တွေကို index ရဲ့ main GIN data structure ဆီ အစုလိုက် ရွှေ့ပြီး ပြန်လည် သန့်ရှင်းပါတယ်။ ဒီတန်ဖိုးကို unit မသတ်မှတ်ဘဲ ပေးရင် — kilobyte အဖြစ် ယူပါတယ်။ Default က လေးမီဂါဘိုက် (4MB) ဖြစ်ပါတယ်။ ဒီ setting ကို index storage parameter တွေ ပြောင်းခြင်းဖြင့် GIN index တစ်ခုချင်းစီအတွက် ကျော်လွှားနိုင်ပါတယ်။ ပိုမို သိရှိရန် [အပိုင်း 65.4.4.1](https://www.postgresql.org/docs/current/gin.html) နဲ့ [အပိုင်း 65.4.5](https://www.postgresql.org/docs/current/gin.html) ကို ကြည့်ပါ။
- **createrole_self_grant (string)** — CREATEROLE ရှိပေမယ့် SUPERUSER မဟုတ်တဲ့ user တစ်ဦးက role တစ်ခု ဖန်တီးပြီး — ဒါကို non-empty တန်ဖိုးတစ်ခု သတ်မှတ်ထားရင် — အသစ် ဖန်တီးလိုက်တဲ့ role ကို — သတ်မှတ်ထားတဲ့ option တွေနဲ့အတူ — ဖန်တီးတဲ့ user ဆီ ပေးအပ် (grant) ပါလိမ့်မယ်။ တန်ဖိုးက set ဒါမှမဟုတ် inherit ဒါမှမဟုတ် ဒါတွေရဲ့ comma နဲ့ ခွဲထားတဲ့ စာရင်း ဖြစ်ရပါမယ်။ Default တန်ဖိုးက empty string ဖြစ်ပြီး — feature ကို ပိတ်ပါတယ်။
ဒီ option ရဲ့ ရည်ရွယ်ချက်က — superuser မဟုတ်တဲ့ CREATEROLE user တစ်ဦးကို — ဖန်တီးလိုက်တဲ့ user တွေအပေါ် အလိုအလျောက် အမွေခံစေဖို့ (inherit) ဒါမှမဟုတ် အလိုအလျောက် SET ROLE လုပ်နိုင်တဲ့ စွမ်းရည် ရရှိစေဖို့ ခွင့်ပြုတာပါ။ CREATEROLE user တစ်ဦးက ဖန်တီးလိုက်တဲ့ role တွေအပေါ် ADMIN OPTION ကို အမြဲ implicit အနေနဲ့ ရရှိထားတာမို့ — အဲဒီ user က ဒီ setting နဲ့ အတူတူ ရလဒ် ရရှိစေမယ့် GRANT statement ကို အမြဲ execute လုပ်နိုင်ပါတယ်။ ဒါပေမယ့် — usability အရ — grant က အလိုအလျောက် ဖြစ်သွားရင် အဆင်ပြေနိုင်ပါတယ်။ Superuser တစ်ဦးက role တိုင်းရဲ့ privilege တွေကို အလိုအလျောက် အမွေခံပြီး role မည်သည့်အရာကိုမဆို SET ROLE လုပ်နိုင်တာမို့ — ဒီ setting ကို CREATEROLE user တွေအတွက် — သူတို့ ဖန်တီးတဲ့ user တွေအပေါ် — အလားတူ အပြုအမူ ဖြစ်ပေါ်စေဖို့ သုံးနိုင်ပါတယ်။
- **event_triggers (boolean)** — ချို့ယွင်းနေတဲ့ event trigger တွေကို ဖြေရှင်း ပြုပြင်ဖို့ event trigger တွေ execute လုပ်တာကို ယာယီ ပိတ်ခွင့်ပြုပါတယ်။ false သတ်မှတ်ခြင်းဖြင့် event trigger အားလုံးကို ပိတ်ပါလိမ့်မယ်။ true သတ်မှတ်ခြင်းက event trigger အားလုံးကို ဖြစ်ပေါ်ခွင့်ပြုပြီး — ဒါက default တန်ဖိုး ဖြစ်ပါတယ်။ Superuser တွေနဲ့ သင့်လျော်တဲ့ SET privilege ရှိတဲ့ user တွေသာ ဒီ setting ကို ပြောင်းနိုင်ပါတယ်။
- **restrict_nonsystem_relation_kind (string)** — Non-system relation တွေကို ဝင်ရောက်မှု တားမြစ်ထားတဲ့ relation kind တွေကို သတ်မှတ်ပါတယ်။ တန်ဖိုးက comma နဲ့ ခွဲထားတဲ့ relation kind တွေရဲ့ စာရင်း ပုံစံ ဖြစ်ပါတယ်။ လက်ရှိအချိန်မှာ ထောက်ပံ့တဲ့ relation kind တွေက view နဲ့ foreign-table ဖြစ်ပါတယ်။

### 19.11.2. Locale and Formatting (locale နှင့် formatting)

- **DateStyle (string)** — ရက်စွဲနှင့် အချိန် တန်ဖိုးများအတွက် ပြသမယ့် format ကို သတ်မှတ်ပြီး — မရှင်းလင်းတဲ့ (ambiguous) ရက်စွဲ input တန်ဖိုးများကို အဓိပ္ပာယ် ဖော်တဲ့ စည်းမျဉ်းများကိုလည်း သတ်မှတ်ပါတယ်။ သမိုင်းဆိုင်ရာ အကြောင်းများကြောင့် — ဒီ variable မှာ သီးခြားလွတ်လပ်တဲ့ component နှစ်ခု ပါဝင်ပါတယ် — output format သတ်မှတ်ချက် (ISO, Postgres, SQL, သို့မဟုတ် German) နှင့် year/month/day အစီအစဉ်အတွက် input/output သတ်မှတ်ချက် (DMY, MDY, သို့မဟုတ် YMD) တို့ ဖြစ်ပါတယ်။ ဒါတွေကို သီးခြားစီ ဒါမှမဟုတ် အတူတကွ သတ်မှတ်နိုင်ပါတယ်။ Euro နှင့် European ဆိုတဲ့ keyword များက DMY ရဲ့ အဓိပ္ပာယ်တူ စကားလုံးများ ဖြစ်ပြီး — US, NonEuro နှင့် NonEuropean ဆိုတဲ့ keyword များက MDY ရဲ့ အဓိပ္ပာယ်တူ စကားလုံးများ ဖြစ်ပါတယ်။ ပိုမို သိရှိရန် [အပိုင်း 8.5](/docs/postgresql/datatype-datetime) ကို ကြည့်ပါ။ Built-in default က ISO, MDY ဖြစ်ပေမယ့် — initdb က ရွေးချယ်ထားတဲ့ lc_time locale ရဲ့ အပြုအမူနှင့် ကိုက်ညီတဲ့ setting တစ်ခုနဲ့ configuration file ကို initialize လုပ်ပါလိမ့်မယ်။
- **IntervalStyle (enum)** — interval တန်ဖိုးများအတွက် ပြသမယ့် format ကို သတ်မှတ်ပါတယ်။ sql_standard တန်ဖိုးက SQL standard interval literal များနှင့် ကိုက်ညီတဲ့ output ကို ထုတ်ပေးပါလိမ့်မယ်။ postgres တန်ဖိုး (default ဖြစ်တဲ့) က DateStyle parameter ကို ISO သတ်မှတ်ထားတဲ့အခါ PostgreSQL 8.4 မတိုင်မီ release များနှင့် ကိုက်ညီတဲ့ output ကို ထုတ်ပေးပါလိမ့်မယ်။ postgres_verbose တန်ဖိုးက DateStyle ကို non-ISO output သတ်မှတ်ထားတဲ့အခါ PostgreSQL 8.4 မတိုင်မီ release များနှင့် ကိုက်ညီတဲ့ output ကို ထုတ်ပေးပါလိမ့်မယ်။ iso_8601 တန်ဖိုးက ISO 8601 ရဲ့ section 4.4.3.2 မှာ သတ်မှတ်ထားတဲ့ time interval “format with designators” နှင့် ကိုက်ညီတဲ့ output ကို ထုတ်ပေးပါလိမ့်မယ်။
IntervalStyle parameter က မရှင်းလင်းတဲ့ interval input ကို အဓိပ္ပာယ် ဖော်တာကိုလည်း သက်ရောက်ပါတယ်။ ပိုမို သိရှိရန် [အပိုင်း 8.5.4](/docs/postgresql/datatype-datetime) ကို ကြည့်ပါ။
- **TimeZone (string)** — time stamp များကို ပြသရာနှင့် အဓိပ္ပာယ် ဖော်ရာမှာ သုံးမယ့် time zone ကို သတ်မှတ်ပါတယ်။ Built-in default က GMT ဖြစ်ပေမယ့် — ပုံမှန်အားဖြင့် postgresql.conf ထဲမှာ ကျော်လွှား (override) လုပ်ထားတတ်ပါတယ်; initdb က သူ့ရဲ့ system environment နှင့် ကိုက်ညီတဲ့ setting တစ်ခုကို အဲဒီမှာ install လုပ်သတ်မှတ်ပါလိမ့်မယ်။ ပိုမို သိရှိရန် [အပိုင်း 8.5.3](/docs/postgresql/datatype-datetime) ကို ကြည့်ပါ။
- **timezone_abbreviations (string)** — datetime input အတွက် server က လက်ခံမယ့် (လက်ရှိ TimeZone setting က သတ်မှတ်ထားတဲ့ abbreviation များအပြင်) အပို time zone abbreviation များရဲ့ စုစည်းမှုကို သတ်မှတ်ပါတယ်။ Default က 'Default' ဖြစ်ပြီး — ကမ္ဘာ့နေရာ အများစုမှာ အလုပ်လုပ်တဲ့ စုစည်းမှု တစ်ခု ဖြစ်ပါတယ်; 'Australia' နှင့် 'India' လည်း ရှိပြီး — installation တစ်ခုအတွက် အခြား စုစည်းမှုများကိုလည်း သတ်မှတ်နိုင်ပါတယ်။ ပိုမို သိရှိရန် [အပိုင်း B.4](https://www.postgresql.org/docs/current/datetime-config-files.html) ကို ကြည့်ပါ။
- **extra_float_digits (integer)** — ဒီ parameter က float4, float8 နှင့် geometric data type များ အပါအဝင် floating-point တန်ဖိုးများရဲ့ စာသား output အတွက် သုံးမယ့် digit အရေအတွက်ကို ချိန်ညှိ (adjust) ပါတယ်။
တန်ဖိုးက 1 (default) ဒါမှမဟုတ် အဲဒီထက် ကြီးရင် — float တန်ဖိုးများကို shortest-precise format နဲ့ ထုတ်ပါတယ်; [အပိုင်း 8.1.3](/docs/postgresql/datatype-numeric) ကို ကြည့်ပါ။ ထုတ်လုပ်တဲ့ digit အရေအတွက်က ထုတ်နေတဲ့ တန်ဖိုးအပေါ်သာ မူတည်ပြီး — ဒီ parameter ရဲ့ တန်ဖိုးအပေါ် မမူတည်ပါဘူး။ float8 တန်ဖိုးများအတွက် အများဆုံး 17 digit လိုအပ်ပြီး float4 အတွက် 9 digit လိုအပ်ပါတယ်။ ဒီ format က မြန်ဆန်ပြီး တိကျပါတယ် — မှန်ကန်စွာ ဖတ်တဲ့အခါ မူရင်း binary float တန်ဖိုးကို အတိအကျ ထိန်းသိမ်းပေးပါတယ်။ သမိုင်းဆိုင်ရာ လိုက်လျောညီထွေမှုအတွက် — 3 အထိ တန်ဖိုးများကို ခွင့်ပြုပါတယ်။
တန်ဖိုးက သုည ဒါမှမဟုတ် အနုတ်ဖြစ်ရင် — output ကို သတ်မှတ်ထားတဲ့ decimal precision တစ်ခုအထိ round လုပ်ပါတယ်။ သုံးတဲ့ precision က type အတွက် standard digit အရေအတွက် (သင့်လျော်သလို FLT_DIG သို့မဟုတ် DBL_DIG) ကို ဒီ parameter ရဲ့ တန်ဖိုးအလိုက် လျှော့ချထားတာ ဖြစ်ပါတယ်။ (ဥပမာ — -1 သတ်မှတ်ရင် float4 တန်ဖိုးများကို significant digit 5 လုံးအထိ ပြန်တွက်ပြီး float8 တန်ဖိုးများကို 14 digit အထိ round လုပ်စေပါလိမ့်မယ်။) ဒီ format က ပိုနှေးပြီး binary float တန်ဖိုးရဲ့ bit အားလုံးကို မထိန်းသိမ်းနိုင်ပေမယ့် — လူတွေ ဖတ်ရ ပိုလွယ်နိုင်ပါတယ်။

> **မှတ်ချက်:** ဒီ parameter ရဲ့ အဓိပ္ပာယ်နှင့် သူ့ default တန်ဖိုးက PostgreSQL 12 မှာ ပြောင်းလဲခဲ့ပါတယ်; ပိုမို ဆွေးနွေးချက်အတွက် [အပိုင်း 8.1.3](/docs/postgresql/datatype-numeric) ကို ကြည့်ပါ။
- **client_encoding (string)** — client ဘက်က encoding (character set) ကို သတ်မှတ်ပါတယ်။ Default က database encoding ကို သုံးဖို့ ဖြစ်ပါတယ်။ PostgreSQL server က ထောက်ပံ့တဲ့ character set များကို [အပိုင်း 23.3.1](/docs/postgresql/multibyte) မှာ ဖော်ပြထားပါတယ်။
- **lc_messages (string)** — message များကို ပြသမယ့် ဘာသာစကားကို သတ်မှတ်ပါတယ်။ လက်ခံနိုင်တဲ့ တန်ဖိုးများက system အပေါ် မူတည်ပါတယ်; ပိုမို သိရှိရန် [အပိုင်း 23.1](/docs/postgresql/locale) ကို ကြည့်ပါ။ ဒီ variable ကို empty string (default ဖြစ်တဲ့) သတ်မှတ်ရင် — တန်ဖိုးက server ရဲ့ execution environment ဆီကနေ system အပေါ် မူတည်တဲ့ ပုံစံနဲ့ အမွေခံ ရရှိပါတယ်။
အချို့ system များမှာ ဒီ locale category မရှိပါဘူး။ ဒီ variable ကို သတ်မှတ်တာက အလုပ်လုပ်နေဆဲ ဖြစ်ပေမယ့် — သက်ရောက်မှု ရှိမှာ မဟုတ်ပါဘူး။ ထို့အပြင် — လိုချင်တဲ့ ဘာသာစကားအတွက် ဘာသာပြန် message များ မရှိနိုင်တဲ့ အခွင့်အလမ်းလည်း ရှိပါတယ်။ အဲဒီအခါ — English message များကို ဆက်လက် တွေ့မြင်ရပါလိမ့်မယ်။
Superuser များနှင့် သင့်လျော်တဲ့ SET privilege ရှိတဲ့ user များသာ ဒီ setting ကို ပြောင်းနိုင်ပါတယ်။
- **lc_monetary (string)** — ဥပမာ — to_char function အစုအဝေးနဲ့ ငွေကြေး ပမာဏများကို format လုပ်ရာမှာ သုံးမယ့် locale ကို သတ်မှတ်ပါတယ်။ လက်ခံနိုင်တဲ့ တန်ဖိုးများက system အပေါ် မူတည်ပါတယ်; ပိုမို သိရှိရန် [အပိုင်း 23.1](/docs/postgresql/locale) ကို ကြည့်ပါ။ ဒီ variable ကို empty string (default ဖြစ်တဲ့) သတ်မှတ်ရင် — တန်ဖိုးက server ရဲ့ execution environment ဆီကနေ system အပေါ် မူတည်တဲ့ ပုံစံနဲ့ အမွေခံ ရရှိပါတယ်။
- **lc_numeric (string)** — ဥပမာ — to_char function အစုအဝေးနဲ့ နံပါတ်များကို format လုပ်ရာမှာ သုံးမယ့် locale ကို သတ်မှတ်ပါတယ်။ လက်ခံနိုင်တဲ့ တန်ဖိုးများက system အပေါ် မူတည်ပါတယ်; ပိုမို သိရှိရန် [အပိုင်း 23.1](/docs/postgresql/locale) ကို ကြည့်ပါ။ ဒီ variable ကို empty string (default ဖြစ်တဲ့) သတ်မှတ်ရင် — တန်ဖိုးက server ရဲ့ execution environment ဆီကနေ system အပေါ် မူတည်တဲ့ ပုံစံနဲ့ အမွေခံ ရရှိပါတယ်။
- **lc_time (string)** — ဥပမာ — to_char function အစုအဝေးနဲ့ ရက်စွဲနှင့် အချိန်များကို format လုပ်ရာမှာ သုံးမယ့် locale ကို သတ်မှတ်ပါတယ်။ လက်ခံနိုင်တဲ့ တန်ဖိုးများက system အပေါ် မူတည်ပါတယ်; ပိုမို သိရှိရန် [အပိုင်း 23.1](/docs/postgresql/locale) ကို ကြည့်ပါ။ ဒီ variable ကို empty string (default ဖြစ်တဲ့) သတ်မှတ်ရင် — တန်ဖိုးက server ရဲ့ execution environment ဆီကနေ system အပေါ် မူတည်တဲ့ ပုံစံနဲ့ အမွေခံ ရရှိပါတယ်။
- **icu_validation_level (enum)** — ICU locale validation ပြဿနာများ ကြုံတွေ့ရတဲ့အခါ — ပြဿနာကို သတင်းပို့ရာမှာ ဘယ် message level ကို သုံးမလဲ ဆိုတာကို ထိန်းချုပ်ပါတယ်။ တရားဝင် တန်ဖိုးများက DISABLED, DEBUG5, DEBUG4, DEBUG3, DEBUG2, DEBUG1, INFO, NOTICE, WARNING, ERROR နှင့် LOG တို့ ဖြစ်ပါတယ်။
DISABLED သတ်မှတ်ရင် — validation ပြဿနာများကို လုံးဝ သတင်းမပို့ပါဘူး။ မဟုတ်ရင် — ပြဿနာများကို သတ်မှတ်ထားတဲ့ message level နဲ့ သတင်းပို့ပါတယ်။ Default က WARNING ဖြစ်ပါတယ်။
- **default_text_search_config (string)** — configuration ကို အတိအကျ သတ်မှတ်တဲ့ argument မပါတဲ့ text search function မျိုးကွဲများ (variants) က သုံးမယ့် text search configuration ကို ရွေးချယ်ပါတယ်။ ပိုမို သိရှိရန် [အခန်း 12](https://www.postgresql.org/docs/current/textsearch.html) ကို ကြည့်ပါ။ Built-in default က pg_catalog.simple ဖြစ်ပေမယ့် — အဲဒီ locale နှင့် ကိုက်ညီတဲ့ configuration တစ်ခုကို ခွဲခြား ဖော်ထုတ်နိုင်ရင် — initdb က ရွေးချယ်ထားတဲ့ lc_ctype locale နှင့် ကိုက်ညီတဲ့ setting တစ်ခုနဲ့ configuration file ကို initialize လုပ်ပါလိမ့်မယ်။

### 19.11.3. Shared Library Preloading (shared library ကြိုတင် load လုပ်ခြင်း)

Server ထဲကို shared library များ ကြိုတင် load (preload) လုပ်ဖို့ — အပို functionality များ load လုပ်ရန် ဒါမှမဟုတ် performance အကျိုးအမြတ်များ ရရှိရန် — setting များစွာ ရနိုင်ပါတယ်။ ဥပမာ — '$libdir/mylib' ဆိုတဲ့ setting တစ်ခုက installation ရဲ့ standard library directory ဆီကနေ mylib.so (ဒါမှမဟုတ် အချို့ platform များမှာ mylib.sl) ကို ကြိုတင် load လုပ်စေပါလိမ့်မယ်။ Setting များကြားက ကွာခြားချက်များက — ဘယ်အချိန်မှာ အသက်ဝင်မလဲ နှင့် ဒါတွေကို ပြောင်းဖို့ ဘယ် privilege များ လိုအပ်မလဲ ဆိုတာပါ။

PostgreSQL procedural language library များကို ဒီနည်းနဲ့ ကြိုတင် load လုပ်နိုင်ပြီး — ပုံမှန်အားဖြင့် '$libdir/plXXX' ဆိုတဲ့ syntax ကို သုံးပြီး XXX က pgsql, perl, tcl, သို့မဟုတ် python ဖြစ်ပါတယ်။

PostgreSQL နှင့် သုံးဖို့ ရည်ရွယ်ထားတဲ့ shared library များသာ ဒီနည်းနဲ့ load လုပ်နိုင်ပါတယ်။ PostgreSQL က ထောက်ပံ့တဲ့ library တိုင်းမှာ compatibility ကို အာမခံဖို့ စစ်ဆေးတဲ့ “magic block” တစ်ခု ရှိပါတယ်။ ဒီအကြောင်းကြောင့် — PostgreSQL မဟုတ်တဲ့ library များကို ဒီနည်းနဲ့ load လုပ်လို့ မရပါဘူး။ အဲဒါအတွက် LD_PRELOAD လို operating-system facility များကို သုံးနိုင်ပါတယ်။

ယေဘုယျအားဖြင့် — module တစ်ခုကို load လုပ်ဖို့ အကြံပြုထားတဲ့ နည်းလမ်းအတွက် အဲဒီ module ရဲ့ documentation ကို ကိုးကားပါ။

- **local_preload_libraries (string)** — ဒီ variable က connection စတင်ချိန်မှာ ကြိုတင် load လုပ်ရမယ့် shared library တစ်ခု ဒါမှမဟုတ် တစ်ခုထက် ပိုကို သတ်မှတ်ပါတယ်။ အဲဒါမှာ library အမည်များရဲ့ comma နဲ့ ခွဲထားတဲ့ စာရင်းတစ်ခု ပါဝင်ပြီး — အမည်တစ်ခုချင်းစီကို LOAD command အတွက် သလို အဓိပ္ပာယ် ဖော်ပါတယ်။ entry များကြားက whitespace ကို လျစ်လျူရှုပါတယ်; အမည်ထဲမှာ whitespace ဒါမှမဟုတ် comma များ ထည့်ရ လိုအပ်ရင် — library အမည်ကို double quote များနဲ့ ခြံရံပါ။ Parameter တန်ဖိုးက connection စတင်ချိန်မှာသာ အသက်ဝင်ပါတယ်။ နောက်ဆက်တွဲ ပြောင်းလဲမှုများက သက်ရောက်မှု မရှိပါဘူး။ သတ်မှတ်ထားတဲ့ library တစ်ခုကို မတွေ့ရင် — connection ကြိုးပမ်းမှု ကျရှုံးပါလိမ့်မယ်။
ဒီ option ကို user မည်သူမဆို သတ်မှတ်နိုင်ပါတယ်။ ဒီအကြောင်းကြောင့် — load လုပ်နိုင်တဲ့ library များက installation ရဲ့ standard library directory ထဲက plugins subdirectory မှာ ပေါ်တဲ့ library များအတွက်သာ ကန့်သတ်ထားပါတယ်။ (အဲဒီမှာ “safe” library များသာ install လုပ်ထားကြောင်း သေချာစေတာက database administrator ရဲ့ တာဝန် ဖြစ်ပါတယ်။) local_preload_libraries ထဲက entry များက ဒီ directory ကို — ဥပမာ — $libdir/plugins/mylib လို့ အတိအကျ သတ်မှတ်နိုင်သည် — ဒါမှမဟုတ် library အမည်ကိုသာ သတ်မှတ်နိုင်ပါတယ် — mylib က $libdir/plugins/mylib နဲ့ တူညီတဲ့ သက်ရောက်မှု ရှိပါလိမ့်မယ်။
ဒီ feature ရဲ့ ရည်ရွယ်ချက်က — privilege မရှိတဲ့ user များကို — အတိအကျ LOAD command တစ်ခု မလိုအပ်ဘဲ — debugging ဒါမှမဟုတ် performance-measurement library များကို session သီးသန့်များထဲ load လုပ်ခွင့်ပြုဖို့ ဖြစ်ပါတယ်။ အဲဒီအတွက် — client ဘက်မှာ PGOPTIONS environment variable ကို သုံးပြီး ဒါမှမဟုတ် ALTER ROLE SET ကို သုံးပြီး — ဒီ parameter ကို သတ်မှတ်တာက ပုံမှန် ဖြစ်ပါလိမ့်မယ်။
ဒါပေမယ့် — module တစ်ခုကို non-superuser များ ဒီနည်းနဲ့ သုံးဖို့ အတိအကျ ဒီဇိုင်းဆွဲထားတာ မဟုတ်ရင် — ဒါက သုံးဖို့ မှန်ကန်တဲ့ setting မဟုတ်တတ်ပါဘူး။ အစား session_preload_libraries ကို ကြည့်ပါ။
- **session_preload_libraries (string)** — ဒီ variable က connection စတင်ချိန်မှာ ကြိုတင် load လုပ်ရမယ့် shared library တစ်ခု ဒါမှမဟုတ် တစ်ခုထက် ပိုကို သတ်မှတ်ပါတယ်။ အဲဒါမှာ library အမည်များရဲ့ comma နဲ့ ခွဲထားတဲ့ စာရင်းတစ်ခု ပါဝင်ပြီး — အမည်တစ်ခုချင်းစီကို LOAD command အတွက် သလို အဓိပ္ပာယ် ဖော်ပါတယ်။ entry များကြားက whitespace ကို လျစ်လျူရှုပါတယ်; အမည်ထဲမှာ whitespace ဒါမှမဟုတ် comma များ ထည့်ရ လိုအပ်ရင် — library အမည်ကို double quote များနဲ့ ခြံရံပါ။ Parameter တန်ဖိုးက connection စတင်ချိန်မှာသာ အသက်ဝင်ပါတယ်။ နောက်ဆက်တွဲ ပြောင်းလဲမှုများက သက်ရောက်မှု မရှိပါဘူး။ သတ်မှတ်ထားတဲ့ library တစ်ခုကို မတွေ့ရင် — connection ကြိုးပမ်းမှု ကျရှုံးပါလိမ့်မယ်။ Superuser များနှင့် သင့်လျော်တဲ့ SET privilege ရှိတဲ့ user များသာ ဒီ setting ကို ပြောင်းနိုင်ပါတယ်။
ဒီ feature ရဲ့ ရည်ရွယ်ချက်က — အတိအကျ LOAD command တစ်ခု ပေးစရာ မလိုဘဲ — debugging ဒါမှမဟုတ် performance-measurement library များကို session သီးသန့်များထဲ load လုပ်ခွင့်ပြုဖို့ ဖြစ်ပါတယ်။ ဥပမာ — ALTER ROLE SET နဲ့ ဒီ parameter ကို သတ်မှတ်ခြင်းဖြင့် — သတ်မှတ်ထားတဲ့ user အမည် အောက်က session အားလုံးအတွက် auto_explain ကို ဖွင့်နိုင်ပါတယ်။ ဒါ့အပြင် — ဒီ parameter ကို server ကို restart မလုပ်ဘဲ ပြောင်းနိုင်တာမို့ (ဒါပေမယ့် ပြောင်းလဲမှုများက session အသစ် စတင်ချိန်မှာသာ အသက်ဝင်ပါတယ်) — module အသစ်များကို ဒီနည်းနဲ့ ထည့်ရ ပိုလွယ်ပါတယ် — session အားလုံးအပေါ် သက်ရောက်သင့်ရင်တောင်မှပါ။
shared_preload_libraries နှင့် မတူဘဲ — library တစ်ခုကို ပထမဆုံး သုံးတဲ့အခါ မဟုတ်ဘဲ session စတင်ချိန်မှာ load လုပ်တာက ကြီးမားတဲ့ performance အကျိုးအမြတ် မရှိပါဘူး။ ဒါပေမယ့် — connection pooling သုံးတဲ့အခါ အကျိုးအမြတ် အနည်းငယ် ရှိပါတယ်။
- **shared_preload_libraries (string)** — ဒီ variable က server စတင်ချိန်မှာ ကြိုတင် load လုပ်ရမယ့် shared library တစ်ခု ဒါမှမဟုတ် တစ်ခုထက် ပိုကို သတ်မှတ်ပါတယ်။ အဲဒါမှာ library အမည်များရဲ့ comma နဲ့ ခွဲထားတဲ့ စာရင်းတစ်ခု ပါဝင်ပြီး — အမည်တစ်ခုချင်းစီကို LOAD command အတွက် သလို အဓိပ္ပာယ် ဖော်ပါတယ်။ entry များကြားက whitespace ကို လျစ်လျူရှုပါတယ်; အမည်ထဲမှာ whitespace ဒါမှမဟုတ် comma များ ထည့်ရ လိုအပ်ရင် — library အမည်ကို double quote များနဲ့ ခြံရံပါ။ ဒီ parameter ကို server စတင်ချိန်မှာသာ သတ်မှတ်နိုင်ပါတယ်။ သတ်မှတ်ထားတဲ့ library တစ်ခုကို မတွေ့ရင် — server က စတင် လုပ်ဆောင်တာ ကျရှုံးပါလိမ့်မယ်။
အချို့ library များက — shared memory ခွဲဝေခြင်း၊ light-weight lock များ ကြိုတင်ထားခြင်း ဒါမှမဟုတ် background worker များ စတင်ခြင်း လို — postmaster စတင်ချိန်မှာသာ လုပ်ဆောင်နိုင်တဲ့ အချို့ လုပ်ငန်းများကို လုပ်ဖို့ လိုအပ်ပါတယ်။ အဲဒီ library များကို ဒီ parameter ကတစ်ဆင့် server စတင်ချိန်မှာ load လုပ်ရပါမယ်။ အသေးစိတ်အတွက် library တစ်ခုချင်းစီရဲ့ documentation ကို ကြည့်ပါ။
အခြား library များကိုလည်း ကြိုတင် load လုပ်နိုင်ပါတယ်။ shared library တစ်ခုကို ကြိုတင် load လုပ်ခြင်းဖြင့် — library ကို ပထမဆုံး သုံးတဲ့အခါ သူ့ startup time ကို ရှောင်ရှားနိုင်ပါတယ်။ ဒါပေမယ့် — အဲဒီ process က library ကို ဘယ်တော့မှ မသုံးရင်တောင်မှ — server process အသစ် တစ်ခုချင်း စတင်ဖို့ အချိန် အနည်းငယ် တိုးလာနိုင်ပါတယ်။ ဒါကြောင့် ဒီ parameter ကို session အများစုမှာ သုံးမယ့် library များအတွက်သာ အကြံပြုပါတယ်။ ဒါ့အပြင် — ဒီ parameter ကို ပြောင်းရင် server restart လိုအပ်တာမို့ — ဥပမာ — ရေတို debugging လုပ်ငန်းများအတွက် သုံးဖို့ မှန်ကန်တဲ့ setting မဟုတ်ပါဘူး။ အဲဒါအတွက် အစား session_preload_libraries ကို သုံးပါ။

> **မှတ်ချက်:** Windows host များမှာ — server စတင်ချိန်မှာ library ကို ကြိုတင် load လုပ်တာက server process အသစ် တစ်ခုချင်း စတင်ဖို့ လိုတဲ့ အချိန်ကို လျှော့ပေးမှာ မဟုတ်ပါဘူး; server process တစ်ခုချင်းစီက preload library အားလုံးကို ပြန်လည် load လုပ်ပါလိမ့်မယ်။ ဒါပေမယ့် — postmaster စတင်ချိန်မှာ လုပ်ဆောင်ရ လိုအပ်တဲ့ library များအတွက် shared_preload_libraries က Windows host များမှာ အသုံးဝင်နေဆဲ ဖြစ်ပါတယ်။
- **jit_provider (string)** — ဒီ variable က သုံးရမယ့် JIT provider library ရဲ့ အမည် ဖြစ်ပါတယ် ([အပိုင်း 30.4.2](/docs/postgresql/jit-extensibility) ကို ကြည့်ပါ)။ Default က llvmjit ဖြစ်ပါတယ်။ ဒီ parameter ကို server စတင်ချိန်မှာသာ သတ်မှတ်နိုင်ပါတယ်။
မရှိတဲ့ library တစ်ခုကို သတ်မှတ်ရင် — JIT ရနိုင်မှာ မဟုတ်ပေမယ့် — error မတင်ပါဘူး။ ဒါက JIT support ကို PostgreSQL package အဓိကနဲ့ သီးခြား install လုပ်နိုင်စေပါတယ်။

### 19.11.4. Other Defaults (အခြား default များ)

- **dynamic_library_path (string)** — dynamically loadable module တစ်ခုကို ဖွင့်ရ လိုအပ်ပြီး — CREATE FUNCTION ဒါမှမဟုတ် LOAD command မှာ သတ်မှတ်ထားတဲ့ file အမည်မှာ directory component မပါရင် (ဆိုလိုတာက အမည်ထဲမှာ slash မပါရင်) — system က လိုအပ်တဲ့ file အတွက် ဒီ path ကို ရှာပါလိမ့်မယ်။
dynamic_library_path ရဲ့ တန်ဖိုးက colon (ဒါမှမဟုတ် Windows မှာ semi-colon) နဲ့ ခွဲထားတဲ့ absolute directory path များရဲ့ စာရင်း ဖြစ်ရပါမယ်။ စာရင်း element တစ်ခုက $libdir ဆိုတဲ့ အထူး string နဲ့ စရင် — စုစည်းထည့်သွင်းထားတဲ့ (compiled-in) PostgreSQL package library directory ကို $libdir အစား အစားထိုးပါတယ်; standard PostgreSQL distribution က ပေးတဲ့ module များကို အဲဒီမှာ install လုပ်ထားပါတယ်။ (ဒီ directory ရဲ့ အမည်ကို သိရှိရန် pg_config --pkglibdir ကို သုံးပါ။) ဥပမာ:

dynamic_library_path = '/usr/local/lib/postgresql:/home/my_project/lib:$libdir'

ဒါမှမဟုတ် — Windows environment တစ်ခုမှာ:

dynamic_library_path = 'C:\tools\postgresql;H:\my_project\lib;$libdir'

ဒီ parameter ရဲ့ default တန်ဖိုးက '$libdir' ဖြစ်ပါတယ်။ တန်ဖိုးကို empty string သတ်မှတ်ရင် — အလိုအလျောက် path ရှာဖွေမှုကို ပိတ်ပါတယ်။
ဒီ parameter ကို superuser များနှင့် သင့်လျော်တဲ့ SET privilege ရှိတဲ့ user များက run time မှာ ပြောင်းနိုင်ပေမယ့် — အဲဒီလို သတ်မှတ်တာက client connection ပြီးဆုံးတဲ့အထိသာ တည်ရှိမှာမို့ — ဒီနည်းလမ်းကို development ရည်ရွယ်ချက်များအတွက်သာ သီးသန့်ထားသင့်ပါတယ်။ ဒီ parameter ကို သတ်မှတ်ရန် အကြံပြုတဲ့ နည်းလမ်းက postgresql.conf configuration file ထဲမှာ ဖြစ်ပါတယ်။
- **extension_control_path (string)** — extension များ — အထူးသဖြင့် extension control file များ (name.control) — အတွက် ရှာမယ့် path တစ်ခု။ ကျန်ရှိတဲ့ extension script နှင့် secondary control file များကို primary control file တွေ့ရှိတဲ့ directory တစ်ခုတည်းကနေ load လုပ်ပါတယ်။ အသေးစိတ်အတွက် [အပိုင်း 36.17.1](https://www.postgresql.org/docs/current/extend-extensions.html#EXTEND-EXTENSIONS-FILES) ကို ကြည့်ပါ။
extension_control_path ရဲ့ တန်ဖိုးက colon (ဒါမှမဟုတ် Windows မှာ semi-colon) နဲ့ ခွဲထားတဲ့ absolute directory path များရဲ့ စာရင်း ဖြစ်ရပါမယ်။ စာရင်း element တစ်ခုက $system ဆိုတဲ့ အထူး string နဲ့ စရင် — စုစည်းထည့်သွင်းထားတဲ့ (compiled-in) PostgreSQL extension directory ကို $system အစား အစားထိုးပါတယ်; standard PostgreSQL distribution က ပေးတဲ့ extension များကို အဲဒီမှာ install လုပ်ထားပါတယ်။ (ဒီ directory ရဲ့ အမည်ကို သိရှိရန် pg_config --sharedir ကို သုံးပါ။) ဥပမာ:

extension_control_path = '/usr/local/share/postgresql:/home/my_project/share:$system'

ဒါမှမဟုတ် — Windows environment တစ်ခုမှာ:

extension_control_path = 'C:\tools\postgresql;H:\my_project\share;$system'

သတ်မှတ်ထားတဲ့ path element များမှာ .control နှင့် .sql file များ ပါဝင်မယ့် extension ဆိုတဲ့ subdirectory ရှိရမယ်လို့ မျှော်လင့်ပါတယ် ဆိုတာ သတိပြုပါ; extension suffix ကို path element တစ်ခုချင်းစီအတွက် အလိုအလျောက် ထည့်ပေးပါတယ်။
ဒီ parameter ရဲ့ default တန်ဖိုးက '$system' ဖြစ်ပါတယ်။ တန်ဖိုးကို empty string သတ်မှတ်ရင် — default '$system' ကိုလည်း ယူဆပါတယ်။
အမည်တူ extension များက configured path ထဲက directory များစွာမှာ ရှိနေရင် — path ထဲမှာ ပထမဆုံး တွေ့ရတဲ့ instance ကိုသာ သုံးပါလိမ့်မယ်။
ဒီ parameter ကို superuser များနှင့် သင့်လျော်တဲ့ SET privilege ရှိတဲ့ user များက run time မှာ ပြောင်းနိုင်ပေမယ့် — အဲဒီလို သတ်မှတ်တာက client connection ပြီးဆုံးတဲ့အထိသာ တည်ရှိမှာမို့ — ဒီနည်းလမ်းကို development ရည်ရွယ်ချက်များအတွက်သာ သီးသန့်ထားသင့်ပါတယ်။ ဒီ parameter ကို သတ်မှတ်ရန် အကြံပြုတဲ့ နည်းလမ်းက postgresql.conf configuration file ထဲမှာ ဖြစ်ပါတယ်။
standard မဟုတ်တဲ့ တည်နေရာများကနေ extension များ load လုပ်နိုင်ဖို့ ဒီ parameter ကို သတ်မှတ်ရင် — dynamic_library_path ကိုလည်း ကိုက်ညီတဲ့ တည်နေရာတစ်ခုသို့ သတ်မှတ်ရ လိုအပ်ဖို့ များပါတယ် — ဥပမာ:

extension_control_path = '/usr/local/share/postgresql:$system'
dynamic_library_path = '/usr/local/lib/postgresql:$libdir'
- **gin_fuzzy_search_limit (integer)** — GIN index scan များက ပြန်ပေးတဲ့ set ရဲ့ အရွယ်အစား အတွက် ပျော့ပြောင်းတဲ့ (soft) အထက် ကန့်သတ်ချက်။ ပိုမို သိရှိရန် [အပိုင်း 65.4.5](https://www.postgresql.org/docs/current/gin.html) ကို ကြည့်ပါ။
