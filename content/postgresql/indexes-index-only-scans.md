## 11.9. Index-Only Scans and Covering Indexes (index-only scan နဲ့ covering index များ)

PostgreSQL ထဲက index တွေ အားလုံးက *secondary* index (table ရဲ့ အဓိက data သိမ်းဧရိယာနဲ့ သီးခြားစီ သိမ်းထားသော index) တွေ ဖြစ်ပါတယ် — ဆိုလိုတာက index တစ်ခုချင်းစီကို table ရဲ့ အဓိက data သိမ်းဆည်းရာ နေရာနဲ့ သီးခြား သိမ်းထားပါတယ် (PostgreSQL ဝေါဟာရအရ အဲဒီနေရာကို table ရဲ့ *heap* လို့ ခေါ်ပါတယ်)။ ဒါကြောင့် သာမန် index scan တစ်ခုမှာ — row တစ်ခုချင်းစီ ပြန်ယူဖို့အတွက် index ရော heap ပါ နှစ်ခုလုံးကနေ data ဆွဲထုတ်ယူရပါတယ်။ ဒါ့အပြင် — indexable `WHERE` condition တစ်ခုနဲ့ ကိုက်ညီတဲ့ index entry တွေက index ထဲမှာ များသောအားဖြင့် တစ်နေရာတည်းမှာ စုပြီး နီးနီးကပ်ကပ် ရှိတတ်ပေမယ့် — သူတို့ ရည်ညွှန်းတဲ့ table row တွေကတော့ heap ထဲက ဘယ်နေရာမှာမဆို ရောက်နေနိုင်ပါတယ်။ ဒါကြောင့် index scan ရဲ့ heap ကို ဝင်ရောက်ဖတ်ရတဲ့ အပိုင်းက — heap ထဲကို random access (ကြိုတင် ခန့်မှန်းလို့ မရတဲ့ နေရာတွေကို ကျပန်း ဝင်ရောက်ခြင်း) အများအပြား လုပ်ရပြီး — အထူးသဖြင့် ရိုးရာ rotating media (လည်ပတ်နေတဲ့ disk လို သိုလှောင်ကိရိယာ) တွေမှာ နှေးကွေးတတ်ပါတယ်။ ([အပိုင်း 11.5](/docs/postgresql/indexes-bitmap-scans) မှာ ဖော်ပြထားသလို — bitmap scan တွေက heap access တွေကို စီထားတဲ့ အစီအစဉ်နဲ့ လုပ်ခြင်းအားဖြင့် ဒီကုန်ကျစရိတ်ကို သက်သာအောင် ကြိုးစားပေမယ့် — အဲဒါကလည်း အတိုင်းအတာတစ်ခုအထိပဲ အကျိုးရှိပါတယ်။)

ဒီ performance ပြဿနာကို ဖြေရှင်းဖို့အတွက် PostgreSQL က *index-only scans* ကို ပံ့ပိုးပေးပါတယ် — index-only scan ဆိုတာ heap ကို လုံးဝ မထိဘဲ index တစ်ခုတည်းကနေ query တွေကို ဖြေဆိုပေးနိုင်တဲ့ scan ဖြစ်ပါတယ်။ အခြေခံ နည်းလမ်းကတော့ — ဆက်စပ်နေတဲ့ heap entry ကို သွားမကြည့်ဘဲ — index entry တစ်ခုချင်းစီကနေ တန်ဖိုးတွေကို တိုက်ရိုက် ပြန်ပေးလိုက်တာပဲ ဖြစ်ပါတယ်။ ဒီနည်းလမ်းကို ဘယ်အချိန်တွေမှာ သုံးလို့ရလဲဆိုတာနဲ့ ပတ်သက်ပြီး အခြေခံကျတဲ့ ကန့်သတ်ချက် နှစ်ခု ရှိပါတယ် —

1. Index type က index-only scan ကို ပံ့ပိုးပေးနိုင်ရမည်။ B-tree index တွေကတော့ အမြဲတမ်း ပံ့ပိုးပေးပါတယ်။ GiST နဲ့ SP-GiST index တွေကတော့ operator class တစ်ချို့အတွက် index-only scan ကို ပံ့ပိုးပေးပေမယ့် — အခြား operator class တွေအတွက်တော့ မပံ့ပိုးပါဘူး။ ကျန်တဲ့ index type တွေကတော့ လုံးဝ ပံ့ပိုးပေးခြင်း မရှိပါဘူး။ အရင်းခံ လိုအပ်ချက်ကတော့ — index က index entry တစ်ခုချင်းစီအတွက် မူရင်း data value ကို ရုပ်ပိုင်းဆိုင်ရာအရ သိမ်းဆည်းထားရမယ်၊ ဒါမှမဟုတ် ပြန်လည် တည်ဆောက်နိုင်ရမယ် ဆိုတာပဲ ဖြစ်ပါတယ်။ ဆန့်ကျင်ဘက် ဥပမာအနေနဲ့ — GIN index တွေကတော့ index-only scan ကို မပံ့ပိုးပေးနိုင်ပါဘူး — အကြောင်းကတော့ GIN ရဲ့ index entry တစ်ခုချင်းစီမှာ မူရင်း data value ရဲ့ အစိတ်အပိုင်းတစ်ခုစီပဲ ပါလေ့ ရှိလို့ ဖြစ်ပါတယ်။

2. Query က index ထဲမှာ သိမ်းထားတဲ့ column တွေကိုပဲ ကိုးကားရမည်။ ဥပမာ — column z လည်း ပါဝင်တဲ့ table တစ်ခုရဲ့ column x နဲ့ y ပေါ်မှာ index တစ်ခု ရှိတယ်ဆိုရင် — ဒီ query တွေက index-only scan ကို သုံးနိုင်ပါတယ် —
  
  SELECT x, y FROM tab WHERE x = 'key';
  SELECT x FROM tab WHERE x = 'key' AND y < 42;
  
  ဒါပေမယ့် ဒီ query တွေကတော့ မသုံးနိုင်ပါဘူး —
  
  SELECT x, z FROM tab WHERE x = 'key';
  SELECT x FROM tab WHERE x = 'key' AND z < 42;
  
  (Expression index နဲ့ partial index တွေက ဒီစည်းမျဉ်းကို ပိုမို ရှုပ်ထွေးစေပါတယ် — အောက်မှာ ဆွေးနွေးထားသလိုပါ။)

ဒီ အခြေခံ လိုအပ်ချက် နှစ်ခု ပြည့်မီပြီဆိုရင် — query အတွက် လိုအပ်တဲ့ data value တွေ အားလုံးကို index ကနေ ရနိုင်တာကြောင့် — index-only scan က လက်တွေ့မှာ ဖြစ်နိုင်ပါတယ်။ ဒါပေမယ့် PostgreSQL ထဲက table scan တိုင်းအတွက် နောက်ထပ် လိုအပ်ချက် တစ်ခု ရှိပါသေးတယ် — ပြန်ယူလိုက်တဲ့ row တစ်ခုချင်းစီဟာ query ရဲ့ MVCC snapshot အတွက် "visible" (မြင်နိုင်သည်) ဟုတ်မဟုတ် စစ်ဆေးရပါတယ် — [အခန်း 13](https://www.postgresql.org/docs/current/mvcc.html) မှာ ဆွေးနွေးထားသလိုပါ။ Visibility (မြင်နိုင်မှု) ဆိုင်ရာ အချက်အလက်ကို index entry တွေထဲမှာ သိမ်းမထားဘဲ — heap entry တွေထဲမှာပဲ သိမ်းထားပါတယ်။ ဒါကြောင့် ပထမတစ်ချက် ကြည့်လိုက်ရင် — row တစ်ခုချင်းစီ ပြန်ယူတိုင်း heap access လုပ်ရဦးမှာပဲလို့ ထင်ရပါတယ်။ Table row ကို မကြာသေးမီက ပြုပြင်ထားရင် — တကယ်လည်း အဲဒီလိုပဲ ဖြစ်ပါတယ်။ ဒါပေမယ့် — မကြာခဏ မပြောင်းလဲတဲ့ data တွေအတွက်တော့ ဒီပြဿနာကို ရှောင်လွှဲနိုင်တဲ့ နည်းလမ်း ရှိပါတယ်။ Table တစ်ခုရဲ့ heap ထဲက page တစ်ခုချင်းစီအတွက် — အဲဒီ page ထဲ သိမ်းထားတဲ့ row တွေ အားလုံးဟာ လက်ရှိနဲ့ အနာဂတ် transaction တွေ အားလုံးအတွက် မြင်နိုင်လောက်အောင် သက်တမ်း ရင့်နေပြီလားဆိုတာကို PostgreSQL က ခြေရာခံပါတယ်။ ဒီအချက်အလက်ကို table ရဲ့ *visibility map* (heap page တစ်ခုချင်းစီရဲ့ မြင်နိုင်မှု အခြေအနေကို မှတ်သားထားတဲ့ map) ထဲက bit တစ်ခုမှာ သိမ်းထားပါတယ်။ Index-only scan က ဖြစ်နိုင်ခြေ ရှိတဲ့ index entry တစ်ခု တွေ့ပြီးနောက် — သက်ဆိုင်ရာ heap page ရဲ့ visibility map bit ကို စစ်ဆေးပါတယ်။ အဲဒီ bit သတ်မှတ်ထားရင် — row က မြင်နိုင်တယ်လို့ သိရတာကြောင့် — နောက်ထပ် အလုပ် ဘာမှ မလုပ်ဘဲ data ကို ပြန်ပေးလိုက်လို့ ရပါတယ်။ Bit မသတ်မှတ်ထားရင်တော့ — row က မြင်နိုင်လား မမြင်နိုင်ဘူးလား သိဖို့ heap entry ကို သွားကြည့်ရပါတယ် — ဒါကြောင့် သာမန် index scan နဲ့ ယှဉ်ရင် performance အကျိုးအမြတ် ဘာမှ မရှိပါဘူး။ အောင်မြင်တဲ့ ကိစ္စမှာတောင် — ဒီနည်းလမ်းက visibility map access တွေနဲ့ heap access တွေကို အစားထိုး သုံးနေရတာပါ — ဒါပေမယ့် visibility map ရဲ့ အရွယ်အစားက သူ ဖော်ပြနေတဲ့ heap ရဲ့ 10,000 ပုံ တစ်ပုံ (four orders of magnitude) လောက်ပဲ ရှိတာကြောင့် — အဲဒါကို ဝင်ရောက်ဖို့ လိုအပ်တဲ့ physical I/O က အများကြီး နည်းပါတယ်။ အခြေအနေ အများစုမှာ visibility map က memory ထဲမှာ အချိန်ပြည့် cached (ကက်ရှ်) ဖြစ်နေပါတယ်။

အတိုချုပ် ပြောရရင် — အခြေခံ လိုအပ်ချက် နှစ်ခု ပြည့်မီတာနဲ့ index-only scan က ဖြစ်နိုင်ပေမယ့် — table ရဲ့ heap page တွေထဲက သိသာထင်ရှားတဲ့ အချိုးအစားတစ်ခုမှာ all-visible bit (page ထဲက row အားလုံး မြင်နိုင်ကြောင်း ပြသော bit) တွေ သတ်မှတ်ထားမှသာလျှင် အကျိုးရှိပါတယ်။ ဒါပေမယ့် — row တွေရဲ့ ကြီးမားတဲ့ အချိုးအစားတစ်ခုက မပြောင်းလဲတဲ့ table တွေက တော်တော်လေး အဖြစ်များတာကြောင့် — ဒီ scan အမျိုးအစားက လက်တွေ့မှာ အလွန် အသုံးဝင်ပါတယ်။

Index-only scan feature ကို ထိထိရောက်ရောက် အသုံးချဖို့ဆိုရင် — *covering index* (သင်မကြာခဏ run လေ့ရှိတဲ့ query အမျိုးအစားတစ်ခုအတွက် လိုအပ်တဲ့ column တွေ ပါဝင်အောင် အထူး ဒီဇိုင်းဆွဲထားတဲ့ index) တစ်ခုကို ဖန်တီးဖို့ ရွေးချယ်နိုင်ပါတယ်။ Query တွေက များသောအားဖြင့် — ရှာဖွေတဲ့နေရာမှာ သုံးတဲ့ column တွေထက် column အများကြီး ပိုပြီး ပြန်ယူဖို့ လိုတတ်တာကြောင့် — PostgreSQL က column တစ်ချို့ကို "payload" (index ထဲမှာ သိမ်းထားရုံသက်သက် ဖြစ်ပြီး search key ရဲ့ အစိတ်အပိုင်း မဟုတ်တဲ့ column) သက်သက်အဖြစ် ထားပြီး ဖန်တီးနိုင်တဲ့ index တစ်ခုကို ခွင့်ပြုပေးပါတယ်။ ဒါကို အပို column တွေကို စာရင်းပြုစုပေးတဲ့ `INCLUDE` clause ထည့်ခြင်းအားဖြင့် လုပ်ဆောင်ပါတယ်။ ဥပမာ — သင့်အနေနဲ့ ဒီလို query မျိုးကို မကြာခဏ run လေ့ ရှိတယ်ဆိုရင် —

```sql
SELECT y FROM tab WHERE x = 'key';
```

ဒီလို query တွေကို မြန်ဆန်အောင် လုပ်ဖို့ ရိုးရာ နည်းလမ်းကတော့ — `x` ပေါ်မှာပဲ index တစ်ခု ဖန်တီးတာ ဖြစ်ပါလိမ့်မယ်။ ဒါပေမယ့် ဒီလို သတ်မှတ်ထားတဲ့ index တစ်ခုကတော့ —

```sql
CREATE INDEX tab_x_y ON tab(x) INCLUDE (y);
```

heap ကို မသွားရောက်ဘဲ `y` တန်ဖိုးကို index ကနေ ရနိုင်တာကြောင့် — ဒီ query တွေကို index-only scan အဖြစ် ကိုင်တွယ်နိုင်ပါတယ်။

Column `y` က index ရဲ့ search key ထဲမှာ မပါတာကြောင့် — index က ကိုင်တွယ်နိုင်တဲ့ data type ဖြစ်နေဖို့ မလိုအပ်ပါဘူး။ အဲဒါကို index ထဲမှာ သိမ်းထားရုံပဲ ဖြစ်ပြီး — index ရဲ့ ယန္တရားက အဓိပ္ပာယ် ကောက်ယူခြင်း မပြုပါဘူး။ ဒါ့အပြင် — index က unique index ဆိုရင် — ဥပမာ

```sql
CREATE UNIQUE INDEX tab_x_y ON tab(x) INCLUDE (y);
```

ဆိုရင် — uniqueness (မူထူးခြားမှု) သတ်မှတ်ချက်က `x` column တစ်ခုတည်းကိုပဲ သက်ရောက်ပြီး — `x` နဲ့ `y` ပေါင်းစပ်မှုကိုတော့ သက်ရောက်ခြင်း မရှိပါဘူး။ (`INCLUDE` clause ကို `UNIQUE` နဲ့ `PRIMARY KEY` constraint တွေထဲမှာလည်း ရေးလို့ရပြီး — ဒီလို index မျိုး တည်ဆောက်ဖို့အတွက် နောက်ထပ် syntax တစ်မျိုး ဖြစ်ပါတယ်။)

Non-key payload column တွေကို index ထဲ ထည့်တာကို — အထူးသဖြင့် ကျယ်ပြန့်တဲ့ (wide) column တွေကို — ရှောင်သင့်ရှောင်ထိုက်အောင် သတိထားတာ ပညာရှိရာရောက်ပါတယ်။ Index tuple တစ်ခုက index type အတွက် ခွင့်ပြုထားတဲ့ အများဆုံး အရွယ်အစားထက် ကျော်လွန်သွားရင် — data ထည့်သွင်းမှု မအောင်မြင်ဘဲ ဖြစ်သွားပါလိမ့်မယ်။ ဘယ်လိုပဲ ဖြစ်ဖြစ် — non-key column တွေက index ရဲ့ table ထဲက data တွေကို ပုံတူပွား သိမ်းထားတာမို့ — index ရဲ့ အရွယ်အစားကို ဖောင်းပွစေပြီး — ရှာဖွေမှုတွေကို နှေးကွေးစေနိုင်ပါတယ်။ ပြီးတော့ သတိရထားရမှာက — table က index-only scan မှာ heap ကို မလိုအပ်တော့လောက်အောင် နှေးကွေးစွာ ပြောင်းလဲနေမှသာလျှင် payload column တွေ index ထဲ ထည့်တာ အဓိပ္ပာယ် ရှိပါတယ်။ Heap tuple ကို ဘယ်လိုပဲ ဖြစ်ဖြစ် သွားကြည့်ရမယ်ဆိုရင် — column တန်ဖိုးကို အဲဒီကနေ ယူတာက ထပ်ဆောင်း ကုန်ကျစရိတ် ဘာမှ မရှိပါဘူး။ နောက်ထပ် ကန့်သတ်ချက်တွေကတော့ — expression တွေကို လောလောဆယ် included column (index ထဲ ထည့်သွင်းသိမ်းထားသော column) အဖြစ် ပံ့ပိုးပေးခြင်း မရှိသေးဘဲ — B-tree၊ GiST နဲ့ SP-GiST index တွေကပဲ လောလောဆယ် included column တွေကို ပံ့ပိုးပေးတယ် ဆိုတာတွေ ဖြစ်ပါတယ်။

PostgreSQL မှာ `INCLUDE` feature မပေါ်ခင်က — လူတွေက payload column တွေကို သာမန် index column တွေအနေနဲ့ ရေးသားပြီး covering index တွေကို တခါတရံ ပြုလုပ်ခဲ့ကြပါတယ် — ဥပမာ

```sql
CREATE INDEX tab_x_y ON tab(x, y);
```

လို့ ရေးခဲ့ကြတာပါ — `y` ကို `WHERE` clause ထဲမှာ ဘယ်တော့မှ သုံးဖို့ ရည်ရွယ်ချက် မရှိဘဲနဲ့တောင် ဖြစ်ပါတယ်။ အပို column တွေက နောက်ဆုံး (trailing) column တွေ ဖြစ်နေသရွေ့ ဒီနည်းလမ်းက ကောင်းကောင်း အလုပ်လုပ်ပါတယ်။ အဲဒီ column တွေကို ရှေ့ဆုံး (leading) column တွေ ဖြစ်အောင် လုပ်တာကတော့ — [အပိုင်း 11.3](/docs/postgresql/indexes-multicolumn) မှာ ရှင်းပြထားတဲ့ အကြောင်းရင်းတွေကြောင့် မပညာရှိပါဘူး။ ဒါပေမယ့် — ဒီနည်းလမ်းက key column တွေပေါ်မှာ uniqueness ကို index က ပြဋ္ဌာန်း (enforce) စေချင်တဲ့ အခြေအနေမျိုးကိုတော့ ပံ့ပိုးမပေးပါဘူး။

*Suffix truncation* (နောက်ဆုံးအပိုင်း ဖြတ်တောက်ခြင်း) က အပေါ်ဆုံး B-Tree level တွေကနေ non-key column တွေကို အမြဲတမ်း ဖယ်ရှားပါတယ်။ Payload column တွေက index scan တွေကို လမ်းညွှန်ဖို့ ဘယ်တော့မှ အသုံးမပြုတာကြောင့် ဖြစ်ပါတယ်။ ဒီ ဖြတ်တောက်မှု လုပ်ငန်းစဉ်က — ကျန်ရှိနေတဲ့ key column prefix (ရှေ့ပိုင်း column စု) တွေက အနိမ့်ဆုံး B-Tree level ပေါ်က tuple တွေကို ဖော်ပြဖို့ လုံလောက်နေပြီဆိုရင် — နောက်ဆုံး key column တစ်ခု ဒါမှမဟုတ် တစ်ခုထက်ပိုတာကိုပါ ဖယ်ရှားပါတယ်။ လက်တွေ့မှာ — `INCLUDE` clause မပါတဲ့ covering index တွေက ထိရောက်စွာ payload သဘောဆောင်တဲ့ column တွေကို အပေါ်ဆုံး level တွေမှာ မသိမ်းတော့ဘဲ ရှောင်နိုင်လေ့ ရှိပါတယ်။ ဒါပေမယ့် — payload column တွေကို non-key column အဖြစ် အတိအကျ သတ်မှတ်ထားရင်တော့ — အပေါ်ဆုံး level တွေက tuple တွေ သေးငယ်နေအောင် စိတ်ချရတဲ့ နည်းလမ်းနဲ့ ထိန်းသိမ်းပေးပါတယ်။

သဘောတရားအရဆိုရင် — index-only scan တွေကို expression index တွေနဲ့လည်း သုံးလို့ ရပါတယ်။ ဥပမာ — `x` က table column တစ်ခု ဖြစ်ပြီး `f(x)` ပေါ်မှာ index တစ်ခု ရှိတယ်ဆိုရင် — ဒီ query ကို index-only scan အဖြစ် execute (လုပ်ဆောင်) နိုင်သင့်ပါတယ် —

```sql
SELECT f(x) FROM tab WHERE f(x) < 1;
```

ပြီးတော့ `f()` က တွက်ချက်ရတာ စရိတ်ကြီးတဲ့ function ဆိုရင် — ဒါက အလွန် ဆွဲဆောင်မှု ရှိပါတယ်။ ဒါပေမယ့် — PostgreSQL ရဲ့ planner (query အတွက် အကောင်းဆုံး plan ရေးဆွဲပေးသော အစိတ်အပိုင်း) က လောလောဆယ်မှာ ဒီလို ကိစ္စမျိုးတွေအတွက် သိပ်တော်တာ မဟုတ်ပါဘူး။ Query အတွက် လိုအပ်တဲ့ column တွေ အားလုံးကို index ကနေ ရနိုင်မှသာလျှင် — အဲဒီ query ကို index-only scan နဲ့ run နိုင်ခြေ ရှိတယ်လို့ planner က မှတ်ယူပါတယ်။ ဒီ ဥပမာမှာ — `x` က `f(x)` ဆိုတဲ့ ကွင်းစကွင်းပိတ် အတွင်းမှာပဲ လိုအပ်တာပါ — ဒါပေမယ့် planner က အဲဒါကို သတိမထားမိဘဲ — index-only scan မဖြစ်နိုင်ဘူးလို့ ကောက်ချက်ချပါတယ်။ Index-only scan က အားကျစရာ လုံလောက်စွာ တန်ဖိုးရှိတယ်လို့ ထင်ရရင် — `x` ကို included column အဖြစ် ထည့်ခြင်းအားဖြင့် ဒီပြဿနာကို ရှောင်ကွင်းနိုင်ပါတယ် — ဥပမာ

```sql
CREATE INDEX tab_f_x ON tab (f(x)) INCLUDE (x);
```

နောက်ထပ် သတိပြုရမယ့် အချက်တစ်ခုကတော့ — `f(x)` ကို ပြန်လည် တွက်ချက်ခြင်း မဖြစ်အောင် ရှောင်ဖို့ ရည်ရွယ်တယ်ဆိုရင် — indexable `WHERE` clause တွေထဲမှာ မပါဝင်တဲ့ `f(x)` အသုံးပြုမှုတွေကို planner က index column နဲ့ မလွဲမသွေ ကိုက်ညီအောင် လုပ်ပေးမှာ မဟုတ်ပါဘူး။ အပေါ်မှာ ပြထားတဲ့ ရိုးရှင်းတဲ့ query တွေမှာတော့ များသောအားဖြင့် မှန်မှန်ကန်ကန် လုပ်နိုင်ပါတယ် — ဒါပေမယ့် join တွေ ပါဝင်တဲ့ query တွေမှာတော့ မဟုတ်ပါဘူး။ ဒီလို ချို့ယွင်းချက်တွေကို PostgreSQL ရဲ့ အနာဂတ် version တွေမှာ ပြုပြင်ပေးနိုင်ပါတယ်။

Partial index တွေကလည်း index-only scan နဲ့ စိတ်ဝင်စားစရာ အပြန်အလှန် သက်ရောက်မှုတွေ ရှိပါတယ်။ [ဥပမာ 11.3](/docs/postgresql/indexes-partial) မှာ ပြထားတဲ့ partial index ကို ကြည့်ကြရအောင် —

```sql
CREATE UNIQUE INDEX tests_success_constraint ON tests (subject, target)
    WHERE success;
```

သဘောတရားအရဆိုရင် — ဒီ index ပေါ်မှာ index-only scan လုပ်ပြီး ဒီလို query မျိုးကို ဖြေဆိုနိုင်ပါတယ် —

```sql
SELECT target FROM tests WHERE subject = 'some-subject' AND success;
```

ဒါပေမယ့် ပြဿနာ တစ်ခု ရှိပါတယ် — `WHERE` clause က index ရဲ့ result column (ရလဒ် column) အဖြစ် မရနိုင်တဲ့ `success` ကို ရည်ညွှန်းနေပါတယ်။ ဒါပေမဲ့လည်း index-only scan က ဖြစ်နိုင်ပါသေးတယ် — အကြောင်းကတော့ plan က run time (လုပ်ဆောင်နေချိန်) မှာ `WHERE` clause ရဲ့ အဲဒီအပိုင်းကို ပြန်လည် စစ်ဆေးဖို့ မလိုပါဘူး — index ထဲမှာ တွေ့ရတဲ့ entry တွေ အားလုံးမှာ `success = true` ဖြစ်တာကြောင့် — plan ထဲမှာ အတိအကျ ထပ်စစ်ဆေးစရာ မလိုပါဘူး။ PostgreSQL version 9.6 နဲ့ ၎င်းနောက်ပိုင်း version တွေကတော့ ဒီလို ကိစ္စမျိုးတွေကို မှတ်သားနိုင်ပြီး — index-only scan တွေ ထုတ်လုပ်ဖို့ ခွင့်ပြုပါတယ် — ဒါပေမယ့် ရှေးဟောင်း version တွေကတော့ ခွင့်ပြုမှာ မဟုတ်ပါဘူး။
