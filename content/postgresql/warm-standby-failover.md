## 26.3. Failover (primary ပြောင်းလဲ လွှဲပြောင်းမှု)

Primary server (ပင်မ server) က ကျရှုံးသွားခဲ့ရင် — standby server (အရန် server) က failover (primary ပြောင်းလဲ လွှဲပြောင်းမှု) လုပ်ငန်းစဉ်တွေကို စတင်သင့်ပါတယ်။

Standby server က ကျရှုံးသွားခဲ့ရင်တော့ — failover လုပ်ဖို့ မလိုအပ်ပါဘူး။ Standby server ကို — နောက်ပိုင်း အချိန်တစ်ခုမှာ ဖြစ်စေကာမူ — ပြန်လည် စတင်နိုင်မယ်ဆိုရင် — restartable recovery (ပြန်လည် စတင် လုပ်နိုင်သော recovery) ရဲ့ အကျိုးကို ခံယူပြီး — recovery လုပ်ငန်းစဉ်ကိုလည်း ချက်ချင်း ပြန်လည် စတင်နိုင်ပါတယ်။ Standby server ကို ပြန်လည် စတင်လို့ မရဘူးဆိုရင်တော့ — standby server instance (standby server ၏ လည်ပတ်မှု တစ်ခု) အသစ် တစ်ခုလုံးကို ဖန်တီးပေးရပါမယ်။

Primary server က ကျရှုံးပြီး — standby server က primary အသစ် ဖြစ်လာပြီးတဲ့နောက် — primary အဟောင်းက ပြန်လည် စတင်လာခဲ့ရင် — သူကိုယ်တိုင် primary မဟုတ်တော့ဘူးဆိုတာကို primary အဟောင်းဆီ အသိပေးဖို့ ယန္တရား တစ်ခု သင့်မှာ ရှိရပါမယ်။ ဒါကို တခါတရံ STONITH (Shoot The Other Node In The Head — အခြား node ကို ပစ်လိုက်ခြင်း) လို့ သိကြပြီး — system နှစ်ခုလုံးက သူတို့ကိုယ်သူတို့ primary လို့ ထင်နေတဲ့ အခြေအနေမျိုးတွေကို ရှောင်ရှားဖို့ လိုအပ်ပါတယ် — အဲဒီလို ဖြစ်ရင် ရှုပ်ထွေးမှုတွေ ဖြစ်ပေါ်ပြီး — နောက်ဆုံးမှာ data ဆုံးရှုံးမှုအထိ ဦးတည်သွားလို့ပါ။

Failover system (primary ပြောင်းလဲ လွှဲပြောင်းမှု စနစ်) အများအပြားက — primary နဲ့ standby ဆိုတဲ့ system နှစ်ခုကိုပဲ သုံးပြီး — system နှစ်ခုကြားက ချိတ်ဆက်မှုနဲ့ primary ရဲ့ ရှင်သန် လည်ပတ်နိုင်မှု (viability) ကို စဉ်ဆက်မပြတ် စစ်ဆေးဖို့ — heartbeat (နှလုံးခုန် အချက်ပြမှု) လို့ ခေါ်တဲ့ ယန္တရား တစ်မျိုးမျိုးနဲ့ ချိတ်ဆက်ထားပါတယ်။ မသင့်လျော်တဲ့ failover အခြေအနေ တချို့ကို ကာကွယ်ဖို့ — တတိယ system တစ်ခု (witness server — သက်သေ server — လို့ ခေါ်ပါတယ်) ကိုလည်း သုံးနိုင်ပေမယ့် — လုံလောက်တဲ့ ဂရုစိုက်မှုနဲ့ ပြင်းထန်တဲ့ စမ်းသပ်မှုတွေနဲ့ ပြင်ဆင် သတ်မှတ်ထားခြင်း မရှိဘူးဆိုရင် — ထပ်ဆောင်း ရှုပ်ထွေးမှုက အကျိုးရှိချင်မှ ရှိနိုင်ပါတယ်။

PostgreSQL က primary ပေါ်မှာ ကျရှုံးမှုတစ်ခုကို ဖော်ထုတ်ပြီး — standby database server ဆီ အသိပေးဖို့ လိုအပ်တဲ့ system software (စနစ် ဆော့ဖ်ဝဲ) ကိုတော့ ထောက်ပံ့ပေးခြင်း မရှိပါဘူး။ ဒီလို tools တွေ အများအပြား ရှိပြီး — IP address migration (IP လိပ်စာ ရွှေ့ပြောင်းမှု) လို — အောင်မြင်တဲ့ failover အတွက် လိုအပ်တဲ့ operating system ရဲ့ စွမ်းဆောင်ရည် ယန္တရားတွေနဲ့ ကောင်းစွာ ပေါင်းစပ်ထားပါတယ်။

Standby ဆီ failover ဖြစ်ပွားပြီးတာနဲ့ — လည်ပတ်နေတဲ့ server က တစ်ခုတည်းပဲ ကျန်ပါတော့တယ်။ ဒါကို degenerate state (အင်အား ဆုတ်ယုတ်နေသော အခြေအနေ) လို့ သိကြပါတယ်။ Standby အဟောင်းက ယခု primary ဖြစ်လာပေမယ့် — primary အဟောင်းကတော့ ရပ်ဆိုင်း (down) နေပြီး — ဆက်လက် ရပ်ဆိုင်းနေနိုင်ပါတယ်။ ပုံမှန် လည်ပတ်မှုဆီ ပြန်လည် ရောက်ရှိဖို့ဆိုရင် — standby server တစ်ခုကို — သူ ပြန်လည် စတင်လာတဲ့အခါ primary အဟောင်း system ပေါ်မှာ ဖြစ်စေ — တတိယ ဒါမှမဟုတ် အသစ် ဖြစ်နိုင်တဲ့ system တစ်ခုပေါ်မှာ ဖြစ်စေ — ပြန်လည် ဖန်တီးရပါမယ်။ [pg_rewind](https://www.postgresql.org/docs/current/app-pgrewind.html) utility ကို — ကြီးမားတဲ့ clusters တွေမှာ ဒီလုပ်ငန်းစဉ်ကို အရှိန်မြှင့်ဖို့ သုံးနိုင်ပါတယ်။ ပြီးမြောက်သွားတာနဲ့ — primary နဲ့ standby တို့ဟာ အခန်းကဏ္ဍ (role) တွေ လဲလှယ်ပြီးသား ဖြစ်တယ်လို့ မှတ်ယူနိုင်ပါတယ်။ Standby server အသစ်ကို ပြန်လည် မဖန်တီးမချင်း — primary အသစ်အတွက် backup ပေးဖို့ — လူအချို့က တတိယ server တစ်ခုကို သုံးဖို့ ရွေးချယ်ကြပါတယ် — ဒါပေမယ့် — ဒါက system configuration နဲ့ လည်ပတ်မှု လုပ်ငန်းစဉ်တွေကို ရှုပ်ထွေးစေတာ ထင်ရှားပါတယ်။

ဒါကြောင့် — primary ကနေ standby server ဆီ ပြောင်းလဲခြင်းက လျင်မြန်နိုင်ပေမယ့် — failover cluster ကို ပြန်လည် ပြင်ဆင်ဖို့ အချိန် အတော်အတန် လိုအပ်ပါတယ်။ Primary ကနေ standby ဆီ ပုံမှန် ပြောင်းလဲခြင်းက အသုံးဝင်ပါတယ် — အကြောင်းကတော့ system တစ်ခုချင်းစီပေါ်မှာ ပြုပြင်ထိန်းသိမ်းမှု (maintenance) အတွက် ပုံမှန် downtime (ရပ်နားချိန်) တွေ ရရှိစေလို့ပါ။ ဒါက — သင့်လိုအပ်ချိန်မှာ တကယ် အလုပ်လုပ်ဖြစ်မဖြစ် သေချာစေဖို့ — failover ယန္တရားကို စမ်းသပ်မှု တစ်ခုအနေနဲ့လည်း ဆောင်ရွက်ပေးပါတယ်။ စာဖြင့် မှတ်တမ်းတင်ထားတဲ့ စီမံခန့်ခွဲမှု လုပ်ငန်းစဉ် (written administration procedures) တွေ ရှိထားဖို့ အကြံပြုလိုပါတယ်။

သင့်က logical replication slot synchronization (logical replication slot များ ထပ်တူကျအောင် ချိန်ကိုက်ခြင်း) ကို ရွေးချယ် သုံးစွဲထားတယ်ဆိုရင် ([အပိုင်း 47.2.3](https://www.postgresql.org/docs/current/logicaldecoding-explanation.html#LOGICALDECODING-REPLICATION-SLOTS-SYNCHRONIZATION) ကို ကြည့်ပါ) — standby server ဆီ မပြောင်းမခင် — standby server ပေါ်မှာ synchronization လုပ်ထားတဲ့ logical slots တွေက failover အတွက် အသင့် ဖြစ်မဖြစ် စစ်ဆေးဖို့ အကြံပြုလိုပါတယ်။ ဒါကို [အပိုင်း 29.3](https://www.postgresql.org/docs/current/logical-replication-failover.html) မှာ ဖော်ပြထားတဲ့ အဆင့်တွေကို လိုက်နာခြင်းအားဖြင့် လုပ်ဆောင်နိုင်ပါတယ်။

Log-shipping standby server တစ်ခုရဲ့ failover ကို စတင်ဖို့ဆိုရင် — `pg_ctl promote` ကို run လုပ်ပါ ဒါမှမဟုတ် `pg_promote()` ကို ခေါ်ယူပါ။ သင့်က — high availability ရည်ရွယ်ချက်တွေအတွက် မဟုတ်ဘဲ — primary ကနေ read-only (ဖတ်ရှုရုံသက်သက်) queries တွေကို လွှဲပြောင်း သက်သာစေဖို့ပဲ သုံးမယ့် — reporting server (အစီရင်ခံမှု server) တွေကို ပြင်ဆင် သတ်မှတ်နေတာဆိုရင် — promote လုပ်ဖို့ မလိုအပ်ပါဘူး။
