## 13.4. Data Consistency Checks at the Application Level (application အဆင့်တွင် data ညီညွတ်မှု စစ်ဆေးခြင်း)

- **13.4.1. Enforcing Consistency with Serializable Transactions (Serializable transaction များဖြင့် consistency ထိန်းသိမ်းခြင်း)**
- **13.4.2. Enforcing Consistency with Explicit Blocking Locks (explicit blocking lock များဖြင့် consistency ထိန်းသိမ်းခြင်း)**

Data integrity နဲ့ ပတ်သက်တဲ့ business rules (လုပ်ငန်း စည်းမျဉ်းများ) တွေကို Read Committed transaction တွေနဲ့ အတင်းအကျပ် လိုက်နာစေဖို့ ကြိုးစားတာက အလွန် ခက်ခဲပါတယ် — data ရဲ့ မြင်ကွင်း (view) က statement တစ်ခုနဲ့ တစ်ခု ရွေ့လျား ပြောင်းလဲနေပြီး — write conflict (ရေးသားမှု ထိပ်တိုက်မှု) တစ်ခု ဖြစ်ပေါ်လာရင် — statement တစ်ခုတည်းကတောင် statement ရဲ့ snapshot အတွင်းမှာပဲ ကိုယ့်ကိုယ်ကို ကန့်သတ်ထားနိုင်မှာ မဟုတ်လို့ပါ။

Repeatable Read transaction တစ်ခုက လုပ်ဆောင်နေစဉ် တစ်လျှောက်လုံး data ရဲ့ တည်ငြိမ်တဲ့ (stable) မြင်ကွင်း တစ်ခုကို ပိုင်ဆိုင်ထားပေမယ့် — data consistency စစ်ဆေးမှုတွေအတွက် MVCC snapshot တွေကို သုံးတဲ့အခါ — *read/write conflicts* (ဖတ်ခြင်း/ရေးခြင်း ထိပ်တိုက်မှုများ) လို့ ခေါ်တဲ့ အရာတစ်ခု ပါဝင်ပတ်သက်တဲ့ — သိမ်မွေ့တဲ့ ပြဿနာတစ်ခု ရှိပါတယ်။ Transaction တစ်ခုက data ကို ရေးလိုက်ပြီး — တစ်ပြိုင်နက် လုပ်ဆောင်နေတဲ့ transaction တစ်ခုက အဲဒီ data ကို ဖတ်ဖို့ ကြိုးစားရင် (ရေးတာမတိုင်ခင် ဖြစ်စေ၊ ရေးပြီးမှ ဖြစ်စေ) — အဲဒီ transaction က တစ်ဖက်ရဲ့ အလုပ်ကို မြင်ရမှာ မဟုတ်ပါဘူး။ အဲဒီအခါ — ဘယ်ဟာက အရင် စတင်ခဲ့တယ်၊ ဘယ်ဟာက အရင် commit လုပ်ခဲ့တယ်ဆိုတာ ဘယ်လိုပဲ ဖြစ်ဖြစ် — reader (ဖတ်သူ) က ကိုယ့်အလုပ်ကို အရင် လုပ်ဆောင်ပြီးသား အနေနဲ့ ပေါ်လာပါတယ်။ ဒီလောက်နဲ့ပဲ ရပ်သွားမယ်ဆိုရင် — ပြဿနာ မရှိပါဘူး — ဒါပေမယ့် — reader ကိုယ်တိုင်ကလည်း — တစ်ပြိုင်နက် လုပ်ဆောင်နေတဲ့ transaction တစ်ခုက ဖတ်တဲ့ data တစ်ခုကို ရေးလိုက်မယ်ဆိုရင် — အရင်က ပြောခဲ့တဲ့ transaction နှစ်ခုထဲက တစ်ခုခုထက် အရင် လုပ်ဆောင်ပြီးသား ပုံပေါ်နေတဲ့ transaction တစ်ခု ရှိလာပါတော့တယ်။ နောက်ဆုံး လုပ်ဆောင်ခဲ့သလို ပေါ်နေတဲ့ transaction က တကယ်တော့ အရင် commit လုပ်လိုက်မယ်ဆိုရင် — transaction တွေရဲ့ လုပ်ဆောင်မှု အစီအစဉ် (order of execution) ကို ကိုယ်စားပြုတဲ့ graph တစ်ခုထဲမှာ cycle (သံသရာ) တစ်ခု ပေါ်လာဖို့ အရမ်း လွယ်ကူပါတယ်။ အဲဒီလို cycle တစ်ခု ပေါ်လာတဲ့အခါ — အကူအညီ တစ်စုံတစ်ရာ မရှိဘဲနဲ့တော့ — integrity checks တွေ မှန်မှန်ကန်ကန် အလုပ်လုပ်မှာ မဟုတ်ပါတော့ဘူး။

[အပိုင်း 13.2.3](/docs/postgresql/transaction-iso) မှာ ဖော်ပြခဲ့သလို — Serializable transaction တွေဆိုတာ — အန္တရာယ်ရှိတဲ့ read/write conflict ပုံစံတွေအတွက် — blocking မဟုတ်တဲ့ (nonblocking) စောင့်ကြည့်မှုတွေ ထပ်ဖြည့်ထားတဲ့ — Repeatable Read transaction တွေပဲ ဖြစ်ပါတယ်။ လုပ်ဆောင်မှု အစီအစဉ်ရဲ့ ထင်ရှားတဲ့ (apparent) ပုံစံထဲမှာ cycle တစ်ခုကို ဖြစ်စေနိုင်တဲ့ ပုံစံတစ်ခုကို ထောက်လှမ်းမိတဲ့အခါ — cycle ကို ချိုးဖျက်ဖို့ — ပါဝင်ပတ်သက်နေတဲ့ transaction တွေထဲက တစ်ခုကို rollback လုပ်ပါတယ်။

### 13.4.1. Enforcing Consistency with Serializable Transactions (Serializable transaction များဖြင့် consistency ထိန်းသိမ်းခြင်း)

Serializable transaction isolation level ကို — writes (ရေးသားမှုများ) အားလုံးအတွက်ရော — data ရဲ့ တည်ငြိမ်တဲ့ မြင်ကွင်း လိုအပ်တဲ့ reads (ဖတ်ရှုမှုများ) အားလုံးအတွက်ပါ သုံးမယ်ဆိုရင် — consistency သေချာစေဖို့ တခြား ကြိုးပမ်းအားထုတ်မှု ဘာမှ မလိုအပ်တော့ပါဘူး။ Consistency သေချာစေဖို့ serializable transaction တွေကို သုံးဖို့ ရေးထားတဲ့ — တခြား environment တွေက software တွေက — ဒီကိစ္စမှာ PostgreSQL မှာ “အလုပ်ဖြစ်ရုံသာ” (“just work” — အပိုပြင်ဆင်မှု မလိုဘဲ အလုပ်လုပ်သည်) ဖြစ်သင့်ပါတယ်။

ဒီနည်းလမ်းကို သုံးတဲ့အခါ — application software က — serialization failure နဲ့ rollback ဖြစ်သွားတဲ့ transaction တွေကို အလိုအလျောက် retry (ပြန်လည် ကြိုးစား) လုပ်ပေးတဲ့ framework တစ်ခုကို ဖြတ်သန်း သုံးစွဲနေမယ်ဆိုရင် — application programmer တွေအပေါ် မလိုအပ်တဲ့ ဝန်ထုပ်ဝန်ပိုး (burden) တစ်ခု ဖြစ်လာတာကို ရှောင်ရှားနိုင်ပါလိမ့်မယ်။ `default_transaction_isolation` ကို `serializable` လို့ သတ်မှတ်ထားတာက အကြံကောင်းတစ်ခု ဖြစ်နိုင်ပါတယ်။ Trigger တွေထဲမှာ transaction isolation level ကို စစ်ဆေးခြင်းအားဖြင့် — တခြား transaction isolation level တစ်ခုကို — မတော်တဆ ဖြစ်စေ၊ integrity checks တွေကို ဖျက်ဆီးဖို့ ရည်ရွယ်ချက်နဲ့ ဖြစ်စေ — သုံးမိမှာ မရှိအောင် သေချာစေမယ့် ဆောင်ရွက်ချက် (action) တစ်ခုခု လုပ်ထားတာကလည်း ပညာရှိရာ ရောက်ပါတယ်။

Performance ဆိုင်ရာ အကြံပြုချက်တွေအတွက် [အပိုင်း 13.2.3](/docs/postgresql/transaction-iso) ကို ကြည့်ပါ။

> **သတိပေးချက်:** Serializable transaction တွေကို သုံးပြီး ရရှိတဲ့ ဒီအဆင့် integrity ကာကွယ်မှုက — hot standby mode ([အပိုင်း 26.4](https://www.postgresql.org/docs/current/hot-standby.html)) ဒါမှမဟုတ် logical replica (ယုတ္တိ ပုံတူပွားမှု) တွေအထိတော့ သက်ရောက်မှု မရှိသေးပါဘူး။ ဒါကြောင့် — hot standby ဒါမှမဟုတ် logical replication သုံးနေသူတွေက — primary (ပင်မ ဆာဗာ) ပေါ်မှာ Repeatable Read နဲ့ explicit locking တွေကို သုံးချင်ကြပါလိမ့်မယ်။

### 13.4.2. Enforcing Consistency with Explicit Blocking Locks (explicit blocking lock များဖြင့် consistency ထိန်းသိမ်းခြင်း)

Non-serializable writes တွေ ဖြစ်နိုင်တဲ့အခါ — row တစ်ခုရဲ့ လက်ရှိ တရားဝင်မှု (current validity) ကို သေချာစေဖို့ ပြီးတော့ ၎င်းကို concurrent updates တွေကနေ ကာကွယ်ဖို့ — `SELECT FOR UPDATE`, `SELECT FOR SHARE` ဒါမှမဟုတ် သင့်လျော်တဲ့ `LOCK TABLE` statement တစ်ခုကို သုံးရပါမယ်။ (`SELECT FOR UPDATE` နဲ့ `SELECT FOR SHARE` တွေက ပြန်ပေးလိုက်တဲ့ row တွေကိုပဲ concurrent updates တွေကနေ lock လုပ်ပေးပြီး — `LOCK TABLE` ကတော့ table တစ်ခုလုံးကို lock လုပ်ပါတယ်။) Application တွေကို တခြား environment တွေကနေ PostgreSQL ဆီ port (ရွှေ့ပြောင်း) လုပ်တဲ့အခါ — ဒါကို ထည့်သွင်း စဉ်းစားသင့်ပါတယ်။

တခြား environment တွေကနေ ပြောင်းလဲလာသူတွေ သတိပြုသင့်တဲ့ နောက်တစ်ချက်က — `SELECT FOR UPDATE` က — တစ်ပြိုင်နက် လုပ်ဆောင်နေတဲ့ transaction တစ်ခုက ရွေးချယ်ထားတဲ့ row တစ်ခုကို update ဒါမှမဟုတ် delete လုပ်မှာ မဟုတ်ဘူးဆိုတာကို အာမခံပေးတာ မဟုတ်ပါဘူး။ အဲဒါကို PostgreSQL မှာ လုပ်ဖို့ဆိုရင် — တန်ဖိုး ဘာမှ ပြောင်းစရာ မလိုရင်တောင် — row ကို တကယ် (actually) update လုပ်ရပါတယ်။ `SELECT FOR UPDATE` က တခြား transaction တွေကို — တူညီတဲ့ lock ကို ရယူခြင်း ဒါမှမဟုတ် lock ဖြစ်နေတဲ့ row ကို သက်ရောက်စေမယ့် `UPDATE` ဒါမှမဟုတ် `DELETE` တစ်ခုခု လုပ်ဆောင်ခြင်းကနေ — ယာယီ (temporarily) ပိတ်ဆို့ထားပေမယ့် — ဒီ lock ကို ကိုင်ထားတဲ့ transaction က commit ဒါမှမဟုတ် rollback လုပ်လိုက်တာနဲ့ — lock ကိုင်ထားစဉ်အတွင်း row ကို တကယ့် `UPDATE` တစ်ခု လုပ်ဆောင်ခဲ့ခြင်း မရှိဘူးဆိုရင် — ပိတ်ဆို့ခံထားရတဲ့ transaction က conflict ဖြစ်တဲ့ operation ကို ဆက်လက် လုပ်ဆောင်သွားပါလိမ့်မယ်။

Global validity checks (တစ်ခုလုံး အတိုင်းအတာနဲ့ တရားဝင်မှု စစ်ဆေးမှုများ) တွေက non-serializable MVCC အောက်မှာ အပိုအားထုတ် စဉ်းစားမှု လိုအပ်ပါတယ်။ ဥပမာ — banking application တစ်ခုက — table တစ်ခုထဲက credit တွေ အားလုံးရဲ့ ပေါင်းလဒ်က — တခြား table တစ်ခုထဲက debit တွေ အားလုံးရဲ့ ပေါင်းလဒ်နဲ့ ညီမျှမယ်ဆိုတာကို — table နှစ်ခုလုံး တက်ကြွစွာ update လုပ်ခံနေရချိန်မှာ — စစ်ဆေးချင်တယ်ဆိုပါစို့။ `SELECT sum(...)` command နှစ်ခုရဲ့ ဆက်တိုက် ရလဒ်တွေကို နှိုင်းယှဉ်တာက — Read Committed mode မှာ — စိတ်ချရအောင် အလုပ်လုပ်မှာ မဟုတ်ပါဘူး — ဒုတိယ query က ပထမ query ထဲမှာ မပါဝင်ခဲ့တဲ့ transaction တွေရဲ့ ရလဒ်တွေကို ပါဝင်စေနိုင်လို့ပါ။ Sum နှစ်ခုလုံးကို repeatable read transaction တစ်ခုတည်းထဲမှာ လုပ်တာကတော့ — repeatable read transaction မစတင်ခင် commit လုပ်ပြီးသား transaction တွေရဲ့ အကျိုးသက်ရောက်မှုတွေကိုပဲ — တိကျတဲ့ ပုံရိပ် ရစေမှာ ဖြစ်ပေမယ့် — အဖြေကို ပို့ဆောင်ပေးလိုက်တဲ့ အချိန်မှာ အဲဒီအဖြေက ဆက်စပ်မှု (relevant) ရှိနေဦးမလားဆိုတာ — တရားဝင် (legitimately) သံသယ ဖြစ်စရာ ကောင်းပါတယ်။ Repeatable read transaction ကိုယ်တိုင်က — consistency check ကို မကြိုးစားခင် — ပြောင်းလဲမှု (change) တချို့ကို ကျင့်သုံးပြီးသား ဖြစ်နေမယ်ဆိုရင် — check ရဲ့ အသုံးဝင်မှုက ပိုတောင် အငြင်းပွားစရာ ဖြစ်လာပါတယ် — အခုဆိုရင် transaction စတင်ပြီးနောက် ပြောင်းလဲမှုတွေထဲက တချို့ကိုပဲ ပါဝင်စေပြီး — အားလုံး မပါဝင်တော့လို့ပါ။ အဲဒီလို အခြေအနေမျိုးမှာ — သေချာ စဉ်းစားတတ်တဲ့သူတစ်ယောက်က — လက်ရှိ အဖြစ်မှန်ရဲ့ အငြင်းပွားစရာ မရှိတဲ့ (indisputable) ပုံရိပ်တစ်ခု ရဖို့ — check အတွက် လိုအပ်တဲ့ table တွေ အားလုံးကို lock လုပ်ချင်ပါလိမ့်မယ်။ `SHARE` mode (သို့မဟုတ် ထိုထက် မြင့်တဲ့ mode) lock တစ်ခုက — lock လုပ်ထားတဲ့ table ထဲမှာ — လက်ရှိ transaction ရဲ့ ကိုယ်ပိုင် ပြောင်းလဲမှုတွေကလွဲရင် — uncommitted change (commit မလုပ်ရသေး ပြောင်းလဲမှု) တွေ မရှိဘူးဆိုတာ အာမခံပါတယ်။

ဒါ့အပြင် — concurrent changes တွေကို တားဆီးဖို့ explicit locking ကို အားကိုးနေမယ်ဆိုရင် — Read Committed mode ကို သုံးသင့်ပါတယ် — ဒါမှမဟုတ် — Repeatable Read mode မှာဆိုရင် — queries တွေ မလုပ်ဆောင်ခင် lock တွေကို ရယူဖို့ ဂရုစိုက်သင့်ပါတယ်။ Repeatable read transaction တစ်ခုက ရယူထားတဲ့ lock တစ်ခုက — table ကို ပြုပြင်မွမ်းမံနေတဲ့ တခြား transaction တွေ ဆက်လက် လည်ပတ်နေခြင်း မရှိတော့ဘူးဆိုတာ အာမခံပေးပေမယ့် — transaction က မြင်နေတဲ့ snapshot က lock ရယူခြင်းထက် စောတယ်ဆိုရင် — အခု commit လုပ်ပြီးသွားတဲ့ ပြောင်းလဲမှုတချို့ထက်လည်း စောနေနိုင်ပါတယ်။ Repeatable read transaction တစ်ခုရဲ့ snapshot ကို — တကယ်တော့ — ၎င်းရဲ့ ပထမဆုံး query ဒါမှမဟုတ် data-modification command (`SELECT`, `INSERT`, `UPDATE`, `DELETE` ဒါမှမဟုတ် `MERGE`) စတင်ချိန်မှာ အေးခဲသွားတာ (frozen) ဖြစ်လို့ — snapshot မအေးခဲခင်မှာ lock တွေကို အတိအကျ ရယူထားဖို့ ဖြစ်နိုင်ပါတယ်။
