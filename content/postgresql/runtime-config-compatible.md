## 19.13. Version and Platform Compatibility (ဗားရှင်းနှင့် platform လိုက်ဖက်မှု)

- **19.13.1. Previous PostgreSQL Versions (PostgreSQL ဗားရှင်း အဟောင်းများ)**
- **19.13.2. Platform and Client Compatibility (platform နှင့် client လိုက်ဖက်မှု)**

### 19.13.1. Previous PostgreSQL Versions (PostgreSQL ဗားရှင်း အဟောင်းများ)

- **array_nulls (boolean)** — array input parser က unquoted `NULL` ကို null array element တစ်ခုအဖြစ် သတ်မှတ်ကြောင်း အသိအမှတ်ပြုမပြုကို ဒါက ထိန်းချုပ်ပါတယ်။ Default အားဖြင့် ဒါက on ဖြစ်ပြီး — null တန်ဖိုးများ ပါဝင်တဲ့ array တန်ဖိုးတွေကို ထည့်သွင်း (enter) ခွင့်ပြုပါတယ်။ ဒါပေမယ့် — PostgreSQL 8.2 မတိုင်မီ ဗားရှင်းတွေက array ထဲမှာ null တန်ဖိုးများကို မထောက်ပံ့ခဲ့ဘဲ — ဒါကြောင့် `NULL` ကို “NULL” ဆိုတဲ့ string တန်ဖိုးရှိတဲ့ သာမန် array element တစ်ခုအဖြစ် သတ်မှတ်ခဲ့ပါတယ်။ အပြုအမူ အဟောင်း လိုအပ်တဲ့ application တွေနဲ့ နောက်ပြန် လိုက်ဖက်မှု (backward compatibility) အတွက် — ဒီ variable ကို off လို့ သတ်မှတ်နိုင်ပါတယ်။
ဒီ variable က off ဖြစ်နေရင်တောင် — null တန်ဖိုးများ ပါဝင်တဲ့ array တန်ဖိုးတွေကို ဖန်တီးနိုင်ပါသေးတယ် ဆိုတာ သတိပြုပါ။
- **backslash_quote (enum)** — string literal တစ်ခုထဲမှာ quote mark တစ်ခုကို `\'` နဲ့ ကိုယ်စားပြုနိုင်မနိုင်ကို ဒါက ထိန်းချုပ်ပါတယ်။ Quote mark တစ်ခုကို ကိုယ်စားပြုဖို့ ဦးစားပေးပြီး SQL standard နဲ့ ကိုက်ညီတဲ့ နည်းလမ်းက သူ့ကို နှစ်ခါ ရေးခြင်း (`''`) ဖြစ်ပေမယ့် — PostgreSQL က သမိုင်းအရ `\'` ကိုလည်း လက်ခံခဲ့ပါတယ်။ ဒါပေမယ့် — `\'` ကို သုံးခြင်းက security အန္တရာယ်တွေ ဖြစ်စေပါတယ် — အကြောင်းကတော့ client character set encoding တချို့မှာ — နောက်ဆုံး byte က ASCII `\` နဲ့ ကိန်းဂဏန်းအရ တူညီတဲ့ multibyte character တွေ ရှိတာမို့ပါ။ Client-side code က escaping ကို မှားယွင်းစွာ လုပ်ရင် — SQL-injection တိုက်ခိုက်မှု ဖြစ်နိုင်ပါတယ်။ ဒီအန္တရာယ်ကို — quote mark တစ်ခုကို backslash နဲ့ escape လုပ်ထားပုံရတဲ့ query တွေကို server က ပယ်ချ (reject) စေခြင်းဖြင့် ကာကွယ်နိုင်ပါတယ်။ backslash_quote ရဲ့ ခွင့်ပြုတဲ့ တန်ဖိုးတွေကတော့ on (`\'` ကို အမြဲ ခွင့်ပြုခြင်း)၊ off (အမြဲ ပယ်ချခြင်း) နဲ့ safe_encoding (client encoding က multibyte character တစ်ခုအတွင်းမှာ ASCII `\` ကို ခွင့်မပြုမှသာ ခွင့်ပြုခြင်း) တို့ ဖြစ်ပါတယ်။ safe_encoding က default setting ဖြစ်ပါတယ်။
standard-conforming string literal တစ်ခုမှာ `\` ဆိုတာ ဘယ်လိုပဲဖြစ်ဖြစ် `\` ကိုပဲ ဆိုလိုတာပါ ဆိုတာ သတိပြုပါ။ ဒီ parameter က escape string syntax (`E'...'`) အပါအဝင် standard-conforming မဖြစ်တဲ့ literal တွေရဲ့ ကိုင်တွယ်မှုကိုသာ သက်ရောက်ပါတယ်။
- **escape_string_warning (boolean)** — on ဖြစ်နေရင် — သာမန် string literal (`'...'` syntax) တစ်ခုမှာ backslash (`\`) ပေါ်လာပြီး standard_conforming_strings က off ဖြစ်နေရင် — warning တစ်ခု ထုတ်ပေးပါတယ်။ Default က on ဖြစ်ပါတယ်။
Backslash ကို escape အဖြစ် သုံးလိုတဲ့ application တွေကို — escape string syntax (`E'...'`) သုံးဖို့ ပြင်ဆင်သင့်ပါတယ် — အကြောင်းကတော့ SQL standard အရ — သာမန် string တွေရဲ့ default အပြုအမူက အခုအခါ backslash ကို သာမန် character တစ်ခုအဖြစ် သတ်မှတ်တာမို့ပါ။ ပြောင်းလဲဖို့ လိုအပ်တဲ့ code ကို ရှာဖွေရာမှာ အထောက်အကူဖြစ်စေဖို့ — ဒီ variable ကို enable လုပ်နိုင်ပါတယ်။
- **lo_compat_privileges (boolean)** — PostgreSQL 9.0 မတိုင်မီ ဗားရှင်းတွေမှာ large object တွေမှာ access privilege တွေ မရှိခဲ့ဘဲ — ဒါကြောင့် — user အားလုံးက အမြဲတမ်း ဖတ်နိုင် ရေးနိုင်ခဲ့ပါတယ်။ ဒီ variable ကို on သတ်မှတ်ခြင်းက — ဗားရှင်း အဟောင်းတွေနဲ့ လိုက်ဖက်မှုအတွက် — privilege စစ်ဆေးမှု အသစ်တွေကို disable လုပ်ပါတယ်။ Default က off ဖြစ်ပါတယ်။ Superuser တွေနဲ့ သင့်လျော်တဲ့ `SET` privilege ရှိတဲ့ user တွေသာ ဒီ setting ကို ပြောင်းနိုင်ပါတယ်။
ဒီ variable ကို သတ်မှတ်ခြင်းက large object တွေနဲ့ ဆက်စပ်တဲ့ security စစ်ဆေးမှု အားလုံးကို disable လုပ်တာ မဟုတ်ပါဘူး — PostgreSQL 9.0 မှာ default အပြုအမူ ပြောင်းလဲခဲ့တဲ့ စစ်ဆေးမှုတွေကိုသာ လုပ်ပါတယ်။
- **quote_all_identifiers (boolean)** — Database က SQL ကို ထုတ်လုပ်တဲ့အခါ — identifier တွေက (လက်ရှိ) keyword တွေ မဟုတ်ရင်တောင် — အားလုံးကို quote လုပ်ဖို့ အတင်းအကျပ် သတ်မှတ်ပါတယ်။ ဒါက `EXPLAIN` ရဲ့ output အပြင် `pg_get_viewdef` ကဲ့သို့ function တွေရဲ့ ရလဒ်တွေကိုပါ သက်ရောက်ပါတယ်။ [`pg_dump`](https://www.postgresql.org/docs/current/app-pgdump.html) နဲ့ [`pg_dumpall`](https://www.postgresql.org/docs/current/app-pg-dumpall.html) ရဲ့ `--quote-all-identifiers` option ကိုလည်း ကြည့်ပါ။
- **standard_conforming_strings (boolean)** — သာမန် string literal (`'...'`) တွေက backslash ကို SQL standard မှာ သတ်မှတ်ထားသလို — စာလုံးအတိုင်း (literally) ကိုင်တွယ်မကိုင်တွယ်ကို ဒါက ထိန်းချုပ်ပါတယ်။ PostgreSQL 9.1 ကတည်းက — default က on ဖြစ်ပါတယ် (ဗားရှင်း အဟောင်းတွေမှာ default က off ဖြစ်ခဲ့ပါတယ်)။ string literal တွေကို ဘယ်လို လုပ်ဆောင်မလဲ ဆုံးဖြတ်ဖို့ application တွေက ဒီ parameter ကို စစ်ဆေးနိုင်ပါတယ်။ ဒီ parameter ရှိနေခြင်းကို — escape string syntax (`E'...'`) ကို ထောက်ပံ့တယ်ဆိုတဲ့ အရိပ်အမြွက်အဖြစ်လည်း ယူနိုင်ပါတယ်။ Application တစ်ခုက backslash တွေကို escape character တွေအဖြစ် ကိုင်တွယ်စေလိုရင် — escape string syntax ([အပိုင်း 4.1.2.2](/docs/postgresql/sql-syntax-lexical)) ကို သုံးသင့်ပါတယ်။
- **synchronize_seqscans (boolean)** — ဒါက ကြီးမားတဲ့ table တွေရဲ့ sequential scan တွေ တစ်ခုနဲ့တစ်ခု synchronize ဖြစ်စေပါတယ် — ဒါမှ concurrent scan တွေက block တူတူကို အချိန် တစ်ခုတည်းလောက်မှာ ဖတ်ပြီး — I/O workload ကို မျှဝေနိုင်မှာပါ။ ဒါကို enable လုပ်ထားတဲ့အခါ — scan တစ်ခုက table အလယ်ကနေ စပြီး — လုပ်ဆောင်ဆဲ scan တွေရဲ့ လုပ်ဆောင်မှုနဲ့ synchronize ဖြစ်ဖို့ — row အားလုံးကို လွှမ်းခြုံနိုင်အောင် အဆုံးအထိ “ပတ်ပြီး” (wrap around) သွားနိုင်ပါတယ်။ ဒါက `ORDER BY` clause မပါတဲ့ query တွေ ပြန်ပေးတဲ့ row အစီအစဉ်မှာ မခန့်မှန်းနိုင်တဲ့ ပြောင်းလဲမှုတွေ ဖြစ်စေနိုင်ပါတယ်။ ဒီ parameter ကို off သတ်မှတ်ခြင်းက — sequential scan က table အစကနေ အမြဲ စတင်တဲ့ 8.3 မတိုင်မီ အပြုအမူကို အာမခံပါတယ်။ Default က on ဖြစ်ပါတယ်။

### 19.13.2. Platform and Client Compatibility (platform နှင့် client လိုက်ဖက်မှု)

- **transform_null_equals (boolean)** — on ဖြစ်နေရင် — `expr = NULL` (ဒါမှမဟုတ် `NULL = expr`) ပုံစံ expression တွေကို `expr IS NULL` အဖြစ် ကိုင်တွယ်ပါတယ် — ဆိုလိုတာက — `expr` က null တန်ဖိုးအဖြစ် အကဲဖြတ်ရင် true ပြန်ပြီး — မဟုတ်ရင် false ပြန်ပါတယ်။ `expr = NULL` ရဲ့ SQL-spec နဲ့ ကိုက်ညီတဲ့ မှန်ကန်တဲ့ အပြုအမူက — အမြဲတမ်း null (unknown) ပြန်တာပါ။ ဒါကြောင့် — ဒီ parameter ရဲ့ default က off ဖြစ်ပါတယ်။
ဒါပေမယ့် — Microsoft Access ထဲက filtered form တွေက null တန်ဖိုးတွေကို စမ်းသပ်ဖို့ `expr = NULL` သုံးပုံရတဲ့ query တွေ ထုတ်လုပ်ပါတယ် — ဒါကြောင့် — အဲဒီ interface ကို သုံးပြီး database ကို ဝင်ရောက်ရင် — ဒီ option ကို on လုပ်ချင်နိုင်ပါတယ်။ `expr = NULL` ပုံစံ expression တွေက (SQL standard အဓိပ္ပာယ်ဖွင့်ဆိုချက်ကို သုံးပြီး) အမြဲတမ်း null တန်ဖိုးကို ပြန်တာကြောင့် — သူတို့က သိပ်အသုံးမဝင်ဘဲ — သာမန် application တွေမှာ မကြာခဏ မပေါ်ပါဘူး၊ ဒါကြောင့် ဒီ option က လက်တွေ့မှာ အန္တရာယ် သိပ်မရှိပါဘူး။ ဒါပေမယ့် — user အသစ်တွေက null တန်ဖိုးများ ပါဝင်တဲ့ expression တွေရဲ့ အဓိပ္ပာယ် (semantics) အကြောင်း မကြာခဏ စိတ်ရှုပ်တတ်တာကြောင့် — ဒီ option ရဲ့ default က off ဖြစ်ပါတယ်။
ဒီ option က `= NULL` ဆိုတဲ့ ပုံစံ အတိအကျကိုသာ သက်ရောက်ပြီး — အခြား comparison operator တွေ ဒါမှမဟုတ် equals operator ပါဝင်တဲ့ expression တစ်ခုနဲ့ တွက်ချက်ပုံအရ တူညီတဲ့ အခြား expression တွေ (`IN` ကဲ့သို့) ကို မသက်ရောက်ပါဘူး ဆိုတာ သတိပြုပါ။ ဒါကြောင့် — ဒီ option က မကောင်းတဲ့ programming အတွက် ယေဘုယျ ဖြေရှင်းနည်း မဟုတ်ပါဘူး။
ဆက်စပ် အချက်အလက်အတွက် [အပိုင်း 9.2](/docs/postgresql/functions-comparison) ကို ကြည့်ပါ။
- **allow_alter_system (boolean)** — `allow_alter_system` ကို off သတ်မှတ်ထားတဲ့အခါ — `ALTER SYSTEM` command ကို လုပ်ဆောင်ရင် error တစ်ခု ပြန်ပေးပါတယ်။ ဒီ parameter ကို `postgresql.conf` file ထဲမှာ ဒါမှမဟုတ် server command line ပေါ်မှာသာ သတ်မှတ်နိုင်ပါတယ်။ Default တန်ဖိုးက on ဖြစ်ပါတယ်။
ဒီ setting ကို security feature တစ်ခုအဖြစ် မယူဆရပါဘူး ဆိုတာ သတိပြုပါ။ ဒါက `ALTER SYSTEM` command ကိုသာ disable လုပ်ပါတယ်။ Superuser တစ်ယောက်က အခြား SQL command တွေ သုံးပြီး configuration ကို ပြောင်းတာကို မတားဆီးပါဘူး။ Superuser တစ်ယောက်မှာ operating system အဆင့်မှာ shell command တွေ လုပ်ဆောင်ဖို့ နည်းလမ်း အများအပြား ရှိပြီး — ဒါကြောင့် — ဒီ setting ရဲ့ တန်ဖိုး ဘယ်လိုပဲဖြစ်ဖြစ် — `postgresql.auto.conf` ကို ပြင်ဆင်နိုင်ပါတယ်။
ဒီ setting ကို off လုပ်ခြင်းက — PostgreSQL ရဲ့ configuration ကို external tool တစ်ခုခုက စီမံခန့်ခွဲတဲ့ ပတ်ဝန်းကျင်တွေအတွက် ရည်ရွယ်ထားပါတယ်။ ဒီလို ပတ်ဝန်းကျင်တွေမှာ — စေတနာကောင်းတဲ့ superuser တစ်ယောက်က external tool ကို မသုံးဘဲ — configuration ကို ပြောင်းဖို့ `ALTER SYSTEM` ကို မှားယွင်းစွာ သုံးမိနိုင်ပါတယ်။ ဒါက — external tool က configuration ကို update လုပ်တဲ့အခါ နောက်ပိုင်း အချိန်တစ်ခုမှာ အဲဒီ ပြောင်းလဲမှုကို ပြန်လည် ဖျက်ဆီး (overwrite) လိုက်တာကဲ့သို့သော — မရည်ရွယ်တဲ့ အပြုအမူတွေ ဖြစ်စေနိုင်ပါတယ်။ ဒီ parameter ကို off သတ်မှတ်ခြင်းက — ဒီလို အမှားတွေကို ရှောင်ရှားဖို့ အထောက်အကူဖြစ်နိုင်ပါတယ်။
ဒီ parameter က `ALTER SYSTEM` ရဲ့ အသုံးပြုမှုကိုသာ ထိန်းချုပ်ပါတယ်။ `postgresql.auto.conf` ထဲမှာ သိမ်းဆည်းထားတဲ့ setting တွေက — `allow_alter_system` ကို off သတ်မှတ်ထားရင်တောင် — အသက်ဝင်ပါတယ်။
