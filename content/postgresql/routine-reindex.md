## 24.2. Routine Reindexing (ပုံမှန် reindexing ပြုလုပ်ခြင်း)

အခြေအနေ အချို့မှာ — indexes တွေကို [REINDEX](/docs/postgresql/sql-reindex) command ဒါမှမဟုတ် တစ်ခုချင်းစီ ပြန်လည် တည်ဆောက်ခြင်း အဆင့်တွေ အတွဲလိုက် လုပ်ဆောင်ခြင်းအားဖြင့် — အခါအားလျော်စွာ ပြန်လည် တည်ဆောက် (rebuild) လုပ်တာက အကျိုးရှိပါတယ်။

လုံးဝ ဗလာ ဖြစ်သွားတဲ့ B-tree index pages တွေကို ပြန်လည် အသုံးပြုဖို့ ပြန်လည် ရယူပါတယ်။ ဒါပေမယ့် — space ကို ထိရောက်မှု မရှိဘဲ အသုံးပြုမိနိုင်တဲ့ ဖြစ်နိုင်ခြေ တစ်ခု ရှိနေဆဲပါ: page တစ်ခုပေါ်က index keys တွေထဲက အနည်းငယ်ကလွဲရင် အားလုံး ဖျက်လိုက်ခံရရင် — page က သတ်မှတ် ခွဲဝေခံထားရတာ (allocated) ဆက်လက် ဖြစ်နေပါတယ်။ ဒါကြောင့် — range တစ်ခုချင်းစီထဲက keys တွေရဲ့ အများစု — ဒါပေမယ့် အားလုံး မဟုတ်ဘဲ — နောက်ဆုံးမှာ ဖျက်ပစ်ခံရတဲ့ အသုံးပြုမှု ပုံစံ (usage pattern) တစ်မျိုးမှာ space အသုံးပြုမှု ညံ့ဖျင်းတာ တွေ့ရပါလိမ့်မယ်။ ဒီလို အသုံးပြုမှု ပုံစံတွေအတွက် — အခါအားလျော်စွာ reindexing ပြုလုပ်တာကို အကြံပြုပါတယ်။

Non-B-tree indexes တွေမှာ bloat (ဖောင်းပွမှု) ဖြစ်နိုင်ခြေကိုတော့ ကောင်းစွာ သုတေသန မပြုရသေးပါဘူး။ Non-B-tree index type တစ်ခုခုကို သုံးတဲ့အခါ — index ရဲ့ physical size (ရုပ်ပိုင်း အရွယ်အစား) ကို အခါအားလျော်စွာ စောင့်ကြည့်တာက အကြံကောင်း တစ်ခု ဖြစ်ပါတယ်။

ထို့အပြင် — B-tree indexes တွေအတွက်ဆိုရင် — အသစ် တည်ဆောက်ထားတဲ့ index တစ်ခုက — update အကြိမ်များစွာ ပြုလုပ်ခဲ့ရတဲ့ index တစ်ခုထက် — ဝင်ရောက် အသုံးပြုရတာ အနည်းငယ် ပိုမြန်ပါတယ် — အကြောင်းကတော့ — အသစ် တည်ဆောက်ထားတဲ့ index တစ်ခုမှာ logically adjacent (ယုတ္တိအရ ကပ်လျက်) ဖြစ်တဲ့ pages တွေက ပုံမှန်အားဖြင့် physically adjacent (ရုပ်ပိုင်းအရ ကပ်လျက်) လည်း ဖြစ်နေလို့ပါ။ (ဒီအချက်က non-B-tree indexes တွေနဲ့တော့ မသက်ဆိုင်ပါဘူး။) Access speed (ဝင်ရောက် အသုံးပြုမှု မြန်နှုန်း) ကို တိုးတက်စေဖို့အတွက်ပဲ — အခါအားလျော်စွာ reindex လုပ်တာက အကျိုးရှိနိုင်ပါတယ်။

[REINDEX](/docs/postgresql/sql-reindex) ကို ကိစ္စ အားလုံးမှာ ဘေးကင်းစွာ ရော လွယ်ကူစွာပါ သုံးနိုင်ပါတယ်။ ဒီ command က default အားဖြင့် `ACCESS EXCLUSIVE` lock တစ်ခု လိုအပ်တာမို့ — `SHARE UPDATE EXCLUSIVE` lock တစ်ခုကိုပဲ လိုအပ်တဲ့ — သူ့ရဲ့ `CONCURRENTLY` option နဲ့ execute လုပ်တာက မကြာခဏဆိုသလို ပိုနှစ်သက်ဖွယ် ကောင်းပါတယ်။
