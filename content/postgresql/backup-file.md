## 25.2. File System Level Backup (file system အဆင့် backup)

အခြားရွေးချယ်စရာ backup နည်းဗျူဟာ တစ်ခုကတော့ — PostgreSQL က database ထဲက data တွေကို သိုလှောင်ဖို့ သုံးတဲ့ ဖိုင်တွေကို တိုက်ရိုက် ကူးယူ (copy) တာ ဖြစ်ပါတယ်; ဒီဖိုင်တွေ ဘယ်နေရာမှာ တည်ရှိလဲဆိုတာကို [အပိုင်း 18.2](/docs/postgresql/creating-cluster) မှာ ရှင်းပြထားပါတယ်။ File system backups တွေ လုပ်ဖို့ သင်ကြိုက်နှစ်သက်တဲ့ ဘယ်နည်းလမ်းကိုမဆို သုံးနိုင်ပါတယ်; ဥပမာ:

```sql
tar -cf backup.tar /usr/local/pgsql/data
```

ဒါပေမယ့် — ဒီနည်းလမ်းကို လက်တွေ့မှာ အသုံးမပြုနိုင်အောင် ဒါမှမဟုတ် pg_dump နည်းလမ်းထက် အနည်းဆုံး အားနည်းစေတဲ့ — ကန့်သတ်ချက် နှစ်ခု ရှိပါတယ်:

1. အသုံးပြုလို့ ရတဲ့ backup တစ်ခု ရရှိဖို့ — database server ကို ရပ်တန့် (shut down) ထားရပါမယ်။ Connections တွေ အားလုံးကို ခွင့်မပြုတာလို — ထက်ဝက် ဆောင်ရွက်မှု (half-way measure) တွေက အလုပ်လုပ်မှာ မဟုတ်ပါဘူး (တစိတ်တပိုင်းအားဖြင့် — `tar` နဲ့ အလားတူ tools တွေက file system ရဲ့ အခြေအနေကို atomic snapshot (တစ်ခဲနက် ပုံရိပ်) အနေနဲ့ မယူလို့ ဖြစ်ပြီး — server အတွင်းက buffering (ကြားခံ သိုလှောင်မှု) ကြောင့်လည်း ဖြစ်ပါတယ်)။ Server ကို ရပ်တန့်ခြင်းအကြောင်း အချက်အလက်ကို [အပိုင်း 18.5](/docs/postgresql/server-shutdown) မှာ တွေ့နိုင်ပါတယ်။ ပြောစရာ မလိုအောင် — data တွေကို restore မလုပ်ခင် server ကိုလည်း ရပ်တန့်ထားဖို့ လိုပါတယ်။
2. Database ရဲ့ file system ဖွဲ့စည်းပုံ (layout) အသေးစိတ်ကို လေ့လာထားတယ်ဆိုရင် — သက်ဆိုင်ရာ ဖိုင်တွေ ဒါမှမဟုတ် directories တွေကနေ tables တချို့ ဒါမှမဟုတ် databases တချို့ကိုပဲ backup ဒါမှမဟုတ် restore လုပ်ဖို့ ကြိုးစားချင်စိတ် ဖြစ်မိနိုင်ပါတယ်။ ဒါက အလုပ်လုပ်မှာ မဟုတ်ပါဘူး — အကြောင်းကတော့ ဒီဖိုင်တွေထဲမှာ ပါဝင်တဲ့ အချက်အလက်တွေက — transaction တွေ အားလုံးရဲ့ commit status (commit အခြေအနေ) ပါဝင်တဲ့ — commit log ဖိုင်တွေ ဖြစ်တဲ့ `pg_xact/*` မရှိဘဲ — အသုံးမပြုနိုင်လို့ပါ။ Table ဖိုင်တစ်ခုက ဒီအချက်အလက်နဲ့မှသာ အသုံးပြုနိုင်တာ ဖြစ်ပါတယ်။ ဟုတ်ပါတယ် — table တစ်ခုတည်းနဲ့ ဆက်စပ်နေတဲ့ `pg_xact` data ကိုပဲ restore လုပ်တာကလည်း မဖြစ်နိုင်ပါဘူး — အကြောင်းကတော့ အဲဒါက database cluster ထဲက တခြား tables တွေ အားလုံးကို အသုံးမဝင်တော့အောင် လုပ်လိုက်မှာ မို့ပါ။ ဒါကြောင့် — file system backups တွေက database cluster တစ်ခုလုံးရဲ့ — အပြည့်အဝ backup နဲ့ restore အတွက်ပဲ အလုပ်လုပ်ပါတယ်။

File-system backup ရဲ့ အခြားရွေးချယ်စရာ နည်းလမ်းတစ်ခုကတော့ — file system က အဲဒီ လုပ်ဆောင်ချက်ကို ထောက်ပံ့တယ်ဆိုရင် (ပြီးတော့ ၎င်းကို မှန်ကန်စွာ implement (အကောင်အထည်ဖော်) လုပ်ထားတာကို ယုံကြည်ဖို့ ဆန္ဒ ရှိတယ်ဆိုရင်) — data directory ရဲ့ “consistent snapshot” (တသမတ်တည်း ဖြစ်သော snapshot) တစ်ခုကို ဖန်တီးတာ ဖြစ်ပါတယ်။ ပုံမှန် လုပ်ငန်းစဉ်ကတော့ — database ပါဝင်တဲ့ volume ရဲ့ “frozen snapshot” (အေးခဲ ပုံရိပ်) တစ်ခုကို ဖန်တီးပြီး — snapshot ကနေ data directory တစ်ခုလုံးကို (အစိတ်အပိုင်းတွေပဲ မဟုတ်ဘဲ — အပေါ်မှာ ကြည့်ပါ) backup device (backup စက်) တစ်ခုဆီ ကူးယူပြီး — frozen snapshot ကို လွှတ်ပေးတာ ဖြစ်ပါတယ်။ ဒါက database server run နေတုန်းမှာတောင် အလုပ်လုပ်ပါလိမ့်မယ်။ ဒါပေမယ့် — ဒီနည်းနဲ့ ဖန်တီးထားတဲ့ backup တစ်ခုက database ဖိုင်တွေကို — database server ကို စနစ်တကျ ရပ်တန့်မထားခဲ့သလိုမျိုး အခြေအနေနဲ့ သိမ်းဆည်းပေးပါတယ်; ဒါကြောင့် — backup လုပ်ထားတဲ့ data ပေါ်မှာ database server ကို စတင်တဲ့အခါ — အရင် server instance က ပျက်ကျ (crash) ခဲ့တယ်လို့ ထင်မှတ်ပြီး — WAL log ကို ပြန်လည် ဖွင့်သုံး (replay) ပါလိမ့်မယ်။ ဒါက ပြဿနာ မဟုတ်ပါဘူး; ဒါကို သတိထား နေရုံပါပဲ (ပြီးတော့ WAL ဖိုင်တွေကို သင့် backup ထဲမှာ ထည့်သွင်းဖို့ သေချာ လုပ်ပါ)။ ပြန်လည် နာလန်ထူချိန် (recovery time) ကို လျှော့ချဖို့ — snapshot မယူခင် `CHECKPOINT` တစ်ခုကို လုပ်ဆောင်နိုင်ပါတယ်။

သင့် database က file systems အများအပြားပေါ်မှာ ပျံ့နှံ့ နေတယ်ဆိုရင် — volumes တွေ အားလုံးရဲ့ အတိအကျ တစ်ပြိုင်နက် (exactly-simultaneous) frozen snapshots တွေကို ရယူဖို့ နည်းလမ်း မရှိနိုင်ပါဘူး။ ဥပမာ — သင့် data ဖိုင်တွေနဲ့ WAL log က disk အမျိုးမျိုးပေါ်မှာ ရှိနေရင် ဒါမှမဟုတ် tablespaces တွေက file systems အမျိုးမျိုးပေါ်မှာ ရှိနေရင် — snapshots တွေက တစ်ပြိုင်နက် ဖြစ်ရမှာ မို့လို့ — snapshot backup ကို သုံးဖို့ မဖြစ်နိုင်တာ ဖြစ်နိုင်ပါတယ်။ ဒီလို အခြေအနေမျိုးမှာ consistent-snapshot technique ကို မယုံကြည်ခင် — သင့် file system documentation (မှတ်တမ်း) ကို အလွန် ဂရုတစိုက် ဖတ်ပါ။

တစ်ပြိုင်နက် snapshots တွေ မဖြစ်နိုင်ဘူးဆိုရင် — ရွေးချယ်စရာ တစ်ခုကတော့ frozen snapshots တွေ အားလုံးကို တည်ဆောက်ဖို့ လုံလောက်တဲ့ အချိန်ကြာကြာ database server ကို ရပ်တန့်ထားတာ ဖြစ်ပါတယ်။ နောက် ရွေးချယ်စရာ တစ်ခုကတော့ — continuous archiving base backup တစ်ခု ([အပိုင်း 25.3.2](https://www.postgresql.org/docs/current/continuous-archiving.html#BACKUP-BASE-BACKUP)) ကို လုပ်ဆောင်တာ ဖြစ်ပါတယ် — အကြောင်းကတော့ ဒီလို backups တွေက backup အတွင်း file system ပြောင်းလဲမှုတွေရဲ့ သက်ရောက်မှုကနေ ကင်းလွတ်လို့ပါ။ ဒါက backup လုပ်ငန်းစဉ် အတွင်းမှာပဲ continuous archiving ကို enable (ဖွင့်) လုပ်ဖို့ လိုအပ်ပြီး — restore ကို continuous archive recovery ([အပိုင်း 25.3.5](https://www.postgresql.org/docs/current/continuous-archiving.html#BACKUP-PITR-RECOVERY)) သုံးပြီး လုပ်ဆောင်ပါတယ်။

နောက်ထပ် ရွေးချယ်စရာ တစ်ခုကတော့ — file system backup တစ်ခုကို လုပ်ဆောင်ဖို့ rsync ကို သုံးတာ ဖြစ်ပါတယ်။ ဒါကို — database server run နေတုန်း rsync ကို အရင် run လုပ်ပြီး — နောက်ပိုင်းမှာ `rsync --checksum` တစ်ခုကို လုပ်ဖို့ လုံလောက်တဲ့ အချိန်ကြာကြာ database server ကို ရပ်တန့်ပြီး — လုပ်ဆောင်ပါတယ်။ (`--checksum` က မဖြစ်မနေ လိုအပ်ပါတယ် — အကြောင်းကတော့ `rsync` မှာ ဖိုင် ပြုပြင်ချိန် (file modification-time) ၏ granularity (အသေးစိတ် အတိုင်းအတာ) က တစ်စက္ကန့်ပဲ ရှိလို့ပါ။) ဒုတိယ rsync က ပထမတစ်ခုထက် ပိုမြန်ပါလိမ့်မယ် — အကြောင်းကတော့ လွှဲပြောင်းဖို့ data အနည်းငယ်ပဲ ကျန်တာမို့ — ပြီးတော့ server က ရပ်တန့်ထားလို့ — အဆုံး ရလဒ်က consistent ဖြစ်နေမှာ မို့ပါ။ ဒီနည်းလမ်းက file system backup တစ်ခုကို — downtime (ရပ်နားချိန်) အနည်းဆုံးနဲ့ လုပ်ဆောင်ခွင့် ပေးပါတယ်။

File system backup တစ်ခုက SQL dump တစ်ခုထက် ပုံမှန်အားဖြင့် ပိုကြီးမယ်ဆိုတာ သတိပြုပါ။ (ဥပမာ — pg_dump က indexes တွေရဲ့ ပါဝင်စရာတွေကို dump လုပ်စရာ မလိုဘဲ — ၎င်းတို့ကို ပြန်လည် ဖန်တီးဖို့ commands တွေပဲ လိုပါတယ်။) ဒါပေမယ့် — file system backup တစ်ခု ယူတာက ပိုမြန်နိုင်ပါတယ်။
