## 11.12. Examining Index Usage (index အသုံးပြုမှု စစ်ဆေးခြင်း)

PostgreSQL မှာ index တွေက maintenance (ထိန်းသိမ်းမှု) ဒါမှမဟုတ် tuning (ချိန်ညှိမှု) မလိုအပ်ပေမယ့် — လက်တွေ့ကျတဲ့ query workload (query ဝန်ထုပ်) တွေမှာ ဘယ် index တွေကို တကယ် အသုံးပြုနေလဲဆိုတာ စစ်ဆေးဖို့ကတော့ အရေးကြီးပါသေးတယ်။ Query တစ်ခုချင်းစီအတွက် index အသုံးပြုမှုကို [EXPLAIN](https://www.postgresql.org/docs/current/sql-explain.html) command နဲ့ စစ်ဆေးပါတယ် — ဒီရည်ရွယ်ချက်အတွက် အသုံးပြုပုံကို [အပိုင်း 14.1](https://www.postgresql.org/docs/current/using-explain.html) မှာ သရုပ်ပြထားပါတယ်။ Run နေတဲ့ server တစ်ခုမှာ index အသုံးပြုမှုရဲ့ အလုံးစုံ statistics (စာရင်းအင်း အချက်အလက်များ) တွေကို စုဆောင်းဖို့လည်း ဖြစ်နိုင်ပြီး — အဲဒါကို [အပိုင်း 27.2](https://www.postgresql.org/docs/current/monitoring-stats.html) မှာ ဖော်ပြထားပါတယ်။

ဘယ် index တွေကို ဖန်တီးရမယ်ဆိုတာ ဆုံးဖြတ်ဖို့ ယေဘုယျကျတဲ့ နည်းလမ်းစဉ် (general procedure) တစ်ခုကို ရေးဆွဲဖို့ကတော့ ခက်ခဲပါတယ်။ အရင်က section တွေရဲ့ ဥပမာတွေမှာ ပြသခဲ့တဲ့ ပုံမှန် အခြေအနေ (typical case) တွေ အတော်များများ ရှိပါတယ်။ စမ်းသပ်မှု (experimentation) တွေ အတော်များများ ပြုလုပ်ဖို့ မကြာခဏ လိုအပ်တတ်ပါတယ်။ ဒီ section ရဲ့ ကျန်တဲ့ အပိုင်းတွေမှာ အဲဒီအတွက် အကြံပြုချက် (tip) တချို့ ဖော်ပြပေးထားပါတယ် —

- `ANALYZE` ကို အရင်ဆုံး run ပါ။ ဒီ command က table ထဲက တန်ဖိုးတွေရဲ့ ဖြန့်ကျက်မှု (distribution) နဲ့ ပတ်သက်တဲ့ statistics တွေကို စုဆောင်းပေးပါတယ်။ ဒီအချက်အလက်တွေက — query တစ်ခုက ပြန်ပေးမယ့် row အရေအတွက်ကို ခန့်မှန်းဖို့ လိုအပ်ပြီး — planner (query တစ်ခုအတွက် အကောင်းဆုံး လုပ်ဆောင်မှု အစီအစဉ်ကို ရွေးချယ်ပေးတဲ့ အစိတ်အပိုင်း) က ဖြစ်နိုင်တဲ့ query plan တစ်ခုချင်းစီအတွက် လက်တွေ့ကျတဲ့ cost (ကုန်ကျစရိတ်) တွေ သတ်မှတ်နိုင်ဖို့လည်း လိုအပ်ပါတယ်။ တကယ့် statistics တွေ မရှိတဲ့အခါ — မမှန်ဖို့ သေချာနီးပါး ဖြစ်တဲ့ default တန်ဖိုး (ပုံသေတန်ဖိုး) တချို့ကို ယူဆထားပါတယ်။ ဒါကြောင့် — `ANALYZE` run မထားဘဲ application တစ်ခုရဲ့ index အသုံးပြုမှုကို စစ်ဆေးတာက အကျိုးမရှိတဲ့ လုပ်ရပ်တစ်ခုပါ။ နောက်ထပ် အချက်အလက်တွေအတွက် အပိုင်း 24.1.3 နဲ့ အပိုင်း 24.1.6 ကို ကြည့်ပါ။

- စမ်းသပ်မှုတွေအတွက် တကယ့် data (real data) တွေကို သုံးပါ။ Index တွေ တည်ဆောက်ရာမှာ test data (စမ်းသပ်မှု data) တွေကို သုံးတာက — အဲဒီ test data အတွက် ဘယ် index တွေ လိုလဲဆိုတာကိုပဲ ပြောပြနိုင်ပြီး — အဲဒီလောက်ပဲ ဖြစ်ပါတယ်။

  အထူးသဖြင့် — အလွန် သေးငယ်တဲ့ test data set တွေကို သုံးတာက ဆိုးရွားလှပါတယ်။ Row 100000 ထဲက 1000 ခုကို ရွေးချယ်တာမျိုးက index အတွက် သင့်လျော်တဲ့ ကိုယ်စားလှယ်လောင်း (candidate) ဖြစ်နိုင်ပေမယ့် — row 100 ထဲက 1 ခုကို ရွေးချယ်တာကတော့ ခဲယဉ်းပါတယ် — ဘာကြောင့်လဲဆိုတော့ — row 100 က disk page (disk စာမျက်နှာ) တစ်ခုတည်းထဲမှာ ကိုက်ညီနိုင်လောက်ပြီး — disk page တစ်ခုတည်းကို sequential (အစဉ်လိုက်) ဖတ်ယူတာထက် သာလွန်နိုင်တဲ့ plan ဆိုတာ မရှိလို့ပါ။

  ပြီးတော့ — application က production (လက်တွေ့ အသုံးပြုမှု) အဆင့်ကို မရောက်သေးတဲ့အခါ မကြာခဏဆိုသလို ရှောင်လွှဲလို့ မရတတ်တဲ့ test data တွေ ဖန်တီးတဲ့အခါမှာလည်း သတိထားပါ။ တစ်ခုနဲ့တစ်ခု အလွန် ဆင်တူတဲ့ တန်ဖိုးတွေ၊ လုံးဝ ကျပန်း (random) တန်ဖိုးတွေ ဒါမှမဟုတ် sort လုပ်ပြီးသား အစဉ်အတိုင်း ထည့်သွင်းထားတဲ့ တန်ဖိုးတွေက — တကယ့် data မှာ ရှိမယ့် ဖြန့်ကျက်မှုကနေ ဝေးရာကို statistics တွေကို ဘက်လိုက် (skew) ဖြစ်စေပါတယ်။

- Index တွေကို အသုံးမပြုတဲ့ အခြေအနေမျိုးမှာ — စမ်းသပ်မှုအတွက် သူတို့ကို အတင်းအကျပ် အသုံးပြုစေတာ အသုံးဝင်နိုင်ပါတယ်။ Plan type (plan အမျိုးအစား) အမျိုးမျိုးကို ပိတ်ထားနိုင်တဲ့ run-time parameter (runtime မှာ သတ်မှတ်နိုင်သော parameter) တွေ ရှိပါတယ် (အပိုင်း 19.7.1 ကို ကြည့်ပါ)။ ဥပမာ — အခြေခံအကျဆုံး plan တွေဖြစ်တဲ့ sequential scan (table တစ်ခုလုံးကို row အလိုက် စဉ်ဆက်တိုက် ဖတ်ခြင်း) (`enable_seqscan`) နဲ့ nested-loop join (အပြင်က loop ရဲ့ row တစ်ခုချင်းစီအတွက် အတွင်းက loop ကို scan လုပ်တဲ့ join နည်း) (`enable_nestloop`) တို့ကို ပိတ်လိုက်ရင် — system က တခြား plan တစ်ခုကို သုံးဖို့ အတင်းအကျပ် ဖြစ်စေပါတယ်။ အဲဒီလို လုပ်ပြီးမှ system က sequential scan ဒါမှမဟုတ် nested-loop join ကိုပဲ ထပ်ရွေးချယ်နေသေးရင် — index ကို အသုံးမပြုရတဲ့ ပိုပြီး အခြေခံကျတဲ့ အကြောင်းရင်းတစ်ခု ရှိနေဖို့ များပါတယ် — ဥပမာ — query ရဲ့ condition (စစ်ဆေးမှု အခြေအနေ) က index နဲ့ မကိုက်ညီတာမျိုးပါ။ (ဘယ်လို query အမျိုးအစားက ဘယ်လို index အမျိုးအစားကို သုံးနိုင်လဲဆိုတာကို အရင်က section တွေမှာ ရှင်းပြထားပါတယ်။)

- Index အသုံးပြုမှုကို အတင်းအကျပ် ပြုလုပ်တဲ့အခါ index ကို တကယ် အသုံးပြုဖြစ်သွားရင် — ဖြစ်နိုင်ခြေ နှစ်မျိုး ရှိပါတယ် — system က မှန်ပြီး index သုံးတာက တကယ်ပဲ မသင့်လျော်တာမျိုး ဖြစ်နိုင်သလို — ဒါမှမဟုတ် — query plan တွေရဲ့ cost estimate (ကုန်ကျစရိတ် ခန့်မှန်းချက်) တွေက လက်တွေ့ကို ထင်ဟပ်မနေတာလည်း ဖြစ်နိုင်ပါတယ်။ ဒါကြောင့် — index ပါတဲ့ အနေအထားနဲ့ရော မပါဘဲနဲ့ပါ query ကို အချိန် တိုင်းတာကြည့်သင့်ပါတယ်။ `EXPLAIN ANALYZE` command က ဒီနေရာမှာ အသုံးဝင်နိုင်ပါတယ်။

- Cost estimate တွေ မှားနေတယ်လို့ ပေါ်ပေါက်လာရင်လည်း — ဖြစ်နိုင်ခြေ နှစ်မျိုးပဲ ရှိပါသေးတယ်။ Total cost (စုစုပေါင်း ကုန်ကျစရိတ်) ကို — plan node (plan ထဲက အဆင့်တစ်ခု) တစ်ခုချင်းစီရဲ့ per-row cost (row တစ်ခုစီအတွက် ကုန်ကျစရိတ်) တွေနဲ့ — အဲဒီ plan node ရဲ့ selectivity estimate (condition နဲ့ ကိုက်ညီတဲ့ row အချိုးအစား ခန့်မှန်းချက်) ကို မြှောက်ပြီး တွက်ချက်ပါတယ်။ Plan node တွေအတွက် ခန့်မှန်းထားတဲ့ cost တွေကို run-time parameter တွေနဲ့ ချိန်ညှိနိုင်ပါတယ် (အပိုင်း 19.7.2 မှာ ဖော်ပြထားပါတယ်)။ Selectivity estimate မတိကျတာက — statistics မလုံလောက်လို့ ဖြစ်ပါတယ်။ Statistics စုဆောင်းမှု ဆိုင်ရာ parameter တွေကို ချိန်ညှိပြီး ဒါကို တိုးတက်အောင် လုပ်နိုင်ဖို့ ဖြစ်နိုင်ခြေ ရှိပါတယ် (`ALTER TABLE` ကို ကြည့်ပါ)။

  Cost တွေကို ပိုသင့်လျော်အောင် ချိန်ညှိဖို့ မအောင်မြင်ဘူးဆိုရင် — index အသုံးပြုမှုကို အတိအကျ အတင်းအကျပ် ပြုလုပ်တာကိုပဲ အားကိုးရနိုင်ပါတယ်။ ဒီပြဿနာကို စူးစမ်းလေ့လာဖို့ PostgreSQL developer တွေကို ဆက်သွယ်ဖို့လည်း စဉ်းစားချင်စိတ် ရှိနိုင်ပါတယ်။
